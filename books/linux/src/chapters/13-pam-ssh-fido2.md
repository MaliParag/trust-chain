# PAM, Hybrid Enterprise Identity, OpenSSH Certificates, and regreSSHion

## Overview

* **Link in the Chain:** Closes Part III by governing human and administrative entry into Linux hosts across local consoles and remote networks (`Linux-PAM`, `SSSD` `KCM`/AD/OIDC, `Himmelblau` Entra ID, OpenSSH Certificates, `FIDO2` hardware authenticators, and `sshd` multi-binary privilege separation).
* **Core Security Invariant:** Host entry succeeds only when ordered `PAM` `auth` and `account` stacks both pass without `sufficient` or `PAM_IGNORE` bypasses, `SSSD` cryptographically verifies KDC tickets (`krb5_validate`) or OIDC assertions, and `sshd` validates short-lived CA-signed User Certificates paired with hardware-resident `FIDO2` (`sk-ssh-ed25519@openssh.com` `verify-required`) signatures inside per-connection `ASLR`-randomized `sshd-session` and `sshd-auth` binaries.
* **Deployment Profile Matrix:** Enterprise mutable fleets (`RHEL`, `Ubuntu`, `SUSE`, `Debian`) integrate `PAM` + `SSSD` (`FreeIPA`, Active Directory GPOs, `sssd-kcm`) or `Himmelblau`/`aadsshlogin` (Microsoft Entra ID) with CA-signed OpenSSH certificates; immutable container OSes omit `sshd` and `PAM` completely (`Talos Linux`), isolate admin shells inside dedicated host containers (`Bottlerocket`), or enforce certificate-only `sshd` (`CoreOS`).
* **Trusted Computing Base (TCB):** Master `sshd` listener, `sshd-session` and `sshd-auth` (`OpenSSH 9.8-10.0+`) privilege-separated binaries, `TrustedUserCAKeys` offline or HSM SSH CA, `CTAP2` `FIDO2` authenticator firmware, `libpam` and `/etc/pam.d/*` modules, and `SSSD` / `Himmelblau` responder and backend processes.
* **Integration Seam & Handoff:** Authenticates human operators without static `~/.ssh/authorized_keys` sprawl, world-readable `/tmp/krb5cc_*` ticket files, or harvestable laptop private keys, while isolating pre-authentication `sshd` parsers from `glibc` signal races (`regreSSHion`); hands off container, AI sandbox, and `SPIFFE` machine workload isolation to Part IV ([Chapter 14](14-containers-escapes.md)).

## Problem Statement & Threat Model

Every Linux fleet eventually confronts an operational and cryptographic crisis at its administrative perimeter [74, 75, 76]. In small deployments, engineers append raw `ssh-ed25519` public keys to `~/.ssh/authorized_keys` across dozens of servers, type `yes` past Trust-On-First-Use (`TOFU`) host-key warnings (`The authenticity of host ... can't be established`), set `ForwardAgent yes` so bastion jump boxes can reach private subnets, and store unencrypted `~/.ssh/id_ed25519` files on developer laptops. Scale that workflow to five thousand cloud instances and three hundred engineers, and four structural failures converge simultaneously [74, 75, 391, 392]:

First, *static key immortality and revocation blindness*: when an engineer changes teams, leaves the organization, or loses a laptop, stale `authorized_keys` lines persist indefinitely on forgotten bastions, golden VM snapshots, and configuration drifts because raw SSH public keys encode neither an expiration timestamp (`valid_before`) nor principal attribution; meanwhile, cloud auto-scaling groups recycle private IP addresses hourly, training engineers under `TOFU` to click past genuine Man-in-the-Middle (`MITM`) host-key mismatches [74, 393]. Second, *laptop key exfiltration and `SSH_AUTH_SOCK` hijacking*: any local malware or prompt-injected coding agent ([Chapter 17](17-ai-agent-sandboxes.md)) on an engineer's workstation copies `~/.ssh/id_ed25519` or silently signs challenges over `$SSH_AUTH_SOCK`, while `ssh -A` (`ForwardAgent yes`) exposes a live UNIX domain signing socket (`/tmp/ssh-XXXX/agent.<pid>`) on the remote jump host where any attacker holding `UID 0` can impersonate the engineer laterally across the entire fleet, or even achieve remote code execution back on the engineer's laptop via forwarded `PKCS#11` library loads (`CVE-2023-38408` [391, 394])!

Third, *`PAM` state-machine fragility and hybrid directory drift*: bridging Linux servers into enterprise Active Directory Kerberos realms (`SSSD` [73, 395]) or cloud identity providers (`Microsoft Entra ID`, `Okta` via `Himmelblau` or `aadsshlogin` [396, 397]) funnels credential checks through `Linux-PAM` (`/etc/pam.d/*`), where placing a single `sufficient` directive one line too high bypasses account lockouts (`pam_faillock` [398]), leaving `user_readenv=1` enabled in `pam_env` lets remote SSH users forge physical console seats (`CVE-2025-6018` [392, 399]), and storing Kerberos tickets in `/tmp/krb5cc_*` exposes credentials across shared `/tmp` namespaces [400]. Fourth, *unauthenticated pre-auth `sshd` exposure*: because TCP port `22` frequently faces untrusted networks directly, any memory-corruption race inside `sshd` prior to authentication, exemplified by Qualys's July 2024 `regreSSHion` (`CVE-2024-6387` [76]), threatens unauthenticated remote root takeover before `PAM`, `FIDO2`, or `SELinux` ever execute a single check!

## Kernel & Userspace Mechanics

### `Linux-PAM` Stack Semantics, Control-Flag Disasters, and the 2025 `PAM` CVE Wave

Whenever `login`, `sshd` (`UsePAM yes`), `su`, `polkitd`, or `systemd --user` authenticates a user or opens a session, `libpam` (`pam.conf(5)` [401, 402]) evaluates a service-specific policy file under `/etc/pam.d/<service>` across four independent management groups: `auth` (verifying *who* the caller is via password, Kerberos ticket, OIDC flow, or local `FIDO2` `pam_u2f.so` [403]), `account` (verifying *whether* that authenticated principal is currently authorized to enter: password/account expiration, `/etc/nologin`, `pam_faillock` lockout counters, and Active Directory GPO or FreeIPA Host-Based Access Control `HBAC`), `session` (constructing and tearing down session state: `pam_keyinit.so` allocating a fresh `@s` kernel keyring from [Chapter 12](12-keyrings-systemd-creds.md), `pam_limits.so`, `pam_namespace.so`, and `pam_systemd.so` registering the user's `systemd-logind` session scope and `cgroup v2` slice), and `password` (updating authentication tokens) [401, 402].

Inside each management group, `libpam` executes listed `.so` modules top-to-bottom under an explicit return-value state machine (`requisite`, `required`, `sufficient`, `optional`, or bracketed action rules such as `[success=1 default=ignore]` and `[default=die]` [402]):

| `PAM` Control Keyword | Equivalent Bracket Rule in `pam.conf(5)` | Behavior on `PAM_SUCCESS` | Behavior on Module Failure (`PAM_AUTH_ERR`, etc.) | Classic Misconfiguration Trap |
|---|---|---|---|---|
| `requisite` | `[success=ok new_authtok_reqd=ok ignore=ignore default=die]` | Records pass; continues down stack | Aborts the entire group *immediately* and returns first failure code | Placing slow network modules *above* local `requisite` checks leaks user-enumeration timing [402] |
| `required` | `[success=ok new_authtok_reqd=ok ignore=ignore default=bad]` | Records pass; continues down stack | Latches failure bit internally *yet executes remaining modules* before failing | Omitting `required pam_deny.so` at bottom of bracket-jumping stacks permits `PAM_IGNORE` fallthrough [402, 404] |
| `sufficient` | `[success=done new_authtok_reqd=done default=ignore]` | Terminates group *immediately* with overall success if *no prior* `required` failed! | Failure is *completely ignored*; evaluation continues to next module | Placing `sufficient` *above* `pam_faillock` (`preauth`) or `pam_nologin` bypasses lockout and maintenance gates [398, 402] |
| `optional` | `[success=ok new_authtok_reqd=ok default=ignore]` | Records pass; continues down stack | Ignored unless no other module in the group returned definite pass/fail | Marking `account` authorization modules `optional` allows terminated directory users to log in [401, 402] |

Two control-flag ordering disasters recur constantly in enterprise `/etc/pam.d/` audits [398, 401, 402]. First, examine what happens when an administrator inserts `auth sufficient pam_u2f.so` or `auth sufficient pam_sss.so` at line 1 of `/etc/pam.d/system-auth`, *above* `auth required pam_nologin.so` and `auth required pam_faillock.so preauth`: because no `required` module has run and failed yet, the instant `sufficient` succeeds, `libpam` short-circuits out of the `auth` stack (`[success=done]`), completely bypassing brute-force lockout counters (`pam_faillock` [398]) and `/etc/nologin` maintenance lockdowns! Every `preauth` gate must execute as `required` or `requisite` *before* the first `sufficient` module. Second, when `sshd` runs with `UsePAM yes` and a user authenticates via an SSH public key or OpenSSH Certificate, *`sshd` never invokes `pam_authenticate()` (`auth` stack) at all*: SSHv2 cryptographic verification already proved identity, so `sshd` calls only `pam_acct_mgmt()` (`account`), `pam_open_session()` (`session`), and `pam_setcred()`! Organizations that place group/access restrictions (`pam_access.so`, `pam_listfile.so`, or custom MFA scripts) solely inside `auth` while leaving `account` containing only `account required pam_unix.so` discover during incident response that disabled Active Directory or LDAP users retain full SSH key access unless `account required pam_sss.so` (or `pam_access.so`) enforces revocation inside the `account` stack [73, 401]!

Even well-ordered PAM stacks are only as trustworthy as the `.so` modules running as `UID 0` inside `sshd` and `login`, as three 2025 advisories underscored. In `CVE-2025-24531` [404], `pam_pkcs11`'s `pam_sm_authenticate()` mistakenly returned `PAM_IGNORE` instead of `PAM_AUTHINFO_UNAVAIL` when smartcard/token I/O failed mid-handshake; in stacks lacking strict trailing `pam_deny.so` enforcement, triggering a hardware disconnect caused `libpam` to skip authentication and grant unauthorized login! In `CVE-2025-6020` (`GHSA-f9p8-gjr4-j9gx` [405]), `pam_namespace` (`<= 1.7.0`) traversed user-controlled polyinstantiated directory paths without symlink confinement, enabling local escalation to `UID 0`. Most instructively, in June 2025 Qualys chained `CVE-2025-6018` and `CVE-2025-6019` on SUSE Linux Enterprise 15 / openSUSE Leap 15 for unprivileged-SSH-to-root escalation [392]: `pam_env.so` had retained the legacy default `user_readenv=1` (deprecated upstream in Linux-PAM `1.5.0` explicitly due to environment-poisoning hazards [399]), causing `sshd`'s `do_pam_setcred()` to load the unprivileged SSH user's `~/.pam_environment` *before* `pam_systemd.so` ran in `session`! Writing `XDG_SEAT OVERRIDE=seat0` and `XDG_VTNR OVERRIDE=1` into `~/.pam_environment` tricked `pam_systemd` into registering the remote SSH session with `systemd-logind` as a *physical local console seat* (`allow_active = yes` in `Polkit`), unlocking `udisks2` loopback/XFS mount operations (`CVE-2025-6019` in `libblockdev`) for instant `UID 0` takeover [392]! Hardened hosts must verify `user_readenv=0` (default in Linux-PAM `1.5.0+` [399]) and place `pam_env.so` at the *end* of the stack without user-file overrides.

### `SSSD` Enterprise Identity: `KCM:` Ticket Custody, AD GPO Mapping, and Entra ID (`Himmelblau` / `aadsshlogin`)

Linking complex C network clients (`OpenLDAP`, `MIT krb5`, `libcurl`, JSON/ASN.1 parsers) directly into every `UID 0` `sshd` or `login` process via legacy `pam_krb5.so` and `nss_ldap.so` bloated the privileged TCB and broke offline laptop logins. Modern enterprise Linux isolates directory protocols inside the System Security Services Daemon (`SSSD` [73]): thin unprivileged IPC stubs (`libnss_sss.so.2` reading an ultra-fast volatile `memcache` first, and `pam_sss.so`) talk over local UNIX sockets to unprivileged/isolated `sssd_nss` and `sssd_pam` responder processes, which query a persistent `ldb` cache and dispatch network operations to per-domain `sssd_be` backends [73]. Three `SSSD` and cloud-broker mechanisms close major credential-theft and spoofing gaps in hybrid Linux fleets:

First, *`sssd-kcm(8)` (`default_ccache_name = KCM:`)* eliminates `/tmp` Kerberos ticket files [400]. Classic MIT Kerberos wrote Ticket-Granting Tickets (`TGT`s) to `FILE:/tmp/krb5cc_%{uid}`, exposing filenames across world-readable `/tmp` listings and making every container bind-mounting `/tmp` or compromised daemon sharing `UID 1000` an instant Pass-the-Ticket (`PtT`) harvester; switching to `KEYRING:persistent:%{uid}` moved tickets into Ring 0 memory ([Chapter 12](12-keyrings-systemd-creds.md)), *yet Linux kernel keyrings are not isolated by container UID/mount namespaces*, causing Kerberos caches to bleed unexpectedly across rootless or UID-sharing containers on the same host [400]! `sssd-kcm` solves both problems simultaneously: socket-activated by `systemd` at `/var/run/.heim_org.h5l.kcm-socket`, `sssd-kcm` authenticates `kinit`/`ssh` clients via `SO_PEERCRED` in userspace (honoring UID and mount namespaces cleanly so containers see tickets *only* if the socket is explicitly bind-mounted!), enforces per-UID ownership in an encrypted `/var/lib/sss/secrets` store, and handles background `tgt_renewal` safely off-disk [400].

Second, *Active Directory `krb5_validate = true` and GPO-to-PAM Access Control (`sssd-ad(5)`)* [73, 395]. When a user enters an Active Directory password at a Linux prompt, validating only the KDC's `AS-REP` reply against the user's password falls to KDC spoofing ("Zombieland"): an attacker on the network who already phished the user's password intercepts port `88` and returns a validly encrypted fake `AS-REP`, gaining local `root` if that user holds `sudo` rights! With `krb5_validate = true` (mandatory default in `id_provider = ad` and `ipa`), `sssd_be` immediately uses the returned `TGT` to issue a `TGS-REQ` service ticket request for the Linux server's own restricted `/etc/krb5.keytab` principal (`host/srv01.corp.example@CORP.EXAMPLE`) and decrypts it locally, proving cryptographically that the remote KDC possesses the Active Directory domain secret [73, 395]. Next, during PAM `account` (`pam_acct_mgmt`), `ad_gpo_access_control = enforcing` fetches applicable Group Policy Objects (`GptTmpl.inf` over authenticated SMB `SYSVOL`) and translates Windows logon rights (`SeRemoteInteractiveLogonRight`, `SeDenyInteractiveLogonRight`) directly into Linux PAM service gates (`sshd`, `login`, `sudo`) so Windows domain admins govern Linux host access centrally without custom shell scripts [395]!

Third, *Cloud-Only OIDC and Microsoft Entra ID Brokers (`Himmelblau` & `aadsshlogin`)* [396, 397]. Organizations retiring on-premises Active Directory Domain Controllers in favor of pure cloud identity (`Microsoft Entra ID`, `Okta`, `Google Workspace`, `Keycloak`) deploy either `SSSD`'s `idp` (`oidc_child`) provider, `Himmelblau` (`pam_himmelblau.so` + `nss_himmelblau` [396]), or Azure's `AADSSHLoginForLinux` VM extension (`aadsshlogin` [397]). Written in memory-safe Rust, `Himmelblau` registers the Linux workstation or server with Entra ID, enforces Entra Conditional Access policies and `pam_allow_groups` object-ID allowlists directly inside PAM `auth`/`account`, and enrolls `TPM 2.0`-sealed *Linux Hello* PIN credentials for offline/fast local authentication [396]. On Azure cloud VMs, `aadsshlogin` pairs `az ssh vm` OIDC login with ephemeral OpenSSH certificates bound to Azure RBAC roles (`Virtual Machine Administrator Login` vs. `Virtual Machine User Login`), bridging cloud IAM directly into OpenSSH without passwords or static keys [397].

### Short-Lived OpenSSH Certificates, `FIDO2` (`sk-ssh-ed25519@openssh.com`), and `SSH_AUTH_SOCK` Hazards

Rather than dragging a 200,000-line ASN.1/X.509 parser into `sshd`'s pre-authentication TCB, Damien Miller and the OpenBSD OpenSSH team specified a minimal, non-extensible-by-ASN.1, length-prefixed binary certificate wire format in `PROTOCOL.certkeys` (`ssh-ed25519-cert-v01@openssh.com` and `sk-ssh-ed25519-cert-v01@openssh.com` [74, 393, 406]):

![Figure: Zero-TOFU, zero-authorized_keys fleet SSH architecture combining OIDC-issued short-lived OpenSSH User/Host Certificates with non-exportable FIDO2 hardware keys (sk-ssh-ed25519@openssh.com with verify-required).](diagrams/13-openssh-certs-fido2-handshake.svg)

Every `ssh-ed25519-cert-v01@openssh.com` blob encodes ten deterministic fields signed by an offline or HSM-backed Certificate Authority key [74]: a 32-byte random `nonce`, the subject `ed25519` public key, a 64-bit `serial`, a 32-bit `type` (`1 = SSH_CERT_TYPE_USER` or `2 = SSH_CERT_TYPE_HOST` so a host key can *never* be confused for a user key!), a human-readable `key_id` string (for example, `parag@corp.example:device-yubikey-9412`, which `sshd` writes into `systemd-journald` on every login even when logging into a shared role account like `admin`!), `valid_principals` (matched against `AuthorizedPrincipalsFile` on servers or target FQDNs on clients), 64-bit `valid_after` and `valid_before` UNIX timestamps, `critical_options` (`force-command`, `source-address` CIDR locks, `verify-required`, where any unrecognized critical option forces `sshd` to reject the certificate fail-closed!), `extensions` (`permit-pty`, `permit-port-forwarding`), and the CA's Ed25519 `signature_key` + `signature` [74, 406].

Deploying mutual OpenSSH certificates across a fleet eliminates both `TOFU` and `authorized_keys` in two configuration lines [74, 393, 406]: workstations trust `@cert-authority *.prod.internal ssh-ed25519 AAAAC3...` in `/etc/ssh/ssh_known_hosts` to validate host certificates (`HostCertificate /etc/ssh/ssh_host_ed25519_key-cert.pub`), while servers set `TrustedUserCAKeys /etc/ssh/user_ca.pub` and `AuthorizedKeysFile none` in `/etc/ssh/sshd_config`. Engineers authenticate to an OIDC-backed SSH CA (`step-ca` [393], `HashiCorp Vault`, `Teleport`) at the start of a work shift and receive a certificate expiring automatically in 4 to 12 hours (`-V +8h`) with zero CRL distribution overhead.

What stops local malware on the engineer's laptop from stealing the private key underlying that 8-hour certificate? Pairing OpenSSH Certificates with `FIDO2` (`CTAP2` [407]) hardware security keys (`sk-ssh-ed25519-cert-v01@openssh.com`, specified in `PROTOCOL.u2f` [75])! Generated via `ssh-keygen -t ed25519-sk -O resident -O verify-required -O application=ssh:prod`, the Ed25519 private scalar is generated *inside* the YubiKey or Token2 secure element and never leaves hardware (`-O resident` stores the discoverable credential inside token NVRAM gated by PIN; without `-O resident`, `~/.ssh/id_ed25519_sk` holds only an opaque AEAD-wrapped key handle useless without that exact physical token) [75, 407]. During every SSH handshake over unique session hash $H$, the token signs:

$$M_{\text{FIDO2}} = \operatorname{SHA-256}(\texttt{"ssh:prod"}) \;\parallel\; \text{flags}_{1\text{B}} \;\parallel\; \text{counter}_{4\text{B}} \;\parallel\; \operatorname{SHA-256}(H)$$

Inside `flags`, bit `0x01` (`SSH_SK_USER_PRESENCE_REQD`) attests physical capacitive touch on the token, and bit `0x04` (`SSH_SK_USER_VERIFICATION_REQD`) attests on-device PIN or biometric verification [75, 407]! Enforcing `PubkeyAuthOptions verify-required` inside server `sshd_config` (or baking `verify-required` into the CA's `critical_options`) causes `sshd` itself to verify bit `0x04` inside the signed `M_FIDO2` structure, guaranteeing that even root malware on the engineer's laptop cannot silently ride an open session without both physical touch and the FIDO2 PIN [75, 406]!

Simultaneously, operators must abolish `ssh -A` (`ForwardAgent yes`) across jump hosts (`AllowAgentForwarding no` on servers, `ForwardAgent no` on clients [394, 406, 408]). Forwarding `ssh-agent` creates a UNIX domain socket on the intermediate bastion readable/writable by remote `UID 0`, allowing a compromised bastion admin to sign arbitrary authentication challenges as the visiting engineer for the duration of the connection, *and* exposing the client's local `ssh-agent` parser to hostile remote messages! In July 2023, Qualys demonstrated `CVE-2023-38408` [391] against OpenSSH's `ssh-agent` (`<= 9.3p1`): a malicious server with access to a forwarded agent socket sent crafted `SSH_AGENTC_ADD_SMARTCARD_KEY` and `REMOVE_SMARTCARD_KEY` requests directing the *engineer's local laptop `ssh-agent`* to `dlopen()` and `dlclose()` arbitrary shared libraries under `/usr/lib*`, chaining side-effecting C++ constructors/destructors into remote code execution on the client workstation! Replace `ForwardAgent yes` unconditionally with `ProxyJump` (`ssh -J bastion.corp.example node01.internal` [408]), which tunnels an end-to-end encrypted SSHv2 transport *through* the bastion as raw TCP bytes (`-W %h:%p`) so client authentication occurs exclusively on the laptop (where OpenSSH `8.9+` can also bind `ssh-add -h user@node01` destination constraints [394]).

### `regreSSHion` (`CVE-2024-6387`) and OpenSSH 9.8–10.0's Multi-Binary Split (`sshd-session` & `sshd-auth`)

Even when `PasswordAuthentication no`, `TrustedUserCAKeys`, and `PubkeyAuthOptions verify-required` are configured flawlessly, `sshd` must parse untrusted TCP streams *before* knowing whether the remote peer holds a valid certificate. In 2002–2003, Niels Provos, Markus Friedl, and Peter Honeyman introduced *Privilege Separation* (`privsep` [409]) in OpenSSH: the privileged `UID 0` monitor forked an unprivileged network child (`UID sshd`, `chroot("/var/empty")`, later locked inside a strict `seccomp-BPF` filter) to parse untrusted SSHv2 key-exchange and auth packets, relaying structured requests back over an internal socketpair [409].

![Figure: How regreSSHion (CVE-2024-6387) exploited an async-signal-unsafe syslog() call inside pre-auth sshd's SIGALRM LoginGraceTime handler to corrupt glibc malloc structures, and how OpenSSH 9.8 split sshd-session into a fresh execve() binary to randomize ASLR per connection.](diagrams/13-regresshion-privsep-split.svg)

In July 2024, Qualys disclosed `regreSSHion` (`CVE-2024-6387` [76]), an unauthenticated remote root race condition in `glibc`-based Linux `sshd` (`8.5p1` through `9.7p1`, alongside RHEL 9's downstream `cleanup_exit()` variant `CVE-2024-6409` [410]). Remarkably, `CVE-2024-6387` was an accidental regression of Mark Dowd's 2006 signal race (`CVE-2006-5051` [411], rooted in Michal Zalewski's 2001 non-async-signal-safe exploitation research [412]): in October 2020, OpenSSH `8.5p1` commit `752250c` refactored logging headers and inadvertently deleted `#ifdef DO_LOG_SAFE_IN_SIGHAND` inside `sigdie()` [76]!

Trace the exact Ring 3 heap corruption inside the *privileged `UID 0` monitor process* (which runs *outside* `/var/empty` and *outside* the `privsep` `seccomp` sandbox!) [76]: when an unauthenticated TCP client fails to complete login within `LoginGraceTime` (default `120` seconds), the kernel delivers `SIGALRM` asynchronously to the privileged monitor. Inside `grace_alarm_handler()`, `sigdie()` invoked `syslog()`, which on Linux `glibc` lazily opens `/etc/localtime` (`__tzfile_read()`) and allocates `FILE` and heap chunks via `malloc()` and `free()`, functions strictly forbidden inside POSIX signal handlers! By sending crafted public-key packets that groomed `glibc` `ptmalloc2` bins inside the monitor and stalling TCP reads so `SIGALRM` interrupted a main-loop `malloc()`/`free()` mid-update with heap pointers left inconsistent, Qualys corrupted `glibc` heap metadata and overwrote `_IO_wfile_jumps` vtable pointers in the `UID 0` monitor (~10,000 tries, averaging 6–8 hours against 32-bit `i386` ASLR at `MaxStartups = 100`, with 64-bit `amd64` constrained only by wider ASLR entropy) [76]!

Why could an attacker probe `sshd`'s `glibc` heap layout across 10,000 consecutive TCP connections without `ASLR` invalidating their pointer guesses? Because classic `sshd` handled incoming connections via `fork()` (or a static re-exec of the identical binary on some distros that disabled `-R` re-execution!), cloning or exposing tightly coupled address-space state across pre-auth, monitor, and post-auth code inside one monolithic ELF binary [76, 77]! Across OpenSSH `9.8p1` (July 2024 [77]), `9.9p1` (September 2024 [413]), and `10.0` (April 2025 [414]), the OpenSSH maintainers dismantled that monolithic binary completely:

![Figure: Four-stage OpenSSH 9.8-10.0 multi-binary architecture: the tiny sshd TCP listener with PerSourcePenalties, per-connection execve('sshd-session') ASLR re-randomization, OpenSSH 10.0's disjoint pre-auth sshd-auth sandbox binary, and post-auth PAM/SSSD session setup.](diagrams/13-extra-openssh-98-binary-split.svg)

Observe how four orthogonal defenses interlock in OpenSSH `9.8` through `10.0` [77, 406, 413, 414]:
First, `grace_alarm_handler()` reverted to pure async-signal-safe `_exit(1)` termination (zero `syslog()`, zero `malloc()`), reinforced in OpenSSH `9.9` by adding up to `4` seconds of cryptographic random jitter to `LoginGraceTime` so network attackers cannot synchronize packet stalls with `SIGALRM` delivery [77, 413]. Second, OpenSSH `9.8` enabled `PerSourcePenalties` by default in the master `sshd` listener: any client IP (and `/32` IPv4 or `/128`–`/64` `PerSourceNetBlockSize` CIDR block) that triggers a pre-auth process crash (`crash` penalty), repeated `LoginGraceTime` timeouts, or rapid `authfail` storms is quarantined at `accept()` time before spawning a session, starving multi-thousand-attempt heap races of connection throughput [77, 406]. Third, OpenSSH `9.8` split the daemon into a tiny `sshd` listener binary (containing *zero* SSHv2 protocol parsing code!) that invokes a fresh `execve("/usr/libexec/sshd-session")` on every accepted TCP connection, guaranteeing independent kernel `ASLR` randomization of `glibc`, stack, and heap on every single connection [77]. Fourth, OpenSSH `10.0` extracted the entire pre-authentication protocol state machine out of `sshd-session` into a third dedicated binary, `sshd-auth` (`chroot("/var/empty")`, `UID sshd`, `seccomp-BPF`), ensuring that pre-authentication KEX (`mlkem768x25519-sha256` hybrid post-quantum default in `10.0`!) and certificate parsing execute inside a completely disjoint ELF binary whose code and heap vanish from memory the instant user authentication succeeds [414]!

## Distro, Immutable-OS, & Cloud Trade-Offs

Enterprise Linux distributions (`RHEL 9.4+/10`, `Ubuntu 24.04 LTS`, `Debian 12/13`, `SUSE 15 SP6+`, `Fedora`) ship modular `/etc/ssh/sshd_config.d/*.conf` drop-in directories alongside `authselect` (RHEL/Fedora) or `pam-auth-update` (Debian/Ubuntu) profile generators that synthesize ordered `/etc/pam.d/*` stacks automatically so humans do not hand-edit `sufficient` jumps [398, 402]. Hardened server baselines set `PasswordAuthentication no`, `KbdInteractiveAuthentication no` (unless bound strictly to `Himmelblau`/`SSSD` OIDC MFA), `PermitRootLogin no`, `AllowAgentForwarding no`, `PerSourcePenalties yes`, `TrustedUserCAKeys /etc/ssh/user_ca.pub`, and `PubkeyAuthOptions verify-required` [396, 406], while switching Kerberos workstations and servers to `default_ccache_name = KCM:` under `sssd-kcm.socket` [400].

Cloud-native and immutable operating systems push the perimeter further still [45, 46, 397]. Rather than exposing TCP `22` to `0.0.0.0/0`, cloud fleets gate SSH behind outbound-initiated brokers (`AWS SSM Session Manager`, `GCP OS Login` + `IAP`, `Tailscale SSH` over WireGuard identity, or `Cloudflare Access` short-lived SSH CAs) where zero inbound TCP SYN listener faces the public internet. On `Bottlerocket`, the host root filesystem carries no `sshd` at all (optional emergency debugging runs inside an out-of-band `admin` container), while `Talos Linux` [45] deletes `sshd`, `libpam`, `SSSD`, and `/bin/sh` from the operating system completely, replacing interactive human shell logins with mutual-TLS authenticated, declaratively audited `talosctl` gRPC APIs.

## Inspecting on a Live Linux Host

Check the installed OpenSSH release (`>= 9.8` for `sshd-session` split, `>= 10.0` for `sshd-auth` split) and verify whether split privilege-separation binaries exist under `/usr/libexec/` or `/usr/lib/openssh/`:

```bash
ssh -V
ls -la /usr/libexec/openssh/sshd-* /usr/lib/openssh/sshd-* /usr/libexec/sshd-* 2>/dev/null || true
```

Evaluate the merged runtime `sshd` configuration (`sshd -T` resolves all `Include` drop-ins; requires root or `run0`) for CA certificates, `FIDO2` `verify-required`, agent forwarding, and `PerSourcePenalties`:

```bash
sshd -T 2>/dev/null | grep -E "^(passwordauthentication|permitrootlogin|pubkeyauthoptions|trustedusercakeys|authorizedkeysfile|allowagentforwarding|persourcepenalties)\b" || true
```

Audit `/etc/pam.d/sshd` and `/etc/pam.d/common-auth` or `system-auth` for `sufficient` ordering hazards ahead of `pam_faillock`/`pam_nologin` and verify `pam_env` does not enable `user_readenv=1`:

```bash
grep -vE "^#|^$" /etc/pam.d/sshd 2>/dev/null | head -n 16
grep -rn "pam_env" /etc/pam.d/ 2>/dev/null | head -n 12
```

Verify `SSSD` `KCM:` Kerberos credential socket activation (`sssd-kcm.socket`) and check Active Directory `krb5_validate` or `ad_gpo_access_control` settings:

```bash
systemctl is-active sssd.service sssd-kcm.socket 2>/dev/null || true
grep -rnE "^[[:space:]]*(default_ccache_name|krb5_validate|ad_gpo_access_control)" /etc/krb5.conf /etc/krb5.conf.d/ /etc/sssd/ 2>/dev/null || true
```
