# File-Based Encryption, Physical USB Zero-Days, and Theft Locks

## Overview

* **Link in the Chain:** Data-at-rest cryptographic custody and physical-possession defense layer; encrypts file contents, filenames, and filesystem metadata via `fscrypt` v2, `dm-default-key`, and `UFS` Inline Crypto Engines (`ICE`), partitions Direct Boot keys across `Before First Unlock` (`BFU`) and `After First Unlock` (`AFU`), and hardens physical USB and street-theft surfaces.
* **Core Security Invariant:** Credential Encrypted (`CE`) master keys remain completely absent from host DRAM and `ICE` hardware keyslots during cold-boot `BFU` until `Weaver` and `KeyMint` unwrap the user's `SyntheticPassword`, hardware-wrapped `ICE` keys never expose raw `AES-256-XTS` content keys to `EL1` kernel memory even during `AFU` I/O, and `Identity Check` removes `LSKF` PIN fallback outside Trusted Places.
* **Ecosystem Enforcement Tier:** `File-Based Encryption` (`fscrypt` v2) and `Metadata Encryption` enforce identically across `GREEN` and `YELLOW` locked states (`CDD` Section 9.9); lock-screen USB signaling cutoffs (`IUsb.enableUsbData`) and inactivity reboots enforce under Android 16/17 `Advanced Protection Mode` (`GREEN`) and `GrapheneOS` (`YELLOW`), while `Theft Detection Lock` and `Identity Check` ship across Android 15-17.
* **Trusted Computing Base (TCB):** Linux kernel `fs/crypto/` (`fscrypt` v2 `HKDF-SHA512`), `blk-crypto` and `UFS` `ICE` hardware-wrapped key silicon (`blk_crypto_ll_ops`), `vold` (`system/vold/FsCrypt.cpp`), `SyntheticPasswordManager` + `Weaver`/`KeyMint` ([Chapter 4](04-keymint-weaver-throttling.md)), `IUsb` Type-C HAL, on-device IMU `Theft Detection` ML, and `Identity Check` `BiometricPrompt` gates.
* **Seam & Handoff:** Protects powered-off `BFU` data against chip-off flash readers and `EL1` kernel zero-days while shrinking the live `AFU` physical attack window via USB port cutoffs, auto-reboot, and snatch locks; hands biometric spoof resistance (`Class 3`) and `Passkeys` to [Chapter 13](13-biometrics-passkeys.md).

## Threat Model & Ecosystem Constraint

Desktop full-volume encryption (`BitLocker` in TPM-only mode or single-key `LUKS`) assumes a binary lifecycle: a powered-down laptop holds ciphertext on NVMe, and booting to the OS login screen unseals the single volume key into kernel RAM. Early Android (`5.0` through `6.0`) copied that desktop blueprint via `dm-crypt` Full-Disk Encryption (`FDE`), only to collide immediately with two mobile realities [92, 201, 357]. First, locking the entire `/data` partition behind a pre-OS boot password meant that if a handset installed an unattended overnight security OTA and rebooted at 3:00 a.m., the user's 7:00 a.m. alarm never rang, incoming telephone calls failed silently, Wi-Fi could not bootstrap, and blind users had no `TalkBack` screen reader to enter their password (`Direct Boot` failure) [92, 201]. Second, as Muller and Spreitzenbarth demonstrated in the `FROST` (*Forensic Recovery of Scrambled Telephones*) attack [357], software `dm-crypt` held expanded AES round-key schedules directly inside normal host DRAM, allowing physical attackers with chilling spray and bus/recovery access on unlocked-bootloader phones to carve live encryption keys out of memory remanence.

Replacing `FDE` with per-directory `File-Based Encryption` (`FBE`) solved the boot availability dilemma by splitting every handset's runtime into two distinct cryptographic epochs [92, 201]. Immediately after power-on or reboot, before the human enters their Lock Screen Knowledge Factor (`LSKF` PIN, pattern, or passphrase), the phone sits in `Before First Unlock` (`BFU`): system services and `directBootAware` apps run using `Device Encrypted` (`DE`) storage while `Credential Encrypted` (`CE`) keys do not exist in RAM or storage controllers. Once the owner enters their `LSKF` for the first time after boot, the handset transitions into `After First Unlock` (`AFU`) and *remains in `AFU` even when the user presses the power button to lock the screen* [92, 116]! `CE` keys must remain programmed in hardware during locked `AFU` operation so end-to-end encrypted messengers (*Signal*, *WhatsApp*) can decrypt and index incoming push messages in background push wakes, wearable companions can sync health telemetry, and double-press camera shortcuts can save photos to disk [92, 116].

Crucially, locking the screen in `AFU` engages `Keyguard` (`SystemUI`), which is a *user-interface gate*, not a cryptographic key eviction. When security researcher David Schutz uncovered `CVE-2022-20465` in `KeyguardHostViewController.java` [358], swapping a SIM card and entering a SIM `PUK` code triggered a `.dismiss()` state-machine race that popped the `Keyguard` stack off the screen: on an `AFU` phone, dismissing `Keyguard` dropped the physical attacker straight onto the unlocked home screen with all decrypted `CE` apps accessible, whereas on a freshly rebooted `BFU` phone, `CE` files remained cryptographically unreadable `-ENOKEY` ciphertext because `SyntheticPassword` had never unwrapped them [92, 358]!

Two high-capability physical adversary classes systematically weaponize that `AFU` window (and unguarded `BFU` hardware buses) in the wild [16, 25, 359]:

First are *commercial physical forensic extraction appliances* (*Cellebrite UFED / Inseyets* paired with `Turbo Link` USB hardware adapters, and *Magnet Graykey*) deployed at border crossings, police stations, and intelligence detention centers [16, 359]. In December 2024 (*A Digital Prison* [359]) and February 2025 [16], Amnesty International's Security Lab documented Serbia's Security-Information Agency (`BIA`) detaining journalists and student protesters, plugging locked Samsung and Qualcomm Android handsets into Cellebrite rigs, firing zero-day Linux kernel USB driver chains (`CVE-2024-53104`, `CVE-2024-53197`, `CVE-2024-53150`, `CVE-2024-50302`) and Qualcomm `FASTRPC` DSP zero-days (`CVE-2024-43047` [360]) over the physical USB-C port to gain `EL1` root, extracting private data, and planting Serbian state spyware (*NoviSpy*) [16, 359]!

Second are *organized street-snatch and shoulder-surfing theft rings* operating across major metropolitan transit hubs and nightlife districts [25, 361]. Rather than developing kernel exploits, thieves stand behind a target on a train or in a bar, record the victim tapping their 6-digit `LSKF` PIN on video, snatch the phone out of their hand before the screen locks (or unlock it seconds later with the observed PIN), use the PIN as a universal fallback to reset the victim's cloud account password, enroll the thief's own fingerprint into `BiometricService`, disable *Find My Device*, and empty banking and cryptocurrency balances within minutes [25, 361, 362].

## Architecture & AOSP Implementation

### `fscrypt` v2, `system/vold`, and `dm-default-key` Metadata Encryption

Mandatory on all devices launching with Android 10 or higher (`CDD` Section 9.9), Android's `File-Based Encryption` orchestrates userspace key management inside `system/vold/FsCrypt.cpp` and `KeyUtil.cpp` [92, 363] atop the upstream Linux kernel `fs/crypto/` (`fscrypt` v2) subsystem over `f2fs` and `ext4` [93]. On modern `/data` partitions (`fstab` flag `fileencryption=aes-256-xts:aes-256-cts:v2+inlinecrypt_optimized+wrappedkey` or `aes-256-hctr2` for filenames), every encrypted directory carries an inode extended attribute (`struct fscrypt_policy_v2`) specifying a 16-byte `master_key_identifier`, content and filename cipher modes, and key-derivation flags [92, 93].

Under standard per-file `fscrypt` v2 policies, whenever the filesystem creates a new inode, the kernel generates a fresh 16-byte random `nonce` stored in that inode's xattr and derives a cryptographically isolated key from the 512-bit `fscrypt` master key $K_{\text{master}}$ using `HKDF-SHA512` (`RFC 5869` [86, 93]):

$$K_{\text{inode}} = \text{HKDF-SHA512}\bigl(\text{IKM} = K_{\text{master}}, \; \text{salt} = \varnothing, \; \text{info} = \text{"fscrypt\textbackslash 0"} \parallel \text{ctx\_byte} \parallel \text{mode} \parallel \text{nonce}_{16}\bigr)$$

Notice how `ctx_byte` domain-separates distinct cryptographic outputs from the same root key: `HKDF_CONTEXT_KEY_IDENTIFIER` (`1`) computes the public `master_key_identifier` (`SHA-512` truncated to 16 bytes so userspace `vold` and VFS can verify key presence without exposing key material), `HKDF_CONTEXT_PER_FILE_ENC_KEY` (`2`) derives per-inode keys, and under `inlinecrypt_optimized` (`HKDF_CONTEXT_IV_INO_LBL_64_KEY = 3`), the kernel derives one `AES-256-XTS` contents subkey per storage class (`DE_0`, `CE_0`, `CE_10` work profile) and mixes each file's 32-bit stable inode number concatenated with the 32-bit logical block number directly into the 64-bit `UFS` Data Unit Number (`DUN` IV) so limited hardware keyslots never thrash across thousands of open files [92, 93]! File contents are encrypted in 4,096-byte data units (`dusize_4k` preserving 4 KiB crypto granularity even on Android 15+ 16 KiB virtual-memory page kernels!) using `AES-256-XTS`, while file and symlink names are encrypted using `AES-256-CTS-CBC` or length-preserving wide-block `AES-256-HCTR2` (preferred since Android 14+ because changing a single bit in a filename scrambles the entire ciphertext filename via universal `POLYVAL` hashing without ciphertext expansion) [92, 364]. Only ultra-low-cost entry devices whose ARM cores omit optional ARMv8 Cryptography Extensions (`PMULL`/`AESE`) may substitute Google's `Adiantum` (`XChaCha12-AES-NH-Poly1305`) cipher [92, 364].

Yet `fscrypt` alone encrypts *only* file contents and directory entry names inside designated `FBE` directories: ext4/f2fs superblocks, inode tables, file sizes, POSIX permissions, modification timestamps, extent maps, and top-level unencrypted bootstrap folders (`/data/unencrypted`, `/data/misc/vold/user_keys`) remain visible at the raw block layer unless protected underneath [365]. Android 11+ closes that leakage by mandating *Metadata Encryption* (`CONFIG_DM_DEFAULT_KEY=y`) on internal storage [365]. During `early-fs` boot, `init` mounts a dedicated 16 MiB `/metadata` partition (`ext4`), starts `vold`, waits for `KeyMint` (`exec_start wait_for_keymaster`), unwraps a Verified-Boot-bound metadata key from `/metadata/vold/metadata_encryption`, and instantiates a `dm-default-key` device-mapper target over `userdata` [365]. Unlike legacy `dm-crypt` (which wastefully encrypted every `FBE` file block twice), `dm-default-key` cooperates with `blk-crypto`: any sector bio carrying an `fscrypt` `FBE` encryption context uses its `FBE` `CE`/`DE` key directly, while every remaining sector on `userdata` (superblocks, inode sizes, timestamps, free-space remnants) is transparently encrypted under the `AES-256-XTS` metadata key [365]!

### `UFS` Inline Crypto Engines (`ICE`) and Hardware-Wrapped Storage Keys

Even with `fscrypt` v2 and `dm-default-key`, keeping raw 64-byte `AES-256-XTS` keys inside `EL1` kernel slab memory (`struct fscrypt_master_key`) leaves keys exposed to cold-boot DRAM attacks (`FROST` [357]) and physical kernel memory-disclosure zero-days (`CVE-2024-53150` / `CVE-2024-50302` [366, 367]) [368]. Simply loading keys into `UFS` host-controller Inline Crypto Engine (`ICE`) keyslots (`CONFIG_BLK_INLINE_ENCRYPTION=y`, `CONFIG_SCSI_UFS_CRYPTO=y`) does not by itself eliminate DRAM residency, because `UFS` controllers reset and wipe volatile keyslots during storage link error-recovery routines (requiring the OS to reprogram slots autonomously without re-prompting the user's PIN!), and `ICE` hardware encrypts only 4 KiB sector payloads while VFS still needs a software subkey to encrypt filenames [368, 369].

Android 11 through Android 17 solve all three constraints simultaneously via *Hardware-Wrapped Inline Encryption Keys* (`wrappedkey` in mainline Linux 6.16+ / Android 17 using `BLKCRYPTOGENERATEKEY`, `BLKCRYPTOIMPORTKEY`, and `BLKCRYPTOPREPAREKEY` ioctls on `struct blk_crypto_ll_ops`, superseding the legacy `wrappedkey_v0` `KeyMint` `TAG_STORAGE_KEY` interface) [368, 369]:

| Storage Layer / Key | Cryptographic Primitive | Wrapping & Custody State in `BFU` | Residency & Hardware Path in `AFU` |
|---|---|---|---|
| `Metadata Encryption` (`/metadata/vold/`) | `AES-256-XTS` (`dm-default-key`) | Unwrapped at `late-fs` via `KeyMint` + `AVB` boot binding [365] | Ephemerally wrapped in RAM; raw XTS key inside `ICE` keyslot [365, 368] |
| `System & User DE` (`/data/system_de/0`, `/data/user_de/0`) | `fscrypt` v2 `AES-256-XTS` + `CTS`/`HCTR2` | Active at `post-fs-data` for `directBootAware` alarms & dialer [92, 201] | Raw contents key isolated in SoC `ICE`; `sw_secret` in VFS for filenames [368] |
| `User CE` (`/data/user/0`, `/data/media/0`) | `fscrypt` v2 `AES-256-XTS` + `CTS`/`HCTR2` | *Completely absent* from DRAM & `ICE`; sealed under `Weaver` + `KeyMint` [92, 370] | Unwrapped via `SyntheticPassword` $\to$ ephemerally wrapped blob $\to$ `ICE` keyslot [368, 370] |
| `Work Profile CE` (`/data/user/10`) | `fscrypt` v2 `AES-256-XTS` + `CTS`/`HCTR2` | Absent in `BFU` and evicted independently when Work Mode turns off [201] | Independent ephemerally wrapped key programmed into separate `ICE` slot [92, 368] |

Trace how a hardware-wrapped `CE` key moves from flash to `UFS` silicon without *ever* existing as a plaintext content key in host DRAM [368, 371]. When `vold` first creates a user's `CE` key, dedicated SoC key-wrapping hardware (`Google Tensor` / `Qualcomm HWKM` + `ICE`) generates a random 256-bit raw storage key strictly inside hardware and returns it *long-term wrapped* (`AES-256-GCM` under a die-unique hardware wrapping key fused outside the main CPU), which Android then wraps *a second time* under the user's `LSKF`/`KeyMint`-bound `SyntheticPassword` before saving to `/data/misc/vold/user_keys/ce/0/` [368, 370]. Upon first `LSKF` unlock (`BFU` $\to$ `AFU`), `vold` strips the outer `SyntheticPassword` layer and asks the hardware wrapper (`BLKCRYPTOPREPAREKEY`) to re-encrypt the long-term blob into an *ephemerally wrapped key* encrypted under a random per-boot hardware key generated fresh at power-on [368]. Whenever the storage controller programs an I/O slot (`blk_crypto_ll_ops::keyslot_program`), dedicated hardware unwraps that ephemeral blob internally, runs a `NIST SP 800-108` counter-mode `AES-256-CMAC` KDF (`kdf1..kdf4` verified bit-for-bit by `vts_kernel_encryption_test` [368, 371]), wires `inline_encryption_key` directly over a private hardware bus into a `UFS` `ICE` keyslot, and hands Linux `blk_crypto_ll_ops::derive_sw_secret` *only* a domain-separated `sw_secret` for filename hashing! Even an attacker who dumps every byte of host DRAM or triggers a UFS controller reset obtains at most an ephemerally wrapped blob that becomes cryptographically useless the instant the phone reboots [368].

### Direct Boot Custody: `SyntheticPasswordManager` and `BFU` vs. `AFU`

![Figure: File-Based Encryption (fscrypt v2) and Direct Boot key custody across Before First Unlock (BFU) and After First Unlock (AFU) states.](diagrams/12-fbe-bfu-afu-key-hierarchy.svg)

Inside `frameworks/base/services/core/java/com/android/server/locksettings/SyntheticPasswordManager.java` [370], Android decouples the human's memorable `LSKF` from `fscrypt` master keys via a 256-bit `SyntheticPassword` ($S$). Changing a 6-digit PIN never re-encrypts user media on `/data/media/0`; instead, `LockSettingsService` re-wraps $S$ under a new `Weaver` slot ([Chapter 4](04-keymint-weaver-throttling.md)) and `KeyMint` blob while preserving the `CE` master key derived from $S$ [370]. During `BFU`, $S$ rests sealed behind `StrongBox` `Weaver` hardware throttling and `KeyMint` Verified-Boot binding; `FsCrypt.cpp` has not invoked `FS_IOC_ADD_ENCRYPTION_KEY` for `CE_0`, leaving `/data/user/0/` and `/data/media/0/` as pure ciphertext [92, 363]. Entering the valid `LSKF` unwraps $S$, installs the ephemerally wrapped `CE` key into the kernel/`ICE` keyring via `vold`, and broadcasts `Intent.ACTION_USER_UNLOCKED` to enter `AFU` [201, 363, 370].

### Amnesty Lab's Serbia Investigation: Cellebrite's Linux USB Quirk Chain

Why did Serbian authorities detaining student activist "Vedran" in Belgrade on December 25, 2024 succeed in achieving `EL1` kernel root over the USB-C charging port of his locked Samsung handset using a Cellebrite UFED `Turbo Link` hardware adapter [16, 359]? The answer lies in the interaction between `USB Type-C` Dual-Role Data (`DRD`) controllers (`dwc3` / `xhci-hcd`) and fifteen years of legacy peripheral quirks compiled into the upstream Linux kernel [16].

When a locked smartphone is plugged into a laptop in *USB Peripheral (Gadget) Mode*, Android's userspace `UsbDeviceManager` withholds `MTP` file transfer and unauthorized `adbd` transport until the screen is unlocked. However, when an external dongle asserts the USB Type-C Configuration Channel (`CC` `Rd` pull-down) to request *USB Host Mode* (the exact path used when plugging USB-C headphones, an Ethernet dongle, or a FIDO security key into a phone), the SoC's `xhci` host controller powers `VBUS`, enumerates whatever `USB_DT_DEVICE` and `USB_DT_CONFIG` descriptors the external dongle transmits, and dispatches kernel worker threads (`kworker` `usb_enumerate_device`) in `EL1` to bind matching in-kernel class drivers *even while the lock screen is active* [16, 372]!

![Figure: Cellebrite UFED Turbo Link physical USB Host-Mode exploit chain uncovered in Serbia (2024-2025) chaining Anton HID, ALSA clock, Chicony UVC, and Creative Extigy driver quirks versus hardware USB lane disabling and BFU reboot eviction.](diagrams/12-extra-cellebrite-usb-alsa-chain.svg)

Forensic USB kernel logs recovered by Amnesty International's Security Lab and analyzed with Google Threat Analysis Group researcher Benoit Sevens caught Cellebrite's `Turbo Link` adapter emulating a precise sequence of obscure 2000s-era USB peripherals (uniformly stamped with synthetic firmware revision `bcdDevice = 12.34` and serial strings `00001` and `33117733` behind an emulated `05e3:0610` USB hub) to target single-device quirk branches in the Linux kernel [16]:

First, to defeat `EL1` Kernel Address Space Layout Randomization (`KASLR`) without crashing the kernel, the dongle emulated an `Anton Touch Pad` (`VID 0x1130`, `PID 0x3101`), one of only two USB IDs in Linux that activates the 11-year-old `MT_CLS_EXPORT_ALL_INPUTS` configuration in `drivers/hid/hid-multitouch.c` [16, 367]. Sending crafted multitouch HID reports triggered `CVE-2024-50302`, leaking uninitialized kernel heap pointers back over the USB wire [16, 367], complemented in April 2025 ASB in-the-wild chains by `CVE-2024-53150`, an out-of-bounds kernel memory read in ALSA USB audio clock-selector and multiplier descriptor parsing (`sound/usb/clock.c`) [38, 366].

Second, to achieve arbitrary `EL1` slab write primitives across diverse kernel builds, Cellebrite staged two independent USB media driver overflows [16, 38, 373, 374]. In Flow A, the dongle presented `VID 0x04f2`, `PID 0xb071` (*Chicony CNF7129 Webcam* from a 2009 netbook), the *single* USB ID in `drivers/media/usb/uvc/uvc_driver.c` matching the 15-year-old `UVC_QUIRK_RESTRICT_FRAME_RATE` flag! Supplying malformed `UVC_VS_UNDEFINED` video streaming descriptors caused `uvc_parse_format()` to miscompute frame buffer bounds while skipping restricted frame intervals, triggering an out-of-bounds kernel heap write (`CVE-2024-53104`, patched in the February 2025 Android Security Bulletin) [16, 373]. In Flow B, the dongle presented `VID 0x041e`, `PID 0x3000` (*Creative SoundBlaster Extigy*), hitting `snd_usb_extigy_boot_quirk()` in `sound/usb/quirks.c` [16, 374]. During custom boot-quirk re-initialization, `snd_usb_extigy_boot_quirk()` called `usb_get_descriptor(dev, USB_DT_DEVICE, ...)` directly into `dev->descriptor` *without* verifying that the newly returned `bNumConfigurations` matched the array size allocated during initial enumeration, corrupting `dev->config` (`CVE-2024-53197`, patched upstream November 2024 and in the April 2025 ASB) and visibly overwriting the live kernel device node in place into an `M-Audio FastTrack Pro` (`0x0763:0x2012`) within 200 milliseconds to confirm heap control [16, 38, 374]!

Third, the dongle connected and disconnected an emulated `Microsoft Comfort Mouse 4500` (`VID 0x045e`, `PID 0x076c`, invoking `MS_DUPLICATE_USAGES` `clear_bit()` in `drivers/hid/hid-microsoft.c`) at least 42 times in rapid bursts to groom `kmalloc` slabs and trigger `EL1` root code execution, followed by pushing Cellebrite's `falcon` post-exploitation binary, bypassing the lock screen, and attempting to side-load the Serbian *NoviSpy* surveillance APK [16, 359].

![Figure: Physical USB forensic exploit chains (Cellebrite 2025 UVC/ALSA zero-days) vs. lock-screen USB data disabling, Theft Detection Lock, and Identity Check.](diagrams/12-usb-zero-day-vs-locks.svg)

Patching individual `uvcvideo` and `snd-usb-audio` CVEs is necessary, yet Linux contains hundreds of legacy USB class drivers. Android 15, Android 16/17 (`USB Protection` inside `Advanced Protection Mode`), and `GrapheneOS` eliminate that physical surface structurally [116, 372, 375]. First, via `android.hardware.usb.IUsb` (`UsbPort.enableUsbData(false)`), *USB Protection* forces *charge-only* mode for every new USB connection attached while locked, allowing pre-existing unlocked sessions such as wired Android Auto to persist while severing `D+/D-` and SuperSpeed `TX/RX` data lanes against newly plugged `Turbo Link` rigs until screen unlock [372, 375]. Second, *Inactivity Reboot* (`72 hours` in `Advanced Protection Mode`; `10 minutes` to `72 hours` on `GrapheneOS`) cold-reboots idle locked `AFU` devices, evicting ephemerally wrapped `CE` keys from DRAM and `UFS` `ICE` keyslots before an impounded handset reaches a forensic lab [116, 372].

### Street-Theft and Shoulder-Surfing Defenses: `Theft Detection Lock` and `Identity Check`

Against kinetic street theft and shoulder-surfed PINs, Android 15 through Android 17 layer five runtime locks across Play Services, `SystemUI`, and `BiometricService` [25, 361, 362]:

First, `Theft Detection Lock` runs a low-power on-device ML model over accelerometer and gyroscope kinematics fused with Wi-Fi and Bluetooth peer-proximity loss; detecting a snatch-jerk followed by sprinting, cycling, or vehicle acceleration slams `Keyguard` shut instantaneously, enabled *by default* across Brazil and globally on new and upgraded Android 17 devices [25, 361].

Second, `Offline Device Lock` automatically locks the screen shortly after a thief toggles Airplane Mode, pulls the SIM, or drops an unlocked handset into a Faraday pouch to block remote wipe commands [25, 361].

Third, `Remote Lock` (`android.com/lock`) breaks the 2FA catch-22 on borrowed devices by locking the screen using only the victim's verified phone number plus a security challenge [25, 361]. In Android 17, *Find Hub's Mark as Lost* adds a *mandatory biometric requirement* atop the device PIN, hides Quick Settings tiles, and blocks new Wi-Fi and Bluetooth pairings [25, 361].

Fourth, `Failed Authentication Lock` (upgraded with a settings toggle and steeper PIN retry throttling in Android 16/17) locks the handset down after repeated failed probes inside apps or `Settings`, while ignoring consecutive identical wrong guesses so accidental pocket taps do not exhaust retry counters [361].

Fifth, `Identity Check` (launched on Android 15+ in early 2025 and expanded across *all* apps invoking `BiometricPrompt` in late 2025 and 2026) neutralizes shoulder-surfed PINs structurally [25, 361, 362]. Whenever the handset is physically outside the user's designated *Trusted Places* (such as home or workplace geofences), `Identity Check` strips the `"Use PIN / Use Password"` fallback button from `BiometricPrompt` across critical OS and app operations! A thief who filmed the victim's 6-digit PIN in a bar and snatched the phone *cannot* use that PIN to add a fingerprint, change the `LSKF`, turn off *Find My Device* or `Theft Protection`, factory-reset without `FRP`, read passwords/passkeys in `Google Password Manager`, or authorize transfers in any banking app integrated with `BiometricPrompt`: only a live `Class 3` (`Strong`) biometric ([Chapter 13](13-biometrics-passkeys.md)) unlocks the gate [25, 361, 362].

## Vendor, OEM, & Custom-OS Boundaries

While `CDD` Section 9.9 enforces `fscrypt` v2 `FBE` and `Metadata Encryption` across every certified Android 11+ device, hardware-wrapped `ICE` key support (`wrappedkey` / `wrappedkey_v0`) and physical USB-C data-pin cutoff depend on SoC silicon and HAL integration [92, 368, 372]. Google Pixel (`Tensor` + `Titan M2`), Qualcomm flagship Snapdragon platforms (`ICE` + `Hardware Key Manager`), and Samsung flagship Galaxy devices (`Knox Vault` + `FMP`) isolate bulk `AES-256-XTS` keys inside hardware keyslots and support `IUsb.enableUsbData(false)` at the Type-C controller (noting that cutting USB data lines while locked can limit `USB PD` PPS negotiation to baseline charging wattage on certain controllers [372]). Entry-level SoCs lacking `IUsb` hardware lane switching fall back to Linux `usbcore` software authorization (`authorized_default = 0`) [116, 375]. Samsung One UI additionally exposes `Auto Blocker`, blocking USB host/gadget commands during locked charging [16].

On `GrapheneOS` (`YELLOW` locked Pixel), physical port and key-eviction defenses push hardware capabilities to their theoretical limits [116]: `GrapheneOS` controls *both* the USB-C controller and Pixel magnetic pogo-pin accessories across five granular modes (`Off`, `Charging-only`, `Charging-only when locked`, `Charging-only when locked, except before first unlock`, and `On`), defaulting to hardware data-lane cutoff while locked; supports auto-reboot timers down to `10 minutes`; and implements a hardware-backed *Duress PIN/Password* that, when entered at *any* lock screen or `BiometricPrompt` under physical coercion, instantaneously wipes `KeyMint`/`Weaver` storage keys, zeroes `eSIM` metadata, and powers down irreversibly in under a second [116].

### The `BFU` + USB-Off Operational Imperative

Look closely at a subtle forensic detail inside Amnesty International's Belgrade timeline [16]: student activist "Vedran" *did* power his phone off at 18:36 before handing it to plain-clothes officers! At 20:01 inside the police station, officers powered the handset back on into `BFU` (`Before First Unlock`) and plugged in Cellebrite's `Turbo Link`. Because legacy USB host enumeration ran even in `BFU` when hardware USB protection was absent, Cellebrite achieved `EL1` kernel root in `BFU` (allowing live RAM persistence if the owner later unlocked without rebooting, or brute-forcing weak PINs on legacy non-`Weaver` devices!). Against a modern handset running `StrongBox` `Weaver` ([Chapter 4](04-keymint-weaver-throttling.md)), a high-entropy passphrase or 8+ digit PIN, *and* hardware `USB Protection` (`enableUsbData(false)`), powering down into `BFU` before high-risk custody crossings denies *both* `CE` decryption keys and physical USB driver enumeration [16, 116, 372].

> **Key idea.**
> `Keyguard` locks the screen; only `BFU` evicts `Credential Encrypted` keys from `ICE` silicon, and only `Identity Check` stops a shoulder-surfed PIN from overriding `BiometricPrompt` [92, 358, 362]. Yet `Identity Check` is only as trustworthy as the underlying biometric sensor's resistance to physical spoofs and Normal World frame injection, leading directly to `BiometricPrompt` strength tiers and `Passkeys` in [Chapter 13](13-biometrics-passkeys.md).

## Inspecting via ADB, Fastboot, & Attestation

Confirm that `userdata` enforces `file` (`fscrypt` v2 `File-Based Encryption`) and inspect active `FBE` cipher options and `FS_IOC_ADD_ENCRYPTION_KEY` support:

```bash
adb shell getprop ro.crypto.state
adb shell getprop ro.crypto.type
adb shell getprop ro.crypto.volume.options
adb shell getprop ro.crypto.uses_fs_ioc_add_encryption_key
```

Inspect the current user's Direct Boot cryptographic state (`RUNNING_UNLOCKED` indicates `AFU` with `CE` keys active; `RUNNING_LOCKED` indicates `BFU` with `CE` keys evicted):

```bash
adb shell dumpsys user | grep -E 'UserInfo|State:|lastLoggedIn' | head -n 8
```

Verify active USB Type-C port roles, data-lane signaling status (`usbDataStatus` / `enableUsbData` USB Protection), and connected peripheral classes via `dumpsys usb`:

```bash
adb shell dumpsys usb | grep -iE 'currentMode|usbDataStatus|powerBrick|connected' | head -n 10
```

On a developer/root test build (`adb root`), verify `dm-default-key` `AES-256-XTS` Metadata Encryption and `inlinecrypt` mount flags on `/data`:

```bash
adb shell mount | grep ' /data '
```
