# CloudKit End-to-End Encryption, HSM Escrow, and Advanced Data Protection

## Overview

* **Link in the Chain:** First off-device cloud custody layer opening Part IV; extends local `SEP` keybags ([Chapter 3](03-secure-enclave.md)) and Data Protection Keychains ([Chapter 11](11-keychain-stolen-device.md)) into `CloudKit` Protected Cloud Storage (`PCS`), `Octagon` peer trust cliques, verifiable Cloud `HSM` recovery, and zero-knowledge user backups.
* **Core Security Invariant:** Under `Advanced Data Protection` (`ADP`), `PCS` service root keys across 25+ data categories (`iCloud Backup`, `Photos`, `iCloud Drive`, `Notes`, `Messages in iCloud`) reside exclusively inside the user's `SEP`-anchored `Octagon` / `CKKS` synced circle (plus optional `Recovery Key` or `Recovery Contact`), while Standard `iCloud Keychain` escrow seals recovery bottles inside custom `aks` Cloud `HSM` clusters running client-verified `M`-of-`N` Apple-signed firmware with a strict 10-attempt hardware destruction counter.
* **Platform Matrix:** Unified `CloudKit` `PCS`, `CKKS` `AES-SIV-512` syncing, and `Octagon` clique membership across `iOS` (`16.2+`), `iPadOS` (`16.2+`), `macOS` (`13.1+`), `watchOS` (`9.2+`), `tvOS` (`16.2+`), and `visionOS` (`1.0+`); enforces an account-wide minimum OS gate before purging server keys and restricts user-controllable `CKKS` views on shared `tvOS` / `HomePod` appliances.
* **Trusted Computing Base (TCB):** Every enrolled trusted client device (`SEP`, `secd`, `TrustedPeersHelper`, `cloudd`, `CoreCDP`), `Octagon` peer-signing keys, custom Apple Cloud Security Modules (`aks` `HSM`s) and their officer-quorum firmware signatures when Standard escrow is active, and ephemeral trusted-device session approval when `iCloud.com` web access is temporarily enabled.
* **Failure Horizon & Handoff:** Adding a rogue device to the `Octagon` clique exposes all `TLK`s, `iCloud Mail`/`Contacts`/`Calendars` remain server-decryptable for `SMTP`/`IMAP`/`CalDAV`/`CardDAV` interoperability, structural metadata checksums remain under Standard encryption, and sovereign legal mandates forced regional `ADP` withdrawal in the United Kingdom (`2025-2026`, [Chapter 20](20-mercenary-chains-compulsion.md)); hands off post-quantum transport ratcheting and directory transparency to [Chapter 16](16-imessage-pq3-kt.md).

## Threat Model & Design Tension

Tangling per-file `XTS-AES` keys through an unreadable 256-bit silicon `UID` inside `SEP` ([Chapter 10](10-apfs-data-protection.md)) makes a locked `iPhone` formidable against physical laboratory extraction, yet that local guarantee evaporates overnight if the handset uploads an automatic `iCloud Backup` whose root wrapping keys sit inside an Apple data-center key store [11, 418, 419]. Against a cloud-plane adversary (whether an external attacker compromising multi-tenant object storage, a privileged cloud infrastructure insider, a commercial forensics suite replaying captured authentication tokens via `ElcomSoft`-style cloud pullers [418], or a government agency serving binding legal process on the service provider [27, 420]), confidentiality reduces to a single architectural question: *does Apple possess a cryptographic path to unwrap the user's service keys?*

Moving a consumer ecosystem of more than one billion active accounts to pure client-only End-to-End Encryption (`E2EE`), however, collides head-on with the *custody-availability trilemma* studied across decades of security engineering [11, 421, 422]. Suppose a user owns exactly *one* Apple device (an `iPhone`), drops that phone into a river, has forgotten their Apple Account password, and never printed a recovery code. In a strict zero-escrow cryptosystem, nobody on earth can decrypt their cloud ciphertext: decades of irreplaceable family photographs, notes, and saved passwords are lost permanently [419, 422]. Deploying unrecoverable E2EE unconditionally by default would inflict catastrophic data loss on millions of non-technical single-device households every year.

Apple resolved that trilemma through two layered cryptographic designs [11, 421, 423, 424]. First, for high-sensitivity baseline secrets (`Passwords & Keychain`, `Passkeys`, `Health`, `Payment`, and `Octagon`-synced `PCS` keys) under out-of-the-box *Standard Data Protection*, Apple engineered a *Verifiable Cloud HSM Escrow* fleet (`aks` Cloud Security Modules): recovery bottles are sealed to tamper-responsive hardware modules running client-audited, officer-quorum-signed firmware that verifies the user's device passcode over a blind `SRP` channel and *permanently self-destructs the escrow record on the 10th failed guess* [421, 423]. Second, for users who establish out-of-Apple recovery redundancy via multiple trusted devices, a peer-wrapped *Account Recovery Contact* (`OTCustodianRecoveryKey`), or a self-custodied 28-character *Recovery Key* (`SecRecoveryKey`), *Advanced Data Protection for iCloud (`ADP`)* deletes Apple's server-held keys and rotates root wrapping keys into the user's `SEP`-anchored `Octagon` clique across 25+ `CloudKit` categories [11, 424, 425, 426].

## Silicon & System Mechanics

### CloudKit Protected Cloud Storage (PCS), CKKS Views, and the Standard vs. ADP Split

Every modern `iCloud` application persists structured records and binary asset blobs inside *CloudKit*, managed locally by `cloudd` and bound cryptographically to `secd` via *Protected Cloud Storage (`PCS`)* and *CloudKit Keychain Syncing (`CKKS`)* [11, 427, 428, 429]. Inside `apple-oss-distributions/Security` (`keychain/ckks/CKKS.h` and `keychain/securityd/SecItemSchema.c`), `CKKS` partitions synced Keychain state into logical *views* (`vwht`), each governed by a three-level symmetric key hierarchy: a 256-bit *Top-Level Key (`SecCKKSKeyClassTLK`)* wraps per-lock-state intermediate class keys (`SecCKKSKeyClassA` for unlocked-only items and `SecCKKSKeyClassC` for `AFU`-accessible items), which in turn wrap individual `SecCKRecordItemType` records encrypted on the client using deterministic/nonce-misuse-resistant 512-bit `RFC 5297` *`AES-SIV`* (`CKKSItemEncryptionVersion2`, authenticating all record fields including unknown future schema extensions and padding payloads to `SecCKKSItemPaddingBlockSize` blocks to suppress secret-length side channels) [339, 428, 430].

Because `CloudKit` itself acts as an untrusted transport and storage relay under `CKKS`, `CKKS.h` enforces strict state-machine invariants against server equivocation, replay, and split-brain key creation [428]. Every peer publishes signed `SecCKRecordDeviceStateType` heartbeats (`OctagonPeerID`, `KeyState`, `CurrentTLK`) alongside signed `SecCKRecordManifestType` and `SecCKRecordManifestLeafType` digests (`ManifestGenerationCountKey`, `ManifestSignaturesKey`) committing to the active item set so `CloudKit` cannot silently roll back deleted credentials or replay stale rows [428]. If two offline devices simultaneously initialize a zone and attempt to mint competing root keys (`CKKSSplitKeyHierarchy`, error `32`), `CKKS` arbitrates a single canonical `SecCKRecordCurrentKeyType` pointer and transitions lagging peers through `SecCKKSZoneKeyStateWaitForTLK` and `SecCKKSZoneKeyStateHealTLKShares` until every `Octagon` clique member converges on the exact same `TLK` [428].

![Figure: Octagon SEP peer clique, CKKS Top-Level Key (TLK) views, and the four-tier CloudKit Protected Cloud Storage (PCS) key-wrapping hierarchy.](diagrams/15-extra-octagon-clique-pcs-hierarchy.svg)

Crucially, `SecItemSchema.c` and `CKKS.h` store the user's asymmetric *`PCS` Service Identities* (`pcss` `SecCKRecordPCSServiceIdentifier`, `pcsk` `SecCKRecordPCSPublicKey`, and `pcsi` `SecCKRecordPCSPublicIdentity`) directly inside `CKKS`-synced Keychain rows [339, 428, 429]. Above raw object storage (`S3`/Apple blob stores), `CloudKit` mirrors data organization with a four-tier `RFC 3394` `AES-KW` and `AES-256-GCM` wrapping tree rooted in each category's `PCS` Service Key [11, 306, 427, 431]:

$$K_{\text{PCS-Service}} \xrightarrow{\text{wraps}} K_{\text{Zone}} \xrightarrow{\text{wraps}} K_{\text{Record}} \xrightarrow{\text{wraps}} K_{\text{Field / Asset Chunk}}$$

Whenever `Photos`, `Notes`, or `iCloud Drive` writes a document, `cloudd` generates a fresh random 256-bit `AES-GCM` chunk key ($K_{\text{Chunk}}$) on the client, encrypts the file bytes prior to upload, wraps $K_{\text{Chunk}}$ and encrypted field values under a per-record key ($K_{\text{Record}}$), wraps $K_{\text{Record}}$ under the `CloudKit` private database's Zone key ($K_{\text{Zone}}$), and wraps $K_{\text{Zone}}$ up to $K_{\text{PCS-Service}}$ [11, 427].

![Figure: CloudKit key-custody split contrasting Standard Data Protection (server-accessible Backup, Photos, and Drive service keys) against Advanced Data Protection (trusted-device-only SEP custody across 23+ categories).](diagrams/15-standard-icloud-vs-adp.svg)

Because every file chunk and record is *already* client-encrypted under this `PCS` tree, the architectural boundary between *Standard Data Protection* and *Advanced Data Protection (`ADP`)* reduces cleanly to *who holds $K_{\text{PCS-Service}}$* [11, 419, 427]:

| Protection Tier / Scope | Representative `iCloud` Data Categories | Custody of $K_{\text{PCS-Service}}$ | Cloud Breach / Compulsion Exposure |
|---|---|---|---|
| Always E2EE (`15` Default Categories) | `Passwords & Keychain`, `Health`, `Home`, `Payment`, `Memoji`, `Safari` History/Tabs, `Maps`, `Screen Time`, `Messages`* | Exclusively inside user's `CKKS` / `Octagon` trusted-device circle | Unreadable by Apple (*`Messages` key copied into Backup if Standard `iCloud Backup` is on) |
| Upgraded to E2EE by `ADP` (`10+` Bulk Categories, `25+` Total) | `iCloud Backup` (including `Messages` backup key), `Photos`, `iCloud Drive`, `Notes`, `Reminders`, `Safari Bookmarks`, `Voice Memos`, `Wallet Passes`, `Freeform` | Apple data-center key servers under Standard; rotated into `Octagon`-only custody under `ADP` | Recoverable by Apple under Standard; zero-knowledge ciphertext under `ADP` |
| Operational Metadata & Dedup Checksums | Backup timestamps/sizes/serials, file/photo byte checksums, modification dates, `.pkg` signatures | Standard server-held encryption keys (even when `ADP` is active) | Exposes structural object metadata & dedup hashes, not file/photo plaintext |
| Legacy Open-Protocol Interop Excluded | `iCloud Mail`, `Contacts`, `Calendars` (plus CalDAV-synced Reminders & public `Freeform` copy links) | Apple mail/PIM servers (`TLS` in transit + server keys at rest) | Plaintext accessible to server for `SMTP`, `IMAP4`, `CardDAV`, and `CalDAV` |

Notice the famous *`iCloud Backup` side door* under Standard protection [11, 418, 419]: when `iCloud Backup` is turned *off*, `Messages in iCloud` stores its `PCS` service key exclusively inside `CKKS` (true E2EE); turning *on* Standard `iCloud Backup` places a recoverable copy of the `Messages in iCloud` encryption key inside the backup container (whose own $K_{\text{PCS-Service}}$ sits in Apple's data-center key store) so a single-device user restoring from backup recovers message history [11].

Enabling *Advanced Data Protection* (`kSecEntitlementPrivateOctagonWalrus` / `CoreCDP` `cdp`, [11, 424, 432]) executes a three-phase cryptographic cutover. First, `AuthKit` and `Octagon` verify that *every* device signed into the Apple Account meets the `ADP` OS floor (`iOS 16.2+`, `iPadOS 16.2+`, `macOS 13.1+`, `watchOS 9.2+`, `tvOS 16.2+`, `visionOS 1.0+`, and current *iCloud for Windows*) so no legacy client can re-upload unwrapped `PCS` keys, and verify that the user has enrolled at least one `Recovery Contact` or 28-character `Recovery Key` [11, 424]. Second, the initiating trusted device commands Apple's `CloudKit` key servers to permanently delete all server-stored copies of $K_{\text{PCS-Service}}^{\text{old}}$ across `Backup`, `Photos`, `Drive`, `Notes`, and all upgraded containers [11, 424]. Third, to guarantee post-enrollment forward secrecy against any hypothetical prior compromise of Apple's server key store, the client generates fresh 256-bit $K_{\text{PCS-Service}}^{\text{new}}$ keys strictly inside its `Octagon`-synced `CKKS` views [11, 424]. Simultaneously, `ADP` disables `iCloud.com` web access by default so Apple servers never need standing decryption keys to render browser views; if a user explicitly enables *"Access iCloud Data on the Web,"* Apple still receives zero persistent `PCS` keys. Instead, each web login dispatches a live notification to the user's physically unlocked `iPhone` or `Mac`, establishing an ephemeral end-to-end encrypted tunnel directly between the trusted device's `SEP`/`Octagon` client and WebCrypto inside the user's browser to wrap short-lived, service-specific session keys valid only for that browser session [424, 433].

Why do `iCloud Mail`, `Contacts`, and `Calendars` remain un-E2EE even under `ADP`? Because global email (`RFC 5321` `SMTP` / `RFC 9051` `IMAP4rev2`) arrives unencrypted from arbitrary external mail transfer agents (`@gmail.com`, `@corp.com`) expecting server-side spam filtering and indexing, while `RFC 4791` `CalDAV` and `RFC 6352` `CardDAV` require server-evaluated time-range queries and invitation scheduling (Apple provides optional `S/MIME` for per-message email encryption) [11, 434]. Apple likewise documents explicit collaboration bounds in `102651`: `iCloud` shared folders/notes/albums remain E2EE under `ADP` *only* when every participant has `ADP` enabled; `Apple Invites` reverts published event details to Standard encryption unless host and *all* guests run `ADP`; and `Freeform` *"Send a Copy"* links store a cleartext snapshot while the link remains active [11].

### Octagon Peer Cliques, Verifiable Cloud HSM Escrow (aks), and Recovery Keys

How do a user's `iPhone`, `MacBook`, and `Apple Vision Pro` synchronize `CKKS` `TLK`s without trusting Apple's `CloudKit` (`Cuttlefish`) relay server? Through *Octagon* (`keychain/ot/OTClique.h`, `OctagonStateMachine.m`, and `keychain/TrustedPeersHelper/`), a cryptographic peer-to-peer *clique* that superseded Apple's first-generation `SecureObjectSync` (`SOSCloudCircle` in `keychain/SecureObjectSync/`) mesh [421, 432, 435, 436]. Under legacy `SOS`, devices exchanged gossip-style key-value circle diffs (`SOSPeerInfo` and `SOSEngine`) directly over iCloud key-value storage, which frequently suffered non-convergent split circles whenever a user rotated passcodes or restored devices while an older iPad sat powered off in a drawer [432, 436]. `Octagon` replaced ad-hoc `SOS` gossip with an explicit, `Cuttlefish`-ordered epoch log audited by `TrustedPeersHelper`: each device generates persistent `SEP`-bound `Octagon` peer signing and encryption keys (`P-384` / `P-256`) and commits monotonically numbered trust-state transitions [432, 435]. Signing into `GrandSlam` (`SRP-6a` + 2FA, [Chapter 13](13-accounts-passkeys-continuity.md)) on a brand-new Mac leaves the Mac in `CliqueStatusNotIn`: `CloudKit` authentication alone *never* unlocks `Octagon` [432]! To transition into `CliqueStatusIn`, either an existing clique peer establishes a local/APNs `KCPairingChannel` (`setupPairingChannelAsInitiator` / `Acceptor` during Quick Start piggybacking) or the user proves possession of an existing trusted device's passcode, prompting `TrustedPeersHelper` on an existing peer to sign a cryptographic *Join Voucher* endorsing the new Mac's `Octagon` peer public keys into the signed circle manifest and uploading `SecCKRecordTLKShareType` records wrapping each `CKKS` `TLK` directly to the new Mac's `ReceiverPublicEncryptionKey` [428, 432, 435].

When a Standard Data Protection user owns only *one* `iPhone`, skips manual recovery keys, loses that phone, and signs in on a replacement `iPhone`, `Octagon` recovers `CKKS` `TLK`s from an encrypted *escrow bottle* (`OTBottleIDs`) guarded by Apple's custom *Cloud Security Modules (`aks` HSMs)* [421, 423, 432].

![Figure: iCloud Keychain verifiable Cloud HSM escrow sequence: client audits M-of-N Apple-signed HSM firmware before sealing backup under SRP passcode proof and a strict 10-attempt destruction counter.](diagrams/15-icloud-keychain-hsm-escrow.svg)

Positioned topographically behind `iCloud`, each `HSM` cluster runs `SEP`-derived hardware and firmware signed by an *`M`-of-`N` threshold quorum* of distinct Apple officer keys [421, 423]. Before an `iPhone` ever seals a Keychain escrow record, `secd` verifies the `HSM` cluster's `X.509` public key *and* audits the `M`-of-`N` officer signatures over the `HSM` firmware digest locally on the client, ensuring no single rogue Apple engineer or compelled administrator can deploy backdoored `HSM` code that ignores attempt counters [421, 423]. During recovery (`performEscrowRecoveryWithContextData` in `OTClique.h`), after passing `GSA` login and SMS/2FA verification, the new device executes a zero-knowledge `SRP` handshake *directly into the `HSM` cluster* using the user's former device passcode (`iCloud Security Code`), so Apple's front-end servers see only opaque `SRP` transcripts [423, 432]:

$$\text{Unwrap}_{\text{HSM}}(\text{Bottle}) \iff \text{Verify}_{\text{SRP}}(\text{Passcode}) \;\land\; \Bigl(\sum_{j=1}^{m} \mathbb{I}\bigl[\text{Attempts}_j < 10\bigr] > \frac{m}{2}\Bigr)$$

Each member of the `HSM` cluster independently verifies the per-record retry counter (`MaxAttempts = 10`): after several wrong guesses, the record locks pending an Apple Support cool-down call; on the *10th failed attempt*, the `HSM` cluster *permanently destroys the escrow record*, sacrificing availability rather than permitting brute-force passcode search (and any physical tamper or firmware modification wipes the cluster private key outright, notifying affected owners to re-enroll) [423].

Under `ADP` (or whenever a user opts into self-sovereign recovery), two cryptographic mechanisms in `apple-oss-distributions/Security` replace Apple-assisted account recovery [425, 426, 437, 438]. First, generating a *28-Character Recovery Key* (`SecRKCreateRecoveryKeyString` in `OSX/sec/Security/SecRecoveryKey.m`, `kSecPasswordTypeiCloudRecoveryKey` carrying $> 128\text{ bits}$ of entropy) permanently disables Apple's `iforgot` account-recovery assistance [425, 437]. `SecRecoveryKey.m` stretches the 28-character `UTF-8` basecode inside `SecCFAllocatorZeroize` scratch memory via `cchkdf` (`HKDF-SHA256`, `FIPS 180-4` / `RFC 5869`) across domain-separated `info` labels (`"Backu Publickey"` $\to$ 128-byte seed deterministically generating a compact `P-256` keypair via `ccec_generate_key_deterministic` to wrap `Octagon` bottles, plus `"Master Key Idet"` and a 40,000-iteration `kAppleIDAuthSupportProtocolSRPGROUP2048SHA256PBKDF` verifier so Apple never sees the raw Recovery Key during recovery!) [84, 425]. Second, enrolling an *Account Recovery Contact* (`OTCreateCustodianRecoveryKeyOperation.m`) generates a random `kSecPasswordTypeiCloudRecovery` secret, wraps the user's `CKKS` `viewKeySets` (`TPPBCustodianRecoveryKey_Kind_RECOVERY_KEY` salted with `altDSID`) into `CloudKit`, and sends the symmetric unwrapping share peer-to-peer (encrypted to the trusted friend or spouse's Apple Account identity) [426, 438]. Neither Apple (holding only the `CloudKit` ciphertext) nor the Recovery Contact alone (holding only the custodian wrapping share until generating a time-limited 6-digit recovery release code for the user) can decrypt the vault unilaterally [426, 438]. A parallel split-custody construction in `OTCreateInheritanceKeyOperation.m` (`OTInheritanceKey`) powers *Digital Legacy* contacts: the user prints or shares an `InheritanceKey` claim/wrapping secret with a designated heir while `Octagon` uploads the encrypted `TLK` bundle to `CloudKit`, ensuring that neither Apple (without the heir's offline wrapping key) nor the heir (before Apple verifies a death certificate to release the `CloudKit` inheritance blob) can access the estate's `ADP` data prematurely [426, 432, 438].

## Platform Forks Across Apple OSes

`Octagon` and `CKKS` enforce strict *weakest-link fleet coherence* across `iOS`, `iPadOS`, `macOS`, `watchOS`, `tvOS`, and `visionOS` [11, 424, 432]. Because a single legacy `iPad` running `iOS 15` or an old MacBook running `macOS Monterey 12` signed into the same Apple Account would lack `ADP` `PCS` rotation logic and could re-upload unwrapped service keys to Apple servers, `CoreCDP` refuses to activate `ADP` until every attached device is either upgraded past the `iOS 16.2` / `macOS 13.1` / `watchOS 9.2` / `tvOS 16.2` floor or evicted from the account (`removeFriendsInClique` in `OTClique.h`) [424, 432]. Simultaneously, `OTClique.h` marks `setUserControllableViewsSyncStatus` and recovery-key generation `API_UNAVAILABLE(watchos, tvos)`: shared living-room appliances (`Apple TV` and `HomePod`) participate in narrow Home/media `Octagon` views without syncing the user's full `Passwords`, `iCloud Backup`, or `Health` `TLK`s onto unlocked television hardware [1, 432]. Finally, an explicit organizational boundary governs *Managed Apple Accounts* provisioned through `Apple Business Manager` or `Apple School Manager` ([Chapter 14](14-ddm-platform-sso.md)): because enterprise and education tenants mandate institutional compliance, e-discovery, and administrator-assisted account resets via federated Identity Providers (`Microsoft Entra ID` / `Okta`), Managed Apple Accounts do not support user-enrolled `Advanced Data Protection` (`ADP` is strictly a personal Apple Account custody mode), reinforcing why corporate fleets isolate work secrets inside `SEP`-bound `Platform SSO` and enterprise vaults rather than personal consumer `iCloud` backups [11, 402, 424].

### Circle-Membership Trust Attacks and Forward-Rotation Semantics

Comparing commercial cloud forensics before and after `ADP` clarifies exactly how the attack surface shifted [418, 432]. Under Standard Data Protection, forensic acquisition tools (`ElcomSoft` et al.) that extracted cached `GrandSlam` authentication tokens (`GsIdmsToken` / `com.apple.gs.icloud.auth`, [Chapter 13](13-accounts-passkeys-continuity.md)) from a seized laptop could query Apple's backup servers directly and obtain server-assisted decryption of full `iCloud Backups` and `Photos` without possessing an `Octagon`-enrolled `SEP` [380, 418]. Under `ADP`, stolen HTTP bearer tokens return only `AES-256-GCM` ciphertext blobs whose `PCS` root keys Apple no longer possesses [418, 427].

Consequently, adversary focus under `ADP` shifts directly to *`Octagon` circle membership* and *sovereign enrollment policy* [28, 418, 432, 435]. If an attacker tricks or coerces a user into approving a rogue device into their Apple Account and `Octagon` clique (for example, via pre-`iOS 17.3` shoulder-surfed passcode voucher generation or physical coercion), `CKKS` dutifully wraps `SecCKRecordTLKShareType` records to the rogue peer's `SEP` public key, granting full decryption rights over every `ADP` category [48, 428, 432]. Evicting a compromised device (`removeFriendsInClique`) triggers `TLK` and `PCS` key rotation across remaining honest peers so future writes cut off the evicted device [428, 432]. Conversely, when the UK Home Office served a `Section 253` `Technical Capability Notice` under the *Investigatory Powers Act 2016* (`February 2025`), Apple could not silently read existing `ADP` users' `Octagon`-wrapped vaults because `CKKS` `TLKShare` records require an existing peer's `TrustedPeersHelper` signature; instead, Apple disabled `idmsWalrusStatus` new-user `ADP` enrollment for UK country-code accounts while contesting the mandate before the Investigatory Powers Tribunal ([Chapter 20](20-mercenary-chains-compulsion.md)) [27, 28, 380, 420].

> **Key idea.**
> Why does `ADP` enrollment rotate root `PCS` service keys ($K_{\text{PCS-Service}}^{\text{new}}$) inside `CKKS` instead of re-uploading every terabyte of existing photo and backup chunks in object storage? Because `CloudKit` already encrypted each underlying chunk with an independent random 256-bit `AES-GCM` key ($K_{\text{Chunk}}$) [11, 427]. Deleting Apple's copy of $K_{\text{PCS-Service}}^{\text{old}}$ severs live server access immediately without petabyte re-encryption storms, while minting $K_{\text{PCS-Service}}^{\text{new}}$ exclusively inside `Octagon` guarantees forward secrecy for every subsequent backup, photo, and document even against an adversary who had compromised historical key-server backups prior to `ADP` activation [11, 419, 424]!

`Advanced Data Protection` achieves zero-knowledge confidentiality for data *at rest* inside a single user's `Octagon` circle. When two *separate* users exchange real-time `iMessage` traffic across untrusted networks, however, two harder cryptographic adversaries emerge: a nation-state recording encrypted traffic today for decryption on a future cryptanalytically relevant quantum computer (*harvest-now, decrypt-later*), and a compromised or compelled directory server (`IDS`) silently injecting a ghost public key into a conversation. [Chapter 16](16-imessage-pq3-kt.md) derives `PQ3` post-quantum ratcheting and `Contact Key Verification` (`KT`).
