# De-Privileged Runtimes: gVisor User-Space Kernels and KVM Micro-VMs

## Overview

* **Link in the Chain:** Inserts a dedicated memory-safe user-space application kernel (`Google gVisor` `runsc`) or hardware-virtualized `KVM` micro-VM boundary (`AWS Firecracker`, `Kata Containers`, `Cloud Hypervisor`, `libkrun`) between untrusted OCI containers ([Chapter 14](14-containers-escapes.md)) and the host Linux Ring 0 kernel.
* **Core Security Invariant:** Untrusted tenant machine code never invokes general-purpose host Linux system calls directly; either `gVisor` intercepts guest syscalls via `Systrap` binary hot-patching and services them in memory-safe Go inside a ~68-syscall host `seccomp` cage with zero host `open()` authority, or hardware `VT-x`/`AMD-V` (`EPT`/`NPT`) and `Arm EL2` (`Stage-2`) trap guest execution inside a dedicated per-pod Linux kernel backed by a `jailer`-confined Rust VMM (~35 host syscalls).
* **Deployment Profile Matrix:** Trusted internal microservices run on `runc`/`crun` for zero indirection cost; serverless functions (`AWS Lambda`, `Fargate`, `Cloud Run`), multi-tenant Kubernetes (`GKE Sandbox`, `AKS` Kata pods via `RuntimeClass`), and AI code sandboxes ([Chapter 17](17-ai-agent-sandboxes.md)) deploy `runsc` (`Systrap`) where nested KVM is absent or `Firecracker` / `Kata` / `Cloud Hypervisor` on bare-metal KVM; workstations use `libkrun` (`Podman` / `crun --krun`).
* **Trusted Computing Base (TCB):** For `gVisor`: Go `Sentry` + `lisafs` `Gofer` processes and ~68 argument-filtered host syscalls; for micro-VMs: CPU `EPT`/`NPT`/`Stage-2` silicon, host `KVM` (`arch/*/kvm/`), jailed ~50k-LoC Rust VMM (`Firecracker`, `Cloud Hypervisor`, `Dragonball`), `VMGenID` RNG reseeder, and sandboxed Rust `virtiofsd` or `dm-verity` block devices.
* **Integration Seam & Handoff:** Shrinks reachable host Ring 0 syscall surface by roughly 80% to 90% and contains guest kernel zero-days inside single-pod boundaries; hands off cryptographic cloud workload identity (`OIDC`, `IMDSv2`, `SPIFFE`/`SPIRE`) to [Chapter 16](16-workload-identity-spiffe.md) and AI coding agent confinement to [Chapter 17](17-ai-agent-sandboxes.md).

## Problem Statement & Threat Model

In [Chapter 14](14-containers-escapes.md), we saw why shared-kernel `runc` and `crun` containers cannot safely isolate adversarial tenants even under Kubernetes `PodSecurity: restricted` [437]: after dropping all POSIX capabilities and blocking roughly 44 dangerous administrative syscalls via `seccomp-BPF` (`seccomp/default.json` [390]), between 250 and 300+ complex C system calls (`futex`, `epoll_ctl`, `splice`, `vmsplice`, `mmap`, `madvise`, `sendmsg`, `setsockopt`, `OverlayFS`, `net/ipv4`) remain directly wired from every container thread into the host's single Ring 0 address space [16, 63, 438]. Because Linux's monolithic kernel executes millions of lines of C pointer arithmetic with full physical-memory privilege, any single Use-After-Free, integer overflow, or page-cache reference bug reachable through an allowed syscall compromises all sibling tenants on a 128-core Kubernetes node simultaneously [63, 438].

Conversely, traditional Infrastructure-as-a-Service virtual machines (`QEMU`/`KVM` emulating 1990s `i440fx` or `Q35` PCI motherboards, `SeaBIOS`/`OVMF` firmware, `USB`, `VGA`, `IDE`, `floppy` controllers, and roughly 1.5 to 2 million lines of C device models booting a multi-second OS image with hundreds of megabytes of guest RAM overhead) shattered the sub-second cold start, single-digit-megabyte memory density, and declarative OCI image workflow that drove container adoption [17, 38, 439].

Platform engineers building multi-tenant serverless compute (`AWS Lambda`, `Google Cloud Run`), untrusted SaaS build farms, public CTF infrastructure (`Google kCTF` [63]), or sandboxes executing LLM-generated Python and Bash payloads ([Chapter 17](17-ai-agent-sandboxes.md)) operate under an uncompromising threat model [438, 440]: assume the tenant begins with *arbitrary native Ring 3 machine-code execution* inside the container (and inside a hardware VM, assume the tenant immediately exploits a guest kernel bug to achieve *arbitrary guest Ring 0 execution*), actively fuzzing every system call, `virtio` shared-memory ring, file-sharing proxy, snapshot RNG state, and Simultaneous Multithreading (`SMT` / Hyper-Threading) cache line to escape onto the host worker node. Reconciling OCI container density with hard isolation produced two distinct architectural lineages on Linux: *User-Space Application Kernels* (`Google gVisor` [16, 438, 441]) and *Minimalist Rust KVM Micro-VMs* (`AWS Firecracker`, `Kata Containers`, `Cloud Hypervisor`, and `libkrun` [17, 38, 79, 442]).

## Kernel & Userspace Mechanics

### User-Space Application Kernels: Google `gVisor` (`Sentry`, `Gofer`, and `Systrap`)

Deployed as an OCI-compliant runtime binary (`runsc`, selected declaratively per Kubernetes pod via `runtimeClassName: gvisor` [443]), Google `gVisor` [16, 438] severs direct access to the host Linux syscall table without requiring hardware virtualization. Instead of letting untrusted container threads invoke host Ring 0 C syscalls, `gVisor` routes every guest system call into a dedicated per-sandbox user-space kernel called the `Sentry`, written in memory-safe, bounds-checked, garbage-collected Go [16, 438]:

![Figure: Architectural trade-off matrix comparing shared-kernel OCI containers (runc/crun), memory-safe Go user-space kernels (gVisor Sentry + Gofer), and hardware-virtualized KVM micro-VMs (Firecracker, Kata Containers, Cloud Hypervisor).](diagrams/15-shared-kernel-vs-gvisor-microvm.svg)

Inside `Sentry`, `gVisor` implements a clean-room Linux ABI (`pkg/sentry/`: virtual memory management `mm`, virtual filesystem `vfs2`, pipe/shm IPC, signal delivery, `/proc` synthesis, and a complete user-space TCP/IP network stack `netstack` operating over raw packets read from the pod's `veth` FD so untrusted `socket()`, `setsockopt()`, and malformed TCP segments never touch host `net/ipv4` or `nf_tables`!) [16, 438]. Yet `gVisor`'s security model explicitly refuses to assume `Sentry` itself is bug-free (`Defense-in-Depth` [438]): what if an attacker triggers a logic error (`CVE-2018-19333` in `shm` reference counting [444]) or corrupts a Go slice race inside `Sentry`?

Inspect `runsc/boot/filter/config/config_main.go` [445] to see how tightly `Sentry` cages *itself* against the host kernel before executing a single guest instruction. First, `runsc` places `Sentry` inside isolated `user`, `pid`, `mount`, `ipc`, `uts`, and `net` namespaces, `pivot_root`s into an empty read-only directory, and drops all capabilities. Second, `runsc` installs a precompiled host `seccomp-BPF` filter over `Sentry` permitting roughly *68 host system calls in total* (~53 core unconditional or strictly argument-masked syscalls in `allowedSyscalls` such as `mmap`, `munmap`, `mprotect`, `futex` masked strictly to `FUTEX_WAIT | FUTEX_WAKE | FUTEX_PRIVATE_FLAG`, `epoll_pwait`, `pread64`, `pwrite64`, `sendmsg`/`recvmsg` with `MSG_DONTWAIT`, `clock_gettime`, and `getrandom`, plus ~15 conditional socket/FD helpers) [445]! Notice what is *completely absent* from `Sentry`'s base host `seccomp` filter: `Sentry` cannot call host `open()` or `openat()`, cannot create new host network sockets, cannot call `execve()`, `ioctl()` (save safe terminal/FIONREAD codes), `bpf()`, `keyctl()`, or `io_uring_setup()` [438, 445]!

How, then, does a container inside `gVisor` read files from its OCI image or mounted volumes if `Sentry` cannot open host paths? `runsc` spawns a *second*, separate per-pod host helper process called the `Gofer` [16, 438, 446]. Confined inside its own `chroot`/`pivot_root` rooted at the container's bundle directory with dropped capabilities and its own restrictive `seccomp` filter, `Gofer` speaks `gVisor`'s custom `lisafs` (*Linux Sandbox Filesystem*, introduced in 2021-2022 to replace chatty `9P2000.L` path walks [446]) over a pre-connected `AF_UNIX` socketpair, passing validated open file descriptors back to `Sentry` via `SCM_RIGHTS` (or under `directfs` mode, handing `Sentry` pre-anchored directory FDs restricted by `seccomp` exclusively to non-negative `dirfd`s with `O_NOFOLLOW` enforced so `AT_FDCWD` host-relative opens die with `SIGSYS`! [445, 446]). Even here, strict device filtering at the `Gofer` boundary is mandatory: in `CVE-2026-96812` (`GHSA-3chr-j932-q9pc` [447]), `gVisor` versions prior to commit `573a9e73cf844f` on hosts with Character-Device-in-Userspace (`CUSE`) enabled allowed a malicious container image containing a `/dev/cuse` character node to open host `/dev/cuse` through `Gofer`, register a fake host device, and exploit unrestricted `CUSE` `ioctl` handling to corrupt root `udev` helpers!

The hardest systems-engineering challenge inside `gVisor` has always been *syscall interception latency*: how does `Sentry` trap every guest `syscall` instruction without allowing the guest thread to reach host Ring 0 [439, 441]? Compare `gVisor`'s three interception platforms (`--platform=`) culminating in `Systrap`:

![Figure: Side-by-side internal architecture of gVisor's Systrap user-space kernel (7-byte binary hot-patching into shared-memory rings + 68-syscall Sentry seccomp cage) versus AWS Firecracker + jailer (hardware EPT/Stage-2 KVM micro-VM + 35-syscall VMM seccomp cage).](diagrams/15-extra-gvisor-systrap-vs-firecracker-jailer.svg)

Early `gVisor` defaulted to `ptrace` (`PTRACE_SYSEMU`): portable across every cloud VM lacking `/dev/kvm`, yet requiring four privilege-ring transitions and two kernel scheduler context switches per intercepted syscall, inflicting multi-microsecond penalties quantified in USENIX `HotCloud '19` (`The True Cost of Containing` [439]). Its alternative `KVM` platform mapped `Sentry` into guest Ring 0 via `/dev/kvm` to catch `SYSCALL` via CPU ring switches, achieving better bare-metal speed while failing or degrading sharply under cloud nested virtualization [441].

Released in April 2023 and now `gVisor`'s default platform, `Systrap` [441] eliminates *both* `/dev/kvm` dependencies and `ptrace` scheduler round-trips through dynamic binary hot-patching! When `runsc` initializes a guest executor process under `Systrap`, it installs a tiny `seccomp-BPF` filter returning `SECCOMP_RET_TRAP` on any system call, causing the host kernel to deliver `SIGSYS` (`si_call_addr`) instead of executing the host syscall [104, 441]. On `x86_64`, almost every `glibc` and Go syscall site consists of a 5-byte `mov sysno, %eax` instruction immediately followed by the 2-byte `syscall` (`0f 05`) opcode, forming *7 contiguous bytes in total*! The very first time a call site executes, `SIGSYS` fires; `Systrap`'s signal handler inspects those 7 bytes and asks `Sentry` to atomically overwrite `mov sysno, %eax; syscall` in guest memory with a 7-byte indirect jump `jmp *%gs:offset` (encoding the syscall number inside `offset`!) targeting a trampoline mapped into guest user space [441]!

On every subsequent invocation of that call site, the guest thread *never executes `syscall` and never traps into host Ring 0 at all*: it jumps purely in Ring 3 into the trampoline, saves thread registers into a shared-memory `sysmsg` context structure, and wakes a spinning `Sentry` worker thread via lock-free shared-memory polling (falling back to `futex` only when idle) in sub-hundreds of nanoseconds [441]! On `ARM64` (`AArch64`), where fixed-width 4-byte `svc #0` instructions leave only 4 bytes at the call site, `Systrap` combines `SIGSYS` shared-memory handoff with branch-range trampolines to preserve identical zero-KVM portability across AWS Graviton and Ampere cloud instances. What if a hostile tenant crafts self-modifying shellcode or jumps into a misaligned `0f 05` byte pair lacking a preceding 5-byte `mov`? Because the mandatory `SECCOMP_RET_TRAP` filter remains permanently pinned in host Ring 0 across every executor thread, any unpatched `syscall` instruction traps safely into `SIGSYS` with zero possibility of reaching the host syscall table directly [104, 441].

### Lightweight Hardware Micro-VMs: `AWS Firecracker`, `jailer`, and the `VMGenID` Snapshot RNG Hazard

Where `gVisor` reimplements the Linux ABI in Go (occasionally differing on esoteric `/proc` files, raw `io_uring`, in-pod `eBPF`, or direct PCIe `VFIO` GPU passthrough), hardware `KVM` Micro-VMs run an unmodified, stripped *real Linux guest kernel* isolated behind CPU Second-Level Address Translation (`Intel VT-x` + `EPT`, `AMD-V` + `NPT`, or `Armv8/v9 EL2` + `Stage-2` page tables [88, 89]) while surgically amputating 95% of `QEMU`'s legacy VMM attack surface [17, 440]:

![Figure: End-to-end execution and I/O datapath of a KVM micro-VM container (Kata Containers, Firecracker, Cloud Hypervisor), isolating untrusted guest Ring 3 and guest Ring 0 behind hardware EPT/Stage-2 page tables and a seccomp-jailed Rust VMM.](diagrams/15-firecracker-kata-datapath.svg)

Open-sourced by Amazon Web Services in memory-safe Rust (`rust-vmm` crates [448]) to power multi-tenant `AWS Lambda` and `AWS Fargate` (`USENIX NSDI '20` [17]), `Firecracker` (`~50,000` LoC of Rust versus `QEMU`'s `~2,000,000` LoC of C) strips virtual motherboard emulation down to the bare minimum required to run modern Linux workloads [17, 440]: zero `BIOS`/`UEFI` firmware (loading uncompressed `vmlinux` directly into guest physical RAM via the Linux direct-boot protocol), zero PCI/USB/VGA/IDE buses, exposing solely `virtio-net` (backed by host TAP devices), `virtio-blk` (backed by host files/volumes), `virtio-vsock` (host-to-guest socket channel), `virtio-balloon` and `virtio-rng`, a minimal MicroVM Metadata Service (`MMDS` v2 requiring session-token headers similar to `IMDSv2` in [Chapter 16](16-workload-identity-spiffe.md) to block guest SSRF!), CPU feature-masking templates (`T2`, `T2S`, `T2CL`, `V1N1` ensuring uniform speculative-execution mitigation flags across heterogeneous fleet migrations), a minimal serial console, KVM `PIC`/`IOAPIC`/`PIT` interrupt timers, and a single-purpose `i8042` keyboard-reset register used solely to signal VM exit [440]! Every `Firecracker` micro-VM consumes `< 5 MiB` of VMM memory overhead, cold-boots a minimal guest kernel to user space in `~125 ms`, sustains creation bursts of `150+` micro-VMs/sec per host, and enforces dual token-bucket rate limiters (capping both bandwidth bytes/sec and operations/sec) on every `virtio-net` and `virtio-blk` queue so a noisy tenant cannot saturate shared host NICs or NVMe drives [17, 440].

Assume a sophisticated tenant exploits a zero-day inside the *guest* Linux kernel (achieving guest Ring 0) and fuzzes `Firecracker`'s `virtio` descriptor rings from guest physical memory (as occurred in `CVE-2019-18960` [449], an early bounds-check flaw in `Firecracker` `0.18`/`0.19`'s `virtio-vsock` buffer handling). Two independent host barriers contain the blast radius (`docs/design.md` and `docs/jailer.md` [440, 450]):
First, inside `Firecracker` itself, each micro-VM process splits execution across three thread classes (`API` control-plane thread, single `epoll`-driven `VMM` device-emulation thread, and one `vCPU` `KVM_RUN` thread per guest core), compiling and loading *separate per-thread `seccomp-BPF` allowlists* (~35 syscalls in total, locking `ioctl()` down to exact integer `KVM_*` and `TUN*` command codes; any unexpected syscall kills the process instantly via `SECCOMP_RET_KILL_PROCESS`!) [440, 450].
Second, in production `Firecracker` is never launched directly as root; operators invoke the companion `jailer` binary (`jailer --id <uuid> --exec-file /usr/bin/firecracker --uid <u_id> --gid <g_id> --cgroup-version 2 --netns ...` [450]). Before `Firecracker` ever parses an API request or starts a vCPU, `jailer` validates the 64-char VM ID, closes every inherited FD above `STDERR`, wipes `environ`, copies `firecracker` into `/srv/jailer/firecracker/<uuid>/root/`, sets `RLIMIT_FSIZE` and `RLIMIT_NOFILE` ceilings via `setrlimit()`, moves the task into dedicated `cgroups v2` (`cpu.max`, `memory.max`, `cpuset.cpus`) and `CLONE_NEWNET` (+ optional `--new-pid-ns` `CLONE_NEWPID`), calls `unshare(CLONE_NEWNS)` + `pivot_root(".", "old_root")` + `umount2("old_root", MNT_DETACH)` + `chroot(".")`, creates only `/dev/kvm` and `/dev/net/tun` `chown`ed to the micro-VM's unique unprivileged `<uid>:<gid>`, drops all root privileges via `setresuid()`/`setresgid()`, and finally `execve()`s `./firecracker` [450]! Even a hypothetical RCE inside the Rust VMM lands inside an empty directory under a unique unprivileged UID with zero visibility into sibling micro-VMs!

> **Warning.**
> Sub-5-millisecond serverless cold starts (`AWS Lambda` SnapStart / on-demand container loading in `USENIX ATC '23` [451]) restore hundreds of concurrent `Firecracker` micro-VMs from a single paused guest-memory snapshot (`docs/snapshotting/snapshot-support.md` [452]). Cloning a live VM's physical RAM duplicates the guest Linux kernel's `/dev/urandom` ChaCha20 state, userspace TLS/JVM PRNG pools, and TCP sequence counters byte-for-byte across every restored clone! If two clones transmit a single TLS 1.3 record, `AES-GCM` cipher, or `ECDSA` signature before reseeding entropy, identical nonces leak the `AES-GCM` authentication key (`GHASH` polynomial recovery) and expose raw `ECDSA` private keys algebraically! Production snapshot pipelines *must* rely on `Firecracker`'s Virtual Machine Generation Identifier (`VMGenID` device enabled on x86_64 and AArch64 [452]) paired with Linux `5.18+` (`drivers/char/random.c` `vmgenid` driver by Jason A. Donenfeld [453]): during snapshot resume, *before* vCPUs execute a single guest instruction, `Firecracker` writes a fresh 16-byte random generation UUID and injects an ACPI/MMIO interrupt that forces guest Ring 0 to reseed its CSPRNG synchronously from hardware `RDRAND`/`RNDR` and `virtio-rng` while notifying userspace PRNGs to flush cached state [452, 453]!

### Kubernetes Micro-VM Ecosystems: `Kata Containers 3.x`, `Cloud Hypervisor`, `virtiofsd`, and `libkrun`

While `Firecracker` intentionally omits PCI hotplug and GPU passthrough to keep its serverless TCB minimal (integrating with `containerd` via `firecracker-containerd` block snapshotters [454]), general-purpose Kubernetes clusters schedule untrusted pods into micro-VMs transparently via `Kata Containers 3.x` (`runtimeClassName: kata` [38, 443]). When `kubelet` creates a Kata pod, the Rust shim `containerd-shim-kata-v2` boots a per-pod micro-VM using either Kata's built-in Rust VMM (`Dragonball` [455]), `Firecracker` [17], or `Cloud Hypervisor` [442] (another `rust-vmm` KVM monitor engineered specifically for modern cloud workloads requiring `VFIO` NVIDIA GPU passthrough, CPU/memory hotplug, and Confidential Computing `TDX`/`SEV-SNP` in [Chapters 18](18-confidential-vms-svsm.md) and [19](19-confidential-containers.md)), communicating with an in-guest Rust `kata-agent` (`PID 1` inside the micro-VM) over `AF_VSOCK` `ttrpc` [38].

How do OCI container rootfs layers cross from the host worker node into a `Kata` or `libkrun` micro-VM safely? Two designs compete on security versus flexibility [38, 454, 456, 457]:
First, *`virtio-fs` and Rust `virtiofsd`* [456, 457] share host overlay directories into the guest via `FUSE` protocol messages transported over a shared-memory `virtqueue` ring. Because a compromised guest kernel controls the guest side of the `virtqueue` completely, the host `virtiofsd` daemon is an exposed Ring 3 parser! Early C `virtiofsd` builds running with `CAP_DAC_READ_SEARCH` suffered `CVE-2020-35517` [458] (allowing a malicious guest to `mknod` device files inside shared directories accessible on the host) and `CVE-2022-0358` [459] (creating `S_ISGID` group-owned executables inside shared directories). Upstream replaced the C daemon entirely with a memory-safe *Rust `virtiofsd`* (`gitlab.com/virtio-fs/virtiofsd` [457]) that drops `CAP_DAC_READ_SEARCH`, locks itself inside a private `pivot_root` + user namespace + `Landlock` + `seccomp` sandbox, and resolves paths strictly with `openat2(RESOLVE_IN_ROOT | RESOLVE_BENEATH)` [103, 457]!
Second, *block-mapped `EROFS` / `dm-verity` over `virtio-blk`* (`firecracker-containerd` [454], `nydus`, and Confidential Containers [41]) attaches read-only container image layers directly as block devices verified inside the guest, eliminating host-side `FUSE` directory parsers completely! Finally, on developer laptops and edge appliances, `libkrun` (`containers/libkrun` [79]) compiles a minimalist `rust-vmm` KVM monitor directly into a shared library (`libkrun.so` invoked via `crun --krun` or `Podman`), using Transparent Socket Impersonation (`TSI`) over `virtio-vsock` to isolate untrusted local containers inside instant micro-VMs without any root VMM daemon.

## Distro, Immutable-OS, & Cloud Trade-Offs

Selecting between hardened shared-kernel `runc`/`crun` ([Chapter 14](14-containers-escapes.md)), `gVisor` (`runsc`), and `KVM` micro-VMs (`Firecracker`, `Kata`, `Cloud Hypervisor`) in production Kubernetes (`RuntimeClass` `scheduling.nodeSelector` + `overhead` pod resource accounting [443]) turns on four concrete engineering trade-offs:

| Architectural Dimension | Hardened `runc` / `crun` (`Restricted`) | `gVisor` (`runsc --platform=systrap`) | `KVM` Micro-VM (`Firecracker` / `Kata` / `Cloud Hypervisor`) |
|---|---|---|---|
| Bare-Metal / Nested-Virt Requirement | Runs anywhere on Linux (`cgroups v2`) | Runs anywhere in pure Ring 3 (zero `/dev/kvm` required!) [441] | Requires `/dev/kvm` bare metal (`AWS .metal`) or nested virt (`Azure Dv5`, `GCP C3/N2`) [17, 38] |
| Reachable Host Ring 0 Surface | ~300+ C syscalls, host VFS, host TCP/IP [390] | ~68 filtered syscalls (`Sentry` Go ABI + `netstack`) [445] | Host `KVM` + ~35 VMM syscalls (`virtio` rings) [440, 450] |
| Workload Performance Profile | 100% native CPU, memory, and VFS speed | Near-native CPU; overhead on heavy `open`/`stat` metadata storms [441, 446] | Near-100% native guest CPU & `io_uring`; `~5-30 MiB` RAM overhead per pod [17, 38] |
| ABI Fidelity & GPU (`VFIO`) Support | Full host kernel ABI | Emulated Linux ABI (no guest eBPF or kernel modules) | Real guest Linux kernel + `VFIO` GPU passthrough (`Cloud Hypervisor` + `Kata`) [38, 442] |

One critical bare-metal CPU detail governs multi-tenant `KVM` micro-VM hosts: Simultaneous Multithreading (`SMT` / Intel Hyper-Threading). Hardware `EPT` page tables cannot stop two sibling hyperthreads sharing one physical CPU core's L1 data cache and microarchitectural fill buffers from mounting cross-thread speculative attacks such as `Foreshadow` (`L1TF`, `CVE-2018-3646` [460]) or Microarchitectural Data Sampling (`MDS`). Multi-tenant bare-metal fleets either disable `SMT` (`nosmt` on the kernel command line) or enable *Linux Core Scheduling* (`prctl(PR_SCHED_CORE, ...)` in Linux `5.14+`, `Documentation/admin-guide/hw-vuln/core-scheduling.rst` [461]), assigning a unique per-micro-VM cookie so the host scheduler guarantees two different tenants' vCPU threads *never* execute simultaneously on sibling hyperthreads of the same physical core [229, 440, 461]!

## Seam Failures, CVEs, & Structural Bounds

Even behind `gVisor` or `KVM` micro-VM walls, attackers target the narrow bridges crossing back to the host: `Gofer` device passthrough, `virtio` ring parsers, `virtiofsd` FUSE handlers, snapshot RNG state, and SMT CPU caches.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| `Foreshadow` / `L1TF` Cross-HT Leak (`CVE-2018-3646`) | 2018 | Intel `EPT` + shared `SMT` L1D cache | `EPT` page tables block cross-VM physical memory reads across hyperthreads | Malicious guest faults unmapped PTE to speculatively sample L1D cache lines of sibling-thread micro-VM | Flush L1D on `VM-ENTRY`, disable `SMT`, or enforce `PR_SCHED_CORE` Core Scheduling per VM [460, 461] |
| `gVisor` `Sentry` `shm` Refcount Overwrite (`CVE-2018-19333`) | 2018 | `gVisor` `pkg/sentry/kernel/shm` | Application-kernel syscall logic has zero state bugs | Crafted `shmctl(IPC_RMID)` sequence mishandles refcounting to overwrite in-sandbox root memory | Fix `shm` refcount; contained from host escape by Go bounds checks + 68-syscall `Sentry` `seccomp` jail [444, 445] |
| `Firecracker` `virtio-vsock` Buffer Overflow (`CVE-2019-18960`) | 2019 | `Firecracker 0.18-0.19` `vsock` device | Rust VMM device ring math has zero logic slice errors | Malicious guest Ring 0 crafts `virtio-vsock` descriptor lengths triggering out-of-bounds slice access | Patch `vsock` bounds check; host blast radius contained by `jailer` `pivot_root` + 35-syscall VMM `seccomp` [449, 450] |
| C `virtiofsd` Guest `mknod` Escape (`CVE-2020-35517`) | 2021 | Legacy C `virtiofsd` (`CAP_DAC_READ_SEARCH`) | Compromised guest kernel cannot plant host device nodes over `FUSE` | Rogue guest sends `FUSE_MKNOD` creating block/char device nodes inside shared host directory | Migrate to Rust `virtiofsd` dropping capabilities + `openat2(RESOLVE_IN_ROOT)`, or use `virtio-blk` `dm-verity` [103, 457, 458] |
| `virtiofsd` `S_ISGID` Privilege Escalation (`CVE-2022-0358`) | 2022 | `virtiofsd` shared directory creation | Guest file creation strips `setgid` bits when group mismatches | Guest creates `S_ISGID` executable inside group-writable directory to escalate privileges across shared view | Strip `S_ISGID` explicitly in Rust `virtiofsd` and isolate per-pod rootfs via block snapshotters [454, 457, 459] |
| Micro-VM Snapshot CSPRNG Nonce Reuse | 2020-2023 | Cloned `Firecracker` / `QEMU` VM snapshots | Restored micro-VM clones emit unique TLS/AES-GCM/ECDSA nonces | Cloned RAM snapshots duplicate `/dev/urandom` ChaCha20 state identically across concurrent instances | Enable `Firecracker` `VMGenID` + Linux `5.18+` `vmgenid` synchronous `crng_reseed()` before vCPU resume [451, 452, 453] |
| `gVisor` `Systrap` Unpatched Opcode Fallback | 2023 | `gVisor` `Systrap` binary hot-patcher | Self-modifying guest shellcode might bypass 7-byte `jmp` rewrite | Attacker jumps into mid-instruction `0f 05` (`syscall`) lacking preceding 5-byte `mov` | Kernel `SECCOMP_RET_TRAP` (`SIGSYS`) filter remains permanently active underneath `Systrap` [104, 441] |
| `gVisor` `Gofer` `/dev/cuse` Host RCE (`CVE-2026-96812`) | 2026 | `gVisor` `Gofer` host device passthrough | Opening character nodes inside OCI image cannot register host devices | Container image ships `/dev/cuse` node; `Gofer` opens host `CUSE` allowing `ioctl` overwrite of root `udev` helper | Block host character-device passthrough in `Gofer` (`commit 573a9e73cf84`) and unload unused `cuse.ko` [447] |

Notice the directional asymmetry that still bounds both `gVisor` and `Firecracker` [16, 17]: they protect the *host infrastructure from an untrusted workload*, yet the *host kernel and cloud hypervisor still enjoy total read/write visibility into every guest micro-VM's plaintext RAM* (inverted only by hardware Confidential VMs and Confidential Containers in [Chapters 18](18-confidential-vms-svsm.md) and [19](19-confidential-containers.md)). Before crossing into Confidential Computing, two immediate cloud-runtime links must close: how an isolated `runc`, `gVisor`, or `Firecracker` pod authenticates to cloud APIs and peer services *without* static secrets or SSRF-vulnerable metadata endpoints ([Chapter 16](16-workload-identity-spiffe.md)), and how autonomous AI coding agents combine these sandboxes with network credential-brokering firewalls ([Chapter 17](17-ai-agent-sandboxes.md)).

## Inspecting on a Live Linux Host

Check whether CPU virtualization extensions (`vmx` on Intel or `svm` on AMD) and `/dev/kvm` are exposed to run `Firecracker`, `Kata`, `Cloud Hypervisor`, or `libkrun` micro-VMs:

```bash
ls -la /dev/kvm 2>/dev/null || echo "/dev/kvm not exposed (use gVisor systrap)"
grep -Ec '(vmx|svm)' /proc/cpuinfo 2>/dev/null || true
```

Audit host Simultaneous Multithreading (`SMT`) status and verify whether hardware `L1TF` / `MDS` mitigations are active in Ring 0 on multi-tenant bare metal:

```bash
cat /sys/devices/system/cpu/smt/control 2>/dev/null || true
grep . /sys/devices/system/cpu/vulnerabilities/{l1tf,mds} 2>/dev/null || true
```

Discover installed de-privileged OCI runtimes and VMMs (`runsc`, `firecracker`, `jailer`, `kata-runtime`, `cloud-hypervisor`, `krunvm`) and inspect `containerd` `RuntimeClass` handlers:

```bash
for bin in runsc firecracker jailer kata-runtime cloud-hypervisor krunvm; do command -v "$bin" 2>/dev/null; done
grep -rn "runtime_type" /etc/containerd/ 2>/dev/null | head -n 10 || true
```

Check whether the running Linux kernel includes `VMGenID` snapshot-reseed support (`CONFIG_VMGENID` / `vmgenid` ACPI driver) for cloned micro-VMs:

```bash
grep -E "CONFIG_VMGENID=" "/boot/config-$(uname -r)" 2>/dev/null || ls -d /sys/bus/acpi/drivers/vmgenid 2>/dev/null || true
```
