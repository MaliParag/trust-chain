# Mach IPC, XPC Audit Tokens, Seatbelt, and BlastDoor

## Overview

* **Link in the Chain:** Runtime inter-process communication (`IPC`), capability-broker, and parser-containment layer; governs how processes admitted by `TXM`/`AMFI` ([Chapter 6](06-amfi-txm-notarization.md)) cross privilege boundaries and fences untrusted media and web engines (`WebKit`, `BlastDoor`) inside default-deny `MACF` sandboxes.
* **Core Security Invariant:** Privileged `Mach` and `XPC` services authenticate peers exclusively via kernel-stamped `audit_token_t` trailers carrying a monotonic `pidversion` incarnation counter paired with `DER` signing requirements, while `Seatbelt` (`Sandbox.kext`) blocks every VFS path, `bootstrap_look_up` endpoint, `IOUserClient` class, and syscall outside the process's compiled state-machine profile.
* **Platform Matrix:** Shared `Mach` task/special port capabilities, `XPC` `audit_token_t`, `Sandbox.kext` bytecode interpreter, `JavaScriptCore` (`StructureID`, `Gigacage`, `APRR` JIT), and `BlastDoor` Swift airlock across all Apple OSes; forks in mandatory App Sandbox coverage (`100%` of third-party apps on `iOS`/`iPadOS`/`watchOS`/`visionOS` vs. Mac App Store mandatory and `Developer ID` opt-in on `macOS`) and EU `iOS`/`iPadOS` `BrowserEngineKit` extensions.
* **Trusted Computing Base (TCB):** `XNU` `osfmk/ipc` port right tables, `task_special_ports` gates, `launchd` bootstrap namespaces, `libxpc` and `Security.framework` requirement verifiers, `Sandbox.kext` `mac_policy_ops` bytecode VM, `IOUserClient::externalMethod` dispatch filters, `APRR` core-local JIT registers, and `MessagesBlastDoorService`.
* **Failure Horizon & Handoff:** Missing `audit_token_t` checks (`xpc_connection_get_pid` races), bugs in residual sandbox-reachable `IOKit` selectors (`IOMobileFramebuffer` `CVE-2021-30807`) or VM brokers (*DarkSword* `CVE-2025-43510`), and Turing-complete "weird machines" inside non-JIT media decoders (*FORCEDENTRY* `CVE-2021-30860`, *BLASTPASS* `CVE-2023-41064`) breach user-mode containment; hands off `macOS` user-consent privacy (`TCC`) and `SystemExtensions` to [Chapter 8](08-macos-tcc-sysext.md).

## Threat Model & Design Tension

Cryptographic code signing and `Launch Constraints` ([Chapter 6](06-amfi-txm-notarization.md)) guarantee only that `Safari`'s `WebContent` renderer, `Messages`'s attachment previewer, or a third-party utility began execution from authentic, unmodified code pages. The microsecond that process reads an untrusted `HTTPS` response, `WebGL` shader, `WebP` image, `JBIG2` stream, or zero-click `APNs`/`IDS` `iMessage` payload off the wire, data-driven memory corruption inside the parser becomes an immediate Tier 1 and Tier 3 threat [21, 44, 65]. Compounding parser exposure is `Darwin`'s deeply decomposed micro-service architecture: rather than granting ambient root or hardware privileges to user-facing apps, Apple splits operating system functionality across more than four hundred `launchd`-managed LaunchDaemons and LaunchAgents (`tccd`, `installd`, `securityd`, `mediaplaybackd`, `imagent`, plus third-party privileged helpers registered via `SMAppService`), all conversing continuously over `Mach` ports and `XPC` dictionaries [229, 230, 231].

Decomposing privileges across hundreds of cooperating processes introduces three acute security tensions. First, every IPC channel upward into a higher-privileged daemon is a potential confused-deputy privilege escalation: if a `root` `XPC` helper identifies its caller using mutable POSIX process identifiers (`pid_t` returned by `xpc_connection_get_pid()` or `NSXPCConnection.processIdentifier`) or mishandles asynchronous message reference counts (*Splitting atoms in XPC*, `CVE-2020-9839`), an unprivileged local process can race `execve()` into an Apple-signed binary mid-flight so the server validates the new binary's signature while executing the attacker's payload as `root` [232, 233, 234]. Second, `Mach`'s capability model treats a task's control port (`TASK_KERNEL_PORT`) as total ownership of that process's virtual memory and register state (`mach_vm_write`, `thread_create_running`); unless the kernel restricts task-port acquisition across platform and Hardened Runtime boundaries, compromising one user process yields instant code injection into every sibling process running under the same `UID` [229, 235, 236].

Third, legacy media, font, and document formats (`PDF`, `JBIG2`, `WebP`, `DNG`, `OpenType`, `HEVC`) carry millions of lines of C and C++ arithmetic where a single integer overflow yields arbitrary read/write inside the parser process [21, 65, 237]. Prior to `iOS 14`, `imagent` parsed incoming `iMessage` previews inside a session daemon holding ambient read access to user `Contacts`, `SMS`/`chat.db` archives, and `Photos` metadata, allowing a single zero-click packet to compromise user state without user interaction [44]. Defending runtime execution therefore requires three interlocking layers: *unforgeable kernel IPC identity* (`audit_token_t`), *compiler- and silicon-assisted renderer hardening* (`StructureID`, `Gigacage`, `APRR` JIT), and *default-deny `Seatbelt` micro-sandboxes* (`BlastDoor` and `WebContent`) that sever file, socket, syscall, and `IOKit` driver reachability before untrusted bytes are parsed [42, 44, 238].

## Silicon & System Mechanics

### Mach Special Ports, Task Port Boundaries, and launchd Bootstrap Lookup

Every inter-process boundary on `Darwin` (`XPC`, `AppleEvents`, `IOKit` user-clients, `DriverKit` RPC, and `Mach` exception handlers) rests atop `XNU`'s `Mach` IPC subsystem (`osfmk/ipc/`) [229]. A `Mach` port (`struct ipc_port` in kernel zone memory) is a unidirectional, kernel-mediated message queue referenced by user-space tasks exclusively through task-local 32-bit capability handles (`mach_port_name_t` indexing the task's `ipc_space`). Capabilities cannot be forged by guessing an integer: a process can transmit a message to a port only if its `ipc_space` already holds a `MACH_PORT_RIGHT_SEND` or single-use `MACH_PORT_RIGHT_SEND_ONCE` capability right, while exactly one task holds `MACH_PORT_RIGHT_RECEIVE` [229, 236].

Because `Mach` represents tasks, threads, hosts, and devices themselves as port-backed kernel objects, `osfmk/mach/task_special_ports.h` defines numbered *task special ports* (`task_get_special_port`) whose security sensitivity varies drastically [229, 236].

| Task Special Port Constant | ID | Capability Scope & Hardening Gate (`osfmk/`) |
|---|---|---|
| `TASK_KERNEL_PORT` | `1` | Full VM & thread control (`mach_vm_write`, `mach_vm_remap`, `thread_create_running`); blocked across `CS_PLATFORM_BINARY` & `CS_RUNTIME` |
| `TASK_HOST_PORT` | `2` | Unprivileged host info port (`host_priv_t` restricted strictly to `UID 0` and `SIP`/sandbox gates) |
| `TASK_NAME_PORT` | `3` | Identity-only handle mapping a task without exposing virtual memory or thread state |
| `TASK_BOOTSTRAP_PORT` | `4` | Inherited send right to `launchd` (`PID 1`) namespace broker (`bootstrap_look_up` filtered by `Sandbox.kext`) |
| `TASK_INSPECT_PORT` | `5` | Read-only performance/resource inspection capability (`task_info`); zero VM read or write primitives |
| `TASK_READ_PORT` | `6` | Read-only virtual memory inspection (`mach_vm_read`) separated from write/execution mutation (`macOS 11.3+`) |
| `TASK_ACCESS_PORT` | `9` | Policy gate port (`taskgated`) arbitrating `task_for_pid()` developer debugger authorization |

`TASK_KERNEL_PORT` (`1`, surfaced to a process itself via `mach_task_self()`) is the ultimate user-space control capability: any caller holding a send right to another process's `TASK_KERNEL_PORT` can invoke `mach_vm_read_overwrite()`, `mach_vm_write()`, `mach_vm_protect()`, and `thread_create_running()` (`osfmk/vm/vm_map.c`), achieving immediate arbitrary code execution inside that target process (or arbitrary `EL1` kernel read/write if acquired for `PID 0`'s `kernel_task` port, the classic jailbreak primitive analyzed in Ian Beer's *Task_t Considered Harmful*) [235, 236]. To eliminate lateral `mach_vm_write` injection without breaking crash reporters or memory profilers, `XNU` split task capabilities into strictly weaker `TASK_READ_PORT` (`6`), `TASK_INSPECT_PORT` (`5`), and `TASK_NAME_PORT` (`3`) flavors [229, 235]. Acquiring another process's `TASK_KERNEL_PORT` via `task_for_pid()` or `processor_set_tasks()` is blocked unconditionally across `TF_PLATFORM` (`CS_PLATFORM_BINARY`), `CS_RUNTIME` (Hardened Runtime), and `CS_RESTRICT` boundaries unless the target binary explicitly opts into debugging via `com.apple.security.get-task-allow` (`CS_GET_TASK_ALLOW = 0x4`) or `SIP` is disabled; on `arm64e`, `bsd/sys/spawn_internal.h` also supports pointer-authenticated task port actions (`PSPA_PTRAUTH_TASK_PORT`) [229, 235, 239].

How do isolated processes acquire initial send rights to named OS services? Every newly spawned task inherits `TASK_BOOTSTRAP_PORT` (`4`) pointing to `launchd` (`PID 1`), which maintains hierarchical bootstrap namespaces (`System`, `User`, `LoginWindow`, and per-GUI `Aqua` domains) declared via `MachServices` keys in `launchd.plist(5)` manifests [230]. When a client calls `bootstrap_look_up(bootstrap_port, "com.apple.tccd.system", &service_port)` (or opens an `xpc_connection_create_mach_service` channel), `launchd` queries `Sandbox.kext` (`mpo_mach_check_service_lookup`) against the caller's active `Seatbelt` profile; if denied, the client never receives a `MACH_PORT_RIGHT_SEND` capability to even format a request packet against the target daemon [42, 230].

### XPC audit_token_t, Monotonic pidversion, and PID-Reuse TOCTOU

Historically, system daemons defined IPC interfaces using the `Mach Interface Generator` (`MIG`), compiling `.defs` IDL specifications into C marshaling stubs. Because `MIG` required manual C lifecycle management over out-of-line (`OOL`) virtual memory descriptors and port right dispositions whenever a server handler returned an error code, subtle reference-counting mismatches repeatedly yielded exploitable port use-after-free and double-free bugs in `XNU` and system daemons [232, 236]. Apple superseded `MIG` across user space with *XPC* (`libxpc` and `NSXPCConnection`, paired with `SMAppService` in `macOS 13+` to replace legacy `SMJobBless` root helpers), providing structured, reference-counted dictionary serialization (`xpc_object_t`), on-demand `launchd` activation, and automatic sandbox/QoS propagation [231, 240].

Yet `XPC` still suffered two major vulnerability waves documented by Samuel Groß at Google Project Zero (*Splitting atoms in XPC*, including `libxpc` / daemon race conditions such as `CVE-2020-9839`) and independent macOS researchers [232, 233, 234]. Beyond type-confusion and dictionary-mutation races, hundreds of privileged `root` helpers fatally authenticated incoming `XPC` connections by calling `xpc_connection_get_pid(conn)` or `[connection processIdentifier]` (`pid_t`) and passing that integer PID into `SecCodeCopyGuestWithAttributes(NULL, @{kSecGuestAttributePid: @(pid)}, ...)` [232, 234].

![Figure: XPC peer authentication contrasting the broken POSIX pid_t TOCTOU race against XNU's unforgeable mach_msg_audit_trailer_t (audit_token_t with monotonic pidversion) and peer signing requirements.](diagrams/07-xpc-audit-token-vs-pid.svg)

To see why *every* `pid_t`-based IPC check on `Darwin` is broken by design, trace `bsd/kern/kern_exec.c` during `execve()` [234, 241]. An unprivileged, unsigned attacker binary running at `PID 4812` sends an `XPC` message (`{"cmd": "install_root_pkg"}`) to a privileged `root` daemon and, on the next instruction, calls `execve("/System/Applications/Calculator.app/Contents/MacOS/Calculator", ...)` (or exits while forking ~99,999 short-lived children until the 17-bit BSD PID counter wraps `PID 4812` onto an Apple-signed process). Because `POSIX` preserves `PID 4812` across `execve()`, by the time the scheduled `root` daemon wakes up and inspects `PID 4812` via `kSecGuestAttributePid`, `PID 4812`'s memory image is genuinely `Calculator.app` (`anchor apple`)! The daemon verifies Apple's signature on `Calculator.app` and executes the attacker's root command [232, 234].

`XNU` eliminates this `TOCTOU` race at the kernel message boundary through `mach_msg_audit_trailer_t` [234, 240]. Whenever a thread invokes `mach_msg()`, `XNU` itself (inside `EL1` before returning from the syscall) stamps an unforgeable 32-byte `audit_token_t` (`uint32_t val[8]`) onto the message trailer:

$$\tau = \bigl(\text{auid},\; \text{euid},\; \text{egid},\; \text{ruid},\; \text{rgid},\; \text{pid},\; \text{asid},\; \text{pidversion}\bigr)$$

The eighth word, `pidversion` (`p->p_idversion` in `XNU`'s `struct proc`), is a global monotonically incrementing incarnation counter assigned at `fork()` and *atomically incremented inside `kern_exec.c` on every successful `execve()` or `posix_spawn()` image replacement* [234, 241]. In our attack trace, the attacker's `XPC` message carries $(\text{pid} = 4812, \text{pidversion} = 91)$, whereas `execve("Calculator")` bumps `PID 4812`'s live kernel `p_idversion` to $92$. When the `XPC` server enforces peer identity using `xpc_connection_set_peer_code_signing_requirement(conn, req)` (or `NSXPCConnection.setCodeSigningRequirement(_:)`, or `SecTaskCreateWithAuditToken` backed by `csops_audittoken` in `bsd/sys/codesign.h`), `XNU` looks up `PID 4812` *and* requires `p->p_idversion == 91` [234, 240]. Finding $92 \neq 91$, the kernel rejects the stale `audit_token_t` with `ESRCH` before the `XPC` event handler block is ever invoked [234, 240].

> **Warning.**
> Calling `xpc_connection_get_pid()` or `NSXPCConnection.processIdentifier` for security authorization is an unconditional `TOCTOU` privilege-escalation vulnerability on `macOS` and `iOS` [232, 234]. Privileged `XPC` services must bind verification exclusively to the connection's kernel `audit_token_t` via `xpc_connection_set_peer_code_signing_requirement` and pin both `anchor apple generic` / `TeamID` and explicit `DER` client entitlements [240].

### Seatbelt (Sandbox.kext), TinyScheme Bytecode, and the IOKit User-Client Surface

Mandatory process containment across Apple OSes is enforced by *Seatbelt*, implemented in `Sandbox.kext` alongside `AppleMobileFileIntegrity.kext` atop `XNU`'s TrustedBSD Mandatory Access Control Framework (`security/mac_policy.h`) [42, 242, 243]. At boot, `Sandbox.kext` registers a `mac_policy_ops` table populating more than 120 kernel reference-monitor hooks (`mpo_vnode_check_open`, `mpo_vnode_check_exec`, `mpo_file_check_mmap`, `mpo_socket_check_connect`, `mpo_mach_check_service_lookup`, `mpo_iokit_check_open`, `mpo_proc_check_signal`, and fine-grained `syscall-unix` / `syscall-mach` bitmask interceptors) [42, 242].

Policies are authored in the *Sandbox Profile Language (`SBPL`)*, a TinyScheme Lisp dialect stored on `macOS` as `.sb` files under `/System/Library/Sandbox/Profiles/` (`application.sb`, `system.sb`, `blastdoor.sb`) [42, 238, 243]. Rather than interpreting Scheme strings inside the kernel, `libsandbox.dylib` (at launch on `macOS`, or ahead-of-time at OS build time on `iOS`/`watchOS`/`visionOS` where pre-compiled profile collections are baked directly into `BootKC`) compiles `SBPL` rules into a compact, deterministic bytecode decision graph evaluated by `Sandbox.kext`'s in-kernel VM in microseconds [42, 243]. Entering a sandbox via `posix_spawn` attributes (`_ps_mac_policy_extension_t` in `bsd/sys/spawn_internal.h`) or `sandbox_init()` is strictly monotonic: a process can apply tighter sub-profiles, never shed an active restriction [239, 243]. Controlled inter-app data sharing relies on `DER`-validated *App Groups* (`com.apple.security.application-groups`), whereas Apple's own crown-jewel SQLite stores (`TCC.db`, `chat.db`, Safari history) carry the `UF_DATAVAULT` BSD flag (`CS_DATAVAULT_CONTROLLER = 0x80000000`), blocking even unconstrained `UID 0` `root` processes lacking matching `com.apple.rootless.storage.*` entitlements [238].

![Figure: WebContent renderer memory-hardening layers (StructureID heap, Primitive Gigacage, APRR JIT) paired with Seatbelt MACF bytecode filtering over residual IOKit externalMethod selectors.](diagrams/07-extra-iokit-jsc-sandbox-surface.svg)

Why, then, do sandboxed processes still escape into `EL1`? Rarely through classic POSIX syscalls (`read`, `write`), whose narrow surface is heavily audited; instead, the dominant kernel escape surface from user space is *IOKit user-clients* (`iokit/IOKit/IOUserClient.h`) [244, 245]. Every hardware accelerator, display compositor, GPU shader pipe, and surface manager in `XNU` exposes C++ `IOService` drivers to user space by instantiating an `IOUserClient` subclass when a process calls `IOServiceOpen()` (mediated by `Seatbelt`'s `iokit-open-user-client` class and property filters) [42, 244]. Once a task holds a Mach send right to an open `IOUserClient`, it invokes driver methods via `IOConnectCallMethod()`, which traps through `io_connect_method` into `IOUserClient::externalMethod(uint32_t selector, IOExternalMethodArguments *args, ...)` [244].

Defined in `IOUserClient.h`, `IOExternalMethodArguments` marshals up to 16 64-bit `scalarInput` integers, inline or out-of-line `IOMemoryDescriptor` `structureInput` buffers, and `asyncWakePort` Mach notification ports into driver C++ code indexed by integer `selector` across an `IOExternalMethodDispatch` table (`checkScalarInputCount`, `checkStructureInputSize`, where `kIOUCVariableStructureSize = 0xffffffff` defers length validation to the driver method itself!) [244]. Saar Amar's analysis of the actively exploited `CVE-2021-30807` zero-day illustrates how razor-thin the sandbox margin is [245]: although `WebKit.WebContent`'s `Seatbelt` profile blocked over 95% of `IOKit` classes, rendering performance historically permitted `IOMobileFramebufferUserClient` (`AppleCLCD`) and granted `WebContent` the `com.apple.private.allow-explicit-graphics-priority` entitlement. Selector `#83` (`s_displayed_fb_surface`) accepted an attacker-controlled 32-bit `scalarInput[0]` and indexed directly into an internal `IOSurface*` pointer array (`this + 0xA58 + scalar0 * 8`) with zero bounds checking, handing a compromised renderer direct `EL1` kernel memory corruption [245]! In response, Apple both stripped direct framebuffer `IOKit` access out of `WebContent` into the dedicated `GPU` broker process and introduced `IOExternalMethodDispatch2022` (`uc2022 = 1` in `IOUserClient.h`), adding single-threaded `externalMethod` locking (`defaultLockingSingleThreadExternalMethod`), explicit `allowAsync` gates, and per-selector `const char *checkEntitlement` enforcement directly in the base `IOKit` dispatcher [244].

### WebKit JavaScriptCore Hardening and the BlastDoor Swift Airlock

Before an attacker can even probe `Seatbelt` or `IOKit`, remote exploits must achieve arbitrary read/write inside `WebKit`'s `WebContent` renderer or `Messages`'s `BlastDoor` parser [21, 44, 246]. Inside `JavaScriptCore` (`JSC`), where `JSValue` NaN-boxing and speculative `DFG`/`FTL` JIT compilation historically turned type confusions into instant `addrof`/`fakeobj` arbitrary-memory primitives, Apple engineered three coupled user-space defenses directly in `WebKit` open source [246, 247, 248, 249]:

First, `StructureID` heap isolation (`Source/JavaScriptCore/runtime/StructureID.h`) defeats classic fake-`JSCell` crafting [246, 247]. Every `JSCell` header begins with a 32-bit `StructureID` describing the object's shape and method table. Rather than storing raw 64-bit `Structure*` pointers (or relying solely on the earlier 7-bit-entropy `StructureIDTable`), modern 64-bit `JSC` reserves a dedicated contiguous virtual `Structure` heap (`structureHeapAddressSize = 2 GB` on `arm64e` `iOS`, `4 GB` on `macOS`) [247]. `StructureID` encodes the lower 32-bit byte offset from `structureIDBase()` (reserving bit 0 as `nukedStructureIDBit = 1` during shape transitions), and `StructureID::tryDecode()` enforces `offset >= MarkedBlock::blockSize && offset < g_jscConfig.sizeOfStructureHeap`, preventing forged `StructureID`s from referencing attacker-controlled `ArrayBuffer` payloads outside the `Structure` reservation [247].

Second, `bmalloc` *Gigacage* (`Source/bmalloc/bmalloc/Gigacage.h`) isolates variable-length raw byte buffers (`TypedArray`, `ArrayBuffer`, `Wasm` linear memory) inside a dedicated `16 GB` (`iOS`) or `64 GB` (`macOS`) power-of-two virtual memory region (`primitiveGigacageSize`) flanked by unmapped guard zones [246, 248]. Every `Primitive` backing-store dereference masks the pointer back into the cage:

$$\text{caged}(\text{ptr}) = \text{gigacageBasePtr} + \bigl(\text{ptr} \;\mathbin{\&}\; (\text{primitiveGigacageSize} - 1)\bigr)$$

Combined with `arm64e` `PAC` pointer signing on backing-store pointers, `Gigacage` ensures that even an unbounded 32-bit index overflow on a `Uint8Array` can read or corrupt only neighboring raw byte buffers inside the `Primitive` cage, never `JSObject` headers, `Structure` metadata, or C++ vtables [246, 248]. Third, hardware `APRR` (`MAP_JIT` + `pthread_jit_write_protect_np`, [Chapter 4](04-silicon-memory-safety.md)) enforces thread-local `W^X` over JIT code pages: JIT memory stays mapped `R-X` across all threads, and only a dedicated compiler thread momentarily switches its core-local `APRR` register to `RW-` (`pthread_jit_write_protect_np(false)`) to emit machine instructions before restoring `R-X` (`true`), preventing concurrent threads in a compromised renderer from spraying shellcode into JIT pages [249].

![Figure: Deprivileged parser containment via the stateless BlastDoor Swift service for incoming iMessage/FaceTime traffic and BrowserEngineKit's split WebContent, GPU, and Networking processes.](diagrams/07-blastdoor-webkit-containment.svg)

For zero-click messaging traffic (`iMessage` and `FaceTime`), where JavaScript and `JIT` are completely unnecessary, Apple introduced `MessagesBlastDoorService` (*BlastDoor*) in `iOS 14` and expanded it across `macOS`, `watchOS`, and `visionOS` [44, 238]. Authored primarily in memory-safe Swift (where array indexing traps deterministically on out-of-bounds offsets and automatic value-type/ARC initialization prevents uninitialized stack reads), `BlastDoor` interposes an ephemeral, stateless airlock ahead of `imagent` [44]. Inspection of `/System/Library/Sandbox/Profiles/blastdoor.sb` reveals one of the most restrictive compute-only `Seatbelt` profiles in `Darwin` [238]: `(deny default)`, `(deny file-map-executable process-info* nvram*)`, `(deny dynamic-code-generation)`, `(deny mach-cross-domain-lookup)`, `(deny mach-lookup (xpc-service-name-regex #".*"))` blocking lateral XPC spawning, `(deny socket-ioctl)`, and an explicit `(deny syscall-unix (with telemetry))` default that whitelists only ~45 bare compute/memory/read syscalls! Incoming `APNs` `BPList` payloads, `NSKeyedArchiver` graphs, `Nickname` cards, and `PassKit` bundles are decoded against rigid static schemas inside `BlastDoor`, while complex image/PDF rasterization steps down into even tighter sub-workers (`CGPDFService`, `ImageIOXPCService`) that return flat, uncompressed RGBA pixel buffers to `imagent` [44, 238].

## Platform Forks Across Apple OSes

Across `iOS`, `iPadOS`, `watchOS`, and `visionOS`, process containment admits zero developer opt-outs: 100% of third-party apps execute inside the `container` `Seatbelt` profile (`/private/var/mobile/Containers/Data/Application/<UUID>`), `task_for_pid()` is permanently closed on production builds, and `MAP_JIT` (`CS_EXECSEG_JIT`) is denied across the entire third-party ecosystem [238, 249]. Only inside the European Union (`iOS 17.4+` and `iPadOS 18+` under the `DMA`) does Apple expose `BrowserEngineKit` (`com.apple.developer.web-browser-engine.*`), permitting vetted alternative browser engines (such as Chromium Blink/V8 or Gecko/SpiderMonkey) to replicate `WebKit`'s exact privilege split across isolated `BEWebContentProcess` (granted `APRR`-enforced JIT, `StructureID`/`Gigacage`-equivalent virtual memory ceilings, and strict syscall/filesystem denial), `BERenderingProcess` (`GPUExtension`), and `BENetworkingProcess` (`NetworkingExtension`) `XPC` workers [43, 249]. Because `BrowserEngineKit` brokers XPC transport through strongly typed Swift capabilities rather than raw `bootstrap_look_up` names, even a compromised third-party renderer cannot enumerate system `MachServices` outside its browser bundle [43].

On `macOS`, while Mac App Store apps must declare `com.apple.security.app-sandbox`, notarized `Developer ID` software (`Terminal`, IDEs, `Docker`, third-party browsers, CLI compilers) may run *un-sandboxed* at `UID 501` (though Chromium, Firefox, and `Safari` voluntarily invoke `sandbox_init` / `Seatbelt` profiles on their own renderer children) [238, 243]. Furthermore, `macOS` permits third-party applications to install `root` `LaunchDaemons` (`SMAppService.daemon(plistName:)` replacing deprecated `SMJobBless`), making `audit_token_t` + `xpc_connection_set_peer_code_signing_requirement` verification inside third-party `macOS` `XPC` daemons a perennial local privilege-escalation battleground [231, 240].

## In-the-Wild Failures & Architectural Bounds

`BlastDoor`, `WebKit` process splitting, and `Seatbelt` `MACF` filters succeeded in collapsing single-bug remote root compromises: modern zero-click exploit chains must now chain four to six distinct zero-days across renderer, graphics broker, and kernel boundaries [21, 23, 65]. Yet eight landmark vulnerability classes define the exact architectural limits of user-mode IPC and parser containment.

| Case / Mechanism | Year | Platform Scope | Boundary Tested | Root Cause | Architectural Response |

| `Task Port` / `mach_vm_write` Lateral Injection | 2016-2021 | `macOS` & `iOS` | `TASK_KERNEL_PORT` & `task_for_pid` | Processes lacking `CS_RUNTIME` or leaking send rights to `mach_task_self()` let peers overwrite virtual memory and spawn threads | Split `TASK_READ_PORT` / `INSPECT_PORT`, enforced `CS_RUNTIME` task-port lock, and added `PSPA_PTRAUTH_TASK_PORT` [229, 235, 236] |
| `XPC` Race & Refcount Bugs (`CVE-2020-9839`) | 2020 | `iOS` (`< 13.5`) & `macOS` (`< 10.15.5`) | `libxpc` & privileged `XPC` daemon state | Concurrent message/state handling races (*Splitting atoms in XPC* class) corrupted daemon object lifecycles across privilege boundaries | Hardened `libxpc` state locking and atomic object serialization [232, 233] |
| `xpc_connection_get_pid` `TOCTOU` Spoofing | 2018-2024 | `macOS` (3P `root` `XPC` helpers) | `PID` vs. `audit_token_t` peer identity | Root helpers validated `processIdentifier` (`pid_t`) via `kSecGuestAttributePid`, allowing `execve()` into an Apple binary to spoof signature checks | Added public `xpc_connection_set_peer_code_signing_requirement` & `NSXPCConnection` `pidversion`-bound checks [234, 240, 241] |

### FORCEDENTRY (CVE-2021-30860) and BLASTPASS (CVE-2023-41064): Why Memory-Safe Wrappers Inherit C/C++ Leaf Libraries

Citizen Lab and Google Project Zero's teardowns of NSO Group's *FORCEDENTRY* (`CVE-2021-30860`, 2021) and *BLASTPASS* (`CVE-2023-41064` + `CVE-2023-41061`, 2023) demonstrate a fundamental law of language-level hardening: writing the top-level `BlastDoor` orchestrator in Swift eliminates bugs in `BPList` envelope routing, yet any call down into legacy C/C++ media libraries (`CoreGraphics`, `ImageIO`, `libwebp`) re-opens raw heap corruption inside the airlock [21, 65, 237, 250].

In *FORCEDENTRY*, `BlastDoor` stripped `MAP_JIT` completely and enforced `arm64e` `PAC` on every code and vtable pointer. However, when presented with an `iMessage` attachment carries a `.gif` extension, `CoreGraphics` performed magic-byte content sniffing and routed the file into its legacy `PDF` parser, which supported 1990s `JBIG2` monochrome document compression [21, 250]. Exploiting a 32-bit integer overflow in `JBIG2Stream::readSegments` to escape bitmap buffer bounds, NSO Group weaponized `JBIG2`'s refinement operator (which combines arbitrary source rectangles via bitwise `AND`, `OR`, `XOR`, and `XNOR` raster ops) to wire over *70,000 logic gates* into 64-bit adders, comparators, and conditional branches, executing an entire Turing-complete emulated architecture inside `BlastDoor` data memory without ever allocating a single executable JIT page [21]! Two years later, *BLASTPASS* (`2023`) delivered a crafted `PassKit` (`pkpass`) bundle containing a malicious `WebP` image whose Huffman coding table overflowed a heap allocation inside `ImageIO`'s embedded C `libwebp` decoder (`CVE-2023-41064`), chaining into `CVE-2023-41061` to escape `BlastDoor` [65, 237]. Both campaigns motivated Apple's ongoing replacement of C media parsers, micro-worker sandboxing (`CGPDFService`, `ImageIOXPCService`), synchronous `EMTE` (`MIE` on `A19`/`M5`), and `Lockdown Mode`'s preemptive attachment stripping ([Chapter 10](10-apfs-data-protection.md)).

## Verification & Forensic Artifacts

Inspect `BlastDoor`'s live `SBPL` profile on `macOS` (`/System/Library/Sandbox/Profiles/blastdoor.sb`) to verify `(deny default)`, `(deny dynamic-code-generation)`, XPC spawn blocking, and its explicit `syscall-unix` allowlist [44, 238]:

```bash
ls -la /System/Library/Sandbox/Profiles/blastdoor.sb /System/Library/Sandbox/Profiles/application.sb
grep -E '^\(deny|syscall-unix' /System/Library/Sandbox/Profiles/blastdoor.sb | head -n 10
```

Representative output confirming compute-only isolation rules inside `blastdoor.sb`:

```text
(deny default)
(deny file-map-executable process-info* nvram*)
(deny dynamic-code-generation)
(deny mach-lookup (xpc-service-name-regex #".*"))
(deny syscall-unix (with telemetry) (with message "73669976"))
```

Audit third-party root `LaunchDaemons` for exposed `MachServices` XPC endpoints and enumerate active `IOKit` `IOUserClient` kernel driver connections (`IOUserClientCreator`) held by running processes [230, 244]:

```bash
plutil -p /Library/LaunchDaemons/*.plist 2>/dev/null | grep -E 'ProgramArguments|MachServices' -A 2 | head -n 10
ioreg -l -w 0 | grep '"IOUserClientCreator"' | head -n 6
```

Query Unified Logging for real-time `Sandbox.kext` (`Seatbelt`) `MACF` denials across file, `mach-lookup`, or `iokit-open` hooks [242, 243]:

```bash
log show --last 5m --predicate 'sender == "Sandbox" AND eventMessage CONTAINS "deny"' --style compact | tail -n 5
```

On `iOS`, `iPadOS`, `watchOS`, and `visionOS`, mandatory `App Sandbox` containers isolate every third-party app's filesystem view automatically; on `macOS`, however, un-sandboxed `Developer ID` apps, terminals, and scripts share `UID 501` outside App Sandbox containers altogether. [Chapter 8](08-macos-tcc-sysext.md) examines how `macOS` governs user-consent privacy (`TCC`), `Background Task Management` (`BTM`), and user-space `SystemExtensions` across that open workstation architecture.
