# Foundations

## A Shared Systems Vocabulary Across Silicon, Kernel, and Ecosystem

Tracing a security guarantee on Android requires crossing five engineering layers that are ordinarily documented in separate worlds: `ARMv8-A` and `ARMv9-A` silicon exception architectures, on-die Trusted Execution Environments paired with discrete secure elements, modified Linux kernel subsystems (`Binder`, `SELinux`, `fscrypt`, `dm-verity`, and `pKVM`), the userspace Android Framework (`Zygote`, `ActivityManagerService`, `keystore2`, and `PackageManager`), and Google's compatibility testing and cloud attestation infrastructure [1, 2, 9, 46]. An application security engineer analyzing `Intent` redirection rarely inspects `Stage-2` ARM translation tables in `EL2` or `SMMUv3` stream descriptors, while a bootloader developer configuring `AvbVBMetaImageHeader` partition descriptors may rarely audit `Credential Manager` `caBLE` passkey ceremonies or `Titanium Intelligence Enclave` `DICE` chains. Before [Chapter 1](01-bootrom-avb-vbmeta.md) begins at CPU power-on reset, this chapter establishes the foundational hardware, peripheral bus, operating-system, governance, cryptographic, and adversarial primitives shared across all twenty chapters.

## ARMv8 and ARMv9 Exception Levels, Security Worlds, and RME

Contemporary Android flagship and mid-range handsets execute predominantly on 64-bit `AArch64` (`ARMv8-A` and `ARMv9-A`) System-on-Chip (`SoC`) designs [46]. Unlike classic x86 protection rings (`Ring 3` down to `Ring 0`), the Arm A-Profile architecture organizes privilege along two orthogonal dimensions: vertical Exception Levels (`EL0` through `EL3`) governing instruction privilege within a world, and horizontal Security States (`Worlds`) governing physical address space visibility across worlds [46, 47, 48].

Along the vertical axis inside the Normal World, `EL0` hosts unprivileged userspace code, encompassing Android applications (`ART` managed bytecode and native `JNI` libraries), native system daemons (`init`, `vold`, `keystore2`, `apexd`, `virtmgr`), and Binderized vendor Hardware Abstraction Layer (`HAL`) processes. `EL1` hosts privileged rich operating-system kernels: both the host Android `Generic Kernel Image` (`GKI`) Linux kernel and lightweight `Microdroid` guest Linux kernels running inside virtual machines [4, 13, 49]. Beneath `EL1` sits `EL2`, the Hypervisor Exception Level, which governs processor virtualization traps (`HCR_EL2`), virtual interrupt injection, and `Stage-2` Memory Management Unit (`MMU`) translation tables (`VTTBR_EL2` and `VTCR_EL2`) that translate Guest Intermediate Physical Addresses (`IPA`) into hardware Physical Addresses (`PA`) [4, 46, 50]. At the bottom of every physical Cortex or Oryon CPU core sits `EL3`, the Secure Monitor (implemented on modern SoCs by Arm Trusted Firmware-A `BL31` [51]), which owns the highest architectural privilege on the application processor, services synchronous Secure Monitor Calls (`SMC`) and `PSCI` power-management transitions (`ARM DEN 0022` [52]), routes high-priority Group 0 interrupts via `GICv3`/`GICv4` (`ARM IHI 0069` [53]), and context-switches architectural registers between security worlds [47, 51, 54].

Understanding `EL2` on Android requires contrasting the two virtualization execution modes introduced in `ARMv8.1-A` Virtualization Host Extensions (`VHE`) [4, 46, 50]. On cloud servers running KVM over `ARMv8.1+`, Linux enables `VHE` by setting `HCR_EL2.E2H = 1` and `HCR_EL2.TGE = 1`, collapsing the host kernel directly into `EL2` to avoid world-switch traps between `EL1` and `EL2` [50]. While ideal when the host OS is unconditionally trusted, `VHE` places all multi-million lines of host Linux drivers inside the hypervisor Trusted Computing Base (`TCB`). Android's `Protected KVM` (`pKVM`, examined in [Chapter 5](05-pkvm-avf-microdroid.md)) deliberately rejects `VHE` in favor of split-mode *non-VHE* (`nVHE`, `HCR_EL2.E2H = 0`) execution [4]. During early boot, Linux installs a tiny, self-contained `nVHE` monitor (`arch/arm64/kvm/hyp/nvhe`) into `EL2` and permanently drops the host Linux kernel down to `EL1` (`__pkvm_prot_finalize`), activating an identity-mapped `Stage-2` MMU table (`host_mmu`) *underneath the host Android kernel itself* [4, 55]. Once de-privileged, host `EL1` Linux becomes an untrusted scheduling substrate that loses hardware ability to read or modify physical pages donated to Protected Virtual Machines (`pVMs`) or to `EL2`.

![Figure: ARMv8/ARMv9 Exception Levels, TrustZone Secure World, pKVM EL2 hypervisor ownership, and off-SoC StrongBox security processors.](diagrams/00b-arm-worlds-pkvm-topology.svg)

Along the horizontal axis, `ARMv8-A` `TrustZone` splits physical memory, TLB tags, and `GICv3` interrupt groups (Secure Group 1 vs. Non-Secure Group 1 [53]) into two worlds selected by the Non-Secure (`NS`) bit in the Secure Configuration Register (`SCR_EL3.NS`) [46, 47]. When `SCR_EL3.NS = 1`, the core executes in the Normal World (`EL0`, `EL1`, `EL2`) and emits AXI bus transactions tagged `AxPROT[1] = 1` (`Non-Secure`). When `EL3` traps an `SMC` instruction and clears `SCR_EL3.NS = 0`, execution enters the Secure World, emitting bus transactions with `AxPROT[1] = 0` (`Secure`) admitted by the SoC's TrustZone Address Space Controller (`CoreLink TZC-400` [56]) into Secure DRAM carveouts. Inside the Secure World, `S-EL1` runs a Trusted Operating System (`Google Trusty`, `Qualcomm QTEE`/`QSEE`, `Samsung TEEGRIS`, `Trustonic Kinibi`, or `OP-TEE`), hosting `S-EL0` Trusted Applications (`TAs` or trustlets) for `KeyMint`, `Gatekeeper`, biometrics, and `Widevine` DRM [14, 28, 57]. On `ARMv8.4-A` and later cores implementing Secure `EL2` (`FEAT_SEL2`), a Secure Partition Manager Core (`SPMC` such as TrustedFirmware `Hafnium`) can run at `S-EL2` under the Arm Firmware Framework (`FF-A`, `ARM DEN 0077` [58]) to isolate mutually distrusting Secure Partitions via Secure `Stage-2` tables (`VSTTBR_EL2`).

`ARMv9-A` (`ARMv9.2-A` Confidential Compute Architecture, `CCA`) generalizes this two-world split into *four* hardware-enforced physical address spaces via the Realm Management Extension (`RME`, `ARM DEN 0126` [48, 59]). `RME` introduces a second world-selection bit, `SCR_EL3.NSE`, alongside `SCR_EL3.NS`, decoupling `EL3` (`Root` World) from `TrustZone` (`Secure` World) and creating a dynamically carved `Realm` World for confidential VMs managed by a lightweight Realm Management Monitor (`RMM` at `R-EL2`) [48, 59]. Instead of relying solely on static boot-time `TZC-400` DRAM carveouts, `RME` adds hardware Granule Protection Checks (`GPC`) walked on *every* CPU MMU translation and `SMMUv3` access against `EL3`-owned Granule Protection Tables (`GPTBR_EL3`, configured via `GPCCR_EL3` at $4\text{ KiB}$, $16\text{ KiB}$, or $64\text{ KiB}$ physical granule resolution) [48, 51]. Only `EL3` Root firmware can transition a $4\text{ KiB}$ DRAM granule between `Non-Secure`, `Realm`, `Secure`, and `Root` Physical Address Spaces (`PAS`) after scrubbing its contents, allowing `AVF` confidential compute workloads on `ARMv9` silicon to isolate from *both* Normal World `EL1`/`EL2` and legacy `S-EL1` `TrustZone` trustlets simultaneously [3, 48, 59].

| Execution Domain | `SCR_EL3` `(NSE, NS)` | Exception Levels | Hardware Memory Firewall | Representative Android Software & Security Role |
|---|---|---|---|---|
| Normal World (Host & Guests) | `(0, 1)` | `EL0`, `EL1` | `Stage-1` MMU + `EL2` `Stage-2` (`VTTBR_EL2`) | Android apps, `GKI` Linux kernel, `Microdroid` `pVM` guests [4, 49] |
| Normal World Hypervisor | `(0, 1)` | `EL2` (`nVHE`) | `EL2` `Stage-1` + `host_mmu` `Stage-2` + `SMMUv3` | `pKVM` (`arch/arm64/kvm/hyp/nvhe`) or vendor `Gunyah` [4, 60] |
| Secure World (`TrustZone`) | `(0, 0)` | `S-EL0`, `S-EL1`, optional `S-EL2` | `TZASC` (`TZC-400`) / `RME` `GPT` (`Secure PAS`) | `Trusty`, `QTEE`, `TEEGRIS`, `Hafnium` `SPMC`, `KeyMint`/`DRM` TAs [47, 58] |
| Realm World (`ARMv9 RME`) | `(1, 1)` | `R-EL0`, `R-EL1`, `R-EL2` | `RME` `GPT` (`Realm PAS`) + `RMM` `Stage-2` | `RMM` (`R-EL2`) and `CCA` Realm confidential VMs [48, 59] |
| Root Monitor (`EL3`) | `(1, 0)` on `RME` (`NS=0` on `v8`) | `EL3` | `RME` `GPT` (`Root PAS`, `GPTBR_EL3`) / Secure SRAM | `Boot ROM` (`PBL`/`BL1`) and `TF-A` `BL31` world switcher [48, 51] |
| Discrete `StrongBox` Die | Off-SoC MCU | Dedicated `RISC-V` / Secure Core | Physical package air gap + internal SRAM/NVM + `MPU` | `Google Titan M2` and `Samsung Knox Vault` over `SPI` [26, 27, 61] |

As the final row underscores, even `EL3` and `RME` still execute on the shared main application SoC die connected to external LPDDR DRAM. Because shared silicon remains exposed to invasive lab probing, electromagnetic Differential Power Analysis (`DPA`), and off-chip flash replay (`NAND mirroring` [62]), flagship Android devices anchor their highest-assurance secrets inside a physically separate `StrongBox` security processor (`Google Titan M2` or `Samsung Knox Vault`) with private on-die SRAM, internal embedded flash, active glitch/laser sensors, and narrow `SPI` framing ([Chapter 3](03-trustzone-strongbox.md)) [26, 27, 61].

> **Definition.**
> Modern Android stratifies its hardware Trusted Computing Base across four complementary isolation substrates: off-die `StrongBox` silicon (`Titan M2` / `Knox Vault`) for physical fault resistance and `Weaver` passcode throttling; `TrustZone` (`EL3`/`S-EL1`) for low-latency SoC-integrated crypto and secure sensor/display paths; `EL2` `pKVM` (and `ARMv9` `RME`) for dynamic, Mainline-updatable Protected VMs isolated from host Linux; and `EL1` `GKI` Linux enforcing `SELinux`, `Binder`, and `fscrypt` across `EL0` app sandboxes.

## Peripheral Bus Sovereignty and Arm SMMUv3 Stream Tables

CPU MMU translation tables (`TTBR0_EL1`, `TTBR1_EL1`, and `VTTBR_EL2`) police memory accesses emitted by Cortex application cores, yet application cores represent only a fraction of the bus masters wired onto a smartphone SoC interconnect [63, 64]. A modern mobile chipset integrates dozens of autonomous Direct Memory Access (`DMA`) engines and co-processors sharing physical LPDDR5X DRAM: 5G/LTE cellular baseband modems (`Shannon` or `Snapdragon X-series`), `Arm Mali` or `Qualcomm Adreno` GPUs, Wi-Fi/Bluetooth PCIe or AXI rings, Neural Processing Units (`TPU`/`NPU`), camera Image Signal Processors (`ISP`), audio/sensor `DSP`s, and `USB-C` `DWC3` controllers [18, 64]. Without hardware I/O memory translation, two catastrophic bypasses occur immediately: first, an over-the-air remote code execution exploit inside cellular baseband or Wi-Fi firmware ([Chapter 20](20-multivendor-spyware-chains.md)) could issue raw physical DMA writes over AXI to patch the `EL1` Linux kernel's `SELinux` `selinux_state` structure in DRAM [18, 64]; second, a compromised `EL1` Linux kernel could program a GPU or `USB` DMA descriptor to read physical DRAM frames donated to an `EL2` `pKVM` Protected VM, bypassing CPU `Stage-2` isolation completely [3, 65].

Android SoCs close this peripheral DMA bypass using the `Arm System Memory Management Unit` (`SMMUv3`, `ARM IHI 0070` [63, 66]) combined with SoC memory protection units (`Qualcomm XPU`/`SMMU` or `Tensor` `S2MPU`). Positioned inline between non-CPU bus masters and the SoC interconnect/DRAM controller, `SMMUv3` assigns every hardware peripheral an unforgeable, silicon-hardwired `StreamID` (`SID`, derived from physical AXI `AxUSER`/master port wiring or PCIe `[Bus:Device.Function]` Requester IDs) and an optional `SubstreamID` (`SSID` / `PASID` up to 20 bits) [63]. Because `SID` signals are asserted by the bus fabric outside peripheral firmware control, a compromised Wi-Fi chip or cellular DSP cannot impersonate the `StreamID` of the display controller or application CPU.

When a peripheral emits a DMA read or write targeting an I/O Virtual Address (`IOVA`) or Guest `IPA`, the `SMMUv3` hardware walks an in-memory two-level (or linear) *Stream Table* pointed to by the privileged `SMMU_STRTAB_BASE` register (`drivers/iommu/arm/arm-smmu-v3/arm-smmu-v3.c`) [63, 66]. Indexing by `StreamID` locates a 64-byte *Stream Table Entry* (`STE`) that specifies one of four hardware dispositions: abort all DMA (`Config = 0b000`), translate through `Stage-1` *Context Descriptors* (`CD`, allowing `EL1` Linux IOMMU drivers to isolate individual per-buffer scatter-gather `dma-buf` mappings), translate through `Stage-2` hypervisor page tables (`S2TTB`, translating `IPA` to `PA` with read/write/execute permissions), or enforce nested `Stage-1 + Stage-2` translation simultaneously [63].

Crucially, under `pKVM` ([Chapter 5](05-pkvm-avf-microdroid.md)), the `EL1` Linux kernel is stripped of direct MMIO write access to `SMMU_STRTAB_BASE` and `Stage-2` `STE` fields! Instead, `pKVM` loads a minimal `EL2` `SMMUv3` hypervisor driver (`drivers/iommu/arm/arm-smmu-v3/pkvm/` [65]) that owns `SMMUv3` command queues (`CMDQ`) and `Stage-2` stream tables in `EL2`-private memory. Whenever `pKVM` unmaps a $4\text{ KiB}$ page from Host `EL1`'s CPU `Stage-2` table to donate it to a `pVM`, `EL2` enforces identical revocation across every host-controlled peripheral `STE` and invalidates `SMMU` IOTLBs (`CMD_TLBI_S2_IPA`), ensuring neither a rogue host kernel driver nor a compromised cellular modem can cross its assigned physical memory envelope via DMA [3, 64, 65].

## Inverting Unix: Exact AID Ranges, Multi-User Arithmetic, SELinux, and Binder

Understanding userspace Android requires unlearning how desktop Linux uses `UID`s, filesystems, and IPC sockets. On a traditional POSIX workstation, a human logs into `UID 1000`, and every binary launched during that session inherits `UID 1000`'s ambient discretionary authority over `~/.ssh`, browser cookies, clipboard buffers, and local sockets. Android keeps the Linux scheduler, virtual memory subsystem, and VFS hooks, but repurposes the kernel's `uid_t` and `gid_t` primitives into a mutual-distrust *application sandbox* [1, 2, 21].

The canonical map of Android's 32-bit `uid_t` namespace is codified in `system/core/libcutils/include/private/android_filesystem_config.h` (`DO NOT EVER RENUMBER`) [21, 67]. Rather than lumping system services into `UID 0` (`AID_ROOT`), Android assigns over ninety distinct static low-numbered `AID_*` identities (`1000` through `1095`) to individual framework and hardware daemons so a vulnerability in Bluetooth (`AID_BLUETOOTH = 1002`), media extraction (`AID_MEDIA_EX = 1040`), or `keystore2` (`AID_KEYSTORE = 1017`) runs under a non-root kernel `UID` from birth [67]. Above the daemon and partition-reserved bands sit dedicated dynamic per-application, SDK-runtime, shared-GID, and zero-permission isolated-process intervals [21, 67, 68]:

| `AID_*` Symbolic Range (`android_filesystem_config.h`) | Numeric `appId` Interval | Example `ps -Z` Name (User `0` / User `10`) | Security Principal & Kernel Enforcement Semantics |
|---|---|---|---|
| `AID_ROOT` | `0` | `root` | Kernel threads, `init`, `vold`, `zygote`; heavily partitioned into narrow `SELinux` domains without ambient `CAP_SYS_MODULE` [24, 67] |
| `AID_SYSTEM` | `1000` | `system` | `system_server` and core system-UID packages; blocked from raw block-device or unmediated app-data reads by `SELinux` [21, 67] |
| `AID_RADIO` .. `AID_MMD` | `1001 .. 1095` | `radio`, `bluetooth`, `wifi`, `keystore`, `virtualizationservice` (`1081`), `diced` (`1085`) | Dedicated least-privilege system daemons (`1017` `keystore2`, `1046` `mediacodec`, `1053` `webview_zygote`, `1082` `artd`) [67] |
| `AID_SHELL` | `2000` | `shell` | `adbd` interactive developer shell; confined to `u:r:shell:s0`, barred from reading non-debuggable `/data/data` directories [67] |
| `AID_NET_*` / Supplemental GIDs | `3001 .. 3013` | Supplemental `groups=` | Kernel-checked socket/device gates (`AID_INET = 3003` required by Android kernel patch to create `AF_INET`/`AF_INET6` sockets!) [21, 67] |
| `AID_*_RESERVED` (Vendor/System/ODM/Product) | `2900..2999`, `5000..7999` | `oem_*`, vendor HAL UIDs | Partition-scoped `config.fs` static UIDs for `/vendor` (`5000..5999`), `/odm` (`6500..6999`), `/product` (`7000..7499`) [12, 67] |
| `AID_APP_START` .. `AID_APP_END` | `10000 .. 19999` | `u0_a214` / `u10_a214` | Unique per-APK Application ID allocated by `PackageManager` at install time and persisted in `/data/system/packages.xml` [21, 67] |
| `AID_SDK_SANDBOX_PROCESS_START` .. `END` | `20000 .. 29999` | `u0_a214_sdk` (`20214`) | `Privacy Sandbox` `SdkSandboxManager` runtime isolating third-party ad/analytics SDKs outside the host app's `UID` and storage [67, 68] |
| `AID_CACHE_GID` / `EXT_GID` / `SHARED_GID` | `20000 .. 59999` (GIDs) | Supplemental `groups=` | Per-app cache quota GIDs (`20000..29999`) and legacy `sharedUserId` GIDs (`50000..59999`) [67] |
| `AID_OVERFLOWUID` | `65534` | `nobody` / overflow | Unmapped user-namespace fallback UID matching Linux `DEFAULT_OVERFLOWUID` [67] |
| `AID_ISOLATED_START` .. `AID_ISOLATED_END` | `90000 .. 99999` | `u0_i12` / `u0_ai0` | Ephemeral zero-permission processes (`90000..98999` `AppZygote`; `99000..99999` `isolatedProcess="true"` `WebView`/Chrome renderers) [67, 69] |

Notice two architectural gems inside `android_filesystem_config.h` [67, 68]. First, `AID_INET = 3003` explains how Android enforces the `android.permission.INTERNET` manifest permission without brittle per-app `iptables` rules: only apps granted `INTERNET` receive supplemental GID `3003` at `Zygote` fork time, and Android's common kernel checks `in_egroup_p(AID_INET)` directly inside `inet_create()`. Second, `AID_SDK_SANDBOX_PROCESS_START` (`20000..29999`) and `AID_ISOLATED_START` (`90000..99999`) extend sandboxing *inside* a single app: an `isolatedProcess="true"` `WebView` renderer (`UID 99012`) holds zero filesystem directories, zero network GIDs, and blocks almost every `Binder` service in `SELinux`, while an advertising SDK running in the SDK Runtime for app `10214` receives deterministic sandbox UID $\text{appId} + 10000 = 20214$, preventing the SDK from reading the host banking or health app's `/data/data` files [67, 68, 69]!

When Android hosts multiple human users (`Secondary Users`) or `Android Enterprise` Work Profiles / `Private Space` ([Chapter 17](17-android-enterprise.md)), `frameworks/base/core/java/android/os/UserHandle.java` combines the profile index $u \in \mathbb{Z}_{\ge 0}$ ($u = 0$ for primary owner, $u \ge 10$ for managed/private profiles) with `AID_USER_OFFSET = 100000` via bijective modular arithmetic [67, 70, 71]:

$$\text{uid}(u, \text{appId}) = 100000 \cdot u + (\text{appId} \bmod 100000), \qquad u = \lfloor \text{uid} / 100000 \rfloor, \qquad \text{appId} = \text{uid} \bmod 100000$$

Thus an app assigned $\text{appId} = 10214$ executes as kernel `UID 10214` (`u0_a214`) in the personal profile, as `UID 1010214` (`u10_a214`) in Work Profile $u = 10$, and spawns its SDK sandbox as `UID 1020214` in that Work Profile. Standard Linux VFS Discretionary Access Control (`DAC`) immediately blocks `10214` from opening files owned by `10215` or `1010214` at zero runtime lookup cost [21, 70, 71].

![Figure: Architectural contrast between ambient-user desktop POSIX and Android's mutual-distrust per-application UID, SELinux, and Binder model.](diagrams/00b-android-vs-unix-uid-stack.svg)

Because POSIX `DAC` alone cannot confine `UID 0` daemons or stop an app from `chmod 0777`-sharing its own home directory across profiles, Android welds three mandatory kernel enforcement layers onto every process [2, 24, 72, 73]. First, universal enforcing `SELinux` ([Chapter 6](06-selinux-seccomp.md)) labels every app process and `/data/data` directory with Multi-Category Security (`MCS`) category pairs derived from both `(appId - 10000)` (`c0..c511`) and `userId` (`c512..c1023`), such as `u:r:untrusted_app:s0:c214,c256,c512,c768`, mathematically blocking cross-app and cross-profile file access even if DAC permissions are world-writable [24, 74]. Second, `Zygote` zeroes all POSIX capability sets (`CapInh = CapPrm = CapEff = CapBnd = CapAmb = 0`), sets `PR_SET_NO_NEW_PRIVS`, and installs an architecture-specific `seccomp-BPF` allowlist (`bionic/libc/seccomp`) blocking unused kernel syscalls (`keyctl`, `add_key`, `userfaultfd`, unprivileged `bpf`, `io_uring`) before invoking untrusted app code [72, 75, 76]. Third, with System V IPC compiled out of `GKI` and cross-app Unix domain sockets denied by `SELinux`, inter-process RPC passes exclusively through `/dev/binder` ([Chapter 9](09-uid-zygote-binder.md)), where the kernel driver translates per-process capability handles (`flat_binder_object`) and overwrites `sender_euid` and `sender_pid` on every transaction from the caller's immutable `struct cred`, eliminating sender spoofing [73, 77].

## Multi-Vendor Ecosystem Governance: CDD Section 9, CTS, VTS, Treble, and GKI

Because AOSP is permissive Apache-2.0 open-source software integrated by hundreds of independent OEMs and ODMs atop diverse SoC Board Support Packages (`BSP`s), source code in `android.googlesource.com` guarantees nothing on a retail handset unless a binding technical and contractual gate prevents vendors from weakening security invariants during bring-up [2, 9, 10, 11]. Android enforces uniform security properties across this fragmented supply chain through five interlocking mechanisms.

The normative baseline specification is the Android Compatibility Definition Document (`CDD`), updated for each platform API release [9]. Section 9 of the `CDD` (*Security Model Compatibility*) transforms architectural best practices into non-negotiable release requirements across eleven subsections [9]: `9.1` and `9.2` mandate the Android permission model, unique per-app `UID` isolation, and `seccomp-BPF` syscall filtering; `9.7` mandates kernel `SELinux` in global enforcing mode with zero permissive domains in production builds alongside kernel Control Flow Integrity (`KCFI`) and stack/heap mitigations; `9.9` mandates `File-Based Encryption` (`FBE`) using `AES-256-XTS` and `AES-256-CTS` (only permitting `Adiantum` on ultra-low-end cores lacking `ARMv8` Cryptography Extensions) plus metadata encryption on `/data`; `9.10` mandates `AVB` Verified Boot (`GREEN`/`YELLOW`/`ORANGE`/`RED` lock states), `dm-verity` in strict `VERITY_MODE_RESTART` paired with Reed-Solomon Forward Error Correction (`FEC`), and hardware-backed rollback protection; and `9.11` mandates hardware-backed `KeyMint` (`TEE` and, where present, `StrongBox`), tamper-evident lockscreen passcode throttling (`Gatekeeper`/`Weaver`), and `Remote Key Provisioning` (`RKP`) on Android 13+ launch devices [9, 30].

Paper mandates in `CDD` Section 9 are mechanically audited before any device model can license Google Mobile Services (`GMS`) or receive `Play Integrity` hardware certification (`MEETS_DEVICE_INTEGRITY` / `MEETS_STRONG_INTEGRITY` in [Chapter 16](16-play-integrity-keybox-wars.md)) by two automated test suites [11, 45, 78]. The Compatibility Test Suite (`CTS`) executes millions of host-driven tests against the retail-signed `user` build: `CtsSelinuxTargetSdkCurrentTestCases` and `SELinuxHostTest` pull the live binary `/sys/fs/selinux/policy` off the phone, parse its type-enforcement graph, and verify that zero permissive domains exist and not a single AOSP `neverallow` assertion (`system/sepolicy/public/*.te`) was violated by vendor rules [11, 79]. Simultaneously, the Vendor Test Suite (`VTS`, `test/vts` [78, 80]) flashes a pure Google-signed Generic System Image (`GSI`) onto `/system` atop the OEM's `/vendor` partition and exercises every `AIDL`/`HIDL` HAL directly (`VtsHalKeyMintTargetTest`, `VtsHalWeaverTargetTest`, `VtsHalBootTargetTest`, `VtsKernelLinuxKselftest`), verifying that hardware cryptographic tags, `Weaver` backoff timers, `AVB` rollback floors, and kernel configurations obey exact AOSP semantics [11, 78, 80].

Three modularization reforms complete this governance architecture ([Chapter 2](02-antirollback-verity-apex.md) and [Chapter 7](07-treble-gki-rust.md)) [12, 13, 81]. `Project Treble` (Android 8.0+) severed `/system` from `/vendor` across stable Binderized `VINTF` HAL contracts so framework updates no longer wait on vendor C++ HAL recompilation [12]. `Project Mainline` (Android 10+) encapsulated over thirty security-sensitive OS components (`com.android.art`, `com.android.conscrypt`, `com.android.resolv`, `com.android.media.swcodec`, `com.android.wifi`, `com.android.btservices`, `com.android.permission`, `com.android.rkpd`, and `com.android.virt`) into signed `APEX` loopback `dm-verity` images updated directly via Google Play system updates independent of OEM OTA lag [81, 82, 83]. Finally, `Generic Kernel Image` (`GKI 2.0`, mandatory from Android 12 / Linux 5.10 onward) eliminated vendor forks of core Linux MM, VFS, `Binder`, `SELinux`, and `pKVM` subsystems by shipping a single Google-compiled, Google-signed `boot.img` kernel binary across all ARM64 chipsets, relegating SoC peripheral drivers to KMI-bound loadable modules in `vendor_boot` and `vendor_dlkm` [13].

## Cryptographic Primitives and Key-Derivation Hierarchies

Android's trust chain deliberately avoids bespoke ciphers, standardizing on NIST, IETF, and TCG cryptographic constructions verified continuously by `CTS` and `VTS` [9, 84, 85, 86, 87]. Pre-OS image verification and runtime block/file authenticity rely on `SHA-256` and `SHA-512` (`FIPS 180-4` [84]): `AVB 2.0` authenticates `AvbVBMetaImageHeader` descriptors using `RSA-2048` or `RSA-4096` signatures [22, 88], while `dm-verity`, `fs-verity`, `AuthFS`, and `APK Signature Scheme v2`/`v3`/`v4` evaluate salted `SHA-256` Merkle trees over $4\text{ KiB}$ blocks so tampering with any page on `UFS` flash fails deterministic verification before mapping into user or kernel page tables [23, 89, 90, 91].

Bulk storage confidentiality in `File-Based Encryption` ([Chapter 12](12-fbe-usb-theft-protection.md)) uses dedicated inline encryption silicon (`ICE` / `UFS` Inline Crypto Engine) running `AES-256-XTS` (`NIST SP 800-38E` [85]) for $4\text{ KiB}$ file data blocks and `AES-256-CTS` (`AES-CBC` with Ciphertext Stealing) for directory filenames, deriving per-inode keys from `fscrypt` v2 master keys via `HKDF-SHA512` (`RFC 5869` [86]) [92, 93]:

$$K_{\text{inode}} = \text{HKDF-SHA512}\bigl(K_{\text{master}}, \; \text{"fscrypt\textbackslash 0"} \parallel \text{mode} \parallel \text{nonce}_{16}\bigr)$$

For human-memorized passcodes (`LSKF`) and hardware key sealing ([Chapter 4](04-keymint-weaver-throttling.md)), `LockSettingsService` stretches the user's PIN, pattern, or password with a 16-byte random salt through memory-hard `scrypt` (`RFC 7914` [94], parameterized at $N = 2^{11} = 2048, r = 8, p = 1$), mixes the output with a 128-bit hardware-throttled `Weaver` slot secret on `StrongBox`, and unwraps a permanent 256-bit `SyntheticPassword` (`SP` v3) that derives isolated purpose-bound subkeys (`"fbe-key"`, `"sp-gk-authentication"`, `"keystore-password"`) using counter-mode PRF key derivation (`NIST SP 800-108` [95, 96]). Inside `KeyMint`, wrapped `key_blob` files on `/data/misc/keystore2` use `AES-256-GCM` (`NIST SP 800-38D` [85]) with the hardware-enforced `AuthorizationList` bound into the AEAD Additional Authenticated Data (`AAD`) under a Key Encryption Key mixed with silicon Hardware-Bound Keys (`HBK`), Verified Boot `RootOfTrust`, and security patch levels [28, 97, 98]. Finally, hardware `Key Attestation`, `OpenProfile for DICE` `pVM` certificate chains, `Secretkeeper` `AuthGraph` sessions, and FIDO2 `WebAuthn` passkeys ([Chapter 5](05-pkvm-avf-microdroid.md), [Chapter 13](13-biometrics-passkeys.md), and [Chapter 15](15-key-attestation-rkp.md)) employ `ECDSA` over `NIST P-256`/`P-384` [84] and `Ed25519` (`RFC 8032` [87]), serialized in canonical `CBOR` and `COSE_Sign1` (`RFC 8949` and `RFC 9052` [99]) [30, 33, 100, 101].

## Multi-Actor Threat Model and Mechanism Validity Versus Authorization

Because a smartphone is simultaneously a personal vault, a cellular radio terminal, a general-purpose application computer, and an attested endpoint for remote banking and enterprise services, no single adversary model suffices [1, 2, 102]. Throughout this book, every mechanism is evaluated against six concrete threat actors whose capabilities and goals diverge sharply:

First, the *remote zero-click or one-click network adversary* (including commercial surveillance vendors such as `NSO Group` and `Intellexa`/`Cytrox` analyzed in [Chapter 20](20-multivendor-spyware-chains.md)) transmits crafted `WebRTC`/`V8` web payloads, `HEVC`/image media streams, Bluetooth frames, or over-the-air cellular `VoLTE`/5G NAS packets (`CVE-2023-24033`) to achieve silent code execution without physical access or user installation [17, 18, 103]. Second, the *local malicious application adversary* persuades a user (via Play or sideloading) to install an unprivileged APK running in `u:r:untrusted_app` (`UID u0_a*`) and hunts `Binder`, `Intent` redirection, `AccessibilityService`, or `Mali`/`Adreno` GPU driver bugs (`CVE-2023-4211`, `CVE-2024-23380`) to escalate privileges or siphon financial data [36, 43, 44, 104]. Third, the *physical forensic or theft adversary* seizes a powered-off phone in the `Before First Unlock` (`BFU`) state or snatches a running locked phone in the `After First Unlock` (`AFU`) state, deploying USB-C zero-day exploit appliances (`Cellebrite` `CVE-2024-53104` / `CVE-2024-53197`), `EDL` `Firehose` loaders, cold-boot `fastboot` RAM dumps (`CVE-2024-29745`), or silicon fault-injection rigs [16, 38, 105, 106, 107].

Fourth, the *hostile OEM, ODM, or supply-chain actor* controls factory provisioning lines or vendor `BSP` code, risking leaked hardware attestation keyboxes, unprovisioned `RPMB` keys, backdoored vendor HALs, or multi-month patch gaps between upstream AOSP/GPU fixes and retail OTA delivery [10, 43, 108, 109]. Fifth, the *fraudulent device owner* deliberately unlocks their own bootloader (`ORANGE`), flashes `KernelSU` or `APatch`, hooks `IKeystoreService` via `TrickyStore` with stolen OEM keyboxes, and attempts to spoof `Play Integrity` (`MEETS_STRONG_INTEGRITY`), banking anti-tamper checks, or `Widevine` L1 DRM [42, 45, 110, 111]. Sixth, the *cloud or infrastructure operator adversary* possesses root administrative access or legal compulsion over backend backup and AI servers, requiring client-side encryption anchored in `Titan` Cloud Key Vault HSMs and hardware-attested `Titanium Intelligence Enclaves` ([Chapter 19](19-e2ee-backups-private-ai-compute.md)) so Google itself never holds plaintext recovery keys or AI prompts [8, 112, 113].

Across all six adversary classes, one analytical principle separates resilient architectures from brittle ones: *distinguishing local mechanism validity from end-to-end delegated authorization* [1, 2]. Almost no real-world Android exploit breaks `SHA-256`, factors `RSA-4096`, or distinguishes `AES-256-GCM` from random noise. Instead, chains break at architectural seams where a consumer verifies that a cryptographic signature, `UID` stamp, or hardware state bit is locally valid, yet assumes it proves a stronger system-wide invariant than was actually measured:

At the remote attestation seam ([Chapter 15](15-key-attestation-rkp.md) and [Chapter 16](16-play-integrity-keybox-wars.md)), a valid X.509 certificate chain ending at Google's Hardware Attestation Root CA proves only that *some* non-revoked hardware key signed a `KeyDescription`; if a backend forgets to check `attestationSecurityLevel != SOFTWARE`, ignores Google's live revocation JSON for leaked ODM keyboxes, reads `RootOfTrust` from `softwareEnforced` rather than `teeEnforced`, or fails to bind the attested key to session requests via a fresh server nonce, an `ORANGE`-rooted bot farm replays a clean attestation effortlessly [29, 108, 111]. At the IPC seam ([Chapter 9](09-uid-zygote-binder.md)), `/dev/binder` stamps `getCallingUid()` unforgeably on the outer call, yet an exported `Activity` that blindly calls `startActivity()` on an attacker-supplied nested `Intent` delegates its own valid `UID` and `FileProvider` grants as a confused deputy [73, 104, 114]. At the human-interface seam ([Chapter 10](10-apk-signing-scoped-storage.md) and [Chapter 11](11-accessibility-advanced-protection.md)), an APK signed under `APK Signature Scheme v3` by a verified developer identity proves authorship and byte integrity, not benign intent; once granted `AccessibilityService` outside `Advanced Protection Mode`, UI automation clicks buttons *above* `SELinux` and `KeyMint` as the human user [36, 39, 90, 115]. And at the physical encryption seam ([Chapter 4](04-keymint-weaver-throttling.md) and [Chapter 12](12-fbe-usb-theft-protection.md)), `Weaver`-backed `fscrypt` renders `BFU` flash ciphertext unbreakable offline, yet while a phone rests warm in `AFU` with `CE` keys loaded in `UFS` Inline Crypto keyslots, data confidentiality depends entirely on the USB-C port perimeter, lockscreen state machine (`CVE-2022-20465`), and timed auto-reboot eviction [16, 92, 116, 117].

Every one of those runtime boundaries still terminates downward at CPU reset. If an attacker runs unverified instructions before the Linux kernel or `EL2` `pKVM` hypervisor initializes, `SELinux` policies, `SMMUv3` stream tables, `Arm MTE` tag checks, and `KeyMint` `RootOfTrust` latches can all be subverted before userspace draws its first frame. [Chapter 1](01-bootrom-avb-vbmeta.md) begins at the SoC `Boot ROM`, hardware eFuses, vendor bootloader pipelines, and `AVB 2.0` `VBMeta` descriptor graph that anchor the entire Android trust chain.
