# The Android Trust Chain

## From Verified Boot 2.0, StrongBox, and pKVM Through SELinux and Keystore to Play Integrity and Private Compute

**Parag Mali**

---

Android runs atop the Linux kernel, yet inverts nearly every trust assumption of traditional desktop Unix. On Android, there is no shared interactive user account trusted across installed programs: every application receives a distinct Linux `UID` at install time, executes inside a mandatory enforcing `SELinux` domain governed by `neverallow` Compatibility Test Suite (`CTS`) gates, communicates exclusively over kernel-mediated `Binder` IPC, and stores secrets under `File-Based Encryption` (`FBE`) backed by `Arm TrustZone` `KeyMint` or a discrete `StrongBox` security chip such as `Google Titan M2` [1, 2]. Beneath userspace, `Android Verified Boot 2.0` (`AVB` `VBMeta` descriptors, rollback indexes, and error-correcting `dm-verity`) seals read-only OS partitions, `Protected KVM` (`pKVM` in `EL2`) strips both the host kernel and legacy `TrustZone` TEEs of access to isolated guest frames [2], `Arm MTE` hardens heap safety in production [3], and `Private Compute Core`, typed `AppFunctions` [6], `Intrusion Logging` [5], and `Private AI Compute` (`Titanium Intelligence Enclaves`) [7] extend hardware-attested trust into tamper-evident forensics and agentic AI.
