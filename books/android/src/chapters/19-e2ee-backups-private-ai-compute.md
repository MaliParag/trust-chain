# E2EE Backup Vaults and Private AI Compute

## Overview

* **Link in the Chain:** Hardware-attested cloud extension layer; stretches the handset's silicon trust chain into data-center hardware via `Google Titan` Cloud Key Vault (`CKV`) Trusted Hardware Modules (protecting end-to-end encrypted device backups and passkey security domains) and `Titanium Intelligence Enclaves` (`TIE`) on custom Google `TPU`s (`Private AI Compute`).
* **Core Security Invariant:** Neither cloud storage administrators nor AI cluster SREs possess decryption keys for user backups or `Private AI Compute` workloads: `Application Backup Keys` and `Passkey` vault keys are sealed to OS-attested `Titan` `THM` cohorts enforcing a hard hardware counter of `<= 10` failed `LSKF` attempts, and cloud AI prompts terminate via end-to-end `HPKE` encryption directly inside `DICE`-attested `Titanium Intelligence Enclaves`.
* **Ecosystem Enforcement Tier:** `Google Titan` E2EE Cloud Backup and `Private AI Compute` (`TIE`, including client-keyed encrypted server-side memory) operate natively across certified `GREEN` Android 9-17 handsets; open-source AOSP and `GrapheneOS` (`YELLOW`) integrate `Seedvault` local/WebDAV E2EE backups encrypted under high-entropy `BIP-39` 12-word mnemonics without cloud HSM dependencies.
* **Trusted Computing Base (TCB):** Client `BackupManagerService` + `RecoveryController` `@SystemApi`, `Google Titan` `THM` silicon and offline-signed `Cohort` firmware, client `RATS`/`DICE` attestation verifier + `RFC 9180` `HPKE` / `RFC 9458` `OHTTP` client, `Titanium` (`Titan` + `Caliptra` RTM) host roots of trust, and sealed Google `TPU` enclaves (`TIE`).
* **Seam & Handoff:** Completes the vertical hardware-to-cloud trust chain from handset Boot ROM all the way to data-center HSMs and confidential TPU pods; hands the volume's adversarial synthesis to Finale [Chapter 20](20-multivendor-spyware-chains.md), examining how commercial spyware chains route around AOSP through multi-vendor peripheral silicon and patch gaps.

## Threat Model & Ecosystem Constraint

Keeping every cryptographic key strictly inside a smartphone's discrete `StrongBox` security chip ([Chapter 3](03-trustzone-strongbox.md) and [Chapter 4](04-keymint-weaver-throttling.md)) and encrypting `/data` under `fscrypt` ([Chapter 12](12-fbe-usb-theft-protection.md)) delivers uncompromising local confidentiality right up until the physical phone is crushed in traffic, dropped into salt water, or stolen permanently. Without an off-device backup, pure hardware-bound key custody turns commonplace hardware loss into catastrophic personal data loss: decades of family messages, two-factor authenticator seeds, application databases, and synced `WebAuthn` passkeys vanish forever [388, 513, 514]. Conversely, if the operating system uploads backups encrypted under a server-managed KMS key held by the cloud provider (the pre-2018 industry norm), then a compromised cloud administrator, a nation-state breach of cloud control planes, a SIM-swap account-recovery hijack, or a legal compulsion order can decrypt a user's digital life wholesale without ever touching their physical handset [513].

Why cannot Android simply derive a symmetric backup key locally via `AES_Key = Argon2id(6_digit_PIN, salt)` and upload the resulting ciphertext to untrusted cloud object storage? Because human memory and offline GPU silicon sit orders of magnitude apart! As Joseph Bonneau and Stuart Schechter measured at USENIX Security [515], human beings struggle to recall rarely typed secrets approaching `56 bits` of entropy, whereas users reliably remember their daily Lock Screen Knowledge Factor (`LSKF`: a 4- or 6-digit PIN, 3x3 swipe pattern, or password) precisely because they rehearse it dozens of times a day [513]. Yet a 6-digit numeric PIN spans only $10^6 \approx 2^{19.93}$ combinations! On the physical handset ([Chapter 4](04-keymint-weaver-throttling.md)), `Titan M2` `Weaver` hardware throttling stretches $10^6$ guesses past a millennium; if an attacker obtains a raw PIN-encrypted blob from cloud storage without hardware rate-limiting, a modest cluster of consumer GPUs exhausts all $1{,}000{,}000$ candidates offline in milliseconds [62, 513].

An almost identical trust cliff emerged between 2024 and 2026 for frontier generative AI [8, 516, 517]. While on-device `Gemini Nano` inside `Private Compute Core` ([Chapter 18](18-on-device-agentic-ai.md)) keeps short-context summarization local, proactive cross-application synthesis (such as Pixel 10 *Magic Cue* [518]), multilingual *Recorder* meeting summarization, complex agentic planning, and persistent cross-device AI memory ([519]) require massive frontier *Gemini* models executing across high-bandwidth data-center *Tensor Processing Unit* (`TPU`) pods. Under conventional cloud serving, TLS terminates at a perimeter load balancer or inside a standard host OS where Site Reliability Engineers (`SRE`s) hold break-glass SSH shells, crash dumps capture process RAM, and telemetry pipelines can log plaintext prompts [8, 516]. Extending handset-grade zero-operator-access guarantees into Google's cloud required two purpose-built, hardware-attested systems: the `Google Cloud Key Vault Service` (`CKV` / `CKVS`) protecting E2EE Backups and Passkey Sync [388, 513], and `Private AI Compute` executing inside `Titanium Intelligence Enclaves` (`TIE`) [8, 517].

## Architecture & AOSP Implementation

### End-to-End Encrypted Cloud Backups and the `Google Titan` Cloud Key Vault (`CKVS`)

Introduced in Android 9 (`Pie`) and formalized in Shabsi Walfish's *Google Cloud Key Vault Service* whitepaper [513], Android's E2EE backup architecture (`BackupManagerService` paired with the privileged `RecoveryController` `@SystemApi` in `frameworks/base/core/java/android/security/keystore/recovery/` [514, 520]) bridges low-entropy human `LSKF` secrets to 256-bit cloud encryption by placing custom `Google Titan` Trusted Hardware Modules (`THMs`) inside data-center Vault Servers.

![Figure: End-to-end encrypted Android Cloud Backup protocol wrapping backup keys to verified Google Titan Cloud Key Vault HSM cohorts.](diagrams/19-titan-backup-key-vault.svg)

Observe first how client-side privilege separation minimizes local attack surface [513, 520]. Rather than exposing the user's `LSKF` or backup encryption keys to network-facing Google Play Services code, AOSP splits client duties across two components: the *Android Framework* (`system_server` / `LockSettingsService`, which briefly observes the `LSKF` in RAM at the exact instant the user unlocks the screen and holds exclusive `@SystemApi` access to `RecoveryController`), and the user-space *Recovery Agent* inside Play Services, which transports opaque encrypted protocol bundles to and from Google's servers *without ever observing the current device's `LSKF` or plaintext `Recovery Key`* [513, 520]. Meanwhile, `BackupManagerService` encrypts application `Auto Backup` archives, device settings, and SMS history locally on the phone using authenticated `AES-256-GCM` under random 256-bit keys wrapped by the `Recovery Key` before uploading opaque ciphertext to untrusted Google Backup Storage [513, 514].

To survive individual chip failures and data-center outages across billions of Android phones without weakening hardware security, Google organizes Vault Servers retrofitted with custom `Titan` `THM` microcontrollers into geo-replicated *Cohorts* distributed across independent maintenance zones [513, 521]. Inside each Cohort, the `Titan` chips run minimal, audited `CKV` firmware that generates a shared *Cohort keypair* $(pk_{\text{cohort}}, sk_{\text{cohort}})$ such that $sk_{\text{cohort}}$ never leaves `Titan` silicon boundaries. Follow the three-phase cryptographic protocol [513, 522]:

In *Phase 1 (Initialization and Root-of-Trust Verification)*, an offline, multi-party-quorum signing key controlled by Google signs a monotonic, sequence-numbered manifest of active `Cohort Public Keys` (preventing attacker rollback to retired cohorts). Crucially, *the public verification key for that offline Root of Trust is baked directly into the read-only Android OS image* (`dm-verity` protected, [Chapter 2](02-antirollback-verity-apex.md)) and cannot be altered without a verified OS update [513]! When the Recovery Agent fetches the latest `Cohort Public Key` list, the Android Framework verifies the offline-root signature and sequence number in AOSP code and randomly selects a `Cohort Public Key` $pk_{\text{cohort}}$.

In *Phase 2 (Vault Creation and Key Rotation)*, the next time the user physically enters their `LSKF` on the lock screen, the Framework generates a fresh 256-bit `Recovery Key` $K_{\text{rec}}$, stretches the `LSKF` through a salted, memory-hard hash $H_{\text{LSKF}}$ (providing independent cryptographic defense whenever the user chooses an alphanumeric passphrase!), inner-encrypts $K_{\text{rec}}$ under a key derived from $H_{\text{LSKF}}$, and outer-encrypts the bundle (bound to the creating device's identifier and a deterministic counter slot address) under $pk_{\text{cohort}}$ to produce the opaque `Vault` blob uploaded to `CKV` [513]. When `Recovery Keys` rotate periodically, the Framework reuses the exact same hardware counter slot address unless `LSKF` itself changed, ensuring key rotation never resets failed-guess budgets [513].

In *Phase 3 (Vault Opening and Hardware Rate-Limiting)*, when the user sets up a replacement phone after losing the original, the user enters their old device's `LSKF`. The replacement Framework generates an ephemeral `Claimant Key` $K_{\text{claim}}$ and encrypts $(K_{\text{claim}}, H_{\text{LSKF}}, \text{challenge\_nonce})$ to the original Vault's $pk_{\text{cohort}}$ over an authenticated `Noise`-style handshake [513, 522], forming a fresh `Recovery Claim`. Inside the Cohort's `Titan` `THM`, hardware-enforced logic executes the Vault Opening check: `Titan` inspects its internal non-volatile per-Vault failed-attempt counter *before* testing $H_{\text{LSKF}}$. If $H_{\text{LSKF}}$ fails to match, `Titan` atomically increments the internal NVM counter (supplemented by exponential software backoff on `CKV` front-ends so a cloud account hijacker cannot trivially burn all guesses in one second to DoS the legitimate owner!). Once the counter hits *10 failed attempts*, `Titan` permanently refuses all future `Recovery Claims` for that `Vault`, capping any adversary (including a rogue cloud operator holding raw database dumps) at a $10 / 10^6 = 0.001\%$ brute-force ceiling [513]! If $H_{\text{LSKF}}$ matches within `<= 10` attempts, `Titan` unwraps $K_{\text{rec}}$ in internal SRAM and re-encrypts it directly under $K_{\text{claim}}$ back to the replacement phone's Framework.

What stops Google itself from compiling modified `Titan` firmware that ignores the 10-attempt counter and flashing it onto a live Vault Server? A hardware bootloader invariant inside `CKV` `Titan` silicon [513]: *`Titan`'s immutable mask ROM and altered `CKV` bootloader cryptographically wipe all stored internal state, including $sk_{\text{cohort}}$, prior to applying any firmware update!* Updating `CKV` firmware is therefore mathematically equivalent to physically incinerating the chip; existing Vaults sealed under $pk_{\text{cohort}}$ can never be opened by altered firmware [513]. Android 10 through 17 reuse this exact `LSKF` + `Titan` `CKV` architecture to protect the `Google Password Manager` (`GPM`) `hw_protected` Passkey Security Domain ([Chapter 13](13-biometrics-passkeys.md) [388]): cross-device recovery ceremonies (`Credential Manager` enrollment on a new handset or QR-assisted proximity bootstrap) unwrap the user's shared 256-bit security-domain secret only after proving knowledge of an existing device's `LSKF` to `Titan` `CKV` or completing local hardware-verified transfer, synchronizing `WebAuthn` `ECDSA P-256` passkeys end-to-end without Google ever holding plaintext credential material [388, 513].

### Google `Private AI Compute`: `Titanium` Hardware Roots and `Titanium Intelligence Enclaves` (`TIE`)

Unveiled in November 2025 [8, 517] and expanded in September 2026 with client-keyed persistent cloud memory [519], `Private AI Compute` extends `Private Compute Core`'s ([Chapter 18](18-on-device-agentic-ai.md)) zero-operator-access model from on-device `Gemini Nano` to frontier cloud *Gemini* models running on custom Google `TPU` pods.

To understand why `Private AI Compute` required custom data-center engineering rather than booting an off-the-shelf CPU Confidential VM, examine the *Accelerator Doorstep Problem* [517, 523, 524]. Standard x86 Confidential VMs (`AMD SEV-SNP` and `Intel TDX`) encrypt host CPU DRAM, yet 100-billion-parameter LLMs execute matrix multiplications inside external accelerators (`TPU`s or GPUs) attached over high-speed PCIe or inter-chip interconnects (`ICI`). If a prompt is decrypted inside a CPU Confidential VM and DMA-copied in cleartext over unauthenticated board traces into accelerator High-Bandwidth Memory (`HBM`) managed by an untrusted host driver, physical interposers or privileged host agents can snoop activations at the accelerator boundary [517, 523].

Google solves that hardware perimeter problem atop its multi-layered `Titanium` hardware security architecture [521, 523, 525]:

![Figure: Private AI Compute architecture terminating end-to-end HPKE client tunnels inside DICE-attested Titanium Intelligence Enclaves (TIE) spanning confidential hosts and custom Google TPUs.](diagrams/19-private-ai-compute-tie.svg)

At the physical foundation of `Titanium` sits the principle that *the security perimeter is the silicon package itself*, explicitly distrusting server motherboards, SPI flash traces, and network cables [523]. Every `Titanium` server and accelerator board embeds two complementary silicon roots of trust [521, 523, 526]: first, the discrete `Google Titan` microcontroller (provisioned in unmanned, four-camera Common Criteria OSAT cleanrooms via epoxy-encapsulated *Scribe* handlers whose signing keys live solely in volatile SRAM [521]), which physically interposes on the SPI bus between boot flash and host CPUs/APs, holding the processor in reset until `Titan`'s mask ROM verifies `Titan` firmware (`SVN`-bound) and `Titan` verifies every byte of AP boot flash (*first-instruction integrity* [521]); and second, `Caliptra` (the open-source CHIPS Alliance / OCP silicon Root of Trust for Measurement integrated directly inside SoC/ASIC die layers [523, 526]), which eliminates external SPI bus interposers completely and emits `OpenProfile for DICE` ([Chapter 5](05-pkvm-avf-microdroid.md) [33]) hardware attestation chains across CPUs and custom Google `TPU`s, paired with `Titanium` Offload Processors (`TOPs` / `IPU`s) running line-rate `PSP` cryptographic link encryption [525, 527].

Built directly on that `Titanium` substrate, `Titanium Intelligence Enclaves` (`TIE`) encapsulate both the confidential host orchestrator (`AMD SEV-SNP` / `Titanium`-locked immutable OS images stripped of SSH daemons, debuggers, and admin break-glass shells) and custom Google `TPU` accelerators inside one hardware-attested enclave boundary [8, 517]. Trace the end-to-end lifecycle of a `Private AI Compute` request from a Pixel 10 or Android 17 handset (such as *Magic Cue* synthesizing recent calendar, message, and email context [518]):

First, *Client-Verified Remote Attestation (`RATS` + Binary Transparency)* [517, 519, 528]: before transmitting a single user token, the Android handset receives the `TIE` serving enclave's `DICE`-rooted attestation evidence and verifies both the hardware silicon chain (`Titan` / `Caliptra` `SVN` floors) and inclusion proofs inside a *tamper-proof public server-software transparency record* [517, 519]. If Google attempted to deploy a modified server binary that logged prompts or exported keys, its measurement would diverge from the public transparency log and the handset would abort connection setup locally!

Second, *IP-Blinded Ingress (`OHTTP`) and End-to-End `HPKE` Sealing* [423, 517, 529]: to prevent front-end network infrastructure from correlating user IP addresses with enclave workloads, traffic traverses Oblivious HTTP (`RFC 9458` `OHTTP` [529]) privacy relays while the handset encrypts the prompt payload on-device via `RFC 9180` Hybrid Public Key Encryption (`HPKE` [423]) directly to an ephemeral public key generated inside `TIE` enclave RAM (and never exported outside the enclave). Perimeter load balancers and Google SREs see only opaque `HPKE` ciphertext!

Third, *Stateless `TPU` Execution and Client-Keyed Persistent Memory* [517, 519]: `TIE` decrypts the `HPKE` payload exclusively inside isolated enclave memory, runs frontier Gemini inference across sealed `TPU` `HBM` with zero retention for model training or human review, streams `HPKE`-encrypted response tokens back to the handset, and wipes ephemeral activation and KV-cache state immediately upon completion [8, 517]. Furthermore, in September 2026 Google DeepMind and the Private AI Compute team resolved pure-stateless amnesia across devices (mobile, web, and smart glasses) without weakening operator exclusion [519]: long-term personal AI memory is stored in dedicated encrypted cloud vaults under per-user Data Encryption Keys (`DEK`s) wrapped by Key Encryption Keys (`KEK`s) *held exclusively on the user's personal devices*. Only when the user's device opens an attested, end-to-end encrypted session into `TIE` does the enclave temporarily unwrap the `DEK` in isolated RAM, read and update personal context, re-seal the updated ciphertext, and zeroize all plaintext and keys upon disconnect [519]!

### Three-Way Architectural Synthesis: Google `Private AI Compute` (`TIE`) vs. Apple `PCC` vs. Azure `CVM`s

How does Google's `Private AI Compute` (`TIE`) compare architecturally against Apple's `Private Cloud Compute` (`PCC`) and general-purpose enterprise Cloud Confidential VMs (`Microsoft Azure Confidential VMs` on `AMD SEV-SNP` / `Intel TDX` + `NVIDIA H100`/`Blackwell`)?

![Figure: Three-way confidential cloud AI comparison matrix across Google Private AI Compute (TIE), Apple Private Cloud Compute (PCC on Apple Silicon and Google Cloud), and Microsoft Azure Confidential VMs.](diagrams/19-extra-tie-pcc-cvm-three-way-matrix.svg)

Examine the convergence and structural distinctions across all three systems [8, 516, 524, 530, 531, 532]. General-purpose IaaS Confidential VMs, exemplified by Microsoft Azure Confidential VMs (`DCasv5`/`ECasv5` using AMD `SEV-SNP` Reverse Map Tables `RMP`, `DCesv6` using Intel `TDX` `SEAM` + `PAMT`, an in-boundary Rust paravisor `OpenHCL` at `VMPL0`, and `MAA` Secure Key Release, optionally paired with `NVIDIA H100`/`Blackwell` Confidential GPUs over `SPDM`-attested encrypted PCIe bounce buffers [524, 532]), are designed for *arbitrary tenant-administered operating systems*. Consequently, while the cloud host hypervisor is excluded from guest DRAM, *the enterprise tenant* remains responsible for disabling SSH shells inside their own guest OS image, authoring strict `MAA` attestation policies, conjunctively binding CPU and GPU quotes, and publishing transparency manifests if end users require proof of non-logging [524].

By contrast, both Google `Private AI Compute` (`TIE`) [8, 517] and Apple `Private Cloud Compute` (`PCC`, originally launched in June 2024 on custom M-series Apple Silicon server blades running a stripped iOS/macOS derivative verified by Secure Enclave trust caches and `OHTTP` relays [516]) engineer *single-purpose, zero-admin consumer AI appliances* enforcing five end-to-end invariants at the platform layer: stateless (or strictly client-keyed) personal data processing, zero privileged runtime SRE shells, non-targetability via blinded routing and hardware fleet ledgers, client-enforced pre-flight attestation, and public binary transparency!

In June 2026 at WWDC26, those two ecosystems converged in a landmark engineering collaboration: Apple and Google Cloud jointly unveiled *Expanded Private Cloud Compute on Google Cloud* [530, 531]! To run next-generation Apple Intelligence agentic and Gemini-derived foundation workloads inside third-party Google Cloud data centers *without* relaxing any of Apple's five `PCC` invariants, Apple, Google, Intel, and NVIDIA co-engineered an open-source confidential host stack combining `Intel TDX` CPUs, `NVIDIA Blackwell` Confidential Computing GPUs, and `Google Titan` hardware roots of trust [530, 531]. Look at the defense-in-depth breakthroughs introduced in that joint architecture [530]: every Google Cloud hardware node in the `PCC` fleet is recorded in a cryptographically verifiable, append-only hardware supply-chain ledger; sensitive exfiltration-relevant components require *multi-vendor software attestation rooted in at least two independent silicon roots of trust* (pairing `Google Titan` with CPU/GPU roots and Apple cryptographic approval); inbound network parsing executes inside per-request isolated namespaces; shared inference processes recycle on short time-to-live (`TTL`) timers; and attested decryption keys reside inside a *separate, dedicated Confidential VM* isolated from external network parsers [530, 531]! Meanwhile, Google's native `Private AI Compute` (`TIE`) leverages Google's vertically integrated custom `TPU` tensor pods and `Titanium` (`Titan` + `Caliptra`) fabric to deliver identical zero-operator-access guarantees natively across the global Android ecosystem [8, 517].

> **Key idea.**
> Confidential cloud architectures (`Titan CKV`, `Google TIE`, and `Apple PCC`) transform "trust us not to read your cloud data" from a legal privacy policy into a falsifiable hardware invariant: the smartphone's `dm-verity`-protected OS verifies silicon-signed `DICE`/`THM` quotes and public append-only transparency logs *before* releasing a single `HPKE` or `Noise` ciphertext packet, leaving cloud operators holding opaque randomness.

## Vendor, OEM, & Custom-OS Boundaries

On certified GMS (`GREEN`) devices running Android 9 through 17, `Cloud Key Vault` E2EE backups activate automatically whenever a user configures a screen lock (`PIN`, pattern, or password), protecting all apps participating in standard `BackupManager` `Auto Backup` (apps handling ephemeral session tokens can opt specific files out via `<exclude>` XML rules or `android:allowBackup="false"`) [513, 514]. Enterprise `DevicePolicyManager` controllers ([Chapter 17](17-android-enterprise.md)) can independently govern `setBackupServiceEnabled()` inside a managed `Work Profile` so regulated corporate data inside `User 10` follows organizational archival policies without disabling personal `User 0` E2EE disaster recovery. On de-Googled AOSP forks and `GrapheneOS` (`YELLOW`), where proprietary Google Play Services Recovery Agents are absent by default, `GrapheneOS` ships the open-source `Seedvault` backup engine (`com.stevesoltys.seedvault` [533]) integrated directly into `BackupManagerService`: instead of wrapping keys to a 6-digit PIN inside a remote cloud HSM, `Seedvault` generates a 12-word `BIP-39` mnemonic seed (`128 bits` of true cryptographic entropy!), derives separate `AES-256-GCM` encryption and `HMAC` chunk keys locally via `HKDF`, and streams authenticated ciphertext chunks to local USB-C flash drives or self-hosted `Nextcloud` / `WebDAV` storage, requiring zero trust in any cloud hardware cohort [20, 533].

### The Complete Vertical Spine and Its Final Stress Test

Pause and survey the unbroken vertical trust chain constructed from [Chapter 1](01-bootrom-avb-vbmeta.md) through [Chapter 19](19-e2ee-backups-private-ai-compute.md): immutable SoC `Boot ROM` fuses verify `AVB 2.0` `VBMeta` and `dm-verity` partitions; `Titan M2` `StrongBox` and `Weaver` throttle physical `LSKF` guesses; `EL2` `pKVM` de-privileges the host Linux kernel; enforcing `SELinux` `neverallow` policies, `KCFI`, `Rust`, and hardware `Arm MTE` harden runtime execution; `UID` sandboxes, `APK v3`/`v4` `fs-verity` signatures, `Advanced Protection`, `fscrypt` `FBE`, `Passkeys`, and E2EE `Intrusion Logging` protect local state; and `RKP` `Key Attestation`, `Work Profiles`, `Private Compute Core`, `Titan` `Cloud Key Vault` HSMs, and `Titanium Intelligence Enclaves` carry hardware-verifiable trust across enterprises and into frontier cloud `TPU` clusters.

If every vertical link in that AOSP and cloud architecture is engineered with such rigor, *why do commercial surveillance vendors (`Cytrox / Intellexa Predator`, `NSO Group Pegasus`) and nation-state exploit teams still compromise unpatched Android devices in the wild?* Finale [Chapter 20](20-multivendor-spyware-chains.md) dissects the answer: elite attackers route around Android's hardened core by targeting *horizontal multi-vendor silicon and supply-chain seams*, namely over-the-air cellular basebands, reachable third-party GPU kernel drivers, and the multi-month OEM-to-carrier patch gap.

## Inspecting via ADB, Fastboot, & Attestation

Verify `BackupManagerService` (`bmgr`) activation state and inspect the active backup transport (`com.google.android.gms/.backup.BackupTransportService` on certified GMS builds vs. `com.stevesoltys.seedvault` on `GrapheneOS`):

```bash
adb shell bmgr enabled
adb shell bmgr list transports
```

Query `dumpsys backup` to confirm client-side encryption status, key-value/full-backup queue state, and active vault transport bindings:

```bash
adb shell dumpsys backup | grep -iE 'Encrypted|Transport|BackupManager' | head -n 8
```

Inspect `LockSettingsService` and `RecoveryController` keystore recovery-agent state protecting `LSKF`-wrapped `Cloud Key Vault` snapshots:

```bash
adb shell dumpsys lock_settings | grep -iE 'Recovery|Credential|Weaver' | head -n 8
```
