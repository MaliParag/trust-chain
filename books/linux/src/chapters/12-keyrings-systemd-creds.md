# Local Secret Custody: Kernel Keyrings, systemd-creds, and TPM2 PKCS#11

## Overview

* **Link in the Chain:** Secures symmetric service credentials, API tokens, and asymmetric private keys at rest and in RAM for sandboxed daemons ([Chapter 11](11-systemd-dbus-sandboxing.md)) and user sessions, binding secret availability to the `TPM 2.0` measured boot and PCR policy chain ([Chapter 2](02-uki-systemd-pcrlock.md)).
* **Core Security Invariant:** Long-lived secrets never reside in plaintext `/etc` files, swap-backed `tmpfs` mounts, or `/proc/<pid>/environ` strings; `systemd-creds` seals credentials via `AES-256-GCM` under a hybrid `.host` + `TPM 2.0` key and projects them exclusively into `MS_NOSYMFOLLOW` non-swappable `ramfs` mounts (`/run/credentials/<unit>/`), while operational mTLS and SSH keys execute inside `TPM 2.0` silicon (`tpm2-pkcs11`, `tpm2-openssl`) or `Possessor`-gated (`@s`) kernel keyrings.
* **Deployment Profile Matrix:** Legacy mutable deployments scatter `0600` plaintext secrets across `/etc` and `.env` files; modern `systemd` (`v250+`) servers and immutable appliances (`CoreOS`, `Flatcar`, `UKI` hosts) seal declarative configs via `LoadCredentialEncrypted=` and OpenSSL 3 `tpm2` providers; desktop workstations expose `org.freedesktop.secrets` (`GNOME Keyring`, `KWallet`) over session D-Bus unless isolated behind Flatpak `org.freedesktop.portal.Secret`.
* **Trusted Computing Base (TCB):** Linux `security/keys/` retention subsystem (`trusted`, `encrypted`, and `logon` key types), `mm/secretmem.c` (`memfd_secret`), `TPM 2.0` Storage Root Key (`SRK`) and `PCR[7]`/`PCR[11]` policies, `PID 1` (`src/shared/creds-util.c` credential unsealer and `ramfs` mounter), `tpm2-pkcs11` / `tpm2-openssl`, and `xdg-desktop-portal`.
* **Integration Seam & Handoff:** Eliminates plaintext credential theft from disk backups, swap partitions, passive TPM bus taps, and sibling units; hands off authenticated human login (`PAM`, `SSSD`) and short-lived fleet SSH and `FIDO2` identity to [Chapter 13](13-pam-ssh-fido2.md).

## Problem Statement & Threat Model

Contrast how Windows, Apple platforms, and traditional Linux custody application secrets. Windows provides the Data Protection API (`DPAPI`), `CNG` TPM Key Storage Providers (`MS_PLATFORM_CRYPTO_PROVIDER`), and `VTL1` `LsaIso.exe` Key Guard; Apple platforms provide the Secure Enclave-backed `Keychain` gated cryptographically by per-binary code-signing entitlements. Historically, Linux shipped neither an OS-wide hardware-backed secret broker for services nor per-application MAC-gated user keychains: daemons read plaintext private keys directly from `/etc/ssl/private/server.key`, `/etc/wireguard/wg0.conf`, or `EnvironmentFile=/etc/default/myapp` guarded solely by `0600` POSIX Discretionary Access Control bits [37, 71].

Trace the four concrete seams where `/etc` plaintext files, environment variables, and naive TPM sealing break under realistic adversary models [37, 365, 366]:
First, *offline image, backup, and GitOps exposure*: in declarative infrastructure (`Ansible`, `NixOS`, `rpm-ostree`, golden cloud AMIs, and nightly `/etc` tarballs), placing a plaintext database password or WireGuard private key inside `/etc` leaks live credentials to every backup bucket, CI artifact store, and stolen disk snapshot [37]. Second, *`DynamicUser=yes` incompatibility* ([Chapter 11](11-systemd-dbus-sandboxing.md)): when `/etc/myapp/db.key` is `0400 root:root`, an unprivileged `DynamicUser=yes` daemon whose transient UID (`61184..65519`) was allocated milliseconds before `execve()` cannot open that file without fragile root pre-start shell wrappers. Third, *`/proc` and swap-partition persistence*: passing secrets via `Environment=API_KEY=...` exposes them inside `/proc/<pid>/environ`, `systemctl show` D-Bus properties, core dumps, and every child subprocess (a catastrophic leak vector for autonomous coding agents in [Chapter 17](17-ai-agent-sandboxes.md)), while staging decrypted secrets onto ordinary `tmpfs` (`/run` or `/dev/shm`) allows the kernel VM page reclaimer under memory pressure to *page plaintext secret bytes out to an unencrypted swap device* [37, 367, 368]! Fourth, *hardware bus sniffing vs. post-compromise key cloning*: sealing a secret solely to a discrete motherboard `TPM 2.0` without disk-resident entropy falls to a physical attacker clipping a passive logic analyzer onto the unencrypted SPI or LPC TPM bus during unattended boot (`WithSecure` discrete-TPM sniffing [365]), while decrypting a raw mTLS or SSH private key into userspace DRAM allows an attacker who wins a process memory-read or `UID 0` exploit to exfiltrate the key and impersonate the node from anywhere on the internet forever [72, 369].

Closing all four seams requires matching each secret's lifecycle to the exact Linux custody primitive built for it: Ring 0 non-swappable Kernel Keyrings (`security/keys/` [71, 370]) and `memfd_secret(2)` [371] for runtime symmetric keys, `systemd-creds` hybrid `host+tpm2` sealing projected onto `MS_NOSYMFOLLOW` `ramfs` [37, 372, 373] for service configuration secrets, `tpm2-pkcs11` and OpenSSL 3 `tpm2-openssl` providers [72, 369] for non-exportable asymmetric keys, and `org.freedesktop.portal.Secret` [374] for sandboxed desktop applications.

## Kernel & Userspace Mechanics

### Linux Kernel Key Retention Service: `key_serial_t`, Possession Masks, and `trusted` / `encrypted` Keys

Merged in Linux 2.6.10 (`security/keys/`, `CONFIG_KEYS` [71, 370]) to hold filesystem encryption keys (`dm-crypt`, `fscrypt`, `eCryptfs`), NFSv4/CIFS Kerberos tickets, and kernel X.509 verification roots inside non-swappable Ring 0 slab memory, the Kernel Key Retention Service represents every key or keyring as a reference-counted `struct key` identified by a unique positive 32-bit integer `key_serial_t` [370, 375]. Userspace interacts with `security/keys/` exclusively through three system calls: `add_key(type, description, payload, plen, ringid)`, `request_key(type, description, callout_info, dest_keyring)` (which can invoke `/sbin/request-key` in Ring 3 to instantiate missing keys on demand [376]), and the multiplexed `keyctl(operation, ...)` dispatcher [71, 377]. Every key transitions deterministically across six kernel lifecycle states (`Uninstantiated`, `Instantiated`, `Negative`, `Expired`, `Revoked`, and `Dead`) while per-UID kernel quotas (`/proc/sys/kernel/keys/maxkeys` and `maxbytes`, defaulting typically to `200` keys and `20,000` bytes for unprivileged UIDs) return `-EDQUOT` before a local user can exhaust unswappable kernel memory [370].

Each thread subscribes to hierarchical anchor keyrings addressed via negative special `key_serial_t` constants (`include/uapi/linux/keyctl.h` [71, 375, 378]): `@t` (`KEY_SPEC_THREAD_KEYRING`, `-1`, private to a single thread and destroyed on thread exit or `execve`), `@p` (`KEY_SPEC_PROCESS_KEYRING`, `-2`, shared across POSIX threads of one process and cleared on `execve`), `@s` (`KEY_SPEC_SESSION_KEYRING`, `-3`, inherited across `fork()` and `execve()` throughout a login session or an isolated `systemd` service when `KeyringMode=private` is set [68, 378]), `@u` (`KEY_SPEC_USER_KEYRING`, `-4`, shared globally across *every* process running under the same `kuid_t`!), and `@us` (`KEY_SPEC_USER_SESSION_KEYRING`, `-5`, the fallback default session keyring that automatically links `@u`), alongside optional per-UID `persistent` keyrings (`keyctl_get_persistent()` [379]) and Ring 0 system X.509 anchors (`.builtin_trusted_keys`, `.secondary_trusted_keys`, `.machine`, and `.ima` from [Chapters 4](04-ima-ipe-keylime.md) and [5](05-kernel-lockdown-modules.md) [119]).

![Figure: The five Linux kernel keyring scopes (@t, @p, @s, @u, @us) and the 32-bit Possessor|User|Group|Other permission mask, showing why service secrets belong in isolated @s session keyrings rather than UID-wide @u user keyrings.](diagrams/12-kernel-keyring-scopes.svg)

Unlike 9-bit POSIX file mode bits (`rwxrwxrwx`), every `struct key` enforces a 32-bit access control mask partitioned into four 8-bit role octets (`Possessor | User | Group | Other`, defined in `include/linux/key.h` [370, 375]):

```c
/* 32-bit key_perm_t bitmasks in include/linux/key.h (Possessor|User|Group|Other) */
#define KEY_POS_VIEW    0x01000000 /* Inspect key metadata in /proc/keys or keyctl show */
#define KEY_POS_READ    0x02000000 /* Extract raw payload bytes via keyctl_read()!      */
#define KEY_POS_WRITE   0x04000000 /* Update or revoke payload via add_key/keyctl       */
#define KEY_POS_SEARCH  0x08000000 /* Traverse keyring & authorize in-kernel consumers  */
#define KEY_POS_LINK    0x10000000 /* Link key into another keyring                     */
#define KEY_POS_SETATTR 0x20000000 /* Change owner, group, expiry, or permission mask   */
/* Subsequent shifts: KEY_USR_* (>> 8), KEY_GRP_* (>> 16), KEY_OTH_* (>> 24)            */
```

Two architectural subtleties inside this 32-bit mask separate secure secret custody from trivial local credential theft [71, 370, 375]:
First, *Possession vs. UID Ownership*. A thread is a *Possessor* of key $K$ if and only if $K$ is reachable via a live `SEARCH`-permitted graph walk starting from that thread's own `@t`, `@p`, or `@s` keyrings [370]! Suppose `systemd` spawns `myapp.service` with `KeyringMode=private` (allocating a fresh anonymous `@s` session keyring unlinked from `@u` [68]) and `myapp` instantiates a key with permission `0x3f010000` (`KEY_POS_ALL | KEY_USR_VIEW`, notably omitting `KEY_USR_READ`!). Even if another daemon or desktop process running under the *exact same numeric `UID`* is compromised in a separate session, its `keyctl_read(serial)` call fails with `-EACCES` because UID ownership grants only `VIEW`, whereas `READ` requires *Possession* via `@s` [71, 375]! Conversely, developers who lazily pass `0x3f3f0000` (`KEY_USR_ALL`) or attach keys to `@u` expose raw secrets to every sibling process of that UID.

Second, *`KEY_POS_SEARCH` without `KEY_POS_READ` and Kernel-Only Key Types (`logon`, `trusted`, `encrypted`)* [119, 370]. Even inside the possessing process itself, once a key is loaded for an in-kernel subsystem (`dm-crypt`, `fscrypt`, `CIFS`), userspace never needs to read the raw key bytes again: stripping `KEY_POS_READ` while keeping `KEY_POS_SEARCH` (`0x3d010000`) allows the process to authorize kernel lookups via `request_key()` while blocking `keyctl_read()` against post-initialization memory-compromise exploits! Better yet, `Documentation/security/keys/trusted-encrypted.rst` [119] defines three specialized key types that forbid raw userspace extraction architecturally: `logon` keys (`add_key("logon", "fs:mykey", ...)`) permanently lack a `.read` method (`-EOPNOTSUPP`), rendering their payloads readable exclusively by Ring 0 C callers [370]; `trusted` keys (`add_key("trusted", "kmk", "new 32 keyhandle=0x81000001 pcrinfo=...", ...)`) generate random symmetric keys *inside* a hardware trust source (`TPM 2.0` rooted to the Storage Root Key `SRK`, ARM `OP-TEE` rooted to fused Hardware Unique Keys `HUK`, NXP `CAAM`, or IBM `PowerVM` Platform KeyStore), returning *only* a hardware-sealed ciphertext blob when userspace invokes `keyctl pipe` for disk persistence [119]; and `encrypted` keys (`add_key("encrypted", ...)`) derive and wrap kernel-only symmetric keys (`AES-CBC` + `HMAC-SHA256`) beneath a master `trusted` or `user` key so systems can manage thousands of rotated volume/EVM keys without exhausting scarce TPM NVRAM slots [119]!

For ultra-sensitive secrets processed directly in Ring 3 (such as TLS session ticket keys or WireGuard handshakes), Linux `5.14+` (`mm/secretmem.c`, enabled via `memfd_secret(0)` [371, 380]) closes one additional Ring 0 exposure: pages faulted into a `memfd_secret` file descriptor are locked against swap *and* unmapped from the kernel's own 1:1 physical direct map (`set_direct_map_invalid_noflush()`), preventing both cold-swap persistence and cross-process kernel direct-map read gadgets! Meanwhile, because `security/keys/` and its notification hooks expose complex Ring 0 object lifecycles to unprivileged callers (`SystemCallFilter=@system-service` permits `keyctl` unless tightened, whereas Docker's default `seccomp` blocks `keyctl`/`add_key`/`request_key`!), kernel hardening remains essential: Jann Horn's `CVE-2016-0728` [381] leaked a 32-bit `atomic_t usage` counter in `join_session_keyring()` ($2^{32}$ calls wrapping to zero to trigger a `struct key` Use-After-Free, motivating Linux's saturating `refcount_t` [229]), `CVE-2017-15299` / `15951` [382] and `CVE-2019-19083` [383] hit uninstantiated-key state races, and `CVE-2022-0995` [384] (exploited in the wild and added to CISA KEV) abused `keyctl_watch_key()`'s `watch_queue` event filter (`IOC_WATCH_QUEUE_SET_FILTER`) for an out-of-bounds kernel heap write!

### `systemd-creds`: Hybrid `host+tpm2` Sealing and `MS_NOSYMFOLLOW` `ramfs` Projection

To eliminate `/etc` plaintext secrets and `Environment=` leaks across every Linux daemon uniformly, `systemd` (`v250+`, `src/shared/creds-util.c` [37, 372, 373]) introduced System and Service Credentials (`systemd-creds(1)`):

![Figure: End-to-end secret lifecycle in systemd-creds: sealing secrets to TPM 2.0 + host secret via AES-256-GCM, storing opaque .cred blobs in /etc/credstore.encrypted/, and projecting plaintext exclusively into per-unit non-swappable ramfs mounts.](diagrams/12-systemd-creds-tpm2-flow.svg)

Examine the exact cryptographic construction executed when an administrator seals a service credential via `systemd-creds encrypt --name=db-pass plaintext.secret /etc/credstore.encrypted/db-pass.cred` (`--with-key=auto`, which selects `host+tpm2` whenever persistent `/var` and `/dev/tpmrm0` exist [37, 372, 373]):

![Figure: Cryptographic key derivation and VFS delivery inside systemd-creds host+tpm2 mode: combining the 256-bit /var/lib/systemd/credential.secret host key with a TPM 2.0 PCR 7 + PCR 11 policy key via SHA-256 into AES-256-GCM, unsealed by PID 1 onto an isolated MS_NOSYMFOLLOW ramfs.](diagrams/12-extra-host-plus-tpm2-hybrid-seal.svg)

Why does `systemd-creds` insist on combining *two* independent key halves (`host+tpm2`) instead of relying on `TPM 2.0` alone [37, 372, 373]? Consider both halves of the physical and cloud threat model:
Factor 1 (`.host` key) is a 256-bit random secret generated on first use and stored mode `0400 root:root` at `/var/lib/systemd/credential.secret` inside the OS's persistent (typically `LUKS2`-encrypted) `/var` filesystem. Factor 2 (`tpm2` key) is a random secret sealed under the `TPM 2.0` Storage Root Key (`SRK`) bound to a `TPM2_PolicyPCR` digest over `PCR[7]` (UEFI Secure Boot authority state) plus optional `PCR[11]` / `systemd-pcrlock` Unified Kernel Image measurements (`--tpm2-pcrs=7+11` from [Chapter 2](02-uki-systemd-pcrlock.md) [28, 29, 372]). Inside `creds-util.c`, `systemd-creds` hashes both 256-bit secrets together via `SHA-256` to derive the symmetric `AES-256-GCM` Content Encryption Key, while binding the credential's logical name (`--name=db-pass`), optional monotonic expiration timestamp (`--not-after=`), and TPM2 policy metadata inside the `AES-256-GCM` Additional Authenticated Data (`AAD`) [372, 373]!

Look at what that hybrid `SHA-256(K_host || K_tpm2)` construction + GCM `AAD` achieves simultaneously [365, 372, 373]:
First, *offline disk/backup theft fails*: an attacker who downloads `/etc/credstore.encrypted/db-pass.cred` (or even `SetCredentialEncrypted=` pasted directly inside a world-readable git-tracked `.service` unit!) and steals `/var/lib/systemd/credential.secret` from a backup snapshot still lacks physical access to the host's `TPM 2.0` `SRK` under valid Secure Boot `PCR[7]` state. Second, *passive discrete-TPM bus sniffing fails*: on servers with discrete SPI or LPC `TPM 2.0` chips vulnerable to passive hardware interposers (`WithSecure` bus-sniffing attacks [365]), sniffing the TPM wire during boot reveals at most the TPM half (when unencrypted sessions occur) while `.host` remains invisible on NVMe storage (and modern `systemd` further wraps TPM parameter transport in salted HMAC/XOR sessions). Third, *credential-swapping attacks fail*: because `db-pass` is authenticated inside GCM `AAD`, renaming `/etc/credstore.encrypted/low-priv-webhook.cred` to `db-pass.cred` causes `PID 1`'s GCM tag verification to fail deterministically before the service ever starts [372, 373]! Note also that for pre-enrolled first-boot images (`--with-key=null`), operators should pass `systemd.credentials_boot_policy=strict` on the verified kernel command line once provisioned so `PID 1` rejects unencrypted `null`-key envelopes permanently [37].

At runtime, when `myapp.service` declares `LoadCredentialEncrypted=db-pass:/etc/credstore.encrypted/db-pass.cred` (or `ImportCredential=myapp.*` to auto-import matching credentials from `/etc/credstore.encrypted/`, `/run/credstore.encrypted/`, SMBIOS Type 11 `io.systemd.credential:` OEM strings, QEMU `fw_cfg`, or UKI `.cred` sections [28, 37]), `PID 1` performs all `TPM 2.0` unsealing and `AES-256-GCM` tag verification *outside* the service's address space. `PID 1` then mounts a dedicated `ramfs` filesystem at `/run/credentials/myapp.service/` inside the unit's mount namespace with strict VFS mount flags (`MS_RDONLY | MS_NODEV | MS_NOSUID | MS_NOEXEC | MS_NOSYMFOLLOW` [367, 373]). Every flag here carries weight: `ramfs` (`Documentation/filesystems/ramfs-rootfs-initramfs.rst` [368]), unlike `tmpfs`, intentionally implements *zero swap-out backing store* in the Linux VM subsystem, guaranteeing that not a single plaintext credential byte can ever be paged out to swap under extreme memory pressure; `MS_NOSYMFOLLOW` (Linux `5.10+` [367]) instructs VFS never to follow symbolic links inside the credential mount; and each decrypted credential file is written mode `0400` owned by the unit's transient `DynamicUser` (`$CREDENTIALS_DIRECTORY/db-pass`, or `%d/db-pass` in `ExecStart=`), remaining completely invisible to sibling services, `/proc/<pid>/environ` readers, and crash-dump environment harvesters, then unmounted and freed on unit deactivation [37, 372, 373]!

### Non-Exportable Hardware Keys: `tpm2-pkcs11` and OpenSSL 3 `tpm2-openssl` (`OSSL_PROVIDER`)

While `systemd-creds` protects symmetric passwords, API tokens, and static config blobs at rest and during injection, once a service reads a PEM private key out of `$CREDENTIALS_DIRECTORY/tls.key` into OpenSSL's heap, an attacker who achieves arbitrary memory read or post-exploit RCE inside that daemon can still copy the private key scalar and impersonate the server off-box [72]. For high-value asymmetric node identities (mTLS client certificates, `SPIRE` X.509/TPM node attestation in [Chapter 16](16-workload-identity-spiffe.md), SSH host keys, and local `IMA`/module signing keys), Linux eliminates private-key exportability entirely by executing RSA and ECDSA private-key operations inside `TPM 2.0` silicon via two modern userspace stacks [72, 369, 385, 386]:

First, `tpm2-pkcs11` (`libtpm2_pkcs11.so` [72]) exposes `TPM 2.0` hierarchies through the standard OASIS `PKCS#11` (`Cryptoki`) C ABI, consumed natively by `OpenSSH` (`HostKey` / `PKCS11Provider /usr/lib64/pkcs11/libtpm2_pkcs11.so`), `GnuTLS`, `NSS`, `strongSwan`, and OpenSSL 3 via Simo Sorce's `pkcs11-provider` (`pkcs11:` URIs [385]). Second, `tpm2-openssl` (`tpm2.so` [369]) implements OpenSSL 3's native `OSSL_PROVIDER`, `OSSL_STORE`, and `OSSL_DECODER` interfaces [386] (cleanly replacing OpenSSL 1.1's deprecated `ENGINE` API) so any unmodified OpenSSL 3.x application (`nginx`, `envoy`, `curl`, `systemd-networkd`) can generate and use TPM-resident keys directly via `-provider tpm2 -provider default` and `handle:0x81000001` or TSS2 PEM blobs (`-----BEGIN TSS2 PRIVATE KEY-----`)!

When `tpm2_ptool` or `openssl genpkey -provider tpm2` creates an ECDSA P-256 or RSA-2048 key inside the TPM, the chip generates the private key from its internal hardware RNG with object attributes `TPMA_OBJECT_FIXEDTPM | TPMA_OBJECT_FIXEDPARENT | TPMA_OBJECT_SENSITIVEDATAORIGIN` [72, 111, 369]: silicon microcode mathematically forbids `TPM2_Duplicate` export to any external parent. During a TLS 1.3 handshake (`CertificateVerify`) or SSH signature, OpenSSL hashes the transcript in host CPU speed and sends only the 32-byte digest over `/dev/tpmrm0` (the Linux kernel's built-in TPM Resource Manager, which transparently swaps transient key contexts into TPM RAM slots and isolates concurrent process sessions) to `TPM2_Sign` [72, 369]. Even total memory disclosure of `nginx` or `sshd` yields only a public key and a TPM-wrapped blob useless on any other motherboard!

### Desktop Session Secret Failure Modes: `org.freedesktop.secrets` vs. `org.freedesktop.portal.Secret`

Server credential discipline stands in sharp contrast to a widespread Linux workstation vulnerability: the Freedesktop Secret Service D-Bus API (`org.freedesktop.secrets`, implemented by `gnome-keyring-daemon` [387] and KDE `KWallet` `kwalletd6` [388] and accessed through `libsecret` [389]). When a developer logs into a graphical Wayland or X11 desktop session, `pam_gnome_keyring.so` or `pam_kwallet5.so` uses the login password to unlock `~/.local/share/keyrings/login.keyring` into memory for the entire session. Because `org.freedesktop.secrets` predates desktop application sandboxing, its D-Bus daemon authenticates callers *solely by checking that `SO_PEERCRED.uid == session_uid`*, offering zero per-application access control over items in the default collection [366, 389]!

Think about what that means on an engineer's Linux laptop: `Chromium`/`Chrome` stores its symmetric cookie/password encryption key in `login.keyring`, `gh` CLI and `git-credential-libsecret` store GitHub PATs there, and `NetworkManager` user connections or Slack/VS Code tokens sit right beside them. Any unconfined process running as `UID 1000` (a compromised `pypi`/`npm` `postinstall` script, a prompt-injected MCP tool in [Chapter 17](17-ai-agent-sandboxes.md), or a trojaned binary) simply connects to `$DBUS_SESSION_BUS_ADDRESS`, calls `org.freedesktop.Secret.Service.OpenSession("plain", "")` followed by `SearchItems({})` and `GetSecrets(...)`, and silently exfiltrates every unlocked secret in milliseconds with zero user prompt [366, 389]! Worse, `login.keyring`'s on-disk file format leaves item lookup attributes unkeyed-hashed, leaking metadata about which services have stored secrets even while locked [366].

Modern desktop sandboxing (`Flatpak` paired with `xdg-desktop-portal` [366, 374]) closes this ambient D-Bus scraping hole cleanly. A hardened Flatpak manifest omits `--socket=session-bus` and `--talk-name=org.freedesktop.secrets` completely. When `libsecret` (`0.19+` [387]) detects `/.flatpak-info` inside a sandbox, it switches automatically from the shared network-wide `org.freedesktop.secrets` D-Bus service to `org.freedesktop.portal.Secret.RetrieveSecret(fd, options)` [366, 374]: `xdg-desktop-portal` inspects the caller's kernel-verified Flatpak `app_id` (`org.mozilla.firefox`), retrieves a *unique per-application 64-byte master encryption key* dedicated strictly to `org.mozilla.firefox` from the host keyring backend, and writes those 64 bytes into the one-way pipe descriptor `fd`. Inside the sandbox, `libsecret` uses that per-app master key to encrypt a private keyring file at `~/.var/app/org.mozilla.firefox/data/keyrings/default.keyring`, completely isolating every sandboxed app's secrets from sibling apps on the same desktop [366, 374]! For high-consequence workstation SSH and cloud admin keys, hardware-resident `FIDO2` tokens (`verify-required` in [Chapter 13](13-pam-ssh-fido2.md)) or `tpm2-pkcs11` with PIN policies remain essential so no silent background process can sign without physical presence.

## Distro, Immutable-OS, & Cloud Trade-Offs

Deploying `systemd-creds` (`LoadCredentialEncrypted=`) and `KeyringMode=private` requires zero kernel patches on any current enterprise or cloud Linux distribution (`RHEL 9/10`, `Fedora`, `Ubuntu 22.04/24.04 LTS`, `Debian 12/13`, `SUSE`, `Arch`) [37, 68]. Where upstream daemons (`systemd-networkd`, `systemd-cryptsetup`, `Caddy`, modern Go/Rust daemons) read `$CREDENTIALS_DIRECTORY` natively, configuration is a single declarative line; for legacy C daemons (`PostgreSQL`, `OpenVPN`, `Redis`) that insist on reading a path or CLI flag, operators either pass `%d/<cred>` on `ExecStart=` or run a two-line `ExecStartPre=` / shell `systemd-creds cat` adapter inside the unit's isolated mount namespace [37, 372].

On immutable and cloud-native Linux distributions (`Fedora CoreOS`, `Flatcar`, `Bottlerocket`, `UKI`-booted bare metal), `systemd` system credentials bridge external provisioning into read-only `/usr` images without mutating `/etc`: hypervisors inject bootstrap secrets over `SMBIOS` Type 11 OEM strings (`io.systemd.credential.binary:...`) or QEMU `fw_cfg`, while `systemd-stub(7)` [28] picks up `.cred` sidecar files from the EFI System Partition (`*.efi.extra.d/*.cred`), measures/passes them across the initrd transition, and unseals them only if `PCR[7]` + `PCR[11]` match signed `systemd-pcrlock` policies [28, 29, 37]. Finally, size hardware `TPM 2.0` workloads realistically: discrete SPI/I2C `TPM 2.0` chips sustain roughly `15` to `40` `TPM2_Sign` ECDSA P-256 operations per second (`tpm2-pkcs11` / `tpm2-openssl` [72, 369]), making silicon keys ideal for node mTLS client authentication, `SPIRE` node attestation ([Chapter 16](16-workload-identity-spiffe.md)), and `sshd` host keys, whereas `10,000` TLS handshakes/sec public ingress proxies pair TPM-attested node identity with short-lived in-memory workload certificates (`memfd_secret` + `SPIFFE` X.509-SVIDs [40, 371]).

## Seam Failures, CVEs, & Structural Bounds

Local secret custody breaks whenever kernel keyring refcounts or watch filters corrupt Ring 0 memory, applications grant `KEY_USR_READ` or `@u` visibility to session secrets, daemons stage credentials on swappable `tmpfs`, or desktop apps share an unlocked `org.freedesktop.secrets` D-Bus bus.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| Kernel Keyring Refcount Overflow (`CVE-2016-0728`) | 2016 | `security/keys/process_keys.c` | `join_session_keyring()` decrements `usage` on same-session fast path | $2^{32}$ calls overflow 32-bit `atomic_t usage` to zero, freeing active `struct key` for Ring 0 UAF LPE | Convert kernel object refcounts to saturating `refcount_t` pinned at `UINT_MAX` [229, 381] |
| Uninstantiated Key Race & Null Deref (`CVE-2017-15299` / `15951`) | 2017 | `security/keys/` `encrypted` & `keyctl` | Concurrent `add_key()` / `request_key()` updates serialize cleanly on negative/uninstantiated keys | Craft concurrent `add_key` update on uninstantiated key to trigger Ring 0 null-pointer dereference or state corruption | Enforce atomic state-transition barriers in `key_update()` and restrict `keyctl` in `seccomp` [370, 382] |
| Keyring `watch_queue` Heap OOB Write (`CVE-2022-0995`) | 2022 | `kernel/watch_queue.c` + `keyctl_watch_key` | `IOC_WATCH_QUEUE_SET_FILTER` bounds-checks user type-filter bitmask indices | Malformed watch filter writes out-of-bounds into adjacent `kmalloc` slab object for in-the-wild root LPE (CISA KEV) | Validate filter `type` bounds strictly and block `keyctl` inside untrusted container `seccomp` profiles [384, 390] |
| Over-Permissive `@u` Keyring / `0x3f3f0000` Mask | Recurring | Application `add_key()` bitmask misuse | Kernel keyring isolates processes sharing the same numeric `UID` | Linking secrets into `@u` or granting `KEY_USR_READ` (`0x3f3f0000`) lets any sibling `UID 1000` process dump payloads via `keyctl print` | Set `KeyringMode=private`, link to `@s`, grant `READ` only to `Possessor` (`0x3f010000`), or use `logon`/`trusted` keys [68, 71, 375] |
| Discrete `TPM 2.0` Passive SPI/LPC Bus Sniffing | 2021-2024 | Unauthenticated TPM-only volume/cred unseal | Discrete motherboard TPM bus is inaccessible to physical attackers | Logic analyzer on SPI/LPC pins captures unencrypted `TPM2_Unseal` response bytes during unattended boot | Use `systemd-creds` hybrid `host+tpm2` (`SHA-256` KDF with `/var/lib/systemd/credential.secret`) + encrypted TPM sessions [365, 372, 373] |
| `Environment=` & `tmpfs` Swap Secret Exposure | Architectural | `systemd` `Environment=` & `/dev/shm` | RAM-backed `tmpfs` never writes secret pages to persistent disk | `/proc/<pid>/environ` exposes env vars to child/debug readers, and `tmpfs` pages swap out to unencrypted swap under load | Inject secrets via `LoadCredentialEncrypted=` on unswappable `ramfs` (`MS_NOSYMFOLLOW`) or `memfd_secret(2)` [37, 367, 368, 371] |
| Legacy OpenSSL `ENGINE` Key Extraction | Architectural | Software PEM keys in daemon DRAM | `0400` disk permissions prevent remote TLS/SSH private-key cloning | Post-RCE heap dump or Heartbleed-style memory read copies raw RSA/ECDSA private scalar out of process RAM | Generate non-exportable keys (`FIXEDTPM`) via `tpm2-pkcs11` or OpenSSL 3 `tpm2-openssl` `OSSL_PROVIDER` [72, 369, 386] |
| Desktop `org.freedesktop.secrets` D-Bus Scraping | 2019-2025 | `gnome-keyring` / `KWallet` session bus | PAM-unlocked `login.keyring` is safe from local user processes | Malicious `npm`/`pip` hook queries `org.freedesktop.secrets` over session D-Bus to dump browser/GitHub secrets silently | Sandbox desktop apps with `Flatpak` (`org.freedesktop.portal.Secret` per-app keys) and move SSH keys to `FIDO2` [366, 374, 389] |

Two structural bounds define the outer edge of single-host secret custody. First, even `ramfs` and `memfd_secret` reside in physical DRAM: defending decrypted runtime symmetric secrets against a malicious cloud hypervisor or cold-boot physical RAM probing requires hardware memory encryption (`AMD SEV-SNP` and `Intel TDX` in [Chapter 18](18-confidential-vms-svsm.md)). Second, securing how local daemons custody secrets on one machine leaves open how human engineers and enterprise directories authenticate *into* thousands of Linux servers without static `~/.ssh/authorized_keys` sprawl or remote `sshd` heap exploits: the exact domain of `PAM`, `SSSD`, OpenSSH Certificates, `FIDO2`, and `regreSSHion` in [Chapter 13](13-pam-ssh-fido2.md).

## Inspecting on a Live Linux Host

Inspect your active thread, process, and session kernel keyrings (`@s`, `@u`) along with their 32-bit `Possessor|User|Group|Other` hex permission masks and per-UID kernel quotas:

```bash
keyctl show 2>/dev/null || head -n 10 /proc/keys 2>/dev/null || true
cat /proc/key-users 2>/dev/null | head -n 8
```

Verify whether `systemd-creds` detects usable `TPM 2.0` + host-key sealing support on the host and run an isolated RAM round-trip envelope test:

```bash
systemd-analyze has-tpm2 2>/dev/null || systemd-creds has-tpm2 2>/dev/null || true
printf "demo-secret" | systemd-creds encrypt --with-key=null --name=demo - - 2>/dev/null | systemd-creds decrypt --name=demo - - 2>/dev/null; echo
```

Confirm that active service credential directories under `/run/credentials/` are mounted on non-swappable `ramfs` with `nosymfollow`, `noexec`, and `nosuid` enforced:

```bash
findmnt -t ramfs 2>/dev/null | head -n 12 || mount | grep "/run/credentials" | head -n 10
```

Check registered OpenSSL 3 cryptographic providers (`default`, `tpm2`, `pkcs11`) and inspect whether `org.freedesktop.secrets` or `org.freedesktop.portal.Secret` is active on the session bus:

```bash
openssl list -providers 2>/dev/null | head -n 14
busctl --user list 2>/dev/null | grep -E "freedesktop\.(secrets|portal\.Secret)" || true
```
