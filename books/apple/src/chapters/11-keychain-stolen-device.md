# Keychain Custody, Legacy macOS Gaps, and Stolen Device Protection

## Overview

* **Link in the Chain:** Structured credential vault and anti-theft policy layer in Part III; builds atop `SEP` keybags ([Chapter 3](03-secure-enclave.md)), `DER` entitlements ([Chapter 6](06-amfi-txm-notarization.md)), and `APFS` lock classes ([Chapter 10](10-apfs-data-protection.md)) to guard application tokens, enclave-resident signing keys, and physical device ownership.
* **Core Security Invariant:** Items stored in the Data Protection Keychain (`secd`) are wrapped individually under `SEP`-bound `AKS` class keys and readable only by processes whose `TXM`-verified `DER` entitlements match the item's `keychain-access-groups`, while `Stolen Device Protection` (`iOS 17.3+`) strips passcode fallback from sensitive credential and account-custody mutations outside familiar locations.
* **Platform Matrix:** `iOS`, `iPadOS`, `watchOS`, and `visionOS` run the `SEP`-backed Data Protection Keychain (`secd`) exclusively; `macOS` operates a split daemon architecture pairing `secd` alongside the legacy `CSSM` file-based `login.keychain-db` (`securityd` / `SecurityServer` hardened with machine binding in `macOS Tahoe 26.4+`), while `Stolen Device Protection` targets `iOS` and `Activation Lock` spans `iOS`, `iPadOS`, `macOS`, `watchOS`, and `visionOS`.
* **Trusted Computing Base (TCB):** `secd` (`SecItemServer`) and `SEP` `AppleKeyStore` (`SKS`), `TXM`/`AMFI` `audit_token_t` entitlement verification, legacy `macOS` `securityd` (`SecurityServer`) and `WindowServer` prompt isolation, `CoreRoutine` on-device `Significant Locations` state, `LocalAuthentication` (`coreauthd`), and Apple's `Find My` Activation Lock servers.
* **Failure Horizon & Handoff:** `macOS` apps omitting `kSecUseDataProtectionKeychain` expose secrets to legacy `SecACL` prompting, unauthenticated `encrypt` overwrites (`TALOS-2026-2444`), or pre-`26.4` offline `login.keychain-db` cracking by *Atomic macOS Stealer* (`AMOS`), while live `iOS` kernel exploit chains (*DarkSword*) harvest unlocked `AFU` tokens in memory; hands off remote cryptographic proof of `SEP` keys to [Chapter 12](12-sep-app-device-attestation.md).

## Threat Model & Design Tension

`APFS` per-file Data Protection ([Chapter 10](10-apfs-data-protection.md)) encrypts storage extents on flash, yet short, high-leverage secrets (OAuth refresh tokens, `802.1X` enterprise `Wi-Fi` credentials, `SSH` keys, `WebAuthn` `Passkeys`, and biometric-gated `P-256` signing keys) require three security properties that filesystem permissions cannot express [321, 322]. First, modern application suites require fine-grained secret sharing across distinct sandboxed Mach-O binaries (for example, a primary banking app, its `NotificationServiceExtension`, and its `WidgetExtension`) compiled under one verified developer `TeamID`, while strictly excluding every other application running under the exact same UNIX `UID` (such as `UID 501` on `macOS`) [321, 323]. Second, credential queries need metadata indexing in `After First Unlock` (`AFU`) so background daemons can check whether an account record exists without unwrapping high-sensitivity secret payloads until an explicit user gesture occurs [324]. Third, high-assurance keys (`Apple Pay`, corporate VPN identities, passkeys) must support *non-exportable enclave execution*, allowing user-space code to request an `ECDSA` signature or `ECDH` shared secret from `SEP` only after a live biometric scan without raw private-key bytes ever entering application or daemon RAM [12, 325, 326].

Between 2017 and 2026, four distinct adversarial vectors stress-tested Apple's credential and anti-theft boundaries across desktop and mobile hardware [48, 327, 328, 329, 330]. On `macOS`, preserving binary compatibility for unprovisioned POSIX command-line tools, Homebrew utilities, and cross-platform browsers forced Apple to keep the year-2000 Common Data Security Architecture (`CDSA`/`CSSM`) *File-Based Keychain* (`~/Library/Keychains/login.keychain-db`) running beside the modern `SEP`-backed Data Protection Keychain [331, 332, 333, 334]. Because `login.keychain-db` unlocks automatically at GUI login for every process executing as `UID 501`, local attackers repeatedly targeted `SecurityServer` UI prompts and IPC session tracking (`CVE-2017-7150` and *KeySteal* `CVE-2019-8526`) [328, 329], while commodity infostealers (*Atomic macOS Stealer* `AMOS`, *Poseidon*, *Odyssey*, and *ClickLock*) industrialized fake `osascript` password harvesting and `Chrome Safe Storage` extraction [330, 335, 336].

Simultaneously, on `iPhone`, organized physical theft rings exploited a subtle human-factors flaw documented in *The Wall Street Journal* by Joanna Stern and Nicole Nguyen in 2023 [327, 337]. Because `iOS` historically treated the 6-digit device unlock passcode as an omnipotent fallback whenever `Face ID` or `Touch ID` failed, criminals who shoulder-surfed a victim entering their PIN in a crowded bar and then snatched the handset could reset the victim's Apple Account password, enroll a new 28-character Recovery Key, disable `Find My` Activation Lock, and drain saved Keychain credentials in under three minutes [327, 337]. Defending against both silent local malware on `macOS` and coerced or observed passcodes on `iOS` required decoupling software passwords from hardware key custody and introducing spatiotemporal friction into account recovery [48, 330, 338].

## Silicon & System Mechanics

### The Data Protection Keychain (secd), SQLite V7 Wrapping, and DER Access Groups

Across `iOS`, `iPadOS`, `watchOS`, and `visionOS` (and on `macOS` whenever a caller sets `kSecUseDataProtectionKeychain: kCFBooleanTrue` or `kSecAttrSynchronizable: kCFBooleanTrue`), `SecItemAdd`, `SecItemCopyMatching`, `SecItemUpdate`, and `SecItemDelete` serialize requests over `XPC` (`SecuritydXPC`) to the per-user `secd` daemon implemented in `apple-oss-distributions/Security` under `keychain/securityd/SecItemServer.c` and `SecItemDb.c` [321, 322, 332]. `secd` persists items inside a SQLite database (`keychain-2.db`, located under `/private/var/Keychains/` on `iOS` and `~/Library/Keychains/<Hardware-UUID>/` on `macOS`) partitioned across four core item tables defined in `SecItemSchema.c`: `genp` (generic passwords), `inet` (internet passwords), `cert` (X.509 certificates), and `keys` (cryptographic keys) [322, 339]. Each table indexes authenticated primary-key columns (`agrp` access group, `pdmn` protection domain, `sync` synchronizable flag, `vwht` `CKKS` view hint, `tkid` token identifier, `musr` multi-user UUID, and `tomb` deletion tombstone) alongside an opaque encrypted `data` blob [339].

Inside `SecDbKeychainItemV7.m`, every Keychain row undergoes a two-tier `AES-256-GCM` (`SFAuthenticatedEncryptionOperation`) envelope construction that separates searchable metadata from secret material [321, 324]. Rather than decrypting full rows during a `SecItemCopyMatching` query, `SecDbKeychainItemV7` splits attributes into `SecDbKeychainMetadata` (holding `acct`, `svce`, `labl`, creation/modification timestamps `cdat`/`mdat`, and protocol metadata) and `SecDbKeychainSecretData` (holding the sensitive `v_Data` payload, typically bounded around `REASONABLE_SECRET_DATA_SIZE` of 32 KiB) [324, 339]. `SecDbKeychainMetadata` is encrypted under a random per-row 256-bit `SFAESKey`, which is wrapped in turn under a per-protection-class *metadata class key* managed by `SecDbKeychainMetadataKeyStore` and cached in `secd` memory while the device is in `AFU` [324]. By contrast, `SecDbKeychainSecretData` encrypts `v_Data` under an independent random 256-bit row key wrapped directly inside the Secure Enclave (`SEP` `AppleKeyStore` / `SKS`) as a `SecDbKeychainSerializedAKSWrappedKey` (`Regular` or `RefKey` blob), with an authenticated `TamperCheck` UUID string cryptographically binding `_encryptedMetadata` and `_encryptedSecretData` together so an attacker with raw SQLite write access cannot splice secret blobs across metadata rows [321, 324].

Every item's `SEP` unwrapping policy is governed first by its `kSecAttrAccessible` protection domain (`pdmn`), which maps to `SEP` keybag classes (`Ak` through `Ek` in `AppleKeyStore`) and controls both lock-state availability and backup portability during `SecKeychainMigrate` [12, 321, 322, 325]:

| `kSecAttrAccessible` Constant | `SEP` `AKS` Class | Lock-State Availability | Backup & Device-Migration Semantics |
|---|---|---|---|
| `WhenUnlocked` | Class `Ak` | Only while device is actively unlocked | Included in encrypted backups; migrates to new user devices |
| `AfterFirstUnlock` | Class `Ck` | Available from first post-boot passcode entry until reboot (`AFU`) | Included in encrypted backups; migrates to new user devices |
| `WhenPasscodeSetThisDeviceOnly` | Class `Ak` + `Passcode` (`Ek`) | Unlocked only; creation fails if no passcode is set | Never backed up; permanently destroyed inside `SEP` if user turns off passcode |
| `WhenUnlockedThisDeviceOnly` | Class `Ak` (`Ek` non-migratable) | Only while device is actively unlocked | Encrypted to device-specific backup keybag; discarded on restore to different silicon |
| `AfterFirstUnlockThisDeviceOnly` | Class `Ck` (`Ek` non-migratable) | Available throughout `AFU` until reboot or 72h timer | Non-migratable; bound strictly to originating `SEP` `UID` |
| `UntilReboot` | Ephemeral in-memory class | Available until next `XNU`/`SEP` reset | Transient runtime secret; excluded from persistent backups |

Beyond static lock classes, callers can attach a fine-grained `SecAccessControlRef` constructed via `SecAccessControlCreateWithFlags` in `OSX/sec/Security/SecAccessControl.m` [325, 326]. `SecAccessControl.m` compiles high-level flags into a `DER`-encoded `kAKSKeyAcl` dictionary evaluated inside `SEP` hardware before `SKS` permits key unwrapping (`kAKSKeyOpDecrypt`) or private-key operations (`kAKSKeyOpSign`, `kAKSKeyOpComputeKey`, `kAKSKeyOpKEMDecapsulate`) [325]. Specifying `.userPresence` maps to `kACMPolicyDeviceOwnerAuthentication` (permitting either live biometry or device passcode), `.devicePasscode` requires explicit passcode verification, `.companion` gates unwrapping on paired `Apple Watch` proximity, and `.biometryAny` versus `.biometryCurrentSet` binds key release to `Face ID`, `Touch ID`, or `Optic ID` match tokens delivered over the `SEP` biometric channel [138, 325, 326]:

$$\text{Permit}_{\text{SEP}}(\text{op}, \text{item}) \iff \text{ClassOpen}(\texttt{pdmn}) \;\land\; \text{BioMatch}_{\text{live}} \;\land\; \bigl(H(\mathcal{B}_{\text{enrolled}}) = \texttt{acl.bioSetDigest}\bigr)$$

Under `kSecAccessControlBiometryCurrentSet`, `SEP` commits to the cryptographic digest $H(\mathcal{B}_{\text{enrolled}})$ of enrolled biometric templates (or mathematical facial representations) at item creation [138, 325, 326]. If a local attacker who knows the device passcode enrolls an additional fingerprint or alternate appearance in Settings, $H(\mathcal{B}_{\text{enrolled}})$ mutates and `SEP` permanently refuses to unwrap or sign with that key [138, 326]. Combining `.biometryCurrentSet` with `.privateKeyUsage` and `kSecAttrTokenID: kSecAttrTokenIDSecureEnclave` elevates custody from software secret storage to hardware enclave execution: `SEP` generates a `P-256` elliptic-curve scalar internally, seals it under `UID`-tangled `SKS` keys, stores only the opaque reference blob (`tkid = com.apple.setoken`) in `keychain-2.db`, and executes `ECDSA`, `ECIES`, or `ML-KEM`/hybrid decapsulation inside `SEP` SRAM [12, 321, 325, 339].

Caller authorization in `secd` ignores POSIX file ownership altogether, inspecting the XPC client's kernel-authenticated `audit_token_t` (`ipc/server_entitlement_helpers.h`, [Chapter 7](07-ipc-seatbelt-blastdoor.md)) to extract `TXM`-verified `DER` code-signing entitlements ([Chapter 6](06-amfi-txm-notarization.md)) [321, 322, 323]. `secd` builds the caller's permitted `agrp` list from the union of `keychain-access-groups`, `application-identifier` (`<TeamID>.<BundleID>`), and `com.apple.token` (plus `Associated Domains` `webcredentials` groups validated by `swcd` in `SecItemServer+SWC.m`) [322, 323]. Because Apple's Developer Provisioning CA signs `<TeamID>.*` prefixes into provisioning profiles verified by `AMFI` and `TXM` at launch, an unentitled binary or another vendor's signed app running under the same `UID 501` on `macOS` cannot forge a matching `agrp` to read `secd` rows [321, 323].

### Legacy macOS File-Based Keychains (securityd / CSSM) and Browser Safe Storage

Why, then, do `macOS` credential stealers remain a staple of cybercrime? Whenever a `macOS` binary calls `SecItemAdd` or `SecItemCopyMatching` *without* setting `kSecUseDataProtectionKeychain` (or calls deprecated `SecKeychain*` APIs), `Security.framework` routes the call not to `secd`, but to the legacy `CSSM` (`Common Security Services Manager`, Open Group `CDSA` Standard `C914`) implementation in `OSX/libsecurity_keychain/` and the root daemon `securityd` (advertising Mach bootstrap service `com.apple.SecurityServer` over MIG/UCSP protocol `SSPROTOVERSION 20000`) [329, 331, 332, 333, 334].

![Figure: Split macOS Keychain architecture contrasting the SEP-sealed, entitlement-isolated Data Protection Keychain (secd) against the legacy password-derived login.keychain-db targeted by Atomic Stealer (AMOS).](diagrams/11-dp-keychain-vs-file-keychain.svg)

`SecurityServer` manages `~/Library/Keychains/login.keychain-db` and `/Library/Keychains/System.keychain` so unprovisioned command-line binaries (`curl`, `ssh-agent`, `git-credential-osxkeychain`, Python scripts, and standalone Electron or Chromium builds lacking Apple App Store provisioning profiles) can store secrets on `macOS` [331, 332, 333]. Historically, `login.keychain-db` wrapped item records under a software master key derived via `PBKDF2` (`3DES-CBC` / `AES`) from the user's `macOS` login password and unlocked the entire vault automatically at `LoginWindow` sign-in for the duration of the GUI session (`no-timeout` by default) [330, 331, 333]. Inter-process isolation inside `login.keychain-db` relies on legacy `SecAccess` objects containing per-operation `SecACL` entries (`encrypt`, `decrypt`, `derive`, `export_clear`, `integrity`, `partition_id`, and `change_acl`) bound to code-signing requirements (`csreq`) or binary paths [333, 336].

Google Chrome and Chromium-derived browsers (`Brave`, `Edge`, `Arc`, `Vivaldi`) exemplify the architectural hazard of this legacy default [330, 335, 336]. Whereas `Safari` and `Passwords.app` store website credentials and session secrets inside `secd`'s Data Protection Keychain gated by private Apple entitlements, Chromium's `components/os_crypt/sync/os_crypt_mac.mm` and `crypto/apple/keychain_v2.mm` (`KeychainV2::AddGenericPassword`) omit `kSecUseDataProtectionKeychain` and write 16 random base64-encoded bytes into `login.keychain-db` under `kSecAttrService = "Chrome Safe Storage"` and `kSecAttrAccount = "Chrome"` [332, 335, 336]. Chromium feeds that 24-character string into `PBKDF2-HMAC-SHA1` with hardcoded salt `"saltysalt"` and `1003` iterations to derive a single `128-bit AES-CBC` key encrypting every cookie, OAuth token, saved password, and payment card in `~/Library/Application Support/Google/Chrome/Default/Cookies` and `Login Data` [335, 336].

Prior to `macOS Tahoe 26.4` (`September 2026`), this software-only key derivation enabled a devastating two-step offline attack used by *Atomic macOS Stealer* (`AMOS`), *Poseidon*, and *MacStealer* [330]: the malware popped a fake `osascript` password dialog (`display dialog "System Settings wants to make changes..." with hidden answer`) to phish the user's `macOS` login password, copied `~/Library/Keychains/login.keychain-db` and Chrome's `Cookies` SQLite database to an attacker C2 server, and decrypted `Chrome Safe Storage` completely offline on Linux without ever triggering a `SecurityServer` `SecACL` dialog on the victim's Mac [330]! In `macOS Tahoe 26.4`, Apple added hardware machine-binding to `login.keychain-db` so exfiltrated keychain files can no longer be decrypted off-host with just the login password; within weeks (`October 2026`), threat researchers caught updated *AMOS*/*Odyssey* samples checking `sw_vers -productVersion` and pivoting on `>= 26.4` to invoke `security find-generic-password -ga "Chrome"` locally, socially engineering the user into clicking *Allow* on the live `SecurityServer` ACL dialog instead [330].

### Activation Lock and Stolen Device Protection (iOS 17.3+)

At the physical anti-theft plane, Apple pairs cloud activation gating with on-device biometric/location policy [48, 340]. *Activation Lock* (`Find My`) binds a device's hardware `ECID` and `SEP` Silicon Identity Key (`SIK`, [Chapter 12](12-sep-app-device-attestation.md)) to a cryptographic token associated with the owner's Apple Account on Apple's activation servers (mirrored locally as `fmm-mobileme-token-FMM` in NVRAM on Macs) [340, 341]. Even if a thief enters `DFU` mode ([Chapter 1](01-secure-boot.md)) and flashes a clean `Image4`-signed OS build, `Setup Assistant` must fetch a signed activation ticket before booting into an operational user environment; without the owner's `GrandSlam` credentials (or an enterprise `MDM` `ActivationLockBypassCode` escrowed via `device.activationlock.bypasscode` on supervised corporate fleets, [Chapter 14](14-ddm-platform-sso.md)), the hardware remains an unactivatable brick [340, 341].

Activation Lock alone, however, collapses if the thief steals an unlocked phone *after* observing the victim's 6-digit passcode [48, 327, 337]. Because `AuthKit` trusted the local device passcode to prove account ownership during trusted-device password resets, WSJ's 2023 investigation documented thieves shoulder-surfing passcodes in bars, snatching the iPhone, resetting the Apple Account password in Settings within 30 seconds, generating a new 28-character Apple Account Recovery Key (which permanently locks the legitimate owner out of Apple Support recovery!), turning off `Find My` Activation Lock using the newly reset Apple Account password, and using passcode fallback inside Keychain to empty bank and Venmo accounts [327, 337].

![Figure: Stolen Device Protection three-stage gate defeating shoulder-surfed passcodes through mandatory live biometrics, CoreRoutine familiar-location evaluation, and a 1-hour security delay.](diagrams/11-stolen-device-protection-gate.svg)

Shipped in `iOS 17.3` (`January 2024`) and expanded across `iOS 18` through `iOS 26`, *Stolen Device Protection (`SDP`)* dismantles passcode omnipotence through a two-tier state machine coordinated across `SEP`, `LocalAuthentication` (`coreauthd`), `CoreRoutine` (`routined`), `secd`, and `AuthKit` (`akd`) [48, 338, 342, 343]. `SDP` requires an Apple Account with two-factor authentication, an active device passcode, enrolled `Face ID` or `Touch ID`, `Find My` enabled (which cannot be turned off while `SDP` is active), and `CoreRoutine` `Significant Locations` (`Settings -> Privacy & Security -> Location Services -> System Services`), which learns encrypted on-device dwell clusters (home, office) without uploading raw location traces to Apple [48, 342].

![Figure: Dual-rail timeline contrasting the 2023 WSJ 180-second shoulder-surfed passcode takeover kill chain against iOS 17.3+ Stolen Device Protection biometric-only and 60-minute delay gates.](diagrams/11-extra-shoulder-surf-killchain-vs-sdp.svg)

Whenever `CoreRoutine` evaluates the iPhone as *outside* a familiar location (or at *all* locations if the user sets `Require Security Delay` to *Always*), `SDP` enforces two distinct hardware-backed tiers [48, 338, 343]. First, *Tier 1 Biometric-Only Operations* completely remove the *"Enter Passcode"* fallback button after failed `Face ID` or `Touch ID` scans when viewing saved passwords or `Passkeys` in `Passwords.app` (`Keychain`), autofilling saved Safari payment cards, disabling Lost Mode, opening a biometric-locked or hidden app (`iOS 18+`), invoking `Erase All Content and Settings`, applying for Apple Card or viewing virtual card numbers, initiating Apple Cash/Savings transfers, using Quick Start to provision a new device, or transferring an `eSIM` [48, 343].

Second, *Tier 2 Security-Delay Operations* interpose a mandatory 60-minute temporal quarantine on irreversible custody mutations: changing the Apple Account password, signing out of the Apple Account, adding or removing a trusted device, `Recovery Key`, or `Recovery Contact`, adding or deleting `Face ID`/`Touch ID` enrollments, changing the device passcode, running `Reset All Settings`, enrolling in `MDM`, or turning off `Stolen Device Protection` itself [48]. To execute any Tier 2 change away from home, the caller must pass live `Face ID` or `Touch ID` (`t = 0`), wait a full 60 minutes enforced by `SEP`/`coreauthd` timers (ending early only if `CoreRoutine` confirms physical arrival back at an established familiar location), and pass a *second* live `Face ID` or `Touch ID` scan (`t >= 60 min`) [48]. Simultaneously, Apple blocks mutating those critical account settings via the web at `account.apple.com` and suppresses device location visibility on `icloud.com/find` briefly if a password was just changed, ensuring a robbery victim has a full hour to borrow any browser, sign into `icloud.com/find` (which accepts password alone without 2FA specifically for Lost Mode!), and lock down the stolen handset [48].

## Platform Forks Across Apple OSes

`iOS`, `iPadOS`, `watchOS`, and `visionOS` enforce a single-daemon credential architecture: `CSSM` and `SecurityServer` (`login.keychain-db`) do not exist on mobile or spatial Darwin builds, so every `SecItem*` call automatically enters `secd` and binds to `SEP` `UID` protection and `TXM`-verified `agrp` entitlements [321, 322, 332]. On `Shared iPad` (`KEYCHAIN_SUPPORTS_EDU_MODE_MULTIUSER` in `SecItemServer.c`), `secd` partitions rows by the active user's `musr` UUID column and runs `InternalTranscryptToSystemKeychainKeybag` to keep system-wide `802.1X` Wi-Fi credentials isolated from per-student keybags [322, 339].

`macOS` remains the lone Apple platform straddling two credential eras [330, 331, 332]. First-party frameworks (`Safari` AutoFill, `Passkeys`, `CKKS` `iCloud Keychain`, and `Passwords.app`) store secrets exclusively in `secd`'s Data Protection Keychain, and `macOS Tahoe 26.4` closed offline `login.keychain-db` file exfiltration via machine-bound wrapping [330, 332]. Nevertheless, third-party `macOS` developers shipping outside the Mac App Store must explicitly embed a Developer ID Provisioning Profile carrying `com.apple.application-identifier` and pass `kSecUseDataProtectionKeychain: true` to escape legacy `SecACL` risks [323, 332]. Meanwhile, `Stolen Device Protection` remains `iPhone`-specific because pocket snatching after public PIN observation overwhelmingly targets handheld phones, whereas `Activation Lock` enforces cloud `ECID`/`SIK` ownership across `iPhone`, `iPad`, `Apple Watch`, `Apple Vision Pro`, and all `Apple Silicon` (plus Intel `T2`) Macs [48, 340].

### Historical macOS Daemon Bypasses: CVE-2017-7150 and KeySteal (CVE-2019-8526)

Two classic `macOS` vulnerabilities explain why Apple steadily deprecated `CSSM` and UI-prompt-based `SecACL` mediation in favor of kernel-verified `DER` entitlements [328, 329, 332]. In `CVE-2017-7150`, Patrick Wardle observed that while `WindowServer` (`post_filtered_event_tap_data` / `CGXSenderCanSynthesizeEvents`) blocked unentitled processes lacking `hid-control` from sending synthetic `CoreGraphics` mouse clicks directly onto a `SecurityServer` Keychain *Allow* alert, the Accessibility preference pane enabling *Mouse Keys* was unprotected [328, 344]. Unprivileged malware could open `com.apple.preference.universalaccess` via AppleScript, click *Mouse Keys*, move the cursor over the Keychain prompt, and synthesize keyboard keycode `87` (numeric keypad `5`); because the operating system itself translated keycode `87` into a trusted left mouse click, `SecurityServer` accepted the click and dumped every plaintext password in `login.keychain-db` [328].

Two years later, Linus Henze's *KeySteal* (`CVE-2019-8526`) bypassed UI prompts altogether by attacking Mach port identity inside `securityd` (`SecurityServer`) [329, 345]. During client registration (`ucsp_client_setup`), `securityd` authenticated the calling process using a passed `mach_port_t` task port rather than an immutable per-message `audit_token_t` ([Chapter 7](07-ipc-seatbelt-blastdoor.md)) [41, 329]. By invoking `ucsp_client_registerHosting` in a forked helper to trigger a port reference use-after-free inside `securityd`, reclaiming that exact Mach port name with a controlled `fakeTaskPort`, and calling `posix_spawn` with `POSIX_SPAWN_START_SUSPENDED | POSIX_SPAWN_SETEXEC` onto `/System/Library/InternetAccounts/internetAccountsMigrator`, *KeySteal* tricked `securityd` into attributing the attacker's UCSP session to Apple's privileged migrator binary, reading unlocked Keychain secrets silently [329].

### Modern Infostealers, Chrome Safe Storage ACLs, and Coercion Bounds

Even with `CVE-2017-7150` and `CVE-2019-8526` patched and `macOS Tahoe 26.4` machine-binding `login.keychain-db` [330, 344, 345], Cisco Talos's June 2026 disclosure `TALOS-2026-2444` exposed a structural flaw in legacy `CSSM` `SecAccess` defaults [336]. When Chrome calls `SecItemAdd` without `kSecUseDataProtectionKeychain`, `macOS` generates five default `SecACL` entries: `decrypt` is restricted to `identifier "com.google.Chrome"` and `certificate leaf[subject.OU] = EQHXZ8M8AV`, `change_acl` allows zero apps (`applications (0)`), yet `encrypt` sets `applications: <null>` (unrestricted!) [336]. Any unprivileged `UID 501` process running while `login.keychain-db` is unlocked can silently call `SecItemUpdate` to overwrite `Chrome Safe Storage` with an attacker-chosen 24-byte secret; on next launch, Chrome derives its `AES-128-CBC` key from the attacker's string and encrypts every newly issued session cookie and saved password straight to the attacker's key with zero prompts [335, 336].

> **Key idea.**
> Why does migrating a `macOS` application from `login.keychain-db` (`SecurityServer`) to `keychain-2.db` (`secd` via `kSecUseDataProtectionKeychain: true`) defeat pre-`26.4` offline vault cracking, `TALOS-2026-2444` same-UID key overwrites, and `Chrome Safe Storage` CLI prompt abuse simultaneously? Because `secd` eliminates password-derived software keyfiles and `CSSM` `SecACL` lists alike: every row key tangles through the Mac's unreadable `SEP` `UID` hardware `AES` engine, and read/write access requires a `TXM`-verified `<TeamID>` `DER` entitlement that no unentitled `UID 501` binary or `/usr/bin/security` CLI invocation can ever forge [12, 321, 323, 324, 332]!

Finally, two physical bounds remain irreducible even under `Stolen Device Protection` [48]. First, `SDP` intentionally preserves Apple Pay passcode fallback at retail NFC terminals and exempts familiar locations by default unless the user flips `Require Security Delay` to *Always* (essential for shared-residence or domestic threat models) [48]. Second, no local biometric gate can defeat real-time physical duress (*rubber-hose cryptanalysis*): an armed mugger forcing a victim to look at `Face ID` on the spot passes Tier 1 credential checks immediately, though `SDP`'s non-bypassable 60-minute Tier 2 timer still blocks an assailant from rapidly transferring Apple Account ownership or disabling `Find My` during a brief street robbery [48, 338].

## Verification & Forensic Artifacts

On `macOS`, enumerate active legacy `CSSM` file keychains alongside the hardware-UUID-scoped `secd` Data Protection SQLite store (`keychain-2.db`) [322, 331, 332]:

```bash
security list-keychains
ls -lh ~/Library/Keychains/login.keychain-db ~/Library/Keychains/*/keychain-2.db 2>/dev/null
```

Representative output showing both vaults coexisting on an Apple Silicon Mac:

```text
    "/Users/alice/Library/Keychains/login.keychain-db"
    "/Library/Keychains/System.keychain"
-rw-r--r--  1 alice  staff   1.4M Nov 15 09:12 /Users/alice/Library/Keychains/login.keychain-db
-rw-------  1 alice  staff   8.2M Nov 15 10:40 /Users/alice/Library/Keychains/4A8F19C2-.../keychain-2.db
```

Inspect legacy `SecAccess` / `SecACL` entries (`encrypt`, `decrypt`, `partition_id`) on metadata in `login.keychain-db` without dumping secret values (`-a` prints ACLs only, omitting `-d`) [333, 336]:

```bash
security dump-keychain -a ~/Library/Keychains/login.keychain-db 2>/dev/null | grep -E 'Chrome Safe Storage|authorizations|partition_id' -A 2 | head -n 12
```

Verify `TXM`-enforced `keychain-access-groups` and `application-identifier` `DER` entitlements on a first-party `secd` client binary [321, 323]:

```bash
codesign -d --entitlements :- /System/Applications/Passwords.app 2>/dev/null | grep -E 'keychain-access-groups|application-identifier' -A 2 | head -n 6
```

Confirm `Activation Lock` (`Find My Mac`) hardware NVRAM token presence and inspect recent `secd` and `LocalAuthentication` (`coreauthd`) activity via Unified Logging [322, 340]:

```bash
nvram -p | grep -c 'fmm-mobileme-token-FMM' || true
log show --last 30m --predicate 'process IN {"secd", "coreauthd"}' --style compact | tail -n 5
```

Binding non-exportable keys and anti-theft gates inside `SEP` secures credentials locally on the handset or Mac, yet a remote banking server, relying party, or Zero Trust gateway cannot physically inspect the client's SoC over a TLS socket. [Chapter 12](12-sep-app-device-attestation.md) derives how `SEP` proves hardware key residency and booted OS posture across the network via `DCAppAttestService` and `ACME` `Managed Device Attestation`.
