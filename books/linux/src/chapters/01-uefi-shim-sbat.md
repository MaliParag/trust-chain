# UEFI, shim, Machine Owner Keys, and SBAT Revocation

## Overview

* **Link in the Chain:** First cryptographic admission gate on x86_64 and ARM64 UEFI platforms; authenticates pre-OS Linux bootloaders against firmware NVRAM trust stores before transferring execution to a second-stage loader (`GRUB2`, `systemd-boot`) or Unified Kernel Image (`UKI`).
* **Core Security Invariant:** Firmware `LoadImage()` executes an initial EFI binary only if its PE/COFF Authenticode digest and signing chain are absent from `dbx` and chain to `db`; subsequently, `shim.efi` admits a second-stage PE image only if its `.sbat` component generations satisfy `SbatLevel`, its digest/signer is absent from `dbx` and `MokListX`, and its Authenticode signature chains to `db`, `shim`'s embedded vendor certificate, or `MokList`.
* **Deployment Profile Matrix:** Mutable enterprise distributions (`RHEL`, `Ubuntu`, `Debian`, `SUSE`) deploy Microsoft-signed `shim.efi` chaining to vendor-signed `grubx64.efi` with `MokManager` enabled for out-of-tree `DKMS` modules; immutable appliances and `Talos` / `Bottlerocket` builds either chain `shim.efi` directly to a signed `UKI` or enroll custom OEM/fleet `PK`/`KEK`/`db` keys with Microsoft third-party CAs removed; cloud VMs rely on hypervisor-provisioned OVMF NVRAM templates.
* **Trusted Computing Base (TCB):** Silicon reset roots where fused (`Intel Boot Guard`, `AMD Platform Secure Boot`), SPI flash hosting UEFI `SEC`/`PEI`/`DXE`/`BDS` volumes, NVRAM authenticated variables (`PK`, `KEK`, `db`, `dbx`) and boot-services-only `SbatLevel`/`MokList`, Microsoft UEFI CA signing infrastructure, `shim.efi`, and the distribution's bootloader signing HSM.
* **Integration Seam & Handoff:** Hands off an Authenticode- and `SBAT`-verified bootloader or `vmlinuz` entry point plus runtime-readable `MokListRT` key mirrors; leaves `initramfs` and kernel command-line binding to [Chapter 2](02-uki-systemd-pcrlock.md) and post-boot Ring 0 lockdown to [Chapter 5](05-kernel-lockdown-modules.md).

## Problem Statement & Threat Model

Operating-system access controls, mandatory access control policies, and kernel memory mitigations cannot defend themselves if an adversary executes arbitrary instructions in Ring 0 before the Linux kernel initializes. Under legacy PC BIOS boot, CPU reset jumped into 16-bit real mode, initialized DRAM, read the first 512-byte sector (Master Boot Record) of the boot drive to physical address `0x7C00`, verified only the two-byte `0x55AA` magic trailer, and transferred control unconditionally [1]. Any attacker who gained transient root privileges or brief physical access to an unencrypted boot sector could overwrite Stage 1 or Stage 1.5 of `GRUB` to hook kernel decompression in memory while concealing the modification from userspace utilities.

Unified Extensible Firmware Interface (`UEFI`) Secure Boot (`UEFI` Specification Section 32 [1]) replaced unauthenticated sector jumping with cryptographic verification of Portable Executable (`PE/COFF`) boot applications against authenticated NVRAM variables (`PK`, `KEK`, `db`, `dbx`). On commercial x86_64 hardware, however, Secure Boot immediately collided with the organizational structure of open-source software. Commodity motherboards leave the factory with Microsoft's Platform/Key-Exchange ecosystem pre-enrolled in `KEK` and `db` (`Microsoft Windows Production PCA 2011` / `Windows UEFI CA 2023` for Windows, and `Microsoft Corporation UEFI CA 2011` / `Microsoft UEFI CA 2023` for third-party UEFI drivers, PCIe Option ROMs, and non-Windows bootloaders) [1, 122, 123]. Hundreds of independent Linux distributions, enterprise rebuilds, corporate fleet teams, and individual kernel developers compile custom kernels daily, plus out-of-tree kernel modules (`NVIDIA` GPU drivers, `ZFS`, custom network ASICs) via `DKMS`. Routing every distribution kernel release and every developer's local `make bzImage` through Microsoft's central hardware-dev-center signing portal was operationally impossible, yet asking mainstream laptop users to wipe factory UEFI keys in firmware setup would break Windows dual-boot and brick systems whose PCIe GPU or NVMe Option ROMs are signed solely by the Microsoft third-party UEFI CA [14, 123].

The Linux ecosystem therefore faced a three-part engineering problem under an adversary model encompassing local root compromise (mounting the `FAT32` EFI System Partition at `/boot/efi` and invoking `efivarfs` writes), unattended physical access, and rogue network boot servers (`PXE` / `UEFI HTTP Boot`). First, Linux needed a compact, auditable first-stage UEFI bridge signed once by the Microsoft third-party UEFI CA that could delegate trust cleanly to each distribution's own signing authority *and* allow machine owners with physical console presence to enroll local keys without disabling Secure Boot. Second, when a vulnerability was discovered in shared upstream bootloader code such as `GNU GRUB2`, the ecosystem needed a revocation mechanism that would not exhaust constrained 32-to-64 KiB motherboard SPI flash NVRAM by enumerating thousands of per-distro binary SHA-256 hashes [7, 49]. Third, the handoff from `shim` to `GRUB2` and `vmlinuz` had to block interpreter, dynamic-module, and parser escapes inside the pre-OS environment itself.

## Kernel & Userspace Mechanics

### UEFI Platform Initialization, Silicon Anchors, and Authenticated Variables

Before a single byte of Linux code executes, platform firmware runs the four-phase UEFI Platform Initialization (`PI`) pipeline from motherboard SPI flash: Security (`SEC`), Pre-EFI Initialization (`PEI`), Driver Execution Environment (`DXE`), and Boot Device Selection (`BDS`) [1]. Because `LoadImage()` signature enforcement lives inside `DXE`, UEFI Secure Boot assumes `SEC`, `PEI`, and `DXE` firmware volumes in SPI flash have not been modified. Enterprise servers and modern client systems anchor those pre-UEFI stages in immutable silicon fuses via `Intel Boot Guard` (which verifies an Authenticated Code Module and the OEM Initial Boot Block against Field Programmable Fuses before releasing x86 cores) or `AMD Platform Secure Boot` (`PSB`, verified on the on-die AMD Secure Processor) [1, 124].

Within `DXE`, Secure Boot policy is governed by four authenticated NVRAM variables carrying the `EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS` attribute (`PK`, `KEK`, `db`, `dbx`) [1, 125]. Any call to `SetVariable()` mutating these stores must wrap the new `EFI_SIGNATURE_LIST` payload inside an `EFI_VARIABLE_AUTHENTICATION_2` descriptor signed via PKCS#7 with a strictly monotonic `EFI_TIME` timestamp by an authority higher in the hierarchy (`PK` signs `KEK`; `PK` or `KEK` signs `db` and `dbx`). During `BDS`, `LoadImage()` computes the target binary's PE/COFF Authenticode SHA-256 digest (skipping the PE Optional Header `CheckSum`, the Certificate Table directory entry, and the trailing `WIN_CERTIFICATE` PKCS#7 blob [118]) and enforces denylist precedence: if the binary hash or any certificate in its signing chain matches `dbx`, loading aborts immediately with `EFI_SECURITY_VIOLATION`; otherwise, `LoadImage()` admits the image only if its hash or signing chain matches an entry in `db` [1].

Across the commercial PC ecosystem, `db` trust underwent a once-in-fifteen-years generational turnover in June 2026 [123, 125, 126, 127]. Since 2011, OEM motherboards shipped with two Microsoft root authorities in `db`: `Microsoft Windows Production PCA 2011` (for Windows `bootmgfw.efi`, expiring October 19, 2026) and `Microsoft Corporation UEFI CA 2011` (for third-party PCIe Option ROMs, firmware updaters, and Linux `shim.efi`, carrying X.509 `notAfter` date June 27, 2026) [126, 127]. Ahead of that sunset, Microsoft introduced `Windows UEFI CA 2023` and `Microsoft UEFI CA 2023` (`KB5025885` and `secureboot_objects` [125, 127]); starting in October 2025, Microsoft's signing portal returned Linux `shim` binaries dual-signed by both the `2011` and `2023` CAs, switching exclusively to `Microsoft UEFI CA 2023` after June 27, 2026 [126]. Crucially, UEFI `LoadImage()` intentionally *does not evaluate X.509 `notAfter` expiration timestamps against the real-time clock* so a drained CMOS battery never bricks a server [126, 128]. That design creates a double-edged operational hazard: first, Linux workstations or bare-metal servers whose firmware `db` never enrolled `Microsoft UEFI CA 2023` (via OEM capsule updates or `fwupd` [129]) fail to boot post-June-2026 `2023`-only Linux installation media; second, ancient vulnerable `shim` binaries signed under `Microsoft Corporation UEFI CA 2011` remain trusted forever on every unrotated board unless explicitly added to `dbx` or until the `2011` CA itself is revoked from `db` [126, 127, 128].

### `shim.efi`, `verify_buffer()`, and the `MokList` / `MokListRT` Split

To bridge Microsoft's third-party UEFI CA in `db` to independent Linux distributions, Red Hat and the Linux community created `shim` (`shimx64.efi` on x86_64, `shimaa64.efi` on ARM64), a deliberately compact UEFI application containing a stripped Cryptlib/OpenSSL X.509 verifier, PE section validator (`pe.c`), and embedded vendor certificate (`vendor_cert` / `vendor_db`) [14, 123, 130]. Microsoft's review committee audits each distribution's `shim` build (verifying reproducible build provenance inside clean container environments, HSM-protected vendor CA policy, NX memory-protection flags, and current `SBAT` metadata [123, 131]) before signing `shim.efi`.

![Figure: UEFI Secure Boot trust delegation from firmware dbx/db through Microsoft-signed shim.efi, boot-services-only MokList mirrored to MokListRT, and second-stage GRUB2 or UKI loading into the Linux kernel.](diagrams/01-shim-mok-trust-chain.svg)

When UEFI `BDS` invokes `shim.efi`, `shim` cannot rely on firmware `LoadImage()` alone to verify `grubx64.efi` or `vmlinuz`, because firmware `db` knows nothing about Fedora's, Ubuntu's, or Debian's signing keys. Instead, `shim` implements its own PE/COFF parser and Authenticode verifier (`verify_buffer()` and `generate_hash()` in `pe.c` [130]): `generate_hash()` validates the `MZ`/`PE\0\0` headers, checks `SizeOfHeaders`, copies all `EFI_IMAGE_SECTION_HEADER` entries into an isolated heap buffer sorted by `PointerToRawData`, verifies that cumulative `SizeOfRawData` never overflows image bounds or overlaps headers, enforces non-writable/non-executable (`W^X`) section alignment when firmware exposes `EFI_MEMORY_ATTRIBUTE_PROTOCOL` (`shim` `15.8+`, tracked in `HSIStatus` [115, 131]), checks `SBAT` generations (`verify_sbat_section()` [132]), checks all denylists (`dbx`, `MokListX`, `vendor_deauthorized`) first, and finally checks allowlists (`db` unless `MokIgnoreDB` is set, `vendor_cert`/`vendor_db`, and `MokList`) [14, 115, 130]. Downstream loaders access this verifier through `SHIM_LOCK_GUID` (`605dab50-e046-4300-abb6-3dd810dd8b23`, exposing `shim_lock->Verify(buffer, size)`), while `shim` `15.8+` also hooks the UEFI Boot Services `LoadImage()` / `Security2` architectural protocols so nested EFI loads route automatically through `verify_buffer()` [14, 130].

How does `shim` allow local administrators or developers to sign custom kernels, enroll out-of-tree `DKMS` module keys, or toggle `shim` validation without possessing an `EFI_VARIABLE_TIME_BASED_AUTHENTICATED_WRITE_ACCESS` `KEK` private key? Through Machine Owner Keys (`MOK`), engineered in `mok.c` (`mok_state_variable_data[]`) around a strict UEFI variable attribute split [14, 115]:

```c
/* UEFI variable attribute split enforced by shim (mok.c) */
#define MOK_NV_ATTR  (EFI_VARIABLE_NON_VOLATILE | EFI_VARIABLE_BOOTSERVICE_ACCESS)
#define MOK_RT_ATTR  (EFI_VARIABLE_BOOTSERVICE_ACCESS | EFI_VARIABLE_RUNTIME_ACCESS)
```

Notice the `.no_attr = EFI_VARIABLE_RUNTIME_ACCESS` constraint enforced by `shim` on persistent `MokList`, `MokListX` (MOK denylist), `MokSBState` (Secure Boot validation disable toggle), `MokDBState` (ignore firmware `db`), and `SbatLevel` [115]! Once the Linux kernel invokes `ExitBootServices()`, UEFI firmware completely hides every variable lacking `RUNTIME_ACCESS` from the running operating system (`/sys/firmware/efi/efivars` cannot read or mutate `MokList`, `MokSBState`, or `SbatLevel`) [1, 115]. If a rogue OS kernel or firmware bug ever creates one of these persistent variables *with* `RUNTIME_ACCESS` set, `shim` detects the illegal `.no_attr` bit on the next boot, deletes the untrusted variable immediately, and re-initializes clean boot-services-only storage [115].

Consequently, an attacker who achieves `UID 0` in Linux userspace *cannot* silently inject a rogue X.509 certificate into `MokList` or flip `MokSBState` to bypass Secure Boot. Instead, running `mokutil --import key.der` or `mokutil --disable-validation` from Linux writes a runtime-accessible request variable (`MokNew`, `MokXNew`, or `MokSB`) paired with an `SHA-256` salted one-time password hash (`MokAuth` / `MokPW`) [115, 133]. On the next reboot, `check_mok_request()` in `mok.c` runs *before* `ExitBootServices()`, detects the pending request variable, and launches `MokManager.efi` (`mmx64.efi`) on the physical UEFI console, requiring a human at the keyboard to prove physical presence by typing the password before `MokManager` commits changes into boot-services-only `MokList` or `MokSBState` [14, 115]. Before transferring control to the OS, `mirror_mok_db()` copies `MokList`, `MokListX`, `MokSBState`, and `SbatLevel` into *volatile* (RAM-backed, non-`NON_VOLATILE`) runtime-readable mirrors named `MokListRT`, `MokListXRT`, `MokSBStateRT`, and `SbatLevelRT`, while extending `MokList`, `MokListX`, and `MokSBState` into `TPM 2.0` `PCR[14]` (`SbatLevel` into `PCR[7]`) [115]. During Linux initialization, `security/integrity/platform_certs/load_uefi.c` checks `arch_get_secureboot()` (which inspects both firmware `SecureBoot` and `MokSBStateRT` so `mokutil --disable-validation` disables kernel trust in MOKs and avoids falsely claiming verified boot!) before importing `MokListRT` into the `.machine` keyring ([Chapter 5](05-kernel-lockdown-modules.md)) [115, 134].

### `GRUB2` `grub_file_verifier` Surface, `BootHole`, and `.sbat` Revocation

Once `shim` authenticates `grubx64.efi`, `GRUB2` itself becomes an active pre-OS operating system running in Ring 0 UEFI Boot Services, complete with filesystem drivers (`ext2`, `xfs`, `btrfs`, `fat`), network stacks (`tftp`, `http`), `pf2` bitmap font and `PNG`/`JPEG`/`TGA` image decoders, and a Turing-complete shell interpreter parsing `/boot/grub/grub.cfg` [49, 135, 136]. To prevent `GRUB2` from acting as a signed trampoline into unsigned code, `GRUB2` (`2.06+`) routes every file open through `grub_verifiers_open()` in `grub-core/kern/verifiers.c` [135, 136]. When `SecureBoot = 1`, `GRUB2` enters lockdown mode: it disables raw memory/port commands (`iorw`, `memrw`), blocks custom `acpi` table injection and legacy 16-bit `linux16` loaders, forbids loading external `.mod` dynamic modules from `/boot/grub/x86_64-efi/` (requiring distributions to link needed modules into the single signed monolithic `grubx64.efi` binary), buffers opened files completely in `verified_fs` (`verified->buf`) to prevent disk read-time `TOCTOU`, and invokes registered `struct grub_file_verifier` callbacks (`shim_lock`) so `GRUB_FILE_TYPE_LINUX_KERNEL` payloads must pass `shim_lock->Verify()` before execution [135, 136].

![Figure: Contrast between pre-verifier untrusted parser attack surfaces in UEFI DXE, shim HTTP boot, and GRUB2 themes/configs versus hardened grub_file_verifier lockdown and direct UKI boot.](diagrams/01-extra-grub-verifier-surface.svg)

Yet repeatedly between 2020 and 2024, attackers broke `GRUB2` and `shim` *before* or *around* `shim_lock->Verify()` by exploiting memory-corrupting C parsers reachable from unauthenticated files on the FAT32 EFI System Partition [49, 137, 138, 139]. In July 2020, Eclypsium disclosed `BootHole` (`CVE-2020-10713`): an integer overflow in `grub_script_yyparse()` while lexing crafted tokens inside unauthenticated `grub.cfg` corrupted the `GRUB2` heap and achieved arbitrary Ring 0 execution under active Secure Boot [49]. In March 2021, `CVE-2021-20225` exposed a heap out-of-bounds write in `GRUB2`'s command-line option parser reachable by passing crafted short/long argument counts in `grub.cfg` [137]. Even after script and option parsers were patched, security researchers pivoted to graphical boot assets loaded prior to OS verification: in `CVE-2022-2601` (paired with `CVE-2022-3775`), a crafted `unicode.pf2` font file on the ESP triggered a 32-bit integer overflow in `grub_font_construct_glyph()` when computing `max_glyph_size` (`width * height`), allocating a near-zero `grub_malloc()` buffer and overwriting Ring 0 heap metadata with attacker-controlled glyph bitmap bytes [138]!

`BootHole` simultaneously triggered a structural crisis in UEFI revocation [7, 49]. Because every Linux distribution, point release, and derivative compiled its own `grubx64.efi` signed by its own vendor sub-CA, hundreds of distinct vulnerable `shim` and `GRUB2` binaries existed in the wild. Revoking every distribution's CA in UEFI `dbx` would brick retail install media, while appending 150+ 32-byte `EFI_CERT_SHA256_GUID` digests (48 bytes per `EFI_SIGNATURE_DATA` entry) consumed roughly 10 KiB, nearly a third of the entire 32 KiB NVRAM `dbx` budget available on many motherboards [7].

![Figure: Why hash-based UEFI dbx revocation failed to scale during BootHole (CVE-2020-10713) and how SBAT (.sbat PE metadata compared against the boot-services-only SbatLevel variable) achieves constant-space generation revocation.](diagrams/01-sbat-vs-dbx-revocation.svg)

To eliminate $O(N_{\text{binaries}})$ NVRAM bloat permanently, Linux and Microsoft co-designed `UEFI Secure Boot Advanced Targeting` (`SBAT`), implemented in `sbat.c` [7, 132]. Every Secure-Boot-signed PE binary (`shim`, `GRUB2`, `systemd-boot`, `UKI`, `fwupd`) embeds an Authenticode-covered `.sbat` PE section containing UTF-8 CSV rows with exactly six mandatory columns (`SBAT_SECTION_COLUMNS = 6` in `parse_sbat_section()`): `component_name`, `component_generation`, `vendor_name`, `vendor_package_name`, `vendor_version`, and `vendor_url` [7, 132]:

```text
sbat,1,SBAT Version,sbat,1,https://github.com/rhboot/shim/blob/main/SBAT.md
grub,4,Free Software Foundation,grub,2.12,https://www.gnu.org/software/grub/
grub.fedora,3,The Fedora Project,grub2,2.12-10.fc41,https://fedoraproject.org/
```

Notice how `.sbat` distinguishes *upstream global* generations (`grub,4`) from *vendor-fork* generations (`grub.fedora,3`): if a vulnerability affects upstream `GRUB2` (`CVE-2022-2601`), bumping `grub,4` in `SbatLevel` revokes every distribution's pre-patch `GRUB2` in six ASCII bytes; conversely, if Fedora alone mis-merges a backport patch, bumping `grub.fedora,4` revokes only Fedora's affected build without forcing Ubuntu, Debian, or SUSE to re-sign their bootloaders [7]! Correspondingly, `shim` maintains the boot-services-only `SbatLevel` variable (`parse_sbat_var_data()` in `sbat.c`) starting with a version-and-datestamp header (`sbat,1,2024010900`) followed by compact `(component_name, component_generation)` floors [7, 132]. Formally, let $C(B) = \{(c_i, g_i)\}$ denote the pairs inside binary $B$'s `.sbat` section, and let $R = \{(c_j, g^{\min}_j)\}$ denote the floors in `SbatLevel`. Inside `verify_single_entry()`, `atoi()` parses non-numeric strings as `0` (failing closed) and enforces:

$$\operatorname{SBAT\_Valid}(B, R) \iff C(B) \neq \emptyset \;\land\; \forall (c, g) \in C(B),\; \forall (c, g^{\min}) \in R:\; g \ge g^{\min}$$

If a candidate binary lacks `.sbat` or declares `grub,3` when `SbatLevel` demands `grub,4`, `shim` aborts with `EFI_SECURITY_VIOLATION` [132]. Each `shim` release embeds two payload tables (`automatic` conservative floor applied unconditionally whenever on-flash `sbat_datestamp` is older, and `latest` floor applied when `mokutil --set-sbat-policy latest` or an OS update requests aggressive revocation), reserving `dbx` hash entries strictly for vulnerabilities inside `shim` itself or ancient pre-SBAT (`shim <= 15.2`) binaries [7, 132, 133].

## Distro, Immutable-OS, & Cloud Trade-Offs

Across mutable enterprise distributions (`RHEL 9/10`, `Ubuntu 22.04/24.04 LTS`, `Debian 12/13`, `SUSE`), the standard `shim` to `GRUB2` to `vmlinuz` chain optimizes for hardware compatibility and dual-boot coexistence with Windows on retail OEM firmware [14, 122]. Leaving `MokManager` available allows enterprise operators to sign proprietary third-party `.ko` modules (`NVIDIA`, EDR kernel sensors) under an organization-owned MOK key without disabling Secure Boot, and `shim` additionally ships a companion `fbx64.efi` (`fallback.efi`) helper inside `/EFI/BOOT/` that reconstructs wiped UEFI `Boot####` NVRAM entries from `/EFI/<distro>/BOOTX64.CSV` whenever a motherboard BIOS flash resets boot order [14]. Operators who want `shim` to trust *only* their embedded vendor CA and enrolled `MokList` while distrusting sibling Microsoft-signed bootloaders in firmware `db` can even toggle `mokutil --ignore-db`, setting boot-services-only `MokDBState` (`MokIgnoreDB` at runtime) so `shim` and Linux's `load_uefi_certs()` ignore UEFI `db` certificates during downstream verification [115, 133, 134]. Yet this flexibility carries a steep TCB cost: firmware `BDS` itself still trusts `db` before `shim` runs (so an attacker with ESP write access can replace `shimx64.efi` directly with another `db`-signed EFI binary), `GRUB2`'s 300,000-line parser stack remains inside Ring 0 Boot Services, and locally built `initramfs` archives stay outside Authenticode coverage unless paired with UKIs ([Chapter 2](02-uki-systemd-pcrlock.md)).

Immutable container operating systems (`Talos Linux`, `Bottlerocket`, `Flatcar`, and UKI-configured `Fedora CoreOS`) aggressively prune this surface [2, 45, 46]. By eliminating `GRUB2` completely in favor of `systemd-boot` (`sd-boot` [140], roughly one-tenth the code size, possessing no script interpreter, no font/image decoders, no filesystem drivers beyond UEFI's native `EFI_SIMPLE_FILE_SYSTEM_PROTOCOL`, and no network stack) or invoking a signed `UKI` directly from `shim.efi` (or directly from UEFI `BDS`), immutable builds delete hundreds of thousands of lines of Ring 0 parser code [8, 45, 140]. On dedicated bare-metal appliances, workstations managed with `sbctl` [141], and hyperscale cloud instances (`AWS Nitro` UEFI, `GCP Shielded VMs`, `Azure Trusted Launch`), platform owners frequently go one step further: transitioning firmware into Setup Mode and enrolling custom fleet-specific `PK`, `KEK`, and `db` X.509 certificates via `systemd-boot` (`loader/keys/auto/*.auth`) or `sbctl enroll-keys` while omitting `Microsoft Corporation UEFI CA` (`2011` and `2023`) altogether [1, 140, 141]. Removing Microsoft's third-party UEFI CA shrinks the pre-OS TCB from every `shim`, bootloader, and diagnostics binary ever signed across the global PC industry down to a single organization-owned keypair, provided that bare-metal operators audit PCIe GPU/NIC Option ROM dependencies first (using `sbctl enroll-keys --microsoft` or `OpROM` hash allowlisting only where add-in cards lack OEM-`db`-signed firmware) [123, 141].

## Seam Failures, CVEs, & Structural Bounds

Real-world Linux Secure Boot failures demonstrate how parser complexity inside pre-OS loaders, subtle UEFI variable-persistence bugs, pre-SBAT downgrade chains, and cross-OS revocation coordination break otherwise sound Authenticode cryptography.

Three structural lessons stand out across this failure history. First, *any parser executing before cryptographic verification inherits adversarial inputs at Ring 0 privilege*. In `CVE-2023-40547` (scored CVSS 9.8 by MSRC [139, 144]), `shim.efi`'s HTTP boot client parsed remote HTTP `Content-Length` headers into `rx_buf` *before* `verify_buffer()` could check the downloaded image's signature; an adjacent network attacker or compromised DHCP relay gained Ring 0 execution inside a genuine Microsoft-signed `shim` binary, forcing an emergency `dbx` hash revocation because `shim` is the root evaluator of `SbatLevel` and cannot revoke itself via `SBAT` when loaded directly by UEFI `BDS` [7, 132, 144]. Second, the August 2024 `KB5041595` dual-boot outage and the June 2026 `Microsoft UEFI CA 2011` transition underscored that `UEFI` NVRAM (`db`, `dbx`, and `SbatLevel`) is a *shared global state bus* across every operating system on a machine: Windows updates can block older Linux `shim` installs via `SbatLevel`, and conversely an unrevoked Windows (`BlackLotus` `CVE-2022-21894`) or legacy Oracle/Red Hat (`shim <= 0.9` `CVE-2026-8863`) bootloader signed under a shared Microsoft CA compromises every OS trusting that CA [122, 126, 128, 142]. Finally, UEFI Secure Boot and `SBAT` possess an explicit theoretical ceiling: they authenticate *PE executable entry*, not unmeasured kernel command lines or locally generated `/boot/initramfs-*.img` CPIO archives. Closing that gap requires binding early-boot inputs into a signed `Unified Kernel Image` paired with `TPM 2.0` PCR policies ([Chapter 2](02-uki-systemd-pcrlock.md)).

## Inspecting on a Live Linux Host

Verify whether UEFI Secure Boot is currently active in `User` / `Deployed` mode and inspect `shim`'s MOK enforcement state via `mokutil` and `bootctl`:

```bash
mokutil --sb-state
bootctl status 2>/dev/null | head -n 18
```

Inspect the certificates currently enrolled in firmware `db`, the count of revoked `dbx` hashes/certificates, and any local Machine Owner Keys mirrored into `MokListRT`:

```bash
mokutil --db | grep -E "Subject:|Issuer:" | head -n 10
mokutil --dbx | grep -c "SHA-256"
mokutil --list-enrolled | grep -E "Subject:|Valid"
```

Read the active `SBAT` revocation floor from the runtime mirror variable `SbatLevelRT` and inspect the `.sbat` metadata compiled into the installed `shim` or `GRUB2` EFI binary:

```bash
mokutil --list-sbat-revocations
objcopy -O binary --only-section=.sbat /boot/efi/EFI/*/shimx64.efi /dev/stdout 2>/dev/null
```

Check whether the platform `PK` carries a test/placeholder subject (`PKfail` `DO NOT TRUST` indicator) and verify whether `Microsoft UEFI CA 2023` is enrolled in firmware `db` alongside `fwupd` UEFI `dbx` status:

```bash
mokutil --pk | grep -E "Subject:|Issuer:"
mokutil --db | grep -F "Microsoft UEFI CA 2023" || echo "2023 UEFI CA missing from db"
fwupdmgr get-devices 2>/dev/null | grep -A 3 -F "UEFI dbx"
```
