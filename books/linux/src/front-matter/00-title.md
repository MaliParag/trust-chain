# The Linux Trust Chain

## From UEFI, Unified Kernel Images, and dm-verity Through LSMs, eBPF, and Containers to Confidential Cloud

**Parag Mali**

---

Unlike Windows or Apple platforms, Linux has no single vendor root key, no monolithic userland, and no single deployment shape: the same kernel family powers developer laptops, immutable `ostree` / `systemd-sysext` appliances, hyperscale `Kubernetes` nodes, autonomous AI execution sandboxes, and `AMD SEV-SNP` / `Intel TDX` confidential cloud guests. Historically, that modularity left a gaping hole right across early boot: `UEFI` verified `shim` and `vmlinuz`, while an unencrypted, unsigned `initramfs` and mutable `/etc` allowed physical or root-fs attackers to hijack execution before userspace ever started [1]. Modern Linux closes those seams through a composable chain: `SBAT` generation revocations, signed `Unified Kernel Images` (`UKIs`) measured into `TPM 2.0` `PCR[11]` (`systemd-stub` and `systemd-pcrlock`), `LUKS2` + `dm-verity`, `fs-verity`, and the `Integrity Policy Enforcement` (`IPE`) LSM [1, 2], `Kernel Lockdown` and stacked `Linux Security Modules` (`SELinux`, `AppArmor`, and unprivileged `Landlock`), `eBPF` runtime mediation, `systemd` `run0` SUID-free privilege brokers [5], `gVisor` and `Firecracker` micro-VM AI agent sandboxes [6], `SPIFFE`/`SPIRE` workload attestation, and `COCONUT-SVSM` / `Confidential Containers` paravisors [3].
