# Open-Source Supply-Chain Subversion: XZ Utils, Sigstore, and Reproducible Builds

## Overview

* **Link in the Chain:** Finale of Volume III; confronts the ultimate upstream boundary *preceding* every hardware, firmware, bootloader, kernel, MAC, container, and TEE mechanism in [Chapters 1](01-uefi-shim-sbat.md) through [19](19-confidential-containers.md): verifying that the compiled open-source binaries signed by Linux distributions correspond faithfully to audited source code without hidden build-time implants.
* **Core Security Invariant:** No release tarball or pre-generated build macro is trusted outside immutable Git commit trees; every binary package must carry a transparency-logged `Sigstore` (`Fulcio` + `Rekor`) signature over an `in-toto` `SLSA Build Level 3` provenance attestation produced by an isolated hermetic builder, AND pass independent bit-for-bit Reproducible Build verification ($\operatorname{SHA-256}(\text{Build}_A(S)) = \operatorname{SHA-256}(\text{Build}_B(S))$), while core system libraries (`libsystemd`) decouple optional compression dependencies via on-demand `dlopen()`.
* **Deployment Profile Matrix:** Traditional distro workflows ingested maintainer-generated Autotools release tarballs (`*.tar.xz`) and linked monolithic shared-library graphs; post-2024 `Debian`, `Fedora`, `Arch`, `NixOS`, `Wolfi`/`Chainguard`, and OCI container ecosystems enforce Git-tag builds, `systemd` `dlopen()` decoupling, `SOURCE_DATE_EPOCH` reproducibility rebuilders (`rebuilderd`), and `SLSA` / `Sigstore` `cosign` verification.
* **Trusted Computing Base (TCB):** Upstream Git trees and multi-party code review, hermetic CI build infrastructure (`SLSA` L3 builders), deterministic compilers (`GCC`/`LLVM`/`rustc` honoring `SOURCE_DATE_EPOCH`), independent `rebuilderd` verifiers, and `Sigstore` (`Fulcio` OIDC CA + `Rekor` Merkle transparency log).
* **Integration Seam & Handoff:** Closes the upstream source-to-binary chasm exposed by `XZ Utils` (`CVE-2024-3094`), completing the end-to-end Linux trust chain from upstream source commit through silicon reset (`UEFI`/`UKI`/`TPM2`), Ring 0 (`Lockdown`/`CFI`/`Rust`/`LSMs`/`eBPF`), userspace (`run0`/`systemd-creds`/`FIDO2`), and cloud isolation (`Firecracker`/`SPIFFE`/`SEV-SNP`/`CoCo`).

## Problem Statement & Threat Model

On Friday, March 29, 2024, Microsoft Principal Software Engineer Andres Freund posted a quiet forensic report to the Openwall `oss-security` mailing list that shook the global computing industry to its foundations [152]: while benchmarking PostgreSQL on a Debian `sid` test system, Freund noticed via `perf` and `cron` monitoring that failed SSH logins to `sshd` were consuming roughly `500 milliseconds` of unexpected CPU time inside `liblzma.so.5` (`xz-utils` versions `5.6.0` and `5.6.1`)! Tracing those cycles uncovered `CVE-2024-3094`, the most sophisticated publicly documented upstream supply-chain operation ever mounted against Linux [152, 153].

Pause and reflect on what `CVE-2024-3094` meant for every runtime defense we constructed across Parts I through IV of this book:
Suppose a Fedora Rawhide or Debian Testing server had booted through `Intel Boot Guard`, `UEFI Secure Boot` + `SBAT` ([Chapter 1](01-uefi-shim-sbat.md)), an Authenticode-signed `Unified Kernel Image` measured into `TPM 2.0` `PCR[11]` ([Chapter 2](02-uki-systemd-pcrlock.md)), a read-only `dm-verity` `/usr` tree ([Chapter 3](03-luks2-verity.md)), strict `IPE` execution enforcement + `Keylime` attestation ([Chapter 4](04-ima-ipe-keylime.md)), `lockdown=confidentiality` ([Chapter 5](05-kernel-lockdown-modules.md)), `FineIBT` + Shadow Stacks ([Chapter 6](06-kernel-memory-rust.md)), `SELinux` `Enforcing` (`sshd_t`, [Chapter 7](07-stacked-lsms-landlock.md)), `SUID`-free `run0` ([Chapter 10](10-suid-to-run0.md)), OpenSSH `TrustedUserCAKeys` + `FIDO2` hardware keys ([Chapter 13](13-pam-ssh-fido2.md)), and `AMD SEV-SNP` Confidential VM memory encryption ([Chapter 18](18-confidential-vms-svsm.md))! Every single cryptographic signature and runtime policy check on that machine would have reported `100% VALID`: because Fedora's and Debian's own legitimate build farms compiled the backdoored `xz-5.6.1.tar.gz` tarball and signed `liblzma.so.5.6.1` with their genuine offline distribution signing keys, and the backdoor executed *inside `sshd_t` itself prior to SSH authentication* [152, 153]!

Cryptographic verification at boot and runtime proves integrity and origin (*"this binary matches bit-for-bit what the vendor signed"*); it can never by itself prove benign intent or upstream build fidelity (*"the binary the vendor signed came purely from reviewed source code without hidden build-script implants"*). Under a patient, state-caliber supply-chain adversary willing to invest three years of social engineering (`2021`–`2024`) to become a trusted co-maintainer of a critical transitive C library, completing the Linux trust chain requires closing four upstream seams simultaneously: *auditing the Git-to-tarball gap*, *severing unnecessary transitive shared-library linkage in privileged daemons*, *enforcing bit-for-bit Reproducible Builds*, and *binding every artifact to transparency-logged `SLSA` + `Sigstore` build provenance* [153, 154, 155, 156, 157].

## Kernel & Userspace Mechanics

### Complete Forensic Anatomy of the `XZ Utils` Backdoor (`CVE-2024-3094`)

Reconstructing all four stages of the `"Jia Tan"` (`JiaT75`) operation reveals a masterclass in exploiting the unverified seams between open-source maintainer culture, GNU Autotools tarballs, Linux distro patches, and ELF dynamic linking [152, 153]:

![Figure: Four-stage forensic kill chain of the XZ Utils backdoor (CVE-2024-3094), tracing how a tarball-only m4 macro extracted an encrypted object implant from binary test files, rode transitive libsystemd linkage into sshd, and hijacked RSA_public_decrypt via glibc GNU_IFUNC for Ed448-gated pre-auth RCE.](diagrams/20-xz-backdoor-kill-chain.svg)

Stage 1: Maintainer Capture & Fuzzing Suppression (`2021`–`2024`) [153]. Starting in October 2021, the pseudonymous account `JiaT75` submitted clean, helpful patches to `xz` while coordinated sockpuppet accounts (`Jigar Kumar`, `Dennis Ens`) sent relentless guilt-inducing emails pressuring burned-out original author Lasse Collin to hand over release authority over the tiny compression library embedded in every Linux install on earth. By 2023, `Jia Tan` controlled `xz`'s GitHub repository, primary release PGP signing key, and `google/oss-fuzz` contact email: quietly submitting an `oss-fuzz` pull request in July 2023 disabling `-fsanitize=...` instrumentation on `IFUNC` resolvers (`--disable-ifunc`) so Google's automated sanitizers wouldn't flag the incoming dynamic-linker hook [153]!

Stage 2: The Git-to-Tarball Seam (`m4/build-to-host.m4` + Binary Test Files) [152, 153]. Had `Jia Tan` committed C backdoor code directly to `xz`'s public Git repository, any code reviewer running `git log -p` would have spotted it instantly. Instead, `Jia Tan` committed two seemingly normal binary test archives (`tests/files/bad-3-corrupt_lzma2.xz` and `tests/files/good-large_compressed.lzma`) into Git under the cover of "decompression fuzzing test cases": *opaque binary blobs nobody can visually review in `git diff`*! Then, when rolling the `xz-5.6.0.tar.gz` and `xz-5.6.1.tar.gz` release tarballs (`make dist`), `Jia Tan` exploited a forty-year-old GNU Autotools blind spot: release tarballs include generated `configure` scripts and `m4/*.m4` macros that do not exist in Git! Inside the tarball-only `m4/build-to-host.m4`, a single obfuscated `gl_am_configmake` line checked quietly whether the build was running inside an `x86_64-linux-gnu` Debian (`DEB_BUILD_ARCH`) or Red Hat/Fedora (`RPM_ARCH`) package build environment (`uname -m == x86_64`, `GCC` + `glibc`: doing *nothing* on macOS, BSD, Alpine `musl`, or manual developer `./configure` builds so casual inspection produced a 100% clean library!) [152, 153]. When triggered inside a distro build farm, the script ran `tr` / `xz -dc` / `head -c` / RC4-like stream-cipher pipelines over `good-large_compressed.lzma` to extract a second-stage script *and* a pre-compiled x86_64 ELF relocatable object (`liblzma_la-crc64-fast.o`), splicing malicious machine code directly into `liblzma.so.5.6.1`'s `crc64_resolve()` compilation unit while stripping original symbol footprints [152, 153]!

Stage 3: Transitive ELF Shared-Library Linkage (`sshd` $\to$ `libsystemd` $\to$ `liblzma`) [152, 154]. Wait: why would `liblzma` (an `.xz` file compression library!) ever be mapped into the virtual address space of OpenSSH `sshd`, which never compresses `.xz` files and deliberately avoids unnecessary dependencies? Because Fedora, RHEL, Debian, and Ubuntu carried a downstream distro patch linking `sshd` against `libsystemd.so.0` solely so `sshd` could send a 10-byte `READY=1` startup datagram (`sd_notify()`) to `PID 1`: and `libsystemd.so.0` (which *also* implements `journalctl` log reading!) carried hard ELF `DT_NEEDED` dynamic-library headers pulling `liblzma.so.5`, `libzstd.so.1`, `liblz4.so.1`, and `libgcrypt.so.20` into every single binary linking `libsystemd` [152, 154]!

Stage 4: `glibc` `GNU_IFUNC` Symbol Hijacking & `Ed448`-Gated Pre-Auth RCE [152, 153]. On `glibc` Linux, an ELF symbol marked `STT_GNU_IFUNC` (*Indirect Function*) executes a custom C resolver function inside `ld.so` dynamic relocation *before* `main()` runs and *before* `BIND_NOW` Full `RELRO` (`PT_GNU_RELRO`) marks the Global Offset Table (`GOT`) read-only! When `sshd` started up (`argv[0] == "/usr/sbin/sshd"`, checked without plaintext strings via custom trie/checksum hashes inside the implant!), `liblzma`'s `crc64_resolve()` `IFUNC` walked `ld.so`'s internal `struct link_map` structures (`_r_debug`), hooked `_dl_audit_symbind_alt`, and redirected OpenSSL `libcrypto`'s `RSA_public_decrypt` (and `EVP_PKEY_set1_RSA`) GOT pointer inside `sshd` to the backdoor! Whenever a remote TCP `22` client initiated SSH public-key or certificate authentication presenting an RSA modulus $N$, the hooked `RSA_public_decrypt` checked a magic arithmetic tag on the upper bytes of $N$, decrypted the remaining modulus payload with `ChaCha20` derived from a hardcoded `Ed448` public key, verified an `Ed448` asymmetric signature over the payload + host key fingerprint, and passed the verified command string straight to `system()` as unsandboxed `UID 0`, returning cleanly on non-matching keys with zero auth-log entries [152, 153]! Only `Jia Tan`'s `Ed448` private key could trigger execution; every honeypot and packet capture on earth saw ordinary invalid RSA logins!

### Layer 1 Fix: Severing Transitive Linkage via `systemd` On-Demand `dlopen()`

Within days of `CVE-2024-3094`, both `systemd` and `OpenSSH` surgically dismantled the transitive linkage vector [113, 154]. First, OpenSSH `9.8` implemented the trivial UNIX-datagram `NOTIFY_SOCKET` (`READY=1`) protocol directly in ~30 lines of standalone C inside `sshd`, removing all distro patches linking `sshd` to `libsystemd.so` [113]! Second, `systemd` maintainers (`PR #32024` in `systemd v256+` [154]) refactored `libsystemd.so.0` to drop hard ELF `DT_NEEDED` dependencies on `liblzma`, `libzstd`, `liblz4`, `libgcrypt`, `libkmod`, `libacl`, and `libblkid`, replacing them with lazy on-demand `dlopen()` wrappers (`src/basic/dlfcn-util.c`): today, a daemon linking `libsystemd` solely for `sd_notify()` or `sd_journal_print()` *never maps `liblzma.so` or `libzstd.so` into its address space at all*!

### Layer 2 & 3 Fixes: Git-Direct Builds, Reproducible Builds, `SLSA` L3, and `Sigstore` (`Rekor`)

Stopping the next `Jia Tan` across the 30,000+ other packages in a Linux distribution requires closing the source-to-binary chasm mathematically [155, 156, 157, 158]:

![Figure: Closing the upstream open-source supply-chain gap: building strictly from signed Git commit trees (no bespoke Autotools tarballs), emitting isolated hermetic SLSA Build Level 3 provenance, verifying bit-for-bit Reproducible Builds across independent builders, and logging keyless OIDC signatures in Sigstore Rekor.](diagrams/20-slsa-sigstore-reproducible-pipeline.svg)

First, Abolishing Maintainer-Rolled Tarballs: Debian, Fedora, Arch, and Wolfi/Chainguard packaging policies increasingly build directly from immutable Git commit hashes (`git archive` + fresh in-builder `autoreconf -fi` using the *distro's* clean `autoconf`/`automake` packages!), eliminating hidden tarball-only `m4/build-to-host.m4` diffs forever [153, 155]!

Second, Bit-for-Bit Reproducible Builds (`reproducible-builds.org` [155]): formally, a build pipeline $\operatorname{Build}(S, E)$ over source Git tree $S$ and pinned build-tool environment $E$ is *deterministic* if two independent organizations ($A$ and $B$) on separate hardware and clocks satisfy:

$$\operatorname{SHA-256}\!\left(\operatorname{Build}_A(S, E)\right) = \operatorname{SHA-256}\!\left(\operatorname{Build}_B(S, E)\right)$$

By exporting `SOURCE_DATE_EPOCH` (clamping embedded `__DATE__`, `ar`, `gzip`, `tar`, and PE/ELF timestamps to the Git commit timestamp), stripping build-directory host paths via `-ffile-prefix-map=$PWD=.` (and Rust `--remap-path-scope`), sorting filesystem glob inputs (`LC_ALL=C`), and running continuous independent verification networks (`rebuilderd` across Debian `96%+`, Arch Linux, Fedora, and `Talos` / `NixOS` [155]), any stealth CI builder compromise or non-deterministic environment trigger becomes immediately visible as a hash mismatch before deployment!

Third, `SLSA` (`v1.0` Build Level 3 [156]), `in-toto` [158], and `Sigstore` (`Fulcio` + `cosign` + `Rekor` [157]): how do downstream Kubernetes admission controllers (`Kyverno` / `Sigstore Policy Controller`), `bootc` / `UKI` updaters, and `Confidential Containers` `image-rs` ([Chapter 19](19-confidential-containers.md)) verify provenance before running an artifact? Instead of relying on long-lived maintainer PGP keys (which `Jia Tan` simply generated and owned!), `SLSA` Build Level 3 mandates building inside an ephemeral, isolated, tenant-separated build service (e.g., GitHub Actions / Tekton Chains / Google Cloud Build) whose control plane: *not* the user's build script!: generates a signed `in-toto` v1.0 Attestation Statement (`slsa.dev/provenance/v1` [156, 158]) recording the exact upstream Git repository URI, immutable `gitCommit` SHA-1/SHA-256 digest, build workflow `.yml` hash, and output artifact SHA-256! To sign that attestation without stealable static private keys, `Sigstore` (`cosign` [157]) exchanges the CI runner's short-lived OIDC identity token with the `Fulcio` Certificate Authority for an ephemeral X.509 code-signing certificate valid for just 10 minutes (embedding the exact OIDC workflow URI in an X.509 SAN extension!), signs the artifact + `SLSA` provenance, and appends the signature, certificate, and timestamp permanently into `Rekor`, a globally replicated, append-only RFC 6962 Merkle Tree Transparency Log [157]! Even if an attacker compromises a maintainer account or CI workflow, they *cannot* sign a targeted single-victim backdoor in secret without publishing an indelible, globally searchable cryptographic receipt in `Rekor`!

## Distro, Immutable-OS, & Cloud Trade-Offs

Across the Linux landscape, supply-chain hardening now separates legacy vs. modern artifact pipelines: `Arch Linux` and `Debian` operate public `rebuilderd` fleets flagging any `.deb`/`.pkg.tar.zst` hash drift; `Fedora`/`RHEL` (`bootc`) and `SUSE` decouple `libsystemd` via `dlopen()` and sign container/OS manifests; `Talos Linux` (`Sidero Labs`), `Bottlerocket`, and `Chainguard Wolfi` publish `Sigstore` `cosign` signatures + `SLSA` provenance + `SBOM` (`SPDX`/`CycloneDX`) bundles verifiable via `cosign verify-attestation` directly inside CI and Kubernetes admission controllers [34, 155, 156, 157]. Note, however, what *even* `SLSA` L3 + `Sigstore` + Reproducible Builds cannot automate away: human code review of binary blobs and complex C build systems (`bad-3-corrupt_lzma2.xz` was committed to Git!). Banning binary test blobs from source trees, migrating foundational compression/parsing libraries from C to memory-safe Rust (`lzma-rs`, `zlib-rs`, `sudo-rs`, `uutils`, `rustls`: where `STT_GNU_IFUNC` C tricks and buffer overflows are statically rejected under `#![forbid(unsafe_code)]`!), and sustaining multi-maintainer governance complete the human side of the trust chain [56, 153].

### Closing Synthesis: The Complete Linux Trust Chain

Step back and survey the unbroken architectural spine we have traced from power-on reset to upstream Git commit across these twenty chapters. On a fully realized modern Linux platform, no layer asks its successor or consumer for blind faith: silicon fuses (`Boot Guard` / `PSB`) and `UEFI` + `SBAT` (`Chapter 1`) verify an atomic `Unified Kernel Image` (`Chapter 2`) whose `systemd-stub` extends phase-locked measurements into `TPM 2.0` `PCR[11]` (or `COCONUT-SVSM`'s `VMPL0` `vTPM` inside an `AMD SEV-SNP` / `Intel TDX` enclave in `Chapter 18`), unsealing `LUKS2` storage keys (`Chapter 3`) strictly during `enter-initrd` under `systemd-pcrlock` policies while pinning `/usr` and `systemd-sysext` overlays to `dm-verity` and `fs-verity` Merkle trees enforced at runtime by `IPE` and attested continuously by `Keylime` (`Chapter 4`). Inside Ring 0, `Kernel Lockdown` (`Chapter 5`), `FineIBT`/`KCFI`, hardware Shadow Stacks, `SLAB_VIRTUAL`, and `Rust-for-Linux` (`Chapter 6`) defend kernel integrity against both `UID 0` and memory corruption, while stacked `LSMs` (`SELinux`, `AppArmor`, unprivileged `Landlock` `ABI v7` in `Chapter 7`) and inline `LSM-BPF` (`Chapter 8`) mediate every resolved VFS and socket object. Above Ring 0, restricted `user_namespaces` (`Chapter 9`), `SUID`-free `systemd` `run0` (`Chapter 10`), `DynamicUser` + `pidfd`-authenticated IPC (`Chapter 11`), `ramfs`-backed `systemd-creds` + `tpm2-pkcs11` (`Chapter 12`), and short-lived OpenSSH + `FIDO2` certificates (`Chapter 13`) harden userspace, scaling outward into `gVisor` and `Firecracker` micro-VMs (`Chapters 14`–`15`), `IMDSv2` + `SPIFFE`/`SPIRE` workload mTLS (`Chapter 16`), zero-key AI agent sandboxes behind credential-injecting proxies (`Chapter 17`), per-pod `Confidential Containers` attested by `Trustee` (`Chapter 19`), and reproducible, `SLSA`-attested, `Rekor`-logged open-source builds (`Chapter 20`). Linux's greatest historical vulnerability: that independent open-source primitives left unverified gaps at every seam: becomes, once each seam is explicitly engineered and measured, its greatest architectural strength: every single link in the chain is open, inspectable, replaceable, and verifiable on a live machine.

## Inspecting on a Live Linux Host

Verify on a live Linux host that `sshd` no longer transitively maps `liblzma.so.5` (`CVE-2024-3094` structural decoupling check: modern hardened distros return zero matches!):

```bash
ldd /usr/sbin/sshd 2>/dev/null | grep -E "liblzma|libsystemd" || echo "Clean: sshd does not link liblzma via DT_NEEDED"
```

Inspect `libsystemd.so.0`'s direct `DT_NEEDED` ELF shared-library headers (`readelf -d`) to confirm compression libraries (`liblzma`, `libzstd`, `liblz4`) were moved to on-demand `dlopen()`:

```bash
readelf -d /usr/lib*/libsystemd.so.0 2>/dev/null | grep "(NEEDED)" || objdump -p /lib/*/libsystemd.so.0 2>/dev/null | grep "NEEDED"
```

Check `xz` version (`5.6.0` and `5.6.1` were the sole affected upstream releases) and verify `cosign` / `SOURCE_DATE_EPOCH` tooling availability:

```bash
xz --version | head -n 2
command -v cosign slsa-verifier 2>/dev/null || true
```
