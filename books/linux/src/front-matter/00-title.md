# The Linux Trust Chain

## From UEFI, Unified Kernel Images, and dm-verity Through LSMs, eBPF, and Containers to Confidential Cloud

**Parag Mali**

[Download the Complete PDF Edition (the-linux-trust-chain.pdf)](../the-linux-trust-chain.pdf)

---

Unlike Windows or Apple platforms, Linux has no single vendor root key, no monolithic userland, and no single deployment shape: the same kernel family powers developer workstations, immutable `ostree` and `systemd-sysext` appliances, hyperscale `Kubernetes` worker nodes, autonomous AI code-execution sandboxes, and `AMD SEV-SNP` or `Intel TDX` confidential cloud guests [1, 2, 3, 4]. Historically, that modularity left an unverified chasm across early boot and runtime administration: `UEFI` verified `shim.efi` and `vmlinuz`, while an unauthenticated `initramfs` CPIO archive, mutable `/etc` configuration, `SUID-root` binaries, and unconstrained `UID 0` processes allowed attackers to subvert execution without breaking a single cryptographic primitive [2, 5, 6]. *The Linux Trust Chain* traces how modern Linux closes each of those integration seams end to end, from `SBAT` generation revocations and signed `Unified Kernel Images` (`UKIs`) measured into `TPM 2.0` `PCR[11]` through `LUKS2`, `dm-verity`, `IPE`, `Kernel Lockdown`, Rust driver boundaries, stacked `LSMs` (`SELinux`, `AppArmor`, and `Landlock`), `eBPF` runtime mediation, `systemd` `run0`, `gVisor` and `Firecracker` sandboxes, `SPIFFE`/`SPIRE` workload identity, `COCONUT-SVSM` confidential paravisors, and `SLSA`/`Sigstore` supply-chain provenance [7, 8, 9, 10, 11, 12].
