# Block and File Integrity: LUKS2, dm-verity, and fs-verity

## Overview

* **Link in the Chain:** Anchors persistent storage immediately after `UKI` and `TPM 2.0` `PCR[11]` early-boot verification ([Chapter 2](02-uki-systemd-pcrlock.md)), providing confidential read-write volumes (`LUKS2`) alongside cryptographically tamper-proof OS trees and files (`dm-verity`, `systemd-sysext`, `fs-verity`).
* **Core Security Invariant:** `LUKS2` protects volume master keys under memory-hard `Argon2id` or `TPM2` keyslots (and detects offline ciphertext tampering only when paired with `dm-integrity` AEAD), while `dm-verity` and `fs-verity` verify every $4\text{ KiB}$ page read on demand against a SHA-256/SHA-512 Merkle tree whose root digest is pinned to a signed `UKI` or kernel keyring certificate before mapping bytes into page cache.
* **Deployment Profile Matrix:** Mutable enterprise distros deploy `LUKS2` (`aes-xts-plain64` without AEAD) over mutable `ext4`/`XFS`/`btrfs` roots; immutable container OSes (`Flatcar`, `Talos`, `Bottlerocket`, `Fedora CoreOS` `composefs`) mount `/usr` (or `/`) read-only over `dm-verity` or `fs-verity` extended by signed `systemd-sysext` images; cloud workloads combine EBS/PD encryption with `dm-verity` root partitions.
* **Trusted Computing Base (TCB):** Linux kernel device-mapper (`dm-crypt`, `dm-integrity`, `dm-verity`), VFS `fs/verity/` subsystem, crypto API (`AES-XTS`, `AEGIS-128`, `ChaCha20-Poly1305`, `SHA-256`), `UKI`-supplied `roothash=` or `.builtin_trusted_keys` / `.secondary_trusted_keys`, and `systemd-gpt-auto-generator` / `systemd-sysext`.
* **Integration Seam & Handoff:** Guarantees block- and inode-level cryptographic integrity for `/usr` and verified files; delegates mandatory execution policy ("refuse `execve` / `mmap(PROT_EXEC)` on any file lacking verity provenance") and remote fleet attestation to `IPE` and `Keylime` in [Chapter 4](04-ima-ipe-keylime.md).

## Problem Statement & Threat Model

Ask ten systems administrators whether `LUKS` full-disk encryption prevents an offline attacker from modifying `/bin/bash` on a powered-off laptop, and nine will answer yes. Under default `cryptsetup` settings, that intuition is dangerously incomplete [27, 29]. Standard disk encryption (`dm-crypt` in `aes-xts-plain64` mode) is a length-preserving *confidentiality* primitive, not an authenticated encryption (`AEAD`) scheme: every 512-byte or 4096-byte disk sector on the raw NVMe drive maps to an identically sized ciphertext sector with zero space reserved for a Message Authentication Code (`MAC`) tag [27, 29]. While an offline Evil Maid adversary who lacks the `LUKS2` master key cannot *read* plaintext sectors, `XTS-AES` operates on independent 16-byte cipher blocks tweaked by the sector index. Flipping bits inside a 16-byte ciphertext block deterministically scrambles only the corresponding 16-byte plaintext block (corrupting specific configuration lines, zeroing flags, or crashing security services), and replaying a previously captured ciphertext sector back to the same Logical Block Address (`LBA`) restores stale data cleanly without `dm-crypt` ever raising an I/O error [29].

Furthermore, encryption and integrity solve orthogonal security problems across an operating system's storage layout [10]. User home directories (`/home`) and mutable service state (`/var`) contain private data that changes every millisecond and therefore require *confidentiality* (ideally paired with integrity). Conversely, the operating system code tree itself (`/usr`, containing the dynamic linker, `glibc`, `systemd`, `sshd`, Python runtimes, and shared libraries) contains zero secret bytes, because its exact binaries are publicly downloadable from upstream mirrors! Encrypting `/usr` inside a single read-write `ext4` volume alongside `/var` fails to distinguish immutable vendor code from mutable runtime state: if a single transient root exploit modifies `/usr/lib64/libc.so.6` while the system is booted and unlocked, `LUKS2` dutifully *encrypts the attacker's backdoor* to disk and serves it back cleanly on every subsequent boot forever [10, 30].

Modern Linux storage architecture addresses an adversary with offline physical access to raw block storage, storage-network (`iSCSI`/`NVMe-oF`/cloud-snapshot) write access, or transient userspace compromise seeking persistent OS modification. Defending against both offline tampering and persistent OS drift requires splitting the storage stack cleanly: hardening mutable data partitions with `LUKS2` `Argon2id` key derivation and optional `dm-integrity` `AEAD` authentication, pinning immutable `/usr` partitions and composable OS extensions (`systemd-sysext`) to `dm-verity` block-level Merkle trees anchored in the signed `UKI`, and bringing demand-paged Merkle verification to individual files on writable filesystems via `fs-verity` and `composefs` [10, 27, 30, 32, 33, 35].

## Kernel & Userspace Mechanics

### `LUKS2` On-Disk Architecture, `Argon2id`, and `dm-integrity` AEAD

Version 2 of the Linux Unified Key Setup (`LUKS2` [27]) replaced `LUKS1`'s rigid binary header and CPU-friendly `PBKDF2` key derivation with a dual-copy, crash-resilient 4 KiB binary header (`LUKS\xba\xbe` magic, version, header size, sequence ID, and `SHA-256` header checksum) followed by an extensible UTF-8 `JSON` metadata area (`keyslots`, `segments`, `digests`, `tokens`, `config`) and encrypted binary keyslot regions [27]. Password-protected keyslots default to `Argon2id` (`RFC 9106` [28]), a hybrid memory-hard key derivation function parameterized by memory cost $m$ (up to `1 GiB` RAM by default in `cryptsetup`), iterations $t$, and parallelism $p$. Because computing each passphrase guess requires filling and pseudo-randomly indexing a gigabyte-scale memory matrix (combining data-independent `Argon2i` passes against cache-timing side channels with data-dependent `Argon2d` passes maximizing Time-Memory Trade-Off resistance), `Argon2id` neutralizes custom ASIC and GPU cracking clusters that previously tested millions of `LUKS1` `PBKDF2-SHA256` passwords per second [27, 28]. Meanwhile, the `tokens` JSON array binds hardware keyslots cleanly to `systemd-tpm2` (`PCR[11]` + `pcrlock` from [Chapter 2](02-uki-systemd-pcrlock.md)) or `systemd-fido2` without duplicating volume master keys [24, 27].

![Figure: Architectural contrast between standard unauthenticated LUKS2 AES-XTS encryption (vulnerable to silent offline block malleability and sector replay) and authenticated LUKS2 layered over dm-integrity AEAD.](diagrams/03-luks2-aead-vs-xts.svg)

When true cryptographic tamper resistance is required on read-write block storage, `cryptsetup luksFormat --cipher aes-gcm-random --integrity aead` (or `--cipher chacha20-random --integrity poly1305`, or hardware-accelerated `aegis128-random` [27, 29]) stacks `dm-crypt` directly atop the kernel `dm-integrity` device-mapper target (`drivers/md/dm-integrity.c`) [29]. Because adding a 16-byte authentication tag to every 4096-byte data sector produces a 4112-byte physical record that no longer aligns cleanly with 4096-byte NVMe atomic block writes, `dm-integrity` maintains an interleaved metadata region paired with a crash-safe write-ahead journal: both the encrypted 4 KiB sector and its 128-bit `AEAD` tag (binding the 64-bit sector number as Additional Authenticated Data so an attacker cannot swap Sector $i$ with Sector $j$) are committed atomically to the journal before flushing in place, preventing "torn-write" tag mismatches after sudden power loss [29]. On every read `bio`, `dm-crypt` + `dm-integrity` verifies the tag in Ring 0 and returns `-EBADMSG` / `-EIO` immediately if a single bit on disk was flipped or replayed offline, trading roughly $1.5\times$ to $2\times$ write throughput (mitigated via `--integrity-no-journal` on battery-backed or copy-on-write flash where acceptable) for mathematical ciphertext integrity [27, 29].

### `dm-verity`, UAPI Discoverable Partitions, and `systemd-sysext`

For immutable `/usr` or root filesystems, write journals are unnecessary because the volume is mounted strictly read-only. Instead, `dm-verity` (`drivers/md/dm-verity-target.c`, originally developed for ChromeOS and Android Verified Boot and now foundational across server/appliance Linux [30]) constructs an offline Merkle hash tree over the filesystem image using `veritysetup format` [30]. Given $N$ data blocks $D_0, \dots, D_{N-1}$ of size $B = 4096$ bytes and a cryptographic per-image `salt` $s$, each leaf digest is computed as $h^{(0)}_i = \operatorname{SHA-256}(s \parallel D_i)$, packed 128 digests per $4\text{ KiB}$ hash block ($b = 4096 / 32 = 128$), and hashed recursively up $H = \lceil \log_{128} N \rceil$ levels until a single 32-byte `root_hash` $R$ summarizes the entire multi-gigabyte partition [30].

![Figure: Cryptographic storage composition linking the UKI-pinned roothash into dm-verity read-only /usr partitions, signed systemd-sysext EROFS/SquashFS extensions, and per-inode fs-verity Merkle trees.](diagrams/03-dm-verity-sysext-tree.svg)

How does the booting kernel find the matching data partition, hash partition, and trusted `root_hash` without relying on a mutable `/etc/fstab`? Through the UAPI Group *Discoverable Partitions Specification* (`DPS` [31]) implemented by `systemd-gpt-auto-generator`. When an image builder sets the `roothash=` (or `usrhash=`) 64-hex-character SHA-256 string inside the Authenticode-signed `UKI` `.cmdline` section ([Chapter 2](02-uki-systemd-pcrlock.md)), `DPS` splits that 256-bit `usrhash` into two 128-bit halves and encodes them directly as the GPT *Partition UUIDs* of the `/usr` data partition (GPT Type UUID `8484680c-9521-48c6-9c11-b0720656f69e` on `x86-64`) and the `/usr` `dm-verity` hash partition (`77ff5f63-e7b6-4633-acf4-1565b864c0e6`) [31]! At boot, `systemd` supports atomic A/B OS updates (`_usr_a` vs. `_usr_b`) with zero mutable configuration files: booting `uki-v2.efi` automatically discovers and mounts the exact `_usr_b` + `_verity_b` partition pair matching `usrhash_v2`, verifies the Merkle root, and triggers `DM_VERITY_MODE_RESTART` or `-EIO` if any 4 KiB page read from disk ever fails its $\le 3$-hash path check to $R$ [30, 31]. Optionally, enabling Reed-Solomon Forward Error Correction (`--fec-device`) allows `dm-verity` to self-heal accidental NAND flash bit rot while still halting on adversarial tampering [30].

What if an operator needs to layer debugging tools (`strace`, `bpftrace`), hardware vendor agents, or Kubernetes runtime updates atop an immutable `dm-verity` `/usr` without rebuilding the base OS image? `systemd-sysext(8)` (for `/usr` and `/opt`) and `systemd-confext(8)` (for `/etc`) package add-on trees as self-contained *Discoverable Disk Images* (`DDIs`: single `.raw` files containing a mini GPT table with an `EROFS` or `SquashFS` filesystem partition, a `dm-verity` hash partition, and a `verity-sig` partition holding a PKCS#7 signature over the extension's `root_hash`) [31, 32]. Before merging extensions via a read-only kernel `OverlayFS` mount over `/usr`, `systemd-sysext` verifies each DDI's PKCS#7 root-hash signature against `/etc/verity.d/*.crt` (or `.builtin_trusted_keys`) and checks `extension-release.<name>` OS-version constraints, extending active extension digests into `TPM 2.0` `PCR[13]` [21, 32].

### `fs-verity` and `composefs`: Per-File Merkle Integrity on Writable Volumes

Block-level `dm-verity` requires an entire dedicated read-only partition or loopback block device. When individual binaries, container layers, or flatpaks reside on a standard writable `ext4`, `btrfs`, or `f2fs` filesystem, Linux (`5.4+`) provides `fs-verity` (`fs/verity/` [33]). Invoking `ioctl(fd, FS_IOC_ENABLE_VERITY, &arg)` on a regular file computes a per-file $4\text{ KiB}$-block SHA-256 or SHA-512 Merkle tree stored in hidden filesystem metadata beyond logical `i_size` (for example past the last extent in `ext4` or inside `btrfs` B-tree items) and sets the immutable `S_VERITY` (`FS_VERITY_FL`) inode flag [33]. Once enabled, the kernel permanently forbids opening the file for writing or truncating it (though `unlink()` and `rename()` remain permitted so packages can be upgraded cleanly!), verifies every demand-paged $4\text{ KiB}$ read via `fsverity_verify_folio()` before marking the page `Uptodate` in page cache, and optionally validates an embedded PKCS#7 signature (`FS_IOC_ENABLE_VERITY` `sig_ptr`) against the `.fs-verity` kernel keyring (`CONFIG_FS_VERITY_BUILTIN_SIGNATURES`) [33].

Projects such as `composefs` (used in `Fedora CoreOS` / `bootc` and `containers/storage` [35]) combine a tiny `fs-verity`-protected `EROFS` metadata image (recording directory trees, permissions, xattrs, and expected 32-byte `fs-verity` digests of every backing file) with a shared content-addressed object store (`/ostree/repo/objects/`). When `composefs` mounts an OS deployment or container rootfs, the kernel verifies the top-level `EROFS` image's `fs-verity` digest first, and on every file open inside the mount verifies that the backing object's kernel-computed `fs-verity` digest matches the exact digest recorded in the `EROFS` inode, delivering full `dm-verity`-grade tamper resistance with zero block duplication across dozens of versions or container images [33, 35].

## Distro, Immutable-OS, & Cloud Trade-Offs

Mutable distributions (`Ubuntu`, `RHEL`, `Debian`) prioritize in-place `apt`/`dnf` mutability and write throughput, defaulting to `LUKS2` `aes-xts-plain64` without `dm-integrity` (avoiding the ~40% IOPS overhead of journaled AEAD) and leaving `/usr` writable; such hosts can still adopt `fs-verity` selectively for critical binaries or container stores [27, 33]. Conversely, purpose-built cloud and Kubernetes node OSes (`Talos Linux`, `AWS Bottlerocket`, `Flatcar Container Linux`, `Azure Linux` immutable profiles) partition the disk into dual A/B read-only `dm-verity` OS slots (~1-2 GiB `EROFS`/`SquashFS`) paired with an ephemeral `LUKS2`-encrypted `/var` data partition wiped or re-keyed via `systemd-repart` on boot [31, 34, 35]. In `Bottlerocket` and `Talos`, even if a container escapes to host `UID 0`, `/usr` is backed by `dm-verity` in `DM_VERITY_MODE_RESTART` (rebooting immediately on raw block corruption) and `Kernel Lockdown` blocks raw device writes to the active backing partition ([Chapter 5](05-kernel-lockdown-modules.md)) [34, 44].

## Seam Failures, CVEs, & Structural Bounds

Storage-integrity failures cluster wherever operators assume unauthenticated encryption detects tampering, leave `roothash` outside signed UKI command lines, or mount writable overlays (`OverlayFS` / `/var`) with `exec` permissions that bypass `/usr` verification.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| `LUKS1` Weak `PBKDF2` Cracking & Header Tampering (`CVE-2016-4484` / offline GPU) | 2016-2021 | `LUKS1` header & `PBKDF2` | CPU-only `PBKDF2` resists GPU clusters and JSON/cipher mode cannot be downgraded | Offline attacker cracks low-entropy passphrases on GPUs or mutates unauthenticated cipher header fields | Upgrade to `LUKS2` (`Argon2id` 1 GiB RAM + authenticated JSON checksums + `TPM2` PIN) [27, 28] |
| `XTS-AES` Evil-Maid Block Malleability & Replay | 2018-2025 | Plain `dm-crypt` `aes-xts-plain64` | Disk encryption implies ciphertext integrity | Offline attacker replays old sectors or flips 16-byte cipher blocks to corrupt configs / inject payloads | Pair `LUKS2` with `--integrity aead` (`dm-integrity`) or put OS code on `dm-verity` [29, 30] |
| Unpinned `dm-verity` `roothash` Substitution | 2020-2023 | Split `GRUB2` + `dm-verity` | `dm-verity` protects `/usr` even when `grub.cfg` is unsigned | Attacker modifies `/usr` Partition, recomputes Merkle tree, and updates `roothash=` in unsigned `grub.cfg` | Embed `roothash=` inside Authenticode-signed `UKI` `.cmdline` or require PKCS#7 `root_hash_sig` [19, 30] |
| `OverlayFS` / `/var` Writable Execution Bypass | 2021-2025 | `dm-verity` `/usr` without `IPE` / `noexec` | Read-only `/usr` alone stops untrusted binary execution | Post-exploitation root writes rogue ELF payload into writable `/tmp`, `/var`, or `memfd_create()` and calls `execve()` | Mount writable data volumes `noexec,nosuid,nodev` and enforce Linux 6.12+ `IPE` LSM ([Chapter 4](04-ima-ipe-keylime.md)) [38] |
| `CVE-2023-2002` / Kernel `fs-verity` Descriptor Races | 2022-2023 | Early filesystem `fs-verity` implementations | Concurrent page cache / descriptor reads cannot observe partial state | Edge-case race conditions during `FS_IOC_ENABLE_VERITY` error paths in specific filesystems | Keep LTS kernel current (`6.6+` / `6.12+`) where `fsverity_info` publication is strictly atomic [33] |

Notice the crucial architectural boundary revealed by Row 4: *`dm-verity` and `fs-verity` are storage integrity primitives, not system-wide execution policies*. Mounting `/usr` over `dm-verity` guarantees that `/usr/bin/sshd` has not changed by a single bit, yet nothing in `dm-verity` stops a compromised service from downloading an unsigned binary into `/dev/shm` or `/var/tmp` and invoking `execve()` or `dlopen()` on it! Enforcing that *only* `dm-verity`- or `fs-verity`-verified code may ever be mapped executable (`PROT_EXEC`) requires coupling storage verity to a mandatory access control execution gate ([Chapter 4](04-ima-ipe-keylime.md)).

## Inspecting on a Live Linux Host

Inspect active device-mapper targets (`crypt`, `verity`, `integrity`) and verify cipher modes and `dm-verity` corruption-handling flags (`restart_on_corruption`):

```bash
lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINTS,RO
# Requires CAP_SYS_ADMIN (root / run0) to query device-mapper table parameters
dmsetup status 2>/dev/null
```

Examine `LUKS2` keyslot KDF parameters (`argon2id`, memory cost, and integrity metadata if configured) on an encrypted partition:

```bash
cryptsetup luksDump /dev/nvme0n1p3 2>/dev/null | grep -A 8 -E "Keyslots:|Memory:|Digests:|Tokens:"
```

Check `systemd-sysext` and `systemd-confext` immutable extension status and verify `fs-verity` digests on individual files where `fsverity-utils` is installed:

```bash
systemd-sysext status 2>/dev/null
fsverity measure /usr/bin/bash 2>/dev/null || lsattr -d /usr/bin/bash 2>/dev/null
```
