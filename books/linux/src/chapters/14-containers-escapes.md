# Shared-Kernel Containers: Namespaces, cgroups v2, seccomp, and Escapes

## Overview

* **Link in the Chain:** Opens Part IV by deconstructing Open Container Initiative (`OCI`) Linux containers (`containerd`, `CRI-O`, `Docker`, `Podman` backed by `runc` or `crun`), showing how eight kernel namespaces, `pivot_root`, `cgroups v2`, capabilities, LSMs, and `seccomp-BPF` compose into workload boundaries and where shared-kernel assumptions break.
* **Core Security Invariant:** A containerized process executes inside isolated namespaces (`mnt`, `pid`, `net`, `ipc`, `uts`, `user`, `cgroup`, `time`), a `pivot_root(2)` detached rootfs, `cgroups v2` resource and `BPF_PROG_TYPE_CGROUP_DEVICE` limits, dropped capabilities, stacked `SELinux`/`AppArmor` labels, and a `seccomp-BPF` filter, while `runc`/`crun` opens container paths strictly via `openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS)` from `F_SEAL_WRITE` `memfd` binaries with zero leaked host descriptors.
* **Deployment Profile Matrix:** Default Docker/`containerd` runs containers as host-mapped `UID 0` (`hostUsers: true`) retaining 14 capabilities and ~300+ open syscalls; hardened Kubernetes (`PodSecurity` `restricted`) mandates `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: ["ALL"]`, and `RuntimeDefault` `seccomp`, reinforced by `hostUsers: false` User Namespaces (`KEP-127`) and `SELinux` `sVirt` MCS labels.
* **Trusted Computing Base (TCB):** The *entire reachable host Linux kernel* (~300+ allowed syscalls, VFS, `OverlayFS`, network stack, slab allocator), `containerd-shim-runc-v2`, `runc` or `crun` initialization binaries, and host `SELinux` `container_t` or `AppArmor` policy.
* **Integration Seam & Handoff:** Delivers sub-second, zero-hypervisor packaging for trusted or semi-trusted microservices, yet leaves every tenant sharing a single Ring 0 kernel; motivates user-space kernels (`gVisor`) and hardware `KVM` micro-VMs (`Firecracker`, `Kata`) for untrusted code in [Chapter 15](15-gvisor-microvms.md).

## Problem Statement & Threat Model

Search the entire Linux kernel source tree for `struct container` and you will find nothing [15, 415]. Unlike Solaris Zones, FreeBSD Jails, or hardware virtual machines, a Linux "container" is a userspace orchestration convention codified by the Open Container Initiative (`OCI` Runtime Specification [15]). When `kubelet` schedules a pod via the Container Runtime Interface (`CRI`), `containerd` spawns a lightweight per-pod `containerd-shim-runc-v2` supervisor process, which invokes `runc` (Go `libcontainer` [416]) or `crun` (low-memory C [417]) to configure namespaces, mounts, `cgroups`, capabilities, LSM labels, and `seccomp` inside a child process (`runc init`) before calling `execve()` on the container entrypoint and exiting so only the tiny `shim` remains as parent [416, 418]. Because every container on a 128-core Kubernetes node executes system calls directly against the *exact same host Ring 0 Linux kernel*, Daniel Walsh's dictum *containers do not contain* expresses a literal architectural fact whenever workloads are hostile [15, 16, 63].

Under a post-RCE or untrusted-tenant threat model (a compromised web microservice, a public CI build runner, or a malicious `Dockerfile` submitted to an image builder), adversaries attack three distinct seams to escape onto the underlying worker node [25, 78, 419, 420]:
First, *operator privilege anti-patterns* (`--privileged`, `CAP_SYS_ADMIN`, `CAP_DAC_READ_SEARCH`, `CAP_NET_RAW`, `/var/run/docker.sock` or host `/` bind mounts, `hostPID: true`, `hostNetwork: true`), which intentionally dismantle isolation primitives and hand the container trivial four-line host root execution [420, 421]. Second, *shared-kernel Ring 0 vulnerabilities*: even under Moby/`containerd`'s default `seccomp` profile (which blocks roughly 44 dangerous syscalls [390, 422]), more than 300 complex C system calls remain directly exposed to every container thread! Any memory-corruption bug in `pipe` page-cache splicing (`Dirty Pipe` `CVE-2022-0847` [306]), `fs_context` parameter parsing (`CVE-2022-0185` [423]), `AF_PACKET` ring buffers (`CVE-2020-14386` [424]), `io_uring` (`kCTF` [63]), or `cgroup` v1 upcalls (`CVE-2022-0492` [419]) elevates the container straight to host Ring 0. Third, *runtime namespace-crossing leaks* (`runc` `CVE-2019-5736` [78], `CVE-2023-27561` [425], `kubectl cp` `CVE-2019-1002101` [426], and Snyk's `Leaky Vessels` `CVE-2024-21626` + BuildKit races `CVE-2024-23651`-`23653` [25, 427]): during container creation or `kubectl exec`, a host-privileged runtime process must enter the container's namespaces while momentarily holding references to its own host binary or host `/sys/fs/cgroup` file descriptors, creating a perilous cross-domain seam where `/proc/self/exe` and `/proc/self/fd/<N>` magic links let the container reach back onto the host root filesystem!

## Kernel & Userspace Mechanics

### OCI Lifecycle (`containerd-shim-runc-v2` to `runc`), the 8 Namespaces, and Why `pivot_root` Beats `chroot`

When `containerd-shim-runc-v2` invokes `runc create` on an unpacked OCI bundle (`rootfs/` + `config.json` [15, 418]), `runc` constructs the workload boundary across five sequential Ring 0 layers before executing the first instruction of user code:

![Figure: Internal composition of a shared-kernel OCI container across 8 Linux namespaces, pivot_root, cgroups v2, dropped capabilities, and seccomp-BPF above a single shared host Ring 0 kernel.](diagrams/14-oci-container-primitives.svg)

First, *8 Linux Namespaces (`struct nsproxy`, `namespaces(7)`)* partition which kernel identifier tables the task can observe [15, 22, 415]: `mnt` (`CLONE_NEWNS`) isolates the VFS mount graph; `pid` (`CLONE_NEWPID`) gives the container an isolated PID `1` tree; `net` (`CLONE_NEWNET`) creates an independent network stack (`lo`, routing tables, `nf_tables` hooks, and a `veth` pair wired into Cilium/Calico); `ipc` (`CLONE_NEWIPC`) isolates SysV IPC and POSIX message queues; `uts` (`CLONE_NEWUTS`) isolates `nodename` and `domainname`; `cgroup` (`CLONE_NEWCGROUP`) virtualizes `/proc/self/cgroup` relative to the container's sub-root; `time` (`CLONE_NEWTIME`, Linux `5.6+`) virtualizes `CLOCK_MONOTONIC` and `CLOCK_BOOTTIME` offsets; and `user` (`CLONE_NEWUSER` [22]) maps container `UID 0` (`root` inside the image) onto an unprivileged high host `kuid_t` (such as `165536..231071`, paired with Linux `5.12+` `MOUNT_ATTR_IDMAP` idmapped volume mounts [364, 428]) so any file-level breakout lands on the host node as unprivileged `UID 165536` rather than host `UID 0`!

Second, *why `pivot_root(2)` beats `chroot(2)`* (`fs/namespace.c` [15, 429]). Novice sandbox builders often reach for `chroot("/var/container/rootfs")`, unaware that `chroot(2)` was never designed as a security boundary against `UID 0`! Calling `chroot()` overwrites only `current->fs->root` while leaving two escape hatches wide open: the outer host `/` mount remains attached in the process's mount table, and `chroot()` intentionally *does not move `current->fs->pwd`* (current working directory)! Any process inside a `chroot` holding `CAP_SYS_CHROOT` trivially escapes in four syscalls: `fd = open(".", O_RDONLY); mkdir("sub", 0755); chroot("sub"); fchdir(fd);` (placing `pwd` *outside and above* `current->fs->root`, where kernel `..` root-clamping checks `dentry == fs->root` and never triggers!), walking `chdir("../../../../..")` to the real host root and calling `chroot(".")` [429]!

OCI runtimes (`runc` and `crun` [416, 417]) close this escape structurally via `pivot_root(2)` inside `CLONE_NEWNS` [15, 429]: after setting mount propagation to `MS_SLAVE | MS_REC` and bind-mounting `rootfs` onto itself, `runc` `chdir()`s into `new_root`, executes `syscall(SYS_pivot_root, ".", ".")` to swap the *mount namespace's root mount* with `new_root` while stacking the old host root underneath `.`, and immediately calls `umount2(".", MNT_DETACH)`! Once `umount2` detaches the old root mount, the host's `/` mount tree ceases to exist inside the container's `mnt_namespace` [429]. Before handing off to user code, `runc` also masks sensitive procfs and sysfs leaks inside the container (`maskedPaths` and `readonlyPaths` in `config.json` [15]), bind-mounting `/dev/null` over `/proc/kcore`, `/proc/keys`, `/proc/timer_list`, `/proc/sched_debug`, and `/proc/acpi` while mounting read-only `tmpfs` over `/sys/firmware` and `/proc/scsi` (and hardening `/proc`/`/sys` destination walks against symlink races `CVE-2019-19921` and `CVE-2023-27561` [425]).

### Unified `cgroups v2` and the eBPF Device Controller (`BPF_PROG_TYPE_CGROUP_DEVICE`)

Namespaces bound *visibility*; Control Groups (`cgroups v2`, `Documentation/admin-guide/cgroup-v2.rst` [430]) bound *consumption and raw device access*. Legacy `cgroup` v1 fractured resource controllers (`cpu`, `memory`, `blkio`, `pids`, `devices`, `rdma`) across a dozen orthogonal mount trees where a single thread could belong to completely unrelated slices in different controllers, breaking page-cache writeback accounting and exposing dangerous root upcall hooks such as `release_agent` [419, 430].

Unified `cgroups v2` organizes every pod and container into a single strict hierarchy (`/sys/fs/cgroup/kubepods.slice/kubepods-burstable.slice/...`), enforcing the *no-internal-process* invariant (processes live exclusively in leaf cgroups while interior nodes distribute budgets) [430]. Four controller files stop container Denial-of-Service attacks in Ring 0: `memory.max` and `memory.swap.max` isolate container OOM kills before pod memory spikes trigger the host-wide OOM killer; `cpu.max` enforces CFS bandwidth quotas; `io.max` throttles per-device read/write MB/s and IOPS; and `pids.max` caps total `task_struct` allocations inside the pod, stopping a container `:(){ :|:& };:` fork bomb before it exhausts global host `kernel.pid_max` [430]!

Crucially, `cgroups v2` deleted the legacy text-based `/sys/fs/cgroup/devices/devices.allow` controller completely, replacing it with an inline eBPF hook: `BPF_PROG_TYPE_CGROUP_DEVICE` (`Documentation/bpf/prog_cgroup_dev.rst` [431]). During `runc create`, `runc` synthesizes and loads a compact eBPF bytecode filter attached directly to the container's cgroup FD (`BPF_CGROUP_DEVICE`). Whenever any thread in that cgroup invokes `open()`, `mknod()`, or `blkdev_get()` on a character or block inode, Ring 0 executes the eBPF filter against `struct bpf_cgroup_dev_ctx { __u32 access_type; __u32 major; __u32 minor; }`, allowing safe virtual majors (`1:3` `/dev/null`, `1:5` `/dev/zero`, `1:8` `/dev/random`, `1:9` `/dev/urandom`, `5:0` `/dev/tty`, `136:*` `/dev/pts/*`) and returning `0` (`-EPERM`) on raw host disk majors (`259:*` NVMe, `8:*` SCSI, `1:1` `/dev/mem`, `10:237` `/dev/loop-control`) even if a root process inside the container runs `mknod` [430, 431]!

### Default Moby `seccomp-BPF`, *Shocker* (`open_by_handle_at`), and `SECCOMP_RET_USER_NOTIF` `TOCTOU`

After applying `SELinux` Multi-Category Security (`container_t:s0:c124,c589` so Container A cannot read Container B's files even if VFS breaks [265]) or `docker-default` `AppArmor` confinement and dropping Linux capabilities down to the 14-capability OCI default (or `drop: ["ALL"]` + `PR_SET_NO_NEW_PRIVS` under hardened specs, noting that default OCI retains `CAP_NET_RAW`, which enabled `AF_PACKET` `TPACKET_V3` kernel heap overflow `CVE-2020-14386` until dropped! [424]), `runc` installs the container's `seccomp-BPF` filter (`seccomp/default.json` in `moby/profiles` [104, 390, 422]).

Designed as a default-deny allowlist (`defaultAction: SCMP_ACT_ERRNO` returning `EPERM`), Moby's default profile allows ~300+ standard application syscalls on validated native architectures (`SCMP_ARCH_X86_64`, `SCMP_ARCH_AARCH64`) while denying roughly 44 high-risk syscalls outright (or gating them behind host capabilities stripped from unprivileged containers) [390, 422]: `kexec_load`, `kexec_file_load`, `init_module`, `finit_module`, `delete_module`, `reboot`, `swapon`, `swapoff`, `acct`, `mount`, `umount2`, `pivot_root`, `fsopen`, `fsmount`, `move_mount`, `bpf`, `keyctl`, `add_key`, `request_key`, `userfaultfd` (infamous for deterministically freezing kernel `copy_from_user()` page faults mid-race during slab UAF exploits!), `perf_event_open`, `lookup_dcookie`, `ioperm`, `iopl`, `clock_settime`, `unshare`, `setns`, `clone`/`clone3` with namespace flags, modern `io_uring_setup` (`kCTF` [63]), and *most famously* `open_by_handle_at(2)` [421, 422, 432]!

Why does `open_by_handle_at(2)` appear on every container security engineer's memorization list? In June 2014, Sebastian Krahmer (`stealth`) published `shocker.c` (*Shocker* [421]), the canonical first Docker (`0.11`) breakout! Originally added for user-space NFS servers, `name_to_handle_at(2)` and `open_by_handle_at(int mount_fd, struct file_handle *handle, int flags)` [432] resolve files directly by *underlying filesystem inode number and generation* rather than walking VFS directory paths! Inside every standard Docker container, `/etc/resolv.conf`, `/etc/hostname`, and `/etc/hosts` are bind-mounted single files from `/var/lib/docker/containers/<id>/` residing directly on the *host's root ext4 or XFS filesystem*. Because Docker `0.11` retained `CAP_DAC_READ_SEARCH` inside containers, `shocker.c` simply opened `/etc/hosts` inside the container as `mount_fd`, constructed an 8-byte `struct file_handle` encoding inode `2` (the fixed root directory inode `/` on ext4/XFS!), and called `open_by_handle_at(mount_fd, &root_fh, O_RDONLY)`, receiving an open file descriptor to the *host's real `/` root directory* completely outside `pivot_root` [421, 432]! Docker `1.0` immediately stripped `CAP_DAC_READ_SEARCH` from the default capability set and blocked `open_by_handle_at` in `seccomp/default.json` [421, 422].

What when advanced runtimes (`Sysbox`, `LXD`/`Incus`, `crun`) use `SECCOMP_RET_USER_NOTIF` (`seccomp_unotify(2)`, Linux `5.0+` [104, 433, 434]) to trap `mount()` or `mknod()` to a privileged host supervisor process over a notification FD? Both `seccomp_unotify(2)` [433] and Christian Brauner's engineering notes [434] highlight two subtle `TOCTOU` traps because `struct seccomp_notif` passes only raw 64-bit register values (`args[0..5]`), *never* snapshotted userspace memory buffers:
First, *PID/TID reuse on `/proc/<tid>/mem`*: if the container thread triggers `SECCOMP_IOCTL_NOTIF_RECV` (`req.pid` + 64-bit unique cookie `req.id`) and immediately exits while a host daemon reuses numeric `req.pid`, a naive supervisor opening `/proc/<req.pid>/mem` reads a host process's memory! Every supervisor *must* open `/proc/<req.pid>/mem` first and *then* invoke `ioctl(notif_fd, SECCOMP_IOCTL_NOTIF_ID_VALID, &req.id)` to verify in Ring 0 that the original trapped thread is still alive and blocked on `req.id` before reading a single byte [433]:

```c
/* Race-free seccomp_unotify supervisor cookie check + atomic FD injection */
int mem_fd = open(proc_tid_mem_path, O_RDONLY | O_CLOEXEC);
if (ioctl(notif_fd, SECCOMP_IOCTL_NOTIF_ID_VALID, &req.id) < 0) {
    close(mem_fd); /* Target exited & TID may have wrapped; abort immediately! */
    return -ENOENT;
}
pread(mem_fd, local_buf, sizeof(local_buf), req.data.args[0]);
/* Validate local_buf in supervisor RAM, open safe_fd, and inject atomically: */
struct seccomp_notif_addfd addfd = {
    .id = req.id, .flags = SECCOMP_ADDFD_FLAG_SEND, .srcfd = safe_fd,
};
ioctl(notif_fd, SECCOMP_IOCTL_NOTIF_ADDFD, &addfd);
```

Second, *sibling-thread pointer mutation*: even while thread A stays blocked in `SECCOMP_RET_USER_NOTIF`, sibling thread B inside the same container address space can overwrite the string at `args[0]` *after* the supervisor validates `/proc/<tid>/mem` and *before* the kernel executes `SECCOMP_USER_NOTIF_FLAG_CONTINUE`! Safe `seccomp_unotify` supervisors therefore *never* pass `SECCOMP_USER_NOTIF_FLAG_CONTINUE` on pointer-bearing syscalls; instead, as shown above, the supervisor copies the bytes once into its own private RAM (`local_buf`), performs the validated operation itself, and injects the resulting file descriptor atomically into the container via `SECCOMP_IOCTL_NOTIF_ADDFD` with `SECCOMP_ADDFD_FLAG_SEND` [104, 433, 434]!

### Canonical Container Escape Anatomy: `--privileged` & `release_agent` (`CVE-2022-0492`), `runc` `/proc/self/exe` (`CVE-2019-5736`), and *Leaky Vessels* (`CVE-2024-21626`)

Trace the three landmark escapes that define container breakout mechanics in production incident response:

First, *`--privileged` and the 4-line `cgroup` v1 `release_agent` breakout (`CVE-2022-0492`)* [419, 420]. Passing `docker run --privileged` (or `securityContext.privileged: true` in Kubernetes) grants all 41 Linux capabilities, disables `seccomp` and `AppArmor`/`SELinux` (`spc_t`), and exposes every host `/dev` node (`mount /dev/nvme0n1p1 /mnt` immediately mounts the host OS disk!). Even when `/dev` is restricted (for example, granting `CAP_SYS_ADMIN` alone without `--privileged`, or exploiting `CVE-2022-0492` [419] where `kernel/cgroup/cgroup-v1.c` `release_agent_write()` checked `capable(CAP_SYS_ADMIN)` instead of `ns_capable(&init_user_ns, CAP_SYS_ADMIN)` so any container lacking `AppArmor`/`SELinux` could `unshare -UrmC` into a user + cgroup namespace!), Felix Wilhelm's classic 4-line `release_agent` PoC achieves instant host root RCE [419, 420]:

![Figure: Four-step execution trace of Felix Wilhelm's cgroup v1 release_agent container escape (CVE-2022-0492), showing OverlayFS upperdir host-path discovery in /etc/mtab and Ring 0 call_usermodehelper() execution in init_pid_ns, alongside cgroups v2's structural fix.](diagrams/14-extra-cgroup-release-agent-escape.svg)

Look at why `release_agent` is a devastating Ring 0 Confused Deputy [419, 420]: the attacker mounts a `cgroup` v1 hierarchy (`mount -t cgroup -o rdma cgroup /tmp/cgrp`), creates child `/tmp/cgrp/x`, and writes `1` into `/tmp/cgrp/x/notify_on_release`. Next, how does the kernel know where the attacker's payload script `/cmd` sits on the *host* filesystem? The container reads its own `OverlayFS` mount options inside `/etc/mtab` (`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`), extracting `/var/lib/docker/overlay2/<hash>/diff`, the exact directory on the *host's root VFS* backing `/` inside the container! Writing `$host_path/cmd` into `/tmp/cgrp/release_agent` and running `sh -c "echo \$\$ > /tmp/cgrp/x/cgroup.procs"` places a shell into child cgroup `x` that exits a microsecond later. Seeing `x` empty with `notify_on_release == 1`, the kernel workqueue `cgroup1_release_agent()` invokes `call_usermodehelper()`, which spawns `$host_path/cmd` inside `init_pid_ns`, `init_mnt_ns`, and `init_user_ns` as unconstrained host `UID 0` [419, 420]! Notice that identical kernel-upcall hazards exist if a container can write `/proc/sys/kernel/core_pattern` or `/proc/sys/kernel/modprobe` (when `/proc/sys` is mounted read-write under `--privileged`): crashing a process or requesting an unknown socket protocol triggers `call_usermodehelper()` on the host! Migrating worker nodes exclusively to unified `cgroups v2` [430] deletes `release_agent` from the kernel ABI altogether (replacing kernel upcalls with safe pollable `cgroup.events` files), while `ReadOnlyPaths=/proc/sys` locks sysctl upcalls read-only!

Second and third, examine the two runtime-seam breakouts in `runc` itself (`CVE-2019-5736` [78] and Snyk's January 2024 `Leaky Vessels` `CVE-2024-21626` [25]):

![Figure: Forensic comparison of runc container breakouts via /proc/self/exe (CVE-2019-5736) and leaked /sys/fs/cgroup file descriptors (Leaky Vessels CVE-2024-21626) alongside their kernel-enforced cures: F_SEAL_WRITE memfd cloning, close_range(), and openat2(RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS).](diagrams/14-runc-fd-escape-mechanics.svg)

In `CVE-2019-5736` (discovered by Adam Iwaniuk and Borys Popko [78]), a malicious image or compromised container replaced `/bin/sh` (or `ld-linux-x86-64.so.2`) with `#!/proc/self/exe`. When `runc init` entered the container's namespaces and called `execve("/bin/sh")`, the kernel resolved `/proc/self/exe` directly to the *host's `/usr/bin/runc` inode*, re-executing host `runc` inside container control! An attacker helper inside the container opened `/proc/<runc-pid>/exe` with `O_PATH`, spun in a tight C loop waiting for `runc` to exit (clearing Linux's `ETXTBSY` active-text write lock), and reopened `/proc/self/fd/<path_fd>` with `O_WRONLY | O_TRUNC`, overwriting `/usr/bin/runc` on the host node so the next `docker` or `kubelet` command ran attacker shellcode as host root [78]! Upstream `runc` (`>= 1.0.0-rc7`) fixed this permanently by cloning itself into an anonymous RAM file via `memfd_create("runc_cloned:/proc/self/exe", MFD_CLOEXEC | MFD_ALLOW_SEALING)` [435], locking it immutable with `fcntl(fd, F_ADD_SEALS, F_SEAL_SEAL | F_SEAL_SHRINK | F_SEAL_GROW | F_SEAL_WRITE)`, and re-executing from sealed RAM (and on `dm-verity` `/usr` immutable nodes from [Chapter 3](03-luks2-verity.md), overwriting `/usr/bin/runc` fails unconditionally with `-EROFS`! [20]).

Five years later, Rory McNamara at Snyk Security Labs uncovered `Leaky Vessels` (`CVE-2024-21626` in `runc <= 1.1.11`, disclosed alongside BuildKit mount/symlink races `CVE-2024-21627`, `CVE-2024-23651`, `CVE-2024-23652`, and `CVE-2024-23653` [25, 427]). Inside `runc`, an internal `open("/sys/fs/cgroup")` call leaked a non-`O_CLOEXEC` directory file descriptor (`fd 7` or `8`) referencing the *host's mount namespace* into `runc init` across `pivot_root`! A malicious `Dockerfile` simply declared `WORKDIR /proc/self/fd/7` (or symlinked a path to `/proc/self/fd/7` prior to `kubectl exec`): `runc init` executed `chdir("/proc/self/fd/7")` *before* `execve()`, anchoring the container process's current working directory (`current->fs->pwd`) directly onto the host's `/sys/fs/cgroup` mount! Even though `execve()` subsequently closed `fd 7`, `/proc/self/cwd` stayed alive on the host mount tree, letting the container process walk `open("../../../../etc/shadow")` or hold a reference to overwrite host binaries [25]! Modern `runc` (`>= 1.1.12`) and `crun` purge all stray descriptors atomically via Linux `5.9+`'s `close_range(3, ~0U, CLOSE_RANGE_CLOEXEC)` [436], verify `getcwd()`/`/proc/self/cwd` resolves inside the container rootfs (`ENOENT` if outside), and perform all host-to-container path resolution via `openat2(2)` [103] (which also kills `kubectl cp` tar symlink breakouts like `CVE-2019-1002101` [426]):

```c
/* Atomic Ring 0 root & magic-link confinement (include/uapi/linux/openat2.h) */
struct open_how how = {
    .flags   = O_RDONLY | O_CLOEXEC,
    .resolve = RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS,
};
int fd = syscall(__NR_openat2, rootfs_dfd, untrusted_container_path, &how, sizeof(how));
```

Passing `RESOLVE_IN_ROOT | RESOLVE_NO_MAGICLINKS` moves symlink and `..` clamping atomically into Ring 0 `link_path_walk()` (`fs/namei.c`) while rejecting `/proc/<pid>/fd/*` and `/proc/<pid>/exe` magic procfs jumps outright with `-ELOOP`, eliminating userspace `filepath-securejoin` `TOCTOU` windows permanently [25, 103].

## Distro, Immutable-OS, & Cloud Trade-Offs

In production Kubernetes clusters (`1.25+` through `1.33+`), built-in Pod Security Admission (`PSA`) enforces the three cumulative Kubernetes Pod Security Standards (`Privileged`, `Baseline`, and `Restricted` [437]) via simple namespace labels (`pod-security.kubernetes.io/enforce: restricted`):

| Pod Security Standard | Intended Workload Tier | Enforced Kernel & `securityContext` Controls | Residual Host Escape Surface |
|---|---|---|---|
| `Privileged` | Trusted CNI (`Cilium`), CSI storage, and eBPF node agents (`Tetragon`) | Unrestricted (`privileged: true`, `hostNetwork`, `hostPID`, `CAP_SYS_ADMIN` allowed) | Direct host root equivalence; compromise equals full worker-node takeover [437] |
| `Baseline` | Legacy internal apps migrating onto Kubernetes | Blocks `privileged`, `hostPID`/`hostIPC`/`hostNetwork`, `hostPath` volumes, non-default `capabilities.add`, and unsafe `/proc` masks | Still permits container `UID 0`, 14 default capabilities (`CAP_NET_RAW`), and unconfined `seccomp` unless set [424, 437] |
| `Restricted` | Hardened multi-service production default | Adds `runAsNonRoot: true`, `allowPrivilegeEscalation: false` (`no_new_privs`), `capabilities.drop: ["ALL"]` (`NET_BIND_SERVICE` only), and mandatory `RuntimeDefault`/`Localhost` `seccompProfile` | Blocks known config escapes, yet still exposes ~300+ shared host Ring 0 syscalls [390, 437] |

Layering four host-OS defenses beneath `PodSecurity: restricted` creates the strongest possible shared-kernel posture [20, 45, 265, 428]: first, run worker nodes exclusively on unified `cgroups v2` (`Fedora`, `RHEL 9/10`, `Ubuntu 22.04/24.04+`, `Debian 12+`) and never bind-mount `/var/run/docker.sock` or `/run/containerd/containerd.sock` into CI pods (use rootless `BuildKit`, `Kaniko`, or `Podman` inside unprivileged user namespaces instead); second, enforce `SELinux` `sVirt` MCS (`RHEL`, `CoreOS`, `Bottlerocket`, noting that `SELinux` `container_t` blocked `CVE-2024-21626` `../../../../etc/shadow` traversal cold with an immediate `AVC` denial! [25, 265]); third, boot immutable `dm-verity` `/usr` worker OSes (`Talos`, `Bottlerocket`, `Flatcar`, `CoreOS`, which blocked `CVE-2019-5736` `/usr/bin/runc` overwrites unconditionally with `-EROFS`! [20, 45]); and fourth, enable Kubernetes User Namespaces (`spec.hostUsers: false`, graduated to Stable in Kubernetes `v1.33` atop Linux `6.3+` `MOUNT_ATTR_IDMAP` [364, 428]) so container `UID`s map to disjoint unprivileged `65536`-wide host `kuid` ranges per pod without expensive recursive `chown`ing of volume mounts. Nevertheless, whenever a cluster executes genuinely adversarial code (public SaaS CI builds, multi-tenant serverless functions, or LLM-generated Python/Bash payloads), sharing a single Ring 0 C kernel across tenants violates isolation first principles, motivating the de-privileged runtimes of [Chapter 15](15-gvisor-microvms.md).

## Seam Failures, CVEs, & Structural Bounds

Container breakouts consistently exploit one of four seams: operator-granted capabilities/devices, `cgroup` v1 kernel upcalls, runtime namespace-crossing descriptors, or shared-kernel Ring 0 memory corruption.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| *Shocker* (`shocker.c` / `open_by_handle_at`) | 2014 | Docker `0.11` `CAP_DAC_READ_SEARCH` | `pivot_root` confines all VFS file lookups inside container | Opens bind-mounted `/etc/hosts` as `mount_fd` and passes host `/` inode `2` to `open_by_handle_at()` | Drop `CAP_DAC_READ_SEARCH` by default and block `open_by_handle_at` in `seccomp/default.json` [421, 422, 432] |
| `runc` `/proc/self/exe` Overwrite (`CVE-2019-5736`) | 2019 | `runc` execution inside container ns | Container cannot mutate host `/usr/bin/runc` binary | Entrypoint `#!/proc/self/exe` reopens host `runc` inode `O_WRONLY` via `/proc/self/fd` on exit | Clone `runc` into `F_SEAL_WRITE` `memfd` and mount host `/usr` read-only via `dm-verity` [20, 78, 435] |
| `kubectl cp` Tar Symlink Escape (`CVE-2019-1002101`) | 2019 | `kubectl cp` client extraction | Container `tar` stream stays inside target destination path | Compromised pod's `tar` binary emits malicious symlinks overwriting files on operator workstation | Validate archive links strictly without following untrusted symlinks (`openat2` `RESOLVE_BENEATH`) [103, 426] |
| `AF_PACKET` `TPACKET_V3` Overflow (`CVE-2020-14386`) | 2020 | Linux `net/packet/af_packet.c` | Default OCI `CAP_NET_RAW` inside `CLONE_NEWNET` only affects pod network | Integer overflow in `packet_set_ring` corrupts host Ring 0 slab memory from default container | Patch kernel and drop `ALL` capabilities (`PodSecurity` `restricted` strips `CAP_NET_RAW`) [424, 437] |
| `fs_context` Heap Overflow (`CVE-2022-0185`) | 2022 | `fs/fs_context.c` `legacy_parse_param` | Unprivileged `CLONE_NEWUSER` inside container is harmless | Integer underflow in `fsconfig()` overflows `kmalloc-4k` slab for full container-to-host Ring 0 escape | Patch bounds check and block `unshare`/`fsopen`/`fsconfig` in `RuntimeDefault` `seccomp` [422, 423] |
| `cgroup` v1 `release_agent` Escape (`CVE-2022-0492`) | 2022 | `kernel/cgroup/cgroup-v1.c` | `release_agent` requires host `init_user_ns` `CAP_SYS_ADMIN` | Mounts `cgroup` v1, extracts `OverlayFS` `upperdir=` from `/etc/mtab`, and triggers `call_usermodehelper()` as host root | Migrate completely to unified `cgroups v2` (deletes `release_agent`!) + enforce `SELinux`/`AppArmor` + `seccomp` [419, 420, 430] |
| Dirty Pipe Read-Only Overwrite (`CVE-2022-0847`) | 2022 | Linux `lib/iov_iter.c` `splice()` | Unprivileged `splice()` cannot mutate read-only page-cache backing files | Uninitialized `PIPE_BUF_FLAG_CAN_MERGE` overwrites read-only container/host page-cache pages | Patch kernel (`>= 5.16.11`), mount sensitive binaries read-only off separate layers, or isolate via micro-VMs [306] |
| `runc` `/proc` & `/sys` Mount Race (`CVE-2023-27561`) | 2023 | `runc` volume setup (`CVE-2019-19921` regression) | Container rootfs directories stay directories during mount setup | Swaps `/proc` or `/sys` target with symlink mid-start to trick `runc` into skipping procfs masking | Verify mount targets via `O_PATH`/`openat2` descriptors prior to bind-mounting [103, 425] |
| *Leaky Vessels* (`CVE-2024-21626` & `23651`-`23653`) | 2024 | `runc <= 1.1.11` & `BuildKit` | Internal `runc` `/sys/fs/cgroup` FDs are closed before `WORKDIR` `chdir` | `WORKDIR /proc/self/fd/7` anchors `/proc/self/cwd` onto host mount tree before `execve()`, traversing `../..` to host `/` | Upgrade `runc >= 1.1.12` (`close_range(CLOSE_RANGE_CLOEXEC)` + `cwd` check), `openat2(RESOLVE_NO_MAGICLINKS)`, and `SELinux` MCS [25, 265, 427, 436] |

Even when `runc` closes every leaked file descriptor, `openat2()` confines every host path walk, `cgroups v2` eliminates `release_agent`, and `PodSecurity` `restricted` strips all capabilities, an irreducible architectural bound remains: every thread inside a shared-kernel container still traps directly into the host's monolithic C kernel across more than 300 system calls [63, 390]. Isolating untrusted multi-tenant code requires removing the host Linux syscall table from the tenant's direct reach, the exact mission of `gVisor` and `KVM` micro-VMs in [Chapter 15](15-gvisor-microvms.md).

## Inspecting on a Live Linux Host

Verify that the host runs unified `cgroups v2` (`cgroup2fs`) rather than legacy `cgroup` v1 (`release_agent`) and check `runc` / `crun` / `containerd` patch versions (`runc >= 1.1.12`):

```bash
stat -fc %T /sys/fs/cgroup
runc --version 2>/dev/null | head -n 3 || crun --version 2>/dev/null | head -n 3 || true
containerd --version 2>/dev/null || true
```

Inspect all 8 namespace inode symlinks (`cgroup`, `ipc`, `mnt`, `net`, `pid`, `time`, `user`, `uts`) alongside `NoNewPrivs`, `Seccomp` (`2` = filter active), and `CapEff` of the current process:

```bash
ls -l /proc/self/ns/
grep -E "^(Name|NoNewPrivs|Seccomp|Seccomp_filters|CapEff|CapBnd):" /proc/self/status
```

Check available `seccomp` return actions in Ring 0 (`user_notif`, `kill_process`, `trap`) and inspect `cgroups v2` controllers enabled at the root slice:

```bash
cat /proc/sys/kernel/seccomp/actions_avail 2>/dev/null || true
cat /sys/fs/cgroup/cgroup.controllers 2>/dev/null || true
```
