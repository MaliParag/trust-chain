# APK Signature Schemes, Developer Verification, and Scoped Storage

## Overview

* **Link in the Chain:** Application code-origin authentication, ecosystem developer accountability, and filesystem privacy-mediation layer; binds every installed `.apk` to an immutable cryptographic signing identity and confines shared media access behind `Scoped Storage`.
* **Core Security Invariant:** `PackageManager` installs or updates an APK if and only if its whole-archive `APK Sig Block 42` (`v2`/`v3`/`v3.1` 1 MiB Merkle digest, plus optional streaming `v4` 4 KiB `fs-verity` root hash) verifies under the package's pinned key or a cryptographically linked `SigningCertificateLineage` rotation proof, while certified handsets bind packages to verified developer identities and mediate `/storage/emulated` via `MediaProvider` `FUSE` passthrough and the zero-permission Photo Picker.
* **Ecosystem Enforcement Tier:** Signature schemes `v2`-`v4`, `sharedUserId` deprecation, runtime permissions, and `Scoped Storage` enforce identically across `GREEN` and `YELLOW` locked states; 2026 Android Developer Verification enforces across Play and sideloading on Google-certified (`GMS` `GREEN`) devices while preserving `adb install`, student Limited Distribution accounts, a 24-hour anti-coercion power-user flow, and sovereign `YELLOW` custom OS builds (`GrapheneOS`).
* **Trusted Computing Base (TCB):** `PackageManagerService`, `PackageInstallerService`, and `ApkSignatureVerifier` (`frameworks/base/core/java/android/util/apk/`), kernel `fs-verity` and `IncFS` (`v4`), `PermissionController` Mainline `APEX`, `MediaProvider` `FUSE` passthrough daemon (`com.android.providers.media.module`), and Play / Android Developer Verification registries.
* **Seam & Handoff:** Eliminates ZIP/DEX polyglot signature bypasses (`Janus`), reckless `/sdcard` scraping, and anonymous throwaway malware re-signing, yet cannot stop a socially engineered user from granting ambient UI automation (`AccessibilityService`) to an authentically signed APK; hands UI-layer trojans and `Advanced Protection Mode` to [Chapter 11](11-accessibility-advanced-protection.md).

## Threat Model & Ecosystem Constraint

Unlike desktop Windows `Authenticode` or Apple `Developer ID` where binary execution historically hinged on commercial Certificate Authorities, Android's original 2008 application model embraced decentralized *self-signed Trust-On-First-Use (`TOFU`)* X.509 certificates [2, 90]. Any developer anywhere in the world could generate an RSA keypair offline, sign `com.example.app`, and distribute it via a store or web link; on first installation, `PackageManagerService` pinned `SHA-256(cert)` to `com.example.app` in `/data/system/packages.xml` so every subsequent update had to prove possession of that exact private key before inheriting `com.example.app`'s `u0_a*` `UID` and `/data/user/0` sandbox ([Chapter 9](09-uid-zygote-binder.md)) [21, 90].

Four concrete classes of real-world attacks forced fundamental architectural upgrades across Android's package and storage stack between 2013 and 2026 [15, 115, 310, 311, 312, 313]:

First, *ZIP and DEX parser differentials broke per-entry `JAR` signing*: Android's legacy `v1` signature scheme (`META-INF/MANIFEST.MF`) authenticated extracted ZIP entries individually while leaving archive framing, duplicate Central Directory headers (*Master Key* `CVE-2013-4787` [312]), and prepended offset-`0` `DEX` bytecode (*Janus* `CVE-2017-13156` [15, 314]) completely unsigned!

Second, *permanent `TOFU` key lock-in collided with `sharedUserId` and package metadata serialization*: under `v1` and `v2`, an enterprise or bank could never rotate an aging `RSA-1024` or potentially exposed signing key without changing `packageName` and stranding millions of installed users (`v3` and `v3.1` solved rotation via cryptographic `Proof-of-Rotation` lineages [310, 315], while `sharedUserId` lineage collisions forced `sharedUserId` deprecation [294]); meanwhile, even with valid APK signatures, unsanitized package-installer metadata written into `/data/system/packages.list` (`CVE-2024-0044` [313, 316]) allowed local `adb` shell attackers to spoof app debuggability and hijack arbitrary `u0_a*` sandboxes!

Third, *anonymous throwaway key churn fueled an epidemic of sideloaded financial malware*: Google's ecosystem telemetry revealed *over 50 times more malware from internet-sideloaded sources than on Google Play* [115]. Whenever Play Protect blocklisted a sideloaded banking dropper (`SharkBot`, `FluBot`, or fake bank clones), criminal operators generated a fresh self-signed key and `packageName` in milliseconds and pushed a new phishing SMS link, directly motivating *2026 Android Developer Verification* on certified devices [115, 317, 318].

Fourth, *broad `/sdcard` permissions enabled silent cross-app surveillance*: prior to Android 10-11, granting a flashlight or QR-scanner app `READ_EXTERNAL_STORAGE` handed it raw POSIX read access across `/storage/emulated/0`, letting SDK trackers harvest `DCIM/` family photos (complete with home GPS latitude/longitude in `EXIF` headers!), `Download/` bank statements, and other apps' external caches [311, 319].

## Architecture & AOSP Implementation

### Archive Parser Differentials (*Master Key* & *Janus*) and the `APK Sig Block 42` Binary Format (`v2`)

An Android `.apk` is simultaneously a ZIP archive and a container of Dalvik/ART executables (`classes.dex`), native ELF shared libraries (`lib/arm64-v8a/*.so`), compiled resources (`resources.arsc`), and binary `AndroidManifest.xml` [90]. Crucially, ZIP parsers locate the `End of Central Directory` (`EOCD`, magic `0x06054b50`) by scanning *backward from the end of the file* to find the `Central Directory` offset, whereas an uncompressed `DEX` file header (`magic = "dex\n035\0"`) begins *at byte offset `0` from the start of the file* [15, 320]!

Legacy `APK Signature Scheme v1` inherited standard Java `JAR` signing: `META-INF/MANIFEST.MF` listed the SHA-1/SHA-256 digest of each uncompressed ZIP entry, `META-INF/<signer>.SF` hashed `MANIFEST.MF`, and `META-INF/<signer>.RSA` (or `.EC`) held a PKCS#7 CMS signature over `.SF` [90, 320]. Two fatal parser differentials exploited the unauthenticated gaps of `v1` [15, 312, 314]. First, in *Master Key* (`CVE-2013-4787`, Bluebox 2013 [312]), placing two entries named `classes.dex` in the same ZIP caused Java's `JarVerifier` to verify the benign second `classes.dex` while C++ `libziparchive` extracted and installed the malicious first `classes.dex`! Second, in *Janus* (`CVE-2017-13156`, GuardSquare 2017 [15, 314]), an attacker prepended a malicious `classes.dex` directly onto the front of an untouched, OEM-signed `v1` APK (`evil.dex || genuine_system_app.apk`) and shifted the ZIP Central Directory offsets by `len(evil.dex)`. Walking backward from EOF, `v1` JAR verification saw every listed ZIP entry intact under the OEM's `UID 1000` signature; opening the file from offset `0` on pre-patched Android 5-8 runtimes, `ART`'s loader saw `"dex\n035\0"` first and executed `evil.dex` inside `UID 1000`!

![Figure: Evolution from JAR v1 signing and the Janus framing vulnerability to whole-archive v2, v3 key rotation, v4 fs-verity streaming, and 2026 Developer Verification.](diagrams/10-apk-signing-schemes-evolution.svg)

Introduced in Android 7.0 (`Nougat`) inside `frameworks/base/core/java/android/util/apk/` (`ApkSignatureVerifier.java` and `ApkSigningBlockUtils.java` [320, 321]), `APK Signature Scheme v2` eradicated `Master Key` and `Janus` structurally by signing *every raw byte of the archive container* rather than individual extracted files [90, 320]. `apksigner` (`tools/apksig` [322]) inserts a binary *APK Signing Block* (`Section 2`) immediately *before* the ZIP `Central Directory` (`Section 3`), partitioning the file on disk into four contiguous byte ranges:

```text
+-------------------------------------------------------------------+  offset 0
| Section 1: Contents of ZIP entries                                |  [Merkle protected]
+-------------------------------------------------------------------+  sig_block_offset
| Section 2: APK Signing Block                                      |
|   uint64  size_of_block (excluding these 8 bytes)                 |
|   pairs:  [uint64 len][uint32 ID][bytes value] ...                |
|             ID 0x7109871a -> APK Signature Scheme v2 Block        |
|             ID 0xf05368c0 -> APK Signature Scheme v3 Block        |
|             ID 0x1b93ad61 -> APK Signature Scheme v3.1 Block      |
|   uint64  size_of_block (must equal leading size_of_block!)       |
|   byte[16] magic = "APK Sig Block 42"                             |
+-------------------------------------------------------------------+  central_dir_offset
| Section 3: ZIP Central Directory                                  |  [Merkle protected]
+-------------------------------------------------------------------+  eocd_offset
| Section 4: ZIP End of Central Directory (EOCD)                    |  [Merkle protected]
+-------------------------------------------------------------------+  EOF
```

Trace the exact binary verification steps executed by `ApkSignatureSchemeV2Verifier` [320, 321]. First, the verifier locates `EOCD` at EOF, confirms zero trailing bytes follow `EOCD` and no `EOCD` comment embeds a second fake `EOCD` signature, reads `central_dir_offset`, checks the 16-byte ASCII trailer `"APK Sig Block 42"` immediately preceding `central_dir_offset`, and asserts that the leading and trailing `uint64` `size_of_block` fields match identically [320]. Second, it splits Sections `1`, `3`, and `4` into consecutive $1\text{ MiB}$ ($2^{20}$-byte) chunks (substituting `sig_block_offset` into `EOCD`'s Central Directory offset field in memory before hashing Section `4` so inserting Section `2` introduces zero circularity!). Third, it computes a parallelizable two-level Merkle tree: each $1\text{ MiB}$ chunk $i$ is hashed with domain-separation prefix byte `0xa5` as $d_i = H(\texttt{0xa5} \parallel \text{uint32\_le}(|C_i|) \parallel C_i)$, and the top-level content digest is computed with root prefix byte `0x5a` as $D = H(\texttt{0x5a} \parallel \text{uint32\_le}(k) \parallel d_1 \parallel \dots \parallel d_k)$ using `SHA-256` or `SHA-512` [320]. Fourth, inside Block ID `0x7109871a`, the verifier checks the strongest supported signature (`RSASSA-PSS`, `RSASSA-PKCS1-v1_5`, `ECDSA P-256/P-384/P-521`, or `DSA`) over `signed data` (`digests`, X.509 `certificates`, and `additional attributes`), verifies that the ordered list of algorithm IDs in `digests` and `signatures` matches byte-for-byte (defeating algorithm-downgrade stripping!), and confirms `SubjectPublicKeyInfo(certificates[0]) == public_key` [320]. Prepending even a single `Janus` byte at offset `0` shifts Section `1` and invalidates $D$ before any ZIP entry or `DEX` loader ever touches the file! To block stripping Section `2` altogether on dual-signed `v1+v2` APKs, `META-INF/*.SF` includes `X-Android-APK-Signed: 2` (or `2, 3`), causing any `v2`-capable verifier to reject fallback to `v1`, while Android 11+ (`targetSdkVersion >= 30`) refuses `v1`-only APKs unconditionally [90, 320].

### `APK Signature Scheme v3` / `v3.1` (`Proof-of-Rotation`), `sharedUserId` Collapse, and `CVE-2024-0044` (`run-as`)

`APK Signature Scheme v2` solved whole-file integrity yet left developers trapped in `TOFU` key permanence: if a studio's original 2012 signing key $K_1$ needed rotation to a hardware HSM `ECDSA P-384` key $K_2$, signing an update with $K_2$ failed `INSTALL_PARSE_FAILED_INCONSISTENT_CERTIFICATES` [310]. Android 9 (`Pie`) introduced `APK Signature Scheme v3` (Block ID `0xf05368c0`), embedding a self-certified *`Proof-of-Rotation` (`SigningCertificateLineage`)* inside `signed data` under attribute ID `0x3ba06f8c` [310, 321].

![Figure: APK Signature Scheme v3 and v3.1 SigningCertificateLineage proof-of-rotation chain and capability bitflags.](diagrams/10-extra-v3-key-rotation-lineage.svg)

Inside attribute `0x3ba06f8c`, `apksigner lineage` constructs a singly-linked chain of `levels` ordered from the app's oldest root certificate $K_1$ to its current active leaf signer $K_n$ (precluding multi-signer APKs and diamond ancestor merges) [310]. At each hop $i \to i+1$, key $K_i$ signs `(DER(cert_{i+1}) || sig_alg_id)` proving that the holder of $K_i$ delegates package authority to $K_{i+1}$, while `signed data` carries a 32-bit `flags` bitmask (`self-trusted-old-certs`) governing which residual rights the *older* key $K_i$ retains [310, 321]: `PAST_CERT_INSTALLED_DATA` (`0x01`, permitting upgrades over existing installs pinned to $K_i$ without wiping `/data/user/0`), `PAST_CERT_SHARED_USER_ID` (`0x02`), `PAST_CERT_PERMISSION` (`0x04`, letting companion apps still signed by $K_i$ acquire `signature`-level permissions declared by the rotated app), `PAST_CERT_ROLLBACK` (`0x08`, deliberately omitted in normal rotations so a compromised $K_i$ can never roll the app back!), and `PAST_CERT_AUTH` (`0x10`) [310, 315, 321]. During installation (`ApkSignatureSchemeV3Verifier.java` producing `SigningDetails`), `PackageManagerService` enforces two strict invariants: first, the APK's outer `v3` signer certificate *must* equal the final leaf certificate $K_n$ of the embedded `Proof-of-Rotation` list; and second, the currently installed APK's pinned certificate on `/data/system/packages.xml` must appear somewhere in `[K_1, \dots, K_n]` with `PAST_CERT_INSTALLED_DATA` asserted [310, 321].

Deploying `v3` in the field uncovered subtle multi-SDK edge cases on Android 9 through 12L (for example `PackageManager.checkSignatures()` mismatches with un-rotated instrumentation test APKs, and `sharedUserId` groups where updating one member with lineage $B \to C$ clobbered another member's $A \to B$ lineage!) [315]. Android 13 (`API 33`) therefore introduced *`APK Signature Scheme v3.1` (Block ID `0x1b93ad61`)* [315]: `apksigner` places the rotated key $K_{\text{new}}$ + lineage inside `0x1b93ad61` (understood only by Android 13+ where all `checkSignatures` and rollback bugs are resolved) while signing the standard `0xf05368c0` `v3` block with the original key $K_{\text{orig}}$ for Android 9-12L devices, protected against stripping by a `rotation-min-sdk-version` attribute inside the `v3` `signed data` block [315]! Concurrently, Android deprecated `android:sharedUserId` (`API 29`) because shared-UID apps dissolved process boundaries, permitted cross-package reflection/JNI injection, and collided fatally during `v3` key rotation, adding `android:sharedUserMaxSdkVersion="32"` so legacy apps shed shared `UID`s cleanly on Android 13+ without losing existing `/data/user/0` files [21, 294, 315].

Yet cryptographic signature verification is only as strong as how `PackageManagerService` persists verified metadata on `/data/system`! In March 2024, Tom Hebb (Meta Red Team X) disclosed *`CVE-2024-0044`* [313, 316]: on Android 12 and 13 (and unpatched Android 14 branches prior to the March/October 2024 ASB fixes), `PackageInstallerService.createSessionInternal()` (`pm install -i "$PAYLOAD" any.apk`) escaped newlines when writing `installerPackageName` to XML `/data/system/packages.xml`, yet wrote `installerPackageName` *completely unescaped* as the final column of space- and newline-delimited `/data/system/packages.list` (`Settings.java`) [313, 316]! A local attacker or physical forensic rig with `adb shell` (`UID 2000`) passed a newline inside `-i` to inject a forged `packages.list` row marking any target `u0_a*` UID as `debuggable = 1` with data path `/data/user/0` (which tripped a symlink special-case bug in `system/core/run-as/run-as.cpp`'s `check_directory()` that skipped directory `UID` ownership verification!), allowing `run-as` to enter any non-`system` app's `UID` and rewrite cached `ODEX`/`VDEX` code inside `/data/user_de/0/com.google.android.gms/app_chimera/` for persistent `gmscore_app` execution [313]!

### `APK Signature Scheme v4` (`fs-verity` `.apk.idsig` & `IncFS`) and 2026 Android Developer Verification

To support instant streaming launch of multi-gigabyte games and continuous runtime integrity without re-hashing an entire `.apk` at install time, Android 11 (`API 30`) added *`APK Signature Scheme v4`* (`<apk>.apk.idsig`, always paired with a `v2`/`v3` block) [91]:

```c
/* Canonical serialized payload signed in APK Signature Scheme v4 (source.android.com) */
struct V4DataForSigning {
    int32_t size;                     /* Total byte length of V4DataForSigning blob   */
    int64_t file_size;                /* Exact byte length of the protected .apk file */
    int32_t hash_algorithm;           /* 1 = SHA-256 (matching kernel fs-verity)      */
    uint8_t log2_blocksize;           /* 12 = 4096-byte leaf Merkle blocks            */
    sized_bytes salt;                 /* Up to 32 bytes zero-padded per fs-verity     */
    sized_bytes raw_root_hash;        /* Salted SHA-256 root digest of 4 KiB tree     */
    sized_bytes apk_digest;           /* Bound content digest from APK v3 / v2 block! */
    sized_bytes x509_certificate;     /* Signer DER X.509 cert matching v3 / v2 leaf  */
    sized_bytes additional_data;
};
```

Look at how `V4DataForSigning` links streaming and whole-archive verification together [89, 91, 323]: `hashing_info` commits to the exact `4096`-byte (`log2_blocksize = 12`) `SHA-256` `raw_root_hash` format consumed natively by Linux kernel `fs-verity`, while `signing_info.apk_digest` cryptographically binds the detached `.idsig` file to the APK's embedded `v3` (`CONTENT_DIGEST_CHUNKED_SHA512` / `SHA256`) or `v2` digest and signing certificate! During Play Instant or `adb install --incremental` streaming installs, `PackageInstaller` passes the stripped `signing_info` blob into the kernel `Incremental File System` (`IncFS`, `fs/incfs/` [323]) while Merkle tree nodes stream over HTTPS on demand; on standard `/data/app` installs, `PackageManager` invokes `ioctl(FS_IOC_ENABLE_VERITY)` on the `.apk` inode so the `EL1` kernel verifies every `4 KiB` page faulted in from flash against `raw_root_hash` throughout the app's installed lifetime ([Chapter 2](02-antirollback-verity-apex.md)) [89, 91].

Now contrast *who* signs APKs across distribution channels [115, 317, 318, 324]. On Google Play (mandatory for new `.aab` App Bundles since August 2021), *Play App Signing* separates key custody: developers sign uploads with a resettable *Upload Key*, while Google signs delivered split APKs inside cloud HSMs (`App Signing Key`, supporting one-click `v3.1` key upgrades) [324]. Outside Google Play, however, self-signed `TOFU` allowed scam syndicates to mass-produce anonymous sideloaded banking trojans (`>50x` higher malware incidence than Play! [115]), rotating keys whenever Play Protect caught up.

Starting September 30, 2026 across initial high-fraud jurisdictions (Brazil, Indonesia, Singapore, and Thailand) and expanding globally in 2027, Google introduced *Android Developer Verification* on certified (`GMS`) Android devices (`developer.android.com/developer-verification`) [115, 317, 318]. Certified devices verify at install time (across Google Play, third-party app stores, and browser sideloading) that the APK's `(packageName, signingCertificate)` pair is registered to a verified developer identity in the Play Console or dedicated non-Play *Android Developer Console* [115, 317]. Look carefully at four architectural choices that distinguish Android Developer Verification from closed desktop/mobile ecosystems [20, 115, 317, 318]: first, Google verifies *who* the developer is ("airport ID check"), *never* reviewing or gating the sideloaded APK's content or alternative store distribution [115]; second, local `adb install` remains open for engineering workflows, complemented by free, government-ID-exempt *Limited Distribution Accounts* (up to 20 devices) for students and hobbyists [317, 318]; third, for power users who genuinely want to sideload unverified software on a `GMS` phone, Android engineered a *coercion-resistant Advanced Flow* (requiring Developer Options, a mandatory phone reboot that severs active remote-coaching calls, a *24-hour cooling-off waiting period* that breaks scammer urgency, and biometric/PIN confirmation [318]); and fourth, non-GMS open-source OS builds (`GrapheneOS` in `YELLOW` locked state) enforce zero Google developer-registry checks [20, 115].

### `Scoped Storage`: `MediaProvider` `FUSE` Passthrough, `EXIF` Redaction, `SAF`, and the System Photo Picker

Once an APK is installed, `Scoped Storage` (enforced universally for `targetSdkVersion >= 30` since Android 11 and refined through Android 16) eliminates ambient `/sdcard` snooping [311]. Android 8-10 previously relied on an out-of-tree kernel wrapper (`SDCardFS`) to emulate case-insensitive `/sdcard` permissions; because in-kernel path string manipulation caused VFS locking bugs and could not be updated via `Mainline`, Android 11 deprecated `SDCardFS` (banning it on launch kernels $\ge 5.4$ [325]) and promoted the updatable *`MediaProvider` Mainline `APEX`* (`com.android.providers.media.module`, running inside `mediaprovider_app`) to serve `/storage/emulated/<u_id>` via userspace `libfuse` [81, 311].

![Figure: Scoped Storage isolation between unmediated app-private POSIX directories and mediated MediaStore, FUSE, and System Photo Picker access.](diagrams/10-scoped-storage-mediastore.svg)

To keep userspace `FUSE` from bottlenecking 4K video recording or game asset reads, Android engineered two kernel-assisted fast paths [311, 326]: first, `Zygote` mount namespaces bind-mount each app's private external directories (`/storage/emulated/0/Android/data/<pkg>` and `Android/obb/<pkg>`) directly onto the lower `/data/media/0` (`f2fs`/`ext4`) filesystem, bypassing `FUSE` completely for native speeds while making every *other* app's `Android/data/<other_pkg>` invisible [311]; second, on shared media files where `MediaProvider`'s `FuseDaemon` approves access without byte modification, `GKI` *FUSE Passthrough* (`FUSE_DEV_IOC_CLONE` / backing-fd passthrough [326]) attaches the lower `f2fs`/`ext4` file descriptor directly to the `FUSE` open reply so subsequent `read()`/`write()`/`mmap()` syscalls execute directly in `EL1` VFS at near-native POSIX throughput without bouncing user buffers back through `MediaProvider`!

Where byte-level privacy mediation *is* required, `MediaProvider` disables passthrough on that open handle and computes exact byte-redaction ranges (`RedactionInfo`) in userspace: unless the calling `UID` holds `ACCESS_MEDIA_LOCATION`, `MediaProvider`'s `FUSE` read handler parses JPEG `EXIF` (`GPSInfo` IFD tags), `XMP` packets, and MP4/HEIC `ISOBMFF` (`xyz` location boxes) on the fly, overwriting GPS latitude, longitude, altitude, and timestamp offsets with spaces or zeros while leaving surrounding compressed image scanlines untouched [311, 319]! Non-media documents (`PDF`, `ZIP`, `DOCX`) in `Download/` require explicit per-file user selection through the *Storage Access Framework* (`ACTION_OPEN_DOCUMENT` backed by `DocumentsProvider` URI grants [327]), while `PermissionController` (`Mainline` `APEX`) enforces Android 13 granular media permissions (`READ_MEDIA_IMAGES`, `READ_MEDIA_VIDEO`, `READ_MEDIA_AUDIO`), 90-day unused *Permission Auto-Reset / Hibernation* [328], Android 14 *Selected Photos Access* (`READ_MEDIA_VISUAL_USER_SELECTED`), and the zero-permission out-of-process *System Photo Picker* (`PickVisualMedia`), which runs inside a system-owned UI surface and returns a transient read-only `content://` URI for *only* the specific photos tapped by the user without granting the app any storage permission whatsoever [311, 329]!

## Vendor, OEM, & Custom-OS Boundaries

Delivering `MediaProvider` and `PermissionController` as Google-signed `Project Mainline` `APEX` packages ([Chapter 2](02-antirollback-verity-apex.md)) eliminated historic OEM `SDCardFS` divergence: when SQL injection permission bypasses (`CVE-2020-0344` and `CVE-2020-0352` [330]) surfaced in early `MediaProvider` `WHERE`-clause filtering, Google shipped a single Mainline `APEX` update across Pixel, Samsung, Xiaomi, and Motorola handsets simultaneously without waiting for OEM firmware builds [81, 311, 330].

`GrapheneOS` (`YELLOW` locked state) extends AOSP's storage and contact model with capability-based *Storage Scopes* and *Contact Scopes* [20, 331]: when an app refuses to function unless `checkSelfPermission()` reports full storage or contacts access, the user can enable Storage or Contact Scopes, returning `PERMISSION_GRANTED` to satisfy the app's check while `MediaProvider` / `ContactsProvider` exposes an isolated virtual sandbox containing *only* the exact files or folders selected by the user [331]!

### When Every Cryptographic Signature and Storage Boundary Holds, Yet the User Clicks "Allow"

Study the final two rows of that table closely: even when an APK carries a valid `APK Signature Scheme v3.1` + `v4` `fs-verity` signature, runs inside a zero-capability `u0_a*` `UID` beneath `SELinux` and `seccomp-BPF`, is memory-tagged by `Arm MTE`, and cannot touch `/sdcard` thanks to `Scoped Storage`, how do modern banking trojans like *Anatsa*, *SharkBot*, and *Xenomorph* still initiate fraudulent wire transfers out of fully patched phones without burning a single kernel or browser zero-day [36, 332]? They step *above* the kernel and cryptographic trust chain into the human UI automation plane, socially engineering the victim into enabling `AccessibilityService` and `NotificationListenerService`. [Chapter 11](11-accessibility-advanced-protection.md) examines UI-layer trojan kill chains, Android 13-15 `Enhanced Confirmation Mode` (`Restricted Settings`), and Android 16/17 `Advanced Protection Mode`.

## Inspecting via ADB, Fastboot, & Attestation

Verify an APK's active signature blocks (`v1`, `v2` `0x7109871a`, `v3` `0xf05368c0`, `v3.1` `0x1b93ad61`, `v4` `.idsig`), signer `SHA-256` digests, and `SigningCertificateLineage` capability flags offline via `apksigner`:

```bash
apksigner verify --verbose --print-certs app-release.apk
apksigner lineage --print-certs --v --in app-release.apk
```

Inspect an installed package's verified `apkSigningVersion`, signing lineage, `targetSdk`, and granted media or location permissions on a live handset:

```bash
adb shell dumpsys package com.google.android.apps.photos | grep -E 'apkSigningVersion|targetSdk|ACCESS_MEDIA_LOCATION|READ_MEDIA' | head -n 8
```

Confirm that `MediaProvider` (`Scoped Storage` `FUSE` passthrough daemon) is executing from its signed `Project Mainline` `APEX` inside `mediaprovider_app` and mediating `/storage/emulated`:

```bash
adb shell ps -AZ | grep -i mediaprovider
adb shell mount | grep '/storage/emulated' | head -n 4
```
