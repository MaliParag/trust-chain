# Hardware Arm MTE and Hardened Heap Allocation in Production

## Overview

* **Link in the Chain:** Hardware-assisted spatial and temporal memory-safety enforcement layer; pairs `Bionic`'s `Scudo` hardened heap allocator with `ARMv8.5-A`/`ARMv9-A` Memory Tagging Extension (`MTE`) 4-bit pointer and 16-byte allocation-granule tags in production.
* **Core Security Invariant:** Every 16-byte `TAG_GRANULE` in `PROT_MTE` heap and stack pages holds a 4-bit physical tag $T_{\text{mem}} \in \{1, \dots, 15\}$ in dedicated Tag RAM, and every load or store compares logical pointer bits `[59:56]` ($T_{\text{ptr}}$) against $T_{\text{mem}}$, raising a hardware tag-check fault whenever $T_{\text{ptr}} \ne T_{\text{mem}}$ on spatial out-of-bounds access or temporal post-`free()` retagging.
* **Ecosystem Enforcement Tier:** Active on `ARMv9` `MTE`-capable silicon (`Google Pixel 8` / `Tensor G3` and newer, selected `Dimensity` / `ARMv9` flagships) across both `GREEN` stock OS (system daemons, `android:memtagMode`, bootloader `memtag-once` escalation, and system-wide under `Advanced Protection Mode`) and `YELLOW` `GrapheneOS` (default synchronous `MTE` + `hardened_malloc` across system and user apps); orthogonal to `ORANGE` lock state.
* **Trusted Computing Base (TCB):** `ARMv8.5-A`/`ARMv9-A` CPU `MTE` tag-check unit, `GCR_EL1`/`SCTLR_EL1` registers, physical Tag DRAM carveout ($\approx 3.125\%$ of RAM), `GKI` `EL1` context switcher and `CONFIG_KASAN_HW_TAGS`, `Bionic` `libc` + LLVM `Scudo` allocator, bootloader `misc_memtag_message` handler, and `debuggerd` tombstone ring buffers.
* **Seam & Handoff:** Converts C/C++ heap overflows and use-after-frees into immediate `SIGSEGV` (`SEGV_MTESERR` / `SEGV_MTEAERR`) crashes, yet remains bounded by 4-bit entropy ($1/16 = 6.25\%$ blind collision), `Zygote` fork-tag inheritance, and speculative side-channel oracles (`TIKTAG-v1`/`v2`); closes Part II and hands application-level `UID`, `WebView`, and `Binder` sandboxing to Part III ([Chapter 9](09-uid-zygote-binder.md)).

## Threat Model & Ecosystem Constraint

[Chapter 7](07-treble-gki-rust.md) established that memory-safe Rust reduces memory-safety vulnerability density by three orders of magnitude in *newly written* AOSP subsystems [245]. Yet every shipping smartphone still executes hundreds of millions of lines of performance-critical C and C++ that cannot be rewritten overnight: Chromium's `Blink` layout engine, `V8`, `Skia`, and `ANGLE` inside `WebView` and Chrome, ubiquitous image and video codecs (`libwebp`, `libdav1d`, `libavc`, `libhevc`), third-party game and augmented-reality engines (`Unity`, `Unreal`, `JNI` NDK `.so` binaries), and legacy system libraries [5, 266, 267]. Across Google Project Zero and Threat Analysis Group (`TAG`) zero-day telemetry, spatial heap buffer overflows (such as the zero-click `libwebp` Huffman table overflow `CVE-2023-4863` [267]) and temporal Use-After-Free (`UAF`) bugs in C/C++ native libraries remain the primary entry vector for commercial mobile spyware [41, 267].

Before `ARMv8.5-A` silicon arrived, defenders faced an unforgiving cost-versus-coverage cliff [268, 269, 270]. Compile-time software sanitizers such as `AddressSanitizer` (`ASan`) and `ARM64` `Top-Byte-Ignore` `Hardware-Assisted AddressSanitizer` (`HWASan` [270]) catch spatial and temporal bugs deterministically during lab fuzzing, yet burn $2\times$ CPU overhead, $10\%\text{ to }35\%$ code-size bloat, and $2\times\text{ to }3\times$ RAM overhead, making them unshippable on retail phones [269, 270]. Conversely, fleet-sampled guard-page detectors such as `GWP-ASan` (`android:gwpAsanMode` [271, 272]) and zero-initializing stack variables (`-ftrivial-auto-var-init=zero` [254]) run at near-zero overhead on retail devices, yet `GWP-ASan` guards only a tiny random fraction of allocations (catching bugs statistically across millions of users for patch telemetry, not blocking a targeted zero-day against a single journalist!) [272, 273]. Traditional software hardened allocators without memory tagging validate chunk headers, yet remain blind when a dangling `UAF` pointer corrupts an application C++ vtable or boolean inside a legitimately recycled heap slot of the same size class [266, 269].

Enforcing continuous, per-dereference spatial and temporal heap safety *in production on battery-constrained smartphones* required meeting four strict hardware-software constraints: physical tag storage overhead near `3%` of DRAM, low single-digit CPU overhead on interactive UI threads, binary compatibility with unmodified prebuilt NDK `.so` libraries, and crash-intolerant containment against multi-attempt exploits [5, 266, 268, 269].

## Architecture & AOSP Implementation

### `ARMv8.5-A` / `ARMv9-A` `MTE` Hardware Mechanics: `TBI`, `TAG_GRANULE`, Instruction Set, and `TCF` Modes

Specified in `ARMv8.5-A` (`FEAT_MTE` / `FEAT_MTE2`), refined in `ARMv8.7-A` (`FEAT_MTE3` asymmetric mode) and `ARMv8.9-A`/`ARMv9.4-A` (`FEAT_MTE4` canonical tag checking [274]), and shipped commercially first on Google Pixel 8 (`Tensor G3`) in October 2023 [5], `Arm MTE` implements architectural lock-and-key memory coloring directly inside the CPU load/store pipeline and memory hierarchy [46, 268, 275].

`MTE` builds directly atop `ARMv8.0`'s *Top-Byte Ignore* (`TBI`, `TCR_EL1.TBI0 = 1`) and Linux's AArch64 Tagged Address ABI (`prctl(PR_SET_TAGGED_ADDR_CTRL, PR_TAGGED_ADDR_ENABLE, ...)` [275, 276]), under which MMU translation ignores virtual address bits `[63:56]`. `MTE` assigns bits `[59:56]` of every 64-bit pointer as a 4-bit *Logical Address Tag* (`key`, $T_{\text{ptr}} \in \{0, 1, \dots, 15\}$). Simultaneously, for every virtual page mapped with the `PROT_MTE` (`0x20`) `mmap()`/`mprotect()` protection flag (supported on `MAP_ANONYMOUS`, `tmpfs`, and `memfd` RAM mappings, and locked so `mprotect()` can never strip `PROT_MTE` once enabled [275]), physical RAM is subdivided into aligned 16-byte *Allocation Granules* (`TAG_GRANULE = 16` bytes) [46, 268, 275]. Each 16-byte granule carries a 4-bit *Physical Allocation Tag* (`lock`, $T_{\text{mem}} \in \{0, 1, \dots, 15\}$) stored in a dedicated physical Tag RAM carveout reserved at boot ($\frac{4\text{ bits}}{128\text{ bits}} = \frac{1}{32} = 3.125\%$ of DRAM) and cached on-die inside coherent CPU Tag Caches [268, 277].

![Figure: ARMv8.5-A Memory Tagging Extension (MTE) 4-bit pointer logical tag vs. 16-byte physical granule allocation tag check.](diagrams/08-mte-pointer-granule-check.svg)

To keep allocation and `free()` tag updates fast enough for every `malloc()` call, AArch64 adds dedicated unprivileged `EL0` tag-manipulation instructions governed by per-thread `GCR_EL1` (*Tag Control Register*) and `RGSR_EL1` (*Random Allocation Tag Seed Register*, stepped by a 16-bit hardware LFSR seeded from `TRNG`) [46, 268, 275]:

```c
/* Representative AArch64 MTE instructions executed inside Scudo malloc() / free() */
gmi   x10, x9, xzr            /* Insert left/right neighbor tag bits into exclude mask x10 */
irg   x0, x0, x10             /* Generate random logical tag in x0[59:56] excluding x10|GCR */
stzg  x0, [x0], #16           /* Write x0[59:56] allocation tag to Tag RAM & zero 16B granule */
ldg   x11, [x8, #0]           /* Read live 4-bit allocation tag from Tag RAM into x11[59:56] */
```

Observe how each instruction maps to allocator primitives [46, 266, 268, 275]: `GMI Xd, Xn, Xm` (*Tag Mask Insert*) extracts the 4-bit tag of an adjacent chunk pointer `Xn` and sets bit $(1 \ll T_{\text{adj}})$ in exclusion mask `Xd`; `IRG Xd, Xn, Xm` (*Insert Random Tag*) draws a fresh non-zero 4-bit tag into `Xd[59:56]` guaranteed not to appear in `Xm | GCR_EL1.Exclude` (controlled from userspace via `PR_MTE_TAG_MASK` in `prctl()` [275]); `ADDG` and `SUBG` perform simultaneous pointer offset and tag arithmetic for stack frame variables (`-fsanitize=memtag-stack`); `LDG` reads physical tags back during crash diagnostics or `realloc()`; and `STG`, `ST2G`, `STZG`, and `STZ2G` write 16-byte or 32-byte allocation tags while optionally zeroing payload memory in a single coalesced bus transaction [46, 268]! For hot `memcpy()` routines copying untagged buffers or crash handlers inspecting memory, `MSR TCO, #1` sets `PSTATE.TCO` (*Tag Check Override*) temporarily, while Linux forcibly zeroes `PSTATE.TCO = 0` on signal handler entry and `EL1` `copy_from_user()` checks [273, 275].

Whenever any `LDR`, `STR`, or atomic instruction dereferences a `PROT_MTE` address (excluding untagged `SP + #imm` accesses), the CPU compares $T_{\text{ptr}} \stackrel{?}{=} T_{\text{mem}}$. Mismatch behavior is configured per-thread via `SCTLR_EL1.TCF0` (`PR_MTE_TCF_*` flags in `prctl(PR_SET_TAGGED_ADDR_CTRL)`) and tuned per heterogeneous CPU core via `/sys/devices/system/cpu/cpu<N>/mte_tcf_preferred` across three hardware fault modes [273, 275, 278]:

First, under *Synchronous Mode* (`SYNC`, `PR_MTE_TCF_SYNC`), a tag mismatch triggers a precise synchronous Data Abort *before* the faulting instruction retires: an offending `STR` never modifies L1 cache or RAM, and an offending `LDR` never architecturalizes leaked bytes into target registers [273, 275]. The kernel delivers fatal `SIGSEGV` (`si_code = SEGV_MTESERR`) with the exact faulting tagged virtual address in `siginfo.si_addr` (preserving bits `[59:56]` when `SA_EXPOSE_TAGBITS` is set on `sigaction`), turning memory corruption into deterministic pre-commit exploit prevention at roughly `2% to 6%` CPU overhead [273, 275]. Second, under *Asynchronous Mode* (`ASYNC`, `PR_MTE_TCF_ASYNC`), out-of-order cores retire loads and stores without pipeline stalls (`< 1%` CPU overhead) and set a sticky fault bit in `TFSRE0_EL1` (or `TFSR_EL1` for kernel `CONFIG_KASAN_HW_TAGS` [259]); on the very next kernel entry (syscall, timer interrupt, or context switch), `GKI` inspects `TFSRE0_EL1 != 0` and kills the process with `SIGSEGV` (`SEGV_MTEAERR`, `si_addr = 0`) [273, 275]. Third, under *Asymmetric Mode* (`ASYMM`, `ARMv8.7-A` `FEAT_MTE3`, selected automatically by Linux when a task passes `PR_MTE_TCF_SYNC | PR_MTE_TCF_ASYNC` on cores whose `mte_tcf_preferred` is `asymm` [273, 275]), loads trap synchronously while stores trap asynchronously. As Mark Brand and Jann Horn of Google Project Zero demonstrated ("The Story of MTE Asymmetry" [278]), `ASYNC` and `ASYMM` remain vulnerable to multi-threaded race exploitation: an attacker thread executing an out-of-bounds `STR` commits corrupted bytes straight to L1/L2 cache, giving a second race thread pinned to another core a microsecond window to consume the corrupted vtable or execute a `system()` syscall *before* the first thread hits a kernel entry check [278]! High-assurance targets therefore require strict `SYNC` mode (configured even on little in-order Cortex-A5xx cores at near-zero penalty via `mte_tcf_preferred = sync`) [273, 278].

### `Scudo` Hardened Allocator in `Bionic` (`Primary`, `Secondary`, Checksummed Headers, and `MTE` Retagging)

Since Android 11 (`API 30`), AOSP's `Bionic` C runtime (`bionic/libc/bionic/scudo.cpp` wrapping `external/scudo` / `compiler-rt/lib/scudo/standalone`) ships LLVM's `Scudo` hardened allocator across all native processes and apps on non-Go devices, co-designed specifically to drive `Arm MTE` [266, 273, 279].

Even on pre-`ARMv9` devices lacking `MTE`, `Scudo` establishes four software heap defenses [266]: first, its 64-bit `Primary` allocator (`SizeClassAllocator64`) segregates small allocations into dedicated size-class virtual regions (releasing contiguous idle pages via `madvise` every `release_to_os_interval_ms`) and shuffles free-list transfer batches randomly using per-thread caches (`TSD Registry`), defeating deterministic heap Feng Shui; second, its `Secondary` (`MapAllocator`) wraps large `mmap()` allocations directly inside `PROT_NONE` guard pages; third, configurable per-thread (`thread_local_quarantine_size_kb`) and global (`quarantine_size_kb`) `Quarantine` queues delay chunk recycling so freed slots cannot be reclaimed predictably on the next allocation; and fourth, every returned chunk is preceded by an atomic 8-byte (64-bit) packed metadata header protected by a 16-bit hardware `CRC32` checksum [266]:

```c
/* Conceptual 64-bit packed chunk header in LLVM Scudo (scudo/standalone/chunk.h) */
struct UnpackedHeader {
    uint64_t ClassId           : 8;  /* 1..N for Primary size class; 0 for Secondary */
    uint64_t State             : 2;  /* 0 = Available, 1 = Allocated, 2 = Quarantined */
    uint64_t Origin            : 2;  /* 0 = Malloc, 1 = New, 2 = NewArray, 3 = Memalign */
    uint64_t SizeOrUnusedBytes : 20; /* Exact requested size or Secondary tail bytes */
    uint64_t Offset            : 16; /* Alignment delta from start of underlying block */
    uint64_t Checksum          : 16; /* CRC32(Cookie, ChunkPtr, HeaderWithoutChecksum) */
};
```

`Scudo` loads that 64-bit header into a local register and updates it via atomic compare-exchange (`CAS`) to eliminate multi-threaded Time-of-Check-to-Time-of-Use (`TOCTOU`) double-fetch races, terminating the process immediately on header corruption, double-`free()`, unaligned pointers, or `new[]` versus `free()` / sized-`delete` API mismatches (`dealloc_type_mismatch` and `delete_size_mismatch=true`) [266]!

![Figure: Scudo hardened allocator and hardware Arm MTE lifecycle catching spatial overflows and temporal use-after-free bugs.](diagrams/08-scudo-mte-lifecycle.svg)

On `ARMv9` silicon with `MTE` active, `Scudo` maps `Primary` and `Secondary` heap arenas with `PROT_MTE` and enforces two selectable tag-coloring strategies via `mallopt(M_MEMTAG_TUNING, ...)` [266, 273, 279]:

Under the default `M_MEMTAG_TUNING_BUFFER_OVERFLOW` policy, `Scudo` partitions odd and even tag banks across neighboring 16-byte-aligned chunks (using `GMI` + `IRG` exclusion masks) so two physically adjacent chunks *never* share the same 4-bit tag ($P(\text{detect linear overflow/underflow}) = 100\%$, with zero wasted ASan redzone padding between chunks!) at the trade-off of halving per-slot `UAF` tag entropy to roughly $7/8 = 87.5\%$ [273]. Under `M_MEMTAG_TUNING_UAF`, `Scudo` draws tags independently across all 15 non-zero values $\{1, \dots, 15\}$, providing uniform $14/15 \approx 93.3\%$ detection across both arbitrary spatial jumps and temporal `UAF`s [273]. On every `free(ptr)` call, `Scudo` immediately retags the freed chunk's granules via `STZG` (either to a fresh random tag $T_{\text{next}} \ne T_{\text{old}}$ or reserved tag `0` while quarantined), instantly invalidating every extant dangling pointer holding $T_{\text{old}}$ in bits `[59:56]`!

Simultaneously, in `SYNC` mode, `Scudo` logs compact `(ptr, size, alloc_tid, alloc_trace, free_tid, free_trace)` entries inside a lock-free `32,768`-slot `allocation_ring_buffer`, while Linux exposes `PTRACE_PEEKMTETAGS` and `PT_AARCH64_MEMTAG_MTE` ELF core-dump segments (`128 bytes` of packed 4-bit granule tags per `4 KiB` page) [266, 275, 280]. When `SEGV_MTESERR` traps, `system/core/debuggerd` attaches to the crashing task, reads the offending pointer tag $T_{\text{ptr}}$ from `siginfo.si_addr[59:56]`, inspects surrounding physical granule tags via `PTRACE_PEEKMTETAGS`, matches `(address, tag)` against `Scudo`'s ring buffer, and automatically classifies the bug inside `/data/tombstones/` (and `ApplicationExitInfo.REASON_CRASH_NATIVE` / `DropboxManager`) as *Buffer Overflow (X bytes right of allocation)* or *Use-After-Free (X bytes into freed allocation)* complete with allocation and `free()` stack traces [266, 273, 275, 280, 281]!

Notice, however, what granule-per-chunk coloring *cannot* distinguish on its own: *intra-object overflows and container confusion* [268, 282, 283]. Because `Scudo` assigns a single 4-bit tag $T$ across all 16-byte granules belonging to a single `malloc(sizeof(struct foo))` object, overflowing `char name[32]` into an adjacent `uint32_t flags` or function pointer *inside the exact same `struct foo`* sees $T_{\text{ptr}} == T_{\text{mem}}$ on every granule! Similarly, Jakob Koschel et al. (*Uncontained*, USENIX Security 2023 [282]) demonstrated that erroneous `container_of()` downcasts in C can step outside an embedded sub-struct while staying inside a larger tagged slab object. Closing intra-object gaps in C requires pairing `MTE` with Clang's `-fbounds-safety` / `__counted_by` flexible-array bounds annotations [283] and forward-edge `KCFI` ([Chapter 7](07-treble-gki-rust.md)), or migrating new parsers to Rust [245].

### Fleet Telemetry, Bootloader `misc_memtag_message` Escalation, Manifest Opt-In, and `Advanced Protection`

Because enabling `MTE` reserves the $3.125\%$ physical Tag RAM carveout at `EL3`/bootloader DRAM initialization time, Android 13+ standardized a bidirectional userspace-to-bootloader `MTE` control ABI (`misc_memtag_message` in `bootable/recovery/bootloader_message`, driven by `/system/bin/mtectrl` when `ro.arm64.memtag.bootctl_supported=1`) [273, 277]. Writing `memtag`, `memtag-once`, `memtag-kernel`, or `memtag-off` to `arm64.memtag.bootctl` updates bitflags (`MISC_MEMTAG_MODE_MEMTAG`, `MISC_MEMTAG_MODE_MEMTAG_ONCE`, `MISC_MEMTAG_MODE_MEMTAG_KERNEL`) on the raw `/misc` partition [277]. On next boot, the bootloader checks those flags, configures `SCR_EL3.ATA = 1` and Tag RAM DeviceTree reservations (or passes `arm64.nomte` / `kasan=on` on the kernel command line), and automatically clears `*_ONCE` bits [277].

That architecture powers four graduated deployment tiers across the Android ecosystem [5, 20, 39, 239, 273, 281]: first, AOSP compiles high-risk privileged native daemons (`bluetooth`, `nfc`, `secure_element`, `statsd`, networking utilities) with `sanitize: { memtag_heap: true }` (and `memtag_stack` on critical parsers) out of the box [273]; second, app developers opt in entire apps or isolated parser processes via `android:memtagMode="sync"` (or `"async"`) in `AndroidManifest.xml`, while QA engineers force-enable `MTE` on unmodified APKs via `adb shell am compat enable NATIVE_MEMTAG_SYNC <pkg>` or Developer Options *Memory Tagging Extension* [273, 281]; third, Pixel 8/9/10+ deploy *Bootloader Timed / One-Shot Telemetry* (`memtag-once` and runtime `M_HEAP_TAGGING_LEVEL_SYNC` escalation) alongside Android 16/17 *Advanced Protection Mode* ([Chapter 11](11-accessibility-advanced-protection.md)), which turns hardware `MTE` on globally across all compatible apps with a single high-risk user toggle [5, 39, 277]; and fourth, `GrapheneOS` (`YELLOW` locked Pixel 8/9/10+) enforces synchronous hardware `MTE` (`SYNC`) by default across both base OS processes and user-installed apps, paired with `hardened_malloc`'s dedicated metadata-out-of-band slab isolation [20, 239]!

## Vendor, OEM, & Custom-OS Boundaries

`Arm MTE` exposes a sharp hardware-firmware boundary across smartphone SoCs: *shipping an `ARMv9` CPU core (`Cortex-X3`/`X4`/`X925` or `Cortex-A715`/`A720`) is necessary but not sufficient for working `MTE`* [5, 268, 277]. The SoC vendor must synthesize coherent Tag Caches across the System-Level Cache / Network-on-Chip (`CMN`), wire `EL3` `ARM Trusted Firmware` (`SCR_EL3.ATA`) to enable non-secure tag access, carve out `3.125%` of physical LPDDR5X DRAM in the bootloader memory map, and implement `misc_memtag_message` in `ABL`/`XBL` [5, 46, 277]. Google (`Tensor G3` on Pixel 8, `Tensor G4` on Pixel 9, and successor `Tensor` silicon) and MediaTek (`Dimensity 9300`+) enabled full production `MTE` in shipping firmware, whereas several early competing `ARMv9` smartphone boards fused `ID_AA64PFR1_EL1.MTE` off in `EL3` firmware to avoid DRAM carveout cost until Android 15-16 `CDD` recommendations and `Advanced Protection` requirements pushed broader SoC enablement [5, 9, 39].

## Exploit Chains & Structural Limits

Evaluating `Arm MTE` as a trust-chain primitive requires confronting four exact mathematical and microarchitectural limits: finite 4-bit tag entropy, `Zygote` fork-state sharing, intra-object sub-bounds blindness, and speculative execution tag oracles (`TIKTAG`).

### Entropy Bounds, `Zygote` Fork Sharing, and Speculative Tag Oracles (`TIKTAG-v1` & `TIKTAG-v2`)

Three subtle boundaries in that table deserve rigorous architectural analysis. First, consider *tag entropy and `Zygote` fork determinism* [275, 278, 284]. Against a remote attacker with zero tag oracle, a single non-linear `UAF` or heap-spray dereference passes `MTE` with probability $p = \frac{1}{15} \approx 6.67\%$ under `M_MEMTAG_TUNING_UAF` (or $p = \frac{1}{8} = 12.5\%$ within same-parity slots under `M_MEMTAG_TUNING_BUFFER_OVERFLOW`) [273, 278]. If an exploit requires $k = 3$ independent blind corruptions, one-shot survival falls to $(1/15)^3 \approx 0.03\%$; however, if a faulty daemon respawns indefinitely (without backoff) upon crashing, an attacker who can retry $N = 60$ times drives cumulative success $1 - (1 - 1/15)^{60}$ above $98.4\%$ [278]! Android therefore treats every `SEGV_MTESERR` / `SEGV_MTEAERR` crash as a security signal, throttling service restarts and recording crashes in `debuggerd` [273, 280]. Furthermore, because Linux `fork()` preserves `PROT_MTE` allocation tags across Copy-on-Write pages (`Documentation/arch/arm64/memory-tagging-extension.html` [275]), every application forked from `Zygote64` ([Chapter 9](09-uid-zygote-binder.md)) inherits identical `MTE` tags on pre-fork `ART` and native allocations unless `MADV_WIPEONFORK` or fresh post-fork `Scudo` allocations (`RGSR_EL1` re-seeded per child) are used, mirroring the classic *Morula* `Zygote` ASLR/canary sharing trap [275, 284]!

![Figure: TIKTAG-v1 and TIKTAG-v2 speculative MTE tag oracle mechanics versus Android browser and OS mitigations.](diagrams/08-extra-tiktag-speculative-oracle.svg)

Second, examine why *speculative execution side channels (`TIKTAG-v1` and `TIKTAG-v2`, Kim et al., ACM CCS 2024 [287])* shattered the assumption that failed tag guesses always crash the target. When an out-of-order CPU executes a tagged memory access down a *mispredicted conditional branch*, hardware must squash any architectural `SEGV_MTESERR` exception so benign mispredicted code never crashes programs; if microarchitectural cache state differs between a speculative tag match ($T_g == T_m$) and mismatch ($T_g \ne T_m$), an attacker can sweep all 15 candidate tags $T_g \in \{1..15\}$ crashlessly [287]!

In `TIKTAG-v1` (verified on `Arm Cortex-X3` in Pixel 8 in both `SYNC` and `ASYNC` modes), executing two or more speculative `LDR`s on `guess_ptr` within 5 cycles of a mispredicted branch triggers an Arm wrong-path power optimization on tag mismatch: the core *shrinks its speculative execution window and aborts hardware data prefetching* of a subsequent `test_ptr` located `> 10` cycles downstream, creating a stark L1 cache hit-rate drop measurable via `CNTVCT_EL0` or shared-memory timers [287]! In `TIKTAG-v2` (verified on the 5-wide `Arm Cortex-A715` in Pixel 8), executing a speculative `STR test_ptr, [guess_ptr]` followed within `< 4` instructions (same dispatch cycle) by `LDR ptr, [guess_ptr]` and `LDR [ptr]` succeeds via *Store-to-Load Forwarding (`STLF`)* in the Load-Store Queue when $T_g == T_m$ (caching `test_ptr`), whereas a tag mismatch blocks `STLF` and leaves `test_ptr` uncached [287]! Using JIT-compiled JavaScript in Chrome V8 or eBPF/syscall gadgets against `CONFIG_KASAN_HW_TAGS` Linux kernels, `TIKTAG` leaked arbitrary 4-bit `MTE` tags in *under 4 seconds with `> 95%` accuracy* without triggering a single `SIGSEGV` [287].

Look at how Android's defense-in-depth architecture counters `TIKTAG` across layers [39, 285, 287]: Android acknowledged the Pixel 8 hardware oracle, while Android 16/17 `Advanced Protection Mode` ([Chapter 11](11-accessibility-advanced-protection.md)) disables V8 JavaScript JIT compilation and `WebGPU` on untrusted web origins (`GrapheneOS`'s `Vanadium` browser disables JIT by default as well [289]), stripping remote web attackers of both the sub-nanosecond timer primitives and the native speculative gadget compiler required to mount `TIKTAG` from a webpage [39, 287]! Even if an attacker defeated `MTE` inside a browser renderer, that renderer remains trapped inside a zero-permission `u0_i*` `isolatedProcess` jail mediated by kernel `Binder` capabilities. Part III now ascends into userspace, starting in [Chapter 9](09-uid-zygote-binder.md) with `UID` sandboxing, `Zygote`, `WebView` isolation, and `Binder` IPC.

## Inspecting via ADB, Fastboot, & Attestation

Verify hardware `Arm MTE`, Pointer Authentication (`paca`), and Branch Target Identification (`bti`) CPU support alongside active `memtag` system properties:

```bash
adb shell grep -m 1 'Features' /proc/cpuinfo | tr ' ' '\n' | grep -E '^(mte|paca|bti)'
adb shell getprop | grep -iE 'memtag|mte' | head -n 8
```

Inspect per-core preferred `MTE` Tag Check Fault (`TCF`) modes (`sync`, `asymm`, `async`) configured by `init` across heterogeneous little, medium, and big CPU cores:

```bash
adb shell head -n 1 /sys/devices/system/cpu/cpu*/mte_tcf_preferred 2>/dev/null
```

Query bootloader `misc_memtag_message` support (`ro.arm64.memtag.bootctl_supported`) and current `arm64.memtag.bootctl` state (`memtag`, `memtag-once`, or `none`) on `MTE`-capable handsets:

```bash
adb shell getprop ro.arm64.memtag.bootctl_supported
adb shell getprop arm64.memtag.bootctl
```

Inspect native heap allocator (`Scudo`) memory mappings on a hardened daemon such as `com.android.nfc` or `bluetooth`:

```bash
adb shell dumpsys meminfo com.android.nfc | head -n 14
```
