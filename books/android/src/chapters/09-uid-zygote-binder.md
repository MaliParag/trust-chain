# Per-App UID Sandboxing, WebView Isolation, and Binder IPC

## Overview

* **Link in the Chain:** Userspace principal isolation and kernel object-capability IPC layer; instantiates every installed application inside a unique Linux `UID` via `Zygote`, confines untrusted web renderers inside zero-permission `isolatedProcess` `UID`s, and mediates all cross-process calls through `/dev/binder`.
* **Core Security Invariant:** No two modern applications signed by distinct developer keys share a Linux `UID`, ephemeral `isolated_app` processes possess zero filesystem, network, or permission authority, and the kernel `Binder` driver stamps every transaction with unforgeable `sender_euid` and `sender_pid` credentials while translating object references exclusively through per-process kernel red-black capability trees (`proc->refs_by_desc`).
* **Ecosystem Enforcement Tier:** Enforced identically across `GREEN` and `YELLOW` locked states (`GrapheneOS` further hardens `WebView` via `Vanadium` per-site JIT disabling and virtualized scopes); remains active in `ORANGE` unlocked state unless explicitly bypassed by root `su` daemons.
* **Trusted Computing Base (TCB):** `PackageManagerService` `/data/system/packages.xml` `appId` allocator, `Zygote64`, `AppZygote`, and `WebViewZygote` fork servers (`com_android_internal_os_Zygote.cpp`), Linux kernel `Binder` driver (`drivers/android/binder.c` and Rust `drivers/android/binder/`), `servicemanager`, and `ActivityManagerService` `Parcel` / `Intent` / `UriPermission` reference monitors.
* **Seam & Handoff:** Prevents direct cross-app memory or file tampering and guarantees unforgeable IPC caller identity, while exposing subtle deserialization (`Parcel` read/write mismatch) and application-logic (`Intent` redirection, `PendingIntent`, `FileProvider`) confused-deputy seams; hands cryptographic package identity and `Scoped Storage` to [Chapter 10](10-apk-signing-scoped-storage.md).

## Threat Model & Ecosystem Constraint

Kernel Mandatory Access Control ([Chapter 6](06-selinux-seccomp.md)), `GKI` `KCFI`/`Rust` ([Chapter 7](07-treble-gki-rust.md)), and hardware `Arm MTE` ([Chapter 8](08-arm-mte-scudo.md)) erect hardened walls around a Linux process, yet a smartphone operating system cannot leave applications sealed inside mute, isolated vaults [2, 73]. A camera app must hand a single captured JPEG to a messaging client without exposing the user's entire photo library; a banking or email app must render untrusted HTML promotional messages inside an embedded `WebView` without surrendering its SQLite session tokens if Chromium's `Blink` or `V8` suffers a renderer zero-day; and dozens of concurrent apps and HALs must invoke `system_server` APIs thousands of times per second at sub-millisecond latency without triply copying megabyte buffers across POSIX sockets [2, 69, 73].

Desktop UNIX workstations historically treated every program launched by Alice as a single omnipotent `UID 1000` principal: a compromised PDF viewer or npm script immediately read `~/.ssh/id_ed25519` and browser cookies. Android inverted that forty-year desktop paradigm from day one by turning the Linux `UID` from a *human user identifier* into a *per-application principal sandbox* [2, 21]. Three distinct adversaries probe the seams of this userspace substrate continuously:

First, a *remote web-content adversary* delivers crafted HTML, WebAssembly, or media inside an in-app `WebView` or browser tab, aiming to pivot from native renderer RCE into the host application's `/data/user/0/<pkg>` credential directory or the `EL1` kernel (`CVE-2019-2215` [218]) [69].

Second, a *malicious co-installed zero-permission application* (`u0_a250`) exploits shared `Zygote` fork memory layouts to defeat `ASLR` and stack canaries (*Morula* [284]), or hammers `/dev/binder` with multi-threaded reference-counting races and asymmetric `Parcel` byte streams (`CVE-2023-20963` [290]) to trick `system_server` (`UID 1000`) into minting forged `Intent` objects on its behalf [73, 290, 291].

Third, a *local confused-deputy adversary* sends crafted outer `Intent`s, mutable `PendingIntent`s, or `..`-laden `content://` URIs to exported `Activity`, `BroadcastReceiver`, `Service`, or `ContentProvider` endpoints of privileged OEM preloads (`priv_app`) or third-party apps, coaxing the victim into exercising its own permissions for the attacker [104, 114, 292, 293].

## Architecture & AOSP Implementation

### `UID` Arithmetic, `ZygoteInit` (`forkAndSpecialize`), and the Fork-Sharing Entropy Trap

At APK installation time, `PackageManagerService` allocates a unique Application ID (`appId`) from `[AID_APP_START, AID_APP_END]` (`10000..19999`, defined in `system/core/libcutils/include/private/android_filesystem_config.h`), recording the binding inside `/data/system/packages.xml` [21]. To support multiple human users and enterprise Work Profiles ([Chapter 17](17-android-enterprise.md)) on a single handset without colliding POSIX `UID`s, `UserHandle` computes each process's effective kernel `UID` via deterministic modular arithmetic [21, 70]:

$$\text{UID}(u, \text{appId}) = 100000 \cdot u + \text{appId}$$

Thus an app assigned `appId = 10214` runs as `UID 10214` (`u0_a214`) in primary personal profile $u = 0$, and as `UID 1010214` (`u10_a214`) inside Work Profile $u = 10$, isolated simultaneously by POSIX `DAC` `UID` checks and `SELinux` `MCS` category sets (`c512` vs. `c522`, [Chapter 6](06-selinux-seccomp.md)) [70, 224]. Early Android permitted apps signed by the same developer certificate to declare `android:sharedUserId` so multiple APKs merged into one `appId` and address space; because `sharedUserId` dissolved inter-app sandboxes and broke key rotation ([Chapter 10](10-apk-signing-scoped-storage.md)), Android 10 (`API 29`) deprecated `sharedUserId` and Android 13 (`API 33`) added `android:sharedUserMaxSdkVersion="32"` so existing suites could shed shared `UID`s cleanly without losing user data [21, 294].

Spawning a fresh Android Runtime (`ART`) virtual machine from a cold `execve()` on every app launch would add hundreds of milliseconds of startup latency and tens of megabytes of duplicate `dex`/`oat` metadata per process. Instead, `init` launches `Zygote64` (`/system/bin/app_process64 -Xzygote`) during early boot [236, 295]. Inside `ZygoteInit.main()` (`frameworks/base/core/java/com/android/internal/os/ZygoteInit.java`), `Zygote64` maps the precompiled `ART` boot image (`boot.art` and `boot-framework.oat`), preloads thousands of core framework Java classes, `ICU` Unicode tables, OpenGL/Vulkan loaders, and `Bionic` native libraries (`libandroid_runtime.so`), and opens the privileged UNIX domain control socket `/dev/socket/zygote` (plus optional Unspecialized App Process `USAP` warm pools `/dev/socket/usap_pool_primary`), accessible exclusively to `system_server` under `0660` DAC + `SELinux` `zygote_socket` policy [236, 295].

![Figure: Process hierarchy across Zygote64, AppZygote, and WebViewZygote ephemeral u0_i* isolatedProcess renderer sandboxes.](diagrams/09-zygote-webview-uid-tree.svg)

When `ActivityManagerService` launches an application, it transmits verified specialization parameters (`uid`, `gid`, supplementary `gids[]`, `runtime_flags`, `mount_external`, `se_info`, `nice_name`) over `/dev/socket/zygote`, invoking JNI `com_android_internal_os_Zygote.cpp` (`ForkCommon()` followed by `SpecializeCommon()`) [236, 237]. Look closely at the security invariants `ForkCommon()` and `SpecializeCommon()` enforce before a single instruction of app code runs [236, 237]: first, `Zygote` audits its open file descriptor table (`FileDescriptorTable::Create()`), detaching `/dev/socket/zygote` and aborting immediately if any unexpected `Zygote` file descriptor would leak across `fork()` into the untrusted child; second, `fork()` clones `Zygote64`'s pre-warmed `ART` heap and shared libraries via hardware Copy-on-Write (`COW`); third, `SpecializeCommon()` unshares mount namespaces (`CLONE_NEWNS`), drops all POSIX capabilities and `PR_CAPBSET_DROP` bounding bits, switches real/effective/saved GIDs and UIDs via `setresgid()` and `setresuid()`, installs `Bionic`'s `FilterType::APP` `seccomp-BPF` syscall filter (`PR_SET_NO_NEW_PRIVS = 1`), and calls `selinux_android_setcontext()` to lock the child into `untrusted_app` before returning to Java `ActivityThread.main()` *without ever calling `execve()`* [72, 236, 237].

Pause and examine the profound cryptographic side effect of skipping `execve()`, famously analyzed in *Morula* (Lee et al., IEEE S&P 2015 [284]): *because Linux assigns `ASLR` `mmap_base` layout and initializes `Bionic`'s TLS stack-protector canary (`__stack_chk_guard`) at `execve()` time inside `Zygote64`, every child forked from `Zygote64` (including `system_server` at `UID 1000` and every installed third-party app) inherits the exact same virtual base addresses for `libc.so`, `libart.so`, and `boot.art`, and the exact same 64-bit stack canary* [284]! On pre-`ARMv8.3` Android phones, a zero-permission malicious app (`u0_a250`) could simply read `/proc/self/maps` and its own TLS slot in-process to learn the exact `ASLR` gadget offsets and stack canary of `system_server` or a target banking app, turning a remote or IPC memory-corruption bug directly into ROP without needing a separate info-leak vulnerability [284]!

Modern Android closes that `Zygote` fork-sharing weakness through four layered hardware and allocator countermeasures without sacrificing `COW` launch speed [32, 255, 266, 296]: first, `x18` `Shadow Call Stack` (`SCS`, [Chapter 7](07-treble-gki-rust.md)) allocates a fresh, randomly positioned guard-page-isolated shadow stack on every thread creation (`pthread_create.cpp`), making leaked TLS stack canaries irrelevant for return-address hijacking [255]; second, on `ARMv8.3-A+` silicon, Pointer Authentication (`PACIASP` / `AUTIASP`) signs return addresses and pointers using 128-bit hardware `APIAKey_EL1` keys that the kernel *re-randomizes freshly per child process* during `Zygote` specialization (`prctl(PR_PAC_RESET_KEYS)`), so pointer authentication codes (`PAC`s) computed in `u0_a250` are cryptographically invalid inside `system_server` or `u0_a214` [296]; third, `Scudo` ([Chapter 8](08-arm-mte-scudo.md)) re-seeds its per-process header `CRC` cookie, randomized free-list shufflers, and `RGSR_EL1` `MTE` random tag generator post-fork so post-launch heap layouts and `MTE` tags diverge completely across sibling apps [266, 279]; and fourth, network-facing `WebView` renderers spawn from a separate `WebViewZygote` tree [69, 236].

### Multiprocess `WebView`, `isolatedProcess="true"`, and `AppZygote` Preloaders

Consider what happens when a financial app (`u0_a214`) embeds `android.webkit.WebView` to render dynamic statements or third-party OAuth pages: if Chromium's `Blink` CSS engine or `V8` JIT compiler ran inside `u0_a214`'s own process, any web renderer exploit would immediately read `/data/user/0/com.bank/databases/` [69]. Since Android 8.0 (`Oreo`), Android isolates `WebView` rendering out-of-process using `android:isolatedProcess="true"` backed by a dedicated `WebViewZygote` fork server [69, 236, 297].

Whenever any host app instantiates a `WebView`, `ActivityManagerService` instructs `WebViewZygote` (which preloads the `WebView` Chromium APK's native `libmonochrome.so` / `libwebviewchromium.so` into a separate address space from `Zygote64`) to spawn a renderer child assigned a transient, ephemeral `UID` drawn from `[AID_ISOLATED_START, AID_ISOLATED_END]` (`99000..99999`, shown as `u0_i*` in `ps`) and locked into the `isolated_app` `SELinux` domain [21, 69, 229]. An `isolated_app` renderer is stripped down to pure computation: it inherits *zero* permissions held by the host banking app, holds no supplementary network GID (`AID_INET` is absent, so `socket(AF_INET, ...)` fails immediately in the kernel!), cannot open *any* directory on `/data` or `/storage`, and is blocked by `service_contexts` (`servicemanager`) from looking up `IActivityManager`, `IPackageManager`, or `IKeystoreService`, communicating exclusively over a pre-established Mojo/`Binder` file-descriptor channel brokered by the host process [24, 69].

For complex applications (such as messaging suites or browsers) that ship custom native libraries yet want `isolatedProcess` confinement without re-running `dlopen()` on every worker spawn, Android 10 introduced `AppZygote` (`android:useAppZygote="true"`, `[AID_APP_ZYGOTE_START, AID_APP_ZYGOTE_END]` = `90000..98999`) [21, 236, 297]. `AppZygote` lets the package preload its own `.so` code inside a networkless `app_zygote` intermediate server guarded by `FilterType::APP_ZYGOTE` `seccomp-BPF` ([Chapter 6](06-selinux-seccomp.md)), which inspects `setresuid` arguments in BPF to ensure children can transition *only* into that app's assigned isolated `UID` sub-range [235, 297].

### Kernel `Binder` IPC (`drivers/android/binder.c` & Rust `drivers/android/binder/`): Single-Copy `VM_RDONLY` Buffers and Object Capabilities

With System V IPC compiled out of `GKI` (`CONFIG_SYSVIPC` disabled so dead apps cannot leak global segments) and cross-app UNIX domain sockets blocked by `SELinux`, virtually every RPC, `Intent`, `ContentProvider` cursor, and `AIDL` HAL call traverses the kernel `Binder` driver (`drivers/android/binder.c` and `binder_alloc.c`, succeeded on `android16-6.12`+ by Rust `drivers/android/binder/`) [73, 264, 298].

Two design properties elevate `Binder` far above ordinary message queues. First is its *single-copy `VM_RDONLY` `mmap()` transport* (`drivers/android/binder_alloc.c` [73, 298]): when a process opens `/dev/binder`, `libbinder` (`ProcessState`) calls `mmap()` to reserve a virtual receive arena (`1 MiB - 8 KiB` for standard apps; `4 MiB` for `system_server`) whose VMA flags are forced by the driver to `VM_RDONLY | VM_DONTCOPY | VM_MIXEDMAP` [298]. Because the recipient's own virtual mapping is strictly read-only (`VM_RDONLY`), a malicious recipient thread cannot race-modify incoming `Parcel` headers while another thread parses them! During `ioctl(fd, BINDER_WRITE_READ)` carrying `BC_TRANSACTION` (enhanced with scatter-gather `BINDER_TYPE_PTR` buffers in Android 8+ [73]), the kernel allocates physical pages on demand inside the target's `binder_alloc` arena, maps them into kernel virtual space, and runs `copy_from_user()` *once* directly from the sender's buffer into those target-mapped physical frames before queueing `BR_TRANSACTION` on the recipient's todo list [73, 298].

![Figure: Kernel Binder unforgeable sender_euid mediation vs. application-layer nested Intent redirection confused-deputy attack.](diagrams/09-binder-capability-vs-intent.svg)

Second, `Binder` implements a true *kernel-mediated object-capability model* (in the formal sense of Mark Miller [299]) across process boundaries [2, 73, 298, 300]. Inside `EL1`, every open `/dev/binder` instance owns a `struct binder_proc` containing three red-black trees: `proc->nodes` (keyed by the server's userspace `BBinder*` object pointer, storing `struct binder_node` alongside a secret 64-bit `cookie`), `proc->refs_by_node`, and `proc->refs_by_desc` (keyed by process-local 32-bit integer descriptor `desc`, where `desc == 0` is reserved exclusively for the context's `servicemanager`) [298, 300]:

```c
/* Wire object translation inside include/uapi/linux/android/binder.h */
struct binder_transaction_data {
    union { __u32 handle; binder_uintptr_t ptr; } target;
    binder_uintptr_t cookie;    /* Delivered to server only on local BBinder dispatch */
    __u32            code;      /* AIDL method ordinal (FIRST_CALL_TRANSACTION + n)  */
    __u32            flags;     /* TF_ONE_WAY (async) or 0 (synchronous RPC)         */
    pid_t            sender_pid;/* Kernel-stamped current->tgid (0 on oneway!)       */
    uid_t            sender_euid;/* Kernel-stamped from_kuid(current_cred()->euid)   */
    binder_size_t    data_size; /* Byte length of serialized Parcel payload          */
    binder_size_t    offsets_size; /* Out-of-band table of flat_binder_object offsets */
    /* ... data.ptr.buffer and data.ptr.offsets ... */
};
```

Trace why an untrusted app (`Process C`) *cannot forge an integer `handle` to invoke an unshared `IBinder` token* (such as a private `WindowToken`, `IContentObserver`, or `PendingIntent` `IIntentSender` held between `Process A` and `Process B`) [73, 298]: when `Process A` exports a local `BBinder` object in a `Parcel` (`hdr.type = BINDER_TYPE_BINDER`, `binder = &obj`, `cookie = secret`), the kernel walks the out-of-band `offsets` array, checks `SELinux` `binder { transfer }`, creates `binder_node` in `Process A`'s `proc->nodes`, allocates the lowest unused local integer `desc` (say `handle = 4`) in `Process B`'s `proc->refs_by_desc` pointing to that `binder_node`, and rewrites the in-flight struct in `Process B`'s `VM_RDONLY` buffer to `hdr.type = BINDER_TYPE_HANDLE, handle = 4` (stripping `Process A`'s raw `BBinder` virtual address so `ASLR` never leaks across processes!) [298, 300]. If `Process C` guesses `target.handle = 4` in its own `BC_TRANSACTION`, the kernel looks up `desc = 4` inside *`Process C`'s own isolated `proc->refs_by_desc` tree*, finding either `-EINVAL` or an unrelated service `Process C` already legitimately held! Simultaneously, for every `BINDER_TYPE_FD` / `BINDER_TYPE_FDA` object in `offsets`, the kernel duplicates the sender's `struct file*` directly into a fresh file descriptor slot in the recipient's `files_struct` (used everywhere from `Scoped Storage` media FDs to `ashmem`/`memfd` shared buffers) [73, 298]. And on every transaction, the kernel stamps `sender_euid` directly from `current_cred()->euid`, surfaced in Java/C++ via `Binder.getCallingUid()` (`IPCThreadState::getCallingUid()`) [300, 301]. Whenever a privileged `system_server` method subsequently invokes another service on its own thread, it must bracket that call with `final long token = Binder.clearCallingIdentity();` and `Binder.restoreCallingIdentity(token);` in a `finally` block so downstream permission checks evaluate `UID 1000` only where intended and never confuse the deputy's identity with the untrusted caller's `UID` [302].

Because `/dev/binder` is reachable from *every* domain on Android (including Chrome's `u0_i*` `isolated_app` renderer sandbox!), any memory-safety bug inside C `drivers/android/binder.c` was an instant zero-click sandbox-escape prize [218]. In October 2019, Maddie Stone of Google Project Zero uncovered *`CVE-2019-2215` (Bad Binder)*, exploited in the wild against Pixel 1/2 and OEM phones [218]. Inside `drivers/android/binder.c`, each per-thread `struct binder_thread` embedded `wait_queue_head_t wait` (`spinlock_t lock; struct list_head task_list;`). When an attacker called `epoll_ctl(epfd, EPOLL_CTL_ADD, binder_fd, ...)` and then issued `ioctl(binder_fd, BINDER_THREAD_EXIT, NULL)`, `binder_thread_release()` immediately called `kfree(thread)` *without* notifying `epoll` via `POLLFREE`, leaving `eppoll_entry` dangling onto `thread->wait.task_list` inside freed `kmalloc-512` memory (an unlinking primitive detectable only when `CONFIG_DEBUG_LIST` was active) [218]! Reclaiming that 512-byte slab slot with a `struct iovec` array via `writev()` on a blocked pipe and then closing `epfd` triggered `remove_wait_queue()` (`__list_del`), which wrote a controlled kernel heap address straight into `iovec.iov_base`, leaking `thread->task` (`struct task_struct*`), overwriting `addr_limit` on pre-`CONFIG_ARM64_UAO` kernels (or corrupting `pipe_buffer` pointers on newer builds), and granting deterministic arbitrary `EL1` read/write to zero `cred->uid` and `selinux_state.enforcing` straight from inside `isolated_app` [218]! Subsequent C lock-dropping races in `binder_inc_ref_for_node()` (`CVE-2022-20421` [303]) and `binder_transaction_buffer_release()` (`CVE-2023-20938` [304]) motivated Google's complete rewrite of the driver in memory-safe Rust (`drivers/android/binder/`, shipped in `android16-6.12` [77, 245, 264]), where `Pin<&mut SpinLock<...>>`, `Arc<Node>`, and explicit death-notification list ownership guarantee at compile time that no `epoll` wait queue or transaction buffer can ever outlive its backing allocation.

### `Parcel` Deserialization Mismatches (`LaunchAnywhere` to `CVE-2023-20963` *WorkSource*) and `Intent` / `FileProvider` Confused Deputies

Even when the kernel `Binder` driver is 100 percent memory-safe in Rust, userspace services communicate by marshaling object graphs into untyped linear byte buffers (`android.os.Parcel` and key-value `android.os.Bundle` maps in `frameworks/native/libs/binder/Parcel.cpp`) [301]. For an entire decade, spanning from Retme7's `AccountManager` *LaunchAnywhere* (`CVE-2013-6272` [291]) through `OutputConfiguration` (`CVE-2017-13286`) and `PeriodicAdvertisingReport` (`CVE-2017-13288` [305]) all the way to *`CVE-2023-20963` (`android.os.WorkSource`)*, exploited in the wild in 2023 to escalate commercial shopping malware into `system_server` (`UID 1000`) [290], Android suffered a devastating class of pure-Java deserialization bugs: *`Parcel` read/write byte-length mismatches*!

![Figure: Parcel read/write deserialization mismatch (LaunchAnywhere to CVE-2023-20963 WorkSource) turning system_server into a confused deputy.](diagrams/09-extra-parcel-mismatch-confused-deputy.svg)

Trace the exact byte-stream mechanics of a *self-mutating `Bundle`* across `CVE-2017-13286`..`CVE-2023-20963` [290, 291, 305, 306]: in `AccountManagerService` (running as `UID 1000` inside `system_server`), an untrusted app can register a custom `AbstractAccountAuthenticator` whose `addAccount()` callback returns a `Bundle` to `system_server`. If that `Bundle` contains `AccountManager.KEY_INTENT`, `system_server` inspects the `Intent` target to verify that the authenticator owns the target Activity before launching it with `system` privileges. Prior to Android 13, `BaseBundle` serialized entries sequentially as `[key_1][type_1][value_1][key_2][type_2][value_2]` *without storing the byte length of each individual `Parcelable` value*!

Suppose `WorkSource` (`CVE-2023-20963`, where `mChains` handling disagreed between `new WorkSource(Parcel)` and `writeToParcel()` [290]) or `PeriodicAdvertisingReport` (`CVE-2017-13288`, reading a 64-bit `long` in `readFromParcel` while writing a 32-bit `int` in `writeToParcel` [305]) consumes $N$ bytes during `createFromParcel()`, yet writes $M < N$ bytes during `writeToParcel()`. The attacker crafts a `Bundle` whose Entry 1 is the buggy `Parcelable` padded so its trailing $N - M$ bytes swallow the header of Entry 2, hiding the string `"intent"` (`KEY_INTENT`) inside what `system_server`'s first unparcel pass thinks is harmless trailing data! `system_server` checks `bundle.getParcelable(KEY_INTENT)`, sees `null`, marks the `Bundle` safe, and *re-serializes* `bundle.writeToParcel()` to forward it across IPC. On re-serialization, Entry 1 writes only $M$ bytes, shifting the `Parcel` read cursor backward by $N - M$ bytes so that on the *second* unparceling pass, `"intent"` (`KEY_INTENT` targeting internal `com.android.settings.password.ChooseLockPassword` or arbitrary `UID 1000` receivers!) materializes out of thin air with `system_server`'s blessing [290, 305]! Android 13 (`API 33`) finally severed this entire bug class structurally by prefixing every `Parcelable` inside a `Bundle` (`LazyValue`) with its exact serialized byte length, throwing an immediate `BadParcelableException` if `createFromParcel()` fails to land on the exact end offset, paired with type-checked `Bundle.getParcelable(key, Class<T>.class)` (`SAFER_PARCEL`) so unexpected `Parcelable` classes can never be instantiated during key lookup [104, 306]!

Above `Parcel` serialization sit three classic application-layer confused deputies [104, 114, 292, 293, 307]: first, *`Intent` Redirection*, where an exported proxy component extracts a nested `Intent` extra (`getParcelableExtra("next")`) and passes it to `startActivity()`, letting an attacker launch the victim's non-exported internal Activities or attach `FLAG_GRANT_READ_URI_PERMISSION | FLAG_GRANT_WRITE_URI_PERMISSION` on `content://com.victim.fileprovider/...` URIs! Android 12 (`API 31`) mandated explicit `android:exported="true|false"` on every component with `<intent-filter>` and added `StrictMode` `detectUnsafeIntentLaunch()`, culminating in Android 16's *by-default platform `Intent` redirection blocker* (`CreatorToken` tracking in `ActivityManagerService` that aborts unvetted nested launches unless the developer explicitly calls `Intent.removeLaunchSecurityProtection()` or `IntentSanitizer`) [104, 307]! Second, *mutable `PendingIntent` hijacking*: because a `PendingIntent` wraps an `IIntentSender` kernel `Binder` token executing with its creator's `UID` and permissions, leaving fields blank on a mutable `PendingIntent` let malicious recipients invoke `Intent.fillIn()` to redirect the target package or steal URI grants; Android 12 forced every `PendingIntent` to declare `FLAG_IMMUTABLE` (or explicit `FLAG_MUTABLE`), Android 14 banned implicit `Intent`s inside `FLAG_MUTABLE` `PendingIntent`s outright, and one-time actions require `FLAG_ONE_SHOT` to prevent token replay [292]. Third, *`ContentProvider` / `FileProvider` path traversal*: custom `ContentProvider.openFile(Uri)` implementations that concatenate `uri.getPath()` without verifying `file.getCanonicalPath().startsWith(expectedRoot)` allow `..%2F..%2Fdatabases/secret.db` escapes, which standard `androidx.core.content.FileProvider` prevents via strict XML root canonicalization [114, 293].

## Vendor, OEM, & Custom-OS Boundaries

Preloaded OEM and carrier system packages (`/product/priv-app`, `/system_ext/priv-app`, and `/vendor/app` running as `UID 1000` or holding `signature|privileged` permissions) remain the widest userspace confused-deputy surface on commercial Android phones [114, 308]. Although AOSP's `privapp-permissions.xml` gate (`CTS` `PrivAppPermissionsTest` [308]) forces OEMs to explicitly allowlist every privileged permission granted to preloaded apps, `CTS` cannot audit custom business logic inside hundreds of carrier diagnostic, theme-store, or cloud-sync Activities, where security researchers (`Oversecured` [114]) routinely uncover exported `Intent` redirections and uncanonicalized `ContentProvider`s. Lean software stacks (`Pixel` and especially `GrapheneOS`, which bundles zero carrier/OEM `priv-app` bloatware and ships `Vanadium` as its hardened `WebView` and browser with JavaScript JIT disabled by default and strict `CFI`/`MTE` active [20, 289]) eliminate that preloaded deputy surface entirely.

### Why `UID` Sandboxing Rests Entirely on Cryptographic Package Identity

Step back and examine the hidden foundation underneath `packages.xml` and `Zygote` `UID` isolation: when a user installs an update to `com.bank` (`v2.0` over `v1.0`), `PackageManagerService` assigns `v2.0` the *exact same `u0_a214` `UID` and `s0:c214,c256,c512,c768` `SELinux` `MCS` label*, handing `v2.0` immediate read/write access to `v1.0`'s SQLite databases and `Keystore2` keys!

> **Key takeaway.**
> Kernel `Binder` capabilities and `Zygote` `UID` walls guarantee that `u0_a250` cannot impersonate `u0_a214` at runtime, yet the *sole* invariant proving at install time that `com.bank v2.0` comes from the legitimate author of `v1.0` (and that no attacker tampered with `classes.dex` in transit or spun up an anonymous bank-impersonating clone) is Android's cryptographic APK signing and developer verification architecture, paired with `Scoped Storage` to govern shared files outside `/data/user/0`. [Chapter 10](10-apk-signing-scoped-storage.md) dissects that layer end to end.

## Inspecting via ADB, Fastboot, & Attestation

Inspect a package's allocated `appId`, `SELinux` `seInfo`, and live `WebViewZygote` ephemeral `u0_i*` `isolated_app` renderer children:

```bash
adb shell dumpsys package com.android.chrome | grep -E 'appId=|seInfo=|targetSdk=' | head -n 6
adb shell ps -AZ | grep -E 'u0_i[0-9]+|webview_zygote' | head -n 6
```

Inspect active kernel `/dev/binder` nodes, Unspecialized App Process (`USAP`) / `Zygote` sockets, and registered `servicemanager` capabilities:

```bash
adb shell ls -lZ /dev/binder* /dev/socket/zygote* 2>/dev/null
adb shell service list | head -n 8
```

Audit exported `Activity`, `Service`, `Receiver`, and `ContentProvider` surfaces on a preloaded package via `dumpsys package`:

```bash
adb shell dumpsys package com.android.settings | grep -A 3 'Activity Resolver Table:'
```
