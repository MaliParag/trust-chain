# Confidential VMs and Open Paravisors: SEV-SNP, TDX, and COCONUT-SVSM

## Overview

* **Link in the Chain:** Inverts the cloud trust model of [Chapters 14](14-containers-escapes.md) through [17](17-ai-agent-sandboxes.md): removes the cloud provider's host Linux kernel (`KVM`), `QEMU`/`Cloud Hypervisor` VMM, and physical DRAM bus from the guest Linux VM's Trusted Computing Base using CPU memory encryption, page-ownership tables, and an intra-enclave Rust paravisor (`COCONUT-SVSM`).
* **Core Security Invariant:** Hardware memory controllers encrypt guest DRAM under per-VM keys and enforce 1-to-1 guest-to-physical page ownership (`AMD SEV-SNP` `RMP`, `Intel TDX` `SEAM`/`S-EPT`, `Arm CCA` `GPT`) so host hypervisor reads return ciphertext and host page remaps/replays fault immediately; inside the enclave, `COCONUT-SVSM` runs at `VMPL0` to furnish a hardware-measured `vTPM`, while `arch/x86/coco` filters untrusted `#VC`/`#VE` traps, `CPUID`/`MSR` values, and DMA bounce buffers.
* **Deployment Profile Matrix:** Standard cloud VMs trust host `KVM` completely; regulated financial, sovereign-cloud, and AI workloads deploy `SEV-SNP` (`AMD EPYC Milan/Genoa/Turin`), `Intel TDX` (`4th/5th/6th Gen Xeon`), or `Arm CCA` Confidential VMs booting measured `UKI` images paired with `COCONUT-SVSM` (or cloud paravisors) and `NVIDIA H100`/`B200` Confidential GPUs over `SPDM`.
* **Trusted Computing Base (TCB):** CPU silicon and signed microcode/firmware (`AMD ASP`/`PSP` + `VCEK`, `Intel TDX SEAM Module` + `PCK`, `Arm EL3 RMM`), `COCONUT-SVSM` (`VMPL0` Rust paravisor + `vTPM`), measured OVMF/UKI guest image, and confidential `NVIDIA` GPU silicon/firmware when attached.
* **Integration Seam & Handoff:** Establishes an encrypted, hardware-attested Linux VM with a measured `vTPM` (`PCR[11]`) even atop a compromised cloud host; hands off enclave-per-pod Kubernetes orchestration and remote key release (`Confidential Containers` + `Trustee`) to [Chapter 19](19-confidential-containers.md).

## Problem Statement & Threat Model

Every Linux security mechanism analyzed from [Chapter 1](01-uefi-shim-sbat.md) through [Chapter 17](17-ai-agent-sandboxes.md) rested on one unspoken axiom: *whoever controls the physical motherboard and host `VMX Root` / `EL2` hypervisor is trusted*. On a standard public-cloud Virtual Machine, that axiom hands total plaintext visibility to the cloud infrastructure layer [140, 141]. A compromised host `KVM` kernel, a rogue `QEMU` process, a malicious data-center technician probing DDR5 DIMMs, or a court-compelled host operator can read every byte of guest `LUKS2` master keys, TLS private keys, and proprietary AI weights via `/dev/mem` or `virsh dump`, modify guest Ring 0 `.text` pages in place via `EPT`/`NPT`, or extract secrets from a host-resident software `swtpm` virtual TPM!

Confidential Computing flips that threat model upside down: the guest Linux VM is the defended asset, and the host hypervisor (`KVM`/`VMM`), host OS (`UID 0` and host Ring 0), PCIe switches, and physical DRAM chips are treated as an active Byzantinely malicious adversary (trusted *only* to schedule vCPUs and deliver network/storage I/O, never for confidentiality or integrity; denial-of-service by halting vCPUs remains an inherent power of any host) [140, 141, 142].

Engineering Linux to survive a malicious hypervisor exposed three deep architectural challenges [140, 143, 144, 146]:
First, *encrypting DRAM alone is broken*: early `AMD SEV` (2016) encrypted guest pages with `AES` without integrity or GPA-to-SPA binding, allowing a malicious hypervisor to remap guest physical page $A$ onto guest physical page $B$ inside Nested Page Tables (`NPT`) or replay captured ciphertext blocks to build decryption/execution oracles! Silicon had to add hardware page-ownership tables (`SEV-SNP` `RMP` and `Intel TDX` `S-EPT`) [140, 141].
Second, *who hosts the guest's `TPM 2.0`?* Standard cloud VMs implement `vTPM` as a `swtpm` process on the *host*: which in a Confidential VM means handing your `PCR[11]` `LUKS2` key straight to the untrusted hypervisor! Confidential Linux needed an open-source, auditable, memory-safe paravisor running *inside* the encrypted enclave at a higher privilege tier than the guest kernel itself (`COCONUT-SVSM` [143]).
Third, *thirty years of Linux kernel code assumed hardware never lies*: when an untrusted hypervisor emulates `CPUID`, `RDMSR`, `MMIO`, `ACPI` tables, PCI hotplug, and `#VC`/`#VE` exceptions (`WeSee` `CVE-2024-25742` [144]), every unvalidated hardware register read becomes a direct Ring 0 exploit vector into the confidential guest [146]!

## Kernel & Userspace Mechanics

### Silicon Isolation Roots: `AMD SEV-SNP`, `Intel TDX`, and `Arm CCA`

Across all three server CPU architectures, Confidential VM silicon enforces three coupled properties: *per-VM memory encryption*, *cryptographic launch measurement*, and *hardware 1-to-1 physical-page integrity* [140, 141, 142]:

On `AMD SEV-SNP` (*Secure Encrypted Virtualization-Secure Nested Paging* [140]), the on-die AMD Secure Processor (`ASP`) programs a dedicated hardware AES-128-XTS engine inside each memory controller keyed by the guest's Address Space Identifier (`ASID`). Inside guest page tables, a high physical-address bit (the `C-bit`, typically bit `51`) marks pages Private (`C = 1`, encrypted in DRAM and unreadable by host `Ring 0`) vs. Shared (`C = 0`, unencrypted `SWIOTLB` bounce buffers intentionally shared with host `virtio` drivers for network/disk DMA) [140]. To defeat hypervisor `NPT` remapping and replay attacks, `SEV-SNP` reserves a contiguous region of DRAM for the silicon-enforced Reverse Map Table (`RMP`), indexed directly by $4\text{ KiB}$ System Physical Address (`SPA`). Every `RMP[SPA]` entry records `(Assigned, ASID, GPA, PageSize, Validated, VMPL_Permissions[0..3])`. On *every* guest memory translation, CPU hardware walks the host's `NPT` ($\text{GPA} \to \text{SPA}$) and immediately cross-checks `RMP[SPA]`:

$$\text{RMP}[\text{SPA}].\text{Assigned} = 1 \;\land\; \text{RMP}[\text{SPA}].\text{ASID} = \text{ASID}_{\text{cur}} \;\land\; \text{RMP}[\text{SPA}].\text{GPA} = \text{GPA}_{\text{req}} \;\land\; \text{RMP}[\text{SPA}].\text{Validated} = 1$$

If the untrusted host `KVM` remaps two GPAs to the same SPA, swaps pages between VMs, or substitutes unvalidated memory, hardware raises an immediate `#PF` (`PFERR_RMP_BIT`) fault; and if the guest executes `PVALIDATE` twice on a page re-backed by the host (*double-validation* attack), `PVALIDATE` clears the `CF` carry flag so the guest Linux kernel panics immediately (`terminate_ghcb`) rather than accepting replayed memory [140, 146]! Crucially, `SEV-SNP` also divides a single guest into four Virtual Machine Privilege Levels (`VMPL0` most privileged .. `VMPL3` least privileged), where `VMPL0` executes `RMPADJUST` to strip write/execute permissions from `VMPL1..3` on `VMPL0`'s own pages!

`Intel TDX` (*Trust Domain Extensions* [141]) achieves equivalent guarantees via a CPU-signed `TDX Module` executing inside a dedicated new x86 processor mode called `SEAM` (*Secure Arbitration Mode*, isolated from host `VMX Root` via Trust Domain Memory Regions `TDMRs`). Memory encryption and integrity use `MKTME` (`AES-XTS-128` or `AES-XTS-256` paired with cryptographic 28-bit SHA-3 MAC tags stored in ECC DRAM bits so even physical DDR5 interposers trigger integrity faults!). Instead of an `RMP`, the `TDX Module` maintains a private Secure EPT (`S-EPT`) inside `SEAM` memory inaccessible to host `KVM`: host `KVM` requests page additions via `TDH.MEM.PAGE.AUG`, and the guest Linux kernel explicitly accepts each page via `TDG.MEM.PAGE.ACCEPT` (`TDX 1.5+` also adds `TD Partitioning`: Intel's counterpart to `VMPL` enabling intra-TD paravisors!) [141, 146]. Meanwhile, `Arm CCA` (*Confidential Compute Architecture* [142]) adds a fourth physical address space (`Realm`) enforced at `EL3` via hardware-walked Granule Protection Tables (`GPT`) alongside a small measured `Realm Management Monitor` (`RMM`) at `R-EL2`.

### `COCONUT-SVSM` (`VMPL0` Rust Paravisor) and Confidential `NVIDIA` GPUs

How does a Confidential Linux guest use `systemd-stub` `PCR[11]`, `systemd-pcrlock`, and `LUKS2` TPM sealing ([Chapters 2](02-uki-systemd-pcrlock.md) and [3](03-luks2-verity.md)) when no physical motherboard TPM belongs exclusively to one cloud tenant?

![Figure: Confidential Linux VM architecture: COCONUT-SVSM running inside AMD SEV-SNP VMPL0 (isolated from the VMPL1 Linux guest via RMP permissions) provides an enclave-resident measured vTPM, while untrusted host KVM sees only ciphertext and explicit SWIOTLB bounce buffers.](diagrams/18-sev-snp-tdx-coconut-svsm.svg)

Developed collaboratively in `#![no_std]` memory-safe Rust across SUSE, AMD, Red Hat, IBM, and Microsoft (`coconut-svsm/svsm` [143]), `COCONUT-SVSM` (*Secure VM Service Module*) boots at `VMPL0` (and `TDX` L1 partitioning) *ahead* of guest OVMF and the guest Linux kernel! At VM launch (`SNP_LAUNCH_FINISH`), the AMD `ASP` hashes the exact initial memory pages of `COCONUT-SVSM` + OVMF into the immutable 384-bit hardware `LAUNCH_DIGEST` signed by silicon `VCEK` (Versioned Chip Endorsement Key chaining to AMD root CAs and encoding exact microcode/firmware `TCB_VERSION` SVNs!). `COCONUT-SVSM` marks its own `VMPL0` code, stack, heap, and `libtpms`/Rust `vTPM` state inaccessible to `VMPL1..3` via `RMPADJUST`, then launches OVMF and the signed Linux `UKI` inside `VMPL1` [143]! Whenever `systemd-stub` or `/dev/tpmrm0` inside `VMPL1` issues a `TPM 2.0` command (`PCR_Extend`, `PolicyAuthorize`, `Unseal`, `Quote`), the request traps cleanly across the `SVSM` Calling Area (`CAA`) into `VMPL0`: entirely inside hardware-encrypted enclave RAM, never once crossing out to the untrusted cloud host! Even if an attacker achieves a Ring 0 exploit inside the `VMPL1` guest Linux kernel, `VMPL1` cannot tamper with `VMPL0`'s `vTPM` NV/PCR state [140, 143]!

What if the confidential Linux workload needs `NVIDIA Hopper H100` or `Blackwell B200` GPU acceleration for LLM training or inference? Raw PCIe DMA cannot read `C-bit = 1` encrypted CPU RAM! `NVIDIA` Confidential Computing (`CC-On` mode [145]) extends the trust boundary across PCIe without trusting the host PCIe root complex: the Linux guest driver (`nvidia.ko` + verifier) runs the DMTF `SPDM` (`Security Protocol and Data Model`) handshake directly with the GPU's hardware Root of Trust (`ECDSA-P384` hardware-fused certificate + signed GPU firmware/VBIOS measurements, confirming debug ports and P2P BARs are locked), negotiates ephemeral `AES-GCM-256` session keys, encrypts tensors inside guest CPU `SWIOTLB` bounce buffers using `AES-GCM-256` *before* DMA, and lets the GPU copy-engine decrypt them directly inside isolated GPU HBM3e memory [145]!

### Hardening `arch/x86/coco` Against a Malicious Hypervisor (`#VC` / `#VE` and `WeSee`)

Removing the hypervisor from the TCB forces a radical rewrite of how the Linux kernel handles hardware traps and device drivers (`arch/x86/coco/` [144, 146]):

![Figure: Defending a Confidential Linux guest against a malicious host hypervisor: mitigating unsolicited #VC/#VE exception injection (WeSee CVE-2024-25742), forged CPUID/MSR values, and rogue PCI/USB device fuzzing via arch/x86/coco hardening.](diagrams/18-untrusted-vmm-vc-ve-surface.svg)

Inside a traditional VM, executing `CPUID` or `RDMSR` causes an automatic `VMExit` where `KVM` reads and writes `vcpu->arch.regs` directly. Under `SEV-SNP` and `TDX`, guest GPR register state is encrypted (`VMSA` encrypted) so `KVM` cannot read `%rax..%r15`! Instead, executing `CPUID` traps *into the guest kernel itself* via a `#VC` VMM Communication Exception (IDT vector `29` on `SEV-SNP`) or `#VE` Virtualization Exception (IDT vector `20` on `TDX`): the guest kernel's `#VC`/`#VE` handler copies *only* the requested leaf numbers into an unencrypted shared `GHCB` page, executes `VMGEXIT` (`TDVMCALL`), and copies the result back [140, 141, 146].

In 2024, researchers disclosed `WeSee` (`CVE-2024-25742` [144]): a malicious `KVM` hypervisor does not have to wait for the guest to execute `CPUID`: using standard `VMCB` `EVENTINJ`, the hypervisor injected fake `#VC` exceptions (vector `29` with `SVM_EXIT_EXCP_BASE` / `MMIO` exit codes) at arbitrary instructions inside guest Ring 0! When Linux's `#VC` handler woke up on an ordinary `mov` instruction thinking an `MMIO` trap had occurred, it decoded the `mov` instruction and helpfully copied private guest kernel register values straight out to the unencrypted `GHCB` (leaking secrets!) or overwrote guest kernel pointers with attacker-supplied hypervisor values (yielding full guest Ring 0 takeover!) [144]! Linux (`arch/x86/coco/` [146]) closed this class across three layers: (1) inspecting the exact opcode at faulting `%rip` inside `#VC` and `#VE` handlers and panicking immediately if `%rip` does not point to an explicit allowed exit opcode (or unencrypted `C=0` MMIO virtual address!); (2) enabling `SEV-SNP` *Restricted Injection* (`SNP_RESTRICTED_INJ`, forbidding the hypervisor from injecting arbitrary vector `0..31` exceptions altogether except single `#HV` doorbell notifications managed cooperatively with `VMPL0` `SVSM`!); and (3) enabling `CONFIG_DEVICE_SECURITY` / Confidential Device Filtering (`authorized_default = 0` on PCI/USB/Thunderbolt buses) so a rogue hypervisor cannot hotplug fake legacy soundcards or ISDN PCI IDs to fuzz 1990s C drivers inside guest Ring 0: admitting *only* hardened `virtio` (`F_ACCESS_Platform` enforcing strict `SWIOTLB` bounce copies + ring-descriptor length validation!) and attested `SPDM` devices [145, 146]!

## Distro, Immutable-OS, & Cloud Trade-Offs

Confidential VMs (`AWS EC2` `SEV-SNP`, `Azure` `DCasv5`/`ECasv5` `SEV-SNP` and `DCesv5` `TDX`, `GCP` Confidential VMs `SEV-SNP` / `TDX` + `H100` Confidential GPU) are supported in mainline `Linux 6.6+` / `6.12+` across `Ubuntu 24.04`, `RHEL 9.4+`, `SUSE SLES 15 SP6+`, and `Fedora` [143, 146, 151]. Note the crucial boot requirement: *booting an unmeasured mutable `/boot` partition off an untrusted cloud `virtio-blk` disk immediately defeats a Confidential VM*, because the untrusted host hypervisor can modify unsigned `/boot/initramfs` before launch! Confidential Linux VMs *must* boot a measured `OVMF` + Authenticode/launch-measured `UKI` ([Chapter 2](02-uki-systemd-pcrlock.md)) + `dm-verity` root (`roothash=` pinned inside the measured `UKI` [Chapter 3](03-luks2-verity.md)), unlocking persistent `LUKS2` data volumes *only* after hardware `SEV-SNP`/`TDX` quote attestation or `COCONUT-SVSM` `vTPM` `PCR[11]` verification succeeds [19, 143, 146]!

## Seam Failures, CVEs, & Structural Bounds

Confidential VM vulnerabilities concentrate along the guest-hypervisor `#VC`/`#VE` communication seam, unhardened guest drivers trusting `MMIO`/ring lengths, firmware `TCB_VERSION` downgrades, and side channels.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| `WeSee` (`CVE-2024-25742`) | 2024 | Linux `#VC` handler (`arch/x86/kernel/sev.c`) | `#VC` (vector `29`) fires only on genuine CPU intercepts | Malicious host injects unsolicited `#VC` (`EVENTINJ`), tricking `#VC` emulator into leaking/overwriting guest Ring 0 registers | Verify exact opcode/PTE `C-bit` at `%rip` in `#VC`/`#VE` and enable `SEV-SNP` `Restricted Injection` [144, 146] |
| `TDX` / `SEV` `virtio` Ring `SWIOTLB` Overreads (`CVE-2021-33034` / `virtio` hardening) | 2021-2024 | Guest `drivers/virtio/` ring descriptors | Hypervisor returns `len <= buffer_size` in shared `virtqueue` | Malicious VMM writes huge `used->ring[i].len` in shared `C=0` RAM, causing guest `memcpy` overflow | Enforce `VIRTIO_F_ACCESS_PLATFORM` (`SWIOTLB`) and clamp `virtqueue_get_buf` lengths strictly in Ring 0 [146] |
| Unmeasured Guest `initramfs` / Mutable `/boot` Injection | 2022-2024 | Lift-and-shift Confidential VM images | `SEV-SNP` memory encryption automatically authenticates guest disk | Host VMM edits unencrypted `/boot/initramfs` on virtual disk prior to guest boot, running backdoor inside TEE | Boot measured direct `UKI` (`LAUNCH_DIGEST` / `MRTD` + `SVSM` `vTPM`) + `dm-verity` `/usr` [19, 143] |
| Ciphertext Side Channels (`Cipherleaks` / Page-Fault Step) | 2021-2024 | Deterministic memory cipher / host `NPT` faults | Encrypted DRAM hides all execution patterns from host `KVM` | Host clears `Present` bits in `NPT`/`S-EPT` to trace 4 KiB page-fault sequences or observes deterministic `AES-XTS` tweaks on constant-secret writes | Use constant-time crypto (`OpenSSL`/`BoringSSL` blinding) and `AMD Turin` / `TDX` ciphertext-hiding updates [140, 141] |

Running an entire virtual machine inside `SEV-SNP` or `TDX` secures IaaS workloads cleanly; yet modern cloud-native teams deploy workloads as Kubernetes Pods, where a compromised worker-node `kubelet` can still hijack standard pods. [Chapter 19](19-confidential-containers.md) shrinks the Confidential VM down to an *enclave-per-pod* boundary with `Confidential Containers` (`CoCo`) and `Trustee`.

## Inspecting on a Live Linux Host

Detect whether the running Linux kernel is executing inside an active hardware Confidential VM (`SEV-SNP`, `TDX`, or `Arm CCA` `CC` attributes) via `dmesg` / `systemd-detect-virt` and CPU confidential flags:

```bash
systemd-detect-virt --cvm 2>/dev/null || true
# Reading early kernel confidential-computing boot messages may require root / run0 if dmesg_restrict=1
dmesg 2>/dev/null | grep -iE "(Memory Encryption|SEV-SNP|TDX|SVSM|SWIOTLB)" | head -n 10 || true
```

Check whether `/dev/sev-guest` or `/dev/tdx_guest` hardware attestation quote devices and `TPM 2.0` (`SVSM` `vTPM`) are exposed inside the guest:

```bash
ls -la /dev/sev-guest /dev/tdx_guest /dev/tpmrm0 2>/dev/null || echo "Host is not a Confidential VM guest"
grep -E "CONFIG_(AMD_MEM_ENCRYPT|INTEL_TDX_GUEST|COCO_SECRET)=" /boot/config-$(uname -r) 2>/dev/null
```
