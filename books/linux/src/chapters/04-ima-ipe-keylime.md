# Runtime Appraisal and Attestation: IMA, IPE, and Keylime

## Overview

* **Link in the Chain:** Completes Part I by turning passive storage integrity (`dm-verity` and `fs-verity` in [Chapter 3](03-luks2-verity.md)) into active kernel execution enforcement (`IMA-appraisal` / `EVM` and Linux 6.12+ `IPE` LSM) and cryptographic proof to off-host verifiers (`Keylime` + `IETF RATS`).
* **Core Security Invariant:** Locally, the kernel admits `execve()`, `mmap(PROT_EXEC)`, `mprotect(PROT_EXEC)`, and firmware/policy reads only when the backing file satisfies active `IMA-appraisal` signatures or `IPE` verity policy; remotely, a `Keylime` verifier grants workload trust only when a `TPM 2.0` Attestation Key bound to genuine Endorsement silicon signs a fresh nonce-bearing `TPM2_Quote` over `PCR[0..11]` and `PCR[10]` whose replayed TCG and `IMA` event logs match approved reference values.
* **Deployment Profile Matrix:** Regulated mutable servers (`RHEL`, `SUSE`, telecom/defense) deploy `IMA` measurement into `PCR[10]` + `Keylime` continuous monitoring (and selectively `IMA-appraisal` + `EVM`); modern immutable appliances (`Linux 6.12+`, Azure Linux / embedded / CoreOS-style builds) adopt `IPE` over `dm-verity` and `fs-verity`; confidential cloud pods pair `RATS` attestation with `Trustee` ([Chapter 19](19-confidential-containers.md)).
* **Trusted Computing Base (TCB):** Linux kernel `security/integrity/ima/`, `security/integrity/evm/`, and `security/ipe/` LSMs, `.ima` / `.evm` / `.secondary_trusted_keys` keyrings, `TPM 2.0` `PCR[10]` and restricted Attestation Key (`AK`), Rust `keylime_agent`, and off-box `Keylime` Registrar + Verifier + Reference Value database.
* **Integration Seam & Handoff:** Prevents unapproved files from being mapped executable and exposes tamper-evident boot/runtime evidence off-host; hands off protection of running Ring 0 memory, kernel modules, and `kexec` transitions to Part II ([Chapters 5](05-kernel-lockdown-modules.md) through [7](07-stacked-lsms-landlock.md)).

## Problem Statement & Threat Model

Suppose a Linux host boots through a Microsoft- and `SBAT`-verified `shim.efi` ([Chapter 1](01-uefi-shim-sbat.md)), authenticates a signed `Unified Kernel Image` into `PCR[11]` ([Chapter 2](02-uki-systemd-pcrlock.md)), and mounts `/usr` read-only over `dm-verity` ([Chapter 3](03-luks2-verity.md)). Two fundamental trust gaps still remain open the instant `PID 1` spawns multi-user services. First, real Linux machines always mount writable filesystems alongside `/usr`: `/var`, `/tmp`, `/run`, `/dev/shm`, and anonymous memory descriptors (`memfd_create(2)`). If a network-facing service suffers a command-injection flaw or compromised credentials, nothing in `dm-verity` prevents the attacker from writing a malicious ELF implant or Python shared object to `/dev/shm/payload.so` and calling `execve()` or `dlopen(..., RTLD_NOW)` (`mmap` with `PROT_EXEC`). Storage integrity proves `/usr/bin/python3` is authentic; it says nothing about whether `/dev/shm/payload.so` is *authorized to execute*.

Second, even when local kernel gates function properly, a remote orchestrator, Kubernetes control plane, or zero-trust relying party cannot simply take a Linux node's word over TLS that Secure Boot, `UKI`, and runtime code integrity are intact. A compromised host with a stolen TLS client key will happily report `"healthy": true` in software APIs [52, 53]. Under an adversary model where individual edge servers, telecom base stations, or bare-metal worker nodes may experience offline tampering, disabled Secure Boot, unauthorized package installations, or post-compromise binary execution, the platform needs two coupled capabilities: *local runtime appraisal* (refusing to execute or load any code artifact lacking cryptographic provenance) and *continuous remote attestation* (proving both boot-time `PCR[0..11]` and runtime `PCR[10]` execution history to an external verifier via hardware-rooted `TPM 2.0` quotes) [9, 51, 52, 53].

Historically, Linux tackled both problems inside a single subsystem, the `Integrity Measurement Architecture` (`IMA`, merged in Linux 2.6.30 from IBM Research [51, 185]) paired with the `Extended Verification Module` (`EVM`). Twenty years of deployment experience revealed sharp engineering trade-offs in `IMA`'s mutable-xattr and sequential-hashing design, directly motivating the Linux 6.12 `Integrity Policy Enforcement` (`IPE`) LSM [9, 186] for modern verity-backed systems alongside CNCF `Keylime` [53, 187] for scalable `IETF RATS` (`RFC 9334` [52]) remote attestation.

## Kernel & Userspace Mechanics

### `IMA` Measurement (`PCR[10]`), `IMA-Appraisal`, and `EVM` Metadata Binding

Inside `security/integrity/ima/ima_main.c` [51, 185, 188], `process_measurement()` mediates five execution and file-ingest paths: `ima_bprm_check` (`BPRM_CHECK` on `execve` / `execveat`), `ima_file_mmap` (`MMAP_CHECK` and `MMAP_CHECK_REQPROT` on shared libraries and `PROT_EXEC` mappings), `ima_file_mprotect`, `ima_file_check` (`FILE_CHECK` on policy-matched `open()` calls), and `ima_read_file` / `ima_post_read_file` (`READING_MODULE`, `READING_FIRMWARE`, `READING_KEXEC_IMAGE`, and `READING_POLICY`), complemented in modern kernels by `ima_measure_critical_data()` (`func=CRITICAL_DATA` under `ima_policy=critical_data` [189]) which measures live in-memory `SELinux` policy state, `IPE` active policies, `dm-crypt` / `dm-verity` target tables, and trusted keyring contents directly into `PCR[10]`! `IMA` separates two orthogonal duties: *measurement* (`ima_policy=tcb`, recording every executed binary, kernel module, and critical kernel data buffer into an append-only event log for off-host verifiers without blocking local access) and *appraisal* (`ima_appraise=enforce`, returning `-EACCES` locally whenever a file lacks valid cryptographic provenance) [185, 188, 189].

When `IMA` measures an inode for the first time, it caches the result inside a red-black tree of `struct ima_iint_cache` (`iint`) descriptors and re-evaluates only if `ima_detect_file_change()` observes a mutated `STATX_CHANGE_COOKIE` or `i_version` counter (including `d_real_inode()` checks across `OverlayFS` upper/lower layers so stacked container mounts cannot serve stale cached verdicts [188, 190]). To compute the measurement, the kernel reads the file linearly from byte zero to EOF to calculate $\text{digest}(F) = \operatorname{SHA-256}(F)$, formats a template record (`ima-ng` packing `<hash_algo>:<digest>` + `<path>`, `ima-sig` appending the raw `security.ima` signature blob, or `ima-modsig` for appended PKCS#7 signatures [189]), appends the record to `/sys/kernel/security/ima/binary_runtime_measurements`, and extends `TPM 2.0` `PCR[10]`:

$$H_{\text{entry}} = \operatorname{SHA-256}\!\left(d_{\text{ima-ng}}(F, \text{path})\right), \qquad \text{PCR}[10] \leftarrow \operatorname{SHA-256}\!\left(\text{PCR}[10] \;\parallel\; H_{\text{entry}}\right)$$

Pause and ask a foundational architectural question: why can operators seal `LUKS2` keys to `PCR[11]` ([Chapter 2](02-uki-systemd-pcrlock.md)), yet *never* seal `LUKS2` or local `TPM2_PolicyPCR` secrets to `PCR[10]` [51, 53, 113]? Because `TPM2_PCR_Extend` ($H(P \parallel d)$) is *non-commutative*! On a modern multicore Linux server, `systemd` spawns dozens of `udev` workers, network daemons, and cron helpers concurrently; if `/usr/sbin/chronyd` opens `/lib64/libcap.so.2` two microseconds ahead of `/usr/lib/systemd/systemd-resolved` opening `/lib64/libcrypto.so.3` on Tuesday, and in the reverse order on Wednesday, `PCR[10]` arrives at two completely unrelated 256-bit hashes despite executing the *exact same set of legitimate binaries*! Order-dependence makes `PCR[10]` unusable for local `TPM2_PolicyPCR` sealing, yet perfectly suited to remote attestation: an off-host `Keylime` verifier fetches the ordered measurement list, replays the sequential `SHA-256` chain from $0^{256}$ to confirm its simulated `PCR[10]` matches the hardware `TPM2_Quote` digest bit-for-bit, and then validates each individual `(path, digest)` entry as an *order-independent set* against its Reference Value database [53, 191]! Furthermore, `ima_main.c` closes concurrent reader/writer races explicitly [188]: `mmap_violation_check()` rejects `PROT_EXEC` mappings on any file with active writable `mmap` regions (`mapping_writably_mapped()`) with `-ETXTBSY`, while `ima_rdwr_violation_check()` catches `ToMToU` (a writer opening an already-being-read measured file) and `open_writers` (a reader measuring an already-open-for-write file) by calling `ima_add_violation()` to extend a sentinel all-zeroes ($0^{256}$, translated inside `ima_queue.c` to `0xff..ff` for the TPM extend so untrusted code cannot spoof a zero digest) violation marker into `PCR[10]`, permanently flagging the runtime log to remote verifiers until reboot [51, 188].

![Figure: How the Extended Verification Module (EVM) computes security.evm over security.ima, SELinux/SMACK labels, file capabilities, and struct h_misc inode metadata to prevent offline SUID escalation and xattr transplantation.](diagrams/04-extra-evm-inode-hmac-binding.svg)

When local `IMA-appraisal` is active (`ima_appraise=enforce`), `evmctl` (`ima-evm-utils` [192]) signs files into the `security.ima` extended attribute using either asymmetric v2 RSA/ECDSA signatures over full-file hashes or v3 signatures over constant-time `fs-verity` Merkle digests (`IMA` `appraise_type=imasig|verity` [192, 193]), verified against the kernel `.ima` keyring. Importantly, under `CONFIG_INTEGRITY_ASYMMETRIC_KEYS` and `CONFIG_IMA_KEYRINGS_PERMIT_SIGNED_BY_BUILTIN_OR_SECONDARY`, the `.ima` and `.evm` keyrings apply the exact same `restrict_link_by_builtin_and_secondary_trusted()` cryptographic gate as module signing ([Chapter 5](05-kernel-lockdown-modules.md)): even a compromised `UID 0` process invoking `keyctl padd asymmetric ... %:.ima` at runtime cannot enroll a self-signed key to bless attacker binaries unless that X.509 certificate chains directly to an offline CA compiled into `.builtin_trusted_keys` or enrolled via physical `MokManager` console confirmation in `.machine` [119, 192]! Yet on a mutable filesystem, `security.ima` authenticates only file *bytes*, not inode *permissions* or *MAC labels*: an offline Evil Maid attacker could copy a legitimately signed helper binary, run `chmod u+s` to make it `SUID-root`, or strip `security.selinux` to run it unconfined! Inside `security/integrity/evm/evm_crypto.c` [185, 194], the `Extended Verification Module` (`EVM`) closes metadata tampering by maintaining `security.evm` via `evm_calc_hmac_or_hash()`. Across every configured security xattr (`security.selinux`, `security.SMACK64`, `security.ima`, `security.capability`, and `system.posix_acl_access`), `EVM` hashes the raw xattr values and appends `hmac_add_misc()` over `struct h_misc` (`i_ino`, `i_generation`, `uid` and `gid` mapped explicitly into `init_user_ns` via `from_kuid(&init_user_ns, inode->i_uid)` so an attacker cannot forge valid metadata inside an unprivileged FUSE userns mount, `i_mode`, and optionally superblock `s_uuid`) [194]. On mutable hosts, `security.evm` stores an `HMAC-SHA256` keyed by a `TPM 2.0` Trusted Key (`evm-key` [119, 194]); for read-only vendor packages distributed across many hosts where `i_ino` and `i_generation` vary per installation, `EVM_XATTR_PORTABLE_DIGSIG` (`0x05`) omits `ino`/`generation` and signs the remaining tuple asymmetrically with the vendor's offline private key [192, 194].

### Linux 6.12+ Integrity Policy Enforcement (`IPE`) LSM and `AT_EXECVE_CHECK`

Why did hyperscale cloud operators, container hosts, and immutable appliance builders struggle to run `IMA-appraisal` + `EVM` at fleet scale [186, 195]? Documented candidly in `Documentation/security/ipe.rst` [195], `IMA` + `EVM` suffered three architectural friction points: first, maintaining `security.ima` and `security.evm` xattrs across millions of files broke standard archival and container tooling (and on unencrypted mutable volumes, an offline attacker could strip *all* xattrs including the `SELinux` label that selected a data file for `IMA` read appraisal!); second, whole-file linear hashing on first `execve()` stalled cold startup and failed to detect a malicious block device serving clean bytes during `IMA` open-time hashing and trojanized bytes on a later page fault; third, `IMA` lacked human-readable, atomically updatable, rollback-protected policy semantics coupled natively to `dm-verity` [9, 195]. (For mutable RPM/DEB hosts, the complementary `digest_cache` LSM proposed by Roberto Sassu parses signed package-header digest lists in Ring 0 to ease xattr management [196].)

![Figure: Architectural comparison between legacy IMA-Appraisal + EVM (per-file xattrs, whole-file linear hashing, and ToMToU hazards) and the Linux 6.12+ Integrity Policy Enforcement (IPE) LSM evaluating demand-paged dm-verity and fs-verity Merkle roots.](diagrams/04-ima-vs-ipe-enforcement.svg)

Merged in Linux `6.12` (`CONFIG_SECURITY_IPE=y`, `security/ipe/hooks.c` by Fan Wu and Deven Bowers [9, 186, 197]), `Integrity Policy Enforcement` (`IPE`) separates *integrity mechanism* (`dm-verity`, `fs-verity`, and `UKI` `initramfs`) from *execution policy*. `IPE` registers seven compact LSM hooks in `security/ipe/hooks.c` [197]: `ipe_bprm_check_security` (`execve`), `ipe_bprm_creds_for_exec` (handling `AT_EXECVE_CHECK` script probes!), `ipe_mmap_file` and `ipe_file_mprotect` (mediating transitions to `PROT_EXEC`), `ipe_kernel_read_file` and `ipe_kernel_load_data` (`FIRMWARE`, `KERNEL_MODULE`, `KEXEC_IMAGE`, `KEXEC_INITRAMFS`, `POLICY`, `X509`), plus `ipe_bdev_setintegrity` and `ipe_inode_setintegrity` capturing validated `dm-verity` root hashes/signatures and `fs-verity` digests/built-in signatures into RCU-protected LSM security blobs in $O(1)$ time [197]. At early boot, the kernel enforces a compiled-in plain-text `SECURITY_IPE_BOOT_POLICY` (`boot_verified=TRUE` trusting the `UKI` `initramfs` marked by `ipe_unpack_initramfs()`), after which `initrd` writes a PKCS#7-signed policy (`openssl smime -sign -outform der`, verified against `.builtin_trusted_keys` or `.secondary_trusted_keys`) into `/sys/kernel/security/ipe/new_policy` and activates it atomically under RCU by writing `1` to `/sys/kernel/security/ipe/policies/<name>/active` [9, 197]:

```text
policy_name=immutable_node policy_version=1.0.0
DEFAULT action=DENY

op=EXECUTE boot_verified=TRUE action=ALLOW
op=EXECUTE dmverity_signature=TRUE action=ALLOW
op=EXECUTE fsverity_signature=TRUE action=ALLOW
op=KERNEL_MODULE boot_verified=TRUE action=ALLOW
```

Look at what those six plain-text rules enforce with zero extended attributes [9, 195, 197]: only binaries residing inside the verified `UKI` `initramfs` (`boot_verified=TRUE`), mounted from a PKCS#7-signed `dm-verity` `/usr` or `systemd-sysext` DDI (`dmverity_signature=TRUE` or `dmverity_roothash=<sha256>`), or carrying a `.fs-verity`-verified built-in signature (`fsverity_signature=TRUE` or `fsverity_digest=<sha256>`) may ever be executed or `mmap(..., PROT_EXEC)`-mapped! Every attempt to run or `dlopen()` code dropped into `/tmp`, `/var`, `/dev/shm`, or `memfd_create()` hits `DEFAULT action=DENY`, fails with `-EACCES`, and emits structured kernel audit record `type=1420` (`AUDIT_IPE_ACCESS`) recording `ipe_op`, `ipe_hook`, `pid`, `comm`, `path`, and the exact denying rule [9]. Subsequent live policy updates written to `/sys/kernel/security/ipe/policies/<name>/update` require `CAP_MAC_ADMIN`, a valid PKCS#7 kernel-keyring signature, and a strictly higher `policy_version` tuple (`major.minor.patch`) to block policy rollback attacks [9]. To close the remaining gap where a signed interpreter (`/usr/bin/python3 script.py`) reads scripts via plain `open(O_RDONLY)` rather than `execve()`, Linux `6.14+` introduced `execveat(fd, "", NULL, NULL, AT_EMPTY_PATH | AT_EXECVE_CHECK)` paired with process securebits `SECBIT_EXEC_RESTRICT_FILE` and `SECBIT_EXEC_DENY_INTERACTIVE` (`Documentation/userspace-api/check_exec.rst` by Mickael Salaun [198, 199]), allowing enlightened shells, Python runtimes (`PEP 578` [200]), and dynamic linkers to ask `IPE` and `IMA` (`bprm->is_check` in `ipe_bprm_creds_for_exec()` [197]) whether `fd` is authorized to execute before interpreting a single line!

### Continuous Remote Attestation with `Keylime` and `IETF RATS` (`RFC 9334`)

Local enforcement (`IPE` or `IMA-appraisal`) stops unauthorized payloads on an honest kernel, yet cannot prove to a remote peer that an edge server did not reboot with `SecureBoot` disabled in BIOS setup or boot an unhardened kernel. Standardized in `IETF RATS` (`RFC 9334` [52], with CBOR/JWT Entity Attestation Tokens defined in `RFC 9711` [201]) and implemented for Linux fleets by CNCF `Keylime` (using the memory-safe Rust `rust-keylime` agent on monitored hosts [53, 191, 202]), remote attestation separates four architectural roles: the *Attester* (the Linux node + `TPM 2.0`), the *Verifier* (`keylime_verifier`), the *Endorser / Reference Value Provider* (supplying TPM manufacturer `EK` roots plus golden `UKI` `PCR[11]` digests, UEFI `PCR[0..7]` policies, and `IMA` file allowlists), and the *Relying Party* (the Kubernetes control plane, `SPIRE` CA, or secret broker acting on the Verifier's appraisal result) [52, 53, 191].

![Figure: Continuous remote attestation protocol in CNCF Keylime mapped onto IETF RATS (RFC 9334), binding a restricted TPM 2.0 Attestation Key to hardware Endorsement silicon via MakeCredential/ActivateCredential before polling nonce-fresh PCR[0..11] + IMA PCR[10] quotes.](diagrams/04-keylime-rats-attestation.svg)

How does the `Keylime` Registrar prove it is talking to genuine silicon rather than a `swtpm` emulator running on an attacker's workstation [111, 202, 203]? Under the `TCG EK Credential Profile` [203], every hardware `TPM 2.0` ships with an immutable Endorsement Primary Seed (`EPS`), a persistent Endorsement Key (`EK`, e.g., handle `0x81010002` for ECC P-256), and a manufacturer-signed X.509 `EK` certificate in NV index `0x01c00002`. Because the `EK` is a decryption-only storage root, `keylime_agent` generates a fresh signing *Attestation Key* (`AK`) marked with `TPMA_OBJECT_RESTRICTED = 1`, a silicon hardware bit that forbids `TPM2_Sign` from signing any arbitrary user-supplied hash, permitting signatures *exclusively* over internal `TPM` structures prefixed with magic header `TPM_GENERATED_VALUE` (`0xff544347`) [111, 202]! During registration (hardened after `CVE-2022-1053` to enforce strict Registrar challenge-response identity binding [204]), the Registrar verifies the `EK` X.509 chain against TPM vendor roots, generates a random credential challenge, and wraps it via `TPM2_MakeCredential(PK_EK, Name(AK))`. Only the physical TPM holding $SK_{\text{EK}}$ *and* the exact loaded `AK` matching $\operatorname{Name}(AK)$ can execute `TPM2_ActivateCredential` to decrypt the challenge and complete enrollment [111, 202, 203].

Once enrolled, `keylime_verifier` continuously appraises the agent every few seconds using a fresh 128-bit cryptographic nonce $n$, supporting both classic verifier-initiated mTLS *pull mode* (for reachable data-center nodes) and NAT-friendly agent-initiated *push mode* (where edge or cellular-connected `rust-keylime` agents fetch a challenge nonce from the Verifier and push signed quotes outbound without opening inbound listening ports on the monitored host!) [53, 191, 202]. On each cycle, the TPM executes `TPM2_Quote`, signing `TPMS_ATTEST` (binding $n$, monotonic TPM clock/reset/restart counters that expose unexpected host power-cycles, and the composite `SHA-256` digest across `PCR[0..15]`, including `PCR[10]`) under $SK_{\text{AK}}$, while `keylime_agent` streams only the incremental byte delta appended to `/sys/kernel/security/ima/ascii_runtime_measurements` since the last quote (plus the binary UEFI TCG / `CEL` event log evaluated against Keylime's Python/Rego measured-boot `mb_refstate` engine on initial boot or `kexec`, preserved across soft reboots via `CONFIG_IMA_KEXEC` in `security/integrity/ima/ima_kexec.c` [205]) [191, 202]. The Verifier checks the `AK` signature and nonce $n$, replays the UEFI and `IMA` event logs to confirm they reproduce `PCR[0..11]` and `PCR[10]` bit-for-bit, checks every executed binary, script, and `CRITICAL_DATA` record against its signed runtime policy (failing immediately on any unknown hash or `ToMToU` $0^{256}$ violation), and fires signed revocation webhooks, draining Kubernetes pods, revoking `SPIFFE` X.509-SVIDs, or quarantining switch ports within seconds of drift [53, 191].

## Distro, Immutable-OS, & Cloud Trade-Offs

Choosing between `IMA` + `Keylime` and `IPE` reflects a fundamental operational split between mutable package-managed servers and immutable verity-backed appliances [9, 53, 185, 195]. On mutable enterprise distributions (`RHEL 9/10`, `SUSE Linux Enterprise`, `Ubuntu Server`) where operators apply in-place `dnf` or `apt` package updates and execute administrative Python or Bash scripts, `RHEL` ships `rpm-plugin-ima` to extract per-file `ima-sig` signatures from signed RPM headers (`RPMSIGTAG_FILESIGNATURES`) into `security.ima` during package installation, while `Keylime` ingests signed distribution repository metadata to build dynamic Reference Value allowlists automatically [185, 191, 192]. Even so, running `IMA` measurement on high-density Kubernetes or CI build nodes requires disciplined policy engineering: because every unique entry in `/sys/kernel/security/ima/binary_runtime_measurements` resides permanently in *non-swappable Ring 0 kernel RAM* (`ima_queue.c`) until reboot, a naive policy that measures ephemeral container scratch files, log rotations, or pseudo-filesystems can append millions of records, exhausting gigabytes of kernel memory and stalling `Keylime` log replay! Production `IMA` policies therefore prepend explicit `dont_measure` rules filtering `PROC_SUPER_MAGIC`, `SYSFS_MAGIC`, `TMPFS_MAGIC` (where covered by `noexec`), or scoped container data volumes while strictly measuring `BPRM_CHECK`, `MMAP_CHECK`, and `MODULE_CHECK` [188, 189, 191].

Conversely, on modern Linux `6.12+` immutable operating systems (`Azure Linux` / `CBL-Mariner` appliance profiles, `Flatcar`/`Talos`-style `dm-verity` hosts, and `composefs` / `bootc` deployments [9, 45, 46, 121]), `IPE` enforces preventative execution integrity in Ring 0 with $O(1)$ per-execve policy lookup, zero extended-attribute maintenance, and zero unbounded in-kernel measurement list growth [9, 195, 197]. Because the entire `/usr` tree and any `systemd-sysext` overlays are already summarized by constant-size `dm-verity` root hashes extended into `PCR[11]` and `PCR[13]`, remote attestation can appraise the exact OS software bill of materials via boot-time `PCR[0..15]` quotes alone (or pair lightweight `Keylime` boot/policy quotes with `IPE` audit monitoring) [9, 113, 191]. In Confidential Containers (`CoCo` on `AMD SEV-SNP` and `Intel TDX`, examined in [Chapter 19](19-confidential-containers.md)), the `IETF RATS` architecture generalizes directly from discrete `TPM 2.0` `AK` quotes to CPU-signed hardware attestation reports verified by `Trustee` before releasing OCI container decryption keys [42, 52, 201].

## Seam Failures, CVEs, & Structural Bounds

Runtime appraisal and remote attestation encounter sharp structural limits around interpreted languages, memory-only payloads, `PCR[10]` log saturation, and the Time-of-Attest to Time-of-Compromise window.

Row 1 and Row 8 state two permanent theoretical bounds of *all* file-level integrity architectures [52, 195, 198]. First, *the interpreter and JIT equivalence bound*: `execve()` and file-backed `mmap(PROT_EXEC)` mediate compiled ELF binaries and shared libraries, not data streams interpreted by Turing-complete runtimes (`bash`, `python3`, `node`, `perl`) or anonymous executable pages (`mmap(NULL, ..., PROT_READ | PROT_WRITE | PROT_EXEC, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)`) synthesized by Just-In-Time (`JIT`) engines (`V8`, `JVM`) and legacy `libffi` closures [9, 195]. Note how `ipe_mmap_file()` in `security/ipe/hooks.c` receives `f == NULL` on anonymous `MAP_ANONYMOUS` mappings [197]: if an `IPE` policy sets `DEFAULT op=EXECUTE action=DENY`, unpermitted anonymous `PROT_EXEC` transitions are blocked alongside untrusted files unless JIT processes are confined via `SELinux` `execmem` booleans and `systemd` `MemoryDenyWriteExecute=yes` ([Chapter 11](11-systemd-dbus-sandboxing.md)) [9, 68], while interpreted script files require runtimes compiled to enforce `execveat(..., AT_EMPTY_PATH | AT_EXECVE_CHECK)` under locked `SECBIT_EXEC_RESTRICT_FILE | SECBIT_EXEC_DENY_INTERACTIVE` securebits (`Linux 6.14+` [198, 199]) or complete interpreter removal (`Talos` / `Distroless` [45]). Second, *load-time measurement is not runtime memory safety*: `IMA`, `IPE`, and `Keylime` prove that only authentic binaries entered memory, yet if an authentic kernel driver or network daemon contains a Use-After-Free vulnerability, an attacker hijacks Ring 0 in RAM without ever touching disk or extending `PCR[10]`. Protecting the running kernel itself against `UID 0` and memory corruption is the task of Part II ([Chapters 5](05-kernel-lockdown-modules.md) through [7](07-stacked-lsms-landlock.md)).

> **Note.**
> When deploying `IMA-appraisal` or `IPE` in production, always test new rules under permissive/audit mode (`ima_appraise=log` only during non-Lockdown staging, or `ipe.enforce=0` monitoring `auditd` `type=1420` `AUDIT_IPE_ACCESS` records) before flipping `enforce=1` [9, 206]. On `IPE` hosts, keep an emergency signed rollback-safe recovery UKI available during initial rollout, as a syntax-valid `DEFAULT action=DENY` policy that forgets to allow `/usr/lib64/ld-linux-x86-64.so.2`'s backing `dm-verity` volume will block every subsequent `execve()` immediately upon activation [9].

## Inspecting on a Live Linux Host

Check whether `IMA`, `EVM`, and `IPE` are active in the running kernel's stacked LSM list and inspect the `IMA` runtime measurement count:

```bash
cat /sys/kernel/security/lsm 2>/dev/null; echo
# Reading securityfs IMA/IPE policy and logs typically requires root / run0
wc -l /sys/kernel/security/ima/ascii_runtime_measurements 2>/dev/null
head -n 4 /sys/kernel/security/ima/ascii_runtime_measurements 2>/dev/null
```

Inspect active `IMA` policy rules and check `EVM` initialization bitmask (`0x1` = HMAC key loaded, `0x2` = X.509 public key loaded, `0x80000000` = setup complete):

```bash
cat /sys/kernel/security/ima/policy 2>/dev/null | head -n 15
cat /sys/kernel/security/evm 2>/dev/null
```

On Linux `6.12+` kernels built with `CONFIG_SECURITY_IPE=y`, inspect enforce mode and list loaded `IPE` policies and versions under `securityfs`:

```bash
cat /sys/kernel/security/ipe/enforce 2>/dev/null || true
ls -la /sys/kernel/security/ipe/policies/ 2>/dev/null
head -n 10 /sys/kernel/security/ipe/policies/*/policy 2>/dev/null || true
```

Verify `TPM 2.0` `PCR[10]` bank state alongside any running `Keylime` agent unit:

```bash
tpm2_pcrread sha256:10 2>/dev/null || systemd-analyze pcrs 10 2>/dev/null
systemctl is-active keylime_agent.service 2>/dev/null || true
```
