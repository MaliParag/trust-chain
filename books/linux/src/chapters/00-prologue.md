# Prologue

## Composable Mechanisms and the Seam Between Them

Inspect a classic enterprise Linux server running `UEFI Secure Boot`, and ask what cryptographic guarantee actually holds between firmware `LoadImage()` and the moment `sshd` accepts its first connection. On a traditionally configured distribution, `UEFI` verifies Microsoft-signed `shim.efi`, `shim` verifies the vendor's `GRUB2` and `vmlinuz` kernel image, and verification stops cold: `GRUB2` loads an unauthenticated `initramfs` CPIO archive off an unencrypted `/boot` partition, executes shell scripts inside it as `UID 0`, and pivots into a mutable root filesystem [1]. Every individual component functions as documented, yet an attacker with offline disk access drops a two-line hook into `initramfs` and captures the `LUKS` passphrase at the next reboot without touching Secure Boot keys.

*The Linux Trust Chain* is about how modern Linux closes those integration seams from reset vector to multi-tenant cloud silicon, and why assembling a coherent chain out of independent open-source subsystems creates failure modes fundamentally different from Windows or Apple platforms.

### From Mutable Distros to Image-Based Verified Systems

Modern Linux engineering (`systemd` `Unified Kernel Images`, `SBAT`, `dm-verity`, `IPE`, `Landlock`, `run0`, and `COCONUT-SVSM`) systematically replaces ad-hoc boot scripts, `SUID` binaries, and mutable root filesystems with measured, signed artifacts and explicit IPC boundaries [1, 2, 3, 5]. Packing the kernel, kernel command line, `initrd`, and `.sbat` metadata into a single Authenticode-signed PE binary (`UKI`) lets `UEFI` verify the entire pre-userspace payload in one pass while `systemd-stub` binds phase-specific `TPM 2.0` policies (`PCR[11]` signed policies via `systemd-pcrlock`) so secrets unseal only to authorized boot phases [1]. Above block storage, `dm-verity` and the `Integrity Policy Enforcement` (`IPE`) LSM pin immutable `/usr` trees to cryptographic root digests, `systemd` `run0` eliminates `SUID` privilege-escalation surfaces in favor of isolated transient units [5], and stacked Linux Security Modules (`SELinux`, `AppArmor`, and unprivileged `Landlock`) plus `Kernel Lockdown` prevent even `UID 0` from mutating running Ring 0 code [2].

### Shared-Kernel Density, Agentic Sandboxes, and Supply-Chain Trust

At the cloud and AI execution layer, Linux carries a unique burden: millions of multi-tenant Kubernetes pods, `MCP` tool servers, and autonomous AI code-execution sandboxes run atop Linux hosts [6]. Whenever untrusted or prompt-injected workloads share a host kernel guarded only by `namespaces`, `cgroups v2`, and `seccomp-BPF`, a single memory bug in `nf_tables`, `io_uring`, or the `eBPF` verifier (`Dirty Pipe`) amplified by unprivileged `user_namespaces` collapses container isolation into host Ring 0 compromise, motivating user-space kernels (`gVisor`), lightweight KVM micro-VMs (`Firecracker` and `Kata Containers`), credential-injecting egress proxies, and hardware-encrypted `Confidential Containers` [3, 6]. Even hardened userland daemons remain exposed along subtle seams, from async-signal-unsafe races inside `OpenSSH` (`regreSSHion`, `CVE-2024-6387` [7]) to the March 2024 `XZ Utils` (`CVE-2024-3094`) backdoor [4], which proved that an intact hardware and kernel chain still snaps if a patient adversary subverts upstream build tarballs before distro signing keys ever touch the binary [8].
