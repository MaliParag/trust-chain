# APFS Per-File Data Protection, BFU/AFU States, and Lockdown Mode

## Overview

* **Link in the Chain:** Local data-at-rest cryptography and lock-state surface-reduction layer opening Part III; binds `APFS` file extents on the writable `Data` volume ([Chapter 5](05-apfs-ssv-dyld.md)) to silicon-fused `SEP` `UID` keys, `Effaceable Storage` lockers, and user passcode keybags ([Chapter 3](03-secure-enclave.md)).
* **Core Security Invariant:** Every `APFS` file extent is encrypted inline by the `ANS` storage controller under an independent random per-file/per-extent `AES-256-XTS` key wrapped inside `j_crypto_val_t` by a `SEP` Data Protection class key (`A`, `B`, `C`, or `D`), such that Class `A` keys are evicted upon screen lock, Class `B` permits locked writes exclusively via asymmetric `ECDH` without exposing decryption keys, Class `A`/`B`/`C` remain sealed in `Before First Unlock` (`BFU`), and idle `AFU` devices auto-reboot back to `BFU` after 72 hours (`iOS 18.1+`).
* **Platform Matrix:** Mandatory per-file four-class Data Protection across `iOS`, `iPadOS`, `watchOS`, and `visionOS`; Apple Silicon `macOS` enforces always-on `ANS` volume encryption wrapped by `SEP`-backed `FileVault` (`SecureToken` / `BootstrapToken`) alongside opt-in per-file classes, while `Lockdown Mode` spans `iOS`, `iPadOS`, `macOS`, and `watchOS` (`visionOS` omits legacy `2G` baseband and wired data pairing natively).
* **Trusted Computing Base (TCB):** `SEP` `SKS` keybags (`SystemKeybag.kb`, Backup, and Escrow keybags) and 72-hour `sepOS` inactivity timer, inline `ANS`/`ANS2` NVMe `AES-XTS` DMA engines, `Effaceable Storage` NAND lockers (`BAG1`, `DKey`, `EMF`), `apfs.kext` `cprotect` / `j_crypto_val_t` handlers, `USB Restricted Mode` (`AccessorySecurity`), and `lockdownmoded`.
* **Failure Horizon & Handoff:** While in `After First Unlock` (`AFU`), unwrapped Class `C` capability inside `SEP` exposes background-accessible app data (`Messages`, third-party SQLite stores) to physical USB + kernel zero-day chains (`CVE-2025-24200`) during the 72-hour window, and coerced or shoulder-surfed passcodes unlock Class `A`; hands off fine-grained `Keychain` access groups and `Stolen Device Protection` biometric delays to [Chapter 11](11-keychain-stolen-device.md).

## Threat Model & Design Tension

Traditional workstation Full-Disk Encryption (`FDE`, such as `LUKS`/`dm-crypt` on Linux or TPM-only `BitLocker` on Windows) encrypts an entire block device under one monolithic Volume Master Key (`VMK`) unwrapped into kernel RAM at boot. On a mobile computer carried continuously across international borders, protests, hotel rooms, rideshares, and forensic seizure laboratories, single-key `FDE` fails three fundamental Tier 2 (physical theft/seizure) and Tier 3 (targeted mercenary exploit) requirements [45, 46, 297]. First, once the owner boots the device on Monday morning and enters their passcode once, single-key block encryption leaves *every file on the drive* decrypted in the OS view for weeks on end: if the phone is snatched while screen-locked or placed inside a forensic laboratory's Faraday bag, any physical USB or local kernel memory-read vulnerability dumps the user's most sensitive health records, password vaults, and tax documents without ever touching the passcode [46, 297]. Second, paired trusted computers and cloud backup pipelines need a way to back up user files without exporting raw hardware keys or breaking per-file isolation [13, 298]. Third, retiring, trading in, or remotely wiping (`MDM` `EraseDevice` / `Find My`) a 2 TB flash drive cannot rely on a twenty-minute sequential NAND overwrite while an adversary pulls the battery; sanitization must complete in milliseconds with cryptographic finality (`NIST SP 800-88` Cryptographic Erase) [299, 300].

Yet purging *all* encryption keys from DRAM the instant the screen turns off would render a modern pocket computer unusable [45, 301]. Incoming cellular calls could not resolve caller names against `Contacts`; `APNs` push notifications could not wake `Messages` or `Mail` to download encrypted attachments; `Apple Watch` and `HealthKit` workouts could not record continuous heart-rate samples while the display is off; and an unattended midnight software update or kernel panic reboot (`Before First Unlock`, or `BFU`) could not rejoin known Wi-Fi networks or ring morning alarms [45].

Apple's `APFS` Data Protection architecture resolves this availability-versus-confidentiality conflict by decomposing storage cryptography along two orthogonal axes: *spatial granularity* (independent 256-bit keys per file extent wrapped under four distinct `NSFileProtection` lifecycle classes inside `SEP`) and *temporal lock state* (`BFU` vs. `AFU`, bounded since `iOS 18.1` by a hardware-enforced 72-hour inactivity reboot timer, `USB Restricted Mode`, and `Lockdown Mode`) [45, 46, 184, 302].

## Silicon & System Mechanics

### APFS j_crypto_key_t / j_crypto_val_t Records, cprotect, and Per-Extent AES-256-XTS Tweaks

Unlike HFS+ (which bolted Data Protection onto `com.apple.system.cprotect` extended attributes late in its lifecycle), `APFS` designed per-file and per-extent hardware encryption directly into its core B-tree object schema (`Apple File System Reference` and `bsd/sys/cprotect.h`) [184, 303, 304]. Whenever `apfs.kext` creates a file on an encrypted `Data` volume, its data stream descriptor (`j_dstream_t`) records a `default_crypto_id`, while each physical file-extent record (`j_file_extent_val_t`) stores an explicit 64-bit `crypto_id` (`cp_crypto_id_t`) referencing a `(j_crypto_key_t, j_crypto_val_t)` pair inside the volume's filesystem B-tree [304, 305]. Keying at *extent granularity* (`j_crypto_val_t` maintains a `uint32_t refcnt` reference counter alongside a `wrapped_crypto_state_t` payload) enables `APFS`'s signature zero-copy `clonefile(2)` and copy-on-write snapshots: two cloned files share identical ciphertext extents under the original `crypto_id`, while overwriting a 4 KB range inside the clone allocates a fresh physical extent encrypted under a newly minted `crypto_id` without re-encrypting the unchanged megabytes [184, 304, 305]!

![Figure: APFS per-file Data Protection hierarchy linking SEP UID fuses, stretched user passcodes, and Effaceable Storage lockers through Classes A, B, C, and D down to per-extent inline XTS-AES encryption.](diagrams/10-apfs-data-protection-hierarchy.svg)

Inside `wrapped_crypto_state_t` (represented in `XNU` VFS memory by opaque `cprotect_t` and fixed-zone `fcpx_t` contexts in `bsd/sys/cprotect.h`), `APFS` persists `major_version`, `minor_version`, `cp_flags`, `persistent_class` (`cp_key_class_t`), `key_os_version`, `key_revision` (`cp_key_revision_t`), `key_len`, and `persistent_key[]` (up to `CP_MAX_WRAPPEDKEYSIZE = 128` bytes wrapping the raw per-file key via `RFC 3394` `AES-KW` under the class key held inside `SEP`) [303, 304, 306]. User-space daemons and apps inspect or upgrade protection classes atomically via `fcntl(fd, F_GETPROTECTIONCLASS)` (`63`), `fcntl(fd, F_SETPROTECTIONCLASS, class)` (`64`), `F_TRANSCODEKEY` (`75`), and `open_dprotected_np(path, flags, class, dpflags, mode)` (`<sys/fcntl.h>`) [307].

On the physical DMA path between DRAM and raw NAND flash, `XNU` never executes software `AES` loops on modern Apple Silicon; instead, `AppleKeyStore` / `apfs.kext` programs unwrapped extent key slots into the inline hardware `AES` crypto engine integrated inside the `ANS` / `ANS2` NVMe storage controller [45, 308]. Operating in `NIST SP 800-38E` `XTS-AES` mode (`AES-128-XTS` using 256-bit composite keys on earlier A-series chips; full `AES-256-XTS` using 512-bit $(K_1 \| K_2)$ composite keys on Apple Silicon Macs and modern A/M-series SoCs), the `ANS` engine computes a unique 128-bit sector tweak $T_b$ derived from the logical extent offset / `crypto_id` (`cpx_use_offset_for_iv` and `cpx_synthetic_offset_for_iv` in `cprotect.h`) and steps across 16-byte cipher blocks $j \in \{0, \dots, 255\}$ within each 4 KB block via Galois-field multiplication in $\text{GF}(2^{128})$ modulo $x^{128} + x^7 + x^2 + x + 1$ [303, 305, 309]:

$$C_{b,j} = \text{AES-256}_{K_1}\bigl(P_{b,j} \oplus \Delta_{b,j}\bigr) \oplus \Delta_{b,j}, \qquad \Delta_{b,j} = \text{AES-256}_{K_2}(T_b) \otimes \alpha^{j}$$

Unlinking a single file decrements `j_crypto_val_t.refcnt` to zero and removes its wrapped key from the B-tree, crypto-shredding that file once old `APFS` transaction checkpoints roll over (unless pinned intentionally by an active Time Machine or backup snapshot) [184, 305].

### The Four NSFileProtection Classes and Class B Ephemeral ECDH Wrapping

Every file on an `APFS` Data volume carries an integer `cp_key_class_t` binding its wrapped per-file key to a specific lock-state lifecycle inside `SEP`'s `SKS` (`Security Key Store`) [13, 45, 301, 304]:

| `cp_key_class_t` | `NSFileProtectionType` Constant | Key Wrapping Anchor in `SEP` | Availability Across `BFU` & Screen-Locked `AFU` |
|---|---|---|---|
| `Class A` (`1`) | `NSFileProtectionComplete` | `UID` + Stretched User Passcode | Sealed in `BFU` *and* evicted 10s after screen lock in `AFU` |
| `Class B` (`2`) | `NSFileProtectionCompleteUnlessOpen` | `UID` + Passcode + `P-256`/`X25519` `ECDH` | Sealed in `BFU`; locked `AFU` permits *new writes* via public $Q_B$ (closed files unreadable) |
| `Class C` (`3`) | `CompleteUntilFirstUserAuthentication` | `UID` + Stretched User Passcode | Sealed in `BFU`; remains unwrapped for background reads/writes throughout `AFU` (default class) |
| `Class D` (`4`) | `NSFileProtectionNone` | `UID` + `Effaceable` `DKey` locker | Available in `BFU` & `AFU` for boot/Wi-Fi/telephony; defeated off-chip via `UID` + instant wipe |
| `Class F` (`6`) | Kernel Volatile / VM Swap Only | Ephemeral Boot-Random RAM Key | Non-persistent; encrypts `macOS`/`iOS` compressor swap pages, destroyed on every reboot |

Among these five classes, *Class B* (`NSFileProtectionCompleteUnlessOpen`, `cp_key_class_t = 2`) embodies one of the most elegant applications of public-key cryptography in operating system storage design [45, 301, 310]. Suppose an iPhone sits locked inside a user's bag (`AFU`, screen locked $> 10\text{ seconds}$ so Class `A` keys have been wiped via `cpx_flush()` and `CP_ACTION_LOCKED`), and `Mail` or `HealthKit` receives a background push carrying a confidential PDF attachment or ECG sample. If the daemon wrote the attachment as `Class C`, a thief seizing the locked phone could read it via an `AFU` kernel exploit; if it tried to open a `Class A` file, `SEP` would reject the request with `EPERM` because Class `A` keys are evicted while locked!

![Figure: Class B (NSFileProtectionCompleteUnlessOpen) asymmetric ECDH key agreement allowing background daemons to write new encrypted APFS files while locked without exposing closed Class B decryption keys.](diagrams/10-extra-class-b-asymmetric-wrap.svg)

Class `B` solves this asymmetry using ephemeral-static Elliptic-Curve Diffie-Hellman (`ECDH` over `NIST P-256` / `Curve25519`, `RFC 7748` and `SP 800-56A`) [45, 310]. Inside `SystemKeybag.kb`, Class `B` is represented as an asymmetric keypair $(d_B, Q_B = d_B G)$. Ten seconds after the screen locks (`MKBLockDevice`), `SEP` wipes the Class `B` *private scalar* $d_B$ from active unwrapped `SKS` memory while keeping the Class `B` *public key* $Q_B$ available. When a background daemon invokes `open_dprotected_np(path, O_CREAT | O_WRONLY, PROTECTION_CLASS_B, 0, 0600)` while locked, `SEP`/`AppleKeyStore` mints a random 256-bit per-file key $K_{\text{file}}$ alongside a one-time ephemeral elliptic-curve keypair $(e_f, Q_f = e_f G)$, computes the ECDH shared point $Z = e_f Q_B$, derives a wrapping key via `RFC 5869` `HKDF-SHA256`, wraps $K_{\text{file}}$ via `RFC 3394` `AES-KW`, and immediately destroys the ephemeral scalar $e_f$ [45, 306, 310]:

$$K_{\text{wrap}} = \text{HKDF-SHA256}\bigl(e_f \cdot Q_B\bigr), \qquad \texttt{j\_crypto\_val\_t.persistent\_key} = Q_f \;\|\; \text{AES-KW}_{K_{\text{wrap}}}(K_{\text{file}})$$

As long as that initial file descriptor remains open, `apfs.kext` holds $K_{\text{file}}$ in its `fcpx_t` buffer to stream encrypted `XTS-AES` blocks to flash. The microsecond the background daemon calls `close(fd)`, `apfs.kext` zeroes `fcpx_t` in DRAM! Because $e_f$ was erased at creation and $d_B$ sits locked inside `SEP` under the user's passcode, *not even `XNU` at `EL1` can reopen the file it just finished writing* until the owner authenticates via Face ID / Touch ID / passcode, allowing `SEP` to unwrap $d_B$, compute $d_B \cdot Q_f = d_B (e_f G) = e_f Q_B$, re-derive $K_{\text{wrap}}$, and unwrap $K_{\text{file}}$ [45, 303]!

### System, Backup, Escrow, and iCloud Keybags Plus Effaceable NAND Lockers

Class keys themselves are organized inside binary Tag-Length-Value (`TLV`: `VERS`, `TYPE`, `UUID`, `HMCK`, `WRAP`, `SALT`, `ITER`, followed by per-class `CLAS`, `WPKY`, `KTYP`, and `WPBK` public-key tags) containers called *Keybags* [13, 298, 311]. Apple maintains four distinct keybag roles to decouple local hardware `UID` binding from authorized backup and pairing workflows [13, 298]:

First, the *System Keybag* (`/private/var/keybags/systembag.kb`) holds the live device's Class `A`, `B`, `C`, and `D` keys. Its `WPKY` entries are double-wrapped (`WRAP = 3`): tangled inside `SEP` using the silicon-fused `UID` key ([Chapter 3](03-secure-enclave.md)) *and* encrypted under a keybag-encryption key (`BAG1`) stored in *Effaceable Storage* [13, 299]. Even if an attacker desolders the NAND flash chip and dumps `systembag.kb`, brute-forcing the user's passcode offline on a GPU cluster is mathematically impossible because every candidate guess requires `SEP`'s unexportable hardware `UID` engine [13, 311]. Second, when creating a local encrypted backup (`Finder` or `libimobiledevice`), the device mints an independent *Backup Keybag* with fresh random class keys protected by `10,000,000` rounds of `PBKDF2-HMAC-SHA256` + `1,000` rounds of `SHA-1` over the user's backup password (omitting `UID` tangling intentionally so the user can restore that backup onto a *replacement* iPhone if the original phone falls into the ocean!) [298, 311]. Third, when a user taps *"Trust This Computer"* over USB and enters their passcode (or when a supervised enterprise device binds to an MDM management certificate), `lockdownd` / `keybagd` creates an *Escrow Keybag*: a copy of the System Keybag wrapped under a freshly generated 256-bit pairing secret split between the host computer's `/var/db/lockdown/<UDID>.plist` and `SEP` anti-replay storage, enabling unattended local backups or MDM `ClearPasscode` recovery [298, 311]. Fourth, *iCloud Backup Keybags* wrap cloud backup class keys either in Apple cloud HSMs (Standard Data Protection) or exclusively inside user-controlled `SEP`-synced keys under *Advanced Data Protection* ([Chapter 15](15-icloud-hsm-adp.md)).

To satisfy `NIST SP 800-88` instantaneous cryptographic sanitization, *Effaceable Storage* dedicates physically addressable, non-wear-leveled storage lockers (`BAG1` wrapping `systembag.kb`, `DKey` wrapping `Class D`, and `EMF` wrapping volume metadata) managed by the storage controller / `SEP` [299, 300, 308]. Invoking *Erase All Content and Settings*, remote `Find My` wipe, `MDM` `EraseDevice`, or exceeding ten failed passcode attempts (`auto-erase`) issues a single hardware obliteration command that zeroes `BAG1`, `DKey`, and `EMF` in milliseconds: without `BAG1` and `DKey`, every `j_crypto_val_t` record and `XTS-AES` extent across the entire multi-terabyte NVMe array becomes indistinguishable from random noise instantly, even if an attacker subsequently coerces the user's passcode [299, 300].

### BFU vs. AFU Residency, the iOS 18.1 72-Hour Inactivity Timer, USB Restricted Mode, and Lockdown Mode

In real-world physical seizures and border inspections, Data Protection security hinges on whether the device sits in *Before First Unlock (`BFU`)* or *After First Unlock (`AFU`)* [45, 46, 297].

![Figure: Device lock lifecycle contrasting Before First Unlock (BFU) and After First Unlock (AFU), reinforced by USB Restricted Mode and the iOS 18.1+ 72-hour inactivity auto-reboot timer.](diagrams/10-bfu-afu-state-machine.svg)

Immediately after cold power-up, battery depletion, panic, or intentional user power-off, the device boots into `BFU`: Face ID, Touch ID, and Optic ID are cryptographically disabled (`SEP` requires passcode entropy to derive the keybag unwrapping key), user apps have never executed, DRAM holds zero decrypted SQLite caches, and `Class A`, `Class B`, and `Class C` keys sit completely wrapped inside `systembag.kb` [45, 297]. Against a patched modern iPhone in `BFU`, physical extraction boxes (`GrayKey`, `Cellebrite UFED`) can read only `Class D` system plumbing unless the owner chose a weak 4- or 6-digit numeric PIN vulnerable to slow `SEP`-paced guessing. Once the owner types their passcode a single time after boot, however, the device enters `AFU`: even after the screen subsequently locks, `Class C` remains unwrapped inside `SEP` (`AppleKeyStore`) so `imagent`, `WhatsApp`, `Signal`, and background daemons can decrypt their databases on incoming pushes! Because the overwhelming majority of third-party app files default to `Class C` (`CompleteUntilFirstUserAuthentication`), any physical USB + kernel zero-day chain executed against a locked `AFU` device extracts nearly the user's entire digital life without knowing their passcode [46, 297].

For years, forensic laboratories exploited `AFU` persistence by keeping seized `AFU` phones powered on inside RF-shielded Faraday enclosures for months until a new USB/kernel exploit became available [46, 312]. In October and November 2024 (`iOS 18.1` and `iPadOS 18.1`), law-enforcement examiners reported that seized `AFU` iPhones inside Faraday lockers were mysteriously rebooting themselves back into `BFU` (`404 Media` and Magnet Forensics) [312]! Reverse engineering of `keybagd` and `sepOS` (`SKS`) by Jiska Classen and Matthias Hollick revealed Apple's architectural countermeasure: `SEP` and `keybagd` arm a hardware-backed monotonic countdown timer (`max_inactivity_duration = 259,200 seconds`, or *72 hours*) on every transition into locked `AFU` state [46, 313]. If 72 hours elapse without a successful biometric or passcode unlock, `SEP` expires the `AFU` session and triggers an immediate kernel panic/reboot, returning the device irreversibly to `BFU` and wiping all unwrapped `Class C` keys and DRAM caches [46, 313]!

Complementing the 72-hour timer are *USB Restricted Mode* (`AccessorySecurity` / `IOAccessoryManager`, disabling Lightning, USB-C, and Thunderbolt data lanes while locked so physical extraction hardware sees only dumb 5V charging pins until unlocked) [314] and *Lockdown Mode* (`lockdownmoded`, `/System/Library/Sandbox/Profiles/lockdownmoded.sb`, `LDMGlobalEnabled`) [302, 315]. Designed for Tier 3 mercenary-spyware targets, `Lockdown Mode` deterministically amputates seven high-risk remote and physical surfaces simultaneously [302, 315, 316, 317]: disabling `JavaScriptCore` and `WebAssembly` `JIT` compilation completely inside `WebKit` (`WebGL`, `SVG` fonts, complex font tables, and `WebRTC` local IP candidates are also stripped or sandboxed per-site) [317]; blocking most `iMessage` attachment parsers (`JBIG2`, `PassKit`, link previews) ahead of `BlastDoor`; dropping `FaceTime` calls and `Home`/`Photos` shared invitations from previously uncontacted accounts; disabling unauthenticated `2G` GSM cellular baseband connectivity (and `3G` where supported) to defeat fake-base-station baseband exploits [316]; blocking unmanaged `.mobileconfig` profile enrollment; blocking non-enterprise Wi-Fi auto-join on insecure networks; and severing *all* wired USB/Thunderbolt data connections unconditionally whenever the device is locked [302, 314].

## Platform Forks Across Apple OSes

Across `iOS`, `iPadOS`, `watchOS`, and `visionOS`, four-class per-file Data Protection is mandatory from factory boot with zero user toggle to disable encryption [45]. On Apple Silicon `macOS`, storage encryption adapts to multi-user POSIX workstation semantics across two layers [45, 318]. At the bottom layer, *every* Apple Silicon Mac encrypts its `APFS` `Data` volume inline via `ANS2` `AES-256-XTS` from day one using a Volume Encryption Key (`VEK`) wrapped inside `SEP` and `Effaceable Storage` *even when FileVault is turned off*, which is why `Erase All Content and Settings` (`System Settings $\to$ General $\to$ Transfer or Reset`) wipes a 4 TB Mac Studio in two seconds [308, 318]! Enabling *FileVault* (`fdesetup enable`, default during Setup Assistant when signing in with an Apple Account) binds unwrapping of that `SEP` `VEK` to cryptographic *SecureToken* user credentials, an MDM *Bootstrap Token*, or a Personal/Institutional Recovery Key (`PRK`/`IRK`), forcing cold boots into a pre-boot `LoginWindow` equivalent to `BFU` [318, 319].

Once a `macOS` user logs in, however, standard POSIX files under `/Users/alice` operate at volume-level `AFU` rather than evicting `Class A` file keys ten seconds after screen-saver lock (so background `cron`, `tmux`, compilation jobs, and SSH sessions continue running cleanly), reserving strict `Class A` and biometric `SEP` gating on `macOS` for the *Data Protection Keychain* ([Chapter 11](11-keychain-stolen-device.md)) [318]. Portable Apple Silicon MacBooks (`MacBook Air` and `MacBook Pro`) additionally enforce an explicit interactive accessory-approval dialog (*"Allow accessory to connect?"*) before enumerating USB or `PCIDriverKit` Thunderbolt tunnels on newly plugged cables [314]. Meanwhile, `Lockdown Mode` ships across `iOS 16+`, `iPadOS 16+`, `macOS Ventura+`, and `watchOS 10+`, whereas `visionOS` omits cellular `2G` modems and locked Lightning/USB pairing protocols natively [302, 315].

## In-the-Wild Failures & Architectural Bounds

`AES-256-XTS` and `SEP` `UID` key wrapping have never been broken cryptanalysis-wise in the wild; instead, every real-world Data Protection failure exploits `AFU` key residency, developer misuse of `Class C`, paired host trust, or state-machine bugs in physical USB port gating.

| Case / Mechanism | Year | Platform Scope | Boundary Tested | Root Cause | Architectural Response |
|---|---|---|---|---|---|
| Third-Party App `Class C` Default Residency | Architectural | `iOS` & `iPadOS` | Screen-locked `AFU` confidentiality | Apps storing chats/tokens in default `Class C` files (`CompleteUntilFirstUserAuthentication`) leave data readable to any `AFU` kernel exploit | `iOS 18.1+` 72-hour `AFU`-to-`BFU` auto-reboot; sensitive secrets belong in `Class A` or `SEP` Keychain [45, 297, 301] |
| `Lockdown` Escrow Keybag Host Theft | 2014-2023 | `iOS` paired to `macOS`/PC | Trusted-host `Escrow Keybag` (`/var/db/lockdown/`) | Stealing `/var/db/lockdown/<UDID>.plist` from a compromised laptop bypassed USB pairing prompts when reconnected to the phone | Required explicit passcode confirmation on initial trust, periodic pairing expiration, and `Stolen Device Protection` [298, 311] |

### CVE-2025-24200 and the Forensic Arms Race Between AFU Zero-Days and the 72-Hour SEP Timer

Two events between November 2024 and February 2025 crystallized the cat-and-mouse dynamics of physical `iOS` data custody [46, 312, 320]. First, when `iOS 18.1` quietly activated its 72-hour `AFU`-to-`BFU` inactivity timer (`keybagd` + `SEP`), forensic labs worldwide discovered that seized `AFU` phones stored in evidence lockers were rebooting themselves on day four, permanently evicting `Class C` keys before lab backlogs or newly leased kernel exploits could run [312, 313]. Second, in February 2025, Apple issued `iOS 18.3.1` patching `CVE-2025-24200` (reported by Citizen Lab's Bill Marczak), warning that the flaw had been exploited in *"an extremely sophisticated attack against specific targeted individuals"* with physical access to a locked phone [320]. Rather than breaking `AES-256-XTS` or extracting `UID` fuses from `SEP`, `CVE-2025-24200` abused a state-management authorization flaw (reachable via physical Assistive Access / lock-screen port state transitions) to disable `USB Restricted Mode` on a locked `AFU` device, reopening USB data lines to physical exploit appliances *inside* the 72-hour window [314, 320]. Together, the two events establish a clear operational rule for high-risk travelers and journalists: while the 72-hour `SEP` timer and `Lockdown Mode` shrink unintended `AFU` exposure dramatically, *powering the device completely off before crossing a hostile checkpoint* forces immediate `BFU` at minute zero.

## Verification & Forensic Artifacts

On `macOS`, verify `FileVault` (`SEP`-wrapped `APFS` `VEK`) status and enumerate authorized `SecureToken` / cryptographic volume unlock identities via `fdesetup` and `diskutil` [318, 319]:

```bash
fdesetup status
diskutil apfs listCryptoUsers / | head -n 10
```

Expected output confirming active `FileVault` encryption and authorized cryptographic user UUIDs:

```text
FileVault is On.
Cryptographic users for disk3s5 (2 found)
|
+-- E48192A1-7C3B-4E10-9B1A-... (Local Open Directory User)
```

Query a local file's integer `APFS` `cp_key_class_t` (`fcntl` `F_GETPROTECTIONCLASS = 63`, returning `3` for `Class C` or `4` for `Class D`) and check `Lockdown Mode` global state (`LDMGlobalEnabled`) [307, 315]:

```bash
python3 -c 'import fcntl, os; fd=os.open("/etc/hosts", os.O_RDONLY); print("ProtectionClass:", fcntl.fcntl(fd, 63))'
defaults read .GlobalPreferences LDMGlobalEnabled 2>/dev/null || echo "Lockdown Mode: disabled (0)"
```

When analyzing an extracted `iOS` `sysdiagnose` archive, inspect `keybagd` state transitions, `AccessorySecurity` USB port lock logs, and `ResetCounter` / panic logs for `72-hour` `SEP` inactivity reboots [46, 313, 314]:

```bash
grep -iE 'inactivity|keybagd|USBRestricted' ./logs/SystemVersion/* ./logs/panics/* 2>/dev/null | head -n 5 || true
```

While `APFS` Data Protection encrypts bulk files and SQLite databases across lock states, modern apps also require fine-grained secret sharing across `Access Groups`, biometric-bound `SEP` private keys, and defenses against an attacker who *watches the victim type their passcode* before snatching the unlocked phone, the exact mission of [Chapter 11](11-keychain-stolen-device.md).
