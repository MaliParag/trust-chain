# Foundations

Every security boundary in Linux reduces to a precise interplay among five substrates: CPU privilege rings and hardware memory translation, kernel task credentials managed under Read-Copy-Update (`RCU`), Virtual File System (`VFS`) object resolution paired with `Linux Security Module` (`LSM`) hooks, `TPM 2.0` cryptographic state registers, and asymmetric or Merkle-tree integrity formats. When an architectural review treats these layers informally, subtle violations slip past: a system-call filter inspects a raw user-space pointer that another thread mutates mid-flight, a administrator assumes `UID 0` and Ring 0 are synonymous, or a disk encryption policy encrypts blocks without authenticating them. Establishing the exact hardware, kernel, and cryptographic invariants up front makes every subsequent chapter self-contained and unambiguous.

## Hardware Privilege Rings, Virtualization Extensions, and Confidential Silicon

Modern Linux executes primarily across two processor families, `x86_64` (`AMD64` / `Intel 64`) and `ARM64` (`AArch64`), both of which enforce hierarchical hardware privilege modes in silicon [3, 4]. On `x86_64`, architectural history defines four protection rings (`CPL 0` through `CPL 3` encoded in the low two bits of the `%cs` code-segment selector), of which Linux uses two: Ring 3 (`CPL = 3`) executes unprivileged userspace processes under user-accessible page-table entries (`PTE` bit `U/S = 1`), while Ring 0 (`CPL = 0`) executes the Linux kernel (`vmlinux` and loadable `.ko` modules) with access to supervisor-only pages (`U/S = 0`), control registers (`%cr0`, `%cr3`, `%cr4`), Model-Specific Registers (`WRMSR`/`RDMSR`), and I/OMMU tables [3]. Transitions from Ring 3 to Ring 0 occur strictly through hardware-controlled gates, principally the fast `SYSCALL` instruction, which saves the user instruction pointer into `%rcx` and `%rflags` into `%r11`, masks interrupts via `IA32_FMASK`, sets `CPL = 0`, and jumps deterministically to the kernel address programmed in `IA32_LSTAR` (`entry_SYSCALL_64` in `arch/x86/entry/entry_64.S`) [3]. On `ARM64`, the architecture defines four orthogonal Exception Levels (`EL0` through `EL3`): `EL0` runs userspace applications, `EL1` runs the Linux kernel entered via the `SVC #0` supervisor-call instruction trapping into `VBAR_EL1`, `EL2` hosts the hypervisor (`KVM` in either `nVHE` split mode or `VHE` Virtualization Host Extensions where a host Linux kernel runs directly at `EL2`), and `EL3` executes Secure Monitor firmware (`TF-A`) gating transitions between the Normal World and TrustZone Secure World [4].

Hardware virtualization introduces a second orthogonal dimension beneath Ring 0. Under Intel `VT-x` (`VMX`) and AMD `SVM` (`AMD-V`), the host hypervisor (`KVM`) runs in `VMX Root Operation` (or `SVM` host mode), while guest virtual machines execute in `VMX Non-Root Operation` with their own guest Ring 0 and guest Ring 3 [3]. Even though a guest Linux kernel executes at `CPL = 0` inside `VMX Non-Root`, every guest physical address (`GPA`) produced by the guest's `%cr3` page tables must traverse a second hardware-walked translation table controlled exclusively by the host hypervisor: Intel Extended Page Tables (`EPT`) or AMD Nested Page Tables (`NPT`, and `Stage-2` translation tables under `VTTBR_EL2` on `ARM64`) [3, 4]. Consequently, a Ring 0 kernel exploit inside a `KVM` micro-VM (`Firecracker` or `Kata Containers`, analyzed in [Chapter 15](15-gvisor-microvms.md)) remains confined to the host physical RAM frames mapped into that guest's `EPT`/`Stage-2` table unless the attacker additionally compromises the host `KVM` subsystem or user-space Virtual Machine Monitor (`VMM`).

Classical `VT-x`, `SVM`, and `EL2` assume the host hypervisor is trustworthy: because host `VMX Root` controls `EPT`/`NPT` and maps all physical DRAM, a compromised cloud host can read or modify any guest page at will. Confidential Computing extensions invert that trust hierarchy inside the CPU memory controller itself ([Chapter 18](18-confidential-vms-svsm.md)) [140, 141, 142]. On `AMD SEV-SNP` (Secure Encrypted Virtualization-Secure Nested Paging), an on-die AMD Secure Processor (`ASP`/`PSP`) assigns each guest a unique `AES-128-XTS` memory encryption key in hardware and maintains a silicon-enforced Reverse Map Table (`RMP`) indexed by System Physical Address (`SPA`); before any CPU core completes a write or `NPT` walk, hardware verifies that the `SPA` belongs to the active `ASID` at the expected `GPA`, raising a fatal `#PF` fault if the untrusted host hypervisor remaps, aliases, or replays guest memory [140]. Furthermore, `SEV-SNP` partitions a single confidential guest internally into four Virtual Machine Privilege Levels (`VMPL0` most privileged through `VMPL3` least privileged), allowing an open-source Rust paravisor (`COCONUT-SVSM`) to execute in `VMPL0` and expose a measured virtual `TPM 2.0` to a guest Linux kernel isolated in `VMPL1` [140, 143]. Intel `TDX` (Trust Domain Extensions) achieves analogous isolation via a CPU-attested `TDX Module` running in `SEAM` (Secure Arbitration Mode) alongside Multi-Key Total Memory Encryption (`MKTME`) and Trust Domain Memory Regions (`TDMRs`) [141], while `Arm CCA` (Confidential Compute Architecture) introduces a Realm Management Extension (`RME`) with Granule Protection Tables (`GPT`) enforced at `EL3` to isolate dynamically allocated `Realms` from both the Normal-World `EL2` hypervisor and the TrustZone Secure World [142].

## Task Identity, RCU `struct cred`, and Namespace-Scoped UIDs

Inside the Linux kernel, every schedulable thread is represented by a `struct task_struct` (`include/linux/sched.h`) [5]. Rather than scattering security identifiers directly across mutable `task_struct` fields where concurrent readers and writers could race, Linux encapsulates a thread's entire security context inside an immutable, reference-counted `struct cred` (`include/linux/cred.h`) managed via Read-Copy-Update (`RCU`) [5]:

```c
struct task_struct {
    /* ... scheduler and memory descriptors ... */
    const struct cred __rcu *real_cred; /* Objective identity (who may signal/ptrace me) */
    const struct cred __rcu *cred;      /* Effective subjective identity (acting creds) */
    /* ... */
};

struct cred {
    atomic_long_t   usage;
    kuid_t          uid, euid, suid, fsuid;
    kgid_t          gid, egid, sgid, fgid;
    kernel_cap_t    cap_inheritable, cap_permitted, cap_effective, cap_bset, cap_ambient;
    struct key      *session_keyring, *process_keyring, *thread_keyring;
    void            *security;          /* Stacked LSM security blob */
    struct user_namespace *user_ns;     /* Owning user namespace */
    struct rcu_head rcu;
};
```

Distinguishing `real_cred` (objective credentials governing who can act *upon* the task, such as sending signals or inspecting `/proc/<pid>`) from `cred` (subjective credentials governing what the task itself may access when performing VFS operations, temporarily overridden during kernel asynchronous I/O or `override_creds()` calls) prevents confused-deputy privilege leaks when a kernel worker thread services a request on behalf of an unprivileged caller [5]. Because an active `struct cred` is strictly read-only once published, permission checks on the hot path (`current_cred()`, `current_euid()`) read `task->cred` locklessly inside an `rcu_read_lock()` critical section with near-zero cache contention. Whenever a task legitimately changes privilege via `setresuid(2)`, `capset(2)`, `landlock_restrict_self(2)`, or `execve(2)`, the kernel allocates a private copy with `prepare_creds()`, mutates the unshared struct, and atomically swaps `task->cred` and `task->real_cred` via `commit_creds()`, deferring deallocation of the old `struct cred` through `call_rcu(&old->rcu, put_cred_rcu)` until all pre-existing RCU readers complete [5]. That clean design also explains why raw `struct cred` overwrites remain a prized post-exploitation target in kernel Use-After-Free (`UAF`) attacks ([Chapter 6](06-kernel-memory-rust.md)): zeroing the `uid` through `fsgid` fields and setting all capability masks to `0x1ffffffffffULL` on a leaked `cred` pointer elevates a task to `root` without executing a single shellcode instruction if data-integrity protections are absent [54].

Notice also that `uid` and `euid` inside `struct cred` have type `kuid_t`, not raw integer `uid_t` [5, 80]. `kuid_t` stores the flat global kernel identifier in the initial user namespace (`init_user_ns`). When a process calls `unshare(CLONE_NEWUSER)` ([Chapter 9](09-capabilities-userns.md)), the kernel creates a child `struct user_namespace` (`cred->user_ns`) containing piecewise-linear `uid_map` and `gid_map` extents translating between global `kuid_t` values and namespace-local `uid_t` values [80]. A thread whose global `kuid_t` is `1000` can map itself to `UID 0` inside its child `user_ns` and receive full `CapEff` bits *relative to that `user_ns`*. Crucially, the kernel offers two distinct capability-check functions: `capable(CAP_SYS_ADMIN)` checks privilege against `init_user_ns` (global host privilege), whereas `ns_capable(ns, CAP_NET_ADMIN)` checks whether `cred` holds the capability over the target resource's owning `user_namespace` [78, 80]. Confusing `ns_capable()` with host safety, or allowing `ns_capable()` to gate entry into buggy Ring 0 parsers whose memory allocators are global across the entire machine, drives a huge share of modern Linux local privilege escalations ([Chapter 9](09-capabilities-userns.md)).

## VFS Object Resolution, Discretionary Access Control, and LSM Hook Placement

Every file, socket, pipe, device node, and anonymous memory descriptor on Linux is mediated through the Virtual File System (`VFS`, `fs/`) [6]. Four primary kernel structures define VFS state: `struct super_block` represents a mounted filesystem instance (carrying mount flags such as `SB_RDONLY` and filesystem-wide `SELinux` or `fs-verity` state); `struct inode` represents an individual filesystem metadata object on disk or in RAM (storing ownership `i_uid`/`i_gid`, mode `i_mode`, extended attributes `i_op->get_acl`, `i_security` LSM labels, and optional `fsverity_info`); `struct dentry` caches a single directory-entry name-to-inode link (`d_name` $\to$ `d_inode`, chained via `d_parent` to form directory hierarchies); and `struct file` represents an open file description held in a process's file-descriptor table (`files_struct`), recording open flags (`f_flags`), current offset (`f_pos`), `f_cred` (the `struct cred` captured at `open()` time!), and `f_security` [6, 7].

![Figure: Hardware privilege modes on x86_64/ARM64 and the placement of seccomp-BPF, VFS Discretionary Access Control, and stacked Linux Security Module (LSM) hooks on resolved kernel objects.](diagrams/00b-linux-privilege-rings-lsm.svg)

Why does the exact vertical placement of security checks along the `SYSCALL` $\to$ `VFS` pipeline matter so profoundly? Consider what happens when a multi-threaded userspace process invokes `openat2(dfd, pathname, &how, sizeof(how))` [6, 120]. At the `entry_SYSCALL_64` boundary, `pathname` is merely a `const char __user *` virtual address pointing into writable Ring 3 memory shared by every thread in the caller's address space (`CLONE_VM`). `seccomp-BPF` (`__secure_computing()`) runs at this earliest gate over the system-call number and the six raw 64-bit register values (`arg0..arg5`) [116]. Because `seccomp-BPF` intentionally forbids dereferencing user-space pointers, any external supervisor or naive `kprobe` monitor that reads the string at `pathname` from user memory before the kernel copies it in suffers a classic Time-of-Check to Time-of-Use (`TOCTOU`) race [67, 116]: Thread B in the same process flips `/tmp/benign` to `/etc/shadow` nanoseconds after the monitor reads `pathname` and nanoseconds before VFS calls `getname_flags()` to copy the path into a kernel slab buffer (`struct filename`).

The `Linux Security Module` (`LSM`) architecture (`security/security.c`, originally designed by Wright et al. [7] and extended to arbitrary module stacking via `lsm_blob_sizes` [61]) defeats user-memory `TOCTOU` by placing mandatory access control (`MAC`) hooks *inside* VFS and subsystem implementations *after* user buffers are copied into kernel memory and paths are resolved to pinned kernel `dentry` and `inode` structures [7, 61]. During `do_filp_open()`, VFS copies `pathname` into kernel space once, walks directory components under RCU-walk or ref-walk (`link_path_walk()`), enforces classic POSIX Discretionary Access Control (`DAC` mode bits, `POSIX` ACLs, and `CAP_DAC_OVERRIDE` / `CAP_DAC_READ_SEARCH`) via `inode_permission()` $\to$ `generic_permission()`, and immediately invokes `security_inode_permission(inode, mask)` followed by `security_file_open(file)` before returning an installed file descriptor [6, 61]. Under stacked LSM execution, `call_int_hook()` iterates over the registered `security_hook_list` chain (`landlock`, `lockdown`, `yama`, `ipe`, `selinux` or `apparmor`, and `bpf`): access succeeds if and only if POSIX `DAC` returns `0` *and* every stacked LSM hook returns `0` ("restrictive composition", where any single `-EACCES` or `-EPERM` veto terminates the loop) [61]. Even between LSM models, subtle VFS invariants remain ([Chapter 7](07-stacked-lsms-landlock.md)): label-based LSMs (`SELinux`) attach `security.selinux` extended attributes directly to `struct inode`, whereas pathname-based LSMs (`AppArmor`) reconstruct pathnames from `dentry`/`vfsmount` pairs (`d_absolute_path()`) and must additionally mediate `link()`, `rename()`, and mount operations so hardlinks cannot alias an unconfined path onto a sensitive inode [62, 63].

## TPM 2.0 PCR Algebra and Enhanced Authorization Policies

Cryptographic software checks inside Ring 0 cannot attest their own integrity to an external verifier or protect disk decryption keys against offline firmware tampering unless anchored in discrete or firmware-isolated hardware state. On x86 and ARM64 servers and workstations, that hardware state engine is a Trusted Platform Module conforming to the `TPM 2.0` Library Specification [2, 9]. A `TPM 2.0` exposes at least twenty-four Platform Configuration Registers (`PCR[0]` through `PCR[23]`), organized in banks per hash algorithm (exclusively `SHA-256` or `SHA-384` on modern Linux deployments, as `SHA-1` banks are collision-broken and deprecated) [2, 21]. No host command can ever write an arbitrary value into PCRs `0` through `15`; after initializing to all-zeroes ($0^{256}$) at platform reset, the sole mutation primitive is `TPM2_PCR_Extend`, which computes an irreversible cryptographic chain over each measurement digest $d \in \{0,1\}^{256}$:

$$\text{PCR}_{\text{new}}[i] \leftarrow \operatorname{SHA-256}\!\left(\text{PCR}_{\text{old}}[i] \;\parallel\; d\right)$$

Because $\operatorname{SHA-256}$ is preimage- and collision-resistant, no sequence of subsequent `TPM2_PCR_Extend` calls from a compromised later stage can roll $\text{PCR}[i]$ back to an earlier value or forge the final digest produced by a clean boot sequence $(d_1, d_2, \dots, d_k)$ [2]. Under the TCG PC Client Platform Firmware Profile [9] and the UAPI Group *Linux TPM PCR Registry* [21], Linux assigns distinct semantic roles across PCR indices: `PCR[0]` records core UEFI firmware (`SRTM`, `POST`, `DXE`), `PCR[1]` records firmware/platform configuration, `PCR[2]` and `PCR[3]` record external PCIe Option ROM code and data, `PCR[4]` records the UEFI Boot Manager execution flow (`shim.efi`, `grubx64.efi`, and PE `UKI` binaries invoked via `LoadImage()`), `PCR[5]` records GPT partition tables and `ExitBootServices()` transitions, `PCR[7]` records UEFI Secure Boot policy (`PK`, `KEK`, `db`, `dbx`, plus the exact X.509 authority entry in `db` or `MokList` that validated each binary), `PCR[9]` measures Linux kernel-loaded `initrd` CPIO archives, `PCR[10]` accumulates runtime `IMA` file measurements ([Chapter 4](04-ima-ipe-keylime.md)), `PCR[11]` measures `Unified Kernel Image` sections and monotonic boot phases via `systemd-stub` ([Chapter 2](02-uki-systemd-pcrlock.md)), `PCR[12]` records kernel command-line overrides and system credentials, `PCR[13]` records `systemd-sysext` images, and `PCR[15]` binds file-system volume keys after root mount [20, 21].

Sealing a secret (such as a `LUKS2` volume key or `systemd-creds` master key) directly to raw `PCR[4]` and `PCR[7]` digests via `TPM2_PolicyPCR` creates an operational trap: every routine distribution kernel or firmware capsule update alters `PCR[4]` (or `PCR[0]`/`PCR[7]`), locking the machine out of its root disk on reboot. `TPM 2.0` *Enhanced Authorization* (`EA`) solves that brittleness through policy indirection [2, 22, 23]. Every sealed TPM object stores a single 32-byte `authPolicy` digest computed inside a trial session. When a policy incorporates `TPM2_PolicyAuthorize(approvedPolicy, policyRef, keySign, checkTicket)`, the object's immutable `authPolicy` pins only the *public key* $PK_{\text{vendor}}$ (`keySign`, embedded in the `UKI` `.pcrpkey` section), not a static PCR hash:

$$\text{authPolicy} = \operatorname{SHA-256}\!\left(\text{authPolicy}_0 \;\parallel\; \texttt{TPM\_CC\_PolicyAuthorize} \;\parallel\; \operatorname{Name}(PK_{\text{vendor}}) \;\parallel\; \text{policyRef}\right)$$

Whenever a distribution builds a new kernel `UKI`, its build service computes the new expected `PCR[11]` value, constructs a trial policy digest $P_{\text{new}}$, and signs $aHash = \operatorname{SHA-256}(P_{\text{new}} \parallel \text{policyRef})$ with $SK_{\text{vendor}}$ into the `.pcrsig` PE section [22]. At boot, `TPM2_VerifySignature` produces an internal `TPMT_TK_VERIFIED` ticket proving $SK_{\text{vendor}}$ authorized $P_{\text{new}}$, allowing `TPM2_PolicyAuthorize` to satisfy the sealed `LUKS2` keyslot seamlessly across kernel upgrades while combining via `TPM2_PolicyOR` and NV-index pinning (`systemd-pcrlock`) with local firmware measurements ([Chapter 2](02-uki-systemd-pcrlock.md)) [22, 23].

## Cryptographic Integrity Formats: PE Authenticode, PKCS#7, and Merkle Trees

Linux deliberately employs three distinct cryptographic verification formats matched to the execution semantics of early firmware, discrete kernel artifacts, and demand-paged block or file storage:

First, all UEFI executables (`shimx64.efi`, `grubx64.efi`, `systemd-bootx64.efi`, and `UKI` `.efi` bundles) use the Microsoft `PE/COFF` *Authenticode* format (`WIN_CERTIFICATE_TYPE_PKCS_SIGNED_DATA`) because UEFI `LoadImage()` implements the PE specification natively [1, 8, 19]. Computing a PE Authenticode digest hashes the entire image cleanly while skipping the mutable PE `CheckSum`, the Data Directory Certificate Table pointer, and the trailing PKCS#7 signature block itself [8]. Second, post-boot kernel artifacts, including `.ko` loadable kernel modules (`~Module signature appended~\n` magic trailer), `fs-verity` root digests, `dm-verity` root-hash blobs, and `IPE` policy updates, use detached or appended Cryptographic Message Syntax (`CMS` / `PKCS#7`, RFC 5652) signatures verified in Ring 0 by `verify_pkcs7_signature()` against the kernel's `.builtin_trusted_keys`, `.machine`, and `.secondary_trusted_keys` X.509 keyrings ([Chapter 5](05-kernel-lockdown-modules.md)) [45, 46].

Third, signing multi-gigabyte `/usr` partitions or large container binaries with a flat linear signature is incompatible with demand paging: reading and hashing a 4 GiB image before executing its first 4 KiB page would stall boot for seconds and leave swapped or uncached pages vulnerable to mid-execution disk modification (`TOCTOU`). Both `dm-verity` (block-device level) and `fs-verity` (inode level) solve demand-paged verification with a balanced $b$-ary *Merkle hash tree* ([Chapter 3](03-luks2-verity.md)) [30, 33]. Partitioning an image of $N$ data blocks of size $B = 4096$ bytes with `SHA-256` digests ($|h| = 32$ bytes) yields a tree branching factor of $b = B / |h| = 4096 / 32 = 128$ hashes per internal tree node and tree height:

$$H = \left\lceil \log_{128} N \right\rceil$$

For a $4\text{ GiB}$ `/usr` filesystem ($N = 2^{20} = 1{,}048{,}576$ pages), $H = \lceil \log_{128}(2^{20}) \rceil = 3$ levels, adding less than $0.8\%$ storage overhead ($\approx 33\text{ MiB}$) while enabling the kernel page-fault handler to authenticate any individual $4\text{ KiB}$ page read on demand with at most $3$ SHA-256 block hashes (quickly cached in RAM once verified) anchored to a single 32-byte `root_hash` pinned inside the Authenticode-signed `UKI` [19, 30].

## Mutable Distros, Immutable Appliances, and Hostile Cloud Threat Models

A recurring source of confusion in Linux security engineering is evaluating a mechanism without naming the deployment model and adversary against which it operates. Throughout this book, we evaluate every link against three concrete Linux deployment postures and four adversary tiers.

![Figure: Architectural contrast between a mutable package-managed Linux distribution (stopping verification at vmlinuz) and an image-based immutable verified Linux OS (carrying cryptographic verification through UKI, dm-verity, IPE, and SUID-free userspace).](diagrams/00b-mutable-vs-immutable-boot.svg)

In a *mutable general-purpose distribution* (classic Debian, Ubuntu Server, or RHEL installations), package managers (`apt`, `dnf`, `zypper`) unpack archives directly onto a read-write root filesystem, regenerate `initramfs` locally on `/boot`, maintain human-edited `/etc` files, and expose interactive shells alongside `SUID` utilities; such hosts prioritize administrative flexibility at the cost of persistent post-boot drift and an unverified `initramfs` seam unless explicitly hardened with `UKI` and `systemd-pcrlock` [10, 23]. In an *immutable image-based operating system* (`Fedora CoreOS`, `Flatcar`, `Talos Linux`, `Bottlerocket`), the OS vendor builds and signs atomic versioned `/usr` images verified via `dm-verity` or `composefs` (`fs-verity` + `EROFS`), eliminates package managers and `SUID` binaries (`Talos` omits `/bin/sh` and `sshd` entirely in favor of mutual-TLS gRPC APIs), and treats `/etc` and `/var` as declarative or ephemeral state [34, 35]. In a *multi-tenant cloud, Kubernetes, or AI sandbox host*, the machine executes untrusted code supplied directly by external tenants or synthesized dynamically by Large Language Models exposed to untrusted web/repository inputs (`Indirect Prompt Injection`), turning every reachable host syscall, container runtime file descriptor, instance metadata endpoint (`169.254.169.254`), and ambient environment variable into an active exploitation boundary [122, 129, 134]. Finally, under a *confidential cloud threat model*, even the physical server operator, host `KVM` hypervisor, and Kubernetes worker-node `kubelet` sit outside the Trusted Computing Base, requiring hardware memory encryption (`SEV-SNP`, `TDX`, `Arm CCA`), guest input hardening against malicious hypervisor `#VC`/`#VE` traps, and enclave-side secret release (`COCONUT-SVSM` and `Confidential Containers`) [140, 143, 144, 147]. With these primitives, data structures, and threat models fixed, [Chapter 1](01-uefi-shim-sbat.md) begins at processor reset inside UEFI firmware.
