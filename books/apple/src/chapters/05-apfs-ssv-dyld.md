# APFS Signed System Volume, Cryptexes, and Shared Cache Trust

## Overview

* **Link in the Chain:** First file-system and dynamic-linking layer above `iBoot` ([Chapter 1](01-secure-boot.md)) and `SPTM` ([Chapter 4](04-silicon-memory-safety.md)); extends silicon boot verification across every 4 KB operating-system disk block, out-of-band security graft (`Cryptex1`), and pre-linked shared library mapped into user processes.
* **Core Security Invariant:** `XNU` mounts `/` strictly from an immutable `APFS` snapshot whose `fs_tree` and `fext_tree` cryptographic Merkle root matches the `Image4` `IM4M` seal verified at boot, re-verifies every faulted 4 KB system extent on page-in, and maps a single-boot `ASLR`-slid `dyld_shared_cache` whose interior pointers are `PAC`-signed on kernel page-in and write-locked via `TPRO`.
* **Platform Matrix:** Unified `APFS` `Signed System Volume` (`SSV`), personalized `Cryptex1` grafting, and `dyld4` `PrebuiltLoader` / shared-cache architecture across `iOS` (`15+`), `iPadOS`, `macOS` (`Big Sur 11+`), `watchOS`, `visionOS`, and `Private Cloud Compute`; `macOS` alone permits owner-authorized `csrutil authenticated-root disable` (`LocalPolicy.sip1`) inside paired `1TR` ([Chapter 2](02-mac-localpolicy.md)).
* **Trusted Computing Base (TCB):** `APFS` `apfs_integrity_meta_phys_t` Merkle verification in `apfs.kext`, `Image4` `SSV` and `Cryptex1` manifests (`TSS` or `LocalPolicy`), `XNU` `mach_loader.c` and `vm_shared_region_slide_page`, `dyld4` (`PrebuiltLoaderSet` and `JustInTimeLoader`), and `TPRO` (`APRR`/`SPRR`) hardware read-only state locks.
* **Failure Horizon & Handoff:** Eliminates persistent `/` disk rootkits even under live `EL1` kernel compromise, but cannot prevent in-memory corruption of `dyld` transition state once an attacker holds an in-process write primitive (`CVE-2026-20700`) or stop malware living on the mutable `Data` volume; hands off per-process code signing and `Launch Constraints` to `AMFI` and `TXM` ([Chapter 6](06-amfi-txm-notarization.md)).

## Threat Model & Design Tension

Authenticating the `XNU` `BootKC` kernel collection at boot ([Chapter 1](01-secure-boot.md)) leaves an enormous persistence surface if the root filesystem mounted at `/` remains a writable block device. Over ninety-five percent of a modern operating system's privileged TCB resides outside the kernel binary inside user-space daemons (`launchd`, `securityd`, `tccd`, `imagent`, `opendirectoryd`), shared frameworks (`Security.framework`, `WebKit`, `CoreGraphics`), `PAM` modules, and `LaunchDaemons` property lists. Historically, on both `OS X` (`Rootless` / `SIP`) and early `iOS`, system files lived on a standard read-write or software-guarded partition protected only by `MACF` access hooks (`SF_RESTRICTED`) and individual Mach-O signatures. Whenever an attacker achieved a transient `EL1` write primitive, modifying an unhashed resource or planting a launch plist on `/` yielded silent reboot survival; conversely, checking separate X.509 signatures across tens of thousands of system files added launch latency without catching deleted files, downgraded Apple dylibs, or altered symlink/firmlink metadata.

Transforming the entire multi-gigabyte OS volume into a single read-only cryptographic Merkle tree (`Signed System Volume`, `SSV`) eradicates persistent `/` rootkits, yet immediately collides with three UNIX and servicing constraints [37, 38, 184, 185]. First, POSIX software expects `/` to interleave immutable binaries (`/usr/bin`, `/sbin`) with mutable directories (`/Users`, `/Library`, `/private/var`, and enterprise NFS mount points at `/`). Second, re-downloading and re-hashing a 14 GB OS snapshot every time Apple patches an actively exploited `WebKit` or `dyld` zero-day would stall fleet remediation by days. Third, dynamically relocating 2,800+ system frameworks separately during every `execve()` would consume tens of milliseconds and hundreds of megabytes of dirty private pages per app unless pre-linked into a shared cache whose rebased `arm64e` pointers remain unforgeable across processes [186, 187, 188].

## Silicon & System Mechanics

### APFS Volume Groups, Bi-Directional Firmlinks, synthetic.conf, and the SSV Seal

Introduced across `macOS Catalina`/`Big Sur` and unified onto `iOS 15+`, Apple partitions each operating-system installation inside an `APFS` container (`nx_superblock_t`) into an asymmetric *Volume Group* pairing an immutable `System` role volume (`APFS_VOL_ROLE_SYSTEM`) with a writable `Data` role volume (`APFS_VOL_ROLE_DATA`, mounted at `/System/Volumes/Data` on `macOS` and `/private/var` on `iOS`) [37, 184, 185, 189]. To preserve legacy POSIX paths without slow union-filesystem layering, `APFS` implements *bi-directional firmlinks* (`APFS_TYPE_SIBLING_LINK` catalog records defined in `/usr/share/firmlinks` and activated by `apfs.util(8)`): transparent VFS bridges splicing fixed directories on the read-only `System` volume (`/Users`, `/Library`, `/Applications`, `/opt`, `/private`) directly to their mutable counterparts on `Data` [184, 189, 190]. For administrators and package managers (`Nix`, enterprise NFS automounts) that historically created top-level directories or symlinks directly under `/`, `macOS` adds `synthetic.conf(5)` (`/etc/synthetic.conf` and `/etc/synthetic.d`): parsed by `apfs.util` during early boot, `synthetic.conf` instructs `XNU` to synthesize virtual in-memory empty mount points or symlinks at `/` (such as `bar -> System/Volumes/Data/bar`) without writing a single byte to the sealed `System` disk [190, 191].

Crucially, a booted `macOS`, `iOS`, or `visionOS` kernel *never mounts the mutable `System` volume `apfs_superblock_t` directly* [37, 192]. During OS installation or OTA preparation, an updater constructs the clean `System` filesystem, freezes an immutable `APFS` snapshot (`fs_snapshot_create` in `bsd/sys/snapshot.h`, named `com.apple.os.update-<Hash>`), populates an `apfs_integrity_meta_phys_t` seal structure (`SHA-256` / `SHA-384`), and hashes every metadata and data node bottom-up into a single root digest [37, 184, 192, 193].

![Figure: APFS Signed System Volume (SSV) Merkle hash seal anchoring read-only catalog metadata and 4 KB file extents to the Image4 IM4M root digest alongside Personalized Cryptex1 grafts.](diagrams/05-apfs-ssv-cryptex-tree.svg)

Inside a sealed `APFS` snapshot, cryptographic verification replaces ordinary `APFS` block checksums (`o_cksum` Fletcher-64 inside `obj_phys_t`, which catches accidental NAND bit-rot at high speed but offers zero resistance against intentional offline flash edits) with an `apfs_integrity_meta_phys_t` header (`im_version`, `im_flags` tracking `APFS_SEAL_BROKEN`, `im_hash_type` `APFS_HASH_SHA256` or `APFS_HASH_SHA384`, and `im_root_hash_offset`) spanning two coupled B-trees [37, 184, 193]. First, the physical file-extent tree (`fext_tree`, keyed by `j_fext_tree_key_t` pairing object `private_id` with `logical_addr`) records the cryptographic digest $H(B_j)$ of every 4 KB physical disk block $B_j$ across all system data streams (`j_file_extent_val_t`), eliminating the indirection of mutable object maps (`omap_phys_t`) during sealed reads. Second, the catalog file-system tree (`fs_tree`) hashes every inode (`j_inode_val_t` permissions, `UID`/`GID`, `UF_IMMUTABLE`/`SF_RESTRICTED` flags), hashed directory record (`j_drec_hashed_key_t`), symlink target, firmlink (`APFS_TYPE_SIBLING_LINK`), and extended attribute (`j_xattr_val_t`, including inline `Mach-O` code signatures) up through interior B-tree parent nodes, where each parent stores the `SHA-256`/`SHA-384` digests of its child nodes alongside their logical block addresses until collapsing into the 384-bit *APFS Seal Hash* ($H_{\text{seal}}$) [37, 184, 193]:

$$H_{\text{seal}} = \text{MerkleRoot}_{\text{SHA-384}}\Bigl(\texttt{fs\_tree}_{\text{snap}} \;\bowtie\; \texttt{fext\_tree}\bigl(\{H(B_0), H(B_1), \dots, H(B_{m-1})\}\bigr)\Bigr)$$

During `TSS` personalization ([Chapter 1](01-secure-boot.md)), Apple's signing server verifies that $H_{\text{seal}}$ matches an official Apple release and signs $H_{\text{seal}}$ inside the device's `Image4` `IM4M` manifest (`ApTicket`, pinned on Macs by `LocalPolicy.nsih`) [37, 194]. At boot, `iBoot` authenticates `IM4M` and passes $H_{\text{seal}}$ in memory to `XNU`. When `apfs_vfsop_mount()` mounts `/` via `fs_snapshot_mount()`, `apfs.kext` rejects any mount attempt targeting the live mutable volume (`APFS_VOL_ROLE_SYSTEM` cannot mount read-write under `SSV`) and verifies the snapshot superblock root against $H_{\text{seal}}$; thereafter, on *every 4 KB VFS page-in* (`apfs_vnop_pagein`), `apfs.kext` hashes the incoming NVMe block and validates its Merkle path up to cached verified parent nodes before placing the page into the unified buffer cache [37, 192, 194]. Even OS updates preserve this invariant atomically: `softwareupdated` / `mobileassetd` unpacks a delta update into a background writable clone of `System` without disturbing the currently booted snapshot, seals a new `com.apple.os.update-<NewHash>` snapshot, personalizes its new `IM4M` via `TSS`, and flips `Preboot` (`nsih`) for the next reboot, guaranteeing zero window where `/` runs unsealed [37, 185, 192].

> **Key idea.**
> Under `APFS` `SSV`, not even a live `EL1` kernel exploit that writes raw NVMe flash blocks directly can achieve persistent `/` rootkit survival: flipping a single bit of `/sbin/launchd` or `/usr/lib/dyld` on flash causes the next cold boot's Merkle verification against the `Image4`-pinned $H_{\text{seal}}$ to fail (`apfs_seal_broken`), triggering a kernel panic or forcing recovery restore [37, 194].

### Personalized Cryptexes (Cryptex1) and Rapid Security Updates

Sealing `/` inside a monolithic Merkle snapshot creates an acute patching bottleneck: how can Apple ship an emergency zero-day fix for `WebKit` (`Safari`) or `dyld` (`CVE-2026-20700`), update Neural Engine weights, or mount Xcode developer instrumentation tools without rebuilding and re-downloading a 14 GB base OS snapshot? Apple solves this through *Cryptexes* (*Cryptographic Extensions*, specifically the `Cryptex1` architecture) [38, 194, 195, 196].

Distributed inside Apple Encrypted Archives (`.aea`) and unpacked into `/System/Volumes/Preboot/Cryptexes`, a production `Cryptex1` bundle consists of a read-only, Merkle-hashed `APFS` disk image wrapped as an `Image4` payload (`IM4P`), a companion loadable trust cache (`ltrs`), and a dedicated `TSS`-personalized `IM4M` manifest bound to the device's `ECID` and an independent `Cryptex1` anti-replay nonce [38, 194, 195]. Separating `OS` Cryptexes (mounted at `/System/Cryptexes/OS`, hosting updated system frameworks and the active `dyld_shared_cache`) from `App` Cryptexes (`/System/Cryptexes/App`, hosting `Safari.app` and `WebKit` bundles) and developer `DDI` Cryptexes allows `iBoot`, `cryptexd`, and `mount_apfs(8)` to *graft* verified subtrees seamlessly into the sealed namespace at boot while registering their CDHashes into `TXM` (`GL0`, [Chapter 6](06-amfi-txm-notarization.md)) [38, 190, 194, 196].

This `Cryptex1` pipeline powers *Rapid Security Responses* (`RSR` in `iOS 16`–`18`, evolved in `iOS 26` and `macOS Tahoe 26` into *Background Security Improvements*) [38, 196]. When Apple ships an out-of-band `WebKit` or `dyld` patch, endpoints download a compact `Cryptex1` delta (~80–250 MB) containing only the rebuilt `dyld_shared_cache` and patched frameworks, obtain a fresh `Cryptex1` `IM4M` ticket from `TSS` (rolling the `Cryptex1` nonce so vulnerable older `Cryptex` grafts cannot be replayed onto the same base kernel!), and activate the fix across a fast userspace/quick reboot [38, 194, 196]. Internally, grafting preserves every `SSV` and `SPTM` invariant without copying a single byte onto the read-only `System` volume: `cryptexd` and `iBoot` validate the `Cryptex1` `IM4M` against `ECID`, `CHIP`, `BORD`, and the `Cryptex1` `BNCH` nonce, load the accompanying `ltrs` trust cache into `TXM` (`GL0`) so newly patched `Mach-O` pages satisfy `XNU_USER_EXEC` CDHash checks, and invoke `mount_apfs` graft mounts onto `/System/Cryptexes/OS` and `/System/Cryptexes/App` [38, 190, 194]. At early boot, `dyld` inspects `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/` ahead of the base `/System/Library/dyld/` directory; if an authenticated `OS` `Cryptex` is active, `XNU` maps the `Cryptex` shared cache globally while leaving the underlying base `SSV` snapshot untouched, allowing an administrator or user to remove a problematic rapid patch cleanly by unmounting the graft and rolling the `Cryptex1` ticket forward [38, 196, 197].

### dyld4 PrebuiltLoaders, Slide Info v3/v5 PAC Rebasing, and TPRO Sealing

When `execve()`/`posix_spawn()` launches a binary (`bsd/kern/mach_loader.c`), `load_machfile()` maps the executable's Mach-O segments, calls `load_dylinker()` to map `/usr/lib/dyld`, sets `CS_RESTRICT` if required, and starts `EL0` execution at `_dyld_start` [186, 198]. Rather than loading 2,800+ system dylibs individually from disk, Apple pre-links them offline into a multi-file `dyld_shared_cache` (`dyld_shared_cache_arm64e`, `.01`, `.data`, `.tpro_const` under `/System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/` on `macOS` and `/System/Library/Caches/com.apple.dyld/` on `iOS`) [186, 197, 199].

How can a shared cache pre-built in Cupertino contain valid `PAC`-signed interior pointers (`vtable`s in `__AUTH_CONST` and stubs in `__AUTH_GOT`) when `ASLR` slide offsets and `APIAKey`/`APDAKey` hardware keys differ per device and per boot? Apple solves this via *kernel page-in linking* (`vm_shared_region_slide_page` in `osfmk/vm/vm_shared_region.c`) driven by `dyld_cache_slide_info3` and `dyld_cache_slide_info5` (`include/mach-o/dyld_cache_format.h` and `fixup-chains.h`) [186, 188, 197, 200, 201]:

```c
/* Exact arm64e shared-cache chained pointer encoding from dyld/include/mach-o/fixup-chains.h */
struct dyld_cache_slide_info5 {
    uint32_t version;           /* 5 (v3 uses auth_value_add with 51-bit plain layout) */
    uint32_t page_size;         /* 16384 (0x4000) on Apple Silicon */
    uint32_t page_starts_count;
    uint64_t value_add;         /* unslid base address of shared cache */
    uint16_t page_starts[];     /* 0xFFFF == DYLD_CACHE_SLIDE_V5_PAGE_ATTR_NO_REBASE */
};

struct dyld_chained_ptr_arm64e_shared_cache_auth_rebase {
    uint64_t runtimeOffset : 34, /* byte offset from start of shared cache (up to 16 GB) */
             diversity     : 16, /* C++/ObjC type-hash discriminator */
             addrDiv       :  1, /* 1 => blend storage address into QARMA tweak */
             keyIsData     :  1, /* 0 => APIAKey (code), 1 => APDAKey (data) */
             next          : 11, /* 8-byte stride delta to next fixup on this 16 KB page */
             auth          :  1; /* == 1 (0 selects plain high8 + runtimeOffset rebase) */
};
```

Notice the elegance of this zero-trust on-disk encoding [197, 199, 200, 201]. On disk inside the sealed `SSV` / `Cryptex`, *zero* valid `PAC` signatures exist; instead, the upper bits of every pointer inside `__DATA_CONST`, `__AUTH_CONST`, and `__AUTH_GOT` form an in-place singly linked list (`next * 8` bytes) starting at `page_starts[pageIndex]` (`0xFFFF` marks pages needing no rebase) and encoding each pointer's `runtimeOffset`, `diversity`, `addrDiv`, and `keyIsData` metadata [197, 200].

![Figure: dyld_shared_cache slide info v3/v5 chained fixup layout, XNU vm_shared_region_slide_page in-kernel PAC rebasing, and TPRO read-only state sealing.](diagrams/05-extra-dsc-pac-slide-pointers.svg)

At early boot, `XNU` selects one random `ASLR` slide $S \in [0, \texttt{maxSlide}]$ for the global shared region [197, 201]. Whenever any user process first faults a 16 KB `DATA` page from the shared cache, `vm_shared_region_slide_page()` reads the raw page from the `SSV`-verified file, walks the `dyld_cache_slide_pointer5` (`or v3`) chain inside kernel memory, computes $\text{target} = \texttt{value\_add} + \texttt{runtimeOffset} + S$, executes hardware `PACIA`/`PACDA` signing (`auth == 1`) using the shared-region `A` key and blended `(addrDiv, diversity)` tweak, and maps the resulting slid, `PAC`-authenticated page read-only/copy-on-write into the faulting task without dirtying per-process physical RAM [197, 199, 200, 201]!

![Figure: dyld4 shared-cache mapping, single-boot ASLR slide, PrebuiltLoader validation, TPRO read-only state sealing, and the CVE-2026-20700 writable-state corruption boundary.](diagrams/05-dyld-shared-cache-trust.svg)

Above kernel page-in linking, `dyld4` (`dyld/PrebuiltLoader.h`, `DyldRuntimeState.h`, and `SharedCacheRuntime.cpp`) splits user-space linking into an ahead-of-time `PrebuiltLoader` fast path and a runtime `JustInTimeLoader` fallback [186, 187, 199, 202, 203]. Modern `dyld_shared_cache` releases exceed 4 GB and partition into modular `.subcache` files (`dyld_subcache_entry` in `dyld_cache_format.h`, such as `.01`, `.02`, `.data`, and `.tpro_const`, each bound by UUID into the primary `dyld_cache_header`) alongside pre-optimized global Objective-C selector/class tables (`objcOptsOffset`), Swift protocol conformance witness tables (`swiftOptsOffset`), and CPU microarchitecture `FunctionVariants` (`dyld_cache_function_variant_entry` with `pacAuth` and `pacDiversity`) [197, 199]. Inside `dylibsPBLSetAddr` and `programsPBLSetPoolAddr`, `dyld4` embeds mmap-ready `PrebuiltLoaderSet` closures containing `BindTargetRef` fixup arrays, `FileValidationInfo` (`inode`, `mtime`, and `recordedCdHashIs` 20-byte `CDHash` predicates), and `mustBeMissingPaths` arrays (recording `@rpath` search slots that were absent when the closure was built, so if an enterprise root override or attacker later drops a new dylib into an earlier search directory, `PrebuiltLoaderSet::isValid()` detects the change!) [197, 202].

Even third-party `macOS` and `iOS` applications residing outside the shared cache benefit from kernel page-in linking via `LC_DYLD_CHAINED_FIXUPS` (`fixup-chains.h`) [188, 200]. Instead of traditional `dyld` rebase/bind bytecodes that forced `dyld` at startup to dirty every `__DATA_CONST` page in user space before calling `mprotect(..., PROT_READ)`, modern `arm64e` Mach-O binaries encode `dyld_chained_starts_in_segment` (`DYLD_CHAINED_PTR_ARM64E_USERLAND24`) and register their resolved bind table with `XNU` (`map_with_linking`), allowing the kernel to rebase and `PAC`-sign app `__DATA_CONST` and `__AUTH_GOT` pages lazily on fault while keeping them clean and immutable from first touch [187, 188, 200]. Meanwhile, `dyld`'s own internal `RuntimeState` allocator pools and `DYLD_CACHE_MAPPING_CONST_TPRO_DATA` (`tproMappingsOffset`) segments reside inside hardware *Thread-Local Permission Restriction* (`TPRO`, an `APRR`/`SPRR` permission slot): `DyldCacheDataConstLazyScopedWriter` flips the current CPU core's `TPRO` register to `RW-` solely for the microseconds needed to record a `dlopen()` `JustInTimeLoader` node or lazy `__DATA_CONST` fixup, and immediately locks `TPRO` back to `R--` before calling library initializers or `main()` [2, 197, 202, 203].

## Platform Forks Across Apple OSes

Across `iOS`, `iPadOS`, `watchOS`, `visionOS`, and `PCC`, the `dyld_shared_cache` (plus separate `/System/DriverKit/` and `/System/ExclaveKit/` caches) is compiled exclusively by Apple's build infrastructure and sealed inside `SSV` or `Cryptex1`; endpoints never build shared caches locally, and `SSV` root sealing cannot be turned off [37, 186, 197]. Prior to `macOS Big Sur` (`10.15` and earlier), `macOS` ran `update_dyld_shared_cache` locally as `root` after updates, a fragile persistence target retired permanently when `Big Sur` adopted `iOS`-style pre-built `SSV` shared caches [185].

Today, `macOS` forks from `iOS` in two strictly bounded ways [37, 186, 202]. First, notarized `macOS` applications routinely bundle hundreds of private `.dylib`s and plug-ins outside `/System`, exercising `dyld4`'s `JustInTimeLoader` (`LC_DYLD_CHAINED_FIXUPS` userland page-in linking via `DYLD_CHAINED_PTR_ARM64E_USERLAND24`) and `@rpath` resolution under Hardened Runtime Library Validation ([Chapter 6](06-amfi-txm-notarization.md)) [188, 200, 202]. Second, if a physical Mac owner enters paired `1TR` ([Chapter 2](02-mac-localpolicy.md)), downgrades a test volume to `Permissive Security`, disables `SIP` and `FileVault`, and runs `csrutil authenticated-root disable` (`bputil -s`, setting `LocalPolicy.sip1 = true`), `apfs.kext` permits mounting unsealed `APFS` snapshots (`mount -o nobrowse -t apfs` followed by `bless --mount ... --bootefi --create-snapshot`) on that volume group alone [37, 192]. Notice why Apple forbids setting `LocalPolicy.sip1 = true` whenever `FileVault` is active on that volume group: if an unauthenticated root snapshot could boot while `SEP` still auto-unwrapped `FileVault` volume keys after login, an offline attacker who tampered with `/sbin/launchd` on an unsealed `System` partition could harvest decrypted `Data`-volume secrets, so `BootPolicy` enforces mutual exclusion between `FileVault` key custody and unsealed `SSV` snapshots [37, 192].

## In-the-Wild Failures & Architectural Bounds

`APFS` `SSV` completely ended persistent `/` filesystem modification in the wild, forcing both commodity `macOS` malware and mercenary `iOS` spyware out of `/System` and upward into `Data`-volume persistence, `Cryptex1` downgrade attempts, `@rpath` loader abuse, and in-memory `dyld` state corruption (`Fugu15`, `CVE-2026-20700`).

### Search-Path Hijacks, Fugu15, and CVE-2026-20700 (DarkSword)

Tracking offensive abuse of `dyld` across a decade of `macOS` and `iOS` disclosures illuminates why hardening the filesystem (`SSV`) inevitably concentrates pressure onto dynamic-linker state transitions [22, 23, 198, 204, 205, 206]. Before `SSV` and Notarization matured on `macOS`, Patrick Wardle documented widespread user-space persistence and privilege escalation via `dyld` search-path hijacking: when a privileged or `TCC`-authorized third-party Mach-O binary contained `LC_LOAD_WEAK_DYLIB` commands pointing to a nonexistent optional dylib or multiple `@rpath` directories (`LC_RPATH`) where an earlier search directory sat writable on `Data`, planting a malicious `.dylib` hijacked execution at `_dyld_start` without modifying the signed host binary; similarly, unhardened binaries lacking `CS_RESTRICT` or Hardened Runtime (`CS_RUNTIME`) honored `DYLD_INSERT_LIBRARIES` environment injection [198, 204]. In `bsd/kern/mach_loader.c`, `XNU` neutralizes environment injection on setuid, entitled, and `CS_RUNTIME` binaries by setting `CS_RESTRICT` before `_dyld_start` runs, causing `dyld4`'s `ProcessConfig::Security` constructor to prune all `DYLD_*` variables unconditionally [186, 198].

On `arm64e` `iOS`, attackers targeted deeper architectural seams between `mach_loader.c`, `dyld4`, and hardware pointer authentication. In October 2022, Linus Henze's `Fugu15` chain on `iOS 15.4.1` demonstrated how discrepancies between kernel Mach-O segment loading and `dyld4` user-space mapping (chained with a `CoreTrust` signature-validation flaw) allowed pivoting into attacker-controlled `arm64e` execution prior to `SPTM`/`TXM` deployment, directly motivating Apple to isolate trust-cache and `CDHash` evaluation inside `GL0` `TXM` and enforce `Launch Constraints` across system binaries [198, 205].

Four years later, in early 2026, Apple (`iOS 26.3` and `macOS Tahoe 26.3` security updates) and Google Threat Intelligence Group (`GTIG`), iVerify, and Lookout disclosed `CVE-2026-20700`: an actively exploited zero-day memory-corruption vulnerability in `dyld` spanning `iOS`, `iPadOS`, `macOS`, `watchOS`, `tvOS`, and `visionOS`, deployed at the core of the *DarkSword* commercial iOS exploit kit [22, 23, 206]. At first glance, spending a scarce cross-platform zero-day inside `dyld` seems paradoxical: *DarkSword* had already achieved arbitrary in-process memory read/write inside `WebContent` (`CVE-2025-43529` in `JavaScriptCore`) and downstream daemons (`mediaplaybackd` via `CVE-2025-43510`) [23]. Why did arbitrary heap read/write still require a dedicated `dyld` vulnerability to achieve arbitrary code execution?

On modern `arm64e` silicon (`SPTM` + `TXM` + `FPAC` + `TPRO`), raw memory read/write inside a non-JIT daemon is boxed in from every angle: `SPTM` (`GL2`) bars mapping anonymous writable memory executable (`XNU_USER_EXEC` requires a `TXM`-verified `CDHash`), `FPAC` traps synchronously on any forged `vtable` or return address, and `dyld4` locks both `__DATA_CONST` and its own `RuntimeState` pools `R--` behind hardware `TPRO` [2, 197, 203]. Yet `dyld` itself *must* possess legitimate `arm64e` `PAC`-signing paths, legitimate `DyldCacheDataConstLazyScopedWriter` gates that flip `TPRO` to `RW-`, and legitimate authority to invoke initializer vectors (`_ModInitFuncs`), C++ static constructors, and `dlopen()` `JustInTimeLoader` callbacks [202, 203]. Because `CVE-2026-20700` arose from improper state validation across `dyld`'s mutable transition structures when an attacker already held a memory-write primitive, corrupting unsealed intermediate loader state tricked `dyld`'s own trusted machinery into unlocking `TPRO`, signing attacker-chosen targets with valid `PAC`s, and dispatching arbitrary execution cleanly without triggering `FPAC` or `SPTM` faults (a data-corruption pivot that `A19`/`M5` `MIE` directly targets by tagging `dyld` and daemon heaps under synchronous `EMTE`) [2, 22, 23, 206].

## Verification & Forensic Artifacts

Inspect the `APFS` Volume Group roles, active `Signed System Volume` seal (`Sealed: Yes`), and mounted read-only `com.apple.os.update-*` root snapshot on `macOS` using `diskutil` and `mount` [37, 184, 192]:

```bash
diskutil apfs list | grep -E 'APFS Volume Disk|Name:|Role:|Sealed:|Snapshot' | head -n 12
mount | grep ' / '
```

Representative output confirming `/` is mounted `read-only` and `sealed` from an immutable snapshot (`disk3s1s1`) rather than raw `disk3s1`:

```text
    Name:                      Macintosh HD (Case-insensitive)
    Role:                      System
    Sealed:                    Yes
/dev/disk3s1s1 on / (apfs, sealed, local, read-only, journaled)
```

Verify active `Cryptex1` (`OS` and `App` / `Safari`) read-only grafts and check `/etc/synthetic.conf` for custom root symlinks [38, 190, 191]:

```bash
mount | grep '/System/Cryptexes'
cat /etc/synthetic.conf 2>/dev/null || true
```

Representative output showing sealed `Cryptex` mounts:

```text
/dev/disk4s1 on /System/Cryptexes/App (apfs, sealed, local, read-only, nobrowse)
/dev/disk5s1 on /System/Cryptexes/OS (apfs, sealed, local, read-only, nobrowse)
```

Confirm the active `arm64e` `dyld_shared_cache` and `.tpro_const` / `.data` subcache files staged inside the `Preboot` `OS` `Cryptex` [197, 199]:

```bash
ls -lh /System/Volumes/Preboot/Cryptexes/OS/System/Library/dyld/dyld_shared_cache_arm64e* 2>/dev/null | head -n 4
```

Sealing `/` via `APFS` `SSV` and kernel page-in `PAC` rebasing guarantees that system libraries match Apple's published release bit for bit, yet user space constantly executes third-party apps and tools off the *unsealed* `Data` volume (`/Applications`, developer builds, App Store downloads). [Chapter 6](06-amfi-txm-notarization.md) traces how `AMFI`, `TXM` (`GL0`) trust caches, `DER` entitlements, `Launch Constraints`, and `Notarization` govern every executable page faulted from any volume.
