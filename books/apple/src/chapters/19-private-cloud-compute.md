# Private Cloud Compute and Verifiable Cloud Inference

## Overview

* **Link in the Chain:** Verifiable confidential-cloud capstone of Part IV; extends `Boot ROM`, `Image4`, `SEP` attestation, `SPTM`, `TXM`, and cryptographic transparency logs ([Chapter 1](01-secure-boot.md) through [Chapter 6](06-amfi-txm-notarization.md), [Chapter 12](12-sep-app-device-attestation.md), [Chapter 16](16-imessage-pq3-kt.md)) into data-center inference (`PrivateCloudComputeLanguageModel`) across both custom Apple Silicon blades and Google Cloud bare-metal confidential GPU clusters.
* **Core Security Invariant:** Client devices (`Thimble` / `privatecloudcomputed`) wrap prompt keys via `HPKE` exclusively to attested ephemeral keys of stateless `PCC` nodes whose exact `Image4` or multi-vendor `Titan`/`Intel TDX`/`NVIDIA B200` release digests appear in the public append-only `Apple Transparency Service` log, authenticated via unlinkable `RSA Blind Signature` (`Privacy Pass`) tokens over third-party `Oblivious HTTP` (`OHTTP`) relays.
* **Platform Matrix:** Client-side `PCC` attestation verification, `OHTTP` IP blinding, and `WWDC26` `PrivateCloudComputeLanguageModel` APIs run across `iOS` (`18.1+`/`26+`), `iPadOS`, `macOS` (`15.1+`/`26+`, including the `fm` CLI and `pccvre` research VM), `visionOS`, and `watchOS 27`, served by bare-metal Apple Silicon (`pccOS`) and Google Cloud `A4` (`aCOS` + `Megacontainer`) nodes.
* **Trusted Computing Base (TCB):** On Apple Silicon nodes, `Boot ROM`, `SEP` (`DCIK` and `Ephemeral Data Mode`), `SPTM`/`TXM`, `pccOS` plus signed `Cryptexes`, and `splunkloggingd` static allowlists; on Google Cloud `A4` nodes, `Google Titan` TPM, `Intel Emerald Rapids TDX` (`PCK`), and `NVIDIA Blackwell B200` Confidential GPUs; plus non-collusion between third-party `OHTTP`/`MASQUE` relays (`Cloudflare`/`Fastly`) and Apple, audited by external researchers.
* **Failure Horizon & Handoff:** Exploiting a vulnerability inside a publicly logged `PCC` release prior to 14-day certificate expiry, unredacted runtime string interpolation slipping past pre-release log review, or user-consented handoff to external clouds (`ChatGPT`, `Claude`, `Gemini`) outside `PCC` boundaries; leads into the full-chain and statutory compulsion finale in [Chapter 20](20-mercenary-chains-compulsion.md).

## Threat Model & Design Tension

For two decades, consumer cloud services and frontier AI APIs rested on an unverifiable operational contract: *"Your prompts traverse TLS 1.3 to our edge load balancers, and our terms of service promise not to train on or inspect your cleartext."* From a systems-security perspective, terminating TLS at a provider's perimeter proxy places *the entire data-center fleet, every site-reliability engineer (`SRE`) holding break-glass SSH or `kubectl exec` access, every packet-capture appliance, every crash-dump collector, every unstructured logging pipeline, and every targeted government wiretap order squarely inside the user's Trusted Computing Base (`TCB`)* [5, 505]. During a routine latency outage, an engineer enabling verbose ingress request logging or snapshotting a live container heap can inadvertently copy millions of private medical summaries, draft legal briefs, and source-code snippets into persistent telemetry stores without leaving any client-detectable trace [5, 506].

Why couldn't Apple simply rent standard enterprise *Confidential Virtual Machines* (`AMD SEV-SNP` or `Intel TDX`, such as Windows `Azure Confidential VMs` with `OpenHCL` [507, 508]) and declare the problem solved? Enterprise confidential computing was architected for a *tenant-versus-cloud-provider* boundary: when an enterprise bank (`Contoso`) deploys a confidential VM on Azure, CPU inline memory encryption and hardware page-ownership tables (`RMP` / `PAMT`) exclude `Microsoft`'s host hypervisor from reading guest DRAM, *while `Contoso`'s own administrators retain SSH access, encrypted persistent virtual disks, and full control over the guest OS image* [5, 508]. In a first-party consumer AI service (`Apple Intelligence` and `WWDC26`'s 32,000-token `PrivateCloudComputeLanguageModel` [6, 490]), *Apple itself is the service operator*! Hardware memory encryption proves nothing to an end user if Apple could sign a second, undisclosed "logging-enabled" server image and route prompts coming from one targeted journalist's IP address to that special node [5, 505].

To exclude *both* data-center operators and *Apple itself* from runtime access to user prompts, Apple SEAR structured *Private Cloud Compute (`PCC`)* around five non-negotiable engineering requirements grouped across three assurance tiers (*High-Security Inference*, *Verified Service and Cloud*, and *Frontier Security and Privacy*) [5, 505]:

First, *Stateless Computation*: personal prompt data is used solely to fulfill the active inference request, never touches persistent non-volatile storage, and becomes cryptographically unrecoverable upon request completion or reboot [5, 505]. Second, *Enforceable Guarantees*: confidentiality and code integrity rest on silicon roots (`SEP`, `SPTM`, `TXM`, or multi-vendor confidential hardware) rather than perimeter firewalls or employee policy rules [5, 509]. Third, *No Privileged Runtime Access*: production nodes contain zero SSH daemons, zero interactive shells, zero live debuggers, and zero dynamic code-loading paths, even during severe outages [506]. Fourth, *Non-Targetability*: neither network ingress nor load balancers learn which user or IP submitted a request, forcing any physical or supply-chain attacker to mount a noisy fleet-wide attack rather than surgically targeting one individual [5, 510]. Fifth, *Verifiable Transparency*: client devices mathematically refuse to encrypt prompts to any server node whose exact software measurements have not been pre-committed to a public append-only Merkle Transparency Log and published as inspectable binaries for outside security researchers [5, 511, 512].

## Silicon & System Mechanics

### Custom Apple Silicon Blades, Ephemeral Data Mode, and Restricted Execution Mode

Apple's primary `PCC` fleet runs on custom-engineered, bare-metal Apple Silicon server blades housed multiple nodes per chassis alongside an Apple Silicon Baseboard Management Controller (`BMC`) over untrusted chassis-internal networking [5, 509]. Running bare metal as the sole tenant eliminates both hypervisor escape surfaces and cross-tenant CPU cache/speculative side channels [509]. Supply-chain provenance begins on the factory floor: each server blade undergoes high-resolution optical component imaging before chassis sealing and physical tamper-switch activation, followed by multi-team cross-verification monitored by an independent third-party observer upon data-center arrival [5, 505]. Only after passing physical validation is a node provisioned with an X.509 attestation certificate anchored in its on-die `SEP` hardware `UID`-derived *Data Center Identity Key (`DCIK`)* [122, 509].

At boot, the Application Processor (`AP`) executes immutable mask `Boot ROM` ([Chapter 1](01-secure-boot.md)), locking the digest of the node's `Image4` boot manifest into a write-once hardware register before launching `iBoot` and a stripped, hardened subset of `iOS` and `macOS` (`pccOS`) [5, 509]. Storage persistence is eliminated in silicon via *Ephemeral Data Mode*: on every boot, `SEP` generates a fresh random storage-key hierarchy for the scratch data volume in volatile enclave memory and *never persists those keys to non-volatile flash*, guaranteeing immediate cryptographic erasure whenever `SEP` resets [5, 509].

Above the minimal `pccOS` kernel (which strips shells, script interpreters, and `Developer Mode` debugging hooks [506, 509]), `PCC` composes its runtime exclusively from signed, measured *Cryptexes* ([Chapter 5](05-apfs-ssv-dyld.md)): a `Private Cloud Extensions` system cryptex (node initialization, attestation, and multi-node ensemble coordination), `Application cryptexes` (`CloudBoard` request termination, `TIE` Trusted Inference Engine, `EnsembleWarden` encrypted multi-turn KV-cache reuse, plus `PCC` workloads such as `PCCAgent`, `MultiTurnAgent`, `VisualGeneration` diffusion, and `HKSVAnalysis` [505, 513]), and data-only *Codeless cryptexes* carrying foundation model weights and LoRA adapters mapped strictly non-executable [509]. During startup, `darwin-init` mounts and activates those cryptexes under `APFS` `Signed System Volume` (`SSV`) Merkle sealing [37], *ratchets every active `Image4` and cryptex manifest irreversibly into `SEP` measurement registers*, and transitions the node into *Restricted Execution Mode* [509]: `TXM` (`GL0`, [Chapter 6](06-amfi-txm-notarization.md)) locks the Trust Cache permanently so zero dynamic trust caches, zero `JIT` pages, and zero unsigned executables can ever load until reboot [5, 36, 509]!

### No Privileged Runtime Access and Structured Log Allow-Listing (splunkloggingd)

How do Apple SREs operate millions of cloud inference cores if `sshd` and live debuggers do not exist, and failing blades can only be rebooted or replaced [506]? `PCC` enforces five deterministic outbound telemetry bounds compiled directly into the measured release [506, 513].

First, `PCC` removes general-purpose string logging and routes all node output through `splunkloggingd` (`darwinOSBits/splunkloggingd` in `github.com/apple/security-pcc`) governed by *static published allowlists* [506, 513]. Every single log statement and metric emitted by a process whose address space handles user prompts is individually reviewed by argument type prior to release; `secureconfigd` (`libsecureconfig`) allows runtime control-plane policies to *narrow* emitted logs during operation, but *never to expand output beyond the compiled allowlist* inspectable by external researchers [506, 513]. Second, because crash reports and backtraces cannot be enumerated ahead of time, `PCC` strips register/heap fields capable of holding user prompt slices and aggressively rate-limits and samples crash exports [506]. Third, remote diagnostic RPCs expose only a fixed enum of safe health probes (external connectivity, encrypted-interface packet capture, aggregate resource counters). Fourth, metrics whose magnitude or timing might correlate with prompt tokens undergo *in-node threshold suppression and differential noise injection* before export; fifth, `EventHorizon` (`securitymonitorlited`) exports strictly fixed-schema security telemetry (process launches and `Seatbelt` violations, never file or buffer contents) [506, 513].

### Target Diffusion: Privacy Pass Blind Tokens, OHTTP Relays, and Thimble Validation

Even a hermetic, diskless node fails if an attacker who physically compromises one blade in a rack can steer a specific dissident's requests onto that blade [5, 510]. `PCC` defeats targeted routing through *Target Diffusion*, orchestrated on the client device by `modelmanagerd`, `PrivateMLClientInferenceProviderService`, and the `Thimble` project's `privatecloudcomputed` daemon (`CloudAttestation`) [510, 513]:

![Figure: Private Cloud Compute (PCC) end-to-end request lifecycle combining Transparency Log Image4 verification, third-party OHTTP IP blinding, and stateless SEP-attested node inference.](diagrams/19-pcc-ohttp-attestation-flow.svg)

Trace the updated client-to-node cryptographic protocol (`iOS` and `macOS 27` single-step `TGS` flow [510]):

First, *Unlinkable Rate-Limiting via `RSA Blind Signatures` (`Privacy Pass`)* [510, 514, 515, 516]: to block denial-of-service abuse without attaching an Apple Account or device serial to inference calls, `privatecloudcomputed` authenticates out of band to Apple's *Token Granting Service (`TGS`)* and requests a batch of blinded *One-Time Tokens (`OTT`s)* constructed under `RFC 9474` (`RSA Blind Signatures` [514]) and `RFC 9576`/`9578` (`Privacy Pass` [515, 516]). Mathematical blindness guarantees that when the client later unblinds and attaches a single `OTT` to an inference request (and when `CloudBoard` in `iOS`/`macOS 27` returns a blinded *cost token* carrying only bucketed timestamps and compute cost so variable-size 32K reasoning calls debit rate limits fairly [510]), Apple's `PCC` Gateway verifies token validity under the `OTT` public key (whose uniqueness across all users is itself audited in the Transparency Log!) *with zero cryptographic link back to the `TGS` issuance session* [510].

Second, *Source-IP Blinding via Chunked `Oblivious HTTP` (`RFC 9458`)* [16, 510, 517]: the client wraps its request in an outer `HPKE` (`RFC 9180` [518]) envelope addressed to Apple's *Oblivious Gateway (`OG`)* and transmits it over `HTTP/3` (`QUIC`, falling back to `HTTP/2`) to a randomly chosen third-party *Oblivious Relay (`OR`)* operated by an independent network partner (`Cloudflare` or `Fastly`, authenticated via distinct `Privacy Pass` tokens!) [510, 517]. The third-party `OR` sees the client's source IP address (`TCP`/`QUIC`), strips it, and forwards the opaque `OHTTP` ciphertext to Apple's `OG`; Apple's `OG` and `PCC` Gateway never see the user's IP address, while `Cloudflare`/`Fastly` never see the inner request or target nodes [16, 510].

Third, *Client-Side `Thimble` Attestation & `HPKE` Key Wrapping* [510, 511, 513]: the `PCC` Gateway returns attestation bundles for a small candidate subset of ready compute nodes (unable to bias selection toward a targeted user because the request is anonymous!). Locally on the user's `iPhone` or `Mac`, `privatecloudcomputed` invokes `CloudAttestation` to verify every candidate node $N$ before releasing a single prompt token [510, 511, 513]:

$$\text{AcceptNode}(N) \iff \text{VerifyChain}_{\text{HW}}(\texttt{Bundle}_N) \;\land\; \text{VerifyLogInclusion}\bigl(\text{Digest}(\texttt{Release}_N),\, \text{Milestone}_{\text{AT}},\, t_{\text{exp}} \le 14\text{d}\bigr)$$

Only for nodes passing both hardware certificate verification and public Transparency Log inclusion does the client wrap the inner `HPKE` content-encryption key directly to the node's ephemeral attested public key (generated inside `SEP` / `Key Protection Service` with strict short TTLs [5, 510]). Load balancers and `OG` proxies hold zero decryption keys; `CloudBoard` inside the chosen `PCC` node unwraps the request inside an isolated per-request namespace, runs inference (validating any downstream ensemble worker nodes transitively against the client's committed *trusted log revision* [510, 511]), encrypts the streamed response directly back to the client, zeroizes the request arena, and recycles shared inference worker address spaces on short TTL timers [5, 519].

### Verifiable Release Transparency, MASQUE Log Proxies, and the PCC VRE

How does `PCC` guarantee that Apple cannot serve a doctored Transparency Log view to one target IP, or ship a backdoored binary into the log unnoticed [511, 512]?

![Figure: Private Cloud Compute release transparency architecture linking MASQUE-blinded Merkle milestones, client-side Thimble/CloudAttestation enforcement, and macOS pccvre researcher verification.](diagrams/19-extra-vre-transparency-log-audit.svg)

Managed by the `Apple Transparency Service` (shared with `iMessage` `KT` from [Chapter 16](16-imessage-pq3-kt.md)), the `PCC` Merkle log enforces three anti-equivocation defenses [511]. First, clients fetch Transparency Log proofs and daily promoted *milestones* exclusively through hardcoded third-party `RFC 9298` *`MASQUE` proxies* [511, 520], hiding client IPs from the log server itself so an attacker cannot selectively serve a forked tree! Second, every logged release carries a mandatory *14-day maximum expiry* (requiring active releases to be re-logged every two weeks), and devices validate backward Merkle consistency proofs across daily milestones right back to log genesis (alerting if any inconsistency remains unresolved after a 7-day operational recovery window) [511]. Third, Apple publishes the actual production binary artifacts (including, for the first time on any Apple platform, *unencrypted plaintext `iBoot` and `sepOS` firmware* alongside `pccOS`, `splunkloggingd` allowlists, and `github.com/apple/security-pcc` source code!) paired with the *`PCC` Virtual Research Environment (`VRE`, `pccvre`)* built into `macOS` (`15.1+` / `26+`) [5, 512, 513]. Running atop `Virtualization.framework` on any Apple Silicon Mac, `pccvre` virtualizes *both* the `AP` and `SEP`, allowing independent researchers (backed by $1,000,000 *Apple Security Bounty* awards [521]) to boot exact production `PCC` builds, override `darwin-init` `Restricted Execution Mode`, inject custom shell `Cryptexes`, and audit every IPC and logging boundary [512].

### WWDC26 Expansion: PCC on Google Cloud (Titan + Intel TDX + NVIDIA B200)

In June 2026 (*Expanding Private Cloud Compute* [519, 522]), as Apple Intelligence scaled frontier Gemini-derived reasoning and multimodal agentic workloads [6, 519], Apple extended `PCC`'s exact five-requirement trust model beyond Apple-owned data centers onto *bare-metal Google Cloud `A4` instances* [519, 522]. Rather than trusting a single x86 silicon vendor's enclave root or sharing multi-tenant cloud hosts, `PCC` on Google Cloud composes confidential hardware from *three independent silicon vendors* on dedicated sole-tenant bare-metal servers [519, 522]:

First, the host's *Google `Titan` hardware security chip* (`TPM 2.0` root of trust [523]) measures and attests system firmware and Google's hardened Container-Optimized OS (`host-acos` `KVM`/`QEMU` stack [513, 522]). Second, dual *Intel `Emerald Rapids` CPUs with `Intel TDX`* (`Trust Domain Extensions`, bound under a single multi-package `PCK` certificate [507, 522]) isolate two separate memory-encrypted Confidential VMs: a dedicated *`Key Protection Service` CVM* (`key-protection-module`, shielding attested `HPKE` private keys away from external network parsers!) and the *`Workload VM`* running Apple's single measured *`Megacontainer`* (`CloudBoard-GoogleCloud`, inference engine, and `lsecuritymonitorlited`) [513, 519, 522]. Third, eight *`NVIDIA Blackwell B200` GPUs running in `NVIDIA Confidential Computing` mode* [522, 524] isolate `HBM` memory from the host, attest their own GPU firmware, and negotiate session keys with the `TDX` CVM and peer GPUs to encrypt all prompt and activation tensors crossing `PCIe` and `NVLink` buses [522, 524]! Local scratch SSDs are physically unavailable, `ConnectX-7` GPUDirect RDMA NICs carry zero traffic (using only Intel `IDPF` interfaces), the host Linux kernel outright denies loading the NVIDIA driver, and Apple maintains an append-only hardware supply-chain ledger requiring conjunctive attestation quotes across multiple independent vendor roots (`CloudAttestation-GoogleCloud`) matched against dual software-and-firmware Transparency Log entries [511, 513, 519, 522].

## Platform Forks Across Apple OSes

Across `iOS`, `iPadOS`, `macOS`, `visionOS`, and (new in `WWDC26`) `watchOS 27` [490], `privatecloudcomputed` enforces identical `OHTTP`, `Privacy Pass`, and Transparency Log predicates whether an inference request lands on an Apple Silicon blade or a Google Cloud `A4` node [510, 511]. At `WWDC26`, Apple opened `PrivateCloudComputeLanguageModel` (`32,000`-token context window with configurable `reasoningLevel` [490]) to third-party developers with fewer than 2 million first-time App Store downloads at zero cloud API cost [6]. Conversely, whenever a user or developer opts into *external* cloud providers (`ChatGPT` via Siri, or third-party `Claude`/`Gemini` Swift packages conforming to `FoundationModels`' `LanguageModel` protocol [5, 6]), requests explicitly cross outside `PCC`'s hardware/Transparency-Log perimeter under user/app consent and rely on the external provider's contractual policies.

Observe how these failure modes clarify what `Private Cloud Compute` solves and what remains outside its boundary [505, 506, 512]. Against data-center operators, rogue insiders, fiber wiretappers, and targeted government warrants seeking one user's cloud AI transcripts, `PCC` eliminates server-side key custody and identity linkability simultaneously: `OHTTP` (`Cloudflare`/`Fastly`) strips source IPs, `TGS` `RSA Blind Signatures` (`Privacy Pass`) strip `Apple Account` linkability, `Ephemeral Data Mode` and disabled scratch SSDs eliminate post-reboot forensics, and `splunkloggingd` allowlists block arbitrary runtime introspection [5, 506, 510, 522]. Conversely, `PCC` deliberately treats two domains as explicit research perimeters subject to continuous public audit and $1,000,000 Apple Security Bounty incentives [512, 521]: first, human review of static log allowlists where an allowed object `.description` string could inadvertently format sensitive state unless caught by pre-release or external `VRE` audits [506]; and second, memory-safety or deserialization bugs inside `CloudBoard`, media decoders, or unpublished `Codeless cryptex` model-weight parsers during the 14-day lifetime of a signed Transparency Log release [511, 512]. Finally, because `PCC` faithfully executes whatever reasoning task the client submits, confidential cloud inference never replaces client-side `.onToolCall` authorization ([Chapter 18](18-agentic-ai-workload-isolation.md)) when returned structured outputs drive local actions [490].

> **Key idea.**
> `Private Cloud Compute` proves that "cloud privacy" need not rest on corporate promises [5, 505]. By combining stateless ephemeral keys, third-party `OHTTP`/`MASQUE` network blinding, `Privacy Pass` anonymous tokens, and a hard client-side `Thimble` gate rejecting any server measurement absent from a globally inspected Transparency Log, `PCC` forces any backdoor (even one ordered on Apple itself) to become a publicly downloadable binary artifact visible to every researcher running `pccvre` [510, 511, 512].

## Verification & Forensic Artifacts

On `macOS` (`15.1+` / `26+`), inspect the built-in `pccvre` Virtual Research Environment CLI and check active `privatecloudcomputed` (`Thimble`) and `modelmanagerd` daemons [510, 512, 513]:

```bash
which pccvre >/dev/null 2>&1 && pccvre release list 2>/dev/null | head -n 4 || true
launchctl print "gui/$(id -u)/com.apple.privatecloudcomputed" 2>/dev/null | grep -E 'state =|path =' | head -n 4
```

Expected output confirming `Thimble`'s local attestation verifier daemon on `macOS`:

```text
	path = /System/Library/PrivateFrameworks/PrivateCloudCompute.framework/Resources/privatecloudcomputed
	state = running
```

Monitor live `Private Cloud Compute` `OHTTP` relay selection, `TGS` `Privacy Pass` token redemption, and `Transparency` milestone checks via Unified Logging [510, 511]:

```bash
log show --last 1h --predicate 'subsystem CONTAINS "PrivateCloudCompute" OR subsystem == "com.apple.Transparency"' --style compact | tail -n 4
```

To inspect exact attested `Image4` or Google Cloud `A4` release measurements for recent personal cloud requests, users can also export the biometric-gated *Apple Intelligence Report* (*System Settings* to *Privacy & Security* to *Apple Intelligence Report*) and cross-check every logged release digest directly against `security-pcc` tooling [511, 513]:

```bash
ls -ld "$HOME/Library/Application Support/com.apple.privatecloudcomputed" 2>/dev/null || true
```
