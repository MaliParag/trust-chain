# Anti-Rollback Indexes, dm-verity, fs-verity, and APEX Mainline

## Overview

* **Link in the Chain:** Temporal and runtime storage-integrity layer; extends [Chapter 1](01-bootrom-avb-vbmeta.md)'s boot-time `VBMeta` signature check forward across time (blocking signed firmware and module downgrades via `RPMB`) and across every runtime $4\text{ KiB}$ block, `fs-verity` inode, and modular `APEX` read inside the running Linux kernel.
* **Core Security Invariant:** A signed `VBMeta` or `APEX` image is admitted only if its `rollback_index` satisfies $\text{index}_{\text{image}} \ge \text{floor}_{\text{RPMB}}$ (ratcheted permanently only after `markBootSuccessful()`), and the kernel admits a read-only filesystem page into the page cache if and only if its salted `SHA-256` Merkle path (directly or after `RS(255, 253)` parity repair) matches the authenticated root digest.
* **Ecosystem Enforcement Tier:** Enforced identically in `GREEN` and `YELLOW` locked states (`VERITY_MODE_RESTART` + `RPMB` hardware rollback counters); decoupled or bypassed in `ORANGE` unlocked developer builds (`fastboot --disable-verity`) so owners can test experimental kernels without bricking rollback floors.
* **Trusted Computing Base (TCB):** `UFS`/`eMMC` `Replay Protected Memory Block` (`RPMB`) authenticated via 256-bit `HMAC-SHA256` keyed in `TEE`/`StrongBox`, `IBootControl` A/B slot state machine, Linux `drivers/md/dm-verity*` and `dm-verity-fec.c`, VFS `fs/verity/`, `odsign`, and userspace `system/apex/apexd`.
* **Seam & Handoff:** Guarantees immutable, downgrade-resistant OS and Mainline module code from flash to kernel page cache, rendering persistent `/system` rootkits extinct, yet cannot protect mutable cryptographic keys or throttle PIN guesses; hands hardware secret isolation to `TrustZone` and `StrongBox` in [Chapter 3](03-trustzone-strongbox.md).

## Threat Model & Ecosystem Constraint

Cryptographic digital signatures are inherently timeless unless anchored to mutable monotonic state. Suppose an OEM signs `boot.img` and `vbmeta.img` in January 2025 under its fused production root key $K_{\text{OEM}}$, remediates a critical `EL1` kernel privilege-escalation vulnerability in March 2025, and ships a patched OTA signed under the exact same $K_{\text{OEM}}$ (because `Boot ROM` `OTP` fuses cannot be rotated on deployed handsets). Without hardware anti-rollback protection, an attacker with physical `fastboot`/`EDL` access or transient `Ring 0` flash-write privileges can overwrite `boot_a` and `vbmeta_a` with the genuine January 2025 images, pass every `RSA-4096` and `SHA-256` verification check in [Chapter 1](01-bootrom-avb-vbmeta.md) with `GREEN` status, and re-exploit the patched vulnerability indefinitely [22, 140]. Yet monotonic counters introduce an equally perilous availability hazard: if a bootloader incremented its irreversible hardware floor *before* confirming that a newly installed OTA actually boots to userspace, a single buggy OTA crashing in `init` would lock out both the broken new slot and the previously working fallback slot, permanently bricking millions of consumer phones [140, 141].

A second threat arises *after* `ABL` jumps to the Linux kernel. On a modern flagship carrying four to six gigabytes of read-only `/system`, `/vendor`, `/product`, and `/system_ext` `EROFS` partitions [142], `ABL` cannot stall boot for ten seconds to linearly hash gigabytes of `UFS` flash, nor would a one-time boot scan detect an interposer or runtime block-device exploit mutating flash sectors *after* `/` is mounted [23, 143]. Simultaneously, high-density 3D TLC/QLC `NAND` inside `UFS` packages experiences non-zero physical charge leakage, read-disturb errors, and cosmic-ray bit flips over a five-to-seven-year handset lifecycle [143, 144]. Prior to Android 7.0, OEMs feared that strict `DM_VERITY_MODE_RESTART` would turn harmless single-bit media defects in unused font or ringtone files into fatal bootloops, tempting vendors to ship weaker `EIO` or `LOGGING` modes that degraded security guarantees [143, 144].

Third, immutable whole-partition `dm-verity` created an acute servicing bottleneck across Android's multi-vendor supply chain [10, 81, 82]. Historically, patching a heap overflow in `Conscrypt` TLS, media codec extractors, `DnsResolver`, or the `ART` runtime required rebuilding `/system`, regenerating its entire `dm-verity` Merkle tree, re-signing `vbmeta_system`, and waiting months for OEM and carrier regression testing. Android needed a modular package architecture (`Project Mainline` `APEX`) capable of delivering Google-signed binary OS updates directly through Google Play onto mutable `/data` while preserving `dm-verity` block-level immutability and rollback protection [81, 83].

## Architecture & AOSP Implementation

### `RPMB` Authenticated Silicon Storage and the A/B Slot Ratchet

`AVB 2.0` blocks signed partition downgrades by pairing the 64-bit `rollback_index` inside `AvbVBMetaImageHeader` across up to 32 independent rollback locations (`slot 0` for root `vbmeta` and `slots 1..31` assigned to chained partitions such as `vbmeta_system` and `vbmeta_vendor` via `AvbChainPartitionDescriptor` [88, 130]) against hardware-authenticated counters stored in the flash package's `Replay Protected Memory Block` (`RPMB`) [140, 145, 146]. Standardized in JEDEC `eMMC` (`JESD84`) and `UFS` (`JESD220` / `UFS 4.0` [145, 147]), `RPMB` is a dedicated physical partition inside the `UFS` controller provisioned once on the secure factory line with a per-device 256-bit shared secret key $K_{\text{RPMB}}$ burned simultaneously into `UFS` one-time registers and sealed inside the SoC's `TrustZone` TEE (or discrete `StrongBox`) [146, 147].

Normal World software (`ABL` or `EL1` Linux `ufs_bsg` drivers) acts solely as an untrusted packet courier between the `TEE` `AVB` trustlet and the `UFS` chip; `EL1` never sees $K_{\text{RPMB}}$ [146]. Every 512-byte `RPMB` protocol frame embeds a 256-byte payload, a 16-byte caller `nonce` (for reads), a 32-bit strictly monotonic hardware `write_counter` maintained internally by the `UFS` silicon, address/block counts, and a 32-byte `HMAC-SHA256` computed under $K_{\text{RPMB}}$:

$$\text{MAC}_{\text{RPMB}} = \text{HMAC-SHA256}_{K_{\text{RPMB}}}\bigl(\texttt{data}_{256} \parallel \texttt{nonce}_{16} \parallel \texttt{write\_counter}_{4} \parallel \texttt{addr}_{2} \parallel \texttt{cnt}_{2} \parallel \texttt{res}_{2} \parallel \texttt{req}_{2}\bigr)$$

When updating `stored_rollback_index[s]`, the `TEE` first reads the live `write_counter` from `UFS` (authenticated with a fresh 16-byte random `nonce`), increments `write_counter` by 1, signs the new `RPMB` write frame with $K_{\text{RPMB}}$, and sends it to the `UFS` controller [145, 146]. Inside the flash die, the `UFS` controller independently recomputes `HMAC-SHA256`, verifies exact equality with its internal `write_counter`, atomically commits the 256-byte block, and increments `write_counter` in silicon. Desoldering the `UFS` chip or interposing on the M-PHY bus to replay an older `RPMB` sector fails deterministically because `write_counter` has already advanced inside the storage controller [140, 146].

How does Android combine irreversible `RPMB` floors with crash-safe over-the-air (`OTA`) updates? Seamless A/B (`system/update_engine` [141]) and Virtual A/B (`snapuserd` Copy-on-Write snapshots over `dm-user` [148]) maintain two logical boot slots (`_a` and `_b`) governed by the `IBootControl` AIDL HAL (`hardware/interfaces/boot/aidl/android/hardware/boot/IBootControl.aidl` [149]). Each slot carries four metadata flags in `misc` / bootloader storage: `priority` ($0\text{..}15$), `tries_remaining` (initialized to $7$ on update), `successful_boot` ($0$ or $1$), and `verity_corrupted` [141, 149].

Trace an OTA from `slot _a` ($\text{rollback\_index} = 14$, `stored_rollback_index` $= 14$) to `slot _b` ($\text{rollback\_index} = 15$) [140, 141, 149, 150]. While the user works normally on `slot _a`, `update_engine` streams the new payload into `slot _b` (or stages `COW` extents on `/data/gsi/ota`), verifies target partition hashes, and calls `IBootControl::setActiveBootSlot(1)` (`successful_boot = 0`, `tries_remaining = 7`). On reboot, `ABL` decrements `tries_remaining` to $6$, runs `avb_slot_verify()` on `slot _b`, verifies $15 \ge 14$, and boots `slot _b` *without yet raising `stored_rollback_index` in `RPMB` to 15*! Once `slot _b` reaches userspace, `update_verifier` (`bootable/recovery/update_verifier` [150]) reads every critical block listed in `/data/ota_package/care_map.pb` through `dm-verity` (and merges Virtual A/B snapshots) before invoking `IBootControl::markBootSuccessful()`. Only when `successful_boot` flips to $1$ does the `AVB` HAL / next bootloader entry commit $\text{stored\_rollback\_index}[s] \leftarrow 15$ into `RPMB` [140, 141, 149]. If `slot _b` instead kernel-panics repeatedly, `tries_remaining` counts down to $0$, `ABL` marks `slot _b` unbootable (`isSlotBootable == false`), falls back cleanly to `slot _a` (which still satisfies $14 \ge 14$), and keeps the phone alive; once `slot _b` succeeds, `slot _a` ($14 < 15$) is permanently sealed out against downgrade attacks!

### `dm-verity` Lazy Merkle Trees and `RS(255, 253)` Forward Error Correction

To authenticate multi-gigabyte read-only `EROFS` or `ext4` partitions (`system`, `vendor`, `product`, `system_ext`, `odm` [142]) at page-in granularity, Android interposes the Linux device-mapper `dm-verity` target (`drivers/md/dm-verity-target.c`) between the VFS mount and the underlying `/dev/block/dm-*` logical volume [23, 143]. At build time, `avbtool add_hashtree_footer` divides an image of $N$ data blocks (each $B = 4096$ bytes) into salted leaf digests $d_{0,j} = \text{SHA-256}(\text{salt} \parallel \text{block}_j)$, packs $4096 / 32 = 128$ digests into each $4\text{ KiB}$ level-1 hash block, pads partial blocks with zeroes, and iterates upward through $\lceil \log_{128} N \rceil$ tree layers until a single 32-byte `root_digest` remains inside `AvbHashtreeDescriptor` [22, 23, 130]. For a $4\text{ GiB}$ `/system` image ($N = 2^{20}$ blocks), $\lceil \log_{128} 2^{20} \rceil = 3$ levels consume $32.26\text{ MiB}$ ($\approx 0.79\%$) of flash and require at most three intermediate hash-block checks on a cold cache miss, dropping to a single `ARMv8` hardware `SHA256H` computation once interior hash pages warm the kernel buffer cache [23].

![Figure: Runtime block verification via dm-verity SHA-256 Merkle tree and Reed-Solomon Forward Error Correction.](diagrams/02-dm-verity-merkle-fec.svg)

To enforce `DM_VERITY_MODE_RESTART` strictly across a billion consumer flash chips without false-positive RMA bricking from physical bit-rot, Sami Tolvanen's `dm-verity` Forward Error Correction engine (`drivers/md/dm-verity-fec.c` and `dm-verity-fec.h` [23, 144, 151]) appends interleaved Reed-Solomon parity codes after the hash tree. Specifically, `dm-verity-fec` operates over Galois field $\text{GF}(2^8)$ with codeword length $N_{\text{RS}} = 255$ (`DM_VERITY_FEC_RS_N = 255`) and `fec_num_roots` $= R = 2$ parity roots (`DM_VERITY_FEC_MIN_ROOTS = 2`, yielding $\text{RS}(255, 253)$ at $\approx 0.79\%$ space overhead, configurable up to `MAX_ROOTS = 24`) [130, 151].

Rather than computing Reed-Solomon parity over 253 *contiguous* bytes inside a single $4\text{ KiB}$ page (which would fail instantly if a single dead NAND flash page corrupted all $4096$ bytes at once!), `avbtool` partitions the $M$ total data-plus-hash blocks into `region_blocks` $= \lceil M / 253 \rceil$ regions and *interleaves* one byte from each of 253 widely separated physical blocks into each 255-byte codeword [144, 151]. Because $\text{RS}(255, 253)$ corrects $\lfloor R / 2 \rfloor = 1$ arbitrary byte error per codeword without erasure hints, a contiguous burst corruption destroying $\lceil M / 253 \rceil$ consecutive $4\text{ KiB}$ blocks on flash (for example, *over $16\text{ MiB}$ of consecutive wiped flash sectors* on a $4\text{ GiB}$ `/system` partition!) corrupts at most *one* byte in any interleaved codeword [144]! When `verity_verify_io()` detects a `SHA-256` mismatch on $\text{block}_j$, it invokes `verity_fec_decode()` (`decode_rs8()`), reconstructs candidate block $\widehat{\text{block}}_j$, increments `v->fec->corrected`, and *re-verifies* $\text{SHA-256}(\text{salt} \parallel \widehat{\text{block}}_j)$ against the signed Merkle tree [151]. Natural NAND wear heals invisibly in place; a deliberate multi-region rootkit patch exceeds parity radius, fails the cryptographic re-hash check, sets `verity_corrupted`, and triggers immediate `kernel_restart("dm-verity device corrupted")` [143, 144].

Modern Android releases (`Android 13` through `Android 16`) pair `dm-verity` and `FEC` with two storage-stack refinements that preserve cryptographic integrity while shrinking `super` flash footprints: `EROFS` (`Enhanced Read-Only File System`, `fs/erofs/` [142]) and `Virtual A/B` (`snapuserd` [148]). Unlike `ext4`, which compresses poorly or suffers read-amplification spikes when variable-sized compressed extents cross page boundaries, `EROFS` employs *fixed-sized output compression* (`LZ4` / `LZ4HC` into exact $4\text{ KiB}$ physical `pclusters`), aligning every compressed on-disk extent 1-to-1 with `dm-verity`'s $4\text{ KiB}$ `data_block_size` so page-in verification hashes compressed flash blocks directly before `EROFS` decompresses into page cache in place [142]. Simultaneously, `Virtual A/B` eliminates the 50 percent `super` storage duplication penalty of classic dual-slot partitions by storing post-OTA block deltas inside compressed Copy-on-Write (`COW`) files under `/data/gsi/ota` [148]. During the experimental first boot before `markBootSuccessful()`, early `init` spawns the userspace `snapuserd` daemon bound to `/dev/dm-user` *beneath* `dm-verity`: whenever the kernel faults in a page of `/system_b`, `snapuserd` synthesizes the updated $4\text{ KiB}$ block by combining unchanged `/system_a` extents with `/data/gsi/ota` COW deltas, and `dm-verity` verifies the reconstructed block against `vbmeta_b`'s signed `AvbHashtreeDescriptor` root before admitting a single byte to userspace! Even though unmerged COW deltas sit physically on mutable `/data`, any malicious alteration of `/data/gsi/ota` fails `dm-verity` verification identically to raw flash corruption and triggers automatic rollback to `slot _a` [141, 148].

### File-Granular `fs-verity` Inode Sealing on Mutable `/data`

Whole-partition `dm-verity` works only on immutable read-only block devices (`EROFS`/`ext4` in `super`). Yet Android also stores security-critical read-only artifacts inside the mutable, `fscrypt`-encrypted `/data` (`f2fs` or `ext4`) partition where physical block allocations shift dynamically under garbage collection: Incremental/streamed `APK` packages (`APK Signature Scheme v4` in [Chapter 10](10-apk-signing-scoped-storage.md)), `odsign`-verified `ART` compilation artifacts (`/data/misc/apexdata/com.android.art/dalvik-cache` [152]), and updatable key/certificate bundles [89, 91, 153].

Linux's `fs-verity` subsystem (`fs/verity/`, `include/uapi/linux/fsverity.h` [89, 153]) lifts lazy Merkle verification from the block layer to the VFS inode layer. After a privileged installer writes a file completely to `/data` and closes all writable descriptors, invoking `ioctl(fd, FS_IOC_ENABLE_VERITY, &arg)` (`_IOW('f', 133, struct fsverity_enable_arg)`) builds a per-file $4\text{ KiB}$ `SHA-256` (`FS_VERITY_HASH_ALG_SHA256 = 1`) Merkle tree stored in hidden filesystem metadata blocks past `i_size`, writes a 256-byte `struct fsverity_descriptor` (`version = 1`, `hash_algorithm`, `log_blocksize = 12`, `data_size`, `root_hash`, `salt`), and sets the persistent `FS_VERITY_FL` inode flag [89, 153]:

```c
/* Canonical digest hashed over fsverity_descriptor (uapi/linux/fsverity.h) */
struct fsverity_formatted_digest {
  char   magic[8];          /* "FSVerity" context separation prefix */
  __le16 digest_algorithm;  /* FS_VERITY_HASH_ALG_SHA256 (1) */
  __le16 digest_size;       /* 32 bytes */
  __u8   digest[];          /* SHA-256(struct fsverity_descriptor) */
};
```

Once `FS_VERITY_FL` is active, the VFS unconditionally denies `open(..., O_RDWR)`, `write()`, and `truncate()` with `-EPERM` / `-ETXTBSY`, while `f2fs`/`ext4` `read_folio()` hooks verify every $4\text{ KiB}$ page against the hidden Merkle tree before setting `PG_uptodate` [89, 153]. Userspace services (`odsign` or `PackageManager`) query `FS_IOC_MEASURE_VERITY` (`_IOWR('f', 134, ...)`) in $O(1)$ time to compare the kernel-enforced `fsverity_digest` against a trusted signature, guaranteeing that even a compromised `system` process with directory write permissions on `/data` cannot silently mutate a single byte inside an `fs-verity`-sealed file without tearing down and recreating the file (which fails signature/digest re-measurement) [89, 152, 153].

### `Project Mainline` and `.apex` Container Anatomy

Combining `AVB` `VBMeta`, `dm-verity`, and version floors enabled Android 10+ to launch `Project Mainline` (`Android Pony EXpress`, `system/apex/` [81, 83, 154]), turning core OS userspace subsystems into Google-signed, independently updatable miniature Verified Boot partitions!

![Figure: Project Mainline APEX two-layer signature verification, anti-rollback enforcement, and dm-verity loopback mount pipeline.](diagrams/02-apex-mainline-mount-pipeline.svg)

At the binary container level, an `.apex` archive is an uncompressed, $4\text{ KiB}$-aligned ZIP file (and simultaneously a valid signed APK!) containing four entries [81, 155]: `apex_manifest.pb` (serialized `ApexManifest` Protobuf from `system/apex/proto/apex_manifest.proto` specifying the module `name` such as `com.android.conscrypt`, monotonic 64-bit `version`, `provideNativeLibs`, `requireNativeLibs`, and `jniLibs`), `AndroidManifest.xml` (exposing package metadata to `PackageManager` and Google Play delivery pipelines), `apex_pubkey` (the module's dedicated `AVB` public key), and `apex_payload.img` (a read-only `EROFS` or `ext4` filesystem image carrying an appended `dm-verity` Merkle tree, `AvbFooter`, and RSA-signed `AvbVBMetaImageHeader` at its tail) [81, 142, 155].

Factory baseline versions of over thirty Mainline modules (`com.android.art` runtime/JIT, `com.android.conscrypt` BoringSSL/TLS, `com.android.resolv` DNS-over-TLS/HTTP3, `com.android.media` and `com.android.media.swcodec` sandboxed codecs, `com.android.wifi`, `com.android.btservices`, `com.android.uwb`, `com.android.permission` `PermissionController`, `com.android.adservices`, `com.android.rkpd` Remote Key Provisioning, and `com.android.virt` `pKVM`/`crosvm`/`pvmfw`) ship pre-installed inside `/system/apex` (or `/system_ext/apex` / `/vendor/apex`), protected by `/system`'s own `dm-verity` tree [81, 83].

Trace what happens when Google delivers an out-of-band security update via Google Play system updates [81, 152, 154, 156]. During download staging, `PackageManager` hands the `.apex` session to the native `apexd` daemon (`system/apex/apexd/apexd.cpp`), which enforces *dual-layer asymmetric verification*: first, the outer ZIP's `APK Signature Scheme v3` certificate must match the exact signing lineage of the pre-installed `/system/apex` factory module; second, `apexd` invokes `libavb` to verify `apex_payload.img`'s internal `AvbVBMetaImageHeader` against `apex_pubkey`, confirming `apex_pubkey` matches the factory module's embedded `apex_pubkey` and `manifest.version >= active_version` [81, 154]. Validated packages are hardlinked into `/data/apex/active/<name>@<version>.apex` for activation on next reboot.

On the next boot, early in `init` *before* `Zygote` or `system_server` starts, `apexd --bootstrap` and `apexd` scan `/data/apex/active`, re-verify each `.apex`'s `VBMeta` header, attach the $4\text{ KiB}$-aligned `apex_payload.img` slice inside the uncompressed ZIP directly to a `/dev/block/loopN` device via `LOOP_CONFIGURE` (with `LO_FLAGS_DIRECT_IO` avoiding double page-cache buffering), instantiate a live kernel `dm-verity` block target (`/dev/block/dm-N`) seeded with `AvbHashtreeDescriptor`'s verified root digest, and bind-mount it read-only at `/apex/<module_name>@<version>` and `/apex/<module_name>` [81, 154]. When `com.android.art` updates, `odrefresh` and `odsign` (`system/security/ondevice-signing` [152], or `CompOS` in [Chapter 5](05-pkvm-avf-microdroid.md)) recompile boot-classpath `.oat`/`.art` files, seal each output file on `/data` with `FS_IOC_ENABLE_VERITY`, and sign their `fs-verity` digests under a `KeyMint` early-boot key (`Tag::MAX_BOOT_LEVEL` in [Chapter 4](04-keymint-weaver-throttling.md) [157]). Should a buggy Mainline push cause repeated `system_server` or native crashes after boot, `PackageWatchdog` and `RollbackManager` automatically trigger tiered Mainline crash recovery, reverting `/data/apex/active` cleanly back to the prior healthy revision [156].

## Vendor, OEM, & Custom-OS Boundaries

Although `dm-verity`, `fs-verity`, and `apexd` reside in open-source AOSP and `GKI`, three architectural boundaries differentiate certified `GMS` handsets, budget OEM boards, and custom operating systems [9, 20, 81, 146].

First, `Project Mainline` over-the-air module delivery relies on Google's private `APEX` signing keys trusted inside `/system/apex` on `GMS`-licensed (`GREEN`) devices [81, 83]. Privacy-hardened AOSP distributions such as `GrapheneOS` (`YELLOW`) deliberately replace Google's `APEX` public keys in `/system/apex` with `GrapheneOS` build keys, compile every Mainline module (`ART`, `BoringSSL`/`Conscrypt`, `Virtualization`, `Wi-Fi`, `Bluetooth`) directly from audited source code, and ship updates exclusively inside atomic, full-OS `A/B` signed images rather than accepting out-of-band binary `.apex` pushes over Play, thereby preserving single-party build reproducibility across 100 percent of `/system` and `/apex` [20].

Second, `RPMB` anti-rollback coverage exhibits a hardware seam between `ABL` and pre-`ABL` silicon loaders [124, 127, 140]. Because `UFS` and `TEE` `RPMB` drivers are not running when mask `Boot ROM` (`PBL` / `BL0`) executes in SRAM, pre-`ABL` firmware (`XBL`, `BL1`/`BL2`, `tz.mbn`) relies on physical SoC OTP anti-rollback eFuse rows (`QFPROM` `ANTI_ROLLBACK` bitmasks) [124, 125]. Because a physical SoC die provides only a finite number of fuse bits (typically 32 to 64 lifetime increments), OEMs increment `RPMB` `AVB` `rollback_index` slots on every monthly Security Bulletin while blowing physical `QFPROM` fuse bits only after high-severity `XBL` or `TrustZone` vulnerabilities, leaving narrow multi-month windows where a recent prior month's signed `tz.mbn` or `XBL` could be flashed if an attacker already gained physical `EDL` or boot-LUN write access [31, 105, 127].

Third, performance-conscious OEMs previously experimented with `AVB_HASHTREE_DESCRIPTOR_FLAGS_CHECK_AT_MOST_ONCE` (`dm-verity` `check_at_most_once` option [23, 130]), which skips re-hashing a `dm-verity` block if a bitset remembers it was verified earlier during boot. Because a transient physical flash interposer (or rowhammer/DMA fault) could return clean bytes on first read and malicious bytes after page-cache eviction, security-hardened Android configurations favor standard every-page-in verification atop compressed `EROFS` + hardware `ARMv8` `SHA-256` instructions, where throughput exceeds $2\text{ to }3\text{ GB/s}$ at negligible CPU cost [23, 142].

## Exploit Chains & Structural Limits

Attacks against Android's anti-rollback, runtime block-verification, and `APEX` layer target weak OEM `verity` error modes, unprovisioned factory `RPMB` keys, pre-fuse firmware downgrades, or session-staging logic inside `apexd` and `fs-verity`.

### Why Verified Read-Only Partitions Killed Persistent Mobile Rootkits

Step back and appreciate the systems milestone achieved jointly by `AVB 2.0`, `RPMB` rollback floors, `dm-verity` with `RS(255, 253)` `FEC`, `fs-verity`, and `APEX` Mainline: on a locked `GREEN` or `YELLOW` Android handset, *persistent file-based rootkits on `/system`, `/vendor`, `/product`, `boot`, and `/apex` are functionally extinct* [2, 40, 41]. Even when a commercial surveillance chain ([Chapter 20](20-multivendor-spyware-chains.md)) achieves complete `EL1` kernel read/write control, altering a single byte of `/system` or `/data/apex/active/*.apex` on `UFS` flash will exceed Reed-Solomon parity distance and trip `VERITY_MODE_RESTART` on page-in or reboot.

> **Key idea.**
> Verified Boot and `dm-verity` force even nation-state Android implants to remain *ephemeral in-RAM residents* or hide inside unverified app databases on `/data` hoping to re-trigger a userspace vulnerability after boot, turning a simple daily or timed reboot (`GrapheneOS` auto-reboot / Android 16 inactivity reboot in [Chapter 12](12-fbe-usb-theft-protection.md)) into a genuine eviction primitive against `Ring 0` kernel compromise [40, 116].

Yet immutable code partitions cannot protect *mutable secrets*: user `File-Based Encryption` keys, FIDO2 passkey private scalars, biometric authentication tokens, and PIN retry counters cannot be compiled into public `EROFS` images, nor can the `EL1` Linux kernel hold them safely in normal LPDDR DRAM where any GPU or USB driver exploit can read `physmap`. Isolating mutable secrets from `EL1` and from physical lab probes requires dedicated security hardware, bringing us to `Arm TrustZone` TEEs and discrete `StrongBox` processors in [Chapter 3](03-trustzone-strongbox.md).

## Inspecting via ADB, Fastboot, & Attestation

Verify active `dm-verity` enforcement mode (`enforcing` maps to `DM_VERITY_MODE_RESTART`), A/B slot suffix (`_a` or `_b`), and `IBootControl` `successful` status on a booted device:

```bash
adb shell getprop ro.boot.veritymode
adb shell getprop ro.boot.slot_suffix
adb shell getprop ro.boot.vbmeta.avb_version
adb shell mount | grep -E ' / | /vendor | /apex/' | head -n 6
```

Enumerate active `Project Mainline` `APEX` modules, comparing factory `/system/apex` baselines against Play-updated `/data/apex/active` loopback `dm-verity` mounts (`35xxxxxxx` / `36xxxxxxx` version codes):

```bash
adb shell cmd package list packages --apex-only --show-versioncode | head -n 8
adb shell ls -lh /data/apex/active
adb shell ls -d /apex/*@* | head -n 8
```

Inspect `AvbHashtreeDescriptor` Merkle parameters (`SHA256`, `4096` byte blocks, salt, root digest) and Reed-Solomon `FEC` configuration (`FEC num roots: 2`) inside a local `system.img` or extracted `apex_payload.img`:

```bash
avbtool info_image --image system.img
avbtool print_partition_digests --image vbmeta_system.img
```

Confirm `fs-verity` protection on `odsign`-verified `ART` boot-classpath artifacts and Incremental/verified `APK` installations via `dumpsys` and `odsign` properties:

```bash
adb shell getprop odsign.key.done
adb shell getprop odsign.verification.success
adb shell dumpsys package com.android.chrome | grep -iE 'versionCode|verity|SigningDetails' | head -n 6
```
