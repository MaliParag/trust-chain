# UI-Layer Bypasses, Banking Trojans, and Advanced Protection Lockdown

## Overview

* **Link in the Chain:** Human-interface capability mediation and high-risk system-lockdown layer; governs cross-app UI observation and input-synthesis APIs (`AccessibilityService`, `NotificationListenerService`, `SYSTEM_ALERT_WINDOW`) and unifies OS-wide exploit and scam mitigations under `Advanced Protection Mode`.
* **Core Security Invariant:** Assistive UI-automation grants are denied to untrusted packages by `Enhanced Confirmation Mode` (`ECM` factory installer allowlists and immutable `PACKAGE_SOURCE_DOWNLOADED_FILE` provenance), transient one-time passwords (`OTP`s) are quarantined from `READ_SMS`, untrusted notification listeners, and screen shares for up to three hours, and enabling `Advanced Protection Mode` atomically locks sideloading, non-verified `AccessibilityService` grants, `Arm MTE`, 2G cellular, lock-screen USB data, and Chrome `JIT`/`WebGPU`.
* **Ecosystem Enforcement Tier:** `InputDispatcher` tapjacking filters, `ECM` Restricted Settings, and `OTP` notification redaction enforce across `GREEN` and `YELLOW` locked states (`AOSP` Android 13-17); `Advanced Protection Mode` (`AdvancedProtectionManager` in Android 16 and Android 17) coordinates OS, Play Protect, and Chrome policies on `GREEN` certified handsets while `GrapheneOS` (`YELLOW`) enforces equivalent or stricter exploit defaults natively without cloud dependencies.
* **Trusted Computing Base (TCB):** `AccessibilityManagerService` and `AccessibilitySecurityPolicy` (`frameworks/base/services/accessibility/`), `InputDispatcher` (`frameworks/native/services/inputflinger/`), `EnhancedConfirmationService` (`packages/modules/Permission/EnhancedConfirmation/`), `InstallPackageHelper`, `NotificationManagerService` (`NAS` OTP classifier), and `AdvancedProtectionService` (`frameworks/base/services/core/java/com/android/server/security/advancedprotection/`).
* **Seam & Handoff:** Closes the social-engineering loophole through which financial trojans hijacked authenticated banking sessions above an intact kernel and `KeyMint` sandbox, while leaving physical data-at-rest cryptography, lock-screen USB kernel zero-days, and street-snatch theft defenses to [Chapter 12](12-fbe-usb-theft-protection.md).

## Threat Model & Ecosystem Constraint

Every modern operating system confronts an architectural collision between *per-application isolation* and *universal assistive accessibility*. On Android, discretionary Linux `UID` separation ([Chapter 9](09-uid-zygote-binder.md)), mandatory `SELinux` `u0_a*` type enforcement ([Chapter 6](06-selinux-seccomp.md)), `Scoped Storage` ([Chapter 10](10-apk-signing-scoped-storage.md)), and `KeyMint` hardware-backed key isolation ([Chapter 4](04-keymint-weaver-throttling.md)) ensure that a malicious utility executing as `u0_a241` cannot `ptrace`, `openat`, or `ioctl` its way into a banking application's memory or `/data/user/0/com.bank/` directory. Yet a blind user navigating via a refreshable braille display (`TalkBack`) or a user with motor impairments operating a head-tracking switch (`Switch Access`) requires an assistive agent that can read the text and coordinates of *every* visible UI control across *every* foreground window and synthesize taps, text entry, and scroll gestures on the human's behalf [333, 334].

By 2017, organized financial crime syndicates recognized a devastating economic asymmetry in that assistive bridge: `android.accessibilityservice.AccessibilityService` is an *omniscient cross-UID capability* sitting directly above the entire kernel and hardware security stack [36, 37, 333]. Purchasing a zero-click `Chrome` renderer plus `Mali` or `Adreno` GPU kernel chain from a commercial exploit broker costs millions of dollars and burns on contact with Monthly Security Updates. Renting an Android Crimeware-as-a-Service (`CaaS`) banking trojan (*Cerberus*, *FluBot*, *SharkBot*, *Xenomorph*, *Anatsa*/*TeaBot*, *Hook*, *PixPirate*, or *Crocodilus*) costs USD 1,000 to USD 5,000 per month and requires zero memory corruption [36, 335, 336, 337]. Instead of attacking `SELinux` or `KeyMint`, the trojan social-engineers the human owner into sideloading a decoy courier, PDF reader, or browser update APK and granting `BIND_ACCESSIBILITY_SERVICE` [36, 338].

Once an unverified package acquires `BIND_ACCESSIBILITY_SERVICE` alongside `SYSTEM_ALERT_WINDOW` or `BIND_NOTIFICATION_LISTENER_SERVICE`, three UI-layer primitives collapse application isolation without violating a single kernel invariant [37, 333, 334, 339]:

First is *visual deception and tapjacking (`SYSTEM_ALERT_WINDOW`)*. In the foundational *Cloak and Dagger* attack demonstrated by Fratantonio et al. at IEEE S&P 2017 [37] and extended to zero-permission `TYPE_TOAST` windows in `CVE-2017-0752` [340], an attacker-controlled window floats above Android's own `Settings` or `PermissionController` dialogs. By marking the overlay `FLAG_NOT_TOUCHABLE` while rendering an innocuous prompt ("Tap Continue to claim parcel"), the trojan tricks the user into physically tapping the exact screen coordinates of the underlying `"Allow"` button that grants `AccessibilityService` [37, 341].

Second is *semantic view-hierarchy scraping and automated wire execution (`AccessibilityNodeInfo` + `ATS`)*. Developers often assume that setting `WindowManager.LayoutParams.FLAG_SECURE` on a banking transfer screen or cryptocurrency seed-phrase view blocks screen capture. While `FLAG_SECURE` prevents `SurfaceFlinger` from copying pixel buffers into normal screenshots or untrusted `MediaProjection` streams, an enabled `AccessibilityService` declaring `android:canRetrieveWindowContent="true"` does not need pixels: `AccessibilityManagerService` serializes the live `View` hierarchy into `AccessibilityNodeInfo` parcelables containing exact `getText()`, `getViewIdResourceName()`, and screen bounding boxes unless views explicitly restrict assistive sensitivity [333, 334, 339]! Worse, the trojan's *Automatic Transfer System* (`ATS`) waits silently until the genuine owner opens their banking app and completes `BiometricPrompt` + `KeyMint` authentication, then projects a full-screen black `"System Updating - Do Not Touch"` overlay, mutes audio streams, populates a mule account IBAN via `ACTION_SET_TEXT`, and executes `performAction(ACTION_CLICK)` or `dispatchGesture()` bezier strokes to authorize an irreversible instant payment (`Pix` or `SEPA`) *from inside the genuine, attested banking session on a `GREEN` locked phone* [36, 335, 337, 339]. In March-June 2025 campaigns analyzed by ThreatFabric, *Crocodilus* combined black-screen `AccessibilityService` logging with contact-list injection (writing fake `"Bank Support"` entries into the victim's address book to spoof caller ID during follow-up vishing calls) and fake wallet backup overlays that harvested 12-word cryptocurrency seed phrases directly via accessibility text events [337].

Third is *out-of-band OTP and call-redirection hijacking (`NotificationListenerService`, `READ_SMS`, and MMI codes)*. Whenever a bank or messaging service sends a transaction-confirmation one-time password (`OTP`) via SMS or push notification, trojans holding `BIND_NOTIFICATION_LISTENER_SERVICE` or `READ_SMS` intercept the `StatusBarNotification` payload in milliseconds and call `cancelNotification()` before the victim's screen even lights up, or trick victims into dialing Man-Machine Interface (`MMI`) unconditional call-forwarding strings (`*21*<attacker_number>#`) to hijack voice 2FA callbacks [36, 342, 343, 344].

At the opposite end of the adversary spectrum, investigative journalists, election officials, and human-rights defenders face commercial zero-click spyware exploiting `V8` JavaScript JIT compilers, `WebGPU` shader pipelines, 2G false base stations ("SMS blasters" and IMSI catchers), and physical USB ports [39, 345, 346]. Prior to Android 16, neutralizing both social-engineered UI trojans and commercial exploit chains required toggling more than a dozen fragmented controls scattered across `Settings`, `Google Play Protect`, and `chrome://flags`, where overlooking a single toggle left the device exposed [39, 345].

## Architecture & AOSP Implementation

### `InputDispatcher` Touch-Obscured Gates and Overlay Eviction

Android dismantled classic tapjacking inside the native input pipeline (`frameworks/native/services/inputflinger/dispatcher/InputDispatcher.cpp`) and `WindowManagerService` across Android 10 through Android 12 [341, 347]. Earlier Android releases merely annotated obscured `MotionEvent` deliveries with `FLAG_WINDOW_IS_OBSCURED` (when another window sat directly over the touch coordinate) without setting `FLAG_WINDOW_IS_OBSCURED` for adjacent split/cutout windows (`FLAG_WINDOW_IS_PARTIALLY_OBSCURED`), leaving individual app developers to remember `android:filterTouchesWhenObscured="true"` [341, 347].

Android 12 (`API 31`) replaced opt-in app filtering with two system-wide enforcement invariants inside `InputDispatcher::findTouchedWindowTargetsLocked()` [341, 347]. First, for *pass-through overlays* (windows carrying `FLAG_NOT_TOUCHABLE` from a different `UID` than the target window), `InputDispatcher` computes the combined obscuring opacity $\alpha_{\text{total}} = 1 - \prod_i (1 - \alpha_i)$ across all intervening untrusted windows (`TYPE_APPLICATION_OVERLAY`) stacked above the target surface. Whenever $\alpha_{\text{total}}$ exceeds `MaximumObscuringOpacityForTouch` (configured at $0.80$ by default in `InputManagerService`), `InputDispatcher` *drops the touch event inside native code* before it ever reaches the target application, neutralizing opaque click-routing lures while allowing subtle, low-opacity screen-tint utilities to function only below the visibility threshold [341, 347].

Second, for *zero-tolerance security surfaces*, Android 12 introduced `Window.setHideOverlayWindows(true)` (gated by `HIDE_NON_SYSTEM_OVERLAY_WINDOWS` for system packages and available to any third-party banking or wallet `Activity` via `<uses-permission android:name="android.permission.HIDE_OVERLAY_WINDOWS"/>`) [333, 341]. While any window carrying `PRIVATE_FLAG_HIDE_NON_SYSTEM_OVERLAY_WINDOWS` is visible on screen (including `PermissionController` runtime grants, `PackageInstaller` confirmation sheets, `BiometricPrompt`, VPN consent, and `Settings` Accessibility enablement screens), `WindowManagerService` temporarily strips all non-system `TYPE_APPLICATION_OVERLAY` surfaces from the compositor stack [333, 341, 347]. Consequently, an unprivileged app holding `SYSTEM_ALERT_WINDOW` can no longer paint fake UI over an Accessibility or installation prompt.

### Session-Installing Droppers vs. `EnhancedConfirmationService` (`ECM`)

Blocking overlay tapjacking forced crimeware groups to pivot to pure voice and SMS social engineering ("Tap Settings, tap Accessibility, tap Downloaded Apps, and switch Package Tracker ON"). Android 13 (`API 33`) countered with *Restricted Settings*, the first generation of `Enhanced Confirmation Mode` (`ECM`) [338, 348]. When a user attempted to enable `AccessibilityService` or `NotificationListenerService` for a sideloaded APK, `AppOpsManager` checked `OPSTR_ACCESS_RESTRICTED_SETTINGS`; if denied (`MODE_ERRORED`), `Settings` disabled the switch and displayed `"Restricted setting: For your security, this setting is currently unavailable"` [348, 349].

Look closely at *how* Android 13 decided whether an APK was "sideloaded" versus "store-installed", because that exact distinction triggered an immediate underground arms race documented by ThreatFabric and Cleafy [335, 336, 338, 350]. Android exposes two APK installation paths: legacy single-file intent installation (`Intent.ACTION_VIEW` / `ACTION_INSTALL_PACKAGE` invoked by browsers, chat apps, and file managers) and the multi-part *Session-Based PackageInstaller API* (`PackageInstaller.createSession(SessionParams)` $\to$ `Session.openWrite()` $\to$ `Session.commit()`), originally designed so marketplaces such as Google Play or OEM stores could stream split APKs [338, 351]. Android 13 applied Restricted Settings *only* to APKs installed via the non-session URI flow, implicitly trusting any package committed via `PackageInstaller.Session`!

Within weeks of Android 13's release in August 2022, ThreatFabric caught the Hadoken Group (*Xenomorph* operators) developing *BugDrop*, embedding `SESSION_API_PACKAGE_INSTALLED` session-commit routines to drop *Xenomorph* without triggering Restricted Settings [350]. By late 2023, turnkey *Dropper-as-a-Service* (`DaaS`) builders led by *SecuriDropper* and *Zombinder* commercialized the bypass across underground markets [338]. A victim downloaded a clean Stage-1 decoy APK that requested *zero* restricted permissions (only `REQUEST_INSTALL_PACKAGES`), clicked an in-app `"Reinstall Update"` button, and let Stage 1 open a `PackageInstaller.Session` to stream the decrypted Stage-2 banking trojan (*SpyNote*, *Ermac*, *SharkBot*, *Anatsa*/*TeaBot*, or *Hook*) from encrypted assets [336, 338]. Because Stage 2 arrived via `createSession()`, Android 13 classified Stage 2 as store-installed and left its `AccessibilityService` toggle wide open! Cleafy simultaneously uncovered *PixPirate* pairing session/split installation with a manifest lacking `<category android:name="android.intent.category.LAUNCHER"/>`, creating a launcherless Stage-2 banking implant invisible in the user's home-screen drawer [335].

![Figure: Session-based dropper evasion of Android 13 Restricted Settings via PackageInstaller.createSession versus Android 15-17 EnhancedConfirmationService factory allowlists, immutable source pinning, and Advanced Protection lockdown.](diagrams/11-extra-session-dropper-ecm-bypass.svg)

Android 14 (`API 34`), Android 15 (`API 35`), and Android 16/17 systematically closed the session-dropper loophole inside `EnhancedConfirmationService` (`packages/modules/Permission/EnhancedConfirmation/` [349]) and `InstallPackageHelper.java` (`frameworks/base/services/core/java/com/android/server/pm/InstallPackageHelper.java` [351]):

First, Android 14 tightened `PackageInstaller.SessionParams.setInstallerPackageName()` ownership checks so an unprivileged dropper can no longer spoof another store's installer identity, and introduced explicit origin attribution via `SessionParams.setPackageSource()` (`PACKAGE_SOURCE_DOWNLOADED_FILE` and `PACKAGE_SOURCE_LOCAL_FILE`), requiring browsers and file managers using session APIs to taint downloaded APKs as untrusted [348, 351].

Second, Android 15 replaced API-shape heuristics altogether with `EnhancedConfirmationManager` (`SystemApi` inside the updatable `com.android.permission` Mainline `APEX`) backed by an immutable factory XML allowlist under `/system/etc/sysconfig/` (`<enhanced-confirmation-trusted-packages>` and `<enhanced-confirmation-trusted-installers>`) [349]. Under `EnhancedConfirmationService.isRestricted()`, *every* newly installed package defaults to `ECM`-restricted regardless of whether its installer called `createSession()` unless *both* conditions hold: the installing package's `packageName` and `SHA-256` signing certificate appear in the factory `/system/etc/sysconfig` trusted-installer list (such as Google Play or a certified OEM store) *and* the session's `packageSource` is neither `PACKAGE_SOURCE_DOWNLOADED_FILE` nor `PACKAGE_SOURCE_LOCAL_FILE` [349, 351]! When a Stage-1 *SecuriDropper* or *Anatsa* loader calls `PackageInstaller.createSession()`, `EnhancedConfirmationService` sees an un-allowlisted installer UID and locks Stage 2 under `ECM` immediately [349]. Even subtle state-transition bugs are policed as privilege-escalation vulnerabilities: in November 2026, Google patched `CVE-2026-58836` (`ASB-A-349318333`) in `InstallPackageHelper.handlePackagePostInstall()`, where a sideloaded package could launder its recorded `packageSource` during a self-update session to shed `ECM` restrictions [352].

### Sensitive View Isolation, `MediaProjection` Blanking, and the 3-Hour `OTP` Quarantine

Even if a social-engineered victim manually overrides `ECM` (on a device outside `Advanced Protection Mode`) or is coached onto a live screen-sharing session, Android 14 through Android 17 sever access to high-value UI views and transient authentication codes across five distinct subsystem gates [333, 334, 339, 342, 343, 344, 353]:

| UI / Notification Capability | AOSP Mediation Service | Malware Abuse Primitive | Android 14-17 Structural Gate |
|---|---|---|---|
| `SYSTEM_ALERT_WINDOW` | `WindowManagerService` + `InputDispatcher` | Full-screen fake bank overlays & pass-through tapjacking | $\alpha > 0.80$ pass-through touch drop + `HIDE_OVERLAY_WINDOWS` eviction [341, 347] |
| `BIND_ACCESSIBILITY_SERVICE` | `AccessibilityManagerService` + `AccessibilitySecurityPolicy` | `AccessibilityNodeInfo` scraping + `ACTION_CLICK` / `dispatchGesture()` `ATS` | `ECM` `/system/etc/sysconfig` gate + `ACCESSIBILITY_DATA_SENSITIVE_YES` + Android 17 `AAPM` hard-block [334, 339, 346, 349] |
| `BIND_NOTIFICATION_LISTENER_SERVICE` | `NotificationManagerService` + `NAS` | Silent read & dismissal of 2FA push/SMS `OTP` banners | `RECEIVE_SENSITIVE_NOTIFICATIONS` role lock + `NAS` `OTP` stripping [342, 343] |
| `READ_SMS` / `RECEIVE_SMS` | `SmsBroadcastUndelivered` / Telephony | Background exfiltration of bank SMS `OTP` codes | `ECM` restriction + Android 16/17 automatic 3-hour `OTP` SMS quarantine [353] |
| `MediaProjection` + Telephony | `MediaProjectionManagerService` + `Telecom` | Remote tech-support screen share + `*21*` call-forwarding `OTP` theft | Automatic native/Chrome/`WebView` password & `OTP` blanking + MMI/Verified Bank Call blocks [344, 353] |

Inside `frameworks/base/core/java/android/view/accessibility/AccessibilityNodeInfo.java` and `AccessibilitySecurityPolicy.java`, Android 14 (`API 34`) added the per-view `accessibilityDataSensitive` property (`View.setAccessibilityDataSensitive(View.ACCESSIBILITY_DATA_SENSITIVE_YES)`) [333, 334, 339]. When a banking app marks account balances, transfer recipient fields, PIN pads, or seed-phrase views `ACCESSIBILITY_DATA_SENSITIVE_YES`, `AccessibilitySecurityPolicy.canRetrieveWindowContent()` filters out those nodes, blocks `performAction()`, and suppresses `AccessibilityEvent` text emissions to *every* bound `AccessibilityService` *except* verified assistive tools declaring `android:isAccessibilityTool="true"` in their `<accessibility-service>` XML metadata (subject to strict Google Play Console assistive-review audits [354]) [333, 334, 339].

In parallel, Android 15 (`API 35`) through Android 17 closed notification and SMS `OTP` theft [342, 343, 353]. Inside `NotificationManagerService` (`frameworks/base/services/core/java/com/android/server/notification/NotificationManagerService.java`), the system `NotificationAssistantService` (`NAS`, running inside isolated system intelligence sandboxes) inspects incoming notifications using regular expressions and on-device ML classifiers to detect one-time security codes (`OTP`s) [342, 343]. Flagged notifications have their public and untrusted listener payloads redacted unless the consumer holds the signature/privileged `RECEIVE_SENSITIVE_NOTIFICATIONS` permission (reserved for system UI and verified `CompanionDeviceManager` watch/wearable bridges) [342, 343]. In 2026, Android extended `OTP` protection directly to the SMS/telephony layer: Android now *automatically quarantines and hides incoming SMS/notification `OTP` codes for three hours from virtually all third-party apps* (even apps previously granted SMS read access under untrusted conditions), outlasting the `5`-to-`15`-minute validity window of every banking 2FA code [353]!

To defeat live voice-guided scams ("bank security department" impersonators coaching victims to share screens via remote-support tools), Android 15-17 added three real-time circuit breakers [344, 353]. First, during active `MediaProjection` screen sharing, the compositor blanks notification pop-ups, lock-screen `LSKF` entry, and (as rolled out in October 2026) login password and payment card fields inside Chrome and `Android WebView` [342, 344]. Second, Android blocks background apps from silently enabling call forwarding and displays a full-screen fraud warning if a user manually dials an `MMI` forwarding code (`*21*`) [344]. Third, *Verified Financial Calls* (launched in 2026 with Revolut, Banco do Brasil, Itaú Unibanco, and Nubank) queries the user's signed-in banking app in real time when an incoming caller ID matches a bank line, automatically hanging up spoofed VoIP calls when the bank app attests that no outbound call is active [344, 353].

### Android 16 and Android 17 `Advanced Protection Mode` (`AAPM`)

Introduced in Android 16 (`API 36`) and substantially expanded in Android 17 (`API 37`), Android `Advanced Protection Mode` (`AAPM`) unifies high-assurance exploit prevention, scam blocking, network hardening, and forensic readiness behind a single hardware-authenticated OS switch (`Settings` $\to$ `Security & privacy` $\to$ `Advanced Protection`) [39, 345, 346, 355]. Managed in AOSP by `AdvancedProtectionService` (`frameworks/base/services/core/java/com/android/server/security/advancedprotection/`), `AAPM` enforces an atomic, non-downgradable policy bundle across six subsystems so neither social engineering nor user fatigue can selectively weaken individual defenses while the mode is active [345, 346, 355]:

![Figure: Android 16/17 Advanced Protection Mode single-toggle enforcement across app installation, memory safety, browser JIT/WebGPU, radio, USB, and third-party apps.](diagrams/11-advanced-protection-lockdown.svg)

First, across *package installation and `AccessibilityService` mediation*, `AAPM` sets a global user restriction (`DISALLOW_INSTALL_UNKNOWN_SOURCES_GLOBALLY`) blocking APK sideloading across *all* browsers, chat apps, and file managers (even those previously granted `REQUEST_INSTALL_PACKAGES`), locks `Google Play Protect` + `Live Threat Detection` permanently ON, enables Chrome Safe Browsing pre-download APK malware evaluation, and blocks high-risk actions during active calls from unknown numbers [39, 345, 353]. Crucially, *Android 17 `AAPM` introduces strict `Accessibility Protection`*: enabling `Advanced Protection` automatically blocks `BIND_ACCESSIBILITY_SERVICE` grants to *every* application not explicitly verified and categorized as an `Accessibility Tool`, shutting down the entire UI-automation trojan class even for store-distributed decoys while keeping `TalkBack` and certified assistive tools working seamlessly [346, 353]!

Second, across *memory safety and browser zero-click surfaces*, `AAPM` activates hardware `Arm MTE` ([Chapter 8](08-arm-mte-scudo.md)) across all compatible system and third-party binaries, enforces Chrome `HTTPS-First` warnings before any cleartext `http://` socket opens, disables Chrome's `V8` JavaScript `JIT` optimizer (`JITless` execution removing dynamic `RWX`/`RX` codegen gadgets), and *in Android 17 disables Chrome `WebGPU` hardware shader compilation*, eliminating two of the highest-yield remote browser exploit surfaces abused by commercial spyware vendors [39, 346, 353].

Third, across *cellular and local radio surfaces*, `AAPM` disables legacy 2G GSM/EDGE connectivity via `IRadio` HAL 1.6+ (`setAllowedNetworkTypesBitmap`, complemented in Android 17 by carrier default-off 2G profiles and Local Network Protection [356]) so portable USD 3,000 false base stations ("SMS blasters" and IMSI catchers) cannot force LTE/5G handsets down to unauthenticated 2G channels to inject spoofed bank SMS links or exploit legacy baseband parsers, and blocks automatic connections to insecure `WEP` or open Wi-Fi networks [39, 345, 353, 356].

Fourth, across *physical port, lock-screen, and forensic surfaces*, `AAPM` enables *USB Protection* (forcing any new physical USB connection while locked into charge-only mode, [Chapter 12](12-fbe-usb-theft-protection.md)), activates `Theft Detection Lock`, `Offline Device Lock`, `Failed Authentication Lock`, and a `72-hour` inactivity reboot back to `BFU`, disables device-to-device (`Watch Unlock`) proximity unlocking in Android 17, and offers opt-in End-to-End Encrypted Cloud `Intrusion Logging` ([Chapter 14](14-play-protect-intrusion-logging.md)) [346, 353].

Fifth, through the *third-party application posture API* (`android.security.advancedprotection.AdvancedProtectionManager`), any app declaring the normal permission `QUERY_ADVANCED_PROTECTION_MODE` can query `isAdvancedProtectionEnabled()` and register a real-time `AdvancedProtectionManager.Callback` [345]:

```kotlin
// Query OS-wide Advanced Protection posture (Android 16+ API 36/37)
val aapm = context.getSystemService(AdvancedProtectionManager::class.java)
if (aapm?.isAdvancedProtectionEnabled == true) {
    enableStrictCallRelayDisableLinkPreviewsAndRequirePasskeys()
}
```

Android 17 complements this API with a `"View Supporting Apps"` transparency screen in `Settings` showing users which installed messengers (*Signal*, *WhatsApp*) and financial apps actively harden their internal attack surface under `AAPM`, plus full `Android Enterprise` `DevicePolicyManager` policy support so organizations can mandate `AAPM` across managed fleets [346, 353].

## Vendor, OEM, & Custom-OS Boundaries

While `InputDispatcher` touch filtering, `EnhancedConfirmationService`, and `ACCESSIBILITY_DATA_SENSITIVE_YES` ship in core AOSP (`GREEN` and `YELLOW` locked devices), ecosystem behavior diverges across OEM skins and custom operating systems [6, 345, 349]. On certified `GREEN` Pixel and Android 16/17 partner devices, `AAPM` integrates OS services directly with Google Play's `isAccessibilityTool` verification metadata, Chrome `JIT`/`WebGPU` policies, and Private AI Compute scam classifiers [344, 346, 353]. Samsung complements AOSP controls on One UI Galaxy devices with `Samsung Auto Blocker` (*Maximum Restrictions*), which independently blocks unknown-source sideloading, blocks USB cable commands at the port controller, sandboxes MMS/chat image decoding inside *Samsung Message Guard*, strips photo GPS metadata on share, and disables 2G networks [345]. Historically, several third-party OEM skins inadvertently weakened user conditioning around `AccessibilityService` by encouraging mainstream battery-saver or "one-tap booster" utilities to request `AccessibilityService` simply to force-stop apps in `Settings`, training users to click through Accessibility warnings; Google Play policy and Android 14-17 `isAccessibilityTool` enforcement explicitly prohibit non-assistive automation from holding `BIND_ACCESSIBILITY_SERVICE` [346, 354].

On `GrapheneOS` (`YELLOW` locked Pixel), equivalent or tighter hardware and runtime mitigations are enforced *by default for all users* without requiring a Google Account or cloud telemetry: `GrapheneOS` ships `Vanadium` (`Chromium` + `WebView`) with JavaScript `JIT` disabled by default and `WebGPU` restricted, enables synchronous hardware `Arm MTE` on supported Pixels, enforces hardware-level USB-C port data cutoffs when locked, disables 2G at the baseband HAL on toggle, and provides granular per-app `exploit protection compatibility` overrides alongside configurable `10-minute` to `72-hour` auto-reboot timers [39, 345].

### The Assistive Capability Boundary and Typed Cross-App Delegation

Even after closing tapjacking, session-dropper `ECM` loopholes, and `OTP` notification leaks, assistive computing preserves one irreducible structural tension: *a genuine assistive tool carrying verified `isAccessibilityTool="true"` metadata must still inspect UI trees and inject actions so blind and motor-impaired users retain equal sovereignty over their devices* [333, 334, 354]. Rather than crippling assistive technology, Android 16 and Android 17 eliminate every illegitimate *reason* for mainstream apps or AI assistants to request `AccessibilityService`: `Advanced Protection Mode` hard-blocks non-verified `AccessibilityService` grants outright [346], while `AppFunctions` (`android.app.appfunctions`, [Chapter 18](18-on-device-agentic-ai.md)) provides typed, permission-mediated cross-app capability execution without raw screen scraping [6].

> **Key idea.**
> Application sandboxing in `EL0`/`EL1` cannot save a banking app that renders plaintext secrets into unmarked UI nodes or relies on SMS `OTP`s without `ACCESSIBILITY_DATA_SENSITIVE_YES` and `HIDE_OVERLAY_WINDOWS` [339, 341]. Financial and wallet developers must pair `setHideOverlayWindows(true)` and `ACCESSIBILITY_DATA_SENSITIVE_YES` on sensitive screens with `AdvancedProtectionManager` posture checks so UI-layer trojans hit an opaque wall even if sideloaded on unhardened devices [339, 345].

Securing interactive UI mediation defends the handset while it rests in the legitimate user's hands. What happens, however, when the phone is snatched mid-unlock on a crowded street by a thief who just filmed the owner's 6-digit PIN, or seized while locked in police custody and wired into a Cellebrite physical USB kernel zero-day rig? [Chapter 12](12-fbe-usb-theft-protection.md) examines `File-Based Encryption`, `UFS` Inline Crypto Engines, physical USB driver exploitation, `Theft Detection Lock`, and `Identity Check`.

## Inspecting via ADB, Fastboot, & Attestation

Enumerate all currently active `AccessibilityService` and `NotificationListenerService` components bound to the user session (any unrecognized package in either setting is a primary banking-trojan or stalkerware indicator):

```bash
adb shell settings get secure enabled_accessibility_services
adb shell settings get secure enabled_notification_listeners
```

Query `AdvancedProtectionService` lockdown state and inspect `Enhanced Confirmation Mode` (`ACCESS_RESTRICTED_SETTINGS`) enforcement on an installed third-party UID:

```bash
adb shell dumpsys advanced_protection 2>/dev/null | head -n 14
adb shell appops get --uid 10250 ACCESS_RESTRICTED_SETTINGS 2>/dev/null
```

Inspect a package's recorded installer attribution and `packageSource` (`PACKAGE_SOURCE_DOWNLOADED_FILE = 4`, `PACKAGE_SOURCE_LOCAL_FILE = 3`, `PACKAGE_SOURCE_STORE = 2`) inside `PackageManager`:

```bash
adb shell dumpsys package com.android.chrome | grep -iE 'installerPackageName|packageSource' | head -n 6
```

Audit all installed packages holding `SYSTEM_ALERT_WINDOW` (`draw over other apps`) allow-states across the device:

```bash
adb shell cmd appops query-op SYSTEM_ALERT_WINDOW allow
```
