# Confidential Containers, Trustee Attestation, and Sealed AI Workloads

## Overview

* **Link in the Chain:** Completes Part IV by combining `Kata` micro-VMs ([Chapter 15](15-gvisor-microvms.md)), `IETF RATS` attestation ([Chapter 4](04-ima-ipe-keylime.md)), and `SEV-SNP` / `TDX` + Confidential GPUs ([Chapter 18](18-confidential-vms-svsm.md)) to place a hardware TEE boundary around *each individual Kubernetes Pod* (`CNCF Confidential Containers`), removing both the cloud provider and the Kubernetes worker-node `kubelet` from the TCB.
* **Core Security Invariant:** Untrusted host `kubelet` and `containerd` never pull, decrypt, or `exec` into confidential container images; instead, `image-rs` pulls encrypted `ocicrypt` layers *inside* the pod's measured `Kata` TEE, `Initdata` (`HOST_DATA` / `MRCONFIGID`) pins an immutable `OPA` `AgentPolicy` blocking unauthorized `kubectl exec`/env tampering, and an off-cluster `Trustee` Key Broker Service releases decryption keys and sealed AI model secrets strictly upon verifying hardware CPU (+ `SPDM` GPU) quotes.
* **Deployment Profile Matrix:** Standard Kubernetes trusts worker nodes and `etcd`/`kubelet` admins completely; regulated multi-party analytics and proprietary AI inference fleets deploy `Confidential Containers` (`CoCo` `runtimeClassName: kata-qemu-snp`, `kata-clh-tdx`, Azure `AKS Kata-CC`, OpenShift `Peer Pods`) paired with a tenant-controlled `Trustee` (`KBS`) cluster.
* **Trusted Computing Base (TCB):** CPU TEE silicon (`SEV-SNP` / `TDX` / `Arm CCA`) + optional `NVIDIA` `H100`/`B200` `CC-On` silicon, measured `CoCo` guest kernel + `dm-verity` rootfs (`kata-agent`, `Confidential Data Hub` `CDH`, `Attestation Agent` `AA`, `image-rs`), signed `Initdata` pod policy, and the tenant-owned remote `Trustee` (`AS` + `RVPS` + `KBS`).
* **Integration Seam & Handoff:** Guarantees zero-trust confidentiality and code integrity for containerized microservices and AI weights even when the Kubernetes control plane and worker nodes are compromised; hands off the final open question of the entire book: *what if the vendor-signed code inside your verified enclave was backdoored upstream before compilation?*: to [Chapter 20](20-xz-supply-chain-provenance.md).

## Problem Statement & Threat Model

Suppose an enterprise deploys its flagship proprietary Large Language Model (whose FP8/BF16 model weights cost $\$100\text{M}$ to train) or a multi-hospital genomic federated-learning service onto a managed cloud Kubernetes cluster (`EKS`, `AKS`, `GKE`, or third-party GPU cloud). Why isn't scheduling those pods onto `SEV-SNP` or `Intel TDX` *Confidential VM worker nodes* ([Chapter 18](18-confidential-vms-svsm.md)) enough [147, 151]?

Trace who still sits *inside* the Trusted Computing Base of a whole-node Confidential VM! While hardware memory encryption blinds the cloud provider's underlying `KVM` hypervisor, every process running as `root` on the Kubernetes worker node OS itself executes *inside* the decrypted VM boundary: `kubelet`, `containerd`, CNI/monitoring DaemonSets, cluster SREs with node SSH or `kubectl debug node/...` access, and any attacker who compromises the Kubernetes API Server! On a standard worker node, `containerd` unpacks plaintext OCI image layers straight onto `/var/lib/containerd/` on the node's disk (anyone with node root `tar`s up your $\$100\text{M}$ `.safetensors` weights in seconds!), `kubelet` injects arbitrary `LD_PRELOAD` environment variables or `command: ["/bin/sh"]` overrides into Pod specs, and any cluster admin with `pods/exec` RBAC runs `kubectl exec -it llm-pod -- gcore 1` to dump live user inference prompts straight out of GPU/CPU memory [147, 150]!

The threat model of CNCF `Confidential Containers` (`CoCo` [147, 148]) treats both the cloud hypervisor *and* the Kubernetes control plane / worker-node `kubelet` as untrusted infrastructure orchestrators. Under this hostile-orchestrator model, the workload owner holds two crown jewels off-cluster inside a dedicated `Trustee` attestation and key-vault appliance [148]: (1) the symmetric decryption keys for encrypted OCI container images and AI model weights, and (2) the Reference Values (`LAUNCH_DIGEST` / `MRTD` + signed `Initdata` Pod security policy). Even if an attacker obtains full `cluster-admin` on Kubernetes *and* `UID 0` on the Linux worker node, they must gain zero access to container filesystem layers, zero ability to execute diagnostic shells or alter environment variables inside running pods, and zero visibility into decrypted AI weights or user prompts in RAM/VRAM [147, 148, 150]!

## Kernel & Userspace Mechanics

### Enclave-Per-Pod Architecture: `guest-components` and `Initdata` Policy Binding

`Confidential Containers` (`CoCo` [147]) extends `Kata Containers 3.x` ([Chapter 15](15-gvisor-microvms.md)) so every Pod with `runtimeClassName: kata-qemu-snp` or `kata-clh-tdx` boots inside its own dedicated, hardware-encrypted `SEV-SNP` or `Intel TDX` micro-VM enclave:

![Figure: End-to-end boot, attestation, and encrypted image unlock sequence in CNCF Confidential Containers (CoCo): an untrusted worker node launches a measured Kata TEE pod, Attestation Agent proves CPU + Initdata integrity to off-cluster Trustee (KBS), and Confidential Data Hub unwraps ocicrypt layers exclusively inside enclave RAM.](diagrams/19-coco-kata-trustee-flow.svg)

First, *how does `CoCo` stop the untrusted host `containerd` from reading container images on the host*? In standard `Kata`, host `containerd` downloads and unpacks OCI layers on the host and shares them into the guest over `virtio-fs` ([Chapter 15](15-gvisor-microvms.md)). In `CoCo`, host image pulling is disabled (`guest_pull`) [147, 149]. The host `containerd-shim-kata-v2` boots only a generic, publicly auditable, read-only `dm-verity` guest appliance (`UKI` + rootfs whose exact `SHA-384` measurement matches the hardware `SEV-SNP` `LAUNCH_DIGEST` or `TDX` `MRTD`), inside which four memory-safe Rust `guest-components` collaborate [147, 148]. First, `kata-agent` receives `CreateContainer` RPCs over `AF_VSOCK` from the untrusted host shim and validates every single RPC field against a compiled-in Open Policy Agent (`OPA` Rego) `AgentPolicy` before acting. Second, `image-rs` pulls OCI container images directly from the container registry into encrypted guest RAM (or an ephemeral guest-side `LUKS2` scratch disk keyed by random enclave-only entropy that vanishes on pod exit), verifying `Sigstore`/`cosign` image signatures and decrypting `ocicrypt` layers [149, 157]. Third, the `Confidential Data Hub` (`CDH`) acts as a local secret and storage broker inside the enclave (`127.0.0.1:8043`), unsealing `sealed-secret` Kubernetes placeholders (`sealed.fakeJWSheader...`) and unwrapping `LUKS2` or `ocicrypt` keys. Fourth, the `Attestation Agent` (`AA`) issues hardware `ioctl` requests to `/dev/sev-guest`, `/dev/tdx_guest`, and `NVIDIA` `SPDM` verifiers to collect signed hardware Evidence for `Trustee` [147, 148].

Pause and ask a critical adversarial question: if a single generic `CoCo` guest VM image boots *every* pod across the company, what stops a compromised `kubelet` on the worker node from booting that genuine `CoCo` VM image with a tampered Pod YAML: for instance changing `command: ["/app/server"]` to `command: ["/bin/sh", "-c", "cat /models/weights.bin > /dev/console"]` or leaving `ExecProcessRequest` (`kubectl exec`) enabled?

`CoCo` solves the *Pod-Spec Substitution Attack* via `Initdata` (`CoCo` Initdata Specification [150]) paired with `kata-agent` `AgentPolicy` (`genpolicy`)! At CI deployment time, `genpolicy` inspects the legitimate Pod YAML (`image: registry.corp/llm@sha256:9f8a...`, exact `argv`, exact allowed `env` vars, `ReadStreamRequest: false` blocking log leaks if desired, and `ExecProcessRequest: false` unconditionally blocking `kubectl exec`!) and compiles a strict `policy.rego` bundled into a TOML `initdata` document [147, 150]. When the untrusted host VMM boots the `SEV-SNP` or `TDX` enclave, it passes `SHA-384(initdata)` into the CPU's dedicated hardware host-data measurement register (`HOST_DATA` in `SEV-SNP`'s `SNP_LAUNCH_FINISH` `id_block`, or `MRCONFIGID` in `Intel TDX`'s `TDH.MNG.INIT`)! Inside the enclave, `CDH` hashes the received `initdata` blob, verifies it matches the hardware-committed register, loads `policy.rego` into `kata-agent`, and includes `HOST_DATA`/`MRCONFIGID` inside the signed hardware quote sent to `Trustee` [148, 150]! If the untrusted `kubelet` changes a single character of `policy.rego` (e.g., enabling `kubectl exec`), `HOST_DATA` changes and `Trustee` refuses to release a single decryption key; if `kubelet` leaves `policy.rego` intact and sends a rogue `CreateContainer` command over `vsock`, `kata-agent`'s Rego engine rejects the RPC inside the enclave with `PermissionDenied`!

### Remote Attestation and Key Release with `Trustee` (`KBS`) and `ocicrypt`

Container images holding proprietary code or model parameters are encrypted at build time (`skopeo copy --encryption-key jwe:...` using `ocicrypt` [149]), wrapping each `tar+gzip`/`zstd` OCI layer under `AES-256-GCM` (`org.opencontainers.image.enc.keys.jwe` or `provider:attestation-agent:kbs:///default/llm-keys/weights-v1`). The encrypted image can sit safely on public Docker Hub or an untrusted node cache because no key exists in the cluster!

When `image-rs` inside the pod TEE encounters `kbs:///default/llm-keys/weights-v1`, `Attestation Agent` executes the `KBS` `RATS` Attestation Protocol (`RFC 9334` [40, 148]) over HTTPS to the workload owner's `Trustee` server:
First, `AA` sends an `Auth` request declaring its TEE architecture (`snp`, `tdx`, `cca`, or `az-snp-vtpm`); `Trustee` returns a fresh random 256-bit `nonce` + session cookie. Second, `AA` generates an ephemeral RSA/ECDH keypair `(pk_{\text{eph}}, sk_{\text{eph}})` purely inside encrypted TEE RAM and asks `/dev/sev-guest` or `/dev/tdx_guest` to sign a hardware attestation report binding:

$$\texttt{REPORT\_DATA}_{64\text{B}} = \operatorname{SHA-512}\!\left(\text{nonce} \;\parallel\; \operatorname{JWK}(pk_{\text{eph}})\right)$$

Silicon signs `SNP_ATTESTATION_REPORT` (using `VCEK` chaining to AMD Milan/Genoa/Turin Root CA) or `TD_QUOTE` (using Intel Quoting Enclave `PCK` chaining to Intel SGX/TDX Root CA), covering `LAUNCH_DIGEST`/`MRTD`, `HOST_DATA`/`MRCONFIGID`, `POLICY.DEBUG == 0` (critical! If debug mode were `1`, the hypervisor could decrypt guest memory via `SNP_DBG_DECRYPT`!), `SMT` flags, and hardware microcode `TCB_SVN` [140, 141, 148]. Third, `Trustee`'s *Attestation Service (`AS`)* verifies the silicon certificate chain + CRLs, compares measurements against the *Reference Value Provider Service (`RVPS`)*, evaluates an `OPA` appraisal policy, and only on `EAR = AFFIRMING` instructs the *Key Broker Service (`KBS`)* to wrap `llm-keys/weights-v1` in a `JWE` encrypted strictly to $pk_{\text{eph}}$ [148]! Even if an attacker MITMs the network, only $sk_{\text{eph}}$ inside that attested enclave can unwrap the key!

### Sealing Proprietary AI Weights and Prompts End to End (`CPU TEE + GPU TEE + RA-TLS`)

Combine every piece we have built across Chapters 18 and 19 to see how modern Linux seals frontier AI inference on untrusted GPU clouds [145, 148, 150]:

![Figure: End-to-end confidential AI inference pipeline on Linux: encrypted ocicrypt model weights, composite CPU (SEV-SNP/TDX) + GPU (NVIDIA H100/B200 SPDM) attestation to Trustee KBS, encrypted PCIe tensor transfer, and Remote-Attested TLS (RA-TLS) for client prompts.](diagrams/19-sealed-ai-inference-pipeline.svg)

At pod startup on a bare-metal or cloud `TDX` + `NVIDIA H100/B200` worker node (`CC-On`), the `CoCo` pod's `nvrc` / `gpu-attester` inside the enclave completes the `SPDM` mutual attestation with the physical `H100` GPU over PCIe (`VFIO` passed directly into the `Kata` CVM) and bundles *both* the CPU `TD_QUOTE` and the `NVIDIA` signed GPU `SPDM` attestation report into a composite `RATS` Evidence bundle sent to `Trustee` [145, 148]. `Trustee` verifies *both* silicon quotes before releasing the `ocicrypt` / `CDH` model-weight decryption key; weights stream straight from encrypted CPU RAM across `AES-GCM-256` PCIe bounce buffers into isolated GPU HBM3e without touching disk! Finally, to protect *user prompts and completions* from an untrusted cluster Ingress load balancer, the inference server (`vLLM` / `Triton` inside the pod TEE) terminates `RA-TLS` (*Remote-Attested TLS*): embedding a fresh hardware TEE quote binding its ephemeral TLS X.509 public key inside a custom X.509 extension so the enterprise client's SDK verifies enclave authenticity *before* sending a single prompt token over TLS 1.3 [148, 150]!

## Distro, Immutable-OS, & Cloud Trade-Offs

Deploying `Confidential Containers` trades ~`1–3` seconds of initial pod cold-start latency (booting the per-pod `SEV-SNP`/`TDX` VM, running `Trustee` quote verification, and pulling/decrypting OCI layers inside the guest rather than sharing host page cache across pods!) and ~`256–512 MiB` of per-pod base guest RAM overhead in exchange for complete cryptographic immunity against compromised Kubernetes nodes and cloud operators [147, 151]. On bare-metal or nested-CVM clusters (`Kata` + `QEMU`/`Cloud Hypervisor`), `CoCo` creates enclaves directly via `/dev/kvm`; on public clouds that do not yet expose nested `SEV-SNP`/`TDX` inside worker VMs (`Azure AKS` Confidential Pods, `IBM`/`AWS` OpenShift Sandboxed Containers), `CoCo`'s `cloud-api-adaptor` (`Peer Pods`) transparently calls the cloud provider API to spawn a sibling L1 Confidential VM per Pod wired seamlessly into the cluster CNI over encrypted VXLAN/WireGuard [147, 151]!

## Seam Failures, CVEs, & Structural Bounds

Confidential Container compromises happen when operators ship permissive `AgentPolicy` Rego rules (`ExecProcessRequest: true`), forget to check `POLICY.DEBUG == 0` or microcode `TCB_SVN` floors in `Trustee`, or leak plaintext stdout logs to untrusted host `kubelet` collectors.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| Permissive `genpolicy` (`ExecProcessRequest: true`) | 2023-2025 | `CoCo` `kata-agent` `AgentPolicy` | Default developer/debug Rego policy is safe for production | Compromised `kubelet` sends `ExecProcess` (`kubectl exec`) over `vsock` and dumps decrypted secrets from enclave RAM | Enforce production `genpolicy` (`ExecProcessRequest = false`, `ReadStreamRequest = false`, pinned `argv`/`env`) bound in `Initdata` [147, 150] |
| Unchecked `DEBUG = 1` or Stale `TCB_SVN` in Verifier | 2022-2024 | Custom `RATS` / `KBS` quote policies | Valid AMD `VCEK` / Intel `PCK` signature alone guarantees enclave safety | Host launches VM with `SNP_POLICY_DEBUG = 1` (enabling `SNP_DBG_DECRYPT`) or downgraded vulnerable microcode (`WeSee` / `Downfall`) | Enforce strict `Trustee` `OPA` + `RVPS` policies rejecting `debug == true` and requiring latest `TCB_SVN` [140, 148] |
| Plaintext Container `stdout` / `/var/log/pods` Leakage | Architectural | `kata-agent` `ReadStream` console pipe | Pod logs are insensitive metadata | Application logs prompt tokens or stack-trace env vars to `stdout`, read in plaintext by untrusted host `kubelet` | Disable `ReadStreamRequest` in `AgentPolicy` and ship logs encrypted directly from inside the TEE over mTLS [147, 150] |
| Malicious Upstream Binary Inside Verified Enclave | 2024 | Guest OS / OCI supply chain (`CVE-2024-3094` class) | Verified `LAUNCH_DIGEST` + `ocicrypt` signature means enclave code is trustworthy | Upstream open-source library (`liblzma` / PyPI dependency) was backdoored *before* image builder signed and encrypted it | Pair `CoCo` runtime attestation with Reproducible Builds, `SLSA` L3 provenance, and `Sigstore` (`Rekor`) ([Chapter 20](20-xz-supply-chain-provenance.md)) [152, 156, 157] |

Look at Row 4: suppose you verify every `SEV-SNP` `VCEK` signature, `COCONUT-SVSM` `PCR[11]` digest, `dm-verity` Merkle root, `IPE` policy, `SELinux` label, and `Trustee` `Initdata` hash to 384-bit mathematical perfection: *what happens when the open-source maintainer who released the source tarball inside that signed image was an adversary all along?* [Chapter 20](20-xz-supply-chain-provenance.md) closes *The Linux Trust Chain* with the `XZ Utils` (`CVE-2024-3094`) supply-chain backdoor and the cryptographic provenance architecture built to stop its successors.

## Inspecting on a Live Linux Host

Check Kubernetes `RuntimeClass` handlers or local `containerd` `CoCo` (`kata-qemu-snp`, `kata-qemu-tdx`, `kata-clh-tdx`) configuration entries on a cluster worker node:

```bash
grep -rnE "kata-(qemu|clh)-(snp|tdx)" /etc/containerd/ 2>/dev/null || kubectl get runtimeclass 2>/dev/null || true
```

Inspect `Confidential Containers` artifacts (`/opt/confidential-containers/`) or `kata-runtime check` hardware TEE readiness when installed:

```bash
ls -la /opt/confidential-containers/bin/ 2>/dev/null || kata-runtime check --no-network-checks 2>/dev/null | head -n 12 || true
```
