# BiometricPrompt Strength Tiers and Credential Manager Passkeys

## Overview

* **Link in the Chain:** Local human-presence verification and phishing-resistant remote authentication layer; classifies biometric pipelines into quantitative `CDD` tiers (`Class 1`, `Class 2`, `Class 3`) to gate `KeyMint` keys via `HardwareAuthToken` MACs and unifies `FIDO2`/`WebAuthn` passkeys behind `Credential Manager`.
* **Core Security Invariant:** Only a `Class 3` (`Strong`) biometric sensor executing inside `TEE`/`StrongBox`-isolated memory with `SAR <= 7%` and `FAR <= 1/50,000` possesses the shared `HMAC-SHA256` key required to authorize `KeyMint` `CryptoObject` signatures (which auto-invalidate via `authenticatorId` rotation if a new biometric is enrolled), while `WebAuthn` passkey assertions cryptographically bind `SHA-256(rpId)` and `BLE` proximity.
* **Ecosystem Enforcement Tier:** `CDD` Section 7.3.10 biometric strength bounds, `HardwareAuthToken` verification, and `CredentialProviderService` APIs enforce identically across `GREEN` and `YELLOW` locked states (`GrapheneOS` supports `Class 3` hardware biometrics and third-party vaults such as `Bitwarden` and `1Password`); `Google Password Manager` E2EE passkey sync runs on GMS (`GREEN`) devices pinned to `Google Titan` Cloud Key Vault HSMs.
* **Trusted Computing Base (TCB):** `TZASC`-isolated `SPI`/`MIPI CSI-2` biometric sensor pipeline, `IFingerprint`/`IFace` `TEE` matcher Trusted Applications (`hardware/interfaces/biometrics/`), `HardwareAuthToken.aidl` HMAC verifier inside `KeyMint`/`StrongBox` ([Chapter 4](04-keymint-weaver-throttling.md)), `BiometricService`, `CredentialManagerService`, `Titan` Cloud Key Vault HSMs, and the `CTAP 2.2` `caBLE` v2 `BLE`/`Noise` stack.
* **Seam & Handoff:** Completes Part III by binding live human presence on the handset to non-exportable local keys and phishing-immune remote sessions; transitions to the Interlude ([Chapter 14](14-play-protect-intrusion-logging.md)) to examine runtime threat detection and forward-secure cloud `Intrusion Logging`.

## Threat Model & Ecosystem Constraint

Across an open hardware ecosystem spanning USD 90 entry smartphones and USD 1,400 flagships, OEMs integrate radically different biometric sensors: single front-facing RGB selfie cameras running normal-world neural networks, 2D near-infrared (`NIR`) cameras, side-mounted capacitive fingerprint strips, under-display optical CMOS fingerprint cameras, 3D ultrasonic under-display transducers, and dual-pixel or structured-light infrared depth pipelines [376, 377]. In early smartphone generations, if a vendor shipped a 2D RGB face-unlock routine whose liveness heuristic could be fooled by a curved laser-printed photograph (`Spoof Acceptance Rate` exceeding `30%`) and exposed it under the same Java callback as a `TrustZone`-isolated fingerprint matcher, relying financial applications had zero architectural signal distinguishing genuine silicon verification from a trivially spoofed camera heuristic [376, 377, 378].

Below and above that sensor diversity, three concrete attack classes target biometric and credential pipelines in production [379, 380, 381, 382]:

First are *physical presentation attacks (`PAI`) and peripheral bus interception*. Beyond gelatin fingerprint molds, printed high-DPI photographs, and 3D masks evaluated under `ISO/IEC 30107-3` [378], Yu Chen, Yiling He, and colleagues demonstrated at USENIX Security 2023 (*BrutePrint* [381]) that physical attackers with board access on unhardened smartphones could interpose on the Serial Peripheral Interface (`SPI`) bus between the fingerprint sensor IC and the SoC! By combining unencrypted `SPI` frame injection with two protocol logic bugs, *Cancel-After-Match-Fail* (`CAMF`, corrupting frame checksums on failed matches to abort retry-counter increments) and *Match-After-Lockout* (`MAL`, inferring match scores via timing side channels even during lockout), *BrutePrint* turned a 5-attempt fingerprint sensor into an unlimited offline dictionary brute-forcer [381]. Similarly, if raw `MIPI CSI-2` camera frames pass through `EL1` Linux kernel memory before entering `TrustZone`, a kernel exploit can inject synthetic enrolled face frames without presenting any physical spoof at all [376, 377].

Second is *application-layer boolean-callback spoofing and post-compromise biometric enrollment* [380, 382, 383, 384]. Across mobile penetration tests cataloged by `OWASP MASTG-TEST-0018` [382] and WithSecure Labs [384], the single most prevalent mobile banking authentication bug occurs when developers invoke `BiometricPrompt.authenticate(promptInfo)` *without* passing a `KeyMint`-backed `BiometricPrompt.CryptoObject`, treating `onAuthenticationSucceeded()` as a pure Java boolean gate (`if (success) openVault()`). Any attacker with in-process dynamic instrumentation (`Frida`, `Zygisk`, or memory corruption inside the app sandbox) simply calls `AuthenticationCallback.onAuthenticationSucceeded(null)` directly in ART memory, bypassing the fingerprint sensor and `TEE` completely [380, 382, 384]! Conversely, if an attacker observes a victim's `LSKF` PIN (before `Identity Check` intervenes) and enrolls the attacker's *own* thumbprint in `Settings`, any pre-existing app key that blindly accepts "any currently enrolled biometric" would suddenly unlock for the attacker unless cryptographic keys detect template-set mutation [383, 385].

Third is *real-time Adversary-in-the-Middle (`AiTM`) credential phishing and cross-device relay* [379, 386, 387]. Human-memorable passwords paired with SMS or TOTP 6-digit codes fail deterministically against reverse-proxy phishing kits (*Evilginx*), which relay the victim's password and OTP straight to the genuine bank in real time. Asymmetric `FIDO2`/`WebAuthn` passkeys eliminate phishing by binding signatures to the TLS origin, yet create an immediate custody trilemma: storing passkeys exclusively inside one phone's `StrongBox` bricks every bank and email login when the phone drops off a pier; syncing plaintext passkey private keys through a cloud database exposes every user to cloud breaches or subpoenas; and letting desktop logins trigger remote push prompts on a phone invites *MFA push-fatigue* and remote QR-code social engineering over Discord or Zoom calls [379, 387, 388, 389].

## Architecture & AOSP Implementation

### `CDD` Section 7.3.10: `Class 1-3` Metrics, Arc Calibration, and `TZ` Bus Isolation

Android's Compatibility Definition Document (`CDD` Section 7.3.10) and AOSP Biometric Security specification evaluate every biometric implementation across two non-negotiable pillars: *empirical spoof/impostor bounds* and *end-to-end hardware pipeline isolation* [376, 377, 378].

To prevent OEMs from cherry-picking favorable camera angles during lab testing, AOSP defines a mandatory two-phase *Calibration and Arc Testing Protocol* aligned with `ISO/IEC 30107-3` Presentation Attack Detection (`PAD`) [376, 378]. Testers first prepare Level A (printed photos, digital screen photos/videos, conductive latex/wood-glue molds) and Level B (curved cheek-contoured masks with live eye cutouts for blink bypass, contact-lens overlays on iris prints, 3D masks) Presentation Attack Instruments (`PAI`s), then sweep each `PAI` across 10-degree vertical and horizontal arcs (`20-80 cm`) across diverse age, gender, skin-tone, and iris cohorts to identify the *calibrated maximum-weakness position* [376]. In the test phase across $E \ge 10$ unique enrollments and $U \ge 10$ attempts per enrollment (385+ iterations per subject for a 5% confidence margin), labs measure three error rates [376, 377]: False Acceptance Rate (`FAR`, random distinct human match probability), Impostor Acceptance Rate (`IAR`, active mimicry), and Spoof Acceptance Rate (`SAR`, also termed `IAPMR`):

$$\text{SAR} = \frac{\sum_{i=1}^{E} S_i}{U \cdot E} \times 100\%$$

Simultaneously, AOSP audits *Architectural Pipeline Security* [376, 377, 385]. A biometric pipeline qualifies as *Secure* if and only if compromising the entire `EL0` Android userspace and `EL1` Linux kernel confers *neither* the ability to read raw biometric images/templates *nor* the ability to inject synthetic biometric frames to influence an authentication verdict! Concretely, `SPI` fingerprint sensors and `MIPI CSI-2` secure-camera streams must be isolated via Arm `TrustZone` Address Space Controller (`TZASC`) / `SMMU` Stage-2 firewall rules (with per-session `SPI` encryption/MAC authentication between modern sensor dies and the `TEE` to defeat physical `BrutePrint` bus injection [381]), template files stored under `/data/vendor_de/0/fpdata` must be encrypted and MACed under `TEE`-private keys with hardware anti-rollback counters inhibiting `CAMF` retry resets, and feature extraction plus matching must run strictly inside the `IFingerprint` / `IFace` Trusted Application (`hardware/interfaces/biometrics/`) [376, 377, 385].

![Figure: Android BiometricManager Class 1 (Convenience), Class 2 (Weak), and Class 3 (Strong) spoof bounds, pipeline isolation, and KeyMint privileges.](diagrams/13-biometric-class-tiers.svg)

`BiometricService` (`frameworks/base/services/core/java/com/android/server/biometrics/BiometricService.java` [390]) enforces an immutable capability matrix based on the sensor's certified class (`Authenticators.BIOMETRIC_STRONG = 15`, `BIOMETRIC_WEAK = 255`, `BIOMETRIC_CONVENIENCE = 4095`) [376, 377, 390]:

`Class 3` (`BIOMETRIC_STRONG`) demands a *Secure* hardware-isolated pipeline, `FAR <= 1/50,000`, `FRR <= 10%`, and aggregate `SAR <= 7%` across Level A `PAI`s. *Exclusively* `Class 3` Trusted Applications are provisioned at boot with the 256-bit shared `KeyMint` `HMAC` key ([Chapter 4](04-keymint-weaver-throttling.md)); therefore, *only* `Class 3` sensors can mint a `HardwareAuthToken` to unlock `KeyMint` `CryptoObject` keys, satisfy `Identity Check` outside Trusted Places ([Chapter 12](12-fbe-usb-theft-protection.md)), and sign local passkeys or `ISO 18013-5` `mDL` digital credentials, subject to a 72-hour maximum / 4-hour idle primary `LSKF` fallback timer [376, 377, 391].

`Class 2` (`BIOMETRIC_WEAK`) requires a *Secure* isolated pipeline and `FAR <= 1/50,000`, but exhibits `7% < SAR <= 20%` (typical of 2D NIR face sensors without dense depth maps). `BiometricService` permits third-party apps to invoke `Class 2` sensors via `BiometricPrompt` (`setAllowedAuthenticators(BIOMETRIC_WEAK)`) *solely* for non-cryptographic UI gating: `Class 2` TAs *never* hold the `KeyMint` `HMAC` key, cannot participate in `CryptoObject` signatures, and force `LSKF` fallback every 24 hours (or after 4 hours idle / 3 failed attempts) [376, 377, 390].

`Class 1` (`BIOMETRIC_CONVENIENCE`) covers `20% < SAR <= 30%` or any *Insecure* normal-world pipeline. `BiometricService` hides `Class 1` sensors completely from `BiometricPrompt` and `FIDO2` APIs, confining them to low-assurance lock-screen swipe convenience with a 24-hour / 4-hour idle / 3-strike `LSKF` fallback [376, 377].

### `HardwareAuthToken` HMACs, `CryptoObject` Gating, and `authenticatorId` Rotation

Walk through what actually crosses silicon boundaries when a properly engineered banking or passkey app binds `BiometricPrompt` to an `AndroidKeyStore` key (`setUserAuthenticationRequired(true)` and `setUserAuthenticationParameters(0, KeyProperties.AUTH_BIOMETRIC_STRONG)`) versus the broken event-only anti-pattern [97, 194, 382, 384, 392]:

![Figure: Event-only BiometricPrompt Java callback spoofing via Frida dynamic instrumentation versus hardware-enforced Class 3 KeyMint CryptoObject gating via 69-byte HMAC-SHA256 HardwareAuthTokens and authenticatorId rotation.](diagrams/13-extra-cryptoobject-vs-frida-bypass.svg)

When the app initializes a `Signature` (or `Cipher` / `Mac`) with its `AndroidKeyStore` `PrivateKey` and wraps it inside `BiometricPrompt.CryptoObject(signature)`, `keystore2` invokes `IKeyMintDevice::begin(KeyPurpose::SIGN, keyBlob)` inside `TEE` or `StrongBox` [97, 194]. Because `Tag::NO_AUTH_REQUIRED` is absent and `Tag::AUTH_TIMEOUT == 0` (per-operation authentication), `KeyMint` generates a fresh cryptographically random 64-bit `challenge` (`operationHandle`) inside secure memory and returns it to `keystore2` and `AuthSession.java` [390, 392]. `BiometricService` passes that exact 64-bit `challenge` across the Binderized HAL into `IFingerprint::authenticate(operationId)` [385, 390].

Only after the isolated `Class 3` fingerprint or 3D face TA physically captures a live scan from its `TZASC`-protected sensor bus and matches an enrolled template does the TA construct a 69-byte `HardwareAuthToken` (`hardware/interfaces/security/keymint/aidl/android/hardware/security/keymint/HardwareAuthToken.aidl` [392]), authenticating the exact `challenge` under the boot-shared 256-bit `HMAC` key $H$ known only to `Gatekeeper`, `Class 3` biometric TAs, and `KeyMint`/`StrongBox`:

$$\text{mac}_{32} = \text{HMAC-SHA256}\bigl(H, \; \text{0x00} \parallel \text{challenge}_{64} \parallel \text{userId}_{64} \parallel \text{authenticatorId}_{64} \parallel \text{authType}_{32,\text{BE}} \parallel \text{timestamp}_{64,\text{BE}}\bigr)$$

(Notice the historical wire quirk preserved in `HardwareAuthToken.aidl` for backward compatibility with legacy C `hw_auth_token_t`: `challenge`, `userId`, and `authenticatorId` are hashed in native little-endian machine order, whereas `authenticatorType` (`HW_AUTH_BIOMETRIC = 2`) and monotonic secure-clock `timestamp` are hashed in network big-endian order [392]!)

When `Signature.sign(serverChallenge)` executes inside `onAuthenticationSucceeded()`, `keystore2` forwards the `HardwareAuthToken` into `IKeyMintOperation::finish()` [97, 392]. Inside `StrongBox` or `TEE`, `KeyMint` recomputes `HMAC-SHA256` using $H$, verifies `token.challenge == op.challenge` (defeating replay of an older `HardwareAuthToken` captured in `EL1` RAM!), checks `token.authenticatorType & Tag::USER_AUTH_TYPE`, and checks *one more critical invariant*: `token.authenticatorId == keyBlob.TAG_USER_SECURE_ID` (`Tag 502`) [97, 383, 385, 392]!

Why does `authenticatorId` (`TAG_USER_SECURE_ID`) matter so deeply? By default in `KeyGenParameterSpec.Builder`, `setInvalidatedByBiometricEnrollment(true)` is enabled [383]. At key generation time, `keystore2` queries `IFingerprint::getAuthenticatorId()` (and `IFace::getAuthenticatorId()`), which returns a random 64-bit entropy value generated inside the `TEE` representing the *exact current set of enrolled templates*, and seals that 64-bit integer into the key's `hardwareEnforced` `Tag::USER_SECURE_ID` list [97, 383, 385]. The instant *any* new fingerprint or face profile is added in `Settings` (`IFingerprint::enroll()`), the biometric TA overwrites its stored `authenticatorId` in `RPMB`/secure storage with a brand-new random 64-bit integer [385]! Consequently, even if an attacker learns a user's `LSKF` PIN and enrolls their own finger, every `HardwareAuthToken` minted thereafter carries the *new* `authenticatorId`, causing `KeyMint` to permanently reject `IKeyMintOperation::finish()` on existing `CryptoObject` keys (`KeyPermanentlyInvalidatedException`) and forcing full server-side re-authentication [383, 385]! And if an attacker uses `Frida` inside the app process to call `onAuthenticationSucceeded(null)` without touching the sensor, `KeyMint` receives zero valid `HardwareAuthToken` and refuses to sign a single byte [382, 384].

> **Key idea.**
> A local boolean inside `onAuthenticationSucceeded()` proves only that a Java method ran inside untrusted `EL0` RAM; a `KeyMint` `ECDSA` signature produced via `BiometricPrompt.CryptoObject` over a server-issued challenge proves to your remote backend that `StrongBox`/`TEE` verified a `Class 3` `HardwareAuthToken` bound to an un-mutated biometric template set [194, 382, 392].

### `Credential Manager`, Pluggable Passkey Vaults, and `Digital Asset Links`

Introduced in Android 14 (`API 34`) and matured across Android 15-17 (`androidx.credentials` + `frameworks/base/services/credentials/java/com/android/server/credentials/CredentialManagerService.java` [386, 393, 394]), `Credential Manager` replaces fragmented Autofill hacks and legacy FIDO intents with a system-brokered, provider-agnostic passkey and credential architecture. Users can choose `Google Password Manager` (`GPM`) alongside third-party `CredentialProviderService` vaults (`1Password`, `Bitwarden`, `Dashlane`, `Proton Pass`, `KeePassDX`) simultaneously [393, 395].

Look at how `CredentialManagerService` and `ProviderSession.java` isolate vault secrets across a strict *two-phase IPC protocol* (`BIND_CREDENTIAL_PROVIDER_SERVICE` ensures only `system_server` can bind to providers) [393, 394]:

| Protocol Phase / Boundary | System / Provider Action | Origin & Privilege Enforcement Gate |
|---|---|---|
| Phase 1 · Query (`onBeginGetCredentialRequest`) | System fans out RP request metadata; providers return visual `CredentialEntry` slices + `FLAG_MUTABLE` `PendingIntent`s | Vault remains locked; zero private keys or plaintext passwords enter `system_server` [393, 394] |
| Phase 2 · Selection (`PendingIntent` Activity) | User taps chosen passkey on system bottom sheet; OS fires provider's `Activity` + `BiometricPrompt` | Provider extracts kernel-verified `CallingAppInfo` (`packageName` + `SigningInfo` `SHA-256` cert) [393] |
| Native App `rpId` Binding (`assetlinks.json`) | Provider / GMS verifies APK cert against `https://<rpId>/.well-known/assetlinks.json` | Requires `delegate_permission/common.get_login_creds`; blocks clone APKs from requesting `rpId` [396] |
| Browser Cross-Origin Delegation (`getOrigin()`) | Chrome / Firefox passes HTTPS page origin inside `GetCredentialRequest.origin` | Restricted strictly to browsers holding `CREDENTIAL_MANAGER_SET_ORIGIN` / trusted-browser XML [393, 394, 395] |

During `WebAuthn Level 3` passkey authentication [379], once the user approves `BiometricPrompt`, the credential provider constructs `authenticatorData` (`32`-byte `SHA-256(rpId)` $\parallel$ flags `UP | UV | BE | BS` $\parallel$ 32-bit `signCount`) and `clientDataJSON` (binding the exact server `challenge` and verified `origin`, either `https://<domain>` from a `CREDENTIAL_MANAGER_SET_ORIGIN` browser or `android:apk-key-hash:<base64url_sha256>` verified against `assetlinks.json` [379, 393, 396]), then signs `authenticatorData || SHA-256(clientDataJSON)` using the credential's `ECDSA NIST P-256` private scalar. Even a pixel-perfect real-time `AiTM` phishing proxy at `bank-secure.com` receives `SHA-256("bank-secure.com")`, matching zero credentials registered for `bank.com` [379]. Note also an operational change rolled out in April 2025: Android's platform `FIDO2` / device-bound authenticator API switched to standard hardware-backed `Key Attestation` by default after retiring legacy `SafetyNet` attestation statements [397].

How does `Google Password Manager` sync multi-device passkeys (`BE = 1, BS = 1` backup-eligible/backed-up flags in `authenticatorData`) across a user's Android phones and Chrome profiles without exposing private keys to Google [388, 389]? Every passkey private key is encrypted on-device with `AES-256-GCM` under a random 256-bit *Security Domain Secret* ($K_{\text{vault}}$) inside Chrome Sync's `hw_protected` security domain [388, 389]. Google's sync servers store only opaque ciphertext. Enrolling a replacement phone after losing your handset requires recovering $K_{\text{vault}}$ either via direct peer-to-peer device transfer or by proving knowledge of your prior phone's `LSKF` PIN/password directly to a hardware-attested `Google Titan` Cloud Key Vault (`CKV`) HSM cohort ([Chapter 19](19-e2ee-backups-private-ai-compute.md)), whose audited silicon firmware enforces a hard lifetime counter (`<= 10` wrong guesses before irreversibly erasing the escrow share) so neither brute-force attackers nor Google operators can unwrap $K_{\text{vault}}$ [388, 389]! Meanwhile, regulated financial or government workflows requiring strictly non-synced, silicon-bound credentials use `AndroidKeyStore` `StrongBox` keys or `OpenID4VP` / `ISO 18013-5` `Multipaz` wallets [379, 391].

### `FIDO CTAP 2.2` Hybrid Transport (`caBLE` v2): Radio Proximity Meets `Noise`

![Figure: Credential Manager passkey authentication, Google Password Manager E2EE sync security domain wrapped via Titan HSM, and CTAP 2.2 caBLE proximity transport.](diagrams/13-passkey-sync-cable-flow.svg)

Suppose a user sits at an unlinked Linux or Windows desktop and clicks `"Sign in with a passkey on another device"`. How does `CTAP 2.2` Section 11 Hybrid Transport (`caBLE` v2, implemented in Chromium's `device/fido/cable/v2_handshake.cc` and Android Play Services / AOSP `config_defaultCredentialManagerHybridService` [379, 387, 394, 398]) defeat a remote scammer screen-sharing that QR code over a video call?

Trace the exact key schedule and radio handshake [387, 398, 399]. First, the desktop browser generates a fresh ephemeral compressed `P-256` identity keypair $(pk_C, sk_C)$ and a random 16-byte `QR secret` $s_{\text{QR}}$, rendering them inside a `fido://` CBOR QR code. Scanning that QR code with the Android camera gives *both* endpoints $s_{\text{QR}}$, from which both sides derive three domain-separated secrets via `HKDF-SHA256` [387, 398]. Under `purpose = 1`, `HKDF` expands a 64-byte *EID Key* split into a 32-byte `AES-256` cipher key and a 32-byte `HMAC-SHA256` tag key: the Android phone generates a 16-byte plaintext BLE payload (nonce, routing hint, and tunnel server index such as `0 = cable.ua5v.com`), encrypts it with `AES-256`, appends a 4-byte truncated `HMAC` over the ciphertext, and broadcasts that 20-byte frame locally over Bluetooth Low Energy (`BLE` Service Data UUID `0xFFF9`) [387, 398]! Under `purpose = 2`, `HKDF` derives a 16-byte *Tunnel ID* naming the rendezvous WebSocket channel on `cable.ua5v.com`, deliberately omitting the `BLE` nonce so the cloud relay server itself cannot brute-force or forge the `BLE` proximity advertisement [387, 398]. Finally, under `purpose = 3`, `HKDF` derives a 32-byte *Handshake Pre-Shared Key* (`PSK`) using the *decrypted 16-byte `BLE` advert plaintext as the `HKDF` salt* [387, 398]!

Look at what happens if a scammer in another city screen-shares their desktop's QR code to a victim over Zoom: the victim's phone scans the QR code and emits `0xFFF9` `BLE` packets *into the victim's room*, kilometers away from the scammer's desktop Bluetooth radio! Because the scammer's PC never receives the 20-byte `0xFFF9` `BLE` frame, it never learns the 16-byte `BLE` advert plaintext needed as the `HKDF` salt for `purpose = 3`, and *cannot complete* the `Noise_KNpsk0_P256_AESGCM_SHA256` (or `Noise_NKpsk0_P256_AESGCM_SHA256` for linked reconnects) authenticated `ECDH` tunnel handshake [387, 398, 399]! Physical co-location within `BLE` radio range is cryptographically bound into the `AES-256-GCM` session keys before a single `CTAP2` byte traverses the WebSocket relay.

## Vendor, OEM, & Custom-OS Boundaries

Two landmark hardware incidents illustrate why `CDD` Section 7.3.10 and `VTS` test both sensor physics and bus cryptography [376, 381, 400]. In October 2019 (`SVE-2019-15879` [400]), Samsung's early under-display ultrasonic fingerprint scanner on Galaxy S10 and Note 10 handsets suffered a severe physical bypass when paired with cheap textured third-party silicone gel screen protectors: the ultrasonic 3D acoustic pulse imaged the stationary micro-air-gap texture of the elastomer pad itself during enrollment and matching, allowing *any* un-enrolled human finger pressing on that gel pad to mint a `HardwareAuthToken` until Samsung updated its `QSEE` ultrasonic matcher TA and `CDD` 7.3.10 mandated pad/prosthetic `PAI` calibration! Four years later, *BrutePrint* [381] proved that mid-range OEM boards wiring fingerprint sensors to SoCs over plaintext `SPI` tracks without session MACs failed hardware-pipeline isolation against physical board probes, driving modern flagship `SPI`/`MIPI` buses (`Qualcomm QFP`/`QTEE`, `Samsung Knox Vault`, and `Google Tensor` + `Titan M2`) to authenticate and encrypt sensor frames end-to-end. Notably, on Pixel 8, 9, and 10+ devices, Google achieved full `Class 3` (`Strong`, `SAR <= 7%`) face authentication from a single punch-hole sensor by feeding dual-pixel phase-detection autofocus (`PDAF`) depth disparities directly over `TZ`-protected `ISP` DMA channels into `Trusty` + secure `TPU` presentation-attack classifiers [376].

On `GrapheneOS` (`YELLOW` locked Pixel), `Class 3` fingerprint and hardware-backed `KeyMint` `CryptoObject` gating work identically to stock `GREEN` Android (including `GrapheneOS`'s option to disable biometric unlock immediately via a lock-screen lockdown button or 5-attempt strict fallback), while `CredentialManagerService` natively supports open-source and zero-knowledge `CredentialProviderService` vaults (`Bitwarden`, `Proton Pass`, `KeePassDX`) alongside optional sandboxed Google Play `caBLE` / `FIDO2` without granting Play Services privileged `SYSTEM` UIDs [393, 395].

## Inspecting via ADB, Fastboot, & Attestation

Inspect all registered biometric sensors on the handset, verifying their certified `CDD` strength bitmask (`15` = `Class 3` `BIOMETRIC_STRONG`; `255` = `Class 2` `BIOMETRIC_WEAK`; `4095` = `Class 1` `BIOMETRIC_CONVENIENCE`) and active `authenticatorId` state:

```bash
adb shell dumpsys biometric | grep -iE 'SensorProps|strength|modality|authenticatorId' | head -n 14
```

Query `CredentialManagerService` state and list user-enabled `CredentialProviderService` passkey and password vaults (`Google Password Manager`, `Bitwarden`, `1Password`):

```bash
adb shell dumpsys credential_service | head -n 16
adb shell settings get secure credential_service
adb shell settings get secure credential_service_primary
```

Verify a relying party's live `Digital Asset Links` passkey delegation (`delegate_permission/common.get_login_creds` and pinned `sha256_cert_fingerprints`) from a workstation:

```bash
curl -fsSL https://www.google.com/.well-known/assetlinks.json | head -n 22
```
