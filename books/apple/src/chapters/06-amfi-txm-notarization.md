# AMFI, TXM Trust Caches, Launch Constraints, and Notarization

## Overview

* **Link in the Chain:** Mandatory code-signing, capability-entitlement, and software-admission layer bridging `APFS`/`XNU` ([Chapter 5](05-apfs-ssv-dyld.md)) and `SPTM`/`TXM` monitors ([Chapter 4](04-silicon-memory-safety.md)) to user-space process execution.
* **Core Security Invariant:** `XNU` and `SPTM` map a 4 KB page into an executable `XNU_USER_EXEC` frame if and only if `TXM` (or `AMFI`/`CoreTrust`) validates its `SHA-256` digest inside a signed `Mach-O` `CS_CodeDirectory` anchored in a Trust Cache or Apple-chained certificate, and `posix_spawn()`/`execve()` succeeds only when self, parent, and responsible identities satisfy active `ASN.1` `DER` `Launch Constraints`.
* **Platform Matrix:** Shared `Mach-O` `CS_CodeDirectory` slots, `DER` entitlements (`slot -7`), `TXM` trust caches, and `lwcr` `Launch Constraints` across all Apple OSes; third-party admission forks between `iOS`/`iPadOS`/`watchOS`/`visionOS` (`App Store` `FairPlay` or EU `DMA` Alternative App Marketplace Notarization) and `macOS` (`CS_LINKER_SIGNED` ad-hoc local builds plus `Gatekeeper`, `com.apple.quarantine`, and `CloudKit` Notary tickets).
* **Trusted Computing Base (TCB):** `Trusted Execution Monitor` (`TXM` in `GL0`), `AppleMobileFileIntegrity.kext` (`AMFI`) and `amfid`, `CoreTrust.kext` `X.509`/`CMS` verifier, `Image4`-authenticated Static and Loaded Trust Caches, `countryd` on EU `iOS`/`iPadOS`, `syspolicyd` and `Quarantine.kext` on `macOS`, and Apple's `App Store` and Notary signing authorities.
* **Failure Horizon & Handoff:** `ASN.1`/`CMS` multi-signer parser differentials in `CoreTrust` (`CVE-2021-30869`, `CVE-2023-41991`), archive extended-attribute stripping on `macOS` (*Achilles* `CVE-2022-42821`, `CVE-2023-27943`), or notarized stage-1 droppers admit unauthorized code; hands off post-launch `Mach`/`XPC` authentication, `Seatbelt` sandboxing, and parser containment to [Chapter 7](07-ipc-seatbelt-blastdoor.md).

## Threat Model & Design Tension

Sealing the base operating system inside an immutable `APFS` `Signed System Volume` ([Chapter 5](05-apfs-ssv-dyld.md)) guarantees that `/sbin/launchd` and `/usr/lib/dyld` cannot be modified on flash, yet every general-purpose or mobile device must still map executable code residing on its writable `Data` volume, mount developer disk images, load dynamic libraries, and spawn hundreds of background helper processes. Opening execution beyond the sealed root snapshot exposes four distinct post-boot attack vectors across commodity malware (Tier 1) and nation-state exploit chains (Tier 3) [36, 40, 55]. First, if executable integrity were checked only once by hashing an entire file linearly during `open()` or `execve()`, an adversary holding concurrent write access to a mutable file, network share, or external volume could overwrite unmapped disk extents after verification (`TOCTOU`), faulting unsigned machine instructions directly into RAM [207, 208]. Second, if fine-grained operating system capabilities (such as `Keychain` access groups, `Sandbox` exemptions, `EndpointSecurity` subscriptions, or `SIP` installation privileges) lived in external configuration files rather than inside the binary's own cryptographic signature, any local `UID 0` privilege escalation could mint arbitrary platform authority [39, 209].

Third, once an attacker achieved initial code execution or a kernel read/write primitive (such as the actively exploited `iOS 16.0` `XNU` out-of-bounds write `CVE-2022-42827` [210]), post-exploitation chains historically did not even need to forge signatures from scratch. On pre-`SPTM` kernels, attackers with `EL1` write primitives patched process `cs_flags` or appended attacker `CDHash` digests directly into writable kernel trust-cache allocations; even without a kernel bug, *living-off-the-land* (`LotL`) adversaries on `macOS` and `iOS` copied genuine Apple-signed binaries out of `/System` into writable directories or invoked `posix_spawn()` directly against entitled `/usr/libexec/` daemons with attacker-controlled environment variables and command-line flags, hijacking authentic Apple signatures outside their intended `launchd` execution hierarchy [40, 211].

Fourth, at the software-distribution layer, Apple confronts a structural tension between locked-down pocket appliances and open UNIX developer workstations [54, 55]. On `iPhone`, `iPad`, `Apple Watch`, and `Apple Vision Pro`, eliminating commodity ransomware and trojanized installers motivates mandatory pre-distribution cryptographic countersigning by Apple, whether through global `App Store` `FairPlay` encryption [212] or, inside the European Union under Article 6(4) of the Digital Markets Act (`DMA`, `Regulation (EU) 2022/1925`) [213], through automated `iOS` Notarization bound to authorized third-party Alternative App Marketplaces [54, 214]. On `macOS`, conversely, an engineer running `clang`, `rustc`, or `go build` on an air-gapped laptop must be able to execute `./a.out` milliseconds after linking without round-tripping to Apple servers. Apple Silicon `macOS` reconciles those requirements by separating *local code-signing mechanics* (requiring every native `arm64` Mach-O image to carry at least an ad-hoc linker-generated `CS_CodeDirectory` so the virtual memory pager always has per-page `SHA-256` digests) from *provenance policy* (`Quarantine.kext` extended attributes, `syspolicyd` `Gatekeeper` evaluation, `Developer ID` certificates, and `CloudKit` Notarization tickets gating internet-sourced software) [55, 208, 215].

## Silicon & System Mechanics

### Mach-O LC_CODE_SIGNATURE SuperBlobs and CS_CodeDirectory Special Slots

Every native Apple Silicon executable, framework, bundle, and `.dylib` carries an `LC_CODE_SIGNATURE` load command (`cmd = 0x1d` in `EXTERNAL_HEADERS/mach-o/loader.h`) whose `dataoff` and `datasize` fields locate an embedded signature structure at the end of the `__LINKEDIT` segment [39, 212]. Defined in `osfmk/kern/cs_blobs.h` and `OSX/libsecurity_codesigning`, that region opens with a network-byte-order (big-endian) `CS_SuperBlob` header carrying magic `CSMAGIC_EMBEDDED_SIGNATURE` (`0xfade0cc0`), total byte length, and an array of `CS_BlobIndex` `(type, offset)` descriptors pointing to self-describing `CS_GenericBlob` payloads [39, 208, 216].

Rather than computing a single monolithic digest over the whole file (the design used by classic Windows `PE` `Authenticode`, which forces eager whole-file reads before the first instruction can run unless optional `/ph` page hashes are attached), Apple's `CS_CodeDirectory` (`CSMAGIC_CODEDIRECTORY = 0xfade0c02`, indexed at `CSSLOT_CODEDIRECTORY = 0` with optional agility digests in `CSSLOT_ALTERNATE_CODEDIRECTORIES = 0x1000..0x1004`) partitions the `Mach-O` slice from file offset `0` up to `codeLimit` (or 64-bit `codeLimit64` in version `0x20300+`) into contiguous `4096`-byte (`pageSize = 12`, $2^{12} = 4\text{ KB}$) code pages [39, 208]. Immediately preceding positive code-page hash slot `0` in memory sits a negative-indexed array of *special metadata slots* growing downward from `-1` to `-nSpecialSlots`:

$$\text{CS\_CodeDirectory} = \bigl[\underbrace{h_{-11}, \dots, h_{-7}, \dots, h_{-1}}_{\text{negative metadata slots}}\;\big\|\;\underbrace{h_{0}, h_{1}, \dots, h_{P-1}}_{\text{4 KB Mach-O page digests}}\bigr], \qquad \text{CDHash} = \text{Trunc}_{160}\bigl(\text{SHA-256}(\text{CS\_CodeDirectory})\bigr)$$

The canonical identity of every signed binary across `XNU`, `TXM`, `EndpointSecurity`, and `Notarization` tickets is its `CDHash`: the first 20 bytes (`CS_CDHASH_LEN = 20`) of the `SHA-256` (`CS_HASHTYPE_SHA256 = 2`) digest computed over the serialized `CS_CodeDirectory` header and its entire negative-plus-positive hash table [39, 208]. Because both the metadata digests and the 4 KB code digests live inside `CS_CodeDirectory`, altering a single byte of `Info.plist`, bundle assets, entitlements, or launch constraints changes the `CDHash` just as surely as patching an `arm64` instruction inside `__TEXT`.

![Figure: Mach-O LC_CODE_SIGNATURE SuperBlob layout indexing negative metadata slots (-1 through -11) and positive 4 KB page digests bound into the canonical 20-byte CDHash.](diagrams/06-extra-macho-superblob-slots.svg)

Each negative slot inside `CS_CodeDirectory` seals a distinct component of the bundle or execution contract (`osfmk/kern/cs_blobs.h`) [39, 208]. Slot `-1` (`CSSLOT_INFOSLOT`) hashes the bundle's `Info.plist` so bundle identifiers and privacy usage descriptions cannot be swapped post-signing. Slot `-2` (`CSSLOT_REQUIREMENTS`, `CSMAGIC_REQUIREMENTS = 0xfade0c01`) hashes internal *Code Signing Requirements* (`csreq` bytecode expressions such as `anchor apple generic and identifier "com.example.app" and certificate leaf[field.1.2.840.113635.100.6.1.9]`, documented in `TN3127`) [217]. Slot `-3` (`CSSLOT_RESOURCEDIR`) hashes `_CodeSignature/CodeResources`, an XML/plist manifest of SHA-256 digests covering non-code bundle files (nib/storyboard layouts, icons, localized strings, metallib shaders), while slot `-4` (`CSSLOT_APPLICATION`) and slot `-6` remain reserved or `DiskImages`-specific [208, 216].

Slots `-5` and `-7` capture one of Apple's most consequential parser-hardening migrations [39, 208]. Historically, `CSSLOT_ENTITLEMENTS` (`slot -5`, `CSMAGIC_EMBEDDED_ENTITLEMENTS = 0xfade7171`) stored entitlements solely as a human-readable XML property list. Repeated exploitable parser differentials between user-space `CoreFoundation` XML deserializers and kernel `OSUnserializeXML` / `IOCFUnserialize` (where duplicate dictionary keys, XML entity tricks, or comment blocks caused `amfid` and `XNU` to see *different* entitlement values from the exact same blob) drove Apple to introduce `CSSLOT_DER_ENTITLEMENTS` (`slot -7`, `CSMAGIC_EMBEDDED_DER_ENTITLEMENTS = 0xfade7172`), encoding entitlements in canonical `ITU-T X.690` `ASN.1` Distinguished Encoding Rules (`DER`) [36, 39]. Canonical `DER` enforces a unique byte representation per key-value tree and enables non-allocating, deterministic verification directly inside `CoreTrust` and `TXM` (`csblob_get_der_entitlements`) [36, 218]. Slots `-8`, `-9`, `-10`, and `-11` (`CSSLOT_LAUNCH_CONSTRAINT_SELF`, `PARENT`, `RESPONSIBLE`, and `CSSLOT_LIBRARY_CONSTRAINT`, each carrying magic `CSMAGIC_EMBEDDED_LAUNCH_CONSTRAINT = 0xfade8181`) extend that exact `DER` discipline to `Launch Constraints` and library-loading rules [39, 219]. Rounding out the `CS_SuperBlob` at high indices are `CSSLOT_SIGNATURESLOT` (`0x10000`, `CSMAGIC_BLOBWRAPPER = 0xfade0b01` wrapping an `RFC 5652` `CMS` / `PKCS#7` `SignedData` cryptographic signature over the `CDHash` for non-trust-cached binaries) and `CSSLOT_TICKETSLOT` (`0x10002`, carrying a stapled Apple Notarization ticket) [39, 220].

### Lazy vm_fault Page-In Verification and Process cs_flags State

During `execve()`/`posix_spawn()` (for a main binary) or `dyld` shared-library mapping (`fcntl(fd, F_ADDFILESIGS_RETURN, ...)` and `F_CHECK_LV`), `XNU` registers the `CS_SuperBlob` onto the file's `ubc_info` (`bsd/kern/ubc_subr.c!ubc_cs_blob_add`) and validates the `CDHash` anchor, `execSegBase`/`execSegLimit` executable segment bounds (`CodeDirectory` version `0x20400+`), and entitlement constraints [39, 221]. Crucially, `XNU` does *not* read and hash all megabytes of `__TEXT` eagerly at launch. Instead, `osfmk/vm/vm_fault.c` enforces code integrity *lazily on every demand page fault* [207, 221].

![Figure: Mach-O CS_CodeDirectory verification across Static Trust Caches, Dynamic Trust Caches, TXM/CoreTrust CMS evaluation, and lazy vm_fault per-page SHA-256 enforcement.](diagrams/06-txm-trustcache-pipeline.svg)

When a thread fetches an instruction from an unmapped virtual page (or attempts to map a file-backed page with `VM_PROT_EXECUTE`), the pager brings the physical frame into memory from `APFS` while keeping it unmapped from user space, invokes `cs_validate_page()` / `cs_validate_range()` (`bsd/kern/ubc_subr.c`) across the four 4 KB `CS_CodeDirectory` hash slots corresponding to a 16 KB Apple Silicon physical page, and checks exact `SHA-256` equality [207, 221]. On `SPTM`-equipped silicon (`A15+` / `M2+`, [Chapter 4](04-silicon-memory-safety.md)), `XNU` cannot mark page-table descriptors executable directly; `TXM` (`GL0`) verifies the page digests against the immutable `CS_CodeDirectory` stored in `TXM` memory before `SPTM` (`GL2`, `osfmk/arm64/sptm/sptm.h`) transitions the physical frame's type to `XNU_USER_EXEC` (or `XNU_USER_JIT` exclusively when `CS_EXECSEG_JIT` and `MAP_JIT` entitlements permit) [35, 222]. If a single byte on disk or in an external storage medium fails its slot digest during `vm_fault`, the kernel response is governed by the process's `cs_flags` bitmask (`osfmk/kern/cs_blobs.h` and `bsd/sys/codesign.h`) [39, 218]:

| Flag Constant (`cs_blobs.h`) | Hex Value | Kernel & Runtime Enforcement Semantics |
|---|---|---|
| `CS_VALID` | `0x00000001` | Process code signature and all pages faulted in thus far remain dynamically valid |
| `CS_ADHOC` | `0x00000002` | Image carries a `CS_CodeDirectory` (`CDHash`) without an X.509 cryptographic `CMS` signer |
| `CS_FORCED_LV` / `CS_REQUIRE_LV` | `0x00000010` / `0x00002000` | Enforces Library Validation (`F_CHECK_LV`): `dyld` may map only platform dylibs or dylibs sharing the main binary's `TeamID` |
| `CS_HARD` | `0x00000100` | Refuses to map invalid pages into the address space and blocks transitions that would clear `CS_VALID` |
| `CS_KILL` | `0x00000200` | Delivers immediate uncatchable `SIGKILL` (`CODESIGNING` exit reason, setting `CS_KILLED = 0x01000000`) if `CS_VALID` clears |
| `CS_RESTRICT` | `0x00000800` | Instructs `dyld` and task-port gates to strip untrusted `DYLD_*` environment variables and block debugging attaches |
| `CS_ENFORCEMENT` | `0x00001000` | Enforces mandatory page-in `SHA-256` validation and blocks unsigned executable mappings (`W^X`) |
| `CS_RUNTIME` | `0x00010000` | Activates `macOS` Hardened Runtime (`W^X`, `CS_REQUIRE_LV`, task-port lock, `DYLD_*` stripping unless relaxed by explicit runtime entitlements) |
| `CS_LINKER_SIGNED` | `0x00020000` | Marks ad-hoc `CS_CodeDirectory` emitted automatically at build time by `ld` on Apple Silicon `macOS` |
| `CS_PLATFORM_BINARY` | `0x04000000` | Identifies first-party Apple OS binaries anchored via Static or Loaded Trust Caches |

On `iOS`, `iPadOS`, `watchOS`, and `visionOS`, `CS_ENFORCEMENT`, `CS_HARD`, `CS_KILL`, and `CS_REQUIRE_LV` are enforced system-wide across all processes (save only active Xcode debug sessions attached via `CS_DEBUGGED = 0x10000000` under a personalized Developer Disk Image) [36, 39]. On `macOS`, opting into `CS_RUNTIME` (`codesign --options runtime`, mandatory for Apple Notarization) brings third-party `Developer ID` apps up to that same bar unless the developer explicitly signs narrow relaxation entitlements such as `com.apple.security.cs.allow-jit` or `com.apple.security.cs.disable-library-validation` [55, 223]. User-space daemons query peer signing flags and validation categories safely without PID races through `csops_audittoken(pid, CS_OPS_STATUS, ...)` and `CS_OPS_VALIDATION_CATEGORY` (`bsd/sys/codesign.h`) [218].

### Static vs. Engineering/Loaded Trust Caches in TXM (GL0)

Validating an `RFC 5652` `CMS` signature, `X.509` certificate chain, and `OCSP`/CRL revocation state on every `execve()` of `/bin/sh` or `/usr/libexec/logd` would waste milliseconds of CPU time and expose complex `ASN.1` certificate parsers on every system boot path. Apple therefore strips embedded `CMS` certificates out of first-party OS binaries altogether and compiles their 20-byte `CDHash` digests into *Trust Caches* (`osfmk/kern/trustcache.h`) [36, 224].

In `XNU`'s `trust_cache_module1` binary layout (and extended `TXM` v2 structures), a trust cache comprises a `version` word, a 128-bit `uuid`, `num_entries`, and a strictly lexicographically sorted array of packed 22-byte `trust_cache_entry1` records (`uint8_t cdhash[20]`, `uint8_t hash_type`, and `uint8_t flags` such as `CS_TRUST_CACHE_AMFID = 0x1`), allowing `TXM` to resolve any first-party binary's authenticity in $O(\log N)$ binary-search comparisons with zero asymmetric cryptography [224]. Apple partitions these tables by lifecycle [36, 224]. The *Static Trust Cache* sits compiled inside the `Image4`-personalized `BootKC` (`ltrs` / kernelcollection payload verified by `iBoot` in [Chapter 1](01-secure-boot.md)), covering every executable and shared cache shipped on the immutable `Signed System Volume`. *Loaded* (or Dynamic and Engineering) *Trust Caches* (`rtsc`, `scrt`, and `Cryptex1` trust-cache `Image4` payloads) are loaded at runtime exclusively when accompanied by a valid `TSS`-personalized `IM4M` manifest signed by Apple (or local `SEP` `OIHR` under Mac `Reduced Security`), authorizing out-of-band `Rapid Security Response` / `Safari` `Cryptexes`, Xcode `Personalized Developer Disk Images` (`DDI`s), and internal engineering builds [36, 224].

Moving Trust Cache custody from `AMFI` (`EL1`) into `TXM` (`GL0`) closed one of the most reliable post-exploitation techniques in `iOS` jailbreak history [35, 36]. Prior to `SPTM`/`TXM`, loaded trust caches were linked into an `EL1` kernel list inside normal `kalloc` memory; once an exploit such as `CVE-2022-42827` achieved arbitrary kernel read/write, it walked the dynamic trust-cache chain, appended the 20-byte `CDHash` of an unsigned root shell, and spawned post-exploitation binaries freely [210]. Under `SPTM` and `TXM`, both the Static Trust Cache and all Loaded Trust Cache slots reside inside `SPTM`-typed `TXM` physical memory frames unreadable or unwritable by `XNU` at `EL1`: registering a new loaded trust cache requires `TXM` itself (`GL0`) to verify the `Image4` RSA/ECDSA/ESS signature inside isolated memory [35, 36, 222]. Only when a binary's `CDHash` misses every Trust Cache does evaluation invoke `CoreTrust.kext` / `TXM` and user-space `amfid` (or `syspolicyd` on `macOS`) to parse the `CMS` `SignerInfo`, determine its `CS_VALIDATION_CATEGORY_*` (`1 = PLATFORM` through `6 = DEVELOPER_ID` and `7 = LOCAL_SIGNING`), and cross-check requested `DER` entitlements against an `embedded.mobileprovision` provisioning profile (`TN3125`) [36, 39, 209].

### Launch Constraints and Environment Constraints (lwcr DER Predicates)

Even after `TXM` prevented `EL1` trust-cache tampering, attackers still exploited a purely architectural gap: a valid `CDHash` in the Static Trust Cache proved *what* binary was launching, not *who* was allowed to launch it or *where* in the process tree it belonged [40, 211]. After achieving initial user-space RCE or a kernel bug (`CVE-2022-42827` [210]), exploits routinely invoked `posix_spawn()` directly on genuine Apple-signed system daemons or XPC helpers (passing crafted arguments, file descriptors, or mounted disk paths) to abuse their private entitlements [40, 211].

Introduced in `iOS 16` and `macOS Ventura 13` (and expanded with third-party `LWCR` support and Library Constraints in `iOS 17` / `macOS Sonoma 14`), *Launch Constraints* and *Environment Constraints* attach mandatory boolean execution contracts to binaries (`Lightweight Code Requirements`, or `lwcr`, `CSMAGIC_EMBEDDED_LAUNCH_CONSTRAINT = 0xfade8181`) [40, 219, 225]. For first-party OS binaries, Apple pre-compiles launch constraint categories directly alongside trust-cache metadata so an attacker cannot strip them even by copying `/usr/libexec/systemmigrationd` to `/tmp`; third-party developers embed `DER`-encoded `lwcr` blobs in `CS_CodeDirectory` slots `-8` through `-11` via Xcode's `Launch Constraint` property lists [39, 225].

When Process $A$ invokes `posix_spawn()` or `execve()` on executable $B$ under responsible process $R$, `TXM`/`AMFI` executes a small non-Turing-complete stack/state-machine query VM over `DER`-encoded `$and`, `$or`, and `$in` operators (`defining-launch-environment-and-library-constraints`) against four fact dictionaries [211, 219]:

$$\text{PermitExec}(A \to B \mid R) \iff C_{\text{self}}(B) \;\land\; C_{\text{parent}}(A) \;\land\; C_{\text{responsible}}(R) \;\land\; C_{\text{spawn}}(A \to B)$$

Each constraint dictionary tests kernel-verified facts including `validation-category` (`1` for `Platform`, `2` for `TestFlight`, `3` for `Development`, `4` for `App Store`, `5` for `Enterprise`, `6` for `Developer ID`), `signing-identifier`, `team-identifier`, `is-init-proc` (`PID 1` `launchd`), `is-sip-protected`, `launch-type` (`psa_launch_type`, such as `CS_LAUNCH_TYPE_SYSTEM_SERVICE = 1` or `CS_LAUNCH_TYPE_SYSDIAGNOSE = 2`), and arbitrary `entitlements` keys [39, 211, 219]. Because nearly every privileged Apple LaunchDaemon now carries `parent-constraint: { is-init-proc: true }` and `self-constraint: { on-authorized-authapfs-volume: true }` (requiring execution directly off the sealed `SSV` or authorized `Cryptex` mount), attempting to spawn a system daemon from an exploited browser, shell, or `/tmp` copy immediately aborts `posix_spawn()` with `EPERM` and emits a structured `AMFI: Launch Constraint Violation (enforcing)` diagnostic (`c[...]`p[...]m[...]e[...]`) before `dyld` ever maps into the child [331, 340]! Meanwhile, `CSSLOT_LIBRARY_CONSTRAINT` (`slot -11`) solves a long-standing `macOS` developer dilemma: instead of setting `com.apple.security.cs.disable-library-validation` (which dangerously opens `dlopen()` to *unsigned* attacker `.dylib` injection!), an app can keep strict Library Validation active while explicitly allowlisting partner SDK `TeamID`s in `DER` [219, 223].

## Platform Forks Across Apple OSes

While `CS_CodeDirectory`, `DER` entitlements, `TXM` page-fault hashing, and `lwcr` Launch Constraints form one identical kernel substrate from `Apple Watch` to `Mac Studio`, third-party software admission diverges along three distinct policy tracks [36, 54, 55].

![Figure: Software admission fork across Launch Constraints for system daemons, App Store and EU DMA Notarization on iOS, and Gatekeeper Quarantine plus Notary tickets on macOS.](diagrams/06-launch-constraints-vs-gatekeeper.svg)

On global `iOS`, `iPadOS`, `watchOS`, and `visionOS`, third-party applications distributed through the `App Store` arrive encrypted under *FairPlay DRM*: the `Mach-O` header includes `LC_ENCRYPTION_INFO_64` (`cmd = 0x2c` in `mach-o/loader.h`) marking an encrypted `__TEXT` range (`cryptoff`, `cryptsize`, `cryptid = 1`) wrapped per-account, while `CS_CodeDirectory` records `preEncryptOffset` hashes over the plaintext pages so `XNU`/`AppleFairPlayTextCrypter` decrypts pages on demand and `TXM` still verifies the developer-and-App-Store-signed plaintext `SHA-256` slots (`CS_VALIDATION_CATEGORY_APP_STORE = 4`) [36, 39, 212]. Non-Store code executes only when paired with an Apple-signed `CMS` `embedded.mobileprovision` profile (`CS_VALIDATION_CATEGORY_DEVELOPMENT = 3`, `TESTFLIGHT = 2`, or `ENTERPRISE = 5`) binding allowed `DER` entitlements to provisioned hardware `UDID`/`ECID` lists (`TN3125`) [209].

In the European Union (`iOS 17.4+` and `iPadOS 18+`), compliance with the EU Digital Markets Act (`Regulation (EU) 2022/1925`) introduced a dedicated *Alternative App Marketplace and iOS Notarization* track without disabling `TXM` or `CoreTrust` [54, 213, 214]. Marketplace operators approved under the `com.apple.developer.marketplace.app-installation` entitlement build distribution clients atop `MarketplaceKit`; third-party developers submit app builds via `App Store Connect` for *iOS Notarization*, an automated static/dynamic malware scan plus baseline human safety check verifying absence of known malware, sandbox escapes, or deceptive identity prompts rather than App Store content rules [54, 214]. Upon passing Notarization, Apple encrypts and countersigns an installation package cryptographically bound to the target Marketplace's certificate, and on-device `CoreTrust`, `installd`, and `countryd` (which fuses SIM MCC, Apple Account billing country, and coarse local device signals inside a privacy-preserving evaluation) verify EU eligibility before admitting the binary [54, 214].

On `macOS`, by contrast, Apple Silicon requires every native `arm64` binary to possess at least an ad-hoc `CS_CodeDirectory` (`CS_ADHOC | CS_LINKER_SIGNED`, emitted automatically by `ld` so locally compiled developer tools run offline under `CS_VALIDATION_CATEGORY_LOCAL_SIGNING = 7`), while gating downloaded software via *Quarantine* and *Gatekeeper* (`syspolicyd`) [39, 55]. Whenever a browser, mail client, chat app, or `Archive Utility` writes a file originating from an external source, `Quarantine.kext` / `LaunchServices` attaches the `com.apple.quarantine` extended attribute (`flags;timestamp;agent_name;UUID`). When a user launches a quarantined binary (and continuously across subsequent launches or bundle mutations since `macOS Ventura 13`, where `syspolicyd` caches vnode state and re-verifies `CodeResources` if any file inside an opened `.app` bundle is modified post-launch!), `Gatekeeper` requires a valid `Developer ID Application` signature (`CS_VALIDATION_CATEGORY_DEVELOPER_ID = 6`), `CS_RUNTIME` Hardened Runtime, absence of `XProtect` YARA/certificate revocations, and a cryptographic *Notarization Ticket* (`CSSLOT_TICKETSLOT` stapled offline via `xcrun stapler` or queried online from Apple's `CloudKit` ticket ledger) [55, 208, 215]. Furthermore, `macOS Sequoia 15` (`2024+`) retired the Finder Control-click *Open* shortcut that commodity stealers (`AMOS`) socially engineered victims into clicking, forcing explicit administrator confirmation inside *System Settings $\to$ Privacy & Security* (and emitting `ES_EVENT_TYPE_NOTIFY_GATEKEEPER_USER_OVERRIDE` to enterprise EDR sensors) [55, 215].

## In-the-Wild Failures & Architectural Bounds

Cryptographic code signing proves *immutability and signer provenance* from the moment a `CS_CodeDirectory` was sealed; it cannot guarantee that complex `ASN.1`/`CMS` containers are parsed unambiguously, that extended attributes survive archive extraction bugs, or that a freshly compiled binary submitted by a rogue `Developer ID` holder is benign.

| Case / Mechanism | Year | Platform Scope | Boundary Tested | Root Cause | Architectural Response |
|---|---|---|---|---|---|
| `Fugu14` `CoreTrust` Slice Confusion (`CVE-2021-30869`) | 2021 | `iOS` & `macOS` | `CoreTrust` `Mach-O` fat/slice validation | Parser mismatch between `XNU` loader and `CoreTrust` `arm64` slice/blob offsets granted App Store trust to untrusted code | Hardened `CoreTrust` Mach-O fat-header and `CS_CodeDirectory` offset bounds [226] |
| `XNU` OOB Write + Trust Cache Patching (`CVE-2022-42827`) | 2022 | `iOS` & `iPadOS` (`< 16.1`) | In-kernel `EL1` dynamic trust cache & `cs_flags` | Actively exploited `XNU` out-of-bounds write let attackers corrupt kernel state and spawn arbitrary post-exploit helpers on pre-`TXM` devices | Migrated trust caches into `SPTM`-isolated `TXM` (`GL0`) and deployed OS-wide `Launch Constraints` [36, 210] |
| *Achilles* `Gatekeeper` ACL Bypass (`CVE-2022-42821`) | 2022 | `macOS` (`< 13.0`) | `com.apple.quarantine` propagation across `.zip` archives | AppleDouble (`._`) metadata inside a crafted `.zip` applied a restrictive NFSv4 ACL (`deny writeextattr`) that blocked `Safari` from writing `com.apple.quarantine` | Patched `Archive Utility` / `Quarantine` ACL handling so quarantine xattrs cannot be suppressed by archive metadata [227] |

### CoreTrust Multi-Signer CMS Ambiguity (CVE-2023-41991)

Linus Henze's discovery of `CVE-2021-30869` (`Fugu14`) and the subsequent `CVE-2023-41991` flaw weaponized by `TrollStore` across `iOS 14.0` through `17.0` demonstrate why cryptographic envelope complexity inside `EL1`/`GL0` is a primary TCB hazard [220, 226]. Because `RFC 5652` `CMS` `SignedData` (`CSSLOT_SIGNATURESLOT = 0x10000`) permits a `SET OF SignerInfo` structures to support co-signed S/MIME documents, an attacker extracted a genuine Apple-signed `CMS` blob from an inbox binary and appended a *second*, self-signed `SignerInfo` whose signed attributes (`1.2.840.113635.100.9.1` / `1.2.840.113635.100.9.2` plist and `CDHash` bags) pointed to the attacker's own modified `CS_CodeDirectory` carrying arbitrary `com.apple.private.*` `DER` entitlements (`slot -7`) [39, 220, 226]. During verification, `CoreTrust` confirmed that at least one `SignerInfo` chained cleanly to Apple's Root CA, yet extracted the `CDHash` list from the unverified co-signer structure, admitting permanently signed, arbitrarily entitled root helpers onto stock iPhones without a kernel exploit until patched in `iOS 16.7` and `17.0.1` [226].

### Gatekeeper Quarantine Stripping: Achilles (CVE-2022-42821) and CVE-2023-27943

On `macOS`, `Gatekeeper`'s historic reliance on the presence of the `com.apple.quarantine` extended attribute created an asymmetric failure mode: if an archive format prevented `com.apple.quarantine` from sticking to extracted files, `syspolicyd` treated an internet payload like a locally compiled developer binary [55, 227]. In *Achilles* (`CVE-2022-42821`, discovered by Jonathan Bar Or at Microsoft Threat Intelligence), an attacker packaged a malicious `.app` inside a `.zip` archive alongside an AppleDouble (`._`) resource-fork metadata entry bearing a crafted NFSv4 Access Control List (`deny writeextattr`) [227]. When `Archive Utility` extracted the `.app`, it faithfully restored the restrictive ACL *before* propagating `Safari`'s `com.apple.quarantine` attribute; the ACL blocked `setxattr()` silently, leaving an unsigned, unnotarized payload ready to execute on double-click without any `Gatekeeper` prompt [227]. Following *Achilles* and `CVE-2023-27943` (`macOS 13.3`), Apple both hardened quarantine propagation inside kernel/archive paths and expanded `syspolicyd` + `XProtect` hooks so even unquarantined executables undergo signature and malware evaluation on `execve()` [55, 228].

## Verification & Forensic Artifacts

Inspect a binary's `CS_SuperBlob` layout, `CodeDirectory` version (`v=20400` or `20500`), negative-plus-positive slot counts (`hashes=N+7` or `+11`), `flags` (`0x10000(runtime)` for `CS_RUNTIME`), `CDHash`, and `DER` entitlements (`slot -7`) via `codesign` [39, 208]:

```bash
codesign -dvvv /System/Applications/Calculator.app
codesign -d --entitlements :- --der /System/Applications/Calculator.app 2>/dev/null | xxd | head -n 6
```

Representative output showing `arm64e`, negative special slots (`+7`), `CDHash`, and platform provenance:

```text
Executable=/System/Applications/Calculator.app/Contents/MacOS/Calculator
Format=app bundle with Mach-O thin (arm64e)
CodeDirectory v=20400 size=5840 flags=0x0(none) hashes=174+7 location=embedded
CDHash=6a91e84b2c7109d3f41a...
```

Dump embedded or trust-cache-associated `Launch Constraints` (`--launch-constraints`) on a system daemon and monitor Unified Logging for `AMFI: Launch Constraint Violation` events [40, 225]:

```bash
codesign -d --launch-constraints :- /usr/libexec/securityd 2>/dev/null | head -n 10
log show --last 15m --predicate 'eventMessage CONTAINS "Launch Constraint Violation"' --style compact | tail -n 4
```

Verify `com.apple.quarantine` extended attributes, `Gatekeeper` (`syspolicyd`) policy evaluation, and stapled `CSSLOT_TICKETSLOT` Notarization tickets on `macOS` [55, 215]:

```bash
xattr -p com.apple.quarantine /Applications/*.app 2>/dev/null | head -n 3
spctl -a -t exec -vv /System/Applications/Calculator.app 2>&1
xcrun stapler validate /Applications/*.app 2>/dev/null | head -n 3
```

Once `TXM`, `Launch Constraints`, and `Notarization` admit an executable into `EL0` memory, code signing's cryptographic guarantee ends: a legitimately signed browser renderer (`WebContent`) or messaging daemon (`imagent`) still ingests untrusted network bytes every second. [Chapter 7](07-ipc-seatbelt-blastdoor.md) examines how `Mach` task ports, `XPC` `audit_token_t` trailers, `Seatbelt` `MACF` bytecode profiles, `IOKit` user-client filters, `JavaScriptCore` cages, and `BlastDoor` contain compromised processes after launch.
