# macOS Privacy Governance, TCC, and System Extensions

## Overview

* **Link in the Chain:** Workstation privacy-consent, persistence-governance, and kernel-deprivileging layer closing Part II; mediates how un-sandboxed `macOS` processes touch user files and sensors (`TCC`), audits background `launchd` persistence (`BTM`), and relocates third-party kernel drivers into `EL0` `SystemExtensions`.
* **Core Security Invariant:** Access to `TCC`-governed user data or hardware (`Full Disk Access`, `ScreenCapture`, `Camera`, `Microphone`, `AppleEvents`) succeeds if and only if `tccd` matches the `responsible_pid`'s live signature against an authorized `csreq` entry in `SIP`-/`UF_DATAVAULT`-sealed `TCC.db` (or a supervised `MDM` `PPPC` profile), while third-party hardware, network, and security extensions run in `EL0` (`DriverKit`, `NetworkExtension`, `EndpointSecurity`) rather than `EL1`.
* **Platform Matrix:** Dual-database `TCC` with `responsible_pid` UNIX tree inheritance, `AppleEvents` automation, `Background Task Management` (`BTM`), and full `SystemExtensions` are architecturally centered on `macOS`; `iOS`, `watchOS`, and `visionOS` rely on per-app sandboxes and out-of-process pickers (`PHPickerViewController`), while `DriverKit` forks selectively onto `M`-series `iPadOS 16+` for USB, PCIe, and audio hardware.
* **Trusted Computing Base (TCB):** System (`root`) and per-user `tccd` daemons, `UF_DATAVAULT`-protected `TCC.db` SQLite databases, `XNU` `responsibility` tracking (`responsibility_get_pid_responsible_for_pid`), `Sandbox.kext` / `WindowServer` / `appleeventsd` hooks, `backgroundtaskmanagementd`, `sysextd`, `IOUserServer`, and `AppleDART` IOMMU mappings.
* **Failure Horizon & Handoff:** Inherited `responsible_pid` trust across consented apps/terminals, missing Library Validation (`CVE-2023-26818`), donor bundle hijacking (*XCSSET* `CVE-2021-30713`), mutable config swaps (`HM Surf` `CVE-2024-44133`), and ambient accessibility daemons (`CVE-2025-43530`) yield recurring confused-deputy `TCC` bypasses; hands off enterprise `EndpointSecurity` telemetry and `iOS` forensic triage to [Chapter 9](09-esf-xprotect-forensics.md).

## Threat Model & Design Tension

On `iOS`, `iPadOS`, `watchOS`, and `visionOS`, mandatory `App Sandbox` containerization ([Chapter 7](07-ipc-seatbelt-blastdoor.md)) solves cross-application file confidentiality at the filesystem namespace root: an unprivileged app inside `/private/var/mobile/Containers/Data/Application/<UUID>` cannot even name another app's documents or `Messages` database in `open()`, and user photos or contacts arrive through out-of-process `XPC` pickers. On `macOS`, however, four decades of POSIX and desktop engineering assume a shared user home directory (`/Users/alice`) inhabited simultaneously by un-sandboxed `Developer ID` GUI apps, package-manager CLI tools (`/opt/homebrew/bin/python3`, `node`, `git`, `curl`), shell scripts, and cross-application `AppleEvents` (`osascript`) workflows [56, 251, 252]. Under classic UNIX discretionary access control (`DAC`), every process spawned by Alice executes with `euid = 501`. Without an additional mandatory layer inside `UID 501`, a trojanized `npm` post-install script, malicious Electron app, or macro-spawned binary immediately inherits silent read/write access to `~/Desktop`, `~/Documents`, `~/.ssh`, `Safari` cookies, `Mail` archives, `Messages` `chat.db`, the FaceTime camera, the microphone, and live `WindowServer` screen buffers [56, 251].

At the same time, `macOS` historically carried two additional desktop-specific exposures absent on locked mobile appliances: silent user-mode persistence and third-party Ring-0 (`EL1`) kernel extensions [57, 253, 254]. Any process running at `UID 501` or `UID 0` could drop a property list into `~/Library/LaunchAgents` or `/Library/LaunchDaemons` to achieve invisible persistence across every reboot without notifying the owner [253, 255]. Worse, hardware vendors, VPN clients, and antivirus products shipped C++ `IOKit` `.kext` binaries, BSD Network Kernel Extensions (`NKE`s), and `Kauth` file listeners directly inside `XNU`'s `EL1` kernel address space: a single use-after-free in a third-party driver panicked the Mac or handed attackers Ring-0 arbitrary read/write, and under Apple Silicon `Full Security` ([Chapter 2](02-mac-localpolicy.md)), loading *any* third-party `.kext` forces the owner to boot `1TR` and downgrade the boot volume group to `Reduced Security` (`AuxKC`) [33, 57, 254].

Apple's workstation architecture resolves these three pressures through three tightly coupled subsystems [56, 57, 253]. *Transparency, Consent, and Control (`TCC`)* partitions `UID 501` authority behind per-service user consent bound to cryptographic code identity (`csreq`). *Background Task Management (`BTM`)* tracks every `LaunchAgent`, `LaunchDaemon`, and `SMAppService` registration in `macOS Ventura` through `Tahoe`, surfacing persistence alerts to the user and telemetry to EDR sensors. *System Extensions* (`DriverKit`, `NetworkExtension`, and `EndpointSecurity`) evict third-party kernel code from `EL1` into sandboxed `EL0` user-space daemons mediated by `Mach` RPC and `AppleDART` IOMMUs [33, 57, 256]. Yet retrofitting app-centric privacy consent onto UNIX `fork()`/`execve()` process trees creates one of the richest confused-deputy surfaces in modern OS design: `responsible_pid` attribution and private Apple `TCC` entitlements [24, 251, 257].

## Silicon & System Mechanics

### Dual TCC Databases, SQLite Schema, and Service Taxonomy

`TCC` splits policy state and enforcement across kernel `MACF` / VFS / `IOKit` interceptors (`Sandbox.kext`, `FileProvider`, `WindowServer`, `coreaudiod`, `appleh13camerad`/`appleh16camerad`, `appleeventsd`) and two distinct instances of the `tccd` policy daemon (`/System/Library/PrivateFrameworks/TCC.framework/Support/tccd`) [56, 251]. A machine-wide *system* instance (`com.apple.tccd.system`, running as `UID 0`) governs global administrative and capture capabilities inside `/Library/Application Support/com.apple.TCC/TCC.db`, while a per-*user* instance (`com.apple.tccd`, running as the logged-in `UID`) governs personal folder, sensor, and automation consents inside `~/Library/Application Support/com.apple.TCC/TCC.db` [56, 251]. Both `TCC.db` SQLite files reside inside kernel-enforced `SIP` and `UF_DATAVAULT` (`com.apple.rootless.storage.TCC`) directories: neither an unprivileged `UID 501` script nor an unconstrained `UID 0` `root` shell can open `TCC.db` to `INSERT` forged grants directly on disk [124, 251, 258].

![Figure: Dual macOS TCC.db scopes (SIP-sealed system tccd.system vs. per-user Data Vault tccd), csreq + responsible_pid evaluation, PPPC MDM overrides, and Background Task Management persistence tracking.](diagrams/08-extra-tcc-database-eval-flow.svg)

Inside each `TCC.db`, the core `access` table binds a `service` string and `client` identifier (`client_type = 0` for bundle ID, `1` for absolute POSIX path) to an `auth_value` (`0 = Denied`, `2 = Allowed`, `3 = Limited`, `4 = Allow Standard User to Set System Service`), an `auth_reason` provenance code, a compiled binary `CodeRequirement` blob (`csreq`), an optional `indirect_object_identifier` + `indirect_object_code_identity` (pinning the *target* application of an `AppleEvents` automation rule), and `last_modified` epoch timestamps [251, 257]. Key `macOS` `TCC` services partition across the two databases as follows [56, 259, 260]:

| TCC Service Key (`kTCCService*`) | `TCC.db` Scope | Primary Enforcer | Supervised MDM `PPPC` Rule (`[364]`) |
|---|---|---|---|
| `SystemPolicyAllFiles` (Full Disk Access) | System (`/Library/...`) | `Sandbox.kext` VFS & Data Vaults | `Allow` or `Deny` permitted via supervised MDM |
| `EndpointSecurityClient` | System (`/Library/...`) | `EndpointSecurity.kext` `es_new_client` | `Allow` or `Deny` permitted via supervised MDM |
| `ScreenCapture` | System (`/Library/...`) | `WindowServer` & `ScreenCaptureKit` | `Deny` or `AllowStandardUserToSetSystemService` only (no silent `Allow`) |
| `Accessibility` / `ListenEvent` | System (`/Library/...`) | `HIServices` / `WindowServer` HID | `Allow` (Accessibility) or `Deny`; blocks silent keylogging |
| `Camera` / `Microphone` | Per-User (`~/Library/...`) | `cmio` / `coreaudiod` + Exclave LED | `Deny` only; MDM *cannot* silently grant Camera or Mic access |
| `SystemPolicyDesktopFolder` (`Documents`, `Downloads`) | Per-User (`~/Library/...`) | `Sandbox.kext` VFS open/readdir | `Allow` or `Deny` permitted via supervised MDM |
| `AppleEvents` | Per-User (`~/Library/...`) | `appleeventsd` Mach message broker | `Allow` or `Deny` scoped to `(client, indirect_object)` pair |

Note Apple's deliberate anti-surveillance constraint inside MDM *Privacy Preferences Policy Control (`PPPC`)* profiles (`com.apple.TCC.configuration-profile-policy`) [56, 259]: even on a corporate-owned, `ADE`-supervised MacBook managed by enterprise IT, an MDM server can pre-authorize `SystemPolicyAllFiles` and `EndpointSecurityClient` for an EDR agent (matching exact `Identifier`, `CodeRequirement`, and `StaticCode` validation), yet MDM is *cryptographically and architecturally forbidden* from silently granting `Camera`, `Microphone`, or `ScreenCapture` (`Allow` payloads are rejected by `tccd`), ensuring a compromised MDM server cannot turn employee laptops into covert room bugs without local consent and hardware Exclave indicator LEDs [56, 259]. Furthermore, `macOS Sequoia 15` (`2024+`) migrated legacy `CGWindowListCreateImage` screen capture toward `ScreenCaptureKit`'s system-drawn content picker and introduced recurring monthly re-confirmation prompts for persistent third-party screen-recording grants [260].

### csreq Verification, Sandbox Extensions, and responsible_pid Attribution

How does `tccd` reconcile app-scoped `Info.plist` consent with UNIX command-line composability? Suppose a developer opens `Terminal.app` (or `iTerm2`, `Xcode`, or `VS Code`), spawns `/bin/zsh`, which invokes `/opt/homebrew/bin/python3 sync.py`, which calls `open("/Users/alice/Documents/roadmap.md", O_RDONLY)`. Bare Mach-O binaries such as `zsh` and `python3` have no `.app` bundle, no `NSDocumentsFolderUsageDescription` plist key, and no distinct UI identity; granting `TCC` directly to `/usr/bin/python3` would silently authorize every piece of malware on the machine to exfiltrate `~/Documents` simply by invoking `python3 -c 'open(...)'` [251, 257]!

![Figure: macOS TCC attribution chain resolving unbundled child CLI processes back to the GUI parent's responsible_pid and CodeRequirement (csreq), illustrating confused-deputy bypass surfaces.](diagrams/08-tcc-attribution-chain.svg)

`XNU` resolves unbundled UNIX descendants through kernel-tracked *process responsibility* (`p_responsible_pid` inside the kernel task/proc ledger, queried by user-space daemons via private `libquarantine` `responsibility_get_pid_responsible_for_pid()` and `responsibility_get_uniqueid_responsible_for_pid()`) [251, 257]. When `LaunchServices` (`launchservicesd` / `xpcproxy`) spawns a bundled GUI application (`Terminal.app`, `PID 1200`), `XNU` sets `PID 1200` as its own responsible process. Across every subsequent `fork()`, `posix_spawn()`, and `execve()` creating `zsh` (`PID 1214`) and `python3` (`PID 1580`), the kernel propagates `responsible_pid = 1200` automatically unless a privileged launcher explicitly invokes `responsibility_spawnattrs_setdisclaim(attr, 1)` (`POSIX_SPAWN_SETDISCLAIM`, used by `sshd-keygen-wrapper` so remote SSH sessions attribute to `sshd-keygen-wrapper` rather than `launchd`) [251, 257].

When `PID 1580` (`python3`) traps into `open("~/Documents/roadmap.md")`, `Sandbox.kext` pauses the VFS open and sends an `XPC` attribution chain upcall to `tccd` containing both the *accessing/requesting* process's `audit_token_t` ($\tau_{\text{req}}$ for `python3`) and the *responsible* GUI process's `audit_token_t` ($\tau_{\text{resp}}$ for `Terminal.app`) [251]:

$$\text{PermitTCC}(\tau_{\text{req}}, \tau_{\text{resp}}, s) \iff \text{VerifyCSReq}\bigl(\tau_{\text{resp}},\, \texttt{TCC.db}[s, \text{client}(\tau_{\text{resp}})].\texttt{csreq}\bigr) \land \bigl(\texttt{auth\_value} = 2\bigr)$$

`tccd` extracts `Terminal.app`'s live code signature via $\tau_{\text{resp}}$ (`pidversion`-safe `SecTaskCreateWithAuditToken`, [Chapter 7](07-ipc-seatbelt-blastdoor.md)), evaluates the stored `csreq` bytecode (`identifier "com.apple.Terminal" and anchor apple`, or `anchor apple generic and certificate leaf[subject.OU] = "<TeamID>"` for third-party apps), prompts the user if undecided, and upon approval issues a kernel `com.apple.tcc.*` sandbox extension token while emitting `ES_SYSCALL_TCC_MODIFY` (`mac-syscall 41` $\to$ `ES_EVENT_TYPE_NOTIFY_TCC_MODIFY`) to `EndpointSecurity` [56, 251]. Crucially, once `Terminal.app` or an IDE holds `auth_value = 2`, *every unbundled child process ever spawned inside its process tree* silently inherits that `TCC` grant!

Two subtle edge cases in `tccd`'s attribution engine explain why desktop automation and remote administration behave counterintuitively under `macOS` [251, 252, 257]. First, inter-application *AppleEvents* (`kTCCServiceAppleEvents`, brokered over Mach IPC by `appleeventsd`) enforce a *directed bipartite graph* rather than a single unary grant: `TCC.db` records `(client, indirect_object_identifier, indirect_object_code_identity)` triples, so granting `Terminal.app` permission to automate `System Events` (`com.apple.systemevents`) does *not* permit `Terminal.app` to send `kAEDoScript` (`do JavaScript`) events to `Safari` or `Google Chrome` without a separate per-target prompt backed by `NSAppleEventsUsageDescription` in the caller's `Info.plist` [252, 257]. Second, incoming remote `OpenSSH` logins cannot inherit a local GUI app's `responsible_pid`: Apple wraps `sshd` inside `/usr/libexec/sshd-keygen-wrapper`, which calls `responsibility_spawnattrs_setdisclaim()` so remote SSH sessions attribute directly to `sshd-keygen-wrapper` (requiring an administrator to explicitly toggle Full Disk Access for `sshd-keygen-wrapper` or Remote Login before an SSH session can read `TCC`-protected user directories) [251, 257]. Meanwhile, `tccd` must also defend against symlink and hardlink path aliasing at the VFS layer: because `~/Documents` and `~/Desktop` are protected by path/inode container metadata rather than per-file encryption keys, creating hardlinks prior to folder migration or swapping directory symlinks during `tccd` path canonicalization repeatedly tested the boundary between VFS lookup and user-space `tccd` verdict caching [24, 251].

### Background Task Management (BTM) in macOS Ventura through Tahoe

Prior to `macOS Ventura 13` (`2022`), persistence on `macOS` operated completely outside user consent: any un-sandboxed process running as `UID 501` could write a LaunchAgent plist into `~/Library/LaunchAgents/` (which is deliberately *not* `TCC`-protected so legitimate updaters function), achieving silent code execution on every login [253, 255]. To close that visibility gap, Apple overhauled *Background Task Management (`BTM`)* under `/System/Library/CoreServices/backgroundtaskmanagementd`, maintaining a binary/keyed-archive persistence ledger under `/private/var/db/com.apple.backgroundtaskmanagement/` (`BackgroundItems-v*.btm`) [253, 255, 261].

Whether an application registers a modern login item, agent, or root helper via `SMAppService` (`macOS 13+`) or drops a legacy `.plist` directly into `~/Library/LaunchAgents`, `/Library/LaunchAgents`, or `/Library/LaunchDaemons`, `backgroundtaskmanagementd` intercepts the registration via `launchd`/`smd` XPC coordination and `FSEvents` directory watches, resolves the binary's `CS_CodeDirectory` `TeamID` and parent `.app` bundle via `Security.framework`, displays an immediate banner alert (*"Background Items Added: [App/Developer] added items that can run in the background"*), exposes a per-developer kill-switch inside *System Settings $\to$ General $\to$ Login Items & Extensions*, and invokes `ES_SYSCALL_BTM_LAUNCH_ITEM_ADD` (`mac-syscall 20`) so enterprise EDR sensors receive an immediate `ES_EVENT_TYPE_NOTIFY_BTM_LAUNCH_ITEM_ADD` event [253, 255]. Internally, each `BTM` item record tracks its `Disposition` bitmask (`enabled`, `allowed`, `visible`, `notified`), container bundle `Bookmark` data (resolved across APFS document IDs via `APFSIOC_DOC_ID_TO_FILE_ID` so renaming an app bundle does not orphan its associated `LaunchAgent`), and parent `Developer Name` extracted directly from the leaf `Developer ID` X.509 certificate [253, 261]. For enterprise fleets on supervised Macs, MDM administrators deploy `com.apple.servicemanagement` (`ManagedLoginItems`) payloads to lock critical security-agent `LaunchDaemons` and `SMAppService` helpers into an always-enabled state that local standard or administrative users cannot toggle off in System Settings [253, 262]. When early `Ventura` builds suffered race and plist-desynchronization flaws in `backgroundtaskmanagementd` that let malware register items while suppressing the user banner (`CVE-2023-32364`, analyzed by Patrick Wardle), Apple tightened `launchd`-to-`BTM` handshakes so `launchd` refuses to bootstrap unapproved legacy plists before `BTM` commits the ledger entry [255, 263].

### SystemExtensions: DriverKit (.dext) User-Space IOKit RPC and NetworkExtension

While `TCC` and `BTM` govern user-space privacy and persistence, `SystemExtensions.framework` (`sysextd`) eliminates third-party code from `XNU` Ring 0 (`EL1`) [57, 254]. Packaged inside `/Applications/<App>.app/Contents/Library/SystemExtensions/`, signed with `com.apple.developer.system-extension.install`, and staged by `sysextd` into `SIP`-protected `/Library/SystemExtensions/<UUID>/` after interactive administrator approval (or silent supervised MDM `com.apple.system-extension-policy` authorization), System Extensions replace all three legacy `.kext` categories while keeping Apple Silicon Macs in `Full Security` [57, 262].

![Figure: Architectural migration from legacy EL1 IOKit kernel extensions (requiring 1TR Reduced Security) to EL0 sandboxed DriverKit, NetworkExtension, and EndpointSecurity System Extensions under Full Security.](diagrams/08-kext-to-driverkit-migration.svg)

First, *DriverKit* (`.dext` bundles across `USBDriverKit`, `PCIDriverKit`, `NetworkingDriverKit`, `HIDDriverKit`, `AudioDriverKit`, and `BlockStorageDeviceDriverKit`) relocates hardware device drivers into isolated, unprivileged (`_driverkit` UID) `EL0` processes [33, 256, 264]. Developers write C++ classes derived from `DriverKit::IOService` and `DriverKit::IOUserClient` using `.iig` (`IOKit Interface Generator`) definitions; the `.iig` compiler automatically generates dual serialization stubs so methods marked `LOCALONLY` execute purely inside the `EL0` `.dext` address space while kernel-facing methods marshal typed parameters across fast `Mach` RPC channels (`IODispatchQueue` workloops and `IOInterruptDispatchSource` event sources) into a tiny first-party `IOUserServer` kernel nub inside `XNU` [256]. High-throughput bulk transfers avoid byte-copying overhead by mapping shared `IOBufferMemoryDescriptor` / `IOMemoryDescriptor` regions between the `.dext` and the hardware controller. Crucially, for bus-mastering PCIe and Thunderbolt peripherals (`PCIDriverKit`), `IOUserServer` programs the hardware `AppleDART` IOMMU ([Chapter 1](01-secure-boot.md)) per PCIe requester ID (`BDF`) so the external device can DMA *only* into the specific `IOMemoryDescriptor` physical pages explicitly prepared for that `.dext` [33, 264]: neither a rogue Thunderbolt dock nor a memory-corrupted `.dext` process can read or overwrite `XNU` kernel memory, and a null-pointer dereference or heap overflow inside a `.dext` merely terminates the `EL0` daemon and triggers a clean `launchd` re-matching cycle without panicking `macOS`!

Second, *NetworkExtension* (`NEFilterDataProvider`, `NEFilterPacketProvider`, `NEDNSProxyProvider`, `NEAppProxyProvider`, and `NEPacketTunnelProvider`) replaces deprecated BSD Network Kernel Extensions (`NKE`s, retired under `QA1574` in `macOS 11+`) [254, 265, 266]. Rather than letting third-party C code mutate `mbuf` chains inside the kernel's TCP/IP interrupt path, `XNU`'s in-kernel `necp` (`Network Extension Control Policy`) subsystem tags every socket and packet flow with its originating process's `audit_token_t`, `signing_id`, and effective `responsible_pid`, then pauses connection setup or streams byte chunks across shared-memory rings to the user-space `NEFilterDataProvider` [265, 266]. Content filters return granular `NEFilterNewFlowVerdict` decisions (`allowVerdict`, `dropVerdict`, or `filterDataVerdict` inspecting exact inbound/outbound byte windows before releasing the remainder to fast-path kernel forwarding), while `NEDNSProxyProvider` intercepts all UDP/TCP port-53 and resolver queries system-wide so enterprise Zero Trust agents enforce encrypted DoH/DoT resolution with zero third-party `EL1` code [265, 266].

Third, *EndpointSecurity* (`ESF`, [Chapter 9](09-esf-xprotect-forensics.md)) replaces `Kauth` kernel file and process listeners. Across all three extension families, `sysextd` enforces a strict deterministic state machine (`[activated waiting_for_user]` $\to$ `[activated enabled]` $\to$ `[terminated waiting_to_uninstall_on_reboot]`): moving a host `.app` to Trash or invoking `OSSystemExtensionRequest.deactivationRequest` cleanly unloads the `EL0` extension (requiring admin or `RemovableSystemExtensions` MDM authorization so local malware cannot silently deactivate an enterprise EDR or firewall sensor) without ever rebuilding `BootKC` or touching `1TR` [57, 262, 267].

## Platform Forks Across Apple OSes

Contrasting `macOS` against `iOS`, `iPadOS`, `watchOS`, and `visionOS` clarifies why `TCC` bypasses cluster overwhelmingly on the Mac [56, 252, 268]. On mobile, spatial, and watch platforms, `tccd` enforces consent for `Camera`, `Microphone`, `Location`, `Contacts`, `Calendar`, `Bluetooth`, and `LocalNetwork`, yet Apple systematically replaces broad `TCC` database grants with *zero-permission out-of-process pickers* (`PHPickerViewController` for Photos and `UIDocumentPickerViewController` for Files), where a system-rendered `UIViewController` hosted in a separate Apple process renders the user's library and passes back *only* the single file descriptor the user tapped, leaving the calling app with zero `TCC` grant to steal if compromised [252, 268]! And because `iOS` forbids unbundled shell trees and cross-app `AppleEvents`, `responsible_pid` inheritance attacks have no mobile foothold.

At the driver layer, Apple forked `DriverKit` selectively onto *`iPadOS 16+` exclusively on Apple Silicon `M`-series iPads* (`M1` through `M5`): hardware vendors distribute `USBDriverKit`, `PCIDriverKit`, and `AudioDriverKit` `.dext` extensions directly inside App Store iPad apps (enabled interactively by the user inside *Settings $\to$ Privacy & Security $\to$ Drivers*) so external Thunderbolt interfaces, capture cards, and pro audio consoles operate in `EL0` on `iPad Pro` under identical `AppleDART` DMA isolation [264]. By contrast, `A`-series iPhones omit third-party `PCIDriverKit` bus-mastering extensions altogether, and `EndpointSecurity` plus `NEFilterDataProvider` host-wide content-inspection System Extensions remain strictly `macOS`-exclusive (save supervised educational/enterprise `NEFilterControlProvider` web-content extensions on `iOS`/`iPadOS`), reflecting Apple's refusal to let third-party daemons intercept cross-app data outside supervised enterprise controls [262, 265].

## In-the-Wild Failures & Architectural Bounds

Between 2020 and 2026, `TCC` accumulated dozens of high-impact CVEs exploited by both commodity macOS malware (*XCSSET*, *AdLoad*) and red-team toolkits [24, 25, 258, 269, 270]. Because `TCC.db` itself sits locked behind `SIP` and `UF_DATAVAULT`, attackers bypass `TCC` horizontally: hijacking environment state, injecting code into already-consented third-party apps that weakened Hardened Runtime, mounting older Apple-signed binaries, or abusing first-party daemons carrying private `com.apple.private.tcc.allow` entitlements.

### Why TCC Bypasses Cluster Around Confused Deputies: From CVE-2020-9934 and XCSSET to HM Surf and CVE-2025-43530

Reviewing six years of `macOS` `TCC` vulnerabilities reveals a striking architectural pattern: not one of these exploits broke `SQLite` or bypassed `UF_DATAVAULT` kernel VFS checks directly; every single one subverted *attribution* or *ambient exemptions* [24, 25, 251]. Matt Shockley's zero-code `CVE-2020-9934` simply executed `launchctl setenv HOME /tmp/fakehome` and restarted user `tccd`, tricking `tccd` into opening `/tmp/fakehome/Library/Application Support/com.apple.TCC/TCC.db` owned and pre-populated by the attacker [258]! In `CVE-2021-30713` (caught in the wild inside the *XCSSET* Xcode-infecting malware by Jamf Threat Labs), attackers realized `LaunchServices` and `tccd` resolved nested app bundles ambiguously, allowing a rogue payload dropped inside an existing consented app's folder structure to silently capture screenshots under the host app's `kTCCServiceScreenCapture` row [269].

Similarly, Dan Revah's `CVE-2023-26818` (`Telegram`) and Wojciech Regula's `ELECTRON_RUN_AS_NODE` research prove that `TCC` is strictly coupled to [Chapter 6](06-amfi-txm-notarization.md)'s Hardened Runtime (`CS_RUNTIME` + `CS_REQUIRE_LV`) [270, 272]: if a third-party chat or IDE vendor disables Library Validation or leaves an interpreter flag (`ELECTRON_RUN_AS_NODE=1`) exposed, `tccd` sees a valid vendor signature on the host `Mach-O` while attacker dylibs or JavaScript execute inside its `audit_token_t`! Finally, Microsoft Threat Intelligence's discovery of `HM Surf` (`CVE-2024-44133`, actively exploited by *AdLoad* via `Safari`'s `PerSitePreferences.db` directory swap) and Mickey Jin's `CVE-2025-43530` (`VoiceOver` `com.apple.scrod` executing arbitrary `AppleScript` files to drive `Finder`) highlight the peril of Apple's own `com.apple.private.tcc.allow` entitlements [24, 25]: whenever a first-party browser or accessibility service holds blanket `TCC` exemptions, *every mutable config file or XPC method it exposes becomes an implicit `TCC` boundary*. And as [Chapter 18](18-agentic-ai-workload-isolation.md) explores, granting Full Disk Access to a terminal or IDE that subsequently spawns `Model Context Protocol` (`MCP`) AI tool servers recreates this exact `responsible_pid` confused deputy without needing any OS vulnerability at all.

