# How to Read This Book

*The Linux Trust Chain* is structured as a single continuous architectural progression from hardware power-on reset to multi-tenant confidential cloud workloads and upstream open-source build pipelines, yet readers arrive from markedly different Linux operational worlds. Because no single Linux configuration exists in production, every numbered chapter explicitly situates its mechanisms across three recurring deployment profiles: *mutable enterprise distributions* (traditional package-managed servers and developer workstations such as Red Hat Enterprise Linux, Ubuntu Server, Debian, and SUSE Linux Enterprise), *immutable image-based systems* (atomic and read-only operating systems such as Fedora CoreOS, Flatcar Container Linux, Talos Linux, Bottlerocket, and embedded `systemd` appliances), and *multi-tenant cloud, Kubernetes, and AI execution substrates* (worker nodes hosting OCI containers, `gVisor` or `Firecracker` sandboxes, autonomous coding agents, and `AMD SEV-SNP` or `Intel TDX` Confidential VMs) [2, 17, 41, 45, 46].

### Navigating by Role and Deployment Profile

Readers seeking the complete end-to-end architectural argument should read sequentially from the [Prologue](../chapters/00-prologue.md) and [Foundations](../chapters/00b-foundations.md) through [Chapter 20](../chapters/20-xz-supply-chain-provenance.md). Each part builds directly upon the cryptographic guarantees and unclosed gaps handed off by the preceding part: Part I ([Chapters 1](../chapters/01-uefi-shim-sbat.md) to [4](../chapters/04-ima-ipe-keylime.md)) establishes verified pre-OS boot, `TPM 2.0` `PCR[11]` sealing, immutable block/file Merkle trees, and remote attestation; Part II ([Chapters 5](../chapters/05-kernel-lockdown-modules.md) to [7](../chapters/07-stacked-lsms-landlock.md)) prevents `UID 0` and memory corruption from subverting Ring 0 and stacks `SELinux`, `AppArmor`, and `Landlock` across kernel objects; the Interlude ([Chapter 8](../chapters/08-ebpf-dual-edge.md)) examines `eBPF` both as an inline `LSM-BPF` security enforcer and as a Ring 0 verifier attack surface; Part III ([Chapters 9](../chapters/09-capabilities-userns.md) to [13](../chapters/13-pam-ssh-fido2.md)) rebuilds userspace privilege, service sandboxing, local secret custody, and fleet SSH/OIDC authentication without `SUID-root` or static keys; Part IV ([Chapters 14](../chapters/14-containers-escapes.md) to [19](../chapters/19-confidential-containers.md)) scales isolation to shared-kernel containers, `gVisor` and `Firecracker` micro-VMs, `SPIFFE`/`SPIRE` workload identity, untrusted AI coding agents, and hardware-encrypted Confidential Containers; and the Finale ([Chapter 20](../chapters/20-xz-supply-chain-provenance.md)) confronts upstream open-source supply-chain subversion prior to binary signing.

Specialists targeting an immediate engineering problem can take focused paths after reading [Foundations](../chapters/00b-foundations.md). Appliance and OS image architects building verified boot and immutable `/usr` roots should focus on [Chapters 1](../chapters/01-uefi-shim-sbat.md) through [5](../chapters/05-kernel-lockdown-modules.md) alongside [Chapter 12](../chapters/12-keyrings-systemd-creds.md) (`systemd-creds`). Workstation and enterprise Linux hardening engineers eliminating `SUID` escalation, locking down `systemd` daemons, and modernizing fleet authentication should read [Chapters 7](../chapters/07-stacked-lsms-landlock.md) through [13](../chapters/13-pam-ssh-fido2.md). Cloud-native, Kubernetes, and AI platform engineers designing multi-tenant sandboxes, `MCP` tool isolation, workload identity, or confidential GPU inference clusters can pair [Chapters 7](../chapters/07-stacked-lsms-landlock.md), [8](../chapters/08-ebpf-dual-edge.md), and [9](../chapters/09-capabilities-userns.md) with all of Part IV ([Chapters 14](../chapters/14-containers-escapes.md) through [19](../chapters/19-confidential-containers.md)) and [Chapter 20](../chapters/20-xz-supply-chain-provenance.md).

### Chapter Structure and the Overview Specification Card

Every numbered chapter (`1` through `20`) follows a consistent six-section progression designed to separate architectural coordinates, threat framing, kernel and userspace implementation, operational trade-offs, historical failure analysis, and hands-on host inspection. Each chapter opens with an `Overview` specification card rendered around five explicit coordinates: `Link in the Chain` locates the subsystem between its upstream anchor and downstream consumers; `Core Security Invariant` states the exact mathematical or state-machine property that must hold for the boundary to remain sound; `Deployment Profile Matrix` contrasts how mutable distros, immutable appliances, and cloud/container hosts configure or omit the mechanism; `Trusted Computing Base (TCB)` enumerates every hardware root, firmware binary, kernel subsystem, cryptographic key, and parser whose compromise invalidates the guarantee; and `Integration Seam & Handoff` pinpoints what verified state passes forward and what residual risk belongs to subsequent chapters.

Following `Overview`, `Problem Statement & Threat Model` motivates the mechanism from concrete adversarial capabilities and legacy design flaws before naming modern mitigations. `Kernel & Userspace Mechanics` walks through the primary-source implementation: kernel C/Rust structs (`struct cred`, `struct linux_binprm`, `struct landlock_ruleset`), system calls (`kexec_file_load`, `openat2`, `bpf`, `keyctl`), `TPM 2.0` commands (`TPM2_PolicyAuthorize`, `TPM2_Quote`), PE/COFF and ELF binary sections, and IPC wire flows. `Distro, Immutable-OS, & Cloud Trade-Offs` analyzes real-world operational friction across RHEL/Fedora, Ubuntu/Debian, CoreOS/Talos/Bottlerocket, and hyperscale cloud environments. `Seam Failures, CVEs, & Structural Bounds` opens with a standardized six-column gap-analysis table (`Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix`) and dissects landmark vulnerabilities alongside fundamental theoretical limits. Finally, `Inspecting on a Live Linux Host` provides self-contained, read-only diagnostic shell snippets so readers can verify every invariant on a running system without mutating host state.

### Mathematical Notation, Diagrams, and Live Host Diagnostics

Cryptographic constructions, `TPM 2.0` PCR extension chains, Merkle tree fanout bounds, and POSIX capability transitions are typeset in inline (`$...$`) and display (`$$...$$`) TeX notation, with `$\parallel$` denoting unambiguous byte-string concatenation, `$\cap$`, `$\cup$`, and `$\subseteq$` denoting bitmask intersection, union, and containment over 64-bit capability vectors, and `$\operatorname{SHA-256}(\cdot)$` or `$\operatorname{HMAC}_k(\cdot)$` denoting standard cryptographic primitives. Code identifiers, kernel configuration symbols (`CONFIG_*`), system calls, sysctl keys, `systemd` directives, file paths, and `CVE` identifiers appear in monospace backticks.

More than forty custom architectural SVG diagrams accompany the prose, each mechanically verified for strict horizontal-and-vertical orthogonal routing and zero visual collisions. Readers should treat the diagrams as exact structural maps synchronized with the kernel functions, PCR indices, and protocol messages analyzed in the surrounding paragraphs. In the closing `Inspecting on a Live Linux Host` section of each chapter, every shell block contains at most four non-comment command lines using standard Linux utilities (`bootctl`, `mokutil`, `systemd-analyze`, `cryptsetup`, `veritysetup`, `bpftool`, `capsh`, `keyctl`, `busctl`, `run0`, `ss`, `uname`, and `/sys` or `/proc` pseudo-files). Commands are strictly read-only inspection queries; where reading protected kernel interfaces such as `/sys/kernel/security/` or `bpftool` requires administrative capabilities, standard privileges (`CAP_SYS_ADMIN` or `run0`) are noted in comments. All inline bracketed citations (`[k]`) link to verified primary specifications, kernel documentation, RFCs, and security advisories in [References](../back-matter/70-references.md), while key domain vocabulary is consolidated in the [Glossary](../back-matter/80-glossary.md) and [Index](../back-matter/95-index.md).
