# Kernel Lockdown, Signed Modules, and kexec Gates

## Overview

* **Link in the Chain:** First post-boot Ring 0 defense in Part II; prevents a compromised or malicious `UID 0` userspace process from overwriting running kernel memory, loading unsigned `.ko` rootkits, or soft-rebooting into an unverified kernel to bypass Part I's verified boot chain.
* **Core Security Invariant:** Under `lockdown=integrity`, no userspace process (even holding all 41 POSIX capabilities) may modify running Ring 0 code or data structures except via cryptographically verified interfaces (`MODULE_SIG_FORCE` PKCS#7 modules and `kexec_file_load` PE/PKCS#7 kernels); under `lockdown=confidentiality`, userspace is additionally barred from reading arbitrary Ring 0 memory.
* **Deployment Profile Matrix:** Mainstream distros (`Fedora`, `RHEL`, `Ubuntu`, `Debian`) automatically activate `lockdown=integrity` whenever UEFI `SecureBoot = 1` while leaving `DKMS` MOK enrollment available; immutable OSes (`Talos`, `Bottlerocket`) compile monolithic or strictly `MODULE_SIG_FORCE` kernels under `lockdown=confidentiality` with legacy `kexec_load` disabled; cloud VMs frequently run `lockdown=none` unless Secure Boot is enabled in OVMF.
* **Trusted Computing Base (TCB):** Linux kernel `security/lockdown/` LSM, `kernel/module/signing.c` PKCS#7 ASN.1/X.509 parser, `.builtin_trusted_keys`, `.secondary_trusted_keys`, `.machine`, and `.blacklist` keyrings, `kexec_file_load` PE/PKCS#7 verifier, and every private key trusted to sign `.ko` modules (including any locally generated `DKMS` MOK key).
* **Integration Seam & Handoff:** Carves a formal privilege boundary between userspace `UID 0` and hardware Ring 0 across administrative APIs; leaves protection against in-kernel memory-corruption exploits (`UAF`, `ROP`) to [Chapter 6](06-kernel-memory-rust.md) and fine-grained VFS/IPC mandatory access control to [Chapter 7](07-stacked-lsms-landlock.md).

## Problem Statement & Threat Model

Throughout the first four decades of Unix and Linux history, `UID 0` (`root`) and Ring 0 (supervisor kernel mode) were treated as a single undivided trust domain [5, 208]. System administrators loaded unsigned device drivers on the fly with `insmod`, poked hardware registers directly through `/dev/mem` and `/dev/port`, overrode broken motherboard `ACPI` bytecode from userspace, inspected live kernel structures via `/dev/kcore`, and fast-rebooted into newly compiled kernels via `kexec_load(2)`. That design made perfect sense when the physical owner, the `root` administrator, and the ultimate arbiter of platform trust were all the same person sitting at a trusted workstation.

The introduction of `UEFI Secure Boot` ([Chapter 1](01-uefi-shim-sbat.md)), `TPM 2.0` `PCR[11]` phase sealing ([Chapter 2](02-uki-systemd-pcrlock.md)), `dm-verity` immutable `/usr` partitions ([Chapter 3](03-luks2-verity.md)), and remote `Keylime` attestation ([Chapter 4](04-ima-ipe-keylime.md)) shattered that equivalence and sparked a seven-year architectural debate on the Linux Kernel Mailing List (`2012` to `2019`) [5, 208, 209]. Traditional kernel maintainers objected that restricting `root` broke Unix's foundational philosophy that the machine owner controls their own kernel; Secure Boot architects led by Matthew Garrett countered that when a Linux distribution asks Microsoft's third-party UEFI CA to sign its `shim` and kernel, an unprivileged `UID 0` escape in Linux must *not* allow an attacker to pivot silently into Ring 0, subvert motherboard firmware or sibling dual-boot operating systems, or forge remote `TPM 2.0` attestation claims while `SecureBoot = 1` remains asserted [208, 209]. Indeed, if `UID 0` remains synonymous with arbitrary Ring 0 code execution, then any remote root vulnerability in a network daemon or container escape instantly neutralizes Part I's entire verified boot chain without touching SPI flash or the EFI System Partition: the attacker simply runs `insmod rootkit.ko`, maps physical RAM via `/dev/mem` to patch out `SELinux` and `IPE`, reprograms `IA32_LSTAR` via `/dev/cpu/0/msr`, or calls `kexec_load(2)` to soft-boot an unsigned kernel while keeping hardware `PCR[0..7]` intact [5, 210, 211]!

The threat model of this chapter assumes an adversary who has *already achieved full `UID 0` (`root`) execution in Linux userspace* with all 41 POSIX capabilities enabled (`CapEff = 0x1ffffffffff`), whether through a `SUID` escalation, a misconfigured `sudo` rule, a stolen SSH root key, or a compromised privileged container. Against an omnipotent `UID 0` adversary, the kernel must enforce two nested security boundaries that operators can select independently of hardware ownership: *Ring 0 integrity* (preventing `UID 0` from injecting unsigned executable code or mutating running kernel data structures) and *Ring 0 confidentiality* (preventing `UID 0` from reading cryptographic secrets such as `dm-crypt` master keys, IPsec session keys, keyring material, or confidential-guest memory resident inside the kernel address space) [5, 208, 212].

## Kernel & Userspace Mechanics

### The `lockdown` LSM Lattice: `integrity` vs. `confidentiality`

Originally proposed by Matthew Garrett in 2012 to close Secure Boot's Ring 3-to-Ring 0 gap and merged into mainline Linux `5.4` by David Howells (`security/lockdown/lockdown.c` and `include/linux/security.h` [5, 208, 209, 212]), `Kernel Lockdown` registers via `DEFINE_EARLY_LSM(lockdown)` so enforcement begins during `early_param("lockdown", ...)` parsing before `initramfs` or device drivers ever execute. Internally, `lockdown.c` maintains a monotonic state variable `kernel_locked_down` evaluated against thirty fine-grained `enum lockdown_reason` constants partitioned by two sentinel ceilings [212]:

```c
enum lockdown_reason {
    LOCKDOWN_NONE = 0,
    LOCKDOWN_MODULE_SIGNATURE,   LOCKDOWN_DEV_MEM,
    LOCKDOWN_EFI_TEST,           LOCKDOWN_KEXEC,
    LOCKDOWN_HIBERNATION,        LOCKDOWN_PCI_ACCESS,
    LOCKDOWN_IOPORT,             LOCKDOWN_MSR,
    LOCKDOWN_ACPI_TABLES,        LOCKDOWN_DEVICE_TREE,
    LOCKDOWN_PCMCIA_CIS,         LOCKDOWN_TIOCSSERIAL,
    LOCKDOWN_MODULE_PARAMETERS,  LOCKDOWN_MMIOTRACE,
    LOCKDOWN_DEBUGFS,            LOCKDOWN_XMON_WR,
    LOCKDOWN_BPF_WRITE_USER,     LOCKDOWN_DBG_WRITE_KERNEL,
    LOCKDOWN_RTAS_ERROR_INJECTION, LOCKDOWN_XEN_USER_ACTIONS,
    LOCKDOWN_INTEGRITY_MAX,
    LOCKDOWN_KCORE,              LOCKDOWN_KPROBES,
    LOCKDOWN_BPF_READ_KERNEL,    LOCKDOWN_DBG_READ_KERNEL,
    LOCKDOWN_PERF,               LOCKDOWN_TRACEFS,
    LOCKDOWN_XMON_RW,            LOCKDOWN_XFRM_SECRET,
    LOCKDOWN_CONFIDENTIALITY_MAX,
};
```

Across thirty-plus privileged kernel call sites, subsystems invoke `security_locked_down(what)` (`lockdown_is_locked_down()` in `security/lockdown/lockdown.c` [212]). Whenever `kernel_locked_down >= what`, the hook emits a rate-limited kernel log notice (`Lockdown: <comm>: <reason> is restricted; see man kernel_lockdown.7`) and returns `-EPERM` unconditionally, overriding `capable(CAP_SYS_ADMIN)`, `capable(CAP_SYS_RAWIO)`, and `capable(CAP_SYS_MODULE)` [5, 212]. Once raised via compile-time kconfig (`CONFIG_LOCK_DOWN_KERNEL_FORCE_INTEGRITY`), kernel command line (`lockdown=integrity` or `lockdown=confidentiality`), automatic UEFI Secure Boot detection (`CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT=y`), or a runtime write to `/sys/kernel/security/lockdown`, `lock_kernel_down()` enforces `if (kernel_locked_down >= level) return -EPERM`: the state can *only ratchet upward* (`none` $\to$ `integrity` $\to$ `confidentiality`), never downward until hardware reset [212].

Walking through the concrete gates below `LOCKDOWN_INTEGRITY_MAX` illustrates how pervasively legacy Unix exposed Ring 0 to `UID 0` [5, 209, 212]:

![Figure: How Linux Kernel Lockdown partitions UID 0 userspace away from Ring 0 across integrity mode (blocking raw memory, port/MSR/PCI writes, unsigned modules, and legacy kexec_load) and confidentiality mode (blocking kernel memory extraction via kcore, kprobes, and raw eBPF reads).](diagrams/05-uid0-ring0-lockdown-boundary.svg)

In `integrity` mode (`kernel_locked_down = LOCKDOWN_INTEGRITY_MAX`), `drivers/char/mem.c` denies `/dev/mem`, `/dev/kmem`, and `/dev/port` openings (`LOCKDOWN_DEV_MEM`, complementing `CONFIG_STRICT_DEVMEM` and `CONFIG_IO_STRICT_DEVMEM` [210]), while `arch/x86/kernel/ioport.c` denies `iopl(2)` and `ioperm(2)` raw x86 `IN`/`OUT` port instructions (`LOCKDOWN_IOPORT` [210]) and `LOCKDOWN_TIOCSSERIAL` / `LOCKDOWN_MODULE_PARAMETERS` block userspace from passing forged hardware I/O port or IRQ base addresses into legacy serial or ISA drivers [5, 212]. On the PCIe bus (`drivers/pci/proc.c` and sysfs `resource*` files), `LOCKDOWN_PCI_ACCESS` blocks raw Base Address Register (`BAR`) `mmap()` and PCI config-space writes so `UID 0` cannot program an NVMe or NIC bus-mastering DMA engine to overwrite physical Ring 0 text [211]. On the CPU itself (`arch/x86/kernel/msr.c`), `LOCKDOWN_MSR` blocks `/dev/cpu/*/msr` `WRMSR` writes, without which `UID 0` can simply overwrite `IA32_LSTAR` (`0xc0000082`) to point `SYSCALL` entry directly at a Ring 3 shellcode page [90, 211]! Firmware and boot-table injection paths close in lockstep: `LOCKDOWN_ACPI_TABLES` and `LOCKDOWN_DEVICE_TREE` block `acpi_rsdp=` pointers, `initrd` `DSDT`/`SSDT` table upgrades, `/sys/kernel/debug/acpi/custom_method`, and the `efivar_ssdt=` boot parameter (`CVE-2019-20908` [213]) because `ACPI` AML bytecode executes inside the kernel's AML interpreter with unrestricted `SystemMemory` OperationRegion physical RAM write access [213, 214]. Likewise, `LOCKDOWN_EFI_TEST` shuts down `/dev/efi_test` (preventing `UID 0` from issuing raw `GetVariable`/`SetVariable`/`QueryVariableInfo` firmware calls that bypass kernel `efivarfs` protections or probe SMM memory corruption bugs), and `LOCKDOWN_HIBERNATION` (`kernel/power/hibernate.c` [215]) disables unauthenticated `swsusp` swap hibernation completely! Laptop users migrating from Windows often ask why Linux disables S4 hibernate-to-disk under Secure Boot while Windows permits `hiberfil.sys`: unlike Windows's `winresume.efi` (which verifies an HMAC/signature over `hiberfil.sys` inside the pre-OS bootloader before restoring Ring 0 pages), traditional Linux `swsusp` resumes from an unauthenticated swap partition *after* the kernel has booted, and even `LUKS2`-encrypted swap fails to stop a live `UID 0` attacker from opening `/dev/mapper/swap` prior to suspend, crafting a modified Ring 0 resume image with `kernel_locked_down = 0`, and triggering `systemctl hibernate` to load arbitrary Ring 0 memory on wake [5, 215]! Alongside hibernation, `LOCKDOWN_BPF_WRITE_USER` blocks `bpf_probe_write_user()` from hijacking privileged processes, `LOCKDOWN_DEBUGFS` / `LOCKDOWN_DBG_WRITE_KERNEL` / `LOCKDOWN_XMON_WR` close raw debugfs and `kgdb`/`xmon` memory writes, and `LOCKDOWN_MODULE_SIGNATURE` plus `LOCKDOWN_KEXEC` mandate cryptographic signatures on all kernel code transitions [5, 212].

Escalating to `lockdown=confidentiality` (`kernel_locked_down = LOCKDOWN_CONFIDENTIALITY_MAX`) seals the eight read-side leakage channels above `LOCKDOWN_INTEGRITY_MAX` [5, 208, 212]: `LOCKDOWN_KCORE` disables `/proc/kcore` (which otherwise exposes all physical RAM, including `dm-crypt` volume keys and Confidential VM guest secrets, as a readable virtual ELF core file!); `LOCKDOWN_KPROBES` and `LOCKDOWN_DBG_READ_KERNEL` disable arbitrary `kprobes` and `kgdb` register/memory inspection; `LOCKDOWN_BPF_READ_KERNEL` rejects raw `bpf_probe_read_kernel()` and `bpf_probe_read_kernel_str()` helpers (`[Chapter 8](08-ebpf-dual-edge.md)` [216]); `LOCKDOWN_TRACEFS` and `LOCKDOWN_PERF` restrict `tracefs` and `perf_event_open()` raw kernel instruction/register sampling; and `LOCKDOWN_XFRM_SECRET` scrubs symmetric IPsec `XFRM` encryption keys from Netlink state dumps [212].

### Signed Kernel Modules (`PKCS#7`), `ML-DSA`, and the System Keyring Hierarchy

Unlike monolithic appliances that disable loadable drivers outright (`CONFIG_MODULES=n`), general-purpose Linux relies on `.ko` ELF relocatable modules. Whenever `CONFIG_MODULE_SIG_FORCE=y` (`module.sig_enforce=1`) or `lockdown=integrity` is active, `init_module(2)` and `finit_module(2)` invoke `module_sig_check()` and `mod_verify_sig()` in `kernel/module/signing.c` *before* the kernel ELF loader (`layout_and_allocate()`) ever parses a single ELF section header or relocation record [54, 217]! Specifically, `module_sig_check()` first rejects modules loaded with `MODULE_INIT_IGNORE_MODVERSIONS` or `MODULE_INIT_IGNORE_VERMAGIC` (preventing forced loading of version-mangled `.ko` binaries), checks for the trailing 28-byte ASCII marker `~Module signature appended~\n` (`MODULE_SIGNATURE_MARKER`), strips the 12-byte `struct module_signature` header (`id_type = PKEY_ID_PKCS7`), and passes the truncated `.ko` payload plus detached `CMS`/`PKCS#7` signature into `verify_pkcs7_signature(..., VERIFY_USE_SECONDARY_KEYRING, VERIFYING_MODULE_SIGNATURE)` [217]. Modern mainline kernels support RSA-4096, NIST P-384 ECDSA (`SHA-2` / `SHA-3`), and post-quantum NIST FIPS-204 `ML-DSA` (`ML-DSA-44`, `ML-DSA-65`, `ML-DSA-87`) module keys [54, 218]. Crucially, even if `sig_enforce` is off, `module_sig_check()` treats malformed or cryptographically invalid signatures as immediately fatal (`-EBADMSG` / `-EKEYREJECTED`), marks the kernel's `/proc/sys/kernel/tainted` bitmask whenever unsigned (`TAINT_UNSIGNED_MODULE`, `'E'`), out-of-tree (`TAINT_OOT_MODULE`, `'O'`), or proprietary (`'P'`) modules enter Ring 0 on unlocked systems, and falls back on unsigned `-ENODATA` / `-ENOKEY` modules to `security_locked_down(LOCKDOWN_MODULE_SIGNATURE)` (`-EPERM` under `Lockdown`) [54, 217].

Module compression introduces an equally subtle verification ordering choice between `kmod` (`modprobe`) in userspace and Ring 0 [54, 197, 217]. Contemporary distributions compress `/lib/modules/$(uname -r)/` into `.ko.zst` (`Zstandard`) or `.ko.xz` files to save `initrd` and `/usr` footprint. If `modprobe` decompresses `.ko.zst` in userspace and passes the raw buffer to legacy `init_module(void *module_image, unsigned long len, ...)`, the appended `~Module signature appended~\n` trailer *inside* the inner `.ko` still satisfies `mod_verify_sig()`, yet file-descriptor LSMs such as `IPE` (`ipe_kernel_load_data(LOADING_MODULE)` vs. `ipe_kernel_read_file(file, READING_MODULE_COMPRESSED)` [197]) lose visibility into the backing `dm-verity` or `fs-verity` inode! Compiling the kernel with in-kernel module decompression (`CONFIG_MODULE_DECOMPRESS=y`) allows `kmod` to invoke `finit_module(fd, params, MODULE_INIT_COMPRESSED_FILE)`: `IPE` and `IMA` verify the compressed `.ko.zst` file descriptor's verity provenance first, the kernel decompresses the stream inside bounded Ring 0 memory, and `mod_verify_sig()` validates the inner PKCS#7 signature prior to ELF relocation [54, 197, 217].

![Figure: The Linux kernel trust keyring hierarchy (.platform, .machine, .builtin_trusted_keys, .secondary_trusted_keys, and .blacklist) governing PKCS#7 module loading and kexec_file_load verification.](diagrams/05-module-sig-kexec-pipeline.svg)

Which X.509 certificates does `VERIFY_USE_SECONDARY_KEYRING` trust? Inside `certs/system_keyring.c` [119, 219] and `security/integrity/platform_certs/load_uefi.c` [134, 220, 221], Linux enforces a strict five-keyring separation where `.blacklist` (populated at boot from UEFI `dbx` and `MokListXRT` X.509 TBS/SHA-256 revocations, hardened after `CVE-2020-26541` [222]) overrides every allowlist unconditionally:

First, `.builtin_trusted_keys` holds X.509 certificates compiled directly into read-only `vmlinux` `.rodata`: the distribution's offline Secure Boot CA plus an ephemeral *build-time autogenerated signing key* (`certs/signing_key.pem` under `CONFIG_MODULE_SIG_ALL=y`) whose private half is wiped at the end of `rpmbuild` / `dpkg-buildpackage`, ensuring no attacker can ever steal the private key used to sign in-tree `.ko` drivers [54, 219]! Second, `.secondary_trusted_keys` links `.builtin_trusted_keys` (and `.machine` when enabled) and gates runtime `keyctl padd` additions through `restrict_link_by_builtin_secondary_and_machine()`: `UID 0` can load a subordinate signing certificate at runtime *if and only if* its X.509 TBS payload carries a valid `digitalSignature` vouching chain from `.builtin_trusted_keys`, `.secondary_trusted_keys`, or `.machine` [219]. Third, `.platform` imports UEFI `db` certificates (`load_uefi_certs()`, skipped if `MokIgnoreDB` is set [220]) to verify `kexec_file_load` PE kernels and optional `IPE` policies *without* letting third-party Microsoft UEFI CA keys load arbitrary `.ko` Ring 0 drivers [219, 220]. Fourth, `.machine` (`CONFIG_INTEGRITY_MACHINE_KEYRING` [221]) imports operator-enrolled `MokListRT` certificates (reading first from the kernel's `EFI MOKvar config table` when `MokListRT` exceeds UEFI runtime variable size limits, and *only* when `arch_get_secureboot()` confirms Secure Boot and `MokSBState` enforcement are active [220]!) and links into `.secondary_trusted_keys` to authorize enterprise or `DKMS` modules [221, 223].

### `kexec_load(2)` vs. `kexec_file_load(2)` and Magic `SysRq` Gates

Linux's `kexec` subsystem soft-boots directly from a running kernel into a new kernel in ~100 milliseconds without traversing motherboard POST or UEFI `DXE` (`kdump` crash capture and fast fleet reboots) [21, 224]. Legacy `kexec_load(2)` accepted raw userspace-prepared `struct kexec_segment` page arrays with zero kernel signature visibility; under `lockdown=integrity`, `kexec_load(2)` is unconditionally blocked by `LOCKDOWN_KEXEC` [5, 224]. Callers must instead invoke `kexec_file_load(kernel_fd, initrd_fd, cmdline_len, cmdline_ptr, flags)` in `kernel/kexec_file.c` [21, 224]: `kimage_file_prepare_segments()` reads the entire image inside Ring 0 via `kernel_read_file_from_fd(..., READING_KEXEC_IMAGE)` (triggering `IMA` and `IPE` hooks!), verifies its PE Authenticode signature via `kexec_kernel_verify_pe_sig()` against `.secondary_trusted_keys` and `.platform`, serializes the `IMA` runtime measurement buffer via `ima_add_kexec_buffer()` (`CONFIG_IMA_KEXEC` [205, 224]), and rejects unsigned images whenever `CONFIG_KEXEC_SIG_FORCE`, `sig_enforce`, or `LOCKDOWN_KEXEC` is active (closing `CVE-2022-21505`, where booting with `ima_appraise=log` previously tricked `kimage_validate_signature()` into permitting unsigned `kexec` loads under `Lockdown` when UEFI Secure Boot was off [206, 224]). Furthermore, when `systemd` / `kdump` pre-stages an emergency crash-capture kernel at boot using `kexec_file_load(..., KEXEC_FILE_ON_CRASH)` into the `crashkernel=` physical memory reservation (`crashk_res`), the kernel immediately calls `arch_kexec_protect_crashkres()` after staging to unmap or mark the reserved crash-kernel pages read-only inside the primary kernel's page tables! That hardware page-table write-lock ensures neither an errant Ring 0 wild pointer during a kernel panic nor a post-staging `UID 0` exploit can tamper with the verified `kdump` kernel sitting in RAM while waiting for a crash [224].

Equally overlooked on physical consoles and `UID 0` hosts is the *Magic `SysRq`* facility (`drivers/tty/sysrq.c` and `Documentation/admin-guide/sysrq.rst` [225]). Controlled for physical/serial keyboards (`Alt+SysRq+<key>` or UART `BREAK`) by the `/proc/sys/kernel/sysrq` bitmask (`0` = disabled, `1` = all enabled, `0x4` keyboard SAK, `0x8` register/memory dumps, `0x10` sync, `0x40` `SIGTERM`/`SIGKILL`/OOM, `0x80` immediate reboot), `sysrq.c` contains a critical subtlety in `__handle_sysrq(key, check_mask)` [225]: writes by `UID 0` to `/proc/sysrq-trigger` pass `check_mask = false`, *ignoring `/proc/sys/kernel/sysrq` bitmasks completely*! Historically, when kernel debuggers (`kgdb` on `SysRq-g` or PowerPC `xmon` on `SysRq-x`) were compiled in, a `UID 0` attacker wrote `g` to `/proc/sysrq-trigger` (`CVE-2022-21499` [226]) or typed `Alt+SysRq+g` on a kiosk keyboard to drop straight into an interactive Ring 0 memory-write debugger and zero `kernel_locked_down`! Patched kernels gate `kgdb` and `xmon` entry behind `LOCKDOWN_DBG_WRITE_KERNEL` / `LOCKDOWN_XMON_WR` (and register/ftrace dumps behind `confidentiality`), while hardened production nodes set `sysctl kernel.sysrq=0` and omit `CONFIG_KGDB` altogether [212, 225, 226].

## Distro, Immutable-OS, & Cloud Trade-Offs

Mutable distributions (`Ubuntu`, `Fedora`, `RHEL`, `Debian`, `SUSE`) automatically activate `lockdown=integrity` whenever `arch_get_secureboot()` detects UEFI Secure Boot (`CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT=y`), while leaving `lockdown=confidentiality` opt-in so root SREs can still attach `bpftrace`, `perf`, and `kprobes` during production incident response [5, 208, 220]. On developer laptops and GPU workstations, these distributions also integrate `DKMS` (`dkms(8)` [223]) or `akmods` with `shim` `MOK`: on first install of `nvidia-driver`, `zfs-dkms`, or `virtualbox-dkms`, the package hook generates an RSA keypair locally on disk (`/var/lib/shim-signed/mok/MOK.priv` on Ubuntu/Debian or `/etc/pki/akmods/private/private_key.priv` on Fedora) and stages the public half for `MokManager` console enrollment on reboot [134, 223]. Pause and trace that exact trust seam! While `MokManager` enforces physical console presence *once* at key enrollment, leaving the unencrypted `MOK.priv` file sitting in `/var/lib/` with `0600` `root:root` permissions means any subsequent `UID 0` attacker on a `DKMS`-enabled host can read `MOK.priv`, run `/usr/src/linux-headers-$(uname -r)/scripts/sign-file sha256 MOK.priv MOK.der rootkit.ko`, and load arbitrary Ring 0 code cleanly past `MODULE_SIG_FORCE` and `lockdown=integrity` [54, 134, 223]!

Enterprise GPU clusters and immutable operating systems eliminate on-host signing keys completely through three complementary patterns [45, 54, 72, 221]. First, where out-of-tree `.ko` drivers (`NVIDIA` data-center GPU drivers or InfiniBand RDMA stacks) are mandatory, build pipelines pre-compile `.ko` packages inside isolated CI runners and invoke `scripts/sign-file` using an `RFC 7512` `PKCS#11` URI (`pkcs11:token=kmod-signer;object=prod-key`) backed by a network Hardware Security Module (`HSM`), enrolling only the public X.509 certificate in target nodes' `.machine` keyrings so no target server ever holds a signing private key [54, 221]. If a standalone workstation *must* sign local `DKMS` builds on-box, wrapping the private key inside the host `TPM 2.0` via `tpm2-pkcs11` [72] with a user PIN prevents silent unattended `UID 0` key exfiltration or misuse. Second, immutable container operating systems (`Talos Linux`, `AWS Bottlerocket`, `Flatcar`) either compile monolithic kernels with `CONFIG_MODULES=n` or ship exclusively build-time ephemeral-key-signed modules, boot with `lockdown=confidentiality` and `module.sig_enforce=1` baked into the signed `UKI` `.cmdline`, disable `kexec` (`CONFIG_KEXEC_CORE=n` or `sysctl kernel.kexec_load_disabled=1`), and flip the one-way sysctl latch `kernel.modules_disabled=1` once early `udev` hardware probing finishes so *not even a validly signed module* can be loaded later at runtime [5, 45, 54].

Third, cloud security architects must watch for a pervasive silent downgrade in public-cloud IaaS fleets (`AWS EC2`, `Azure`, `GCP`) [5, 212]: millions of cloud Linux instances still boot via legacy BIOS/`SeaBIOS` or UEFI `OVMF` templates with `SecureBoot = 0`! Because `CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT` triggers *only* when UEFI reports `SecureBoot = 1`, the exact same `Ubuntu 24.04` or `RHEL 9` kernel that runs locked down on a bare-metal server boots in `lockdown=[none]` on a non-Secure-Boot cloud VM, leaving `/dev/mem`, unsigned `insmod`, and unverified `kexec_load()` wide open to container-escape `UID 0` attackers unless operators enable Cloud UEFI Secure Boot (`AWS Nitro` UEFI Secure Boot, `Azure Trusted Launch`, `GCP Shielded VM`) *and* explicitly pass `lockdown=confidentiality` on the signed kernel command line [5, 212].

## Seam Failures, CVEs, & Structural Bounds

Real-world bypasses of post-boot kernel integrity exploit forgotten raw-hardware interfaces, locally stored `DKMS` signing keys, vulnerable vendor-signed `.ko` modules ("Bring Your Own Vulnerable Driver" on Linux), and `ASN.1`/`PKCS#7` parser bugs inside Ring 0.

| `ACPI` `custom_method` & `efivar_ssdt` (`CVE-2019-20908`) | 2017-2020 | `drivers/acpi/` AML interpreter | `ACPI` tables supply passive hardware topology descriptions | `UID 0` loads crafted SSDT via `efivar_ssdt` or `initrd` using AML `SystemMemory` writes to zero `kernel_locked_down` | Block `efivar_ssdt`, `custom_method`, and initrd ACPI table overrides under `LOCKDOWN_ACPI_TABLES` [213, 214] |
| UEFI `dbx` / `MokListXRT` Keyring Gap (`CVE-2020-26541`) | 2020 | `security/integrity/platform_certs/` | Revoking a cert in `dbx` or `MokListX` blocks it in Linux too | Kernel failed to import all X.509/TBS revocation types from `dbx`/`MokListXRT` into `.blacklist`, allowing `kexec` of revoked images | Enforce complete `dbx` and `MokListXRT` certificate/hash ingestion into `.blacklist` [220, 222] |
| Local `DKMS` `MOK.priv` Key Theft | 2018-2025 | Host `dkms` / `akmods` private key storage | `MODULE_SIG_FORCE` stops `UID 0` from loading custom rootkits | Compromised `UID 0` reads `/var/lib/shim-signed/mok/MOK.priv`, runs `sign-file`, and calls `finit_module()` | Sign out-of-tree `.ko` modules off-host in CI HSMs or seal local `DKMS` keys in `TPM 2.0` (`tpm2-pkcs11`) [54, 72, 223] |
| `kgdb` / Magic `SysRq-g` Bypass (`CVE-2022-21499`) | 2022 | `drivers/tty/sysrq.c` & `kgdb` | `Lockdown` blocks interactive Ring 0 memory debuggers | `UID 0` writes `g` to `/proc/sysrq-trigger` (ignoring `kernel.sysrq` mask) to enter `kgdb` and patch Ring 0 RAM | Gate `kgdb` behind `LOCKDOWN_DBG_WRITE_KERNEL` / `READ_KERNEL` and set `kernel.sysrq=0` [212, 225, 226] |
| `ima_appraise=log` `kexec` Bypass (`CVE-2022-21505`) | 2022 | `kernel/kexec_file.c` + `IMA` | `IMA` signature check substitutes safely for `LOCKDOWN_KEXEC` | `ima_appraise=log` without Secure Boot logged unsigned `kexec_file_load` images instead of rejecting them | Restrict `ima_appraise=log` whenever `Kernel Lockdown` is active [206, 224] |
| Linux `BYOVD` (Vulnerable Vendor `.ko`) | 2022-2025 | Out-of-tree long-lived CA `.ko` drivers | Valid PKCS#7 signature implies memory-safe driver `ioctl`s | Attacker loads older vendor-signed diagnostics `.ko` exposing physical R/W `ioctl` to overwrite `cred` | Use ephemeral per-build keys for in-tree `.ko`s and `.blacklist` hash revocations for third-party CAs [54, 219, 228] |
| `eBPF` / `kprobe` Secret Extraction Under `integrity` | 2021-2025 | `lockdown=integrity` without `confidentiality` | `integrity` mode hides Ring 0 secrets from `UID 0` | `UID 0` attaches `kprobe` or `bpf_probe_read_kernel` to `dm-crypt` functions and dumps live `LUKS2` master keys | Escalate hosts holding high-value keys to `lockdown=confidentiality` [5, 212, 216] |

Notice a striking architectural advantage Linux enjoys over Windows on Row 7 (*Bring Your Own Vulnerable Driver*): whereas Windows's central WHQL CA signs third-party `.sys` drivers that remain loadable across multiple OS builds until added to the Vulnerable Driver Blocklist, in-tree Linux distro modules are signed by a *throwaway key generated fresh for each kernel build* (`CONFIG_MODULE_SIG_ALL=y`, supporting RSA-4096, ECDSA P-384, or post-quantum `ML-DSA` [54, 218]) whose private half is deleted at compile end! Consequently, an attacker cannot take a vulnerable in-tree `.ko` from `linux-6.1.0-10` and load it onto `linux-6.12.0-25` because `6.12`'s `.builtin_trusted_keys` does not contain `6.1`'s ephemeral key. Only long-lived CA keys enrolled in `.machine` or `.secondary_trusted_keys` create cross-version `BYOVD` risk [221, 228], reinforcing why long-lived module CAs must be tightly audited and why production servers should set `sysctl kernel.modules_disabled=1` once boot hardware initialization finishes.

> **Warning.**
> `LOCKDOWN_PCI_ACCESS` blocks `UID 0` software from mapping PCIe BARs via `sysfs`, yet physical DMA isolation beneath `Kernel Lockdown` depends critically on an active hardware IOMMU (`Intel VT-d` or `AMD-Vi` configured in strict non-passthrough mode via `CONFIG_IOMMU_DEFAULT_DMA_STRICT=y` and `iommu.passthrough=0`) plus Thunderbolt/USB4 `bolt` DMA authorization [5, 211, 229]. If an operator boots with `iommu=pt` (passthrough mode for NIC micro-benchmarks) or binds a PCIe device to `vfio-pci` without IOMMU groups enforced, a malicious peripheral or `UID 0` `VFIO` user-space driver can still DMA-overwrite physical Ring 0 memory directly across the PCIe root complex!

Even with strict IOMMU translation, `lockdown=confidentiality`, and ephemeral module keys active, `Lockdown` only closes *architectural administrative interfaces* (`finit_module`, `/dev/mem`, `WRMSR`, `kexec`); it assumes the *already-running* kernel C code has zero exploitable memory-corruption bugs. Defending Ring 0 when a reachable syscall, `io_uring` worker, or network protocol parser contains a Use-After-Free or buffer overflow belongs to [Chapter 6](06-kernel-memory-rust.md).

## Inspecting on a Live Linux Host

Check the current `Kernel Lockdown` state (`[none]`, `[integrity]`, or `[confidentiality]`), one-shot `kexec` / module locks, and Magic `SysRq` bitmask:

```bash
cat /sys/kernel/security/lockdown 2>/dev/null; echo
sysctl kernel.modules_disabled kernel.kexec_load_disabled kernel.sysrq 2>/dev/null
```

Verify kernel compile-time module signature enforcement (`CONFIG_MODULE_SIG_FORCE`) and Lockdown Secure Boot integration in `/boot/config-*` or `/proc/config.gz`:

```bash
grep -E "CONFIG_(MODULE_SIG|LOCK_DOWN_KERNEL)" /boot/config-$(uname -r) 2>/dev/null
cat /sys/module/module/parameters/sig_enforce 2>/dev/null
```

List the X.509 certificates currently loaded into `.builtin_trusted_keys`, `.secondary_trusted_keys`, `.platform`, `.machine`, and `.blacklist` via `/proc/keys` or `keyctl`:

```bash
# Viewing system keyrings in /proc/keys requires root / run0
grep -E "^\S+.*(\.builtin|\.secondary|\.platform|\.machine|\.blacklist)" /proc/keys 2>/dev/null
```

Inspect the appended `PKCS#7` signature metadata on any installed `.ko` kernel module using `modinfo`:

```bash
modinfo $(find /lib/modules/$(uname -r) -name "*.ko*" 2>/dev/null | head -n 1) 2>/dev/null | grep -E "^sig_|^signer"
```
