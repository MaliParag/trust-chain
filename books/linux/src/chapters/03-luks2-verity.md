# Block and File Integrity: LUKS2, dm-verity, and fs-verity

## Overview

* **Link in the Chain:** Anchors persistent storage immediately after `UKI` and `TPM 2.0` `PCR[11]` early-boot verification ([Chapter 2](02-uki-systemd-pcrlock.md)), providing confidential read-write volumes (`LUKS2`) alongside cryptographically tamper-proof OS trees and files (`dm-verity`, `systemd-sysext`, `fs-verity`).
* **Core Security Invariant:** `LUKS2` protects volume master keys under memory-hard `Argon2id` or `TPM2` keyslots (and detects offline ciphertext tampering only when paired with `dm-integrity` AEAD), while `dm-verity` and `fs-verity` verify every $4\text{ KiB}$ page read on demand against a SHA-256/SHA-512 Merkle tree whose root digest is pinned to a signed `UKI` or kernel keyring certificate before mapping bytes into page cache.
* **Deployment Profile Matrix:** Mutable enterprise distros deploy `LUKS2` (`aes-xts-plain64` without AEAD) over mutable `ext4`/`XFS`/`btrfs` roots; immutable container OSes (`Flatcar`, `Talos`, `Bottlerocket`, `Fedora CoreOS` `composefs`) mount `/usr` (or `/`) read-only over `dm-verity` or `fs-verity` extended by signed `systemd-sysext` images; cloud workloads combine EBS/PD encryption with `dm-verity` root partitions.
* **Trusted Computing Base (TCB):** Linux kernel device-mapper (`dm-crypt`, `dm-integrity`, `dm-verity`), VFS `fs/verity/` subsystem, crypto API (`AES-XTS`, `AEGIS-128`, `ChaCha20-Poly1305`, `SHA-256`), `UKI`-supplied `roothash=` or `.builtin_trusted_keys` / `.secondary_trusted_keys`, and `systemd-gpt-auto-generator` / `systemd-sysext`.
* **Integration Seam & Handoff:** Guarantees block- and inode-level cryptographic integrity for `/usr` and verified files; delegates mandatory execution policy ("refuse `execve` / `mmap(PROT_EXEC)` on any file lacking verity provenance") and remote fleet attestation to `IPE` and `Keylime` in [Chapter 4](04-ima-ipe-keylime.md).

## Problem Statement & Threat Model

Ask ten systems administrators whether `LUKS` full-disk encryption prevents an offline attacker from modifying `/bin/bash` on a powered-off laptop, and nine will answer yes. Under default `cryptsetup` settings, that intuition is dangerously incomplete [18, 19]. Standard disk encryption (`dm-crypt` in `aes-xts-plain64` mode) is a length-preserving *confidentiality* primitive, not an authenticated encryption (`AEAD`) scheme: every 512-byte or 4096-byte disk sector on the raw NVMe drive maps to an identically sized ciphertext sector with zero space reserved for a Message Authentication Code (`MAC`) tag [18, 19]. While an offline Evil Maid adversary who lacks the `LUKS2` master key cannot *read* plaintext sectors, `XTS-AES` operates on independent 16-byte cipher blocks tweaked by the sector index. Flipping bits inside a 16-byte ciphertext block deterministically scrambles only the corresponding 16-byte plaintext block (corrupting specific configuration lines, zeroing flags, or crashing security services), and replaying a previously captured ciphertext sector back to the same Logical Block Address (`LBA`) restores stale data cleanly without `dm-crypt` ever raising an I/O error [19].

Furthermore, encryption and integrity solve orthogonal security problems across an operating system's storage layout, and delegating encryption blindly to closed-source drive firmware creates catastrophic blind spots [2, 166]. In 2018, Radboud University researchers Carlo Meijer and Bernard van Woudenberg audited commercial Solid-State Drives implementing the TCG `OPAL` and IEEE 1667 Self-Encrypting Drive (`SED`) specifications (`CVE-2018-12037`, `CVE-2018-12038`, CERT `VU#395981` [166]). Across popular enterprise and consumer SSD models, the controller generated its internal hardware Disk Encryption Key (`DEK`) independently of the user's authentication password: an attacker with physical access to the NVMe/SATA PCB could bridge JTAG debug pads, patch firmware RAM, or read wear-leveling flash blocks to recover the unwrapped `DEK` and decrypt the entire drive with *zero* knowledge of the user passphrase! Equally fundamental, user home directories (`/home`) and mutable service state (`/var`) contain private data that changes continuously and therefore require *confidentiality* paired with authentication, whereas the operating system code tree (`/usr`, containing the dynamic linker, `glibc`, `systemd`, `sshd`, and shared libraries) contains zero secret bytes because its binaries are publicly downloadable from distribution mirrors [2]. Encrypting `/usr` inside a single read-write `ext4` volume alongside `/var` fails to distinguish immutable vendor code from mutable runtime state: if a transient root exploit modifies `/usr/lib64/libc.so.6` while the system is booted and unlocked, `LUKS2` dutifully *encrypts the attacker's backdoor* to disk and serves it back cleanly on every subsequent boot [2, 20].

Modern Linux storage architecture addresses an adversary with offline physical access to raw NVMe flash and SSD controllers, storage-network (`iSCSI`/`NVMe-oF`/cloud-snapshot) write access, rogue USB peripheral insertion during boot, or transient userspace compromise seeking persistent OS modification. Defending against all four vectors requires splitting the storage stack cleanly: keeping encryption inside auditable Ring 0 `dm-crypt` (layering hardware `OPAL` strictly beneath software encryption rather than replacing it [18, 167]), hardening mutable partitions with `LUKS2` `Argon2id` key derivation and `dm-integrity` `AEAD` tags, pinning immutable `/usr` partitions and `systemd-sysext` overlays to `dm-verity` Merkle trees discovered via UAPI GPT UUIDs, and bringing demand-paged Merkle verification to individual files via `fs-verity` and `composefs` [18, 20, 50, 160, 168].

## Kernel & Userspace Mechanics

### `LUKS2` JSON Metadata, `Argon2id`, `OPAL` Layering, and `dm-integrity` AEAD

Version 2 of the Linux Unified Key Setup (`LUKS2` [18]) replaced `LUKS1`'s rigid binary layout and GPU-vulnerable `PBKDF2` key derivation with a dual-copy, crash-resilient 4 KiB binary header (`LUKS\xba\xbe` primary magic and `SKUL\xba\xbe` secondary magic, monotonic `seqid`, header size, and `SHA-256` header checksum covering the entire binary + JSON region) followed by an extensible UTF-8 `JSON` metadata area (`keyslots`, `segments`, `digests`, `tokens`, `config`) and 4000-stripe anti-forensic (`AFsplitter`) encrypted binary keyslots [18]. Password-protected keyslots default to `Argon2id` (`RFC 9106` [169]), a hybrid memory-hard key derivation function parameterized by memory cost $m$ (up to `1 GiB` RAM by default in `cryptsetup`), time iterations $t$, and parallelism $p$. Filling and pseudo-randomly indexing a gigabyte-scale memory matrix (combining data-independent `Argon2i` first-slice addressing against cache-timing side channels with data-dependent `Argon2d` passes maximizing Time-Memory Trade-Off resistance) neutralizes custom ASIC and GPU cracking clusters that tested millions of `LUKS1` `PBKDF2-SHA256` guesses per second [18, 169]. Inside each binary keyslot area (`keyslots_size`), `LUKS2` diffuses the encrypted 32- or 64-byte volume master key across 4,000 XOR stripes (`AFsplitter`, typically `128` to `256 KiB` on disk) so overwriting or retiring a single keyslot (`cryptsetup luksKillSlot` or `cryptsetup erase`) destroys key recoverability even when SSD Flash Translation Layer wear-leveling leaves a handful of stale 4 KiB pages unerased [18]. Still, parsing rich JSON metadata prior to volume unlock demands extreme care: in `CVE-2021-4122` [170], an offline Evil Maid attacker could inject crafted `online-reencrypt` segment entries into the unauthenticated `LUKS2` JSON area, tricking `cryptsetup` on the next legitimate user unlock into "recovering" an interrupted decryption job and silently rewriting encrypted disk sectors into plaintext! Patched `cryptsetup` (`2.4.3+`) binds re-encryption segment layouts cryptographically into a dedicated metadata keyslot digest verified *before* any recovery I/O begins [18, 170]. Similarly, when `cryptsetup 2.7+` configures TCG `OPAL` hardware encryption (`block/sed-opal.c`), `--hw-opal` defaults to *double encryption* (software `dm-crypt` layered atop hardware `OPAL` locking ranges), ensuring Radboud-style SSD controller bypasses (`CVE-2018-12037` [166]) never expose plaintext [18, 167].

Why does plain `aes-xts-plain64` fail to stop offline tampering, and how does `dm-integrity` fix it [19, 171, 172]? Under `NIST SP 800-38E` [171], `XTS-AES` splits a 512-bit key into $K_1 \parallel K_2$ and encrypts the $j$-th 16-byte cipher block of 4096-byte sector $i$ as $C_{i,j} = E_{K_1}(P_{i,j} \oplus T_{i,j}) \oplus T_{i,j}$, where tweak $T_{i,j} = E_{K_2}(i) \otimes \alpha^j$ in $\operatorname{GF}(2^{128})$. Because `XTS` computes zero authentication tags, an offline attacker can replay an older ciphertext capture of sector $i$ back to LBA $i$ (rolling back databases or revocation files cleanly) or mutate 16 bytes of ciphertext to scramble a targeted 16-byte plaintext window without `dm-crypt` noticing [171, 172]. Formatting a volume with `cryptsetup luksFormat --cipher aes-gcm-random --integrity aead` (or `--cipher chacha20-random --integrity poly1305` on CPUs lacking AES instructions, or modern AES-round-based `--cipher aegis128-random --integrity aead` [172, 173]) stacks `dm-crypt` over `drivers/md/dm-integrity.c` [19, 174]. Because appending a 16-byte tag to a 4096-byte sector yields a non-power-of-two 4112-byte record, `dm-integrity` interleaves dedicated metadata blocks and commits both ciphertext and its 128-bit `AEAD` tag (binding the 64-bit sector number as Additional Authenticated Data against cross-LBA sector swaps) through a crash-safe write-ahead journal [19, 174]. While journaled `AES-GCM` roughly halves random-write IOPS due to double writes, `AEGIS-128L` (`aegis128-random` [173]) saturates parallel AES hardware pipelines at multi-GB/s throughput, and copy-on-write or battery-backed NVMe tiers can opt into `--integrity-no-journal` (bitmap mode) so any single bit flip on disk immediately returns `-EBADMSG` / `-EIO` in Ring 0 [19, 172, 174].

### `dm-verity`, Reed-Solomon `FEC`, UAPI `DPS`, and `systemd-repart`

For immutable `/usr` or root partitions, write journals vanish because the target is mounted strictly read-only. Inside `drivers/md/dm-verity-target.c` [20, 175], `veritysetup format` builds an offline version-1 Merkle hash tree over $N$ data blocks $D_0, \dots, D_{N-1}$ ($B = 4096$ bytes). In `dm-verity` version 1, the per-image cryptographic `salt` $s$ is *prepended* (`verity_hash()` precomputes `initial_hashstate.sha256` over $s$ once at mount time to accelerate every subsequent page check!), padding each 32-byte `SHA-256` digest to a power-of-two slot ($b = 4096 / 32 = 128$ hashes per $4\text{ KiB}$ metadata block) across $H = \lceil \log_{128} N \rceil$ levels up to the 32-byte `root_hash` $R$ [20, 175]. As bio reads arrive, `verity_verify_level()` caches verified intermediate hash blocks inside `dm-bufio` (`struct buffer_aux { int hash_verified; }`) and supports low-latency softirq verification (`try_verify_in_tasklet`) whenever parent hash nodes are already hot in RAM [175].

What happens when `verity_hash()` detects a mismatch on block `block`? First, if Reed-Solomon Forward Error Correction (`--fec-device`, `dm-verity-fec.c` [20, 176]) is configured with `fec_roots=2` (an interleaved `RS(255, 253)` code adding just `0.8%` parity space), `verity_fec_decode()` attempts algebraic erasure recovery across interleaved codewords and *re-verifies the repaired block against `want_digest`*, healing physical NAND flash bit rot automatically while never letting an attacker forge unauthenticated data [175, 176]! If `FEC` cannot recover a valid hash match, `verity_handle_err()` sets `v->hash_failed = true`, emits a `DM_VERITY_ERR_BLOCK_NR` `uevent`, and enforces the configured corruption mode [20, 175]: default `-EIO` (`DM_VERITY_MODE_EIO` fails only the offending read), `ignore_corruption` (`DM_VERITY_MODE_LOGGING`, unsafe outside debugging), `restart_on_corruption` (`DM_VERITY_MODE_RESTART`, invoking `kernel_restart("dm-verity device corrupted")` immediately so an A/B bootloader switches cleanly to the backup OS slot), or `panic_on_corruption` (`DM_VERITY_MODE_PANIC`, halting the kernel via `panic()`). Note that constrained embedded builds occasionally pass `check_at_most_once` (`DM_VERITY_OPT_AT_MOST_ONCE`), which verifies each data block only on its *first* read; on high-security hosts, `check_at_most_once` should be avoided because evicted pages re-read later from a malicious storage controller would skip leaf re-hashing [20, 175].

How does the booting kernel bind the right `/usr` data partition, `/usr` verity hash partition, and mutable `/var` partition without trusting a mutable `/etc/fstab` or falling prey to partition-swap attacks? Through the UAPI *Discoverable Partitions Specification* (`DPS` [160]) enforced by `systemd-gpt-auto-generator(8)` [177] paired with declarative first-boot provisioning in `systemd-repart(8)` [178]:

![Figure: UAPI Discoverable Partitions (DPS) and systemd-repart GPT layout linking the UKI-pinned usrhash into paired /usr data and verity Partition UUIDs alongside machine-id-seeded LUKS2 + AEAD /var storage.](diagrams/03-extra-dps-repart-boot-layout.svg)

Trace how `DPS` blocks rogue-disk and slot-swap spoofing end-to-end [149, 160, 177]. First, `systemd-gpt-auto-generator` reads the volatile `LoaderDevicePartUUID` EFI variable set by `systemd-stub` ([Chapter 2](02-uki-systemd-pcrlock.md)) and restricts GPT partition scanning *exclusively to the physical block device hosting the booted ESP*, defeating an attacker who plugs in a malicious USB drive carrying spoofed Linux GPT Type UUIDs! Second, when an image builder embeds `usrhash=` (64 hex chars = 256 bits) inside the signed `UKI` `.cmdline` (or verifies a detached PKCS#7 root-hash signature in Ring 0 via `CONFIG_DM_VERITY_VERIFY_ROOTHASH_SIG` in `dm-verity-verify-sig.c` [179]), `DPS` splits `usrhash` into its upper 128 bits ($H_{\text{hi}}$) and lower 128 bits ($H_{\text{lo}}$), setting $H_{\text{hi}}$ as the GPT *Partition UUID* of the `/usr` filesystem (`8484680c-9521-48c6-9c11-b0720656f69e` on `x86-64`, `b0e01050-ee5f-4390-949a-9101b17104e9` on `ARM64`, typically formatted with compact block-aligned `EROFS` [180]) and $H_{\text{lo}}$ as the GPT *Partition UUID* of `/usr-verity` (`77ff5f63-e7b6-4633-acf4-1565b864c0e6`) [160, 177]. Thus A/B updates (`_usr_a` vs. `_usr_b`) switch atomically just by booting `uki-v2.efi`! Meanwhile, during `initrd`, `systemd-repart` reads `/usr/lib/repart.d/*.conf` from the verified image to create or grow `/var` (`4d21b016-b534-45c2-a9fb-5c16e091fd2d`) on first boot: it wipes free blocks via `BLKDISCARD`, derives deterministic Partition UUIDs keyed from `/etc/machine-id`, formats `LUKS2` + `TPM2` (`PCR[11]` + `PCR[15]`) + optional `dm-integrity`, and supports verified factory reset (`FactoryReset=yes`) [178]. Layered atop `/usr` and `/etc`, `systemd-sysext(8)` and `systemd-confext(8)` mount self-contained *Discoverable Disk Images* (`DDIs` [30, 181]: mini-GPT `.raw` files bundling `EROFS` + `dm-verity` + `verity-sig` PKCS#7 partitions) as read-only `OverlayFS` upper layers after validating their X.509 signatures and extending active DDIs into `PCR[13]` [30, 113, 181].

### `fs-verity` (`fs/verity/verify.c`) and `composefs` (`Linux 6.6+`)

Block-level `dm-verity` protects whole read-only partitions, whereas individual packages, container blobs, or AI model weights living on writable `ext4`, `btrfs`, or `f2fs` volumes require per-inode Merkle authentication via `fs-verity` (`fs/verity/` [50, 182]). Invoking `ioctl(fd, FS_IOC_ENABLE_VERITY, &arg)` (`struct fsverity_enable_arg`, specifying `version = 1`, `FS_VERITY_HASH_ALG_SHA256` or `SHA512`, `block_size` from `1024` up to `PAGE_SIZE`, optional 32-byte `salt`, and optional `sig_ptr` PKCS#7 signature) requires an `O_RDONLY` descriptor while atomically blocking any concurrent writer across the VFS with `-ETXTBSY` [50, 182]. Once the filesystem persists the Merkle tree past logical `i_size` (stored in hidden post-EOF data extents rounded up to 64 KiB boundaries on `ext4` and `f2fs`, or inside dedicated `BTRFS_VERITY_DESC_ITEM_KEY` and `BTRFS_VERITY_MERKLE_ITEM_KEY` B-tree metadata items on `btrfs` so logical `stat(2)` `st_size` remains unchanged [50, 183]) and sets `S_VERITY` (`FS_VERITY_FL`), the kernel permanently forbids writes and truncates (while still allowing `unlink()` and atomic `rename()` upgrades!). Moreover, querying a file's top-level identifier via `ioctl(fd, FS_IOC_MEASURE_VERITY, &digest)` executes in $O(1)$ constant time and returns a domain-separated *`fs-verity` file digest* computed over `struct fsverity_formatted_digest` (the 8-byte ASCII magic `"FSVerity"`, algorithm ID, `block_size`, 64-bit `i_size`, and `root_hash`), guaranteeing that no crafted short file or alternate block-size tree can ever collide with a genuine `fs-verity` measurement or a flat `SHA-256` hash [50, 182]. Inside `fs/verity/verify.c`, `verify_data_block()` ascends the Merkle tree on every page fault only until hitting an already-verified cached hash page (`PageChecked(hpage)` paired with acquire/release memory barriers `smp_rmb()`/`smp_wmb()` so any hash page evicted under RAM pressure starts fresh with `PG_checked = 0` and *must* re-verify against disk!), explicitly checks that bytes beyond `i_size` on the final `mmap`-visible page are all zeroes (`memchr_inv()`), and optionally checks `sig_ptr` against the kernel `.fs-verity` keyring (`CONFIG_FS_VERITY_BUILTIN_SIGNATURES`, exposing `LSM_INT_FSVERITY_BUILTINSIG_VALID` directly to `IPE` in [Chapter 4](04-ima-ipe-keylime.md)) [50, 182].

Merged into mainline Linux `6.6` [168, 184], `composefs` (`EROFS` + `OverlayFS` `metacopy=on,redirect_dir=on,verity=require`) elevates `fs-verity` into full content-addressed OS and container rootfs immutability (powering `Fedora CoreOS` / `bootc` and `containers/storage` [46, 121, 168]). A compact read-only `EROFS` metadata image (itself protected by a top-level `fs-verity` digest) stores the complete directory tree, permissions, xattrs, `trusted.overlay.redirect` object paths, and expected `trusted.overlay.metacopy` `fs-verity` digests pointing into a shared `/ostree/repo/objects` pool. On first open of any file, kernel `OverlayFS` queries `fsverity_get_digest()` on the backing object in $O(1)$ time and returns `-EIO` (`verity=require`) if `fs-verity` is missing or its Merkle digest differs by a single bit from the `EROFS` manifest, delivering `dm-verity` security with full cross-image file deduplication [168, 184].

## Distro, Immutable-OS, & Cloud Trade-Offs

Mutable distributions (`Ubuntu`, `RHEL`, `Debian`, `SUSE`) prioritize in-place `apt`/`dnf` package mutability and low-latency database I/O, defaulting to `LUKS2` `aes-xts-plain64` without `dm-integrity` (avoiding the roughly $1.5\times$ to $2\times$ random-write amplification of journaled `AEAD`) and leaving `/usr` writable [18, 19]. Operators hardening mutable hosts can still opt into `cryptsetup --cipher aegis128-random --integrity aead` on modern `AES-NI` / ARMv8 Crypto Extension silicon to recover near-native sequential throughput [172, 173], or enable `fs-verity` selectively on high-value system binaries, OCI container layers, and AI model weights [50, 182].

Across immutable operating systems, two distinct architectural lineages balance block-level determinism against storage deduplication [45, 46, 120, 168]. Appliance and Kubernetes node distributions (`Talos Linux`, `AWS Bottlerocket`, `Flatcar Container Linux`, `Azure Linux` immutable profiles) partition the boot drive into dual A/B read-only `dm-verity` `/usr` (or `/`) slots (~1 to 2 GiB `EROFS` or `SquashFS` images) paired with a `systemd-repart`-provisioned `LUKS2` `/var` partition [45, 160, 178, 180]. Even more aggressively, hermetic `systemd` builds run with an *ephemeral root filesystem* (`/` mounted as a size-bounded `tmpfs` in RAM or `systemd.volatile=state`), populating `/etc` and `/var` declaratively at every boot via `systemd-tmpfiles` and `systemd-confext` so any unauthorized runtime drift outside persistent volumes evaporates completely on reboot [2, 30]. Conversely, general-purpose immutable distributions (`Fedora CoreOS`, `Fedora Atomic Desktops`, `RHEL Image Mode` powered by `OSTree` and `bootc` [46, 120, 121]) avoid maintaining fixed-size dual A/B partitions by storing deduplicated files inside `/ostree/repo/objects` on a single `LUKS2` filesystem and mounting each versioned OS deployment through `composefs` (`EROFS` + `OverlayFS` `verity=require` [168, 184]), preserving local `/etc` edits via a tracked three-way merge while still enforcing demand-paged `fs-verity` Merkle checks on every executable page fault.

In public-cloud infrastructure (`AWS EBS`, `GCP Persistent Disk`, `Azure Managed Disks`), cloud-provider "encryption at rest" encrypts physical NVMe sleds transparently inside the host storage controller: that protects retired drives leaving a data center, yet gives zero protection against compromised cloud control planes, misconfigured snapshot shares, or sibling-tenant volume attaches because the hypervisor decrypts blocks unconditionally for any VM granted volume attachment! Running guest-managed `LUKS2` (sealed to `vTPM` `PCR[11]` or `COCONUT-SVSM` inside `AMD SEV-SNP` / `Intel TDX` Confidential VMs in [Chapter 18](18-confidential-vms-svsm.md)) paired with `dm-verity` `/usr` ensures the untrusted cloud storage fabric sees only authenticated ciphertext and cannot inject modified OS blocks without triggering immediate `DM_VERITY_MODE_RESTART` halts [11, 20, 175].

## Seam Failures, CVEs, & Structural Bounds

Storage-integrity failures cluster wherever operators trust closed-source `OPAL` drive firmware alone, assume unauthenticated `AES-XTS` encryption detects tampering, leave `roothash` outside signed `UKI` command lines, or mount writable overlays with `exec` permissions.

Notice the crucial architectural boundary revealed by Row 9: *`dm-verity` and `fs-verity` are storage integrity primitives, not system-wide execution policies*. Mounting `/usr` over `dm-verity` guarantees that `/usr/bin/sshd` has not changed by a single bit, yet nothing in `dm-verity` stops a compromised service from downloading an unsigned binary into `/dev/shm` or `/var/tmp` and invoking `execve()` or `dlopen()` on it! Two operational subtleties also merit explicit engineering choices on encrypted and verity-protected flash drives [18, 20, 175]. First, enabling SSD `TRIM` pass-through on `LUKS2` (`--allow-discards` in `/etc/crypttab`) improves NVMe wear-leveling and write performance, yet reveals to an offline forensic observer *which* 4 KiB LBA sectors are unused zeroes versus occupied ciphertext (leaking approximate filesystem fullness and allocation patterns); high-paranoia travel laptops omit `discard` at the cost of lower sustained SSD write speeds [18]. Second, configuring `dm-verity` with `restart_on_corruption` (`DM_VERITY_MODE_RESTART`) without pairing it to automatic bootloader boot-counting (`systemd-bless-boot.service` decrementing `vmlinuz+3-0.efi` tries on the ESP [28, 140]) risks an infinite reboot loop if physical NAND flash wear exceeds `--fec-device` Reed-Solomon parity capacity! Properly wired A/B systems decrement the active UKI's boot counter before mount so three consecutive `dm-verity` restarts automatically fail over to the known-good previous `_usr_a` slot [160, 175]. Enforcing that *only* `dm-verity`- or `fs-verity`-verified code may ever be mapped executable (`PROT_EXEC`) requires coupling storage verity to a mandatory access control execution gate ([Chapter 4](04-ima-ipe-keylime.md)).

> **Warning.**
> Never configure `cryptsetup --hw-opal-only` (delegating confidentiality exclusively to an NVMe drive's closed-source TCG `OPAL` controller) or trust cloud block-storage "at-rest encryption" against an adversary with physical drive or hypervisor storage access. Always keep Ring 0 software `dm-crypt` in the data path (`cryptsetup --hw-opal` double-encrypts if hardware locking is desired) and pair read-write volumes carrying security-critical state with `dm-integrity` `AEAD` so silent `XTS-AES` sector replay and 16-byte block malleability fail closed with `-EIO` [18, 19, 166, 167].

## Inspecting on a Live Linux Host

Inspect active device-mapper targets (`crypt`, `verity`, `integrity`), GPT Partition Type UUIDs (`DPS`), and `dm-verity` corruption-handling flags (`restart_on_corruption`):

```bash
lsblk -o NAME,TYPE,FSTYPE,PARTTYPE,MOUNTPOINTS,RO
# Requires CAP_SYS_ADMIN (root / run0) to query device-mapper table parameters
dmsetup status 2>/dev/null
```

Examine `LUKS2` keyslot KDF parameters (`argon2id`, memory cost, `AF` stripes, and `dm-integrity` / `OPAL` segment metadata) on an encrypted partition:

```bash
cryptsetup luksDump /dev/nvme0n1p3 2>/dev/null | grep -A 8 -E "Keyslots:|Memory:|Data segments:|Tokens:"
```

Check `systemd-repart` dry-run partition plans, `systemd-sysext` / `systemd-confext` DDI overlays, and per-file `fs-verity` digests:

```bash
systemd-repart --dry-run=yes 2>/dev/null || true
systemd-sysext status 2>/dev/null
fsverity measure /usr/bin/bash 2>/dev/null || lsattr -d /usr/bin/bash 2>/dev/null
```
