# Universal Enforcing SELinux, CTS neverallow Gates, and seccomp-BPF

## Overview

* **Link in the Chain:** Host `EL1` kernel Mandatory Access Control (`MAC`) and system-call confinement layer; bounds every userspace daemon, HAL, and application inside default-deny domains while stripping unreachable kernel syscall surfaces.
* **Core Security Invariant:** Every kernel object access `(subject_context, target_context, object_class, permission)` is denied unless explicitly permitted by the compiled `sepolicy` binary, zero production domains run permissive, every OEM policy satisfies AOSP's `neverallow` invariants verified by `CTS`, and untrusted apps execute beneath an immutable `seccomp-BPF` syscall allowlist with zero POSIX capabilities.
* **Ecosystem Enforcement Tier:** 100% enforcing across `GREEN` and `YELLOW` locked builds (`GrapheneOS` further tightens `untrusted_app` `sepolicy`, `userfaultfd`, `perf_event_open`, and `seccomp` surfaces); remains enforcing by default even on stock `ORANGE` unlocked builds unless a root user explicitly patches the kernel or boots a permissive custom `boot.img`.
* **Trusted Computing Base (TCB):** Linux Security Module (`LSM`) hooks (`security/selinux/`), Access Vector Cache (`AVC`) and `allowxperm` 16-bit `ioctl` evaluator, `init` early-boot split `CIL` compiler (`secilc`) and policy loader (`system/core/init/selinux.cpp`), `seapp_contexts` + `MLS`/`MCS` constraint engine, `Zygote` `bionic/libc/seccomp` BPF filters, and `CTS` `SELinuxHostTest`.
* **Seam & Handoff:** Contains compromised `UID 0` daemons and blocks untrusted apps from opening raw `/dev` driver nodes or exotic syscalls, but executes *inside* the host `EL1` kernel; hands `Treble`/`GKI` structural splitting, `KCFI`, and memory-safe kernel `Rust` hardening to [Chapter 7](07-treble-gki-rust.md).

## Threat Model & Ecosystem Constraint

Before Android 4.3 (`Jelly Bean`) introduced permissive logging and Android 5.0 (`Lollipop`) flipped enforcement on universally, Android relied almost exclusively on traditional Linux Discretionary Access Control (`DAC`) [2, 74]. Per-application Linux user IDs (`u0_a*`) separated third-party apps from one another on `/data/data`, while dozens of native system daemons (`vold`, `netd`, `installd`, `rild`, `debuggerd`, `mediaserver`, and SoC vendor camera, modem, or thermal services) executed as unconstrained `UID 0` (`root`) or `UID 1000` (`system`) [2, 24, 74]. Across billions of shipped handsets, that DAC-only perimeter failed systematically along four structural vectors [24, 72, 79, 214]:

First, *omnipotent root daemons turned single parser bugs into total device compromise*. Under standard UNIX `DAC`, `UID 0` bypasses file mode bits (`CAP_DAC_OVERRIDE`), loads kernel modules (`CAP_SYS_MODULE`), attaches debuggers to arbitrary processes (`CAP_SYS_PTRACE`), and opens raw block partitions (`/dev/block/by-name/system`). Whenever a malformed Netlink message, USB volume label, or baseband socket payload compromised a single `UID 0` helper daemon such as `vold` or `netd`, the attacker immediately inherited unrestricted authority over every application's private SQLite databases, credential stores, and kernel memory [74, 215].

Second, *Discretionary Access Control permitted owners to give away their own secrets*. Under `DAC`, the owner of an inode controls its mode bits via `chmod()` and `fchmod()`. Whenever a developer mistakenly created a world-readable preference file (`MODE_WORLD_READABLE` or `chmod 0666`) or followed an attacker-planted symbolic link inside a shared cache directory, `DAC` dutifully honored the permissive mode bits and let co-installed malware harvest OAuth tokens or overwrite internal files [74, 215].

Third, *OEM and SoC Board Support Package (`BSP`) sprawl silently eroded AOSP's baseline*. During hardware bring-up under tight commercial schedules, SoC vendors and OEMs routinely added factory calibration servers, AT-command forwarders (`atfwd`), and diagnostic character devices (`/dev/diag`, `/dev/mem`, or `/dev/kgsl-3d0` configured with `chmod 0666` in `ueventd.rc`), or left vendor daemons running without confinement, punching unreviewed privilege-escalation holes through millions of retail phones [79, 215, 216].

Fourth, *the upstream Linux kernel exposed an enterprise-wide syscall and `ioctl` attack surface to untrusted mobile code*. Upstream Linux implements more than `300` system calls designed for multi-tenant servers, supercomputers, and desktop workstations, including kernel keyrings (`add_key`, `keyctl` exploited in `CVE-2016-0728` [217]), asynchronous ring I/O (`io_uring_setup` [76]), unprivileged page-fault stalling (`userfaultfd` [218]), hardware performance counters (`perf_event_open` [219]), legacy `futex` requeuing (`CVE-2014-3153`, exploited by *Towelroot* [220]), `pipe` `iovec` scatter-gather paths (`CVE-2015-1805`, exploited by *KingRoot* [221]), and Copy-on-Write fault races (`CVE-2016-5195`, *Dirty COW* [222]), alongside tens of thousands of driver-specific `ioctl()` command codes [72, 214].

Transforming `SELinux` from an optional server module notoriously set to `Permissive` by frustrated administrators into a *100 percent universal, zero-exception enforcing reference monitor across hundreds of independent hardware manufacturers* required solving three problems together: modularizing policy compilation across OS updates (`CIL`), proving negative security invariants mechanically in `CTS` (`neverallow`), and filtering syscalls *before* kernel subsystem entry (`seccomp-BPF`) [24, 72, 79, 223].

## Architecture & AOSP Implementation

### First-Stage Policy Loading and Split Common Intermediate Language (`CIL`) Compilation

Android deploys `SELinux` (`security/selinux/` in the Linux kernel, adapted for mobile in the NSA and Google SEAndroid project [74]) in strict default-deny Type Enforcement (`TE`) paired with Multi-Category Security (`MCS`) [24, 224]. Bootstrapping `SELinux` happens inside first-stage `init` (`system/core/init/selinux.cpp`) before a single userspace service starts or a single network interface comes up [225]. Immediately after the kernel mounts `rootfs` and first-stage `init` sets up `dm-verity`-authenticated `/system`, `/system_ext`, `/product`, `/vendor`, and `/odm` partitions ([Chapter 2](02-antirollback-verity-apex.md)), `SelinuxInitialize()` assembles the unified binary policy, writes it into `/sys/fs/selinux/load`, enforces `/sys/fs/selinux/enforce = 1` unconditionally on `user` builds (ignoring kernel command-line `androidboot.selinux=permissive` overrides when compiled with `ALLOW_PERMISSIVE_SELINUX = 0`), applies `selinux_android_restorecon()` to `/dev` and runtime tmpfs directories, and invokes `execv("/system/bin/init", ...)` so `PID 1` transitions out of the initial `u:r:kernel:s0` bootstrap context into `u:r:init:s0` [223, 225].

Through Android 7.x, building `sepolicy` concatenated all AOSP `system/sepolicy` and OEM `BOARD_SEPOLICY_DIRS` `.te` files into a single monolithic `policy.conf` compiled offline into `/sepolicy` inside the root ramdisk [223]. That monolithic binary coupled `/system` and `/vendor` inextricably: Google could not ship a framework-only Over-the-Air (`OTA`) update or Generic System Image (`GSI`) without overwriting or breaking the OEM's vendor HAL policy rules [216, 223].

Starting in Android 8.0 (`Project Treble`) and extended across `/system_ext`, `/product`, and `/odm` in Android 11 through Android 17, AOSP replaced monolithic policy blobs with modular *SELinux Common Intermediate Language (`CIL`)* compilation (`external/selinux/secilc`) [216, 223, 226]. Under `system/sepolicy/Android.bp`, platform policy is partitioned into two visibility tiers: `system/sepolicy/public` (stable types and attributes exported as a formal API to vendor policy authors, such as `vendor_init`, `hal_camera_server`, or `sysfs`) and `system/sepolicy/private` (internal framework domains and types invisible to `/vendor`, free to evolve across OS releases) [216, 223].

![Figure: Treble split Common Intermediate Language (CIL) compilation and Multi-Category Security (MCS) category-pair isolation across apps and user profiles.](diagrams/06-extra-cil-treblesplit-mls.svg)

Consider the subtle compatibility hazard that arises across an OS upgrade [216]: suppose a handset launches on vendor API level `202404` where `/sys/class/udc` carries the generic `sysfs` label, and the OEM's `/vendor` policy grants `allow vendor_init sysfs:chr_file rw_file_perms;`. One year later, a framework-only OTA updates `/system` to API level `202504`, which refines `/sys/class/udc` to a narrower `sysfs_udc` type (`plat_sepolicy_genfs_202504.cil`) or splits an internal framework domain [216]. If `/vendor` referenced raw type names directly, the OTA would silently strip `vendor_init` of USB controller access and brick boot!

Android's split `CIL` pipeline prevents both breakage and privilege creep through *versioned compatibility attributes* (`PLATFORM_SEPOLICY_VERSION`, formatted as `YYYYMM` such as `202504`) [216, 223]. When the OEM builds `vendor.img` against platform API `202504`, the build compiler transforms every platform-public type referenced inside `vendor_sepolicy.cil` into a version-stamped attribute (`vendor_init_202504`, `sysfs_202504`), shipped alongside `/vendor/etc/selinux/plat_pub_versioned.cil` and `/vendor/etc/selinux/vendor_file_contexts` [216, 223]. Meanwhile, `/system/etc/selinux/` ships `plat_sepolicy.cil` plus a directory of historical backward-compatibility mapping files (`/system/etc/selinux/mapping/202404.cil`, `202504.cil`, etc.) containing `typeattributeset` statements that bind old versioned attributes (`sysfs_202404`) to both `sysfs` and any newly carved-out subtypes (`sysfs_udc`), gated further by `/vendor/etc/selinux/genfs_labels_version.txt` (`BOARD_GENFS_LABELS_VERSION`) [216].

To avoid penalizing normal cold-boot latency, `/vendor/etc/selinux/precompiled_sepolicy` caches the pre-linked binary policy alongside `plat_sepolicy_and_mapping.sha256` [223, 225]. During first-stage `init`, `OpenSplitPolicy()` hashes `/system`'s active CIL and mapping files: if the SHA-256 digests match those recorded on `/vendor`, `init` loads `precompiled_sepolicy` straight into `/sys/fs/selinux/load` in milliseconds; if `/system` was updated independently via a Mainline-style system OTA or Dynamic System Update (`DSU`) `GSI`, `init` automatically invokes `/system/bin/secilc` in early boot to link `plat_sepolicy.cil`, `mapping/<ver>.cil`, `plat_pub_versioned.cil`, and `vendor_sepolicy.cil` on the fly before locking `enforce = 1` [223, 225, 226]!

### `mac_permissions.xml`, `seapp_contexts`, and `MLS`/`MCS` Category-Pair Isolation

Every process (`subject`) and every kernel or userspace resource (`object`, covering files, character/block devices, sockets, `ipc`, `anon_inode`, system properties, `Binder` services, and `keystore2` namespaces) carries a four-component security context `user:role:type:mls_level` (for example `u:r:untrusted_app:s0:c214,c256,c512,c768`) [24, 74, 215]. Android fixes `user` to `u` and `role` to `r` for tasks or `object_r` for objects, concentrating Mandatory Access Control inside two orthogonal dimensions: the *Type Enforcement (`TE`) domain/type* and the *Multi-Level / Multi-Category Security (`MLS`/`MCS`) category set* [24, 74, 224].

![Figure: Universal enforcing SELinux domain separation, allowxperm ioctl filtering, and CTS neverallow certification gates.](diagrams/06-selinux-domain-mediation.svg)

Whenever any task invokes a VFS, socket, `ptrace`, `bpf`, or `Binder` operation, the kernel LSM hook queries the Access Vector Cache (`avc_has_perm()` in `security/selinux/avc.c`) [24, 227]. Unless an explicit `allow source_type target_type:object_class { perm_set };` rule exists in the compiled policy graph, the kernel rejects the operation with `-EACCES` and emits a rate-limited `type=1400 audit(...): avc: denied` record (traceable down to unified kernel+userspace call stacks via the `avc:selinux_audited` tracepoint in `simpleperf` on Linux 5.10+ [79]). Unlike desktop Linux distributions (`targeted` policy) where interactive user shells run inside `unconfined_t`, *zero unconfined domains exist on Android* [24, 74]. Even `UID 0` daemons are boxed into narrow functional silos: `vold` mounts block volumes and configures `fscrypt` inline encryption keys, yet `SELinux` denies `vold` network sockets or read access to `app_data_file`; `netd` configures `ebpf` traffic filters and DNS sockets, yet cannot open block devices or `system_data_file` [24, 215]. Beyond kernel objects, Android enforces `SELinux` across three critical userspace object managers via `libselinux` [215, 228]: `init` checks `property_contexts` before permitting any `property_set()` write (stopping compromised HALs from spoofing `ro.boot.*` or `security.*` flags); `servicemanager` and `vndservicemanager` check `service_contexts` and `vndservice_contexts` on `add_service` and `find_service` (`isolated_app` processes cannot even look up handles to `IActivityManager` or `IKeystoreService`); and `keystore2` checks `keystore2_key_contexts` to confine hardware-backed key namespaces [186, 215].

How does Android assign the right `SELinux` domain and `MCS` categories to millions of dynamically installed third-party apps without recompiling `sepolicy`? Through a two-stage lookup spanning `mac_permissions.xml` and `seapp_contexts` (`system/sepolicy/private/seapp_contexts`), evaluated by `libselinux` (`selinux_android_setcontext()` for processes in `Zygote` and `selinux_android_setfilecon()` for `/data/user/<u_id>/<pkg>` directories in `installd`) [215, 228, 229]:

```text
# Illustrative rules from AOSP system/sepolicy/private/seapp_contexts
user=_app isPrivApp=true  seinfo=platform           domain=platform_app       type=app_data_file     levelFrom=user
user=_app isPrivApp=true                            domain=priv_app           type=privapp_data_file levelFrom=user
user=_app minTargetSdkVersion=33                    domain=untrusted_app      type=app_data_file     levelFrom=all
user=_app minTargetSdkVersion=30                    domain=untrusted_app_30   type=app_data_file     levelFrom=all
user=_app isEphemeralApp=true                       domain=ephemeral_app      type=app_data_file     levelFrom=all
user=_isolated isIsolatedComputeApp=true            domain=isolated_compute_app                      levelFrom=all
user=_isolated                                      domain=isolated_app       levelFrom=all
```

First, at APK install time, `PackageManagerService` matches the APK's verified signing certificate ([Chapter 10](10-apk-signing-scoped-storage.md)) against `/system/etc/selinux/plat_mac_permissions.xml` and `/vendor/etc/selinux/vendor_mac_permissions.xml` to derive an authenticated `seinfo` string (`platform`, `media`, `network_stack`, or `default` for Play/sideloaded apps) [215]. Second, when `Zygote` specializes the process, `libselinux` matches `(user, isPrivApp, seinfo, name, isEphemeralApp, isIsolatedComputeApp, minTargetSdkVersion, fromRunAs)` against `seapp_contexts` [228, 229]. Notice two surgical design choices in that table. Legacy apps targeting older SDKs land in versioned domains (`untrusted_app_29`, `untrusted_app_30`, `untrusted_app_32`) so AOSP can tighten `SELinux` restrictions (such as blocking execute-from-home `execmod` or raw `/proc/net` reads) on modern `untrusted_app` targets without breaking older binaries overnight [229]. Meanwhile, Instant Apps land in `ephemeral_app`, and sandboxed on-device AI workloads inside Private Compute Core (`AICore`, [Chapter 18](18-on-device-agentic-ai.md)) land in `isolated_compute_app` [229, 230].

Now look closely at `levelFrom=all` on `untrusted_app` [224, 228, 229]! Every third-party app targeting modern Android shares the *same* `TE` domain name `untrusted_app`, and its files share `app_data_file`. If `TE` allow rules include `allow untrusted_app app_data_file:file { read write open };`, what stops App A (`u0_a214`) from opening App B's (`u0_a215`) files if App B accidentally `chmod 0777`s its directory, OR what stops Personal App A (`u0_a214` in `user 0`) from touching Work Profile App A (`u10_a214` in `user 10`), which shares the *same* `appId = 10214`?

Android's `libselinux` (`context_from_level` in `android_platform.c`) solves both problems simultaneously by encoding a *four-category `MCS` tuple* into `s0` whenever `levelFrom=all` is specified [224, 228]. Given `appId` offset $A = \text{appId} - 10000$ and multi-user profile ID $U = \text{userId}$, `libselinux` emits two disjoint category pairs inside `c0..c1023`:

$$\text{MCS}(A, U) = \bigl\{\; c_{(A \bmod 256)},\; c_{256 + \lfloor A / 256 \rfloor},\; c_{512 + (U \bmod 256)},\; c_{768 + \lfloor U / 256 \rfloor} \;\bigr\}$$

For example, `u0_a214` ($A = 214, U = 0$) receives `s0:c214,c256,c512,c768`; co-installed `u0_a215` ($A = 215, U = 0$) receives `s0:c215,c256,c512,c768`; and the Work Profile clone `u10_a214` ($A = 214, U = 10$) receives `s0:c214,c256,c522,c768` [224, 228]! Inside `system/sepolicy/private/mls`, mandatory `mlsconstrain` expressions wrap `file`, `dir`, `lnk_file`, `sock_file`, and `process` (`ptrace`, `sigkill`) classes [224]: unless the subject carries `mls_trustedsubject` (held only by tightly audited system brokers like `installd` or `vold`) or the target carries `mlstrustedobject` (such as `/dev/binder` or `/dev/null`), access succeeds *if and only if `l1 eq l2` (exact category-set equality)* [74, 224]! Because no single category (`c214`) is ever used alone and bank categories (`c256+`, `c512+`, `c768+`) make every `(A, U)` pair an incomparable 4-element set of identical cardinality, neither `dom` nor `eq` can ever be satisfied across distinct apps or distinct user profiles, turning `SELinux` into a mandatory cross-app and cross-profile firewall even if POSIX `DAC` permissions fail completely [224]!

### `CTS` `SELinuxHostTest`, `checkfc`, and Compile-Time `neverallow` Proofs

How does Google prevent hundreds of OEMs and ODM contractors from silencing `avc: denied` bring-up logs by pasting `permissive vendor_cam_daemon;` or `allow untrusted_app vendor_diag_device:chr_file rw_file_perms;` via reckless `audit2allow` usage [79, 231]? Through compile-time `neverallow` theorem proving backed by `CTS` hardware binary auditing [11, 79, 231, 232].

In `system/sepolicy/public/domain.te`, `app.te`, and `private/untrusted_app_all.te`, AOSP defines hundreds of negative `neverallow` invariants across domain and file attributes [232]:

```text
# Illustrative negative invariants from AOSP system/sepolicy/public/domain.te & app.te
neverallow { domain -kernel -init -vendor_init } kernel:security setenforce;
neverallow { domain -init } kernel:security load_policy;
neverallow untrusted_app_all { dev_type -app_accessible_dev }:chr_file { read write open };
neverallow untrusted_app_all dev_type:blk_file { read write open };
neverallow { appdomain -shell } self:capability *;
neverallow * { file_type -exec_type }:file entrypoint;
neverallow domain debugfs_type:file { open read write };
```

Enforcement operates at three independent checkpoints so no partner build server can cheat [79, 223, 231]. First, during AOSP/vendor build compilation, `checkpolicy` and `secilc` evaluate every `neverallow` rule over the expanded attribute-to-type Cartesian product; any intersecting `allow` or `allowxperm` rule anywhere in `BOARD_SEPOLICY_DIRS` aborts compilation immediately, while `checkfc` validates every regular expression and security context in `file_contexts`, `property_contexts`, `service_contexts`, and `seapp_contexts` against the compiled policy [223, 231]. Second, Android 11+ banned mounting or accessing `debugfs` (`/sys/kernel/debug`) on production devices via both `neverallow` and `VTS` mount checks, eliminating thousands of leaky kernel debug nodes in one stroke [216]. Third, during mandatory GMS certification, `CTS` runs `SELinuxHostTest` (`cts/hostsidetests/security/src/android/security/cts/SELinuxHostTest.java`) from a host workstation over `adb` [11, 231]: `SELinuxHostTest` verifies `getenforce == Enforcing`, pulls the live active `/sys/fs/selinux/policy` binary directly from kernel memory on the physical handset, runs `sepolicy-analyze -p` to assert that *zero* domains have the `permissive` bit set in the kernel's live policy database, validates `seapp_contexts` and `file_contexts` labeling on `/system` and `/vendor`, and re-runs AOSP's canonical `neverallow` suite directly against the handset's extracted binary policy [79, 231]!

### Extended Permissions (`allowxperm`) and Granular `ioctl` Command Whitelisting

Standard `SELinux` `avc` access vectors contain 32 permission bits per object class (`read`, `write`, `open`, `mmap`, `ioctl`, etc.) [214, 227]. That granularity breaks down at `ioctl(int fd, unsigned long cmd, ...)`: every `untrusted_app` *must* hold `ioctl` permission on `/dev/binder`, `unix_stream_socket` / `udp_socket` descriptors, and the SoC's GPU render node (`/dev/mali0` or `/dev/kgsl-3d0`) to execute IPC and Vulkan/GLES rendering, yet a single GPU or network driver routinely multiplexes 80 to 150 distinct `ioctl` command codes behind that one file descriptor, including legacy profiling, hardware-address leak (`SIOCGIFHWADDR`), or debug-register commands that no untrusted app should ever invoke [214, 219].

Android 7.0+ solved this driver multiplexing gap via `SELinux` Extended Permissions (`allowxperm`, upstreamed in `security/selinux/avc.c` and `ss/services.c` by Jeff Vander Stoep and Google's kernel team) [214, 219, 227]. On every `ioctl` syscall, `selinux_file_ioctl()` extracts the low 16 bits of `cmd` (`driver_type = _IOC_TYPE(cmd)` in bits `[15:8]` and `function_nr = _IOC_NR(cmd)` in bits `[7:0]`). Whenever *any* `allowxperm` statement targets a `(source_domain, target_type, object_class, ioctl)` tuple, `SELinux` transitions that descriptor's `ioctl` space from all-or-nothing into a 65,536-bit default-deny bitmap (stored compactly as 256-bit `avc_xperms_decision` chunks per `_IOC_TYPE` prefix), rejecting every non-allowlisted hex command code at the LSM boundary before the underlying GPU or socket `unlocked_ioctl` handler ever executes a single line of C [214, 227]!

```text
# Illustrative allowxperm whitelisting in AOSP system/sepolicy/public/domain.te
allowxperm untrusted_app_all self:udp_socket ioctl { SIOCGIFINDEX SIOCGIFNETMASK };
# SIOCGIFHWADDR (0x8927) is omitted -> hardware MAC address leak blocked in kernel!
```

### `Bionic` `seccomp-BPF` Architecture (`SYSCALLS.TXT` to `Zygote` Filter Installation)

Even with `SELinux` and `allowxperm` active, `LSM` hooks sit *inside* kernel subsystems: a syscall like `keyctl()` (`CVE-2016-0728` [217]), `futex()` (`CVE-2014-3153` [220]), or `io_uring_setup()` [76] parses user flags, allocates kernel structures, and traverses reference-counted lists *before* reaching an `LSM` hook, or executes along paths with no `LSM` hook at all [72, 76]. Android closes that pre-LSM kernel surface by pairing complete POSIX capability eradication with `seccomp-BPF` (`CONFIG_SECCOMP_FILTER`, `Documentation/userspace-api/seccomp_filter.rst` [233]) inside `Bionic` `libc` (`bionic/libc/seccomp/`) [72, 234, 235].

![Figure: Zygote process-specialization pipeline installing seccomp-BPF syscall filters, dropping POSIX capabilities, and locking SELinux domains.](diagrams/06-zygote-seccomp-pipeline.svg)

Rather than maintaining hand-written, error-prone BPF assembly, AOSP derives its syscall filters directly from `bionic/libc/SYSCALLS.TXT` (the authoritative manifest of every C library syscall wrapper actually used by Android's `Bionic` runtime) combined with `SECCOMP_ALLOWLIST_APP.TXT` and `SECCOMP_BLOCKLIST_APP.TXT` via Python build generators (`gensyscalls.py` and `gen_seccomp.py`) [72, 234, 235]. At build time, AOSP compiles balanced binary-search `sock_filter` BPF trees (`arm64_app_filter`, `arm64_app_zygote_filter`, `arm64_system_filter`) directly into `libc.so` (`bionic/libc/seccomp/seccomp_policy.cpp`), keeping per-syscall filter evaluation to $O(\log N)$ instructions ($\approx 8$ BPF comparisons!) [72, 234].

Trace what `ForkCommon()` and `SpecializeCommon()` (`frameworks/base/core/jni/com_android_internal_os_Zygote.cpp`) execute inside every freshly forked child before returning to untrusted application bytecode [234, 236, 237]:

First, `Zygote` unshares mount namespaces (`unshare(CLONE_NEWNS)`) to isolate per-app storage bind mounts ([Chapter 10](10-apk-signing-scoped-storage.md)). Second, it clears all POSIX capability sets (`Effective`, `Permitted`, `Inheritable`, `Ambient`) via `capset()` and drops the capability `Bounding` set (`PR_CAPBSET_DROP`), ensuring zero `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, `CAP_NET_RAW`, or `CAP_DAC_OVERRIDE` authority survives [75, 237]. Third, `set_app_seccomp_filter()` sets `prctl(PR_SET_NO_NEW_PRIVS, 1)` (an irreversible kernel task flag guaranteeing no subsequent `execve()` can ever gain privilege) and loads `FilterType::APP` via `prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &prog)` before `setresgid()` / `setresuid()` drops identity to `u0_aXYZ` and `selinux_android_setcontext()` locks the task into `untrusted_app` or `isolated_app` [72, 234, 237].

Look closely at the three distinct `seccomp_policy.cpp` profiles and the exact syscalls they sever [72, 76, 234, 235]: `FilterType::APP` first validates `seccomp_data.arch == AUDIT_ARCH_AARCH64` (blocking 32-bit compatibility syscall table confusion on 64-bit processes!), allowlists the ~`270` syscalls needed by `Bionic` and `ART`, and immediately traps (`SECCOMP_RET_TRAP`, delivering fatal `SIGSYS` to `debuggerd` for tombstone telemetry) over `130` dangerous Linux syscalls including `keyctl`, `add_key`, `request_key`, `bpf`, `userfaultfd` (additionally gated via `SELinux` `anon_inode` `userfaultfd` class so only `ART` concurrent compaction can request it where permitted), `io_uring_setup`, `io_uring_enter`, `io_uring_register`, `perf_event_open` (further locked behind `LSM` hooks and `sysctl` `perf_event_paranoid`), `kexec_load`, `init_module`, `finit_module`, `delete_module`, `acct`, `swapon`, `swapoff`, `mount`, `umount2`, `pivot_root`, `chroot`, `open_by_handle_at`, `syslog`, `vmsplice`, and `uselib` [72, 76, 219, 234]. Meanwhile, `FilterType::APP_ZYGOTE` (`set_app_zygote_seccomp_filter()`, used by `AppZygote` preloaders in [Chapter 9](09-uid-zygote-binder.md)) inspects `seccomp_data.args[0..2]` on `setresuid()` and `setresgid()` inside BPF instructions so an `AppZygote` process can transition child workers *only* within its allocated `[uid_gid_min, uid_gid_max]` isolated UID slice (`90000..98999`) and never to `0` or another app's `UID` [234, 235]! Native media extractors and codecs (`media.extractor`, `media.swcodec`) go further still, loading bespoke per-daemon `minijail` (`libavservices_minijail`) `seccomp` policies that strip `socket()`, `connect()`, and `openat()` down to less than a few dozen pure computation and `Binder` syscalls [72, 238].

Empirical payoff arrived dramatically during 2021-2023 when `io_uring` became the #1 source of Linux kernel zero-days and Google `kCTF` exploit submissions (accounting for `60%` of `kCTF` payouts!) [76]: because Android had preemptively blocked `io_uring_setup`, `io_uring_enter`, and `io_uring_register` across `untrusted_app` via `SELinux` (`io_uring` object class) and `seccomp-BPF`, the entire wave of upstream `io_uring` exploits landed harmlessly dead-on-arrival against Android apps [76]!

## Vendor, OEM, & Custom-OS Boundaries

While `Project Treble`'s split `CIL` design and `CTS` `SELinuxHostTest` eradicated `permissive` OEM domains on certified `GREEN` phones, vendor `sepolicy` quality inside `/vendor/etc/selinux` remains uneven across the ecosystem [43, 79, 216]. If an OEM groups ten disparate proprietary HALs under an overly broad vendor attribute or grants `untrusted_app` access to a custom `/dev/vendor_*` NPU/DSP accelerator node that passes `neverallow` only because its custom `dev_type` was marked `app_accessible`, kernel driver bugs inside that vendor node become reachable from zero-permission apps [43, 79].

Hardened `YELLOW`-state `GrapheneOS` builds tighten both `SELinux` and `seccomp-BPF` substantially beyond AOSP's compatibility floor [20, 239]: `GrapheneOS` unconditionally blocks `userfaultfd` and `perf_event_open` for untrusted domains (`kernel.perf_event_paranoid = 3`), removes `untrusted_app` read access to residual `/proc` and `/sys` side-channel nodes, enforces strict dynamic code loading (`W^X` memory / `execmem` and file `execmod` denials configurable per app), blocks `io_uring` system-wide even for privileged processes, and implements a revocable `INTERNET` toggle enforced directly at kernel `socket()` creation via supplementary group / `SELinux` checks [20].

## Exploit Chains & Structural Limits

Because `SELinux`, `allowxperm`, and `seccomp-BPF` severed exotic syscalls and unmediated `/dev` nodes, modern Android kernel exploits must tunnel through the narrow set of kernel interfaces an `untrusted_app` or `isolated_app` *must* legitimately invoke (`/dev/binder`, `/dev/mali0` or `/dev/kgsl-3d0`, `epoll`, `futex`, `pipe`, and standard `AF_INET`/`AF_UNIX` sockets), and then use arbitrary `EL1` read/write primitives to disarm `SELinux` in kernel RAM.

### The Theoretical Ceiling of an In-Kernel Reference Monitor

That eighth row states the fundamental architectural boundary of `SELinux` and `seccomp-BPF` with mathematical clarity: *both mechanisms execute inside `EL1` kernel virtual memory and therefore share the fate of the `EL1` memory-safety perimeter* [2, 241]. `seccomp-BPF` and `SELinux` shrink the reachable `EL1` attack surface by more than an order of magnitude, blocking `io_uring`, `keyctl`, `debugfs`, raw block devices, and unapproved `ioctl` codes before untrusted input can touch them [72, 76, 214]. Yet once a vulnerability inside an *allowed* `EL1` entry point (`Binder` or a `Mali`/`Adreno` GPU shader memory-mapping `ioctl`) grants an attacker an arbitrary kernel read/write primitive, the attacker does not need to bypass `KCFI` or load a kernel module: a two-write *data-only attack* overwriting `current->cred` to `UID 0` (`u:r:kernel:s0`) and writing `0x00` to `selinux_state.enforcing` in `EL1` `.data` disables `SELinux` globally until the next verified reboot [17, 241].

> **Key takeaway.**
> `SELinux` and `seccomp-BPF` ensure that compromising a `UID 0` userspace daemon no longer compromises the kernel, and prevent untrusted apps from reaching 90 percent of dusty Linux kernel subsystems. Defending the remaining 10 percent of reachable `EL1` code requires compartmentalizing vendor HALs out of framework daemons (`Project Treble`), unifying kernel patch delivery (`GKI` 2.0), hardening C control flow (`KCFI` and `SCS`), and eliminating memory-safety bugs at compile time with *Rust* in [Chapter 7](07-treble-gki-rust.md).

## Inspecting via ADB, Fastboot, & Attestation

Verify that `SELinux` is actively running in `Enforcing` mode and inspect the live four-part `SELinux` contexts (`-Z`, noting the 4-element `MCS` category tuple `c*` on `untrusted_app` processes) across `init`, `system_server`, `keystore2`, and running apps:

```bash
adb shell getenforce
adb shell ps -AZ | grep -E 'u:r:(init|system_server|keystore|untrusted_app):' | head -n 8
```

Verify active split `CIL` policy artifacts and backward-compatibility mapping versions (`YYYYMM.cil`) across `/system/etc/selinux` and `/vendor/etc/selinux`:

```bash
adb shell ls -l /system/etc/selinux/plat_sepolicy.cil /system/etc/selinux/mapping/ | head -n 8
adb shell ls -l /vendor/etc/selinux/precompiled_sepolicy /vendor/etc/selinux/plat_pub_versioned.cil
```

Confirm `seccomp-BPF` filter enforcement (`Seccomp: 2` denotes `SECCOMP_MODE_FILTER`) alongside zeroed POSIX capability bitmasks (`CapEff: 0000000000000000`, `NoNewPrivs: 1`) on any running application process:

```bash
APP_PID=$(adb shell pidof com.android.chrome | awk '{print $1}')
adb shell grep -E 'Name|Uid|Groups|CapEff|CapBnd|NoNewPrivs|Seccomp' /proc/$APP_PID/status
```

Check `SELinux` object labels on critical `/dev` nodes and inspect recent `avc: denied` audit entries in the `events` log buffer:

```bash
adb shell ls -lZ /dev/binder /dev/vndbinder 2>/dev/null
adb shell logcat -d -b events | grep 'avc: denied' | tail -n 5
```
