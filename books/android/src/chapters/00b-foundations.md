# Foundations

## A Shared Systems Vocabulary Across Silicon, Kernel, and Ecosystem

Tracing a security guarantee on Android requires crossing five engineering layers that are ordinarily documented in separate worlds: `ARMv8`/`ARMv9` silicon exception architectures, Trusted Execution Environments and discrete secure elements, modified Linux kernel subsystems (`Binder`, `SELinux`, `fscrypt`, `dm-verity`, and `pKVM`), the userspace Android Framework (`Zygote`, `ActivityManagerService`, `keystore2`, and `PackageManager`), and Google's Compatibility and cloud attestation infrastructure [1, 2, 4, 5]. An application security engineer analyzing `Intent` redirection rarely inspects `Stage-2` ARM translation tables in `EL2`, while a bootloader developer configuring `AvbVBMetaImageHeader` descriptors may rarely audit `Credential Manager` `caBLE` passkey ceremonies or `Titanium Intelligence Enclave` `DICE` chains. Before [Chapter 1](01-bootrom-avb-vbmeta.md) begins at power-on reset, this chapter establishes the foundational hardware, operating-system, governance, cryptographic, and adversarial primitives shared across all twenty chapters.

## ARMv8 and ARMv9 Exception Levels, Worlds, and Isolation Substrates

Contemporary Android flagship and mid-range handsets execute predominantly on 64-bit `AArch64` (`ARMv8-A` and `ARMv9-A`) System-on-Chip (`SoC`) designs [5]. Unlike classic x86 protection rings (`Ring 3` down to `Ring 0`), the Arm A-Profile architecture organizes privilege along two orthogonal dimensions: vertical Exception Levels (`EL0` through `EL3`) and horizontal Security States controlled by the Non-Secure (`NS`) bit in the Secure Configuration Register (`SCR_EL3`) [5, 6].

Along the vertical axis inside the Normal World (`NS = 1`), `EL0` hosts unprivileged userspace code, encompassing Android applications (`ART` managed code and native `JNI` libraries), native system daemons (`init`, `vold`, `keystore2`, `apexd`), and Binderized vendor Hardware Abstraction Layer (`HAL`) processes. `EL1` hosts privileged rich operating-system kernels: both the host Android `Generic Kernel Image` (`GKI`) Linux kernel and lightweight `Microdroid` guest Linux kernels running inside virtual machines [44, 46, 58]. Beneath `EL1` sits `EL2`, the Hypervisor Exception Level, which governs processor virtualization extensions, Virtualization Host Extensions (`VHE` and non-`VHE` modes), and `Stage-2` Memory Management Unit (`MMU`) page tables (`VTTBR_EL2`) that translate Guest Intermediate Physical Addresses (`IPA`) into true hardware Physical Addresses (`PA`), paired with `SMMUv3` System MMUs policing peripheral Direct Memory Access (`DMA`) [5, 44]. At the bottom of the CPU core sits `EL3`, the Secure Monitor (typically implemented by Arm Trusted Firmware-A `BL31`), which owns the highest CPU privilege, services Secure Monitor Calls (`SMC`), and context-switches architectural registers between the Normal World and the Secure World [6, 28].

![Figure: ARMv8/ARMv9 Exception Levels, TrustZone Secure World, pKVM EL2 hypervisor ownership, and off-SoC StrongBox security processors.](diagrams/00b-arm-worlds-pkvm-topology.svg)

Along the horizontal axis, `Arm TrustZone` partitions memory, caches, and interrupt routing (`GIC` Group 0 vs. Group 1) into a parallel Secure World (`NS = 0`) sharing the same physical CPU cores [6]. When `EL3` clears `SCR_EL3.NS = 0`, execution enters `S-EL1`, running a dedicated Trusted Operating System (`Google Trusty`, `Qualcomm QTEE`/`QSEE`, `Trustonic Kinibi`, or `OP-TEE`), which in turn hosts isolated Trusted Applications (trustlets) in `S-EL0` such as `KeyMint`, `Gatekeeper`, biometric matchers, and `Widevine` Digital Rights Management [29, 30, 36]. A memory controller firewall known as the TrustZone Address Space Controller (`TZASC`) tags AXI bus transactions with an `NS` signal so Normal World `EL1` and `EL2` software cannot read or write DRAM regions carved out for `S-EL1` and `S-EL0` [6].

Historically, Android relied almost exclusively on `TrustZone` (`S-EL1`/`S-EL0`) whenever a secret or policy check needed protection from a compromised Linux kernel. Over a decade of deployment revealed two severe structural flaws in that binary world split, motivating two complementary modern substrates examined in [Chapter 3](03-trustzone-strongbox.md) and [Chapter 5](05-pkvm-avf-microdroid.md). First, because `TrustZone` shares the main SoC die, DRAM controller, and CPU caches while hosting dozens of complex vendor multimedia and sensor trustlets written in C with weak memory mitigations, vulnerabilities inside `S-EL0` trustlets repeatedly yielded complete Secure World compromise (`CVE-2015-6639`, `CVE-2019-10574`), while shared silicon and cache geometry left high-value keys exposed to physical voltage-glitching, electromagnetic side channels, and external flash replay [30, 31, 32, 41]. Flagship Android devices therefore pair `TrustZone` with a discrete, physically separate `StrongBox` security processor (`Google Titan M2` or `Samsung Knox Vault`) sitting on its own silicon die with private SRAM, internal non-volatile flash, dedicated hardware random number generators, laser/glitch sensors, and a minimal fixed-function firmware `TCB` dedicated strictly to `KeyMint`, `Weaver` passcode throttling, and `Protected Confirmation` [33, 34, 35].

Second, cramming third-party DRM parsers, machine-learning compilers, or OEM security workloads into `S-EL1` bloated the Secure World `TCB` for everyone, yet running them in Normal World `EL0` left their memory completely exposed to any host Linux kernel (`EL1`) driver vulnerability. Android 13 and later resolved this tension through `Protected KVM` (`pKVM`) inside the `Android Virtualization Framework` (`AVF`, [Chapter 5](05-pkvm-avf-microdroid.md)) [43, 44]. During early boot, before untrusted kernel modules or userspace processes run, Linux splits off a compact, non-VHE hypervisor (`arch/arm64/kvm/hyp/nvhe`) into `EL2` and surrenders direct control over `Stage-2` translation tables. From that moment onward, even the host Android Linux kernel in `EL1` operates inside a `pKVM`-managed `Stage-2` address space: when the host donates physical pages to a Protected Virtual Machine (`pVM`), `pKVM` unmaps those frames from the host's `Stage-2` page table and `SMMUv3` IOMMU tables, mathematically excluding the multi-million-line host Linux kernel from the confidentiality and integrity `TCB` of isolated Normal World workloads [44, 48].

> **Definition.**
> On modern Android, the Trusted Computing Base (`TCB`) is stratified across four hardware isolation tiers rather than two: off-die `StrongBox` silicon (`Titan M2` / `Knox Vault`) for physical tamper resistance and `Weaver` throttling; `TrustZone` (`EL3`/`S-EL1`) for SoC-integrated `KeyMint` and secure sensor pipelines; Normal World `EL2` (`pKVM` + `pvmfw`) for memory-isolated virtual machines de-privileged from host Linux; and Normal World `EL1` (`GKI` Linux kernel) enforcing `SELinux`, `Binder`, and `fscrypt` across `EL0` application sandboxes.

## Inverting Unix: Application-per-UID, SELinux, and Binder Capabilities

Understanding userspace Android requires unlearning how desktop Linux uses `UID`s, filesystems, and sockets. On a conventional workstation distribution, a human user logs into `UID 1000`, and every application launched during that session inherits `UID 1000`'s full discretionary authority over `/home/alice`, X11 or Wayland clipboards unless portal-confined, D-Bus session buses, and outbound network sockets. Android retains the battle-tested Linux task scheduler, virtual memory manager, and VFS enforcement hooks, but repurposes the kernel's multi-user primitive into an *application sandbox* [1, 4, 7].

As defined in `system/core/libcutils/include/private/android_filesystem_config.h`, Android partitions the 32-bit Linux `uid_t` namespace into deterministic ranges [7, 121]. Static low-numbered Android IDs (`AID_ROOT = 0`, `AID_SYSTEM = 1000`, `AID_RADIO = 1001`, `AID_BLUETOOTH = 1002`, `AID_KEYSTORE = 1017`, `AID_SHELL = 2000`) identify dedicated system services, replacing monolithic `UID 0` execution with narrow daemon identities. User-installed and preloaded applications receive dynamically allocated Application IDs (`appId`) in the closed interval `[AID_APP_START, AID_APP_END]` corresponding to `[10000, 19999]`, while zero-permission ephemeral sandboxes (`android:isolatedProcess="true"`, used by `WebView` and Chrome renderers in [Chapter 9](09-uid-zygote-binder.md)) receive transient IDs in `[AID_ISOLATED_START, AID_ISOLATED_END]` (`[99000, 99999]` or `app_zygote` ranges `[90000, 98999]`) [7, 72]. When multi-user profiles or `Android Enterprise` Work Profiles ([Chapter 17](17-android-enterprise.md)) are active under user index $u \in \mathbb{Z}_{\ge 0}$ (with $u = 0$ for the primary owner and $u \ge 10$ for managed profiles), the kernel `UID` assigned to an application is computed arithmetically via `UserHandle.getUid(u, appId)` [121]:

$$\text{UID}(u, \text{appId}) = 100000 \cdot u + \text{appId}$$

Under this mapping, an application with $\text{appId} = 10214$ runs as kernel `UID` $10214$ (`u0_a214`) inside the personal profile and as kernel `UID` $1010214$ (`u10_a214`) inside Work Profile $u = 10$. The kernel's standard POSIX Discretionary Access Control (`DAC`) check immediately prevents `u0_a214` from opening files owned by `u0_a215` or `u10_a214` without inventing a single line of custom VFS logic [7, 121].

![Figure: Architectural contrast between ambient-user desktop POSIX and Android's mutual-distrust per-application UID, SELinux, and Binder model.](diagrams/00b-android-vs-unix-uid-stack.svg)

Per-app `UID`s alone, however, cannot stop a compromised `UID 0` daemon from reading `/data`, nor can they prevent an application from abusing world-accessible `/dev` driver nodes or legacy Linux system calls. Android therefore layers three mandatory controls atop `AID_*` identities [4, 50, 54, 73]. First, universal enforcing `SELinux` ([Chapter 6](06-selinux-seccomp.md)) assigns every process a tight security context (such as `u:r:untrusted_app:s0:c214,c256,c512,c768`) paired with Multi-Category Security (`MCS`) category sets encoding both the app's `appId` and its profile `userId`, ensuring that even misconfigured `0777` file permissions inside `/data/data` cannot cross app or profile boundaries [50, 51]. Second, `Zygote` installs a strict `seccomp-BPF` system-call filter and drops all POSIX capabilities (`CapEff = CapPrm = CapBnd = 0`) before branching into application code, removing over a hundred unused kernel syscalls from the untrusted attack surface [54, 55]. Third, because standard System V IPC is disabled and Unix domain sockets are blocked between apps by `SELinux`, inter-process communication flows through the kernel `/dev/binder` driver ([Chapter 9](09-uid-zygote-binder.md)), which tracks unforgeable object-capability descriptors (`flat_binder_object`) per process and stamps every incoming transaction (`binder_transaction_data.sender_euid`) with the caller's true kernel `UID` and `PID` [73].

## Multi-Vendor Ecosystem Governance: CDD, CTS, VTS, Treble, and GKI

Because AOSP is open-source software shipped by hundreds of independent hardware manufacturers, source code in `android.googlesource.com` guarantees nothing on a retail handset unless an enforceable ecosystem mechanism prevents OEMs from patching out security checks during Board Support Package (`BSP`) bring-up [2, 3, 4]. Android bridges open-source code and commercial device guarantees through five interlocking governance pillars.

The normative legal and engineering specification is the Android Compatibility Definition Document (`CDD`), published for each major platform release [2]. Section 9 of the `CDD` (*Security Model Compatibility*) codifies mandatory platform invariants: every compatible device must ship with `AVB` Verified Boot, hardware-backed keystore where silicon supports it, universal enforcing `SELinux` with zero permissive production domains, `File-Based Encryption`, `Scoped Storage`, biometric `SAR`/`FAR` strength tiers, and `Remote Key Provisioning` on modern launch levels [2]. Compliance with the `CDD` is verified mechanically before an OEM build can license Google Mobile Services (`GMS`) and receive `Play Integrity` device certification through the Compatibility Test Suite (`CTS`), an automated harness containing millions of host-driven and on-device unit tests [3]. Crucially, `CTS` includes `SELinuxHostTest` and policy analyzers that extract the compiled `/sys/fs/selinux/policy` binary directly from the device under test and verify every `neverallow` assertion from AOSP's `system/sepolicy`, making it impossible for an OEM to slip a hidden root daemon or world-readable block-device rule past certification [52].

Complementing `CTS` at the hardware-software seam are `Project Treble`, the Vendor Test Suite (`VTS`), `Project Mainline`, and the `Generic Kernel Image` (`GKI`), examined in depth in [Chapter 2](02-antirollback-verity-apex.md) and [Chapter 7](07-treble-gki-rust.md) [25, 57, 58]. Prior to Android 8.0, `system_server` and media daemons dynamically loaded vendor-supplied C/C++ shared libraries (`libhardware` `.so` HALs) directly into privileged framework address spaces, while SoC vendors forked the Linux kernel by millions of lines per chip family. `Project Treble` split `/system` cleanly from `/vendor` across versioned, Binderized `HIDL` and `AIDL` interfaces described in Vendor Interface (`VINTF`) manifests and tested continuously by `VTS` [3, 57]. `Project Mainline` (`APEX` containers) packaged over thirty security-critical userspace subsystems (`ART`, `Conscrypt` TLS, media extractors, DNS resolver, Wi-Fi, Bluetooth, `PermissionController`, and `rkpd`) as Google-signed modular filesystem images updated directly through Google Play without waiting for OEM firmware OTAs [25, 27]. Finally, `GKI 2.0` (mandatory for devices launching with Android 12 and Linux 5.10 or later) replaced fragmented OEM kernel trees with a single Google-built, Google-signed core kernel binary (`boot.img` `vmlinux`) exposing a frozen Kernel Module Interface (`KMI`) ABI to vendor loadable kernel modules (`vendor_boot` and `vendor_dlkm`) [58].

## Cryptographic Primitives Across the Chain

Android's trust chain relies on standard, peer-reviewed cryptographic constructions rather than proprietary ciphers, with exact algorithm floors enforced by `CDD` and `VTS` [2, 8, 9, 10, 11]. Pre-OS and filesystem integrity rest on `SHA-256` and `SHA-512` (`FIPS 180-4` [8]): `AVB 2.0` verifies `AvbVBMetaImageHeader` blocks using `RSA-2048` or `RSA-4096` (`RSASSA-PKCS1-v1_5` or `RSASSA-PSS`) with `SHA-256`/`SHA-512` digests [13], while `dm-verity`, `fs-verity`, and `APK Signature Scheme v2`/`v3`/`v4` construct hierarchical `SHA-256` Merkle trees over $4\text{ KiB}$ or $1\text{ MiB}$ chunks so any tampered flash page is caught in $O(\log N)$ hash evaluations before execution [22, 24, 78].

For bulk storage confidentiality in `File-Based Encryption` ([Chapter 12](12-fbe-usb-theft-protection.md)), inline encryption hardware (`ICE` / `UFS` Inline Crypto) encrypts file contents under `AES-256-XTS` (`NIST SP 800-38E` [9]) and encrypts filenames under `AES-256-CTS` (Ciphertext Stealing), deriving per-file keys from master `fscrypt` v2 policies via `HKDF-SHA512` (`RFC 5869` [10]) [91, 93]:

$$K_{\text{file}} = \text{HKDF-SHA512}(K_{\text{master}}, \text{context} \parallel \text{nonce}_{16})$$

Inside `KeyMint` and `StrongBox` ([Chapter 4](04-keymint-weaver-throttling.md)), encrypted key blobs stored on `/data/misc/keystore2` are wrapped using `AES-256-GCM` (`NIST SP 800-38D` [9]) with the key's `AuthorizationList` bound into the AEAD Additional Authenticated Data (`AAD`) under a Key Encryption Key derived from silicon Hardware Bound Keys (`HBK`), Verified Boot state, and patch levels [36, 37]. For asymmetric attestation, `DICE` derivations, and FIDO2 passkeys ([Chapter 5](05-pkvm-avf-microdroid.md), [Chapter 13](13-biometrics-passkeys.md), and [Chapter 15](15-key-attestation-rkp.md)), modern Android favors `ECDSA` over `NIST P-256` (`secp256r1` [8]) and `Ed25519` (`RFC 8032` [11]), encoding `OpenProfile for DICE` and `Remote Key Provisioning` structures in deterministic `CBOR` and `COSE_Sign1` (`RFC 8949` and `RFC 9052` [114]) [47, 113].

## Threat Taxonomy and Serviced Security Boundaries

Throughout this volume, defenses and failures are evaluated against five distinct adversary profiles defined by Android's platform threat model and the Android Security Rewards severity framework [1, 4, 12]. The *remote zero-click or one-click adversary* delivers malicious web content, media streams, Bluetooth frames, or cellular `VoLTE`/baseband packets over the network without user installation, seeking sandbox escape into `EL1` or modem takeover ([Chapter 8](08-arm-mte-scudo.md), [Chapter 9](09-uid-zygote-binder.md), and [Chapter 20](20-multivendor-spyware-chains.md)). The *local unprivileged application adversary* controls an installed APK inside `untrusted_app` (`UID u0_a*`) and attempts privilege escalation across `Binder` IPC, exported `Intent` handlers, GPU kernel drivers, or social-engineered `AccessibilityService` grants ([Chapter 6](06-selinux-seccomp.md), [Chapter 9](09-uid-zygote-binder.md), and [Chapter 11](11-accessibility-advanced-protection.md)).

The *physical adversary* obtains an unattended, stolen, or seized handset in either the cold-booted `Before First Unlock` (`BFU`) state or the warm re-locked `After First Unlock` (`AFU`) state, bringing custom USB-C hardware emulators (`Cellebrite`), NAND flash programmers, or voltage-glitch probes ([Chapter 1](01-bootrom-avb-vbmeta.md), [Chapter 3](03-trustzone-strongbox.md), [Chapter 4](04-keymint-weaver-throttling.md), and [Chapter 12](12-fbe-usb-theft-protection.md)). The *device-owner / fraud adversary* intentionally unlocks the bootloader (`ORANGE`), loads `KernelSU` or `Zygisk`, and injects leaked OEM keyboxes via `TrickyStore` to deceive remote `Play Integrity` or banking servers about the handset's execution environment ([Chapter 15](15-key-attestation-rkp.md) and [Chapter 16](16-play-integrity-keybox-wars.md)). Finally, the *cloud or operator adversary* controls or subpoenas backend storage and AI inference infrastructure, motivating client-side `Titan` Cloud Key Vault HSM wrapping and attested `Titanium Intelligence Enclaves` ([Chapter 14](14-play-protect-intrusion-logging.md) and [Chapter 19](19-e2ee-backups-private-ai-compute.md)).

## Mechanism Validity Versus Delegated Authorization

Across every one of those five adversary profiles, a single analytical discipline governs how this book evaluates defenses: separating *local cryptographic or sandbox validity* from *system-level authorization and intent* [1, 4]. Throughout mobile security history, the most durable exploit classes rarely invert a cryptographic hash function or guess a 256-bit key; instead, they exploit a seam where a higher layer assumes a valid primitive proves more than it actually measures.

Consider four recurring manifestations of that gap across the chapters ahead. At the boot and attestation seam ([Chapter 1](01-bootrom-avb-vbmeta.md), [Chapter 15](15-key-attestation-rkp.md), and [Chapter 16](16-play-integrity-keybox-wars.md)), a valid X.509 signature chaining to Google's Hardware Attestation Root CA proves only that *some* key signed a certificate structure; unless the relying party verifies that `attestationSecurityLevel` is hardware-backed, checks the live revocation list for leaked ODM factory keyboxes, confirms `deviceLocked == TRUE` inside `teeEnforced.rootOfTrust` rather than `softwareEnforced`, and binds the attested public key to subsequent session requests over a fresh challenge nonce, a bot farm can relay genuine attestations from a clean handset onto automated scripts [110, 112, 120].

At the kernel IPC seam ([Chapter 9](09-uid-zygote-binder.md)), `/dev/binder` guarantees with mathematical certainty that `Binder.getCallingUid()` reflects the immediate caller's Linux `UID`, yet if an exported `Activity` or `Service` extracts an untrusted nested `Intent` from a `Bundle` and re-launches it without stripping `FLAG_GRANT_READ_URI_PERMISSION`, the victim app exercises its own valid `UID` to hand private `ContentProvider` files straight back to the attacker [73, 76]. At the user-interface seam ([Chapter 10](10-apk-signing-scoped-storage.md) and [Chapter 11](11-accessibility-advanced-protection.md)), an APK carrying a valid `APK Signature Scheme v3` signature from a registered developer identity proves package integrity and author accountability, not benign behavior: if social engineering convinces a user outside `Advanced Protection Mode` to grant `AccessibilityService`, valid UI automation calls bypass `SELinux`, `Binder`, and `KeyMint` completely by operating as the user above the cryptography [78, 82, 86, 89]. And at the physical storage seam ([Chapter 4](04-keymint-weaver-throttling.md) and [Chapter 12](12-fbe-usb-theft-protection.md)), `fscrypt` `AES-256-XTS` encryption backed by `StrongBox` `Weaver` renders `Before First Unlock` (`BFU`) flash storage impenetrable to offline supercomputers, yet once the phone sits unlocked at rest in `After First Unlock` (`AFU`) with active keys programmed into `UFS` Inline Crypto keyslots, confidentiality shifts from cryptographic hardness to the physical and kernel perimeter guarding the USB-C port and lock screen [91, 94].

Every one of those runtime boundaries still terminates downward at CPU reset. If an adversary executes unverified code before the Linux kernel or `EL2` `pKVM` hypervisor initializes, `SELinux` policies, `Binder` reference tables, `Arm MTE` tag checks, and `KeyMint` patch-level latches can all be subverted before userspace draws its first pixel. [Chapter 1](01-bootrom-avb-vbmeta.md) begins at the SoC `Boot ROM`, hardware eFuses, bootloader lock states, and `AVB 2.0` `VBMeta` partition graph that anchor the entire Android trust chain.
