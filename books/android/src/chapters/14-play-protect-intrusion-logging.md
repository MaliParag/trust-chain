# Play Protect, Dynamic Signal Monitoring, and E2EE Intrusion Logging

## Overview

* **Link in the Chain:** Mobile runtime observability and forward-secure forensic logging interlude; replaces third-party kernel EDR drivers with on-device behavioral ML (`Google Play Protect`), enterprise `SecurityLog` audit streams, and end-to-end encrypted cloud `Intrusion Logging`.
* **Core Security Invariant:** Zero third-party Mobile Threat Defense (`MTD`) applications may load kernel code or read neighboring `u0_a*` sandboxes; instead, the OS detects live dropper behaviors inside `Private Compute Core` (`Dynamic Signal Monitoring`), scopes `SecurityLog` strictly to organization-owned devices, and forward-seals `Intrusion Logging` slices into an append-only 12-month cloud vault under the user's E2EE key so post-compromise `EL1` root implants cannot decrypt or erase pre-compromise history.
* **Ecosystem Enforcement Tier:** `DevicePolicyManager` `SecurityLog` and `NetworkLogger` enforce across AOSP `GREEN` and `YELLOW` managed devices; `Google Play Protect` `Live Threat Detection` and Android 16/17 E2EE `Intrusion Logging` operate on certified GMS (`GREEN`) devices, while `GrapheneOS` (`YELLOW`) enforces deterministic prevention (`SYNC` `MTE`, `Vanadium` JITless, `Auditor`) without cloud telemetry.
* **Trusted Computing Base (TCB):** `VerifyingSession` (`frameworks/base/services/core/java/com/android/server/pm/`), `Google Play Protect` + `Private Compute Core` behavioral classifiers, `SecurityLogMonitor` and `NetworkLogger` (`frameworks/base/services/devicepolicy/`), client-side `HPKE`/E2EE `Intrusion Logging` sealer bound to `Titan` Cloud Key Vault, and consensual forensic parsers (`AndroidQF` and `MVT` `check-advanced-logs`).
* **Seam & Handoff:** Bridges preventive local sandboxing (Part III) to post-incident accountability without sacrificing `GKI` kernel stability or personal BYOD privacy; hands remote cryptographic proof of silicon and boot integrity to Part IV ([Chapter 15](15-key-attestation-rkp.md)).

## Threat Model & Ecosystem Constraint

Security architects arriving on Android from enterprise Windows (`ETW` paired with `ELAM`-anchored kernel minifilter drivers) or cloud Linux (`eBPF` and `LSM` kernel probes) routinely ask how to deploy their corporate Endpoint Detection and Response (`EDR`) kernel sensor onto employee smartphones. On Android, as on iOS, the platform's answer is absolute: *third-party kernel extensions, inline syscall hooks, and cross-sandbox memory or filesystem inspection APIs are architecturally forbidden* [401, 402, 403].

Three first-principles systems constraints dictate that prohibition [401, 402, 403, 404]. First is *operating-system availability and `GKI` immutability*: when third-party security vendors execute complex content parsers synchronously inside `Ring 0` (`EL1`), a single malformed signature update can bugcheck millions of machines simultaneously, as demonstrated worldwide on July 19, 2024 across roughly 8.5 million Windows hosts and reflected in Microsoft's subsequent Windows Resiliency Initiative migrating endpoint sensors out of `Ring 0` [401, 403]. On Android, `AVB` `dm-verity` ([Chapter 2](02-antirollback-verity-apex.md)) and the Generic Kernel Image (`GKI`) signed `KMI` ABI ([Chapter 7](07-treble-gki-rust.md)) forbid loading out-of-tree third-party `.ko` modules at runtime. Second is *mutual-distrust personal privacy*: a smartphone carries intimate medical trackers, private photos, location history, and encrypted personal chats alongside work email. Granting a commercial antivirus or `MTD` app `UID 0` omniscient read authority across every `u0_a*` sandbox would convert every security vendor (and any RCE inside that vendor's parser) into a universal surveillance implant [401, 402, 404]. Third is *mobile energy physics*: marshaling every `openat()`, `mmap()`, and `Binder` IPC across userspace inspection daemons would exhaust smartphone battery budgets within hours.

Refusing third-party kernel EDR hooks, however, leaves two formidable adversarial blind spots that Android had to solve natively inside the operating system [7, 405, 406]:

First is *polymorphic, delayed-activation, and parser-evading malware*. Criminal dropper ecosystems (*Anatsa*, *Xenomorph*, *Crocodilus*, *SpinOk* spyware SDKs, and `WebAPK` progressive-web-app phishing lures [407]) abandoned shipping static malicious payloads inside Stage-1 APKs. Instead, a clean PDF viewer or utility passes initial store inspection, sleeps for forty-eight hours, checks motion sensors to evade headless sandboxes, fetches encrypted secondary DEX bytecode over TLS into `InMemoryDexClassLoader`, hides or swaps its home-screen launcher icon, or corrupts ZIP central-directory headers and `AndroidManifest.xml` string pools (as Kaspersky documented in *SoumniBot* [408]) to crash static third-party scanners while Android's `libziparchive` still parses and installs the package [405, 408, 409].

Second is *the mercenary-spyware forensic volatility paradox* highlighted by Amnesty International's Security Lab, Google's Threat Analysis Group (`TAG`), and Reporters Without Borders (`RSF`) [103, 406, 410, 411]. When commercial surveillance chains (*Pegasus*, *Predator*, *NoviSpy*, or kernel zero-days such as `CVE-2024-36971`, a Linux networking `dst_entry` use-after-free exploited in the wild in 2024 [412]) compromise a journalist's handset, standard Android diagnostic logs evaporate rapidly. Circular `logcat` (`logd`) RAM buffers wrap within minutes or hours of normal phone usage; native crash dumps written by `debuggerd` (`/data/tombstones`) and `DropBoxManagerService` (`frameworks/base/services/core/java/com/android/server/DropBoxManagerService.java` [413]) hold only small rotating quotas; and an attacker who achieves `EL1` kernel root can selectively scrub local `/data/log`, tombstones, and package histories before triggering a clean reboot [7, 406, 413]! When a targeted human-rights defender contacts civil-society forensic investigators weeks or months later, `Scoped Storage` blocks unprivileged data pulls while incidental `bugreport` buffers have long rotated past the intrusion date [406, 410]. Defenders needed a persistent, privacy-preserving flight recorder whose pre-compromise records *neither Google nor a post-exploitation `Ring 0` implant can read or erase* [7, 406, 414].

## Architecture & AOSP Implementation

Android replaces third-party kernel EDR drivers with three purpose-built native telemetry architectures, each scoped to a distinct trust and privacy model [7, 405, 415]:

![Figure: Android's three native observability tiers replacing third-party kernel EDR hooks: Play Protect Dynamic Signal Monitoring, Enterprise SecurityLog, and E2EE Cloud Intrusion Logging.](diagrams/14-telemetry-tiers-architecture.svg)

### Tier 1 · Consumer Threat Defense: `Google Play Protect` and `Dynamic Signal Monitoring`

At the consumer layer across more than three billion active certified devices, Android embeds install-time and runtime verification hooks directly into `PackageManagerService` (`frameworks/base/services/core/java/com/android/server/pm/VerifyingSession.java` [416]) paired with `Google Play Protect` (`com.android.vending`) [405]. Whenever *any* installer stages an APK session (including sideloaded browser or file-manager installs), `VerifyingSession` broadcasts `Intent.ACTION_PACKAGE_NEEDS_VERIFICATION` to the platform-pinned verifier before committing the session to `/data/app/` [416].

To defeat hash-novel, repacked sideloaded droppers that spin up new signing certificates every ten minutes, Android 14-17 *Real-Time Code-Level Scanning* extracts structural control-flow graphs, obfuscation entropy, and sensitive reflection targets from previously unseen APKs during the install dialog, combining on-device feature extraction with cloud ML verdicts in seconds (augmented in 2026 by Chrome Safe Browsing pre-download APK malware blocking and Android 17's public append-only *Binary Transparency* ledger verifying that Google-signed system APKs match authentic Google release manifests [417, 418]). Simultaneously, Android 14 (`API 34`) hardened dynamic bytecode loading at the ART runtime boundary (`SET_WRITABLE_DEX_FILES`): any secondary DEX or JAR loaded via `DexClassLoader` or `PathClassLoader` *must* be marked read-only (`setReadOnly()`) prior to load, throwing `SecurityException` if writable to block post-verification payload self-mutation on disk [409]!

Because multi-stage droppers look benign at install time and activate days later, Android 15 through Android 17 introduced on-device behavioral detection via *Live Threat Detection* (launched November 2024 [419]) and *Android 17 `Dynamic Signal Monitoring`* [405, 419]. Instead of uploading raw user telemetry to Google servers, feature collection and ML classification execute locally inside Android's isolated `Private Compute Core` (`PCC`, [Chapter 18](18-on-device-agentic-ai.md)) [419]. The platform correlates live cross-service state transitions across `ActivityManager`, `PackageManager`, `AccessibilityManager`, and `SmsManager`: an application that alters or disables its `Launcher` component alias (`setComponentEnabledSetting`) to vanish from the app drawer and subsequently launches activities from the background, silently forwards incoming SMS messages to external numbers, projects imperceptible `AccessibilityService` overlays to hijack touches, or stages `InMemoryDexClassLoader` reflection bursts triggers an immediate real-time alert prompting one-tap removal or automatic permission revocation [405, 419]. Under Android 17 `Dynamic Signal Monitoring`, Google Play Protect dynamically pushes updated behavioral signature rules over `Private Compute Services` so newly discovered crimeware evasion sequences are caught fleet-wide without waiting for an OS OTA [405]. Architecturally, hosting `Live Threat Detection` and `Dynamic Signal Monitoring` inside `Private Compute Core` solves the classic mobile antivirus privacy dilemma: the behavioral classifier runs inside an unprivileged, network-less `isolatedProcess` sandbox whose *only* egress to Google backends traverses audited, open-source `Private Compute Services` IPC channels enforcing differential privacy and `Private Information Retrieval` [405, 419]. Consequently, Play Protect evaluates high-entropy runtime telemetry (such as `PackageManager` component-alias toggles, `AccessibilityService` window-overlay durations, `SmsManager` outbound destination deltas, and `InMemoryDexClassLoader` invocation chains) at full system fidelity on the handset while mathematically preventing the cloud rule-distribution service from learning which apps an individual user launches or installs [405, 419].

### Tier 2 · Managed Fleet Telemetry: `DevicePolicyManager` `SecurityLog` and `NetworkLogger`

Consumer ML classifiers intentionally emit zero raw process or network logs to external servers. Corporate SOC teams operating company-owned devices (`Fully Managed` and `Corporate-Owned, Personally Enabled` `COPE` fleets, [Chapter 17](17-android-enterprise.md)), by contrast, require deterministic, timestamped event streams for SIEM ingestion and compliance auditing [402, 415]. AOSP provides this natively through `SecurityLog` (`frameworks/base/core/java/android/app/admin/SecurityLog.java` [420]) and `NetworkLogger` (`frameworks/base/services/devicepolicy/java/com/android/server/devicepolicy/` [404, 421]).

When an enterprise Device Policy Controller (`DPC` or delegated `DELEGATION_SECURITY_LOGGING` Mobile Threat Defense app) calls `DevicePolicyManager.setSecurityLoggingEnabled(admin, true)` and `setNetworkLoggingEnabled(admin, true)`, `logd` (`LOG_ID_SECURITY`) and `netd` (`INetdEventListener`) populate dedicated ring buffers drained asynchronously by `SecurityLogMonitor.java` and `NetworkLogger.java` [404, 415, 420, 421]. Whenever the internal queue crosses its watermark (or periodically on poll intervals), `SecurityLogMonitor` notifies `DeviceAdminReceiver.onSecurityLogsAvailable()`, allowing the `DPC` to batch-pull `SecurityEvent` parcelables via `retrieveSecurityLogs()` (and `retrievePreRebootSecurityLogs()` on hardware supporting `pstore` persistent RAM across warm resets) [404, 415, 420]. Key forensic tags in `SecurityLog.java` include `TAG_OS_STARTUP` (recording exact `AVB` `verifiedBootState` and `dm-verity` `enforcing` mode at boot), `TAG_APP_PROCESS_START` (recording exact process name, nanosecond start timestamp, `UID`, `PID`, `SELinux` `seinfo` label, and the base APK's `SHA-256` digest!), `TAG_PACKAGE_INSTALLED` / `TAG_PACKAGE_UPDATED` / `TAG_PACKAGE_UNINSTALLED`, `TAG_KEYGUARD_DISMISSED` and `TAG_KEYGUARD_DISMISS_AUTH_ATTEMPT` (recording auth success and method strength), `TAG_ADB_SHELL_INTERACTIVE` / `TAG_ADB_SHELL_CMD` / `TAG_SYNC_RECV_FILE` / `TAG_SYNC_SEND_FILE`, `TAG_CERT_AUTHORITY_INSTALLED` / `REMOVED`, and `TAG_KEY_GENERATED` / `IMPORT` / `DESTRUCTION` in `keystore2` [415, 420]. In parallel, `NetworkLogger` subscribes to `IIpConnectivityMetrics` callbacks inside `netd`'s DNS resolver and socket-connect paths, emitting per-package `DnsEvent` (`packageName`, queried `hostname`, up to 10 resolved IP addresses, timestamp) and `ConnectEvent` (`destination IP`, `port`, `packageName`) records attributed by kernel socket `UID` without installing a MitM root CA or breaking end-to-end TLS encryption [404, 421].

Examine the strict privacy invariant enforced inside `SecurityLogMonitor.java` and `DevicePolicyManagerService` [402, 404]: on an employee-owned *BYOD Work Profile*, calling `setSecurityLoggingEnabled()` or device-wide `setNetworkLoggingEnabled()` is *unconditionally rejected* (`SecurityException`), and even on `COPE` devices (where an organization provides a phone allowing both work and personal profiles), personal-profile `DnsEvent`/`ConnectEvent` hostnames and personal app details are scrubbed or blocked unless fully managed! Android refuses to let enterprise MDM enrollment silently surveil an employee's personal sandbox [402, 404].

### Tier 3 · Android 16/17 End-to-End Encrypted Cloud `Intrusion Logging`

Neither `Play Protect` (engineered against APK crimeware rather than memory-corruption spyware) nor enterprise `SecurityLog` (unavailable to independent journalists, lawmakers, and human-rights activists outside corporate MDMs, and stored locally until polled) solved consensual post-compromise forensics against *Pegasus*, *Predator*, *NoviSpy*, or `Cellebrite` custody extractions [406, 410, 411]. Developed in partnership with Amnesty International's Security Lab and Reporters Without Borders (`RSF`) and launched across Android 16 (December QPR+) and Android 17 inside `Advanced Protection Mode`, *Android `Intrusion Logging`* (`IL`) introduces the mobile industry's first native, forward-sealed, end-to-end encrypted cloud forensic flight recorder [7, 406, 411, 422]!

![Figure: End-to-end encrypted Intrusion Logging pipeline sealing forensic events on device and uploading tamper-evident ciphertext batches to an append-only cloud vault.](diagrams/14-e2ee-intrusion-logging-flow.svg)

Walk through the exact event schema, cryptographic sealing properties, and adversarial post-compromise guarantees documented by Google and Amnesty International's Security Lab [7, 406, 414, 422, 423]:

First, *purpose-built forensic event capture*: once the user opts into `Intrusion Logging` under `Settings` $\to$ `Security & privacy` $\to$ `Advanced Protection` $\to$ `Intrusion Logging`, the OS captures three structured JSON/protobuf event streams specifically curated for spyware and physical-tampering triage [406]. Examine representative decoded records documented in Amnesty International Security Lab's May 2026 technical evaluation [406]:

```json
{"security_event":{"event_id":7,"event_time":1770984359195595837,
  "keyguard_dismiss_auth_attempt":{"success":true,"method_strength":1}}}
{"security_event":{"event_id":2,"event_time":1771243841015617441,
  "adb_sync_recv_file":{"path":"/sdcard/Download/mal.txt"}}}
{"security_event":{"event_id":0,"event_time":1767011660603598998,
  "app_process_start":{"process":"WebViewLoader-armeabi-v7a",
  "uid":1037,"pid":2091,"seinfo":"null:complete","sha256":"..."}}}
{"dns_event":{"event_id":2,"event_time":1770983814122,
  "package_name":"com.android.chrome","hostname":"stage1-redirect.example",
  "ip_addresses":["/198.51.100.42"],"ip_addresses_count":1}}
```

Notice how each stream answers a specific post-incident forensic question that previously went unanswered when volatile `logcat` buffers wrapped [406]: `keyguard_secured`, `keyguard_dismiss_auth_attempt`, and `keyguard_dismissed` establish to the nanosecond whether a phone confiscated at a border checkpoint or police station was covertly unlocked; `adb_shell_cmd` and `adb_sync_recv_file` / `send_file` expose physical cable interaction or forensic agent staging (`falcon`); `package_installed` paired with `package_uninstalled` and `app_process_start` (recording `uid`, `pid`, `seinfo`, and APK `sha256`) unmasks stalkerware or spyware APKs (*NoviSpy*) that operators installed manually and later deleted to erase visible evidence; and per-`package_name` `dns_event` plus `connect_event` records preserve sub-second 1-click browser redirection chains and background `C2` socket connections for `MVT` `IOC` matching (which analysts interleave with `DropBoxManagerService` `SYSTEM_TOMBSTONE` native crashes via `supertimeline.csv` [406, 413, 424]) [406, 410].

Second, *forward-secure client-side E2EE sealing (`HPKE` / asymmetric vaulting)*: following classical forward-secure audit-log principles formalized by Bellare and Yee [414] and modern Hybrid Public Key Encryption (`RFC 9180` `HPKE` [423]), log slices are encrypted *on the handset* using a public/sealing key derived from the user's Google Account End-to-End Encrypted recovery domain (`LSKF` PIN/passphrase pinned inside `Google Titan` Cloud Key Vault HSMs, [Chapter 19](19-e2ee-backups-private-ai-compute.md)) [7, 406, 422]. Crucially, the background logger on the handset needs *only* the sealing public/epoch key to encrypt outgoing batches; *the private decryption key is not held in persistent `EL0`/`EL1` daemon memory*!

![Figure: Forward-secure Android 16/17 Intrusion Logging timeline across pre-compromise sealing (t < t0), mercenary spyware EL1 root compromise and local log wiping (t = t0), and post-incident owner-authorized decryption via AndroidQF and MVT (t > t0).](diagrams/14-extra-forward-secure-intrusion-vault.svg)

Third, *append-only 12-month cloud custody against `Ring 0` anti-forensics*: encrypted log slices upload periodically to an append-only cloud vault tied to the user's account, retained for a rolling *12-month window* before automatic expiration [406, 422]. Trace what happens when a zero-day exploit compromises the kernel (`EL1` root) at timestamp $t_0$. First, every forensic event from $t < t_0$ leading up to the compromise (the suspicious link redirect in `dns_event`, the rogue Wi-Fi association, the Cellebrite USB attachment, or an earlier custody `keyguard_dismissed` event) has already been encrypted and committed to the append-only cloud store (or sealed in local ciphertext awaiting upload). Second, even with `UID 0` and full `EL1` kernel read/write authority on the handset at $t \ge t_0$, *the spyware implant cannot decrypt prior sealed batches* (because the decryption scalar requires unsealing via the user's `LSKF` + `Titan` Cloud Key Vault) and *cannot issue cloud API calls to delete or overwrite already-uploaded historical epochs* [7, 406, 422]! Third, *Google itself possesses zero plaintext access*: because encryption is anchored to the user's `LSKF`-protected `Titan` CKV domain, Google cloud servers store only opaque ciphertext blobs unreadable under third-party warrants or cloud infrastructure compromises [7, 406, 422].

Fourth, *consensual forensic decryption via `AndroidQF` and `MVT`*: months after a suspected border seizure or spyware alert, the device owner meets consensually with a forensic specialist (such as Amnesty Security Lab or `RSF` [406, 411]). Running `AndroidQF` (`./androidqf` [424]) prompts the owner on the handset (`Settings` $\to$ `Advanced Protection` $\to$ `Intrusion Logging` $\to$ `Access logs` $\to$ `Download and decrypt`) to authenticate explicitly with their `LSKF` PIN or biometric, downloading and decrypting the 12-month archive into `/sdcard/Download/Intrusion Logging/` [406]. Investigators then run Amnesty's `Mobile Verification Toolkit` (`MVT`) `check-advanced-logs` module to split `security_event.json`, `dns_event.json`, and `connect_event.json` and sweep every domain, IP, and package hash against public spyware `IOC` feeds [406, 410, 424]!

### Cross-OS Comparison: Android `Intrusion Logging` vs. Windows `ETW` and iOS `sysdiagnose`

| Architectural Dimension | Android (`Play Protect` + `Intrusion Logging`) | Windows 11 (`ETW` `EtwTi` + `ELAM` EDR) | Apple iOS (`sysdiagnose` + `Lockdown Mode`) |
|---|---|---|---|
| Third-Party `Ring 0` Drivers | *Forbidden* (`GKI` + `AVB` immutability) [13, 401] | Historically allowed (`ELAM`/minifilters); migrating to userspace post-2024 [403] | *Forbidden* (iOS PPL/TXM kernel integrity) [425] |
| Live Malware Prevention | On-device ML inside `Private Compute Core` (`Dynamic Signal Monitoring`) [405, 419] | Kernel `PsSetCreate*` callbacks + `AMSI` + `Antimalware-PPL` `EtwTi` [403] | App Store gate + XProtect / Gatekeeper (macOS); no 3P iOS scanner [425] |
| Forensic Retention Horizon | *12-month rolling append-only cloud vault* [422] | Local `.evtx` / EDR cloud stream (enterprise only) [403] | Local volatile `sysdiagnose` / `DataUsage.sqlite` / `shutdown.log` [410, 425] |
| Survival Against `Ring 0` Log Wipe | *Yes* for all uploaded $t < t_0$ epochs (no device delete/decrypt right) [7, 406] | Local `.evtx` wipeable by `BYOVD`; cloud EDR survives only on managed PCs [403] | Local buffers overwritable by kernel root or wrapped by OS rotation [406, 425] |
| Provider Plaintext Visibility | *Zero-knowledge E2EE* (`LSKF` + `Titan` CKV) [7, 406] | Visible in plaintext to enterprise SOC / EDR cloud tenant [403] | Local only until user exports `sysdiagnose` tarball [425] |

Step back and appreciate why that three-way architectural contrast represents a milestone across endpoint operating systems [403, 406, 425]. On Windows 11, kernel-emitted `Microsoft-Windows-Threat-Intelligence` (`EtwTi`) prevents user-mode malware from blinding telemetry via `0xC3` (`ret`) patches on `ntdll!EtwEventWrite`, and `Antimalware-PPL` restricts who can subscribe to `EtwTi`; yet an attacker who crosses into `Ring 0` via Bring Your Own Vulnerable Driver (`BYOVD`) can corrupt `_ETW_SILODRIVERSTATE` and clear local `.evtx` logs unless an enterprise SIEM already ingested the plaintext stream, an architecture unavailable to independent journalists who lack a corporate SOC and unacceptable if a cloud vendor could read every personal DNS query [403]. On Apple iOS, forensic analysts running `MVT` rely on local incidental databases inside encrypted backups and `sysdiagnose` archives (`DataUsage.sqlite`, `netusage.sqlite`, `Biome` streams, and `shutdown.log`), which remain entirely local for privacy but suffer from uneven retention windows and sit inside the same `EL1` kernel trust domain targeted by zero-click chains [410, 425]. Android's `Intrusion Logging` synthesizes the strengths of both models: it preserves enterprise-grade `SecurityLog` + `DNS`/`Connect` fidelity across a deterministic 12-month cloud horizon that survives local root wiping, while wrapping every byte in `LSKF`-pinned client-side E2EE so Google never becomes a surveillance intermediary [7, 406, 422].

## Vendor, OEM, & Custom-OS Boundaries

In the enterprise market, commercial Mobile Threat Defense (`MTD`) products (*CrowdStrike Falcon for Mobile*, *Microsoft Defender for Endpoint*, *Zimperium*, *Lookout*) operate strictly inside Android's userspace boundaries: on managed devices, they consume `DevicePolicyManager` `SecurityLog` delegates, inspect installed package manifests, and optionally bind a local loopback `VpnService` to filter DNS/TLS SNI against phishing feeds without touching `EL1` kernel memory [401, 402, 415]. Any vendor brochure claiming "kernel-level hooking" on unrooted commercial Android is architecturally inaccurate.

Across consumer hardware, `Intrusion Logging` launched on Google Pixel devices starting with the Android 16 December update and expands to broader OEM flagships shipping Android 17, subject to Google Account linkage and hardware HAL support (such as `IRadio` 1.6+ for 2G state telemetry) [406, 422]. On `GrapheneOS` (`YELLOW` locked Pixel), background Google cloud scanners (`Play Protect`) and Google-account-linked `Intrusion Logging` are omitted by design to uphold zero-cloud-dependency privacy; `GrapheneOS` prioritizes deterministic exploit prevention (`SYNC` `Arm MTE`, `Vanadium` JITless isolation, hardened `malloc`, strict USB-C hardware cutoff) paired with local log inspection and cryptographic `Auditor` remote verification [401, 406].

### Operational Limits of `Intrusion Logging` and the Bridge to Remote Attestation

Amnesty International's Security Lab highlights three operational caveats that high-risk defenders must respect when deploying `Intrusion Logging` [406, 422]: first, `Intrusion Logging` is *strictly prospective* (`opt-in before an incident`, never retroactive); second, because `dns_event` and `connect_event` contain a 12-month record of visited hostnames and app launches, exported decrypted archives contain sensitive personal metadata requiring strict informed consent during forensic sharing [406]; third, while forward-sealing guarantees that an implant gaining `EL1` root at $t_0$ *cannot* alter or delete pre-$t_0$ logs, an implant live in kernel RAM can suppress *subsequent* telemetry until a reboot allows `AVB` ([Chapter 1](01-bootrom-avb-vbmeta.md)) to restore clean kernel code (making `Advanced Protection`'s 72-hour automatic reboot an essential companion to `Intrusion Logging`) [406, 414]!

> **Key idea.**
> `Play Protect` and `Intrusion Logging` give the *device owner and forensic analyst* visibility into local threats, but they never give a *remote relying server* cryptographic proof that an incoming TLS request originates from genuine, uncompromised Android silicon [7, 406]. Turning local hardware state into remotely verifiable cryptographic truth is the mission of Part IV, beginning in [Chapter 15](15-key-attestation-rkp.md) with X.509 Hardware `Key Attestation` and `Remote Key Provisioning` (`RKP`).

## Inspecting via ADB, Fastboot, & Attestation

Verify that install-time package verification is active (`1`) and inspect the system-bound verifier package (`com.android.vending` on certified GMS builds):

```bash
adb shell settings get global package_verifier_enable
adb shell dumpsys package verifiers | head -n 12
```

Inspect non-sensitive local crash and audit categories (`SYSTEM_TOMBSTONE`, `SYSTEM_AUDIT`, `SYSTEM_RESTART`) retained by `DropBoxManagerService`:

```bash
adb shell dumpsys dropbox | head -n 15
```

Check `DevicePolicyManager` enterprise `SecurityLog` and `NetworkLogger` activation status (active only on `Fully Managed` or `COPE` devices):

```bash
adb shell dumpsys device_policy | grep -iE 'SecurityLogging|NetworkLogging' | head -n 8
```

On a forensic workstation after consensual `AndroidQF` acquisition of decrypted `Intrusion Logging` archives, parse `security_event`, `dns_event`, and `connect_event` records against public spyware IOCs via `MVT`:

```bash
mvt-android download-iocs
mvt-android check-advanced-logs ./intrusion_logs -o ./mvt_output
```
