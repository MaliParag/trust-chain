# BiometricPrompt Strength Tiers and Credential Manager Passkeys

## Overview

* **Link in the Chain:** Local human-presence verification and phishing-resistant remote authentication layer; classifies biometric sensors into quantitative architectural tiers (`Class 1`, `Class 2`, `Class 3`) to gate `KeyMint` keys and unifies FIDO2/WebAuthn passkeys through `Credential Manager`.
* **Core Security Invariant:** Only a `Class 3` (`Strong`) biometric pipeline running inside isolated `TEE`/`StrongBox` hardware with `SAR <= 7%` and `FAR <= 1/50,000` is permitted to mint a `HardwareAuthToken` unlocking `KeyMint` cryptographic keys, and `WebAuthn` passkey assertions cryptographically bind `SHA-256(rpId)` so real-time phishing proxies cannot replay credentials across origins.
* **Ecosystem Enforcement Tier:** `CDD` Section 7.3.10 biometric class bounds and `BiometricPrompt` `CryptoObject` hardware gating enforce identically across `GREEN` and `YELLOW` locked states (`GrapheneOS` supports full `Class 3` hardware biometrics + open-source or third-party `CredentialProviderService` passkey vaults such as Bitwarden/Proton Pass); Google Password Manager E2EE cloud passkey sync runs on GMS (`GREEN`) devices backed by `Google Titan` HSMs.
* **Trusted Computing Base (TCB):** Secure biometric sensor + `SPI`/`MIPI` `TZASC`-isolated pipeline, `IFingerprint`/`IFace` `TEE` matcher TA, `KeyMint` `HardwareAuthToken` HMAC key ([Chapter 4](04-keymint-weaver-throttling.md)), `BiometricService` (`system_server`), `CredentialManager` framework, `GPM` E2EE security domain + `Titan` Cloud HSM, and `CTAP 2.2` `caBLE` BLE/Noise proximity stack.
* **Seam & Handoff:** Completes Part III by connecting verified human presence on the handset to hardware-bound local secrets and phishing-resistant web/app logins; transitions to the Interlude ([Chapter 14](14-play-protect-intrusion-logging.md)) to examine how Android observes runtime threats and preserves tamper-evident forensic logs.

## Threat Model & Ecosystem Constraint

Across a multi-vendor hardware ecosystem spanning USD 90 budget phones and USD 1,400 flagships, OEMs ship wildly divergent biometric sensors: ultrasonic 3D under-display fingerprint scanners, dot-projector structured-light / dual-pixel 3D infrared face cameras, capacitive side-button fingerprint sensors, 2D near-infrared cameras, and plain front-facing RGB selfie cameras running software neural networks [98]. In early Android releases, if an OEM marketed a 2D RGB camera face unlock that could be spoofed with a printed laser-jet photograph (`Spoof Acceptance Rate` > `30%`), and exposed it through the same API as a hardware-isolated fingerprint sensor, banking apps had no reliable way to know whether a `"biometric success"` callback meant genuine silicon verification or a spoofable normal-world heuristic [98, 103]!

Even with a strong ultrasonic fingerprint sensor, a second fatal developer anti-pattern emerged across mobile banking apps: *event-only (`non-CryptoObject`) biometric callbacks* [99, 103]. If an app calls `BiometricPrompt.authenticate(promptInfo)` without passing a `KeyMint`-backed `CryptoObject` and simply flips an in-memory boolean `isLoggedIn = true` inside `onAuthenticationSucceeded()`, any attacker with runtime instrumentation (`Frida` on a compromised process or memory corruption) can call `onAuthenticationSucceeded(null)` directly in Java without touching the fingerprint sensor at all!

Finally, above the handset, human passwords and SMS/TOTP two-factor codes fail catastrophically against modern real-time Adversary-in-the-Middle (`AiTM`) phishing kits (*Evilginx*): a user tricked into visiting `login-bank-verify.com` types both their password and their 6-digit OTP straight into the attacker's reverse proxy [100, 101]. Replacing passwords with `FIDO2`/`WebAuthn` asymmetric passkeys solves phishing mathematically, provided the user does not permanently lose every account the day they drop their phone in the ocean, and provided passkey sync across devices does not hand plaintext private keys to the cloud provider [101, 102]!

## Architecture & AOSP Implementation

### Quantitative Biometric Classification (`Class 1`, `Class 2`, `Class 3`)

Android's Compatibility Definition Document (`CDD` Section 7.3.10) and AOSP Biometric Security specification measure every OEM biometric implementation across three empirical and architectural axes before certifying a device [2, 98]. The first axis is *False Acceptance Rate* (`FAR` / Impostor Rate `IMP`), the probability that a random distinct human's biometric trait matches an enrolled template. The second axis is *Spoof and Impostor Acceptance Rate* (`SAR` / Presentation Attack Detection), the fraction of dedicated physical spoofs (latex/gelatin fingerprint molds, high-resolution printed photos, 3D plaster/silicone masks tested in physical lab evaluations) accepted by the sensor and liveness pipeline [98]. The third axis is *Architectural Pipeline Isolation*: whether raw sensor frames (`SPI` fingerprint bitmaps or `MIPI CSI-2` camera frames), feature extraction, template storage (encrypted under `TEE` keys on `/data/vendor_de`), and template matching execute *completely inside `TrustZone` / `StrongBox` isolated memory* inaccessible to a compromised host `EL1` Linux kernel [98]!

![Figure: Android BiometricManager Class 1 (Convenience), Class 2 (Weak), and Class 3 (Strong) spoof bounds, pipeline isolation, and KeyMint privileges.](diagrams/13-biometric-class-tiers.svg)

Based on the *weakest* link across those three axes, `BiometricService` assigns each sensor on a handset an immutable strength tier (`BiometricManager.Authenticators`) [98, 99]. At the apex sits `Class 3` (`BIOMETRIC_STRONG`), which requires `FAR <= 1/50,000`, `SAR <= 7%`, and an end-to-end hardware-isolated sensor-to-`TEE`/`StrongBox` pipeline. *Only* a `Class 3` authenticator receives the shared hardware `HMAC` key ([Chapter 4](04-keymint-weaver-throttling.md)) needed to mint a 69-byte `HardwareAuthToken` (`HW_AUTH_BIOMETRIC`); consequently, *only* `Class 3` sensors can unlock `KeyMint` cryptographic keys (`CryptoObject`), authorize `Identity Check` outside Trusted Places ([Chapter 12](12-fbe-usb-theft-protection.md)), and sign local passkey assertions [97, 98, 99], while still enforcing a mandatory fallback to the primary `LSKF` PIN/password at least once every 72 hours or after 4 hours of idle timeout. Below it sits `Class 2` (`BIOMETRIC_WEAK`), which satisfies `FAR <= 1/50,000` and `7% < SAR <= 20%` with an isolated matcher, permitting lock-screen unlock and non-cryptographic `BiometricPrompt` UI flows (such as app gating where keys are not unwrapped), *never* `KeyMint` `CryptoObject` operations, with tighter `LSKF` fallback timers (`24 hours` / `4 hours` idle) [98]. At the bottom sits `Class 1` (`BIOMETRIC_CONVENIENCE`), covering `SAR > 20%` or unisolated Normal World camera processing; it is barred completely from `BiometricPrompt` (third-party apps cannot invoke it at all!) and restricted strictly to low-assurance lock-screen dismissal [98].

> **Key idea.**
> Never treat `BiometricPrompt` as a boolean UI callback for high-value secrets: generate an `ECDSA` or `AES-GCM` key in `AndroidKeyStore` with `setUserAuthenticationRequired(true)` and `setUserAuthenticationParameters(0, KeyProperties.AUTH_BIOMETRIC_STRONG)`, wrap a `Signature` or `Cipher` inside `BiometricPrompt.CryptoObject`, and verify the cryptographic output on the server [99, 103]. Even if malware hooks Java methods inside your app process, `KeyMint` inside `StrongBox`/`TEE` refuses to sign without a genuine `HMAC`-authenticated `HardwareAuthToken` minted by the `Class 3` biometric TA!

### `Credential Manager`, Synced Passkeys, and `CTAP 2.2` `caBLE` Hybrid Transport

Starting in Android 14 (`API 34`) through Android 17, `Credential Manager` (`androidx.credentials` + platform `CredentialManagerService`) unified `WebAuthn`/`FIDO2` *Passkeys*, traditional passwords, and federated sign-in (`Sign in with Google`) behind a single system-brokered API supporting *pluggable credential providers* (`Google Password Manager`, `Bitwarden`, `1Password`, `Dashlane`, `KeePassDX`, `Proton Pass`) [100]!

Under `W3C WebAuthn Level 3` [101], when a Relying Party (`rpId = "example.com"`) registers a passkey via `createCredential()`, the active credential provider generates a fresh, per-account, per-origin asymmetric `ECDSA NIST P-256` keypair $(pk, sk)$ and returns $pk$ + `credentialId` to `example.com`. During login (`getCredential()`), `example.com` sends a fresh random 32-byte server `challenge`; after verifying the user via `BiometricPrompt` / `LSKF`, the authenticator constructs `authenticatorData` starting with `rpIdHash = SHA-256("example.com")`, sets the User Present (`UP`) and User Verified (`UV`) flags, increments/sets sign count, and computes:

$$\sigma = \text{ECDSA-Sign}_{sk}\bigl(\text{authenticatorData} \parallel \text{SHA-256}(\text{clientDataJSON})\bigr)$$

Why does this eliminate phishing *mathematically* rather than heuristically [101]? Because the Android OS / verified browser constructs `rpId` and `clientDataJSON.origin` directly from the TLS connection's authenticated domain (or the calling Android APK's `APK Signature Scheme v3` certificate fingerprint registered inside `https://example.com/.well-known/assetlinks.json` via Digital Asset Links!). If a user is tricked onto `example-login.evil.com`, the handset computes `SHA-256("example-login.evil.com")`, finds zero matching passkeys for `evil.com`, and *cannot even select* the `example.com` private key!

![Figure: Credential Manager passkey authentication, Google Password Manager E2EE sync security domain wrapped via Titan HSM, and CTAP 2.2 caBLE proximity transport.](diagrams/13-passkey-sync-cable-flow.svg)

How does `Google Password Manager` (`GPM`) sync multi-device passkeys across a user's Android phone, tablet, and Chrome profile so losing a handset doesn't brick every bank and email login, without allowing Google servers to read or forge passkeys [102]? `GPM` stores passkey private keys inside an *End-to-End Encrypted (`E2EE`) Security Domain* (`hw_protected` Chrome Sync vault). First, passkey private scalars $sk$ are encrypted on-device using `AES-256-GCM` under a random 256-bit *Security Domain Secret* $K_{\text{vault}}$ that Google servers never possess in plaintext. Second, enrolling a new device into the security domain requires proving knowledge of the user's existing Android Lock Screen Knowledge Factor (`LSKF` PIN/password) via the exact same `Google Titan` Cloud Key Vault HSM cohort architecture detailed in [Chapter 19](19-e2ee-backups-private-ai-compute.md) (where hardware-attested `Titan` silicon enforces a strict lifetime ceiling of `<= 10` failed PIN attempts before permanently destroying the escrow share!) or scanning a direct device-to-device recovery transfer [102, 131]. Third, for regulated enterprises or sovereign setups requiring *strictly non-exportable single-device keys* (`device-bound passkeys`), `WebAuthn` supports `residentKey` / Enterprise Attestation or `AndroidKeyStore`-backed `StrongBox` keys that never sync off the originating silicon die [101].

Finally, how do you use a passkey stored on your Android phone to log into a desktop workstation lacking a biometric reader, *without* allowing a remote attacker in another country who phished you on Discord to trick you into approving a push prompt (`MFA fatigue` / push bombing)? Through `CTAP 2.2` Hybrid Transport (`caBLE`, Cloud-Assisted Bluetooth Low Energy) [101]! The desktop browser displays a dynamic QR code encoding an ephemeral P-256 public key + tunnel routing hint. When your Android camera scans that QR code, both the desktop and your phone *must exchange short-range Bluetooth Low Energy (`BLE`) proximity advertisements* proving physical co-location within meters of the monitor before opening an end-to-end `Noise`-protocol encrypted WebSocket tunnel (`cable.ua5v.com`) to transport the `WebAuthn` challenge and signed assertion [101]! Remote attackers miles away cannot emit the local `BLE` advertisement near your phone, neutralizing remote QR-relay / push-fatigue attacks at the radio physics layer.

## Vendor, OEM, & Custom-OS Boundaries

One of the highest-profile biometric failures in smartphone history occurred in 2019 on early ultrasonic under-display fingerprint sensors (`Samsung Galaxy S10 / Note 10`), where certain third-party textured silicone gel screen protectors left a permanent ridge pattern scanned by the ultrasonic transducer, allowing *any* un-enrolled finger pressing on the protector to unlock the phone until Samsung issued an urgent `TEE` matcher firmware update! Today, `CTS` (`CtsBiometricsTestCases`) and `CDD` Section 7.3.10 enforce strict sensor/pipeline testing, and Google's Pixel 8/9/10+ advanced dual-pixel camera + `Tensor` `TPU`/`Trusty` secure ISP face pipeline achieved full `Class 3` (`Strong`) certification even from a single cutout sensor by routing raw sensor frames directly into `TrustZone`-protected memory with ML presentation-attack defenses achieving `SAR <= 7%` [98].

## Inspecting via ADB, Fastboot, & Attestation

Inspect every biometric sensor registered on the handset along with its certified `CDD` strength tier (`strength: 15` = `BIOMETRIC_STRONG` Class 3; `255` = `BIOMETRIC_WEAK` Class 2; `4095` = `BIOMETRIC_CONVENIENCE` Class 1!):

```bash
adb shell dumpsys biometric | grep -iE 'SensorProps|strength|modality|authenticatorId' | head -n 12
```

Query `CredentialManager` service state and registered passkey / password `CredentialProviderService` packages enabled for the current user:

```bash
adb shell dumpsys credential_service | head -n 16
adb shell settings get secure credential_service
```
