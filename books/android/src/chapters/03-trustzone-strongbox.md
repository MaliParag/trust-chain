# Arm TrustZone TEEs vs. Discrete StrongBox Security Processors

## Overview

* **Link in the Chain:** Hardware secret-isolation and physical tamper-resistance substrate; isolates cryptographic key material, passcode rate-limiting state, and What-You-See-Is-What-You-Sign (`WYSIWYS`) confirmation UI outside the Normal World `EL1` Linux kernel.
* **Core Security Invariant:** Private keys generated inside a Trusted Execution Environment (`TEE`) or discrete `StrongBox` security processor never enter Normal World DRAM in plaintext, and `StrongBox` operations additionally resist off-die bus probing, `NAND` flash cloning, electromagnetic side channels, and voltage or laser fault injection.
* **Ecosystem Enforcement Tier:** Available in both `GREEN` and `YELLOW` locked states with hardware key wrapping bound to the active verified boot root; accessible in `ORANGE` unlocked state only for newly generated `UNVERIFIED`-bound keys (previously sealed `GREEN`/`YELLOW` keys remain undecipherable, and Samsung devices blow the irreversible `Knox` fuse on first unlock).
* **Trusted Computing Base (TCB):** For `TEE`: `EL3` Secure Monitor (`BL31`), `TZASC` (`TZC-400`) DRAM firewall, `S-EL1` OS (`Google Trusty`, `Qualcomm QTEE`/`QSEE`, `Samsung TEEGRIS`, `Trustonic Kinibi`, `OP-TEE`), and all co-resident `S-EL0` trustlets; for `StrongBox`: dedicated off-SoC silicon (`Google Titan M2` `RV32IMC` or `Samsung Knox Vault`), private on-die SRAM/NVM, hardware `TRNG`, and narrow `SPI` firmware.
* **Seam & Handoff:** Provides logically and physically isolated cryptographic execution engines (`SECURITY_LEVEL_TRUSTED_ENVIRONMENT` and `SECURITY_LEVEL_STRONGBOX`); hands typed `KeyParameter` policy enforcement, boot-patchlevel sealing, `SyntheticPassword`, and `Weaver` passcode throttling protocols to [Chapter 4](04-keymint-weaver-throttling.md).

## Threat Model & Ecosystem Constraint

Even with `AVB 2.0` ([Chapter 1](01-bootrom-avb-vbmeta.md)) and `dm-verity` ([Chapter 2](02-antirollback-verity-apex.md)) guaranteeing that the Android kernel boots from bit-for-bit authentic read-only partitions, runtime `Ring 0` (`EL1`) memory is never permanently trustworthy. Across the past decade, hundreds of memory-corruption bugs in `Mali` and `Adreno` GPU shader compilers, ALSA/UVC USB gadget parsers, Wi-Fi firmware rings, and VFS subsystems have granted local apps or physical USB appliances arbitrary read/write execution inside `EL1` [14, 16, 43, 44]. If Android kept `File-Based Encryption` master keys, `Keystore` ECDSA signing keys, or Lock Screen Knowledge Factor (`LSKF`) verifiers inside kernel slab caches, a single `EL1` exploit or cold-boot DRAM dump would immediately surrender every secret on the handset and permit offline GPU brute-forcing of a six-digit PIN ($10^6$ candidates in under a millisecond) [14, 62].

Isolating secrets from `EL1` across a multi-vendor mobile ecosystem confronts two distinct adversary classes whose capabilities pull silicon architecture in opposite directions [26, 47, 61]:

First is the *privileged software Ring 0 adversary*: an exploit chain executing arbitrary instructions at Normal World `EL1` on the main application processor. This attacker can issue millions of crafted Secure Monitor Calls (`SMC`), mutate shared Normal-to-Secure communication buffers (`ION` or `DMA-BUF` scatter-gather pages) concurrently from another CPU core to trigger double-fetch Time-of-Check-to-Time-of-Use (`TOCTOU`) races, manipulate SoC Dynamic Voltage and Frequency Scaling (`DVFS`) regulators (`CLKSCREW` [162]), and probe shared L1/L2/Last-Level CPU caches (`TruSpy` [163]) across world switches [14, 31, 164].

Second is the *invasive physical laboratory adversary*: a state forensics lab or hardware attacker with microscope access to the printed circuit board. This attacker can desolder and snapshot external `UFS` flash packages to replay retry counters (`NAND mirroring` [62]), position near-field electromagnetic probes over the SoC package to capture Differential and Correlation Power Analysis (`DPA`/`CPA`) waveforms during `AES` or `ECDSA` operations [165], hijack on-board PMIC SVID/SPMI buses (`VoltPillager` [107]), or fire nanosecond infrared laser pulses through thinned silicon substrate to skip branch instructions inside a PIN check [26, 27, 61]. On-die `Arm TrustZone` was adopted to defeat the software adversary at near-zero bill-of-materials cost; discrete `StrongBox` processors (`Google Titan M2` and `Samsung Knox Vault`) were created because `TrustZone` repeatedly struggled against both bloated software attack surfaces and physical silicon physics.

## Architecture & AOSP Implementation

### `EL3` `SMC` World Switching and `S-EL1` TEE Architectures

Every modern 64-bit Android application processor implements the `Arm TrustZone` Security Extension, time-slicing each physical CPU core between Normal World (`SCR_EL3.NS = 1`) and Secure World (`SCR_EL3.NS = 0`) [46, 47]. Normal World `EL1` kernel drivers (`drivers/trusty/`, `drivers/tee/optee/`, or Qualcomm `qseecom`/`smcinvoke`) cannot branch into Secure memory directly. Instead, they marshal arguments into general-purpose registers `w0`/`x0` through `x7` formatted per the Arm `SMC Calling Convention` (`SMCCC`, `ARM DEN 0028` [54]) and execute `SMC #0`.

Inside the 32-bit Function Identifier passed in `w0`, bit `31` selects between two fundamentally different execution models handled by Arm Trusted Firmware-A `BL31` at `EL3` [51, 54]. A *Fast Call* (`w0[31] == 1`, used for `PSCI` CPU power state transitions [52], `SMCCC_ARCH_WORKAROUND` mitigations, and hardware `TRNG` entropy reads [166]) executes atomically in `EL3` with normal interrupts masked (`DAIF` set) and returns immediately without scheduling a Trusted OS. Conversely, a *Yielding Call* (`w0[31] == 0`, Owning Entity Numbers `50..63`, used for `KeyMint`, `Gatekeeper`, and `Widevine` operations) switches `SCR_EL3.NS = 0`, restores the `S-EL1` register bank, and enters the Trusted OS scheduler with Non-Secure Group 1 interrupts routed to preempt execution cleanly [53, 54]. If a hardware timer or touch IRQ fires in Normal World while `KeyMint` is computing an `RSA-4096` signature in `S-EL0`, `GICv3` traps back to `EL3`, preempts the Secure thread, services the Normal World IRQ in `EL1` without sluggish UI frame drops, and resumes the yielded `SMC` afterward [53, 54].

Memory isolation across worlds rests on AXI bus protection signaling enforced by the `CoreLink TZC-400` (`TZASC` [47, 56]). Secure World page tables clear the `NSTable`/`NS` descriptor bits, driving `AxPROT[1] = 0` onto the interconnect so Secure transactions reach carved-out Secure DRAM regions (`0x...`), whereas Normal World `EL1`/`EL2` hardware forces `AxPROT[1] = 1` regardless of guest PTE contents, causing `TZC-400` to abort any unauthorized Normal World CPU or non-secure DMA access to Secure DRAM [47, 56].

### Why Monolithic `TrustZone` Trustlet Ecosystems Repeatedly Broke

On paper, `S-EL1` was meant to run a tiny, formally verifiable cryptographic kernel. In commercial smartphone reality between 2014 and 2022, SoC vendors and OEMs treated `TrustZone` as an all-purpose DRM and proprietary IP bunker [14, 164, 172]. Alongside `Keymaster` and `Gatekeeper`, OEMs loaded megabytes of complex C code into `S-EL0`: `Widevine` Level 1 video decryptors parsing untrusted H.264/HEVC/AV1 subsample headers, `PlayReady` ASN.1/XML license parsers, `HDCP 2.x` display state machines, biometric image pre-processors, Alipay/WeChat payment applets, and OEM enterprise agents [14, 158, 164].

Gal Beniamini's landmark Google Project Zero research (`CVE-2015-6639` and `CVE-2016-2431` [14, 172]), followed by Check Point (`CVE-2019-10574` [158]), NCC Group (`CVE-2019-1010292`..`298` [174]), Shakevsky et al. (`Trust Dies in Darkness` [169]), and the `Teezz` fuzzing campaign [164], exposed four systemic flaws in this shared-die `TEE` model:

First, *shared-memory boundary confusion (`ION` / `DMA-BUF`)*: to avoid copying megabytes of encrypted 4K video across `EL3` registers, `QSEECOM`, `MobiCore`, and early `OP-TEE` mapped physical Normal World `ION` / `DMA-BUF` scatter-gather buffers directly into `S-EL0` trustlet virtual memory [14, 31, 174]. Whenever a C trustlet validated a length or offset field inside that shared buffer and then re-read the field microseconds later (`double fetch`), a concurrent Normal World `EL1` CPU thread could mutate the buffer mid-check, turning TLV/ASN.1 parsers into deterministic stack or heap overflows (`CVE-2015-6639`, `CVE-2019-10574` [14, 158]). Worse, if `S-EL1` failed to verify that caller-supplied buffer physical addresses did not overlap Secure World `TZASC` ranges (`CVE-2019-14040` / overlap bugs [31]), Normal World callers tricked `S-EL1` into overwriting its own Secure RAM!

Second, *over-privileged `S-EL0` to `S-EL1` escalation and trustlet downgrades*: on Qualcomm `QSEE` prior to modern `QTEE` sandboxing, signed `.mdt`/`.b00` trustlet files lived on the Normal World filesystem (`/system/etc/firmware` or `/vendor/firmware_mnt`) rather than inside Secure flash, and `QSEE` lacked per-trustlet hardware rollback fuses [14, 158]. An attacker with `EL1` root could load an *older*, genuinely Qualcomm-signed vulnerable `widevine` trustlet into `QSEE`, exploit `CVE-2015-6639` for `S-EL0` code execution, and pivot through an unchecked `S-EL1` `qsee_syscall` pointer bug (`CVE-2016-2431`) to gain arbitrary Secure Kernel execution, extracting the hardware-derived `KeyMaster` key encryption key [14]! Even without memory corruption, Shakevsky et al. showed that proprietary cryptographic designs inside Samsung's `TEEGRIS` `Keymaster` TA (`CVE-2021-25444` and `CVE-2021-25490` [169]) allowed Normal World callers to supply custom `AES-GCM` IVs during key wrapping and downgrade v20 blobs to v15, recovering hardware-protected ECDSA keys via trivial stream-cipher XOR across 100 million Galaxy S9 through S21 devices.

Third, *shared silicon side channels and software fault injection*: because `TrustZone` executes on the exact same Cortex cores, L1/L2 caches, and PMIC voltage rails as Normal World Linux, `TruSpy` recovered `AES` keys across world switches via `Prime+Probe` cache contention [163], while `CLKSCREW` (`Tang et al.` [162]) used compromised `EL1` kernel access to overclock and undervolt CPU regulators during `TrustZone` `AES` and `RSA` execution, inducing single-byte differential faults that extracted `QSEE` keys purely from software without touching the hardware!

### Discrete `StrongBox`: `Google Titan M2` and `Samsung Knox Vault`

To sever high-value keys and passcode counters from shared-SoC software bloat, shared CPU caches, shared DVFS rails, and external `UFS` flash chips simultaneously, Android 9 (`API 28`) introduced `SecurityLevel::STRONGBOX` inside `Keystore`/`KeyMint` [26, 28]. On flagship hardware, `StrongBox` is realized as a physically discrete tamper-resistant security SoC: `Google Titan M` (Arm Cortex-M3, Pixel 3 to 5 [175]) succeeded by `Google Titan M2` (custom RISC-V silicon on Pixel 6 through Pixel 10+, co-architected with the open-source `lowRISC OpenTitan` project [26, 61, 176]), and `Samsung Knox Vault` (dedicated secure processor + secure EEPROM certified to Common Criteria `EAL5+`/`EAL6+` on Galaxy S21+ [27]), alongside Qualcomm's die-isolated `Secure Processing Unit` (`SPU` [177]).

![Figure: Google Titan M2 discrete StrongBox internal RISC-V architecture, active fault sensors, and off-die SPI boundary.](diagrams/03-extra-titan-m2-internal-blocks.svg)

Inspect the internal silicon architecture of `Google Titan M2` [26, 61, 176]. Mounted as an independent package on the Pixel mainboard, `Titan M2` shares zero LPDDR DRAM, zero L1/L2/SLC caches, and zero software clock/voltage domains with the `Google Tensor` application processor, communicating exclusively over a narrow, packet-framed Serial Peripheral Interface (`SPI`) bus (`external/nos` / GSC transport [178]). Inside `Titan M2`'s physical die boundary sit five purpose-built hardware blocks derived from `OpenTitan` [26, 61]:

First, a hardened 32-bit *`RV32IMC` RISC-V processor core* (`Ibex` security lineage) incorporating dual-core lockstep execution, shadow program-counter integrity checks, instruction-timing jitter, and a hardware Memory Protection Unit (`MPU`) enforcing strict `W^X` (`Write XOR Execute`) permissions over private on-die SRAM with *zero dynamic heap allocator* (eliminating `malloc`/`free` use-after-free bug classes structurally) [61, 175, 176].

Second, *private on-die embedded flash (`NVM`)* and *on-die SRAM* [26]. Because `Weaver` retry counters ([Chapter 4](04-keymint-weaver-throttling.md)) and root key hierarchies reside inside `Titan M2`'s internal flash rather than external `UFS` `RPMB`, desoldering and cloning external storage chips (`NAND mirroring` [62]) cannot roll back a single PIN attempt counter.

Third, *side-channel-masked cryptographic engines and physical `TRNG`*: hardware `AES`, `SHA-2`/`SHA-3`/`KMAC`, and `OTBN` (`OpenTitan Big Number` ECC/RSA coprocessor) employ first-order Boolean and arithmetic masking, randomized dummy rounds, and internal entropy reseeding from a NIST SP 800-90B physical True Random Number Generator (`TRNG`), defeating electromagnetic `DPA`/`CPA` traces [26, 61, 165].

Fourth, *active environmental and fault-injection sensors*: dedicated analog detectors monitor supply voltage glitches, clock frequency anomalies, temperature extremes, and focused infrared laser pulses (`Alert Handler`); detecting an out-of-envelope fault triggers immediate hardware alert escalation and picosecond zeroization of internal key registers before a faulted instruction can retire [26, 61].

Fifth, *Insider Attack Resistance (`IAR`)* [26]: `Titan M2`'s immutable mask boot ROM refuses to activate updated `Titan M2` firmware unless the user first authenticates with their valid `LSKF` passcode (`IAuthSecret` [179]). Even if a nation-state compromised Google's or Samsung's firmware signing keys and pushed a targeted OTA to a journalist's locked phone, `StrongBox` cannot boot the new firmware while the phone sits locked!

Quarkslab's multi-year offensive audit of first-generation Cortex-M3 `Titan M` (`CVE-2022-20233` [175, 180]) illustrates both why discrete chips shrink attack surface and why `Titan M2` added RISC-V hardware hardening. Fuzzing `Titan M`'s Protobuf `Keymaster` task under `AFL++`/Unicorn, Damiano Melotti and Maxime Rossi Bellom found a single-byte out-of-bounds `strb` write (`0x01`) in `param_find_digests_internal` when `ImportKeyRequest` passed a crafted `Tag::DIGEST` (`0x20005`) integer [180]. On `Titan M`'s static Cortex-M3 memory map (which lacked stack/pointer randomization beyond a static stack canary), corrupting one byte of `KEYMASTER_SPI_DATA` redirected subsequent `SPI` receive buffers over an idle task's saved stack frame to mount a Return-Oriented Programming (`ROP`) chain [180]. Notice two crucial boundaries even in that exploit: triggering `CVE-2022-20233` required *already possessing privileged `system`/`keystore` `EL1` execution* on the host (`SELinux` blocks untrusted apps from `/dev/citadel0`), and `Titan M2` responded by migrating to hardened RISC-V lockstep/CFI/shadow-stack and tightened parameter bounds [26, 176].

### `Android Protected Confirmation`: Hardware `WYSIWYS` Transaction Signing

Even an unbreakable `Titan M2` chip cannot tell whether the human user actually *intended* to sign a payload if a compromised Normal World OS (`EL1` rootkit or `AccessibilityService` overlay trojan in [Chapter 11](11-accessibility-advanced-protection.md)) draws `"Approve $15 coffee"` on the OLED screen while passing `"Wire $150,000 to attacker"` over `SPI` to `KeyMint::finish()`! `Android Protected Confirmation` (`ConfirmationPrompt` API + `IConfirmationUI` HAL + `Tag::TRUSTED_CONFIRMATION_REQUIRED` [97, 181, 182]) closes this What-You-See-Is-What-You-Sign (`WYSIWYS`) display gap.

![Figure: Android Protected Confirmation hardware-isolated display and physical button approval sequence.](diagrams/03-protected-confirmation-flow.svg)

When a medical, banking, or enterprise app generates an asymmetric signing key with `setUserConfirmationRequired(true)` (and optionally `setUnlockedDeviceRequired(true)` or `setUserPresenceRequired(true)` via `Tag::TRUSTED_USER_PRESENCE_REQUIRED` [97]) and invokes `ConfirmationPrompt.presentPrompt(promptText, extraData)`, control enters the Secure World `ConfirmationUI` applet (`Trusty` Trusted UI [57, 181, 182]). Using `TZASC` and `SMMUv3` Secure `StreamID` locks on the display controller (`DPU`) composer planes, `Trusty` takes exclusive hardware ownership of the physical screen buffer, blocking `EL1` Linux `SurfaceFlinger` from compositing transparent overlays or reading/forging touch interrupts [63, 181]. Simultaneously, on Pixel hardware, physical confirmation taps the hardware Power button (with Volume buttons for cancel) wired over a dedicated GPIO trace monitored directly by `Titan M2` (`Tag::TRUSTED_USER_PRESENCE_REQUIRED` [26, 97]).

Only when the human physically presses the hardware button while the isolated display frame lock is uninterrupted does `ConfirmationUI` / `StrongBox` compute a 32-byte `HMAC-SHA256` confirmation token over the exact rendered UTF-8 string and binary nonce (`extraData`) [181, 182]:

$$\tau_{\text{confirm}} = \text{HMAC-SHA256}_{K_{\text{confirm}}}\Bigl(\texttt{"confirmation token"} \parallel \text{CBOR}\bigl(\{\texttt{"prompt"}: \text{promptText}, \; \texttt{"extra"}: \text{extraData}\}\bigr)\Bigr)$$

Here $K_{\text{confirm}}$ is a 256-bit symmetric key shared exclusively inside secure hardware (`ISharedSecret` / `TEE`-to-`StrongBox` channel [183]). When the app passes $\tau_{\text{confirm}}$ to `IKeyMintOperation::finish()` [98], `KeyMint` recomputes the `HMAC` over the exact CBOR message bytes being signed and refuses with `ErrorCode::NO_USER_CONFIRMATION` if a single character differs [97, 181]. Verifying the resulting ECDSA signature alongside the key's X.509 `Key Attestation` chain ([Chapter 15](15-key-attestation-rkp.md)) gives a remote relying party cryptographic certainty that genuine hardware rendered that exact prompt and observed a physical human button press, even under total `EL1` kernel compromise [181].

## Vendor, OEM, & Custom-OS Boundaries

Hardware security tiers diverge across Android price bands under `CDD` Section 9.11 [9]. Entry-level and mid-range Qualcomm Snapdragon and MediaTek Dimensity devices implement `IKeyMintDevice/default` (`SECURITY_LEVEL_TRUSTED_ENVIRONMENT`) inside `QTEE`, `Trusty`, or `OP-TEE` without a discrete security chip; calling `setIsStrongBoxBacked(true)` throws `StrongBoxUnavailableException`, requiring apps to fall back cleanly to `TEE`-backed keys [28]. Even within `TEE`-only devices, modern Snapdragon BSPs significantly narrowed Normal-to-Secure IPC exposure by deprecating raw shared-buffer `/dev/qseecom` device nodes in favor of `SmcInvoke` (`Mink` object-capability IPC [171]), which tracks kernel-mediated capability handles per session, pairs with strict `SELinux` `neverallow` rules barring `untrusted_app` and `shell` from opening TEE character devices directly, and shifts new AOSP TAs (`KeyMint` `kmr` and `Secretkeeper`) from C to memory-safe Rust [79, 101, 170, 171].

Flagship product lines, specifically Google Pixel (`Titan M2`), Samsung Galaxy S and Z series (`Knox Vault`), and selected Snapdragon 8 Elite OEM flagships enabling Qualcomm's `SPU` (`Secure Processing Unit` [177]), register *both* `IKeyMintDevice/default` (`TEE`, optimized for sub-millisecond bulk `AES`/`HMAC`/`ECDSA` throughput over shared memory) and `IKeyMintDevice/strongbox` (discrete or physically isolated silicon over `SPI`/mailbox, trading 15 to 50 ms RPC latency for physical fault, side-channel, and `NAND`-mirroring immunity) [26, 27, 28, 177]. Comparing the three flagship `StrongBox` realizations illuminates subtle trade-offs in physical boundary placement: `Google Titan M2` places compute (`RV32IMC`), RAM, and embedded flash (`NVM`) inside a single off-SoC discrete package wired over `SPI` [26, 61]; `Samsung Knox Vault` pairs an isolated secure subsystem processor with a physically dedicated off-SoC secure `EEPROM` chip over an encrypted hardware bus protected by laser, temperature, and voltage tamper meshes certified to Common Criteria `EAL5+`/`EAL6+` [27]; and `Qualcomm SPU` integrates a dedicated security island inside the Snapdragon die package with independent clock/reset/crypto fencing to lower board area while sacrificing physical multi-package separation [177]. Remarkably, on `GrapheneOS` (`YELLOW` locked Pixel), 100 percent of `Titan M2`'s `StrongBox` `KeyMint`, 64-slot `Weaver` throttling, `Insider Attack Resistance`, and hardware `Auditor` attestation function identically to stock `GREEN` Pixel OS with zero dependency on proprietary cloud services [20, 128].

### The Online-Oracle Boundary of Hardware Key Isolation

Even an air-gapped, laser-hardened `Titan M2` or `Knox Vault` chip obeys a foundational law of cryptographic systems engineering: *hardware key isolation prevents raw key exfiltration, not online key invocation by an authorized host principal that is currently compromised* [2, 28].

> **Warning.**
> If an application generates a `StrongBox` ECDSA key with `setUserAuthenticationRequired(false)` (`Tag::NO_AUTH_REQUIRED`), an exploit running inside that app's UID (or a compromised `EL1` kernel impersonating that UID over `Binder` to `keystore2`) cannot copy the 256-bit private scalar $d$ off the handset, *but it can ask `StrongBox` to sign arbitrary challenges as an online oracle for as long as the implant remains resident in RAM*. Defeating silent background abuse requires binding keys to fresh hardware-authenticated human gestures (`HardwareAuthToken`), Verified Boot patch levels, and `Weaver`-throttled `SyntheticPassword` state, which brings us directly to [Chapter 4](04-keymint-weaver-throttling.md).

Enumerate registered `KeyMint` (`default` `TrustZone` TEE vs. `strongbox` discrete processor), `Weaver`, `AuthSecret`, and `ConfirmationUI` HAL services declared in the device's `VINTF` manifest:

```bash
adb shell service list | grep -iE 'keymint|weaver|authsecret|confirmationui'
adb shell lshal 2>/dev/null | grep -iE 'keymint|keymaster|weaver|confirmationui' | head -n 8
```

Verify whether the handset advertises CTS-certified `StrongBox` silicon (`android.hardware.strongbox_keystore` feature version `100`/`200`/`300`/`400` mapping to `KeyMint` v1–v4) and `Android Protected Confirmation`:

```bash
adb shell pm list features | grep -iE 'strongbox|hardware_keystore|confirmation'
```

On Google Pixel (`Tensor` + `Titan M2` + `Trusty`) or Samsung (`Knox Vault`) devices, inspect non-sensitive `StrongBox` / `TEE` firmware and boot-level strategy properties exposed to `getprop`:

```bash
adb shell getprop ro.hardware.keystore
adb shell getprop ro.keystore.boot_level_key.strategy
adb shell getprop | grep -iE 'titan|gsc|trusty|knox' | head -n 8
```
