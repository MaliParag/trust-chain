# Apple Account, Passkeys, Continuity, and Spatial Gaze Isolation

## Overview

* **Link in the Chain:** Personal account identity, multi-device proximity mesh, and spatial human-intent boundary in Part III; binds cloud sign-in (`GSA`) and phishing-resistant `WebAuthn` credentials to `SEP`-synced circles ([Chapter 11](11-keychain-stolen-device.md), [Chapter 12](12-sep-app-device-attestation.md)) while gating cross-device `Continuity` and `visionOS` eye-tracking telemetry.
* **Core Security Invariant:** User passwords never cross the network during `GrandSlam` (`GSA`) `SRP-6a` exchanges, `Passkeys` sign challenges strictly bound to `SHA-256(rpId)` verified by `authenticationservicesd`, `Auto Unlock` enforces physical speed-of-light Time-of-Flight (`ToF`) distance bounds ($\le 3\text{ m}$), and `visionOS` isolates raw eye-camera streams inside the `R1` co-processor and `RealityKit` system compositor until a physical finger-pinch commit occurs.
* **Platform Matrix:** `GSA`, `Sign in with Apple`, synced `Passkeys` (`prf` and `caBLE` v2), and `Continuity` (`Handoff`, `Universal Clipboard`, `AirDrop`) span `iOS`, `iPadOS`, `macOS`, `watchOS`, and `visionOS`; `Auto Unlock` pairs `watchOS` with `macOS` (and `iOS`), `NameDrop` (`iOS 17+` / `watchOS 10+`) uses ultra-close contact proximity, and `R1` spatial gaze isolation is unique to `visionOS` on `Apple Vision Pro`.
* **Trusted Computing Base (TCB):** `AuthKit` (`akd`), `AppleIDAuthSupport`, and `gsa.apple.com` `SRP-6a` servers; `authenticationservicesd` and `swcd` Associated Domains validators; `iCloud Keychain` (`CKKS`/`Octagon`) sync circles; `IEEE 802.11mc` FTM / `802.15.4z` UWB transceivers; `sharingd` (`BLE` + `AWDL` `mTLS`); and the `Vision Pro` `R1` co-processor + `RealityKit` render server.
* **Failure Horizon & Handoff:** OIDC claim-binding bugs (`CVE-2020-9768`) or local credential-store permission flaws (`CVE-2026-43760`) weaken account isolation, unsalted `SHA-256` phone hashes in legacy `AirDrop` enabled dictionary reversal (*PrivateDrop*), and `FaceTime` `Persona` avatar eye rendering leaked virtual-keyboard gaze vectors (*GAZEploit*); hands off enterprise fleet supervision, `DDM`, and `Platform SSO` to [Chapter 14](14-ddm-platform-sso.md).

## Threat Model & Design Tension

An individual rarely interacts with a single isolated Apple device; an `iPhone`, `MacBook`, `iPad`, `Apple Watch`, and `Apple Vision Pro` function as a cohesive personal mesh unlocking one another on desk approach, sharing clipboards, syncing `WebAuthn` credentials, and authenticating to third-party relying parties [1, 63, 369]. Extending cryptographic trust across that personal constellation exposes four distinct adversarial surfaces spanning remote web attackers, radio-adjacent eavesdroppers, and untrusted local applications [370, 371, 372, 373].

First, at account login and federated web sign-in, credential stuffing, server database breaches, and real-time Adversary-in-the-Middle (`AiTM`) reverse-proxy kits defeat traditional cleartext-over-TLS password and 6-digit OTP flows, while legacy OAuth identity providers routinely track every third-party app a user opens [369, 370, 374, 375]. Second, synchronizing `WebAuthn` `Passkeys` across a user's personal devices creates a high-value cloud target: if Apple's servers held plaintext private keys or if cross-device QR login (`caBLE`) lacked physical proximity proofs, a cloud breach or remote webinar screen-share phish could impersonate users across banks and enterprise tenants [369, 376, 377].

Third, wireless proximity features (`Auto Unlock with Apple Watch`, `Handoff`, and `AirDrop` over `BLE` and `Apple Wireless Direct Link` `AWDL`) confront two classic radio-frequency threats: *mafia-fraud relay attacks*, where two colluding adversaries bridge frames between a victim's wrist in a coffee shop and their locked MacBook in an office [63, 372], and *passive contact enumeration*, where nearby sniffers harvest `BLE` discovery frames to deanonymize telephone numbers [371, 378]. Fourth, on `Apple Vision Pro`, turning human eye gaze into the primary spatial targeting cursor creates an unprecedented biometric privacy hazard: academic eye-tracking studies demonstrate that raw $90\text{--}100\text{ Hz}$ pupil dilation, microsaccade velocity, and gaze dwell heatmaps involuntarily disclose cognitive load, neurological conditions, personal preferences, and virtual-keyboard PIN entries before the user ever clicks [10, 373, 379].

## Silicon & System Mechanics

### GrandSlam (GSA) SRP-6a, Trusted-Device 2FA, and Sign in with Apple

Every interactive Apple Account authentication on-device is orchestrated by `AuthKit` (`akd`) and `AppleIDAuthSupport.framework` communicating over TLS with Apple's *GrandSlam (`GSA`)* directory service at `gsa.apple.com/grandslam/GsService2` [370, 380]. Rather than posting a plaintext password over HTTPS (which would expose the raw secret to server memory inspection, reverse proxies, or accidental logging), `GSA` implements a modified `RFC 2945` / `RFC 5054` *Secure Remote Password (`SRP-6a`)* zero-knowledge password-authenticated key exchange (`s2k` / `s2k_fo` over a 2048-bit safe prime group $N$ with generator $g$ and multiplier $k = H(N \| g)$) [370, 380, 381].

During enrollment or password change, the client derives password scalar $x = \text{PBKDF2-HMAC-SHA256}(\text{UTF8}(\text{password}), s, i)$ using random salt $s$ and iteration count $i$, uploading only $(s, i, v = g^x \bmod N)$ to Apple [370, 380]. At login, a four-request `GsService2` plist exchange executes [380]. In Request 1, `akd` generates ephemeral secret $a$, computes $A = g^a \bmod N$ (`A2k`), and submits `A2k`, username `u`, and a client provisioning dictionary (`cpd`) carrying *Anisette* machine-provisioning headers (`X-Apple-I-MD` and `X-Apple-I-MD-M`, short-lived cryptographic tokens tying the request to provisioned Apple silicon state) [380]. In Response 1, `GSA` returns salt `s`, iterations `i`, session cookie `c`, and blinded server public value $B = (k v + g^b) \bmod N$ [380, 381]. Both sides compute scrambling parameter $u = \text{SHA-256}(A \| B)$, and `akd` derives the shared premaster secret and session key locally without ever transmitting $x$:

$$S = \bigl(B - k g^x\bigr)^{\,a + u x} \equiv g^{a b + u x b} \pmod N, \qquad K_{\text{SRP}} = \text{SHA-256}(S)$$

In Request 2, `akd` proves possession of $K_{\text{SRP}}$ via transcript digest `M1`; in Response 2, `GSA` returns mutual server proof `M2` alongside `spd` (*Server-Provided-Data*), an `AES-GCM` payload encrypted under a key derived from $K_{\text{SRP}}$ containing the account's `adsid`, `DsPrsId`, intermediate `GsIdmsToken`, `idmsWalrusStatus` (`ADP` enrollment flag), `custodianEnabled`, and `passkeyPresent` state [380].

If two-factor authentication (`2FA`) is required, Request 3 (`GET /auth/verify/trusteddevice`) instructs Apple's identity servers to push an encrypted notification over `APNs`/`IDS` to existing devices already bound to the user's `SEP`-backed account circle, displaying coarse login geolocation and minting a 6-digit verification code [1, 380, 382]. Submitting that code in Request 4 (`GET /grandslam/GsService2/validate` with `Security-Code` and `X-Apple-Identity-Token = Base64(adsid:GsIdmsToken)`) yields service-scoped `X-Apple-GS-Token` credentials (`com.apple.gs.icloud.auth`, `com.apple.gs.appleid.auth`, `com.apple.gs.idms.pet`) [380]. High-risk journalists, executives, and developers can replace 6-digit push codes entirely by enrolling two *FIDO Certified Hardware Security Keys* (`Security Keys for Apple Account`, `iOS 16.3+` / `macOS 13.2+`), which permanently disables push-code and SMS 2FA fallbacks at `GSA` [382].

For third-party relying parties, *Sign in with Apple* (`ASAuthorizationAppleIDProvider`, built atop `OpenID Connect Core 1.0` `id_token` JWTs signed by Apple's rotating JWK keys) interposes two structural privacy shields [374, 375, 383]. First, the `sub` (subject) claim is a *pairwise developer-team-scoped identifier*: two apps published under different Apple Developer `TeamID`s receive cryptographically distinct `sub` strings for the same human user, preventing cross-company identity graphs [374, 375]. Second, *Hide My Email* provisions unique per-relying-party `@privaterelay.appleid.com` addresses whose inbound MTA enforces strict sender-domain binding, dropping messages if a breached vendor sells the alias to third-party spammers [375].

### Passkeys (WebAuthn Level 3), the PRF Extension, and caBLE v2 Hybrid Transport

Implemented by `authenticationservicesd` (`ASAuthorizationController` and `ASAuthorizationPlatformPublicKeyCredentialProvider`), *Passkeys* instantiate `W3C WebAuthn` Level 3 / `FIDO2` resident (`discoverable`) `ES256` (`P-256`) credentials [369, 376]. Whenever a browser or native app invokes passkey registration or assertion, the untrusted caller never touches key material or constructs the origin claim; instead, `authenticationservicesd` validates either the browser's active TLS origin or the native app's `com.apple.developer.associated-domains` (`webcredentials:<rpId>`) entitlement against `https://<rpId>/.well-known/apple-app-site-association` fetched and cached by `swcd` [376, 384]. `authenticationservicesd` requires live `Face ID`, `Touch ID`, or `Optic ID` (`UV = 1`), computes `rpIdHash = SHA-256(rpId)` inside `authenticatorData`, and signs `authenticatorData || SHA-256(clientDataJSON)` [369, 376]. Because a real-time `AiTM` phishing proxy at `auth-apple-support.net` cannot force `authenticationservicesd` to emit `SHA-256("apple.com")`, credential phishing fails mathematically [369].

![Figure: Personal identity and proximity sequence integrating GSA SRP-6a login, E2EE iCloud Keychain synced Passkeys, and Apple Watch Auto Unlock Time-of-Flight (ToF) physical distance bounding.](diagrams/13-gsa-passkey-continuity-flow.svg)

Across consumer and enterprise deployments on Apple OSes, three distinct `WebAuthn` credential classes trade off multi-device survivability against single-chip non-exportability [364, 369, 376, 377]:

| Passkey / Authenticator Class | Private Key Custody | `WebAuthn` `BE` / `BS` Flags | Enterprise & Attestation Semantics |
|---|---|---|---|
| Consumer Synced Passkey (`iCloud Keychain`) | `secd` `keychain-2.db` synced E2EE via `CKKS` / `Octagon` circle | `BE = 1, BS = 1` | Privacy-preserving `none` attestation by default; survives device loss via `Octagon` |
| Managed Enterprise Passkey (`MDM`/`DDM` Scoped) | Managed `SEP` / `Keychain` scope (`allowCloudKeychainSync = false` or Managed Apple Account) | Policy-governed (`BE = 0` or managed circle) | Supports enterprise attestation via `com.apple.configuration.security.passkey.attestation` (`ACME` `MDA` cert) |
| Roaming `CTAP 2.2` Hardware Key (`ASAuthorizationSecurityKey*`) | External NFC / USB-C secure element (`YubiKey` et al.) | `BE = 0, BS = 0` | Hardware `fido-u2f` / `packed` attestation; required for Apple Account Security Keys |

Starting in `iOS 18`, `iPadOS 18`, `macOS Sequoia 15`, and `visionOS 2`, Apple's platform passkey authenticator also implements the `W3C WebAuthn` *`prf` (Pseudo-Random Function) extension* (`ASAuthorizationPublicKeyCredentialPRFRegistrationInput` / `AssertionInput`), generalizing the `CTAP 2.2` `hmac-secret` primitive to synced passkeys [377, 385]. During `SecItem` passkey creation, `secd` associates an additional per-credential 256-bit symmetric PRF seed alongside the `P-256` signing scalar inside the synced `iCloud Keychain` item. When an encrypted vault web app or native client passes an evaluation salt $s_1$ (`eval` or `evalByCredential`) during assertion, `authenticationservicesd` returns both the `ECDSA` login signature and a deterministic 32-byte key output:

$$K_{\text{PRF}} = \text{HMAC-SHA256}\bigl(K_{\text{cred-seed}},\; \text{SHA-256}(\texttt{"WebAuthn PRF"} \,\|\, \texttt{0x00} \,\|\, s_1)\bigr)$$

End-to-end encrypted web applications (client-side encrypted notes, password vaults, decentralized wallets) can thus authenticate the user *and* derive an origin-bound `AES-256-GCM` master decryption key in a single `Face ID` gesture with zero user-memorized master password [385].

When signing into a non-Apple desktop (`Windows` or `Linux`) that lacks the user's `iCloud Keychain` circle, `iOS` and `iPadOS` execute `FIDO CTAP 2.2` *Hybrid Transport (`caBLE` v2)* [369, 377]. The desktop browser renders a QR code encoding an ephemeral `P-256` public key, a 16-byte routing secret, and tunnel server metadata. Scanning the QR code with the `iPhone` camera does *not* complete login over the internet alone: the `iPhone` broadcasts an encrypted `BLE` proximity frame (`0xFFF9` FIDO service UUID) that the desktop's Bluetooth radio must physically receive before establishing a `Noise`-authenticated end-to-end encrypted `CTAP 2.2` WebSocket tunnel [377]. Consequently, an attacker tricking a victim into scanning a live QR code streamed over a Zoom call or phishing page outside Bluetooth range ($\approx 5\text{--}10\text{ m}$) cannot complete the hybrid handshake [369, 377].

### Continuity: Watch Auto Unlock Time-of-Flight, Handoff, and AirDrop mTLS

Wireless `Continuity` protocols managed by `sharingd` separate *cryptographic peer identity* from *physical distance verification* [63, 372, 386, 387]. In the classic *mafia-fraud relay model* formalized by Cremers, Capkun, et al. [372], suppose Alice leaves her MacBook asleep on an office desk and walks 50 meters down the hall to an espresso bar wearing her unlocked `Apple Watch`. Collaborator Eve stands beside the office Mac while collaborator Mallory stands near Alice in the bar; if `Auto Unlock` relied solely on `BLE` signal strength (`RSSI`, trivially amplified with a directional antenna) and `AES-GCM` challenge-response signatures, Eve and Mallory could relay encrypted frames over low-latency UDP/LTE and unlock Alice's Mac without breaking a single cipher [372].

![Figure: Auto Unlock physical distance bounding contrasting legitimate sub-3-meter 802.11mc FTM / UWB speed-of-light ranging against a two-transceiver cafe relay attack.](diagrams/13-extra-watch-tof-relay-defense.svg)

*Auto Unlock with Apple Watch* defeats mafia-fraud relays by combining `SEP` wrist-state enforcement with nanosecond *Time-of-Flight (`ToF`)* electromagnetic ranging (`IEEE 802.11mc` Fine Timing Measurement `FTM` / `IEEE 802.15.4z` Scrambled Timestamp Sequence `STS` Ultra-Wideband on U1/U2 silicon) [63, 372, 388]. First, the Watch's `SEP` releases its pairwise Continuity key (bootstrapped out-of-band via `APNs` and `Octagon`) *only* while optical/capacitive skin sensors confirm the Watch has remained continuously on the user's wrist since passcode entry [63]. Second, when the Mac wakes and authenticates the Watch over `BLE` and peer-to-peer `Wi-Fi`, the Mac's wireless PHY records hardware transmit timestamp $t_1$ on a ranging frame; the Watch's PHY records arrival $t_2$ and departure $t_3$, signing the calibrated hardware turnaround delta $(t_3 - t_2)$ over the encrypted channel; and the Mac records arrival $t_4$, computing physical separation at the speed of light $c \approx 0.2998\text{ m/ns}$ [63, 388]:

$$d_{\text{ToF}} = c \cdot \frac{(t_4 - t_1) - (t_3 - t_2)}{2} \le d_{\text{max}} \approx 3\text{ meters} \quad (\text{one-way flight} \le 10\text{ ns})$$

Because the Watch's `SEP`/PHY signs $(t_3 - t_2)$ and passive relays cannot transmit radio waves faster than $c$ in vacuum, relaying frames across even $15\text{ meters}$ plus SDR analog-to-digital conversion injects $\ge 100\text{ ns}$ of unforgeable positive delay, causing `sharingd` to abort unlock immediately [63, 372, 388].

Companion `Continuity` features (*Handoff* and *Universal Clipboard*) pair devices signed into the same iCloud account out-of-band over `APNs` (`iMessage`-grade end-to-end encryption) to establish per-device 256-bit `AES-GCM` keys stored in Keychain [386]. Activity advertisements over `BLE 4.2+` encrypt payload metadata under `AES-256-GCM` with monotonic replay counters; when the user accepts a `Handoff` activity or pastes a large `Universal Clipboard` buffer, `sharingd` opens a direct `Apple Wireless Direct Link` (`AWDL`, virtual interface `awdl0`) peer-to-peer `802.11` socket protected by mutual `TLS` (`mTLS`) using `iCloud Keychain`-synced X.509 peer identities [386].

*AirDrop* extends `BLE` + `AWDL` `mTLS` across *different* users' Apple Accounts via Apple-issued *iCloud Identity Certificates* (2048-bit `RSA` / `ECDSA` X.509 certificates stored in Keychain embedding `SHA-256` hashes of the user's verified telephone numbers and email addresses) [63, 387]. When a sender opens the share sheet, `BLE` broadcasts a short identity hash; nearby awake devices in *Contacts Only* mode check whether that short hash matches any contact in their local Address Book before waking `awdl0` [387]. Once `awdl0` comes up, sender and receiver establish `mTLS`, exchange full iCloud Identity Certificates inside the encrypted tunnel, and verify full contact hashes before displaying names/avatars or transferring files [387]. Following TU Darmstadt's *PrivateDrop* disclosure showing that truncated/unsalted `SHA-256` digests over structured 10-digit E.164 phone numbers ($\approx 10^{10}$ candidates) can be reversed in milliseconds with precomputed GPU rainbow tables [371], cryptographic research demonstrated why Private Set Intersection (`PSI`, blinding contact identifiers with per-session elliptic-curve scalars so neither peer learns unmatched entries) is structurally necessary whenever low-entropy human identifiers participate in discovery [371]. Operationally, Apple restricted *Everyone* mode in `iOS 16.2+` to a self-expiring *Everyone for 10 Minutes* toggle (reverting automatically to *Contacts Only* so devices do not broadcast open `AWDL` discovery indefinitely in public venues) and introduced *NameDrop* (`iOS 17+` / `watchOS 10+`), which initiates contact and file exchange via centimeter-range NFC and UWB physical tap rather than ambient `BLE` broadcast, continuing queued high-bandwidth payloads seamlessly over encrypted `CloudKit` transfer if the two users walk apart mid-transfer [387, 389].

### visionOS and R1 Hardware Spatial Gaze Isolation

On `Apple Vision Pro`, four internal infrared eye-tracking cameras illuminate each cornea and pupil at high frame rates both to authenticate *Optic ID* iris patterns inside `SEP` ([Chapter 3](03-secure-enclave.md)) and to drive spatial UI focus across infinite 3D canvases [10, 141]. Allowing third-party apps to subscribe to raw gaze rays (`(origin, direction, pupilDiameter)` at $90\text{--}100\text{ Hz}$) would let any spatial game, browser, or enterprise workspace infer health states, reading comprehension, emotional reactions to sensitive imagery, and secret PINs [373, 390]. Conversely, putting eye tracking behind a binary `TCC` permission prompt would fail through consent fatigue, because users expect every button in every spatial app to highlight smoothly when looked at [10, 390].

![Figure: visionOS spatial gaze privacy pipeline isolating raw internal IR eye-camera streams inside the R1 co-processor and RealityKit system compositor so sandboxed apps receive only pinch-committed tap events.](diagrams/13-visionos-r1-gaze-isolation.svg)

Apple solved this dilemma through *hardware-to-compositor architectural split-rendering* anchored in the dedicated *R1 real-time sensor co-processor* [10, 390]. Internal eye-camera MIPI streams terminate directly in `R1` ($12\text{ ms}$ photon-to-photon pipeline), which streams computed 3D gaze vectors *exclusively* to the privileged `visionOS` system render server (`backboardd` / `RealityKit` compositor) and `SEP` (`Optic ID`), never to application processes [10, 141]. Third-party `SwiftUI` views and `RealityKit` 3D entities attach declarative `HoverEffectComponent` descriptors (`highlight` or `spotlight` shader parameters) submitted ahead of time to the shared scene graph [390]. As the user's eyes scan across ten buttons in a sandboxed app, the *system compositor* computes ray-mesh intersections and modulates pixel luminance on the micro-OLED displays *entirely outside the app's address space*: the app receives zero `onHover` callbacks, zero frame-time variations, and zero memory writes [10, 390]. Only at the instant downward-facing hand cameras confirm an explicit *thumb-to-index pinch gesture* does `visionOS` synthesize a single `SpatialTapGesture` / `UIEvent` on the intersected target and cross Mach IPC into the app [10, 390]. Crucially, `visionOS` extends the exact same split-compositor discipline into `WebKit` for spatial web browsing: if untrusted JavaScript inside a web page could listen for `mouseenter`, `mouseover`, or `pointermove` events driven by eye gaze (or trigger lazy `background-image: url(...)` HTTP fetches inside CSS `:hover` rules), a malicious site could tile the viewport with invisible $10 \times 10\text{ px}$ `<div>` targets and reconstruct a live $60\text{ Hz}$ eye-tracking heatmap on its web server [10, 373, 390]! `WebKit` on `visionOS` therefore suppresses JavaScript pointer-hover event dispatch prior to pinch commit and delegates visual `:hover` feedback strictly to the isolated system compositor without triggering network side effects or readable DOM layout mutations [10, 390]. Only specialized enterprise or assistive applications granted explicit, user-consented `ARKit` hand-skeleton or head-pose entitlements ever receive broader spatial kinematics, while raw consumer eye-gaze vectors remain unobtainable by third-party code [10, 390].

## Platform Forks Across Apple OSes

While `GrandSlam` `SRP-6a`, `Sign in with Apple`, and `WebAuthn` `Passkeys` (`prf`) behave uniformly across `iOS`, `iPadOS`, `macOS`, `watchOS`, and `visionOS` [375, 376, 380, 385], subtle radio and pasteboard forks separate platforms operationally. First, on `Universal Clipboard`, Apple explicitly documents in *Apple Platform Security* that while `iOS 16+` interposes a visible user-paste banner (`tccd` pasteboard consent) when an app reads `UIPasteboard` without a user paste gesture, `macOS` `NSPasteboard` historically permitted background apps running as `UID 501` to poll copied text unless pasteboard access behavior is restricted, meaning copying a password on an `iPhone` can expose it via `Universal Clipboard` to background `macOS` utilities unless the password manager tags the item `org.nspasteboard.ConcealedType` / local-only (`Handoff` disabled per item) [386]! Second, in managed corporate fleets, administrators routinely set `allowCloudKeychainSync = false` (`iCloud Keychain` disabled) alongside `allowAirDrop = false` or `Everyone` blocked, pivoting `macOS` and `iOS` from consumer `Octagon`-synced passkeys to hardware-bound enterprise `Platform SSO` keys ([Chapter 14](14-ddm-platform-sso.md)) [52, 364].

### Indirect Representation Leaks: PrivateDrop and GAZEploit

Two academic breakthroughs separated by three years (`PrivateDrop` in 2021 and `GAZEploit` in 2024) illustrate a profound systems-security principle: *even when a primary cryptographic or hardware boundary holds 100%, projecting a deterministic derivative of secret state across an adjacent channel reconstructs the secret* [371, 379]. In `AirDrop`, `SHA-256` is preimage-resistant over high-entropy 256-bit keys, yet computing deterministic `SHA-256("+12065550199")` over a $34$-bit domain of valid E.164 telephone numbers turns `SHA-256` into an instant lookup index unless masked by a cryptographic Private Set Intersection (`PSI`) blinding scalar or gated behind `NameDrop` physical contact [371, 389].

> **Key idea.**
> On `visionOS`, `R1` and `RealityKit` enforced a mathematically airtight local boundary: zero third-party processes could read raw eye-tracking coordinates [10, 390]. Yet `GAZEploit` (`2024`) recovered `73%--77%` of typed PINs and passwords remotely without touching an eye-tracking API, simply because `FaceTime` faithfully animated the user's spatial `Persona` eyeballs for remote video participants while the user looked at keys to pinch-type [379]! True isolation requires auditing *every* downstream rendering and side-channel representation of protected sensor state, including virtual avatars and CSS/shader hover timing [379, 390, 393].

## Verification & Forensic Artifacts

On `macOS`, inspect the `awdl0` peer-to-peer Wi-Fi Continuity interface and query `sharingd`'s active `AirDrop` `DiscoverableMode` (`Contacts Only`, `Off`, or `Everyone`) read-only [387]:

```bash
ifconfig awdl0 2>/dev/null | head -n 4
defaults read com.apple.sharingd DiscoverableMode 2>/dev/null || echo "Default (Contacts Only)"
```

Inspect `AuthenticationServices` (`authenticationservicesd` Passkey assertions and `swcd` Associated Domains verification) via Unified Logging [376, 384]:

```bash
log show --last 30m --predicate 'subsystem IN {"com.apple.AuthenticationServices", "com.apple.swc"}' --style compact | tail -n 5
```

Audit `AuthKit` (`akd` `GrandSlam` `SRP-6a` token refreshes) and `Continuity` (`sharingd` `Auto Unlock` `FTM`/UWB ranging verdicts) in Unified Logging [380, 386, 388]:

```bash
log show --last 1h --predicate 'subsystem IN {"com.apple.authkit", "com.apple.sharing"}' --style compact | tail -n 5
```

Check whether hardware `FIDO` USB/NFC security keys (`CryptoTokenKit` / `ctkd` HID enumerations) are visible to `macOS` for Apple Account Security Keys or `WebAuthn` [377, 382]:

```bash
system_profiler SPUSBDataType 2>/dev/null | grep -E -i 'FIDO|YubiKey|Security Key' -A 2 || true
```

Personal `GrandSlam` accounts, `Octagon`-synced `Passkeys`, and `Continuity` meshes assume the individual user owns the hardware outright. When an enterprise deploys 100,000 corporate Macs and iPhones (or supports employee-owned `BYOD` devices) that must survive `DFU` wipes without losing supervision and bind `Microsoft Entra ID` or `Okta` sessions into `SEP` silicon, governance shifts to [Chapter 14](14-ddm-platform-sso.md): `Automated Device Enrollment`, `Account-Driven User Enrollment`, `Declarative Device Management`, and `Platform SSO`.
