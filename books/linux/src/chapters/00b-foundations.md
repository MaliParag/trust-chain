# Foundations

Every security boundary in Linux reduces to a precise interplay among five substrates: CPU privilege rings and hardware memory translation, kernel task credentials managed under Read-Copy-Update (`RCU`), Virtual File System (`VFS`) object resolution paired with `Linux Security Module` (`LSM`) hooks, `TPM 2.0` cryptographic state registers, and asymmetric or Merkle-tree integrity formats. When an architectural review treats these layers informally, subtle violations slip past: a system-call filter inspects a raw user-space pointer that another thread mutates mid-flight, a administrator assumes `UID 0` and Ring 0 are synonymous, or a disk encryption policy encrypts blocks without authenticating them. Establishing the exact hardware, kernel, and cryptographic invariants up front makes every subsequent chapter self-contained and unambiguous.

## Hardware Privilege Rings, Virtualization Extensions, and Confidential Silicon

Modern Linux executes primarily across two processor families, `x86_64` (`AMD64` / `Intel 64`) and `ARM64` (`AArch64`), both of which enforce hierarchical hardware privilege modes in silicon [88, 89]. On `x86_64`, architectural history defines four protection rings (`CPL 0` through `CPL 3` encoded in the low two bits of the `%cs` code-segment selector), of which Linux uses two: Ring 3 (`CPL = 3`) executes unprivileged userspace processes under user-accessible page-table entries (`PTE` bit `U/S = 1`), while Ring 0 (`CPL = 0`) executes the Linux kernel (`vmlinux` and loadable `.ko` modules) with access to supervisor-only pages (`U/S = 0`), control registers (`%cr0`, `%cr3`, `%cr4`), Model-Specific Registers (`WRMSR`/`RDMSR`), and IOMMU tables [88].

Tracing the exact instruction-level Ring 3 to Ring 0 transition inside `arch/x86/entry/entry_64.S` reveals how delicately hardware state is balanced at the kernel boundary [90, 91]. When a 64-bit thread executes `syscall`, the processor saves the next user instruction pointer into `%rcx` and `%rflags` into `%r11`, masks `%rflags` with `IA32_FMASK` (`MSR 0xc0000084`, atomically clearing `EFLAGS.IF` to disable maskable interrupts, `DF` to enforce forward string ops, `TF` to suppress single-step traps, and `AC` so Supervisor Mode Access Prevention engages immediately), loads supervisor segment selectors from `IA32_STAR`, sets `CPL = 0`, and branches to the virtual address held in `IA32_LSTAR` (`MSR_LSTAR`, `0xc0000082`, pointing to `entry_SYSCALL_64`) [88, 90]. Critically, the `syscall` instruction *does not switch `%rsp`*: at the very first instruction of `entry_SYSCALL_64`, `%rsp` still contains an untrusted Ring 3 value! Touching the stack before switching pointers would allow userspace to trick Ring 0 into overwriting arbitrary memory. Therefore, `entry_SYSCALL_64` executes `ENDBR` (satisfying Intel `CET` Indirect Branch Tracking [55]), immediately executes `swapgs` to exchange the user `GS.base` (`IA32_GS_BASE`) with the kernel's per-CPU base (`IA32_KERNEL_GS_BASE`), stashes the untrusted user `%rsp` into per-CPU scratch memory (`PER_CPU_VAR(cpu_tss_rw + TSS_sp2)`), switches `%cr3` to the kernel page table, loads the thread's pinned kernel stack (`cpu_current_top_of_stack`), pushes the five-word `struct pt_regs` hardware frame plus register state, mitigates speculative branch history (`IBRS_ENTER`, `UNTRAIN_RET`, `CLEAR_BRANCH_HISTORY`), and calls `do_syscall_64()` [90, 91]. On return (`syscall_return_via_sysret`), the kernel erases stack residuals (`STACKLEAK_ERASE_NOCLOBBER`), pivots back through the per-CPU trampoline stack to switch `%cr3` to user page tables, executes `swapgs` and `CLEAR_CPU_BUFFERS`, and issues `sysretq` (dropping back to slower `iretq` whenever `pt_regs->rcx` might hold a non-canonical address, avoiding classic Ring 0 `#GP` privilege-escalation errata; modern Intel CPUs introduce Flexible Return and Event Delivery, `FRED`, to unify stack and ring switching in hardware [91, 92]). Even a speculative misprediction over whether `swapgs` already executed on nested interrupt entry created a cross-ring side channel (`CVE-2019-1125`), requiring `lfence` serialization along conditional `swapgs` paths [93].

That `%cr3` switch inside `entry_SYSCALL_64` (`SWITCH_TO_KERNEL_CR3`) did not exist during the first decade of `x86_64` Linux [94, 95]. Historically, every process shared a single page-table hierarchy mapping userspace in the lower canonical half (`0x0000000000000000` to `0x00007fffffffffff`, `U/S = 1`) and the entire kernel text plus all physical RAM (`page_offset_base` direct map) in the upper canonical half (`0xffff800000000000` upward, `U/S = 0`) so syscalls avoided TLB flushes. In January 2018, the disclosure of `Meltdown` (`CVE-2017-5754`) shattered that design [96]: on out-of-order Intel (and select ARM) cores, an unprivileged Ring 3 load targeting a `U/S = 0` kernel virtual address fetched cached secret bytes into transient execution registers and leaked them into a user cache-timing array *before* instruction retirement raised `#PF`. Linux countered with `Page Table Isolation` (`PTI`, derived from the academic `KAISER` design and controlled by `CONFIG_MITIGATION_PAGE_TABLE_ISOLATION=y` in `Documentation/arch/x86/pti.rst`) [94, 95]. Under `PTI`, the kernel allocates an order-1 (8 KiB) Page Global Directory (`PGD`) holding two adjacent 4 KiB roots per `mm_struct`: the *kernel PGD* maps full kernel space (while setting the `NX` bit on top-level user `PGD` entries so any missed `%cr3` switch crashes immediately instead of executing Ring 3 code at `CPL = 0`!), whereas the *user PGD* omits virtually all kernel memory except a minimal 2 MiB-aligned read-only fixmap region (`struct cpu_entry_area`) containing the `entry_SYSCALL_64` trampoline, IDT, GDT, and per-CPU `TSS` [94]. Hardware 12-bit Process Context Identifiers (`PCID` in `%cr3[11:0]` paired with bit 63 `CR3_NOFLUSH` and `INVPCID`) prevent every `SWITCH_TO_KERNEL_CR3` from flushing cached TLB translations, though microarchitectural timing probes against the residual `cpu_entry_area` TLB footprint still defeated `KASLR` in `EntryBleed` (`CVE-2022-4543`) [94, 97]. On `ARM64`, the architecture cleanly splits user and kernel page-table base registers in silicon (`TTBR0_EL1` for `EL0` user addresses vs. `TTBR1_EL1` for `EL1` kernel space), pairing `SVC #0` traps into `VBAR_EL1` with `ARM64` `KPTI` trampolines on Meltdown-affected cores, while `EL2` hosts `KVM` (via `VHE` Virtualization Host Extensions or `nVHE` protected `pKVM`) and `EL3` runs Secure Monitor firmware (`TF-A`) [89, 98].

Hardware virtualization introduces a second orthogonal dimension beneath Ring 0. Under Intel `VT-x` (`VMX`) and AMD `SVM` (`AMD-V`), the host hypervisor (`KVM`) runs in `VMX Root Operation` (or `SVM` host mode), while guest virtual machines execute in `VMX Non-Root Operation` with their own guest Ring 0 and guest Ring 3 [88]. Even though a guest Linux kernel executes at `CPL = 0` inside `VMX Non-Root`, every guest physical address (`GPA`) produced by the guest's `%cr3` page tables must traverse a second hardware-walked translation table controlled exclusively by the host hypervisor: Intel Extended Page Tables (`EPT`) or AMD Nested Page Tables (`NPT`, and `Stage-2` translation tables under `VTTBR_EL2` on `ARM64`) [88, 89]. Consequently, a Ring 0 kernel exploit inside a `KVM` micro-VM (`Firecracker` or `Kata Containers`, analyzed in [Chapter 15](15-gvisor-microvms.md)) remains confined to the host physical RAM frames mapped into that guest's `EPT`/`Stage-2` table unless the attacker additionally compromises the host `KVM` subsystem or user-space Virtual Machine Monitor (`VMM`).

Classical `VT-x`, `SVM`, and `EL2` assume the host hypervisor is trustworthy: because host `VMX Root` controls `EPT`/`NPT` and maps all physical DRAM, a compromised cloud host can read or modify any guest page at will. Confidential Computing extensions invert that trust hierarchy inside the CPU memory controller itself ([Chapter 18](18-confidential-vms-svsm.md)) [3, 4, 85]. On `AMD SEV-SNP` (Secure Encrypted Virtualization-Secure Nested Paging), an on-die AMD Secure Processor (`ASP`/`PSP`) assigns each guest a unique `AES-128-XTS` memory encryption key in hardware and maintains a silicon-enforced Reverse Map Table (`RMP`) indexed by System Physical Address (`SPA`); before any CPU core completes a write or `NPT` walk, hardware verifies that the `SPA` belongs to the active `ASID` at the expected `GPA`, raising a fatal `#PF` fault if the untrusted host hypervisor remaps, aliases, or replays guest memory [3]. Furthermore, `SEV-SNP` partitions a single confidential guest internally into four Virtual Machine Privilege Levels (`VMPL0` most privileged through `VMPL3` least privileged), allowing an open-source Rust paravisor (`COCONUT-SVSM`) to execute in `VMPL0` and expose a measured virtual `TPM 2.0` to a guest Linux kernel isolated in `VMPL1` [3, 11]. Intel `TDX` (Trust Domain Extensions) achieves analogous isolation via a CPU-attested `TDX Module` running in `SEAM` (Secure Arbitration Mode) alongside Multi-Key Total Memory Encryption (`MKTME`) and Trust Domain Memory Regions (`TDMRs`) [4], while `Arm CCA` (Confidential Compute Architecture) introduces a Realm Management Extension (`RME`) with Granule Protection Tables (`GPT`) enforced at `EL3` to isolate dynamically allocated `Realms` from both the Normal-World `EL2` hypervisor and the TrustZone Secure World [85].

## Task Identity, RCU `struct cred`, and Namespace-Scoped UIDs

Inside the Linux kernel, every schedulable thread is represented by a `struct task_struct` (`include/linux/sched.h`) [99]. Rather than scattering security identifiers directly across mutable `task_struct` fields where concurrent readers and writers could race, Linux encapsulates a thread's entire security context inside an immutable, reference-counted `struct cred` (`include/linux/cred.h`) managed via Read-Copy-Update (`RCU`) [99]:

```c
struct task_struct {
    /* ... scheduler and memory descriptors ... */
    const struct cred __rcu *real_cred; /* Objective identity (who may signal/ptrace me) */
    const struct cred __rcu *cred;      /* Effective subjective identity (acting creds) */
    /* ... */
};

struct cred {
    atomic_long_t   usage;
    kuid_t          uid, euid, suid, fsuid;
    kgid_t          gid, egid, sgid, fgid;
    kernel_cap_t    cap_inheritable, cap_permitted, cap_effective, cap_bset, cap_ambient;
    struct key      *session_keyring, *process_keyring, *thread_keyring;
    void            *security;          /* Stacked LSM security blob */
    struct user_namespace *user_ns;     /* Owning user namespace */
    struct rcu_head rcu;
};
```

Distinguishing `real_cred` (objective credentials governing who can act *upon* the task, evaluated via `__task_cred(target)` during `ptrace_may_access()`, cross-process signal delivery, or `/proc/<pid>` inspection) from `cred` (subjective credentials governing what the task itself may access when initiating VFS or network operations via `current_cred()`) prevents confused-deputy privilege leaks whenever the kernel performs work on behalf of another security principal [99, 100]. In `kernel/cred.c`, subsystems such as `OverlayFS` (which must access lower backing layers under the mounter's credentials rather than the calling container user's credentials), `cachefiles`, BSD process accounting, and asynchronous `io_uring` worker threads temporarily swap only the subjective pointer by invoking `old_cred = override_creds(override_cred)` and restoring it immediately afterward via `revert_creds(old_cred)`, leaving `task->real_cred` untouched so an unprivileged caller cannot suddenly evade signals or inspect root-owned `/proc/self` files during the window [99, 100]. Because an active `struct cred` is strictly immutable once published, hot-path permission checks (`current_cred()`, `current_euid()`) dereference `task->cred` locklessly inside a Read-Copy-Update (`RCU`) read-side critical section (`rcu_read_lock()`) with zero atomic bus lock overhead across hundreds of CPU cores [100, 101]. Whenever a task permanently transitions its own identity via `setresuid(2)`, `capset(2)`, `landlock_restrict_self(2)`, or `execve(2)`, the kernel allocates a private mutable copy via `prepare_creds()`, populates the new UIDs, capabilities, and stacked LSM blob, and atomically publishes both `task->cred` and `task->real_cred` via `commit_creds()`, deferring slab reclamation of the retired credential through an RCU grace period (`call_rcu(&old->rcu, put_cred_rcu)`) until every pre-existing reader on every CPU has exited its critical section [99, 100, 101]. That clean Copy-on-Write design also explains why raw `struct cred` overwrites remain a prized post-exploitation target in kernel Use-After-Free (`UAF`) attacks ([Chapter 6](06-kernel-memory-rust.md)): zeroing `uid` through `fsgid` and setting capability masks to `0x1ffffffffffULL` on a dangling `cred` slab slot elevates a task to `root` without injecting executable shellcode [32].

Notice also that `uid` and `euid` inside `struct cred` have type `kuid_t`, not raw integer `uid_t` [22, 99]. `kuid_t` stores the flat global kernel identifier in the initial user namespace (`init_user_ns`). When a process calls `unshare(CLONE_NEWUSER)` ([Chapter 9](09-capabilities-userns.md)), the kernel creates a child `struct user_namespace` (`cred->user_ns`) containing piecewise-linear `uid_map` and `gid_map` extents translating between global `kuid_t` values and namespace-local `uid_t` values [22]. A thread whose global `kuid_t` is `1000` can map itself to `UID 0` inside its child `user_ns` and receive full `CapEff` bits *relative to that `user_ns`*. Crucially, the kernel offers two distinct capability-check functions: `capable(CAP_SYS_ADMIN)` checks privilege against `init_user_ns` (global host privilege), whereas `ns_capable(ns, CAP_NET_ADMIN)` checks whether `cred` holds the capability over the target resource's owning `user_namespace` [22, 62]. Confusing `ns_capable()` with host safety, or allowing `ns_capable()` to gate entry into buggy Ring 0 parsers whose memory allocators are global across the entire machine, drives a huge share of modern Linux local privilege escalations ([Chapter 9](09-capabilities-userns.md)).

## VFS Object Resolution, Discretionary Access Control, and LSM Hook Placement

Every file, socket, pipe, device node, and anonymous memory descriptor on Linux is mediated through the Virtual File System (`VFS`, `fs/`) [102]. Four primary kernel structures define VFS state: `struct super_block` represents a mounted filesystem instance (carrying mount flags such as `SB_RDONLY` and filesystem-wide `SELinux` or `fs-verity` state); `struct inode` represents an individual filesystem metadata object on disk or in RAM (storing ownership `i_uid`/`i_gid`, mode `i_mode`, extended attributes `i_op->get_acl`, `i_security` LSM labels, and optional `fsverity_info`); `struct dentry` caches a single directory-entry name-to-inode link (`d_name` $\to$ `d_inode`, chained via `d_parent` to form directory hierarchies); and `struct file` represents an open file description held in a process's file-descriptor table (`files_struct`), recording open flags (`f_flags`), current offset (`f_pos`), `f_cred` (the `struct cred` captured at `open()` time!), and `f_security` [13, 102].

![Figure: Hardware privilege modes on x86_64/ARM64 and the placement of seccomp-BPF, VFS Discretionary Access Control, and stacked Linux Security Module (LSM) hooks on resolved kernel objects.](diagrams/00b-linux-privilege-rings-lsm.svg)

Why does the exact vertical placement of security checks along the `SYSCALL` $\to$ `VFS` pipeline matter so profoundly? Consider what happens when a multi-threaded userspace process invokes `openat2(dfd, pathname, &how, sizeof(how))` [102, 103]. At the `entry_SYSCALL_64` boundary, `pathname` is merely a `const char __user *` virtual address pointing into writable Ring 3 memory shared by every thread in the caller's address space (`CLONE_VM`). `seccomp-BPF` (`__secure_computing()`) runs at this earliest gate over the system-call number and the six raw 64-bit register values (`arg0..arg5`) [104]. Because `seccomp-BPF` intentionally forbids dereferencing user-space pointers, any external supervisor or naive `kprobe` monitor that reads the string at `pathname` from user memory before the kernel copies it in suffers a classic Time-of-Check to Time-of-Use (`TOCTOU`) race [104, 105]: Thread B in the same process flips `/tmp/benign` to `/etc/shadow` nanoseconds after the monitor reads `pathname` and nanoseconds before VFS calls `getname_flags()` to copy the path into a kernel slab buffer (`struct filename`).

The `Linux Security Module` (`LSM`) architecture (`security/security.c`, originally designed by Wright et al. [13] and generalized to arbitrary module stacking via `lsm_blob_sizes` [47]) defeats user-memory `TOCTOU` by placing mandatory access control (`MAC`) hooks *inside* VFS and subsystem implementations *after* user buffers are copied into kernel slab memory (`getname_flags()`) and resolved to pinned kernel objects [13, 47, 106]. Inside `fs/namei.c`, `do_filp_open()` invokes `path_openat()` and `path_lookupat()` (`link_path_walk()`) using a two-mode concurrency state machine tracked in `struct nameidata` [106, 107]. Lookup begins optimistically in `LOOKUP_RCU` mode (`RCU-walk`): the kernel steps across cached directory entries (`dcache`) under `rcu_read_lock()` without taking a single spinlock or incrementing `dentry` reference counts, validating path consistency at each hop against per-dentry `seqlock` sequence counters (`d_seq`) and the global `mount_lock` sequence counter (`mnt_seq`) [106, 107]. Only when a path component misses in `dcache`, crosses an uncached symlink, or collides with a concurrent `rename()` does `unlazy_walk()` atomically materialize reference counts (`legitimize_links()`) and drop down to traditional lock-and-refcount `REF-walk`, ultimately yielding a pinned `struct path { struct vfsmount *mnt; struct dentry *dentry; }` [106].

Once `path_lookupat()` resolves a `struct path`, modern Linux (`5.12+`) applies a crucial mount-scoped identity transformation before evaluating permissions: *ID-mapped mounts* (`struct mnt_idmap`, documented in `Documentation/filesystems/idmappings.rst` and configured via `mount_setattr(2)` with `MOUNT_ATTR_IDMAP`) [108, 109]. Historically, bind-mounting a host directory or shared container image into two unprivileged containers with disjoint `user_namespace` ranges (`u0:k100000:r65536` vs. `u0:k200000:r65536`) required recursively running `chown -R` across tens of thousands of on-disk inodes. With `struct mnt_idmap`, ownership translation becomes an order-isomorphic function attached to the `vfsmount` rather than the `inode` [108]: raw disk UIDs map first through the filesystem superblock's `s_user_ns` into `inode->i_uid` (`kuid_t`), and `i_uid_into_vfsuid(mnt_idmap(path.mnt), inode)` (`vfsuid_t`) translates that `kuid_t` dynamically through the mount's `mnt_idmap` during `inode_permission(idmap, inode, mask)`, `vfs_getattr()`, and newly created inode ownership assignment [108, 109]. Every mount-sensitive hook in `include/linux/lsm_hook_defs.h` (`inode_permission`, `inode_create`, `inode_setattr`, `inode_setxattr`) now receives `const struct mnt_idmap *idmap` explicitly so POSIX `DAC`, file capabilities (`security.capability`), and LSMs agree identically on effective ownership without mutating backing storage [108, 110].

Inspecting `include/linux/lsm_hook_defs.h` also clarifies the architectural split between *object-based* (`inode_*`) and *path-based* (`#ifdef CONFIG_SECURITY_PATH` `path_*`) LSM hooks [47, 110]. During `do_filp_open()`, after POSIX `DAC` (`generic_permission()`) succeeds, `call_int_hook()` walks the stacked `security_hook_list` (`landlock`, `lockdown`, `yama`, `ipe`, `selinux` or `apparmor`, and `bpf`), succeeding if and only if every registered callback returns `0` [47]. Label-based LSMs (`SELinux`, `Smack`) hook `inode_permission(idmap, inode, mask)`, `inode_unlink(dir, dentry)`, and `file_open(file)` because the security label (`security.selinux` cached in `inode->i_security`) is an intrinsic property of the target object regardless of which hardlink or mount namespace reached it [56, 110]. Conversely, `inode_unlink` and `inode_rename` pass only `struct inode *` and `struct dentry *` without the enclosing `struct vfsmount *`! Pathname and hierarchy LSMs (`AppArmor` [57] and `Landlock` [10]) cannot reconstruct mount-namespace paths (`d_absolute_path()`) or walk mount-crossing parent trees up to a sandbox root from a bare `dentry` alone; they therefore rely on the `CONFIG_SECURITY_PATH` hooks (`path_unlink`, `path_rename`, `path_chmod`, `path_link`, `path_truncate`) invoked with `const struct path *` while the VFS mount context is still live [10, 57, 110].

## TPM 2.0 PCR Algebra and Enhanced Authorization Policies

Cryptographic software checks inside Ring 0 cannot attest their own integrity to an external verifier or protect disk decryption keys against offline firmware tampering unless anchored in discrete or firmware-isolated hardware state. On x86 and ARM64 servers and workstations, that hardware state engine is a Trusted Platform Module conforming to the `TPM 2.0` Library Specification [111, 112]. A `TPM 2.0` exposes at least twenty-four Platform Configuration Registers (`PCR[0]` through `PCR[23]`), organized in banks per hash algorithm (exclusively `SHA-256` or `SHA-384` on modern Linux deployments, as `SHA-1` banks are collision-broken and deprecated) [111, 113]. No host command can ever write an arbitrary value into PCRs `0` through `15`; after initializing to all-zeroes ($0^{256}$) at platform reset, the sole mutation primitive is `TPM2_PCR_Extend`, which computes an irreversible cryptographic chain over each measurement digest $d \in \{0,1\}^{256}$:

$$\text{PCR}_{\text{new}}[i] \leftarrow \operatorname{SHA-256}\!\left(\text{PCR}_{\text{old}}[i] \;\parallel\; d\right)$$

Because $\operatorname{SHA-256}$ is preimage- and collision-resistant, no sequence of subsequent `TPM2_PCR_Extend` calls from a compromised later stage can roll $\text{PCR}[i]$ back to an earlier value or forge the final digest produced by a clean boot sequence $(d_1, d_2, \dots, d_k)$ [111]. Crucially, however, not all twenty-four PCRs share the same hardware reset and locality rules in the TCG Architecture and PC Client Platform Firmware Profile specifications [111, 112, 114]! Registers `PCR[0]` through `PCR[15]` form the Static Root of Trust for Measurement (`SRTM`) bank: they initialize to $0^{256}$ exclusively upon `TPM2_Startup(TPM_SU_CLEAR)` at full host hardware reset and *cannot* be reset by any software running in UEFI runtime or OS Ring 0 (Locality 0 through 3). Within that static bank, the UAPI Group *Linux TPM PCR Registry* [113] assigns strict non-overlapping semantics: `PCR[0]` records core UEFI `SRTM`/`POST`/`DXE` firmware code, `PCR[1]` records host firmware configuration, `PCR[2]` and `PCR[3]` record plug-in PCIe Option ROM code and configuration, `PCR[4]` records UEFI Boot Manager PE executables (`shim.efi`, `grubx64.efi`, and `UKI` binaries), `PCR[5]` records GPT partition headers and `ExitBootServices()` actions, `PCR[7]` records UEFI Secure Boot policy (`PK`, `KEK`, `db`, `dbx`, `SbatLevel`) plus the exact X.509 authority entry validating each stage, `PCR[9]` measures Linux kernel `LOAD_FILE2` `initrd` images, `PCR[10]` accumulates `IMA` runtime file measurements ([Chapter 4](04-ima-ipe-keylime.md)), `PCR[11]` measures `Unified Kernel Image` sections and monotonic boot phases ([Chapter 2](02-uki-systemd-pcrlock.md)), `PCR[12]` records `UKI` PE addons and credential overrides, `PCR[13]` records `systemd-sysext` Discoverable Disk Images, `PCR[14]` records `shim` MOK state (`MokList`, `MokListX`, `MokSBState`), and `PCR[15]` measures `/etc/machine-id` and mounted root/`/var` filesystem identities [28, 113, 115, 116].

By contrast, `PCR[16]` through `PCR[23]` carry resettable hardware attributes that would catastrophically undermine disk encryption if misunderstood [112, 114]. `PCR[16]` is designated as the *Debug PCR*: any process with TPM access at Locality 0 can issue `TPM2_PCR_Reset(PCR[16])` at runtime to zero `PCR[16]` back to $0^{256}$ and replay arbitrary `TPM2_PCR_Extend` sequences without rebooting, making `PCR[16]` strictly forbidden in production `LUKS2` or attestation policies [112, 114]. Registers `PCR[17]` through `PCR[22]` support Dynamic Root of Trust for Measurement (`DRTM`, such as Intel `TXT` `GETSEC[SENTER]` or AMD `SKINIT` late launch): they initialize to all-ones (`0xff..ff`) at power-on and can only be reset to $0^{256}$ by CPU microcode asserting hardware Locality 4 during a measured `DRTM` launch, with `PCR[17..20]` restricted to Locality $\ge 2$ extends [112, 114]. Finally, `PCR[23]` serves as an application-specific resettable register (`Locality 0..3` resettable) reserved for transient userspace testing [113, 114].

Sealing a secret (such as a `LUKS2` volume key or `systemd-creds` master key) directly to raw `PCR[4]` and `PCR[7]` digests via `TPM2_PolicyPCR` creates an operational trap: every routine distribution kernel or firmware capsule update alters `PCR[4]` (or `PCR[0]`/`PCR[7]`), locking the machine out of its root disk on reboot. `TPM 2.0` *Enhanced Authorization* (`EA`) solves that brittleness through policy indirection [29, 111, 117]. Every sealed TPM object stores a single 32-byte `authPolicy` digest computed inside a trial session. When a policy incorporates `TPM2_PolicyAuthorize(approvedPolicy, policyRef, keySign, checkTicket)`, the object's immutable `authPolicy` pins only the *public key* $PK_{\text{vendor}}$ (`keySign`, embedded in the `UKI` `.pcrpkey` section), not a static PCR hash:

$$\text{authPolicy} = \operatorname{SHA-256}\!\left(\text{authPolicy}_0 \;\parallel\; \texttt{TPM\_CC\_PolicyAuthorize} \;\parallel\; \operatorname{Name}(PK_{\text{vendor}}) \;\parallel\; \text{policyRef}\right)$$

Whenever a distribution builds a new kernel `UKI`, its build service computes the new expected `PCR[11]` value, constructs a trial policy digest $P_{\text{new}}$, and signs $aHash = \operatorname{SHA-256}(P_{\text{new}} \parallel \text{policyRef})$ with $SK_{\text{vendor}}$ into the `.pcrsig` PE section [117]. At boot, `TPM2_VerifySignature` produces an internal `TPMT_TK_VERIFIED` ticket proving $SK_{\text{vendor}}$ authorized $P_{\text{new}}$, allowing `TPM2_PolicyAuthorize` to satisfy the sealed `LUKS2` keyslot seamlessly across kernel upgrades while combining via `TPM2_PolicyOR` and NV-index pinning (`systemd-pcrlock`) with local firmware measurements ([Chapter 2](02-uki-systemd-pcrlock.md)) [29, 117].

## Cryptographic Integrity Formats: PE Authenticode, PKCS#7, and Merkle Trees

Linux deliberately employs three distinct cryptographic verification formats matched to the execution semantics of early firmware, discrete kernel artifacts, and demand-paged block or file storage:

First, all UEFI executables (`shimx64.efi`, `grubx64.efi`, `systemd-bootx64.efi`, and `UKI` `.efi` bundles) use the Microsoft `PE/COFF` *Authenticode* format (`WIN_CERTIFICATE_TYPE_PKCS_SIGNED_DATA`) because UEFI `LoadImage()` implements the PE specification natively [1, 8, 118]. Computing a PE Authenticode digest hashes the entire image cleanly while skipping the mutable PE `CheckSum`, the Data Directory Certificate Table pointer, and the trailing PKCS#7 signature block itself [118]. Second, post-boot kernel artifacts, including `.ko` loadable kernel modules (`~Module signature appended~\n` magic trailer), `fs-verity` root digests, `dm-verity` root-hash blobs, and `IPE` policy updates, use detached or appended Cryptographic Message Syntax (`CMS` / `PKCS#7`, RFC 5652) signatures verified in Ring 0 by `verify_pkcs7_signature()` against the kernel's `.builtin_trusted_keys`, `.machine`, and `.secondary_trusted_keys` X.509 keyrings ([Chapter 5](05-kernel-lockdown-modules.md)) [54, 119].

Third, signing multi-gigabyte `/usr` partitions or large container binaries with a flat linear signature is incompatible with demand paging: reading and hashing a 4 GiB image before executing its first 4 KiB page would stall boot for seconds and leave swapped or uncached pages vulnerable to mid-execution disk modification (`TOCTOU`). Both `dm-verity` (block-device level) and `fs-verity` (inode level) solve demand-paged verification with a balanced $b$-ary *Merkle hash tree* ([Chapter 3](03-luks2-verity.md)) [20, 50]. Partitioning an image of $N$ data blocks of size $B = 4096$ bytes with `SHA-256` digests ($|h| = 32$ bytes) yields a tree branching factor of $b = B / |h| = 4096 / 32 = 128$ hashes per internal tree node and tree height:

$$H = \left\lceil \log_{128} N \right\rceil$$

For a $4\text{ GiB}$ `/usr` filesystem ($N = 2^{20} = 1{,}048{,}576$ pages), $H = \lceil \log_{128}(2^{20}) \rceil = 3$ levels, adding less than $0.8\%$ storage overhead ($\approx 33\text{ MiB}$) while enabling the kernel page-fault handler to authenticate any individual $4\text{ KiB}$ page read on demand with at most $3$ SHA-256 block hashes (quickly cached in RAM once verified) anchored to a single 32-byte `root_hash` pinned inside the Authenticode-signed `UKI` [8, 20].

## Mutable Distros, Immutable Appliances, and Hostile Cloud Threat Models

A recurring source of confusion in Linux security engineering is evaluating a mechanism without naming the deployment model and adversary against which it operates. Throughout this book, we evaluate every link against three concrete Linux deployment postures and four adversary tiers.

![Figure: Architectural contrast between a mutable package-managed Linux distribution (stopping verification at vmlinuz) and an image-based immutable verified Linux OS (carrying cryptographic verification through UKI, dm-verity, IPE, and SUID-free userspace).](diagrams/00b-mutable-vs-immutable-boot.svg)

In a *mutable general-purpose distribution* (classic Debian, Ubuntu Server, or RHEL installations), package managers (`apt`, `dnf`, `zypper`) unpack archives directly onto a read-write root filesystem, regenerate `initramfs` locally on `/boot`, maintain human-edited `/etc` files, and expose interactive shells alongside `SUID` utilities; such hosts prioritize administrative flexibility at the cost of persistent post-boot drift and an unverified `initramfs` seam unless explicitly hardened with `UKI` and `systemd-pcrlock` [2, 29]. In an *immutable image-based operating system*, two complementary composition patterns close that mutability gap: block-image appliances (`Flatcar`, `Talos Linux`, `Bottlerocket`) ship dual A/B read-only `/usr` partitions verified at the block layer by `dm-verity` and extended dynamically via PKCS#7-signed `systemd-sysext` Discoverable Disk Images (`OverlayFS` over verified `EROFS`/`SquashFS` mounts) [30, 45], whereas content-addressed transactional systems (`Fedora CoreOS`, `RHEL Image Mode`, `OSTree` [120], and OCI-native `bootc` [121]) store deduplicated objects in `/ostree/repo/objects` and mount versioned `composefs` (`EROFS` + `fs-verity`) root trees while eliminating `SUID` binaries (`Talos` omits `/bin/sh` and `sshd` entirely in favor of mutual-TLS gRPC APIs) [45, 46, 120, 121]. In a *multi-tenant cloud, Kubernetes, or AI sandbox host*, the machine executes untrusted code supplied directly by external tenants or synthesized dynamically by Large Language Models exposed to untrusted web/repository inputs (`Indirect Prompt Injection`), turning every reachable host syscall, unprivileged `user_namespace` surface, container runtime file descriptor, instance metadata endpoint (`169.254.169.254`), and ambient environment variable into an active exploitation boundary [16, 81, 82]. Finally, under a *confidential cloud threat model*, even the physical server operator, host `KVM` hypervisor, and Kubernetes worker-node `kubelet` sit outside the Trusted Computing Base, requiring hardware memory encryption (`SEV-SNP`, `TDX`, `Arm CCA`), guest input hardening against malicious hypervisor `#VC`/`#VE` traps, and enclave-side secret release (`COCONUT-SVSM` and `Confidential Containers`) [3, 11, 41, 48]. With these primitives, data structures, and threat models fixed, [Chapter 1](01-uefi-shim-sbat.md) begins at processor reset inside UEFI firmware.
