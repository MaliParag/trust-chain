# Confidential VMs and Open Paravisors: SEV-SNP, TDX, and COCONUT-SVSM

## Overview

* **Link in the Chain:** Inverts the cloud trust model of [Chapter 14](14-containers-escapes.md) through [Chapter 17](17-ai-agent-sandboxes.md): removes the cloud provider's host Linux kernel (`KVM`), `QEMU` or `Cloud Hypervisor` VMM, PCIe root complex, and physical DDR5 memory bus from the guest Linux VM's Trusted Computing Base using CPU memory encryption, hardware page-ownership tables, and an intra-enclave Rust paravisor (`COCONUT-SVSM`).
* **Core Security Invariant:** Hardware memory controllers encrypt guest DRAM under per-VM keys and enforce 1-to-1 guest-to-physical page ownership (`AMD SEV-SNP` `RMP`, `Intel TDX` `SEAM`/`PAMT`/`S-EPT`, `Arm CCA` `GPT`) so host hypervisor reads return ciphertext and page remaps or replays fault immediately; inside the enclave, `COCONUT-SVSM` runs at `VMPL0` to furnish a hardware-measured `libtpms` `vTPM`, while `arch/x86/coco` filters untrusted `#VC`/`#VE` traps, interrupts, `CPUID`/`MSR` values, and `SWIOTLB` bounce buffers.
* **Deployment Profile Matrix:** Standard cloud VMs trust host `KVM` unconditionally; regulated financial, sovereign-cloud, and frontier AI workloads deploy `AMD SEV-SNP` (`EPYC Milan/Genoa/Turin`), `Intel TDX` (`4th/5th/6th Gen Xeon`), or `Arm CCA` Confidential VMs booting measured `UKI` + `dm-verity` images paired with `COCONUT-SVSM` (or `OpenHCL`) and `NVIDIA H100`/`B200` Confidential GPUs over `DMTF SPDM`.
* **Trusted Computing Base (TCB):** CPU silicon and signed microcode/firmware (`AMD ASP` + `VCEK`, `Intel TDX SEAM Module` + `SGX DCAP` `PCK`, `Arm EL3` + `RMM`), `COCONUT-SVSM` (`VMPL0` `#![no_std]` Rust paravisor + `vTPM`), measured `OVMF` + `UKI` guest image, and confidential `NVIDIA` GPU silicon/firmware when attached.
* **Integration Seam & Handoff:** Establishes an encrypted, hardware-attested Linux VM with an enclave-resident `vTPM` (`PCR[11]`) atop an untrusted cloud host; hands off enclave-per-pod Kubernetes orchestration, `agent-policy.rego` enforcement, and remote key release (`Confidential Containers` + `Trustee`) to [Chapter 19](19-confidential-containers.md).

## Problem Statement & Threat Model

Every Linux security mechanism analyzed from [Chapter 1](01-uefi-shim-sbat.md) through [Chapter 17](17-ai-agent-sandboxes.md) relied on an implicit hardware custody axiom: *whoever controls the physical server motherboard and the host `VMX Root` or `SVM` hypervisor is trusted*. On a multi-tenant public cloud, that axiom grants complete plaintext authority over guest workloads to the cloud infrastructure fabric [3, 511]. A compromised host `KVM` kernel, a subverted `QEMU` or `Cloud Hypervisor` process, a malicious data-center technician attaching a logic analyzer, or a court-compelled operator can read every byte of guest `LUKS2` volume master keys, TLS private keys, and proprietary AI model weights via `/dev/mem` or `virsh dump`, patch guest Ring 0 `.text` pages in place via Extended or Nested Page Tables (`EPT`/`NPT`), or read `PCR`-unsealed secrets directly out of a host-resident `swtpm` virtual TPM process!

Early process-scoped enclaves such as `Intel SGX` (2015) proved that an inline CPU memory-encryption engine could exclude the host OS from a user-mode Enclave Page Cache, yet `SGX` forced applications to split code manually across narrow `ECALL`/`OCALL` boundaries without `fork()`, `execve()`, or standard Linux syscalls. Expanding the Trusted Execution Environment (`TEE`) boundary to encompass an entire unmodified Linux Virtual Machine, pioneered by AMD Secure Encrypted Virtualization (`SEV` in 2016 and `SEV-ES` encrypted register state in 2017 [3]), preserved full POSIX compatibility while immediately exposing three profound cryptographic and systems-engineering lessons [512, 513, 514]:

First, *encrypting guest DRAM without hardware page-mapping integrity is broken*. Under first-generation `SEV` and `SEV-ES`, each VM received an `AES-128` memory key tied to its Address Space Identifier (`ASID`), yet the untrusted host `KVM` hypervisor still controlled Nested Page Tables (`NPT`) mapping Guest Physical Addresses (`GPA`) to System Physical Addresses (`SPA`). In 2018, `SEVered` [512] demonstrated that a malicious hypervisor could simply remap the `NPT` entries backing a guest's `virtio-net` transmit ring onto encrypted physical pages holding secret keys; when the guest transmitted an ordinary network packet, the CPU memory controller dutifully decrypted the secret ciphertext under the guest's `ASID` key and streamed the plaintext out to the attacker! Two years later, `SEVurity` [513] exploited the lack of cryptographic integrity tags on `AES-128-XEX` tweaks to compute controlled XOR bit-flips across remapped ciphertexts, synthesizing arbitrary Ring 0 execution gadgets inside `SEV-ES` guests, while `Cipherleaks` (`CVE-2021-26333` [514]) watched deterministic ciphertext block updates across `VMEXIT` page faults to recover OpenSSL `ECDSA` signing keys!

Second, *host-emulated `vTPM` and UEFI storage collapse under a hostile hypervisor*. Standard cloud Linux guests rely on `systemd-stub` `PCR[11]` measurements and `systemd-pcrlock` ([Chapter 2](02-uki-systemd-pcrlock.md)) to unseal `LUKS2` keys; if the `vTPM` runs as `swtpm` in host user space, the untrusted hypervisor owns every unsealed key. Confidential Linux therefore required an open-source, memory-safe paravisor running *inside* the encrypted VM boundary at a higher hardware privilege ring than the guest Linux kernel itself (`COCONUT-SVSM` [11, 515]).

Third, *thirty years of Linux kernel architecture assumed CPU exceptions, interrupts, `CPUID` leaves, `ACPI` tables, and `PCI` buses are honest* [48, 516, 517, 518]. Under a Byzantine host hypervisor that is trusted *solely* for liveness (scheduling vCPUs and transporting ciphertext I/O; denial of service remains unavoidable), every unvalidated hardware register read, synthetic `#VC`/`#VE` trap (`WeSee` `CVE-2024-25742` [48]), injected software interrupt (`Heckler` [517]), cache invalidation (`CacheWarp` [519]), or shared `SWIOTLB` bounce-buffer length becomes a direct Ring 0 attack vector into the confidential guest!

## Kernel & Userspace Mechanics

### Silicon Isolation Roots: `AMD SEV-SNP`, `Intel TDX`, and `Arm CCA`

Generation-2 Confidential VM architectures across x86-64 and Arm64 close the `SEVered`/`SEVurity` gap by coupling per-VM inline memory encryption with silicon-enforced 1-to-1 physical-page ownership tables and cryptographic launch attestation [3, 511, 520, 521]:

| Architectural Property | `AMD SEV-SNP` (`EPYC Milan/Genoa/Turin`) | `Intel TDX 1.5` (`4th-6th Gen Xeon`) | `Arm CCA` (`Armv9-A RME`) |
|---|---|---|---|
| Inline Memory Cipher | Per-`ASID` `AES-128-XEX`/`XTS`; guest PTE `C-bit` (bit `51`/`47`) marks Private (`1`) vs. Shared (`0`) [3, 522] | `MKTME` per-TD `AES-XTS-128/256` + 28-bit SHA-3 MAC in ECC bits; GPA `Shared` bit marks I/O [511] | Memory Encryption Contexts (`MEC`) per `Realm` physical address space [521] |
| Silicon Arbiter & Root | On-die ARM `AMD Secure Processor` (`ASP`) + CPU microcode [520] | CPU-measured `TDX Module` in Secure Arbitration Mode (`SEAM` / `SEAMRR`) [511] | `EL3` Root firmware + measured `Realm Management Monitor` (`RMM` at `R-EL2`) [521] |
| Page-Ownership Table | Reverse Map Table (`RMP`) indexed by 4 KiB `SPA`; mismatches fault with `#PF(RMP)` [522] | Physical-Address-Metadata Table (`PAMT`) + private Secure EPT (`S-EPT`) inside `SEAM` [511] | Granule Protection Tables (`GPT`) walked by MMU hardware at `EL3` [521] |
| Guest Page Acceptance | `PVALIDATE` instruction sets `RMP.Validated = 1`; replay clears `EFLAGS.CF` [522] | `TDCALL[TDG.MEM.PAGE.ACCEPT]` validates `S-EPT` pending entries [511] | `RSI_IPA_STATE_SET` transitions `RIPAS_EMPTY` to `RIPAS_RAM` [521] |
| Intra-Enclave Rings | 4 Virtual Machine Privilege Levels (`VMPL0` highest to `VMPL3` lowest) via `RMPADJUST` [515, 522] | `TD Partitioning`: `L1` TD paravisor managing nested `L2` guest TDs [523] | `Planes` (`Plane 0` paravisor + `Plane 1..N` guest planes) in `RMM` [521] |
| Measurement & Quote | 384-bit `LAUNCH_DIGEST` signed via `VMPCK0` (`SNP_GET_REPORT`) under `VCEK` (`ECDSA-P384`) [520, 524] | Static `MRTD` + 4 extendable `RTMR[0..3]` registers quoted by `SGX DCAP` Quoting Enclave [511, 525] | `RIM` (Initial) + 4 extendable `REM[0..3]` registers in `CCA` Platform/Realm Token [521] |

Trace the exact hardware invariants on `AMD SEV-SNP` (`Publication #56860` and `#24593` [520, 522]). At boot, a contiguous region of physical DRAM is reserved for the Reverse Map Table (`RMP`), containing one 16-byte entry per 4 KiB System Physical Address (`SPA`). Every `RMP[SPA]` entry tracks `(Assigned, ASID, GPA, PageSize, Immutable, Validated, VMPL_Permissions[0..3])`. Whenever a guest vCPU accesses a private GPA (`C-bit == 1`), the CPU walks the host-managed `NPT` ($\text{GPA}_{\text{req}} \to \text{SPA}$) and immediately enforces the silicon `RMP` check in hardware before touching the cache line:

$$\text{RMP}[\text{SPA}].\text{Assigned} = 1 \;\land\; \text{RMP}[\text{SPA}].\text{ASID} = \text{ASID}_{\text{cur}} \;\land\; \text{RMP}[\text{SPA}].\text{GPA} = \text{GPA}_{\text{req}} \;\land\; \text{RMP}[\text{SPA}].\text{Validated} = 1$$

If a malicious `KVM` hypervisor aliases two GPAs onto one SPA, maps a page belonging to another VM, or swaps ciphertext blocks across addresses, `RMP[SPA].GPA != GPA_req` fires an immediate `#PF` (`PFERR_RMP_BIT`) nested page fault back to the host before a single instruction retires [3, 522]! What if the host hypervisor unmaps a validated guest page via `RMPUPDATE` (`Validated = 0`), substitutes older captured ciphertext, and hopes the guest re-accepts it? Only the guest itself can set `Validated = 1` via the privileged `PVALIDATE` instruction; if `PVALIDATE` observes that `Validated` was already toggled or fails the expected transition, hardware clears the `CF` carry flag (`EFLAGS.CF = 0`), causing the Linux guest kernel to terminate immediately (`sev_es_terminate()`) rather than accepting replayed memory [516, 522]! For remote attestation, the `ASP` provisions four 256-bit symmetric Virtual Machine Platform Communication Keys (`VMPCK0..3`, one per `VMPL`) inside encrypted guest state; the guest encrypts an `SNP_GUEST_REQUEST` (`SNP_GET_REPORT`) under `AES-256-GCM` with `VMPCK0` (so the host `KVM` transporting the request buffer sees only authenticated ciphertext and monotonic sequence numbers!), and the `ASP` signs the `SNP_ATTESTATION_REPORT` using its chip-unique `VCEK` (*Versioned Chip Endorsement Key* [524]), an `ECDSA-P384` key mathematically derived inside silicon fuses from both the processor's hardware ID *and* the exact microcode, `ASP` bootloader, TEE, and `SNP` firmware Security Patch Levels (`TCB_VERSION`) [520, 524]!

On `Intel TDX` (`Document 348549` [511]), rather than placing table logic inside an off-core ARM processor, Intel executes an Intel-signed `TDX Module` inside x86 `SEAM` (*Secure Arbitration Mode*, isolated in `SEAMRR` RAM), entered from host `KVM` via `SEAMCALL` (`TDH.*` leaf functions) and from the guest Trust Domain via `TDCALL` (`TDG.*` leaf functions). Guest memory is encrypted under `MKTME` per-keyID `AES-XTS` engines augmented with 28-bit `SHA-3` cryptographic integrity MACs stored in ECC bits so physical memory modification triggers uncorrectable MAC exceptions. Page ownership is enforced by `PAMT` metadata plus a private Secure EPT (`S-EPT`) living entirely inside `SEAM` RAM where host `KVM` cannot write page-table entries directly; `KVM` asks the `TDX Module` to augment a page (`TDH.MEM.PAGE.AUG`), and Linux accepts it via `TDCALL[TDG.MEM.PAGE.ACCEPT]` [511, 516]. Notably, `Intel TDX` builds four runtime extendable 384-bit measurement registers (`RTMR[0..3]`, extended via `TDG.MR.EXTEND` using `SHA-384` hash chaining identical to `TPM 2.0` PCRs!) right into the CPU `TDCS` structure alongside the static launch digest `MRTD`, quoted via `TDCALL[TDG.MR.REPORT]` and signed over `AF_VSOCK` by an `Intel SGX DCAP` TD Quoting Enclave (`PCK` certificate chain) [511, 525].

### Open-Source `COCONUT-SVSM` (Rust `VMPL0` Paravisor) and Confidential `NVIDIA` GPUs

Notice an immediate asymmetry on `AMD SEV-SNP` (and multi-OS cloud guests expecting standard `/dev/tpmrm0` and persistent UEFI Secure Boot variables): `SEV-SNP` silicon provides a single static launch hash (`LAUNCH_DIGEST`) without built-in runtime `PCR` registers, and placing `swtpm` on the host hypervisor exposes every unsealed secret! AMD's `SVSM` specification (`Publication #58019` [515]) and the open-source Linux community project `COCONUT-SVSM` (`coconut-svsm/svsm`, developed in `#![no_std]` Rust by SUSE, AMD, Red Hat, IBM, and Microsoft alongside Microsoft's `OpenHCL` [11, 526, 527]) solve this cleanly inside `VMPL0`:

![Figure: Confidential Linux VM architecture: COCONUT-SVSM running inside AMD SEV-SNP VMPL0 (isolated from the VMPL1 Linux guest via RMP permissions) provides an enclave-resident measured vTPM, while untrusted host KVM sees only ciphertext and explicit SWIOTLB bounce buffers.](diagrams/18-sev-snp-tdx-coconut-svsm.svg)

Examine the exact privilege hierarchy and `SVSM` Calling Area (`CAA`) protocol (`#58019` [515, 526]):

![Figure: Intra-enclave privilege separation in COCONUT-SVSM: RMPADJUST locks VMPL0 memory away from the VMPL1 Linux kernel, routing page validation (SVSM_CORE_PVALIDATE) and measured libtpms vTPM unsealing (SVSM_VTPM_CMD) across the SVSM Calling Area without exposing keys to host KVM.](diagrams/18-extra-coconut-svsm-vmpl0-vtpm.svg)

At VM creation (`SNP_LAUNCH_UPDATE` + `SNP_LAUNCH_FINISH`), the `ASP` measures the initial memory image of `COCONUT-SVSM` (`stage2` + `svsm` kernel) and guest `OVMF` firmware into the immutable 384-bit `LAUNCH_DIGEST` [11, 520]. Booting first at `VMPL0` (the highest guest privilege ring), `COCONUT-SVSM` allocates its own private encrypted pages, initializes an integrated `TPM 2.0` emulator (`libtpms` [528], migrating toward pure Rust `tpm2` modules) plus an authenticated UEFI variable store (`SVSM_UEFI_VARS`), and executes `RMPADJUST` to strip Read, Write, and Execute permissions for `VMPL1`, `VMPL2`, and `VMPL3` across every `VMPL0` page [11, 515, 522]! Only then does `COCONUT-SVSM` prepare a `VMPL1` Virtual Machine Save Area (`VMSA`) and ask the hypervisor (`SVM_VMGEXIT_AP_CREATE` / `RUN_VMPL`) to enter `OVMF` and the signed Linux `UKI` at `VMPL1` (`Intel TDX 1.5` `TD Partitioning` achieves the exact same isolation by running the paravisor in `L1 TD` and the Linux guest in `L2 TD` [523]).

How does the `VMPL1` Linux kernel (`/dev/tpm_svsm` / `drivers/char/tpm/tpm_svsm.c`) talk to `COCONUT-SVSM` at `VMPL0`? Through a 4 KiB private encrypted page per vCPU called the `SVSM` Calling Area (`CAA`, still marked `C-bit = 1` so the host hypervisor *cannot read or tamper with `SVSM` RPC payloads!* [515]):
`VMPL1` writes `1` to `CAA->call_pending`, loads the 32-bit protocol ID in upper `%eax` (`0` = Core protocol, `2` = `vTPM` protocol, `3` = Attestation protocol) and call ID in lower `%eax` (`SVSM_CORE_PVALIDATE` or `SVSM_VTPM_CMD`), and executes `VMGEXIT` (`SVM_VMGEXIT_SVSM`). The host `KVM` sees only an opaque `RUN_VMPL(0)` scheduling request, switches execution to `VMPL0`, and `COCONUT-SVSM` processes the TPM command inside `VMPL0` RAM before returning to `VMPL1` [11, 515]! Two huge security invariants follow immediately: first, because `PVALIDATE` is an instruction executable *only* at `VMPL0`, a compromised `VMPL1` guest kernel must ask `COCONUT-SVSM` (`SVSM_CORE_PVALIDATE`) to accept memory and can *never* unvalidate or alias `VMPL0` pages [515]; second, when `systemd-stub` extends `PCR[11]` and `systemd-cryptsetup` unseals a `LUKS2` volume key ([Chapter 2](02-uki-systemd-pcrlock.md) and [Chapter 3](03-luks2-verity.md)), the `TPM 2.0` primary seed, NV indices, and `PCR` banks live inside `VMPL0` memory that remains unreadable even if an attacker later exploits a Ring 0 vulnerability inside the `VMPL1` guest Linux kernel [11, 526]! (To unlock persistent `vTPM` state across reboots, `COCONUT-SVSM` runs its two-phase Negotiation and Attestation protocol over a host proxy using `VMPCK0` quotes to unwrap storage keys directly into `VMPL0` [526].)

When AI training or inference workloads attach `NVIDIA Hopper H100` or `Blackwell B200` accelerators (`CC-On` / Multi-GPU `PPCIE` mode [86]), raw PCIe DMA cannot read `C-bit = 1` CPU DRAM, and the host PCIe root complex is untrusted. Inside the Confidential Linux guest, the verifier establishes an end-to-end `DMTF SPDM 1.2/1.3` (`DSP0274` [529]) cryptographic session directly with the GPU's hardware Root of Trust, verifying the GPU's silicon-fused `ECDSA-P384` certificate chain and signed VBIOS/firmware measurements (confirming debug/JTAG ports and unencrypted BAR apertures are locked out), derives ephemeral `AES-GCM-256` keys inside the enclave, encrypts tensors inside CPU `SWIOTLB` bounce buffers (`C = 0` shared pages holding only authenticated `AES-GCM` ciphertext and 96-bit nonces!), and lets the GPU copy engine verify GCM tags and decrypt directly into isolated HBM3e memory [86, 529, 530]!

### The Untrusted-Hypervisor Trap Surface: `#VC` / `#VE`, `WeSee`, `Heckler`, `CacheWarp`, and Device Filtering

Why did confidential Linux kernels suffer critical Ring 0 compromises in 2023–2024 despite mathematically intact `RMP` and `S-EPT` silicon? Because encrypted register state (`VMSA` / `TDVPS`) changed how x86 handles non-automatic VM exits (`#VC` vector `29` in `GHCB` `#56421` [531] on `SEV-SNP`, and `#VE` vector `20` [511] on `TDX`):

![Figure: Defending a Confidential Linux guest against a malicious host hypervisor: mitigating unsolicited #VC/#VE exception injection (WeSee CVE-2024-25742), forged CPUID/MSR values, and rogue PCI/USB device fuzzing via arch/x86/coco hardening.](diagrams/18-untrusted-vmm-vc-ve-surface.svg)

In a standard VM, executing `CPUID`, `RDMSR`, `IOIO` (`in`/`out`), or unmapped `MMIO` traps straight to `KVM`, which reads guest `%rax..%r15` directly. Because `SEV-SNP` and `TDX` encrypt guest registers, hardware instead raises a `#VC` or `#VE` exception *into the guest Linux kernel*: Linux's `#VC`/`#VE` handler (`arch/x86/coco/` [516]) inspects the exit reason, copies *only* the needed register operands into an unencrypted shared `GHCB` page (or `TDCALL` operands), triggers `VMGEXIT`/`TDVMCALL` to the untrusted VMM, and copies the response back into guest registers [511, 531].

Three landmark academic attacks proved how lethal that guest-hypervisor trap seam is if left unhardened:
First, in `WeSee` (`CVE-2024-25742`, IEEE S&P 2024 [48]), ETH Zurich researchers showed that a malicious `KVM` hypervisor could write vector `29` (`#VC`) into `VMCB.EVENTINJ` at *any* arbitrary instruction while the guest executed sensitive Ring 0 code! When Linux's `#VC` handler woke up with exit code `SVM_EXIT_NPF` (emulated MMIO) while `%rip` pointed to an ordinary private-memory `mov (%rdi), %rax` instruction inside `kTLS` or the scheduler, the handler dutifully decoded the `mov` instruction and either copied private kernel register secrets out to the unencrypted `GHCB` (breaking confidentiality!) or overwrote guest kernel pointers with attacker-controlled hypervisor bytes (achieving arbitrary guest Ring 0 root shells!) [48].
Second, in `Heckler` (`CVE-2024-25743` on `SEV-SNP` and `CVE-2024-25744` on `Intel TDX`, USENIX Security 2024 [517]), the same team injected malicious *non-timer software interrupts* (such as vector `0x80`, Linux's legacy 32-bit `int 0x80` syscall gate when `CONFIG_IA32_EMULATION` was enabled, or spurious signal vectors!) into a running vCPU right after an authentication helper set `%rax`, corrupting guest register state across both `SEV-SNP` and `TDX` to bypass `OpenSSH` and `sudo` authentication!
Third, in `CacheWarp` (`CVE-2023-20592` / `AMD-SB-3005`, USENIX Security 2024 [519]), CISPA researchers triggered the x86 `INVD` (Invalidate Internal Caches *without* writeback) instruction from the hypervisor on unpatched Milan/Rome microcode, selectively dropping dirty guest L1/L2 cache lines before they wrote back to encrypted DRAM so stack stores (`authenticated = 0` or RSA-CRT fault checks) silently reverted to stale DRAM values!

Modern Linux (`arch/x86/coco/` [516]) and `COCONUT-SVSM` [526] close these hypervisor-injection seams across four reinforcing defenses:
First, *Strict `#VC` / `#VE` Opcode and PTE Validation*: Linux's `#VC` and `#VE` handlers decode the instruction at faulting `%rip` and reject the exception immediately (`sev_es_terminate`) unless `%rip` points to an explicit valid exit opcode (`cpuid`, `rdmsr`, `wrmsr`, `in`/`out`, `vmmcall`) or, for `MMIO`, a virtual address whose guest page-table entry *explicitly has `C-bit == 0` (`_PAGE_ENC` cleared)*, neutralizing `WeSee` MMIO spoofing on private kernel pointers [48, 516] (while `Intel TDX` additionally sets `CONFIG_TDX_SEPT_VE_DISABLE` so unexpected EPT violations halt rather than invoking `#VE` [511, 532]).
Second, *`Restricted Injection` and `SVSM` `Alternate Injection`* (`#56421` and `alternate-injection.md` [526, 531]): enabling `SNP_POLICY_RESTRICTED_INJ` forbids the hypervisor in silicon from injecting *any* vector `0..255` through `EVENTINJ` except a single `#HV` (`vector 28`) doorbell notification! Paired with `COCONUT-SVSM`'s `Alternate Injection` protocol [526], `#HV` traps exclusively into trusted `VMPL0`, which sweeps a 256-bit pending-interrupt descriptor on the doorbell page and delivers *only* architecturally valid external device/timer vectors (`32..255`, never `0..31` exceptions or `0x80` syscall traps unless explicitly valid!) into `VMPL1`, structurally killing both `WeSee` and `Heckler` [48, 517, 526]! (Meanwhile, `AMD-SB-3005` microcode blocks non-coherent `INVD` against `SEV` guests, enforced remotely via `VCEK` `TCB_VERSION` attestation floors [519, 524].)
Third, *Launch-Measured `CPUID` Pages and MSR Allowlists*: `SEV-SNP` validates `CPUID` leaves against silicon rules inside a launch-measured `PAGE_TYPE_CPUID` page (`SNP_LAUNCH_UPDATE` [520]), while Linux's `#VC`/`#VE` handlers filter `RDMSR` responses and disable `IA32_EMULATION` where unneeded [516, 517].
Fourth, *Confidential Device Filtering (`AUTHORIZED_DEFAULT = 0`) and `SWIOTLB` Clamping* [518, 530]: because a malicious VMM can hotplug emulated 1990s SoundBlaster, floppy, or malformed USB/PCI IDs to fuzz unhardened C drivers inside guest Ring 0, Linux sets `authorized_default = 0` across PCI/ACPI buses in Confidential VMs (`arch/x86/coco/` [518]), admitting *only* explicitly audited `virtio` drivers (`VIRTIO_F_ACCESS_PLATFORM` forcing all DMA through `C = 0` `SWIOTLB` bounce copies where ring descriptor `len` fields are strictly bounds-checked before `memcpy` into private `C = 1` kernel RAM [516, 530]) and `SPDM`-attested `NVIDIA` GPUs [86, 529].

## Distro, Immutable-OS, & Cloud Trade-Offs

Mainline `Linux 6.8+` / `6.12+` ships `AMD SEV-SNP` guest + `SVSM` `vTPM` drivers (`tpm_svsm`), `Intel TDX` guest (`tdx-guest`), and `SWIOTLB` / confidential PCI hardening across `Ubuntu 24.04 LTS`, `RHEL 9.4+`, `SUSE SLES 15 SP6+`, and `Fedora` [11, 516]. Across public clouds (`AWS EC2` `M6a`/`C6a`/`R6a` `SEV-SNP`, `Google Cloud` `N2D`/`C3D` `SEV-SNP` and `C3` `TDX` + `A3` `H100`, and `Microsoft Azure` `DCasv5`/`ECasv5` `SEV-SNP` and `DCesv6` `TDX` using `OpenHCL` [86, 527]), two operational rules are non-negotiable. First, *never boot a Confidential VM from an unmeasured mutable `/boot` filesystem*: if `OVMF` loads an unsigned `/boot/vmlinuz` and `/boot/initramfs.img` off an untrusted host `virtio-blk` disk without verifying them against launch-measured hashes or Secure Boot + `PCR[11]`, the host hypervisor simply edits `initramfs` offline before boot and runs its own backdoor *inside* your encrypted VM! Production Confidential Linux VMs must boot a launch-measured `OVMF` + `Unified Kernel Image` (`UKI`, [Chapter 2](02-uki-systemd-pcrlock.md) [8]) pinning a `dm-verity` `roothash=` for `/usr` ([Chapter 3](03-luks2-verity.md)), unsealing persistent `LUKS2` volumes strictly after `COCONUT-SVSM` `vTPM` `PCR[11]` or remote quote verification succeeds [8, 11, 526]. Second, standard transparent hypervisor live migration is intentionally disabled on `SEV-SNP` and `TDX` (since exporting plaintext RAM to a host daemon would break the TCB), requiring attested intra-TEE migration helpers when workload mobility is needed [511, 520].

## Seam Failures, CVEs, & Structural Bounds

Every major Confidential VM break from 2018 through 2026 reinforces one architectural law: when silicon memory-ownership tables (`RMP`, `PAMT`, `GPT`) hold firm, attackers pivot to hypervisor exception/interrupt seams, microcode cache coherency, unhardened `virtio` rings, or physical DDR interposers.

| Incident / CVE | Year | Subsystem | Broken Assumption | Exploit Mechanism | Architectural Fix |
|---|---|---|---|---|---|
| `SEVered` & `SEVurity` | 2018-2020 | Gen-1 `AMD SEV` / `SEV-ES` (`NPT` & `AES-XEX`) | Memory encryption without GPA-to-SPA integrity protects guest RAM | Host remaps `NPT` pages onto `virtio-net` TX buffers (`SEVered`) or XORs `XEX` tweaks (`SEVurity`) | Deploy `SEV-SNP` `RMP` + `PVALIDATE` or `Intel TDX` `PAMT` + `S-EPT` + SHA-3 ECC MACs [511, 512, 513, 522] |
| `Cipherleaks` (`CVE-2021-26333`) | 2021 | Deterministic TEE memory cipher + `NPT` faults | Encrypted DRAM hides intra-cacheline write patterns across `VMEXIT`s | Host page-steps guest via `NPT` faults and observes deterministic ciphertext changes in OpenSSL `ECDSA` | Constant-time/randomized crypto blinding + `EPYC Turin` / `TDX` ciphertext-hiding modes [511, 514, 520] |
| `CacheWarp` (`CVE-2023-20592` / `AMD-SB-3005`) | 2023-2024 | CPU `INVD` microcode on `SEV-ES` / `SEV-SNP` | Hypervisor cannot discard uncommitted dirty guest L1/L2 cache lines | Host executes `INVD` to drop guest stack/auth stores before DRAM writeback, escalating in `sshd`/`sudo` | Apply `AMD-SB-3005` microcode and enforce minimum `TCB_VERSION` SPLs in `VCEK` attestation [519, 524] |

Whole-node Confidential VMs cleanly exclude the cloud IaaS hypervisor from guest memory; yet modern production teams rarely deploy one static application per VM. They deploy microservices and AI inference engines onto shared *Kubernetes clusters*, where a compromised or cloud-managed worker-node `kubelet` and `containerd` run *inside* the decrypted node OS and can `kubectl exec` into every pod! Shrinking the hardware `SEV-SNP`/`TDX` enclave down to an *individual Kubernetes Pod* and locking out the untrusted `kubelet` via `agent-policy.rego` and `Trustee` is the architecture of [Chapter 19](19-confidential-containers.md).

## Inspecting on a Live Linux Host

Detect whether the running Linux kernel is executing inside a hardware Confidential VM (`sev-snp`, `tdx`, or `arm-cca`) and inspect active memory-encryption and `SVSM` boot indicators:

```bash
systemd-detect-virt --cvm 2>/dev/null || echo "Not running inside a Confidential VM"
# Reading early kernel confidential-computing messages may require root / run0 if dmesg_restrict=1
dmesg 2>/dev/null | grep -iE "(Memory Encryption|SEV-SNP|TDX|SVSM|Restricted Injection|SWIOTLB)" | head -n 10 || true
```

Check for hardware attestation quote character devices (`/dev/sev-guest`, `/dev/tdx_guest`) and `COCONUT-SVSM` / paravisor `TPM 2.0` resource manager (`/dev/tpmrm0`):

```bash
ls -la /dev/sev-guest /dev/tdx_guest /dev/tpmrm0 /sys/devices/platform/tpm_svsm* 2>/dev/null || true
```

Verify Confidential Computing kernel build options (`CONFIG_AMD_MEM_ENCRYPT`, `CONFIG_INTEL_TDX_GUEST`, `CONFIG_TCG_TPM_SVSM`, and PCI `AUTHORIZED_DEFAULT` device security):

```bash
grep -E "CONFIG_(AMD_MEM_ENCRYPT|INTEL_TDX_GUEST|TCG_TPM_SVSM|COCO_SECRET)=" /boot/config-$(uname -r) 2>/dev/null || true
cat /sys/bus/pci/drivers_autoprobe /sys/bus/usb/devices/usb1/authorized_default 2>/dev/null || true
```

Inspect active `SWIOTLB` bounce-buffer allocation in `/proc/meminfo` or sysfs (`Bounce` / `swiotlb` slabs used to isolate untrusted `virtio` DMA from private `C = 1` pages):

```bash
grep -i "Bounce" /proc/meminfo 2>/dev/null || true
```
